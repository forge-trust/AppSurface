# AppSurface evidence gate policy and producer matrix

This is the implementation inventory for [issue #777](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). A selected profile may become a required claim only after every producer, resource, assertion, artifact slot, deadline, and cleanup action in its row has an explicit registration and a passing failure-path proof. Existing workflow success is not an EvidenceHost producer result. The reference gate remains non-required until the [rollout pilot](evidence-gate-rollout.md) proves current-head association and strict freshness.

The existing [build workflow](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml), [package gate](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/package-gate.yml), and [release checks](https://github.com/forge-trust/AppSurface/tree/main/.github/workflows) remain independently necessary. No job is removed with #777. During the pilot, record each existing job's assertion overlap, outcome, and added runtime. A later migration can assign steady-state ownership only after equivalent success and failure behavior is observed and separately reviewed.

The [Release Publish workflow](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/release-publish.yml) now rejects non-`main` dispatches when this protected workflow version runs. It checks that the workflow file ref is the expected `main` workflow and that the checkout running release tooling equals that workflow commit, with checkout credentials disabled. It also requires a configured `release-publish` environment with an independent reviewer, no administrator bypass, and exactly one custom deployment branch policy for `main`; all `contents: write` jobs reference it. The [Release publish guide](../tools/ForgeTrust.AppSurface.Release/README.md#publish) explains the ordering and administrator setup. A branch-edited workflow cannot be authenticated by checks inside itself, so administrator-controlled workflow policy remains necessary for publication. This closes a prerequisite for a trusted release invocation; the EvidenceGate release row remains blocked because its production invocation provider, final remote-tag reread, and exact built package/archive digest binding are still absent.

The AppSurface-specific policy must put unknown paths and mixed changes into a conservative profile containing the union of every targeted PR obligation. The [planner](../Evidence/ForgeTrust.AppSurface.Evidence.Planner/README.md) validates this property before a trusted gate run. Release-preparation PRs use a targeted PR profile; only the protected release invocation may select `ReleaseComplete` from the validated V2 preparation-base/tag diff. A missing safe producer keeps its profile fail-closed and prevents ruleset activation; deleting its obligation to get a green check is not a valid fallback.

The policy uses the same conservative union for package project and lock files inside the PostgreSQL and Keycloak resource trees. Those paths change both dependency supply and an integration surface; the more specific project/lock rules carry explicit precedence so the resource rule cannot silently drop the package obligation. Non-.NET executable assets without a dedicated producer also select the conservative profile and remain incomplete.

The [checked-in policy](https://github.com/forge-trust/AppSurface/blob/main/.appsurface/evidence/evidence.policy.json) also maps the gate runner, release and package tooling, workflows, gate documentation, and [shadow fixtures](fixtures/issue-777-policy-shadow/README.md) explicitly to the conservative control-plane profile. These files can change the authority or evidence inventory itself, so a narrow package-only or documentation-only selection would be insufficient. The [non-claiming shadow comparison](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-evidence-shadow-policy) checks the proposed selection against base-owned fixture cases. Its workflow wiring is currently present only on the implementation branch; protected-base authority requires merge and a live smoke run.

Resource provisioning belongs to the base-owned supervisor, with only declared service endpoints exposed to the credentialless subject VM. Restore, build hooks, and all head-controlled execution stay in that VM with pinned SDK/OCI images and locked dependencies. Exact per-profile deadlines and an overall workflow budget will be fixed from the cold-cache pilot before the check becomes required. The trusted verifier checks the current PR base/head or protected tag after the subject result, so an earlier successful producer cannot authorize a changed revision.

For the fixed `code-coverage` subject, the [host launcher](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject.py) now emits a bounded OCI `envelopeReceipt` only after checking the local image, live scratch tmpfs, and Podman isolation configuration and receiving supervisor cleanup. Its fields distinguish settings checked in Podman inspect from a live scratch-quota check; configured cgroup limits are not proof of effective enforcement. The [handoff verifier](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-handoff.py) binds it to the current run and the digest selected by trusted image preflight. This cross-job consistency check does not authenticate the actual consumed checkout or make an incomplete producer claim complete; the code/coverage row remains blocked pending those independent proofs and the missing service envelope.

After the fresh Git recapture and bounded artifact transfer, the [trusted verifier workflow](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate.yml) also reruns the existing [coverage gate](https://github.com/forge-trust/AppSurface/blob/main/Cli/ForgeTrust.AppSurface.Cli/CoverageGate.cs) on the downloaded Cobertura XML and the freshly captured source diff. The verifier uses an empty `/subject` directory only to normalize the fixed entrypoint's absolute Cobertura paths; it never executes files from that tree. This catches a subject report whose transferred coverage data fails the base-owned threshold calculation. The fixed replay thresholds must change with the trusted `code-coverage` policy declaration. Replaying subject-supplied XML cannot prove that tests ran or that its hit counts are truthful, so this step remains non-claiming until an independent subject measurement and producer registration are available.

The verifier also emits a [bounded subject observation](../tools/ForgeTrust.AppSurface.EvidenceGate/README.md#trusted-subject-observation) after the handoff, cleanup, replay, and attempt-specific job checks. Its hashes identify the downloaded bytes that passed these checks and prepare an authenticated verifier handoff. `claimEligible: false` is fixed; this artifact does not supply the missing checkout, effective isolation, or producer proof and does not change any row's promotion state.
