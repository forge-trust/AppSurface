# AppSurface evidence gate rollout record

This runbook tracks the live proof required by [issue #777](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). The [policy matrix](evidence-gate-policy-matrix.md) identifies which profile obligations have safe first-party producers. A successful local plan, manifest, or shadow check is not proof that GitHub associates a base-owned check with the PR's current head.

## Current state

The active `Default` ruleset (GitHub ruleset ID `7295365`) has no required status-check rule as of 2026-10-01. Existing [build](../.github/workflows/build.yml) and [package gate](../.github/workflows/package-gate.yml) workflows remain active. The #777 implementation branch is a self-change PR candidate: its new `pull_request_target` controller cannot become the base-owned authority until that code reaches the default branch. The [branch-owned shadow workflow](../.github/workflows/evidence-gate-shadow.yml) validates contracts with a distinct, non-claiming name. The [base-owned event pilot](../.github/workflows/evidence-gate.yml) now has a bounded subject snapshot handoff and a trusted verifier rehearsal, but its final step still intentionally fails with `ASEGH003`; it can probe `pull_request_target` event/check association after reaching the base branch, but cannot satisfy a required evidence gate or issue a manifest claim. Keep it non-required until the subject image and offline dependencies, isolation attestation, complete subject-result and producer verification, and all selected producer registrations have been proved.

This ordering requires a staged rollout. First, validate and merge the implementation while the evidence check remains non-required; the branch-owned shadow cannot certify its own proposed controller. Next, run the base-owned live pilot from `main` and record the outcomes below. Only then may an administrator add the observed verifier context to the ruleset. A draft implementation PR cannot itself supply the base-owned pilot evidence or safely activate its own required check.

The [GitHub Actions job API](https://docs.github.com/en/rest/actions/workflow-jobs) reports run and job metadata but has no independent measurement of the worktree a job actually consumed. For [`pull_request_target`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target), run `head_sha` can identify the base-side workflow commit even when a trusted step explicitly supplies a PR head. The implementation therefore cannot infer checkout provenance from API `head_sha`; its production authority provider leaves the subject checkout unknown. An explicit empty profile needs no subject checkout, but any nonempty profile remains ineligible until the approved trusted handoff and isolation checks are implemented. The controller-owned source snapshot and any [GitHub artifact attestation](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds) can authenticate the handed-off bytes, but the base-owned workflow and runner still have to guarantee that the subject job consumes those bytes.

The [approved implementation plan](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md) selects a base-owned handoff across separate ephemeral GitHub-hosted jobs. The [workflow](../.github/workflows/evidence-gate.yml) uses the trusted base checkout to resolve the exact captured base/head diff and checked-in policy into a v2 plan. The [handoff implementation](../scripts/evidence-gate-handoff.py) inventories the exact head tree, rejects Git archive substitutions or omissions, and transports a bounded snapshot and selected plan in a [same-run artifact](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts). The credentialless subject job validates that bundle and can invoke the fixed OCI launcher only when a digest-pinned image is supplied; its result is always non-claiming. The trusted verifier independently recaptures current PR revisions, checks the downloaded handoff's identity, diff, archive blobs, and file modes against the fresh Git tree, checks that the bounded subject result reports a successful execution for the same run, revision, profile, and snapshot, resolves the unique successful subject job from the attempt-specific GitHub APIs through the [verifier-context resolver](../scripts/evidence-gate-verifier-context.py), recomputes a host manifest, and runs `verify-gate`. This can rehearse the empty documentation profile; it does not authenticate a nonempty subject checkout, isolation envelope, or producer artifact bytes. The final workflow step remains non-claiming and fails every run.

For same-repository PRs, the controller now invokes the [bounded policy-shadow preparer](../scripts/evidence-gate-policy-shadow.py) after capturing the exact head. It reads only the candidate policy and fixture blobs at that Git object ID, then passes them as data to the [base-owned shadow command](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-evidence-shadow-policy) alongside the protected policy and fixtures. A missing candidate policy, unsafe Git mode, or incompatible comparison fails before handoff creation; deleted candidate fixtures remain absent so the old fixture obligations cannot be replaced by the PR. This wiring is branch-owned until merged into the protected base and exercised in a live pilot. The shadow result remains nonclaiming and does not supply producer, isolation, or current-head evidence.

Do not add a required check until the pilot below has observed the exact check name, app identity, commit association, and base-update freshness behavior. No row below is a claimed pass until it has a run URL, captured base/head IDs, and an observed outcome.

## Activation and rollback

After all positive and negative pilot rows pass, identify the stable verifier job's exact status-check context and GitHub App/integration identity from a live PR. Add only that context to the active default-branch ruleset with strict required-check freshness. Verify a qualifying same-repository PR can merge and an incomplete or fork-observation PR cannot. Keep existing checks required or advisory according to their current separate policy; #777 does not remove them.

If the check attaches to a merge ref rather than the PR's current head, the event is unavailable under repository policy, an external resource escapes the ephemeral VM, or dependency supply cannot remain isolated, stop before activation. Fix the base-owned workflow and rerun the affected pilot. If an activated gate later produces an incorrect green or blocks safe changes, remove the new required-status-check rule while preserving the workflow and evidence artifacts for diagnosis. A rollback of enforcement does not turn an invalid manifest into a valid one.

When a merge queue is introduced, add and pilot `merge_group` handling before requiring the check in that queue. The checked-in [gate design](designs/issue-777-policy-driven-ci-evidence-gate.md) remains the source for trust and isolation requirements; this record holds observed rollout evidence only.
