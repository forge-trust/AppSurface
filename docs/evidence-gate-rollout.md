# AppSurface evidence gate rollout record

This runbook tracks the live proof required by [issue #777](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). The [policy matrix](evidence-gate-policy-matrix.md) identifies which profile obligations have safe first-party producers. A successful local plan, manifest, or shadow check is not proof that GitHub associates a base-owned check with the PR's current head.

## Current state

The active `Default` ruleset (GitHub ruleset ID `7295365`) has no required status-check rule as of 2026-10-01. Its 2026-10-02 API response also permits `OrganizationAdmin` bypass and neither dismisses stale reviews nor requires approval after the last push. The [protected-main image publisher](../scripts/evidence-gate-subject-image/README.md#protected-main-publisher-future-non-claiming) now rejects those settings; the repository administrator must remove the bypass and require a fresh review of the final PR revision before that publisher can run. Existing [build](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml) and [package gate](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/package-gate.yml) workflows remain active. The #777 implementation branch is a self-change PR candidate: its new `pull_request_target` controller cannot become the base-owned authority until that code reaches the default branch. The [branch-owned shadow workflow](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate-shadow.yml) validates contracts with a distinct, non-claiming name. The [base-owned event pilot](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate.yml) now has a bounded subject snapshot handoff and a trusted verifier rehearsal, but its final step still intentionally fails with `ASEGH003`; it can probe `pull_request_target` event/check association after reaching the base branch, but cannot satisfy a required evidence gate or issue a manifest claim. Keep it non-required until the subject image and offline dependencies, isolation attestation, complete subject-result and producer verification, and all selected producer registrations have been proved.

The publisher also needs the environment-scoped [ruleset-inspection credential](../scripts/evidence-gate-subject-image/README.md#protected-main-publisher-future-non-claiming). Its read-only workflow token cannot see bypass actors in GitHub's ruleset API, so a missing credential leaves publication blocked even after the ruleset settings are corrected.

This ordering requires a staged rollout. First, validate and merge the implementation while the evidence check remains non-required; the branch-owned shadow cannot certify its own proposed controller. Next, run the base-owned live pilot from `main` and record the outcomes below. Only then may an administrator add the observed verifier context to the ruleset. A draft implementation PR cannot itself supply the base-owned pilot evidence or safely activate its own required check.

The [GitHub Actions job API](https://docs.github.com/en/rest/actions/workflow-jobs) reports run and job metadata but has no independent measurement of the worktree a job actually consumed. For [`pull_request_target`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target), run `head_sha` can identify the base-side workflow commit even when a trusted step explicitly supplies a PR head. The implementation therefore cannot infer checkout provenance from API `head_sha`; its production authority provider leaves the subject checkout unknown. An explicit empty profile needs no subject checkout, but any nonempty profile remains ineligible until the approved trusted handoff and isolation checks are implemented. The controller-owned source snapshot and any [GitHub artifact attestation](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds) can authenticate the handed-off bytes, but the base-owned workflow and runner still have to guarantee that the subject job consumes those bytes.

The [approved implementation plan](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md) selects a base-owned handoff across separate ephemeral GitHub-hosted jobs. The [workflow](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate.yml) uses the trusted base checkout to resolve the exact captured base/head diff and checked-in policy into a v2 plan. The [handoff implementation](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-handoff.py) inventories the exact head tree, rejects Git archive substitutions or omissions, and transports a bounded snapshot and selected plan in a [same-run artifact](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts). The credentialless subject job validates that bundle and can invoke the fixed OCI launcher only when a digest-pinned image is supplied; its result is always non-claiming. The trusted verifier independently recaptures current PR revisions, checks the downloaded handoff's identity, diff, archive blobs, and file modes against the fresh Git tree, checks that the bounded subject result reports a successful execution for the same run, revision, profile, and snapshot, resolves the unique successful subject job from the attempt-specific GitHub APIs through the [verifier-context resolver](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-verifier-context.py), recomputes a host manifest, and runs `verify-gate`. This can rehearse the empty documentation profile; it does not authenticate a nonempty subject checkout, isolation envelope, or producer artifact bytes. The final workflow step remains non-claiming and fails every run.

For `code-coverage`, the controller exports only the bounded profile ID after planning. A separate trusted job requires `EVIDENCE_GATE_SUBJECT_IMAGE_DIGEST` to name `ghcr.io/forge-trust/appsurface-subject-native-validation@sha256:<64 lowercase hex digits>`, checks its GitHub artifact attestation against this repository, the protected-main publisher workflow, and `refs/heads/main`, and passes the same digest to the subject job. The subject job keeps `permissions: {}` and pulls that digest with an explicitly empty registry auth file before the launcher enforces its local `RepoDigest` check. A missing image variable, invalid provenance, private package, or failed anonymous pull leaves the pilot failed. The separate `EVIDENCE_GATE_SUBJECT_IMAGE` variable names the publisher's package without a digest. This branch-owned workflow wiring has no published protected-base image to use yet and remains non-claiming; a verified image does not establish subject checkout, isolation, cleanup, or producer evidence. The [subject image guide](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject-image/README.md) describes publication and the first-package visibility step.

For `code-coverage`, the subject result carries the bounded [fixed entrypoint record](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject-entrypoint.py) in a versioned `executionReceipt`. The launcher and verifier require the five declared step names in order, with zero exit codes, and bind the record to the captured base/head revisions, workflow run and attempt, profile, and snapshot digest. A completed record also requires an ordered, bounded SHA-256 index for the generated Cobertura XML, gate Markdown, and gate JSON; failed records cannot include it. Gate JSON is required by this fixed profile even though the policy's diagnostics slot is optional. The [independent cleanup supervisor](evidence-gate-subject-supervisor.md) has a separate private state directory and a bounded non-claiming attestation; the subject job waits for complete cleanup and uploads that record on the coverage path. The trusted verifier now requires that downloaded attempt-scoped record to be canonical, bounded, and complete before host verification; the empty documentation profile must have no cleanup artifact. The receipt's canonical SHA-256 is a self-consistency check only: an artifact editor can recompute it, so neither the receipt nor cleanup-record validation authenticates execution, the consumed checkout, isolation, or producer artifact bytes. The indexed files are still discarded with container scratch and must be transferred and checked independently before any producer claim. Keep the EvidenceGate host and workflow non-claiming.

The fixed subject profile now receives the controller's captured `source.diff` through a separate read-only mount. The launcher compares its bytes with the handoff SHA-256 before creating the container, verifies the mount in OCI inspection, and passes the expected digest to the entrypoint, which checks the mounted file again before running aggregate and patch coverage. The patch gate uses 95% lines, 85% branches, and `codecov` line mode, matching the repository's [coverage gate](https://github.com/forge-trust/AppSurface/blob/main/scripts/coverage-solution.sh). This closes the missing patch-input path only; the current solution's container-backed test projects still cause the offline entrypoint to fail before coverage execution, and no complete producer artifact or checkout/isolation attestation is yet available.

For same-repository PRs, the controller now invokes the [bounded policy-shadow preparer](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-policy-shadow.py) after capturing the exact head. It reads only the candidate policy and fixture blobs at that Git object ID, then passes them as data to the [base-owned shadow command](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-evidence-shadow-policy) alongside the protected policy and fixtures. A missing candidate policy, unsafe Git mode, or incompatible comparison fails before handoff creation; deleted candidate fixtures remain absent so the old fixture obligations cannot be replaced by the PR. This wiring is branch-owned until merged into the protected base and exercised in a live pilot. The shadow result remains nonclaiming and does not supply producer, isolation, or current-head evidence.

Do not add a required check until the pilot below has observed the exact check name, app identity, commit association, and base-update freshness behavior. No row below is a claimed pass until it has a run URL, captured base/head IDs, and an observed outcome.

## Activation and rollback

After all positive and negative pilot rows pass, identify the stable verifier job's exact status-check context and GitHub App/integration identity from a live PR. Add only that context to the active default-branch ruleset with strict required-check freshness. Verify a qualifying same-repository PR can merge and an incomplete or fork-observation PR cannot. Keep existing checks required or advisory according to their current separate policy; #777 does not remove them.

If the check attaches to a merge ref rather than the PR's current head, the event is unavailable under repository policy, an external resource escapes the ephemeral VM, or dependency supply cannot remain isolated, stop before activation. Fix the base-owned workflow and rerun the affected pilot. If an activated gate later produces an incorrect green or blocks safe changes, remove the new required-status-check rule while preserving the workflow and evidence artifacts for diagnosis. A rollback of enforcement does not turn an invalid manifest into a valid one.

When a merge queue is introduced, add and pilot `merge_group` handling before requiring the check in that queue. The checked-in [gate design](designs/issue-777-policy-driven-ci-evidence-gate.md) remains the source for trust and isolation requirements; this record holds observed rollout evidence only.
