# AppSurface evidence gate rollout record

This runbook tracks the live proof required by [issue #777](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). The [policy matrix](evidence-gate-policy-matrix.md) identifies which profile obligations have safe first-party producers. A successful local plan, manifest, or shadow check is not proof that GitHub associates a base-owned check with the PR's current head.

## Current state

The active `Default` ruleset (GitHub ruleset ID `7295365`) has no required status-check rule as of 2026-10-01. Existing [build](../.github/workflows/build.yml) and [package gate](../.github/workflows/package-gate.yml) workflows remain active. The #777 implementation branch is a self-change PR candidate: its new `pull_request_target` controller cannot become the base-owned authority until that code reaches the default branch. The [branch-owned shadow workflow](../.github/workflows/evidence-gate-shadow.yml) validates contracts with a distinct, non-claiming name. The [base-owned event pilot](../.github/workflows/evidence-gate.yml) also has a distinct non-claiming name and intentionally fails with `ASEGH003`; it can probe `pull_request_target` event/check association after reaching the base branch, but cannot satisfy a required evidence gate or issue a manifest claim. Keep it non-required and replace it only after the trusted verifier, isolated subject handoff, and all selected producer registrations have been proved.

This ordering requires a staged rollout. First, validate and merge the implementation while the evidence check remains non-required; the branch-owned shadow cannot certify its own proposed controller. Next, run the base-owned live pilot from `main` and record the outcomes below. Only then may an administrator add the observed verifier context to the ruleset. A draft implementation PR cannot itself supply the base-owned pilot evidence or safely activate its own required check.

The [GitHub Actions job API](https://docs.github.com/en/rest/actions/workflow-jobs) reports run and job metadata but has no independent measurement of the worktree a job actually consumed. For [`pull_request_target`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target), run `head_sha` can identify the base-side workflow commit even when a trusted step explicitly supplies a PR head. The implementation therefore cannot infer checkout provenance from API `head_sha`; its production authority provider returns ineligible until the approved trusted handoff and isolation checks are implemented. The controller-owned source snapshot and any [GitHub artifact attestation](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds) can authenticate the handed-off bytes, but the base-owned workflow and runner still have to guarantee that the subject job consumes those bytes.

The [approved implementation plan](plans/issue-777-policy-driven-ci-evidence-gate-implementation.md) selects a base-owned handoff across separate ephemeral GitHub-hosted jobs. The pinned workflow creates or checks an exact head snapshot, sends it through a bounded [same-run artifact](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts), verifies the snapshot hash and container configuration before subject execution, and has the trusted verifier independently recheck those bytes, the run/job association, and the current PR revisions. This relies on the base-owned workflow and hosted runner to execute the fixed checkout and mount steps; it does not claim a hardware-measured checkout. A separate measured-attestor service would be a stronger future design, but it is outside this reference path. The approved handoff is not yet implemented, so no complete claim is authorized.

Do not add a required check until the pilot below has observed the exact check name, app identity, commit association, and base-update freshness behavior. No row below is a claimed pass until it has a run URL, captured base/head IDs, and an observed outcome.

## Local pre-pilot validation

On the issue #777 implementation branch, the frozen [docs-only fixture](fixtures/issue-777-docs-only/README.md) passed the copyable `explain` → host `run` → local `verify` rehearsal with `--no-restore`. The explained and hosted plans had the same digest (`a935646d382eb5dde80ff23161d499bfdf5506d13236354429dcd751bd2e2a54`); the local manifest reported `NoEvidenceRequired` with `PullRequestGate` eligibility. This is a contract rehearsal, not the trusted GitHub PR verdict or a live pilot row.

Focused local checks also passed for the controller, subject launcher, and fixed offline entrypoint (47 Python tests), the host/verifier tool (19 tests), the CLI Evidence path (179 tests), the Aspire host bootstrap (28 tests), and the read-only release inspect suite (630 tests). A full `./scripts/coverage-solution.sh` run completed all 55 projects and measured 94.54% overall line and 87.97% branch coverage, but exited 1: one RazorWire browser test observed scrolling before its smooth-scroll animation finished, and four Durable AdoptionMetrics Git-process tests timed out inside the local sandbox. The four process tests then passed unchanged when rerun outside that sandbox. The browser test now waits for the actual scroll position and both affected focused tests passed outside the sandbox. These checks do not replace a successful run of the full script or establish patch coverage for the currently uncommitted implementation. Keep the [coverage gate](../scripts/coverage-solution.sh) open until a fresh exact run passes on the final committed code.

Five solution projects that appeared to lack default `packages.lock.json` files instead use the tracked `packages.osx-arm64.lock.json` and `packages.linux-x64.lock.json` variants selected by `NuGetLockFilePath`. All ten existing lock files passed full-graph locked-mode restore with isolated temporary caches. No new lock files are needed for those projects. This verifies the lock graphs; it does not provide the reviewed offline NuGet package feed or pinned subject image required by the isolated CI producer.

## Activation and rollback

After all positive and negative pilot rows pass, identify the stable verifier job's exact status-check context and GitHub App/integration identity from a live PR. Add only that context to the active default-branch ruleset with strict required-check freshness. Verify a qualifying same-repository PR can merge and an incomplete or fork-observation PR cannot. Keep existing checks required or advisory according to their current separate policy; #777 does not remove them.

If the check attaches to a merge ref rather than the PR's current head, the event is unavailable under repository policy, an external resource escapes the ephemeral VM, or dependency supply cannot remain isolated, stop before activation. Fix the base-owned workflow and rerun the affected pilot. If an activated gate later produces an incorrect green or blocks safe changes, remove the new required-status-check rule while preserving the workflow and evidence artifacts for diagnosis. A rollback of enforcement does not turn an invalid manifest into a valid one.

When a merge queue is introduced, add and pilot `merge_group` handling before requiring the check in that queue. The checked-in [gate design](designs/issue-777-policy-driven-ci-evidence-gate.md) remains the source for trust and isolation requirements; this record holds observed rollout evidence only.
