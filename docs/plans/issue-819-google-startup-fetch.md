## Problem and decision

The mapped [Google Secret Manager provider](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerConfigProvider.cs) exposes synchronous configuration resolution and calls a synchronous Google client. On a cache miss, it currently queues `Fetch` with `Task.Run` and blocks the resolving caller on the task. A cold startup therefore needs a second thread to do each winning synchronous lookup. There is no recorded production startup or thread-pool baseline, so this design does not promise a measured speedup.

Use a **provider-local, resource-keyed flight holder**. Publish a waitable holder before starting the remote call. The winning ordinary request without a cancellable token executes the bounded synchronous `Fetch` on its initiating thread. A winning audit request or ordinary request with a cancellable token schedules the fetch so its caller can stop waiting promptly. Requests joining a flight share its outcome and retain their own cancellation semantics. No public async provider/client API or refresh behavior is added.

The user selected prompt cancellation for token-bearing ordinary reads and accepted the precise owner-based inline promise. A startup caller joining a flight already started by an audit or cancellable caller may wait for that worker-owned flight. It must not start a second lookup merely to force inline execution.

## Current contracts and evidence

- `IConfigProvider.Resolve<T>` and `IAppSurfaceGoogleSecretManagerClient.AccessSecretVersion` are synchronous. The [Google adapter](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerClientAdapter.cs) passes the configured lookup timeout to the SDK call.
- [The provider](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerConfigProvider.cs) currently stores `Lazy<Task<PayloadResult>>` by ordinal-exact version resource. `GetPayload` waits with the request token; `Fetch` owns response-name validation, resource claims, cache publication, and value-safe failure mapping.
- [The scope](../../Config/ForgeTrust.AppSurface.Config/ConfigProviderRequest.cs) owns one aggregate audit deadline, remote-lookup budget, and concurrency semaphore. Its present lease is released when the *caller* stops waiting, even if the queued synchronous fetch is still active. A scope whose deadline or caller token has cancelled rejects further lookup reservations, so an expired scope cannot schedule a new worker after releasing a lease.
- The [provider reference](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/README.md) promises one shared fetch for concurrent misses, isolated waiter cancellation, failure eviction, exact resolved-version provenance, cache-generation-safe eviction, and incomplete audit diagnostics.
- Existing [concurrency tests](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager.Tests/GoogleSecretManagerConcurrencyContractTests.cs) exercise claims, cache identity, cancellation, and retry; [provider tests](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager.Tests/GoogleSecretManagerConfigProviderTests.cs) exercise audit deadlines. They need owner-thread and mixed-winner cases for this change.
- The file-declared `Secret<T>` path already calls the synchronous client directly with a remaining-time budget. It does not use the mapped provider's flight dictionary and is outside this scheduling change.

Microsoft documents that wrapping synchronous work in `Task.Run` moves blocking to another thread and adds scheduling overhead; it does not make I/O asynchronous. It also documents that `ConcurrentDictionary.GetOrAdd` may run a value factory more than once. Those are design constraints, not a performance measurement: [async wrapper guidance](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/async-wrappers-for-synchronous-methods), [dictionary contract](https://learn.microsoft.com/en-us/dotnet/api/system.collections.concurrent.concurrentdictionary-2.getoradd?view=net-10.0). Cancelling a wait need not cancel the underlying operation: [cancellation guidance](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/cancel-non-cancelable-async-operations).

## Premises

1. Startup resolves explicit, immutable version resources; updated values are adopted on restart. Runtime refresh and new version selection remain outside #819.
2. A no-token ordinary caller that **wins a new flight** must perform the synchronous client call itself. A joiner follows the existing flight's execution mode.
3. A caller with an explicitly cancellable token, or an audit deadline, may stop waiting while a shared remote call continues. The synchronous client seam cannot preempt that call; its own configured timeout bounds it.
4. Per-resource sharing, exact-version identity, cache-generation ownership, terminal diagnostics, and audit incomplete-coverage semantics take priority over a stronger “every startup caller executes inline” claim.
5. Performance claims require the same repeatable workload on the baseline and changed revisions. A structural thread reduction is an expectation to test, not a measured result.

## Independent review

A fresh-context `combo/sub` review supported an owner-owned flight holder and identified the winner-order race: a cancellable caller may publish a worker-owned flight just before a no-token startup caller joins it, or the startup caller may publish an inline flight before an audit joins. Both orders need deterministic tests. The review proposed an internal async Google client as a longer-term ideal; that changes the client seam and falls outside the issue's explicit synchronous-contract boundary.

## Approaches considered

### A. Provider-local flight holder (selected)

Replace the `Lazy<Task<PayloadResult>>` dictionary value with a small holder containing a completion source configured with `RunContinuationsAsynchronously`. Constructing a candidate has no side effects. The winner publishes the holder, then starts `Fetch` inline or schedules it according to that winner's request. Joiners wait on the published completion with their own token. Completion removes only the matching holder, so a late cleanup cannot evict a replacement flight.

Effort: M, roughly 1–2 human days / 2–4 CC hours. Risk: medium, concentrated in publication and cleanup ordering. This reuses `Fetch`, the current cache and claim logic, and existing test seams. It keeps the change local to the provider, but mixed-caller races and background-work lifetime require explicit proof.

### B. Separate internal flight coordinator

Move publication, winner selection, completion, and exact-entry cleanup to an internal type; keep provider-specific `Fetch`, conversion, cache, and diagnostics in the provider. Effort: L, roughly 2–3 human days / 4–6 CC hours. Risk: medium. Ownership would be clearer if other synchronous secret paths later needed sharing, but it adds an abstraction and test surface without an adopter in #819. The user chose A for this scoped follow-up.

### Deferred: Internal asynchronous Google client operation

The Google SDK offers async access, but introducing an internal async seam while keeping the public synchronous client contract would create two execution paths or a compatibility adapter. This deserves a separate design if measured startup latency or cancellation requirements justify changing the client boundary.

## Selected behavior and ordering

1. Run the existing cancellation check, reference/claim validation, and warm-cache check in their current order. Keep cache keys and flight keys as ordinal-exact full version resources. Do not put network work in `ConcurrentDictionary.GetOrAdd`'s factory.
2. Obtain a candidate holder, atomically publish or join by resource, and identify the actual published winner by reference identity. A joiner must never start work. If it observes a completed holder left in the dictionary, compare-remove that exact holder and retry; this prevents a later uncached read from reusing an old result while preserving a replacement generation.
3. The winning no-token, non-audit caller executes `Fetch` inline and completes the holder in a `finally`-safe path. Its own `Resolve` returns the same result. An audit or explicitly cancellable winner schedules `Fetch` and waits with its request token. All waiters use the holder's published completion, so joining an inline fetch never blocks inside a lazy initializer before applying an audit deadline.
4. Complete the holder with the existing `PayloadResult`, or with the same exception outcome if an unhandled fatal exception escapes `Fetch`; never strand waiters. Remove the exact holder after completion. Only the winner completes the holder and performs normal retirement. Any caller observing an already-completed holder may compare-remove that exact holder and retry; no caller may remove an active holder or a replacement generation. A cancelled waiter never cancels the shared fetch.
5. Preserve `Fetch`'s configured per-call timeout, diagnostic mapping, exact response-version validation, claim-poison recheck, defensive payload copies, and cache-generation comparison. The new holder must not become a cache: once the fetch completes, a later uncached read starts a new flight; a warm successful cache hit bypasses flight creation.
6. Keep the audit's configured remote-lookup count, deadline, and caller-owned concurrency lease. Schedule an audit-owned worker only after the scope grants a lease. While the aggregate deadline remains live, that lease stays with the waiting caller and bounds concurrent starts. A request admitted by a successful audit lease reservation may publish and schedule its worker after scope cancellation, and that worker may enter Fetch after the deadline; the successful reservation is the audit budget boundary. When the scope token is cancelled, its waiter can return and release the lease, but no later request in that scope can reserve a slot or queue another worker. Thus active audit-owned calls can finish after the report deadline yet cannot grow past the operation's configured maximum. An audit joining a startup-owned inline flight keeps the existing caller-side budget behavior but creates no audit worker. No new scope-lifetime API is required.
7. Scope the promise precisely: for an ordinary uncancellable winner, no `Task.Run` precedes its remote lookup and the client sees the initiating managed thread. A no-token joiner may block waiting for the winner, which is required for one fetch per resource.

### R1-1 — completeness

**Problem**

> The audit concurrency proof starts a second request in the same operation only after the first request's audit deadline has expired. Because the scope owns that deadline, the second request can return `config-audit-deadline` before reaching the client even if the first worker prematurely released its slot. The stated assertion that active audit-owned calls never exceed the limit therefore does not distinguish correct lease retention from the defect this test is meant to catch.

**Remedy**

> Revise the proof to observe that the execution lease remains held after the waiter deadline and is released only when the underlying fetch finishes, using an appropriate test seam. If the intended deadline is per request rather than scope-wide, state that contract and keep the second request's deadline live while it contends for the same slot.

### CEO Section 1 — Architecture

Current scope is SELECTIVE EXPANSION with the approved provider-local holder, #833 cleanup compatibility, deterministic tests, a value-free benchmark, and package documentation. The user-approved owner/thread and cancellation contracts remain fixed; credentialed CI, refresh, a shared coordinator, and an async client API are excluded. The only accepted expansion is the direct cleanup regression already on the implementation base.

```text
Config manager -> claim/cancellation checks -> Google mapped provider
                                      | warm cache -> typed conversion/audit provenance
                                      | cold miss -> audit lease (audit only)
                                                   -> exact-resource flight dictionary
                                                      | winner: inline Fetch OR worker Fetch
                                                      | joiners: token-aware completion wait
                                                   -> synchronous Google client -> result/diagnostic
                                                   -> holder completion -> exact-entry retirement
```

The new holder has states `candidate -> published -> running -> completed -> retired`. A candidate has no side effects; only the dictionary winner can move `published -> running` and complete it. A joiner can observe `running` or `completed`, but cannot start a fetch; compare-remove on a completed holder prevents `completed -> reused-as-cache`. A cancellation ends a wait, not the shared flight. The before/after dependency change is `Resolve -> Lazy<Task.Run(Fetch)> -> Wait` to `Resolve -> holder -> inline/worker Fetch -> completion`; it adds no new package or external service.

Happy input is a valid claimed version resource; it reaches the cache or one flight and yields the same payload/provenance as today. A missing key remains unclaimed before publication; an empty payload follows the existing UTF-8 and typed conversion behavior, with rejection evicting only its cache generation. A Google timeout/RPC failure follows the existing value-safe terminal diagnostic and retires the failed flight so a later read retries. Tenfold distinct-resource cold load blocks one caller thread per uncancellable lookup instead of adding a worker for each; hundredfold load is still bounded by caller concurrency and Google/network capacity, not made asynchronous. Google is the single external dependency. There is no new endpoint, auth boundary, data mutation, or persisted state. Rollback is a provider-change revert and package republish after focused test verification.

### CEO Section 2 — Error and rescue map

| Codepath | Trigger / exception class | Rescue and caller result | Verification |
| --- | --- | --- | --- |
| Precheck and reference resolution | Pre-cancelled ordinary token / `OperationCanceledException`; expired audit / `config-audit-deadline`; invalid claim | Ordinary cancellation propagates before claims/cache/client; audit records incomplete coverage; poisoned claim stays terminal | Existing pre-cancel/claim tests plus same-scope cancellation admission test |
| Audit reservation | Remote count or concurrency limit; deadline while waiting | `TryAcquireRemoteLookup` rejects with an incomplete-audit diagnostic; no worker starts; lease is disposed on caller exit | Live-deadline contention, count limit, post-deadline rejection |
| Flight publication | Competing candidates; completed entry; allocation failure | Only returned holder is winner; completed entry compare-removed and retried; fatal allocation propagates without a published orphan | Both winner orders, sequential uncached, #833 replacement regression |
| Winner startup/completion | `Task.Run` startup failure or unexpected fatal `Fetch` exception | Complete published holder with the exception, retire exact entry, and propagate same outcome to owner/joiners; never hang | Deterministic startup seam if feasible; fatal-conversion coverage already exists |
| `Fetch`/Google adapter | `RpcException`, `TimeoutException`, invalid resolved name, claim collision, other nonfatal exception | Existing `config-provider-failed` classification/retryability and claim collision apply; no payload in diagnostic; failed flight retires | Existing failure and provenance suite plus failed-shared-flight retry |
| Wait and conversion | `OperationCanceledException`, invalid UTF-8, typed conversion failure | Cancel only that wait; audit deadline marks incomplete; rejected conversion evicts exact cache generation, not a newer value | Owner/joiner cancel, audit timeout, generation-race test |

The existing `Fetch` catch-all maps nonfatal provider exceptions to a retryable, value-safe diagnostic. It is retained because changing diagnostic policy is outside #819, but the new holder must not swallow a fatal exception or strand waiters. No automatic retry is added inside one resolution; the documented rescue is a later request after failed-flight retirement or an operator override above the remote provider.

### CEO Section 3 — Security and threat model

No new endpoint, input parameter, credential, package, SQL, template, or secret storage is introduced. The provider still resolves only validated, claimed version resources and keeps exact ordinal claim identity; claim poisoning and `MaxAdHocClaims` prevent aliases from bypassing the existing ownership boundary. The main threat is accidental secret disclosure in benchmarking or new diagnostics (likelihood medium, impact high); mitigation is the fake client, value-free aggregate counts, and no resource names or payloads in measurement artifacts. A second threat is stale/incorrect cache publication under cancellation (likelihood medium, impact high for credentials); exact-generation eviction, holder identity, and existing provenance tests are mandatory. No new production log of payload or native resource identity is planned.

### CEO Section 4 — Data flow and interaction edges

```text
request -> parse/claim/cancel -> cache? -> audit reservation? -> flight publish/join
   | nil/missing key -> unclaimed      | empty payload -> existing conversion path
   | cancelled -> throw/mark audit     | timeout/RPC -> value-safe terminal
   | duplicate resource -> one holder  | stale completed holder -> compare-remove/retry
   | encoding failure -> exact cache-generation eviction, no value publication
```

```text
Uncancellable owner       Shared dictionary       Cancellable/audit joiner
create inert holder    ->  publish A
Fetch inline blocked       A running           <-  find A; wait on A completion
                           A running           <-  joiner token cancels; wait exits only
Fetch completes        ->  A completed
compare-remove A       ->  absent               new uncached caller publishes B
```

Reverse order is worker-owned A followed by an uncancellable joiner; that joiner waits, does not start an inline duplicate, and can see the same result. A completed A can be seen before cleanup; the observer compare-removes A, and both observer and winner use key/value identity so neither can delete replacement B. An audit joiner reserves its existing caller-side budget before joining; if its linked scope token cancels, admission closes before another scope request can reserve after lease release. The request surface is synchronous configuration resolution, so double-click, browser navigation/back, list rendering, and mobile states do not apply. The analogous interactions are duplicate reads, retry after failure, cancellation, and staggered resource starts, all covered by the flight and audit tests.

### CEO Section 6 — Test diagram and assertions

```text
GetPayload -> cache hit                 -> no client/flight; exact value and provenance
           -> cold uncancellable owner -> same managed thread, one client call
           -> cold cancellable owner   -> prompt owner wait cancellation; shared work completes
           -> cold audit owner         -> deadline/lease/count diagnostics; no post-deadline start
           -> same-resource joiners    -> one call, both winner orders, isolated cancellation
           -> completed holder         -> new uncached call; replacement survives late cleanup
           -> failed Fetch             -> one shared failure, later retry, preserved diagnostic
           -> conversion/cache         -> invalid bytes/type and newer generation retained
```

The shipping confidence test is a gated inline owner with cancellable and audit joiners: all joiners reach token-aware waits, cancellation returns promptly, the owner finishes once, and the next uncached caller starts a new flight. Hostile QA should race completed-holder cleanup against replacement publication and invalidate an old payload after a newer cache generation; existing #833 and generation tests are the foundation. The chaos case is a slow fake Google call held beyond an audit deadline: the audit report marks incomplete, no new same-scope work starts, and the background call eventually completes before test teardown. Use deterministic barriers rather than sleeps for ownership/order; bounded timeouts guard hung tests. Focused xUnit projects provide most coverage; no browser/E2E test is relevant. Use `./scripts/coverage-solution.sh` when practical and ensure changed branch paths are measured from a committed patch as the repo's coverage gate expects.

### CEO Section 7 — Performance

There is no database query or new connection pool. `_inFlight` size tracks active distinct-resource fetches, including those whose only waiter cancelled, and is bounded in time by the configured synchronous client timeout rather than by current caller count. `_cache` remains bounded by `CacheCapacity`; a cancelled worker can remain active after its waiter exits, as today. The three slow paths are distinct cold Google calls, same-resource join waits, and audit semaphore waits; their p99 depends on network/client timeout and cannot be inferred from fake latency. The benchmark must report elapsed median/spread, peak fake calls, sampled ThreadPool/process threads, baseline/candidate commits, and workload parameters. An inline owner removes a queued worker hop but still blocks its own thread, so neither throughput nor production startup latency is assumed to improve. Do not add a second cache or provider-wide lock.
