## Problem and evidence

An application needs to revalidate its current domain authority and record a conditional handoff immediately before a provider effect. Durable already owns claims, leases, scope generations, epochs, permits, retries, and recovery. Its permit transaction commits before the executor runs; an execution snapshot or unlocked control read cannot hold those fences through the application's transaction.

Add a supported PostgreSQL boundary that combines live native validation with application authorization and its handoff write in the caller's exact transaction. The application owns its ledger; Durable remains the execution owner. Doing nothing leaves consumers choosing between private native SQL and stale observations.

Evidence is static source inspection and public documentation research, not candidate implementation or passing runtime tests. The pump prepares the executor before acquiring a permit, then invokes it after permit commit and optional invocation admission. The existing transaction writer accepts Work in an application transaction but does not validate a live invocation. Existing PostgreSQL fixtures provide controlled clocks, real lock-wait observations, restricted roles, and package-only consumer projects; none proves this new callback boundary.

[Skoolit #735](https://github.com/forge-trust/skoolit/issues/735) is the issue's named downstream consumer. Its fetched issue body describes caregiver schedule safety, not a completed handoff feasibility proof. This design claims no consumer upgrade, production reproduction, or measured adoption benefit.

## What makes this useful

An executor can establish one database decision containing both current application permission and current native execution authority. Consumers can apply it to notifications, exports, or other provider effects without copying private Durable predicates or introducing another dispatcher. The first demonstration should make the two possible race orders observable and repeatable.

## Decisions and alternatives

The user selected open source/research mode, reuse of the existing Durable protocol, public documentation research, all five safety premises, an independent second opinion, and Approach A.

- Keep authorization and the handoff ledger application-owned; preserve native ownership and stable ActivityId/ProviderKey.
- The authority decision occurs at the final successful validation; preparation becomes durable only through caller commit.
- Require an active native invocation and the caller's `ReadCommitted` transaction. Reject other isolation levels without changing them.
- Use savepoints, preserve outer transaction ownership, and never retry the callback automatically.
- Deliver the complete ordered-race, failure, role/RLS, API/documentation, and packed-consumer proof. Local packing, publication, and adoption are distinct milestones.

**Approach A, selected:** a focused scoped fence using narrowly extracted existing transaction and locking helpers. Estimate: 20–30 human engineering hours / 6–10 agent hours, plus maintainer review. Risk: medium, especially predicate drift between legacy and opted-in Work.

**Approach B, rejected for this issue:** consolidate validation across permit, admission, renewal, completion, and handoff first. It offers broader internal uniformity but expands regression exposure and delays the specific public boundary. Estimate: 35–50 human hours / 10–16 agent hours, plus review.

## Public contract

The following is the proposed API, not an existing member or implementation:

```csharp
namespace ForgeTrust.AppSurface.Durable.PostgreSql;

public interface IDurableWorkHandoffFence
{
    ValueTask<DurableOperationResult<DurableWorkHandoffResult>> ExecuteAsync(
        NpgsqlTransaction transaction,
        Func<NpgsqlTransaction, CancellationToken, ValueTask<bool>> authorizeAndRecordHandoff,
        CancellationToken cancellationToken = default);
}

public sealed record DurableWorkHandoffResult(bool HandoffPrepared);
```

Register the default service through [AddAppSurfaceDurablePostgreSql](../../Durable/ForgeTrust.AppSurface.Durable.PostgreSql/README.md#composition-requirement). The public interface and internal concrete implementation resolve to the same scoped instance. No public binder, identity input, scope selector, or implementation constructor enables application-selected execution authority. Existing enqueue APIs retain their behavior.

`true` from the callback means application authorization and its conditional handoff write succeeded. A successful result with `HandoffPrepared=true` is provisional until caller commit. Callback `false` returns a successful result with `HandoffPrepared=false`, after removing callback writes. Native refusal is a failed `DurableOperationResult`; it never executes the callback unless the refusal arose during the post-callback check.

The callback is called at most once per method call, with the same transaction and caller cancellation token. Sequential calls within an invocation are allowed; application compare-and-swap, meaning a write conditioned on the expected domain state, governs duplicate handoffs. Concurrent or reentrant calls on one scoped instance reject before callback execution; the API provides no queue or automatic retry.

## Internal integration and invocation authority

The internal scoped implementation owns an immutable binding containing configured store/epoch, native scope/Work/activity, attempt, lease generation/owner, and exact permit identity. It does not cache lease expiry or require an unchanged Work revision, because renewal legitimately changes those facts.

The pump resolves the same concrete scoped instance used by executor injection. Preparation runs while it is unbound. After permit commit and, for opted-in Work, successful existing invocation admission, the pump enters an internal invocation context around executor execution and deactivates it in `finally`. It preserves existing heartbeat, renewal, cancellation, completion, retry, reconciliation, and typed-exit paths.

Use an internal execution-context marker paired with the binding, such as a private `AsyncLocal` token plus an active flag. Each call checks both: a reference borrowed from invocation B cannot be used under invocation A's marker. A retained marker/reference loses authority when its invocation exits. Child asynchronous work inside the same invocation inherits that context; callers must await handoff work and end its transaction before returning from the executor. Validate binding before any callback and again before success; no escaped operation can succeed after deactivation. This is a same-process framework contract, not a sandbox against application code holding runtime database credentials.

Extract the minimum shared native reads/validators needed by the new operation. The existing opted-in locked-row reader returns no row for legacy Work, so the handoff validator must cover legacy and opted-in records explicitly. Do not call mutating invocation admission a second time, consume another permit, create an attempt, or publish private SQL predicates. Internal helpers expose locked facts and bounded refusal reasons; they own neither transaction completion nor native transitions.

## Transaction and savepoint protocol

1. Validate non-null arguments, active binding, non-overlapping use, an open connection and active exact transaction, configured physical target, and `ReadCommitted`. Reject invalid resources/isolation before the callback. Use the existing [transaction writer](../../Durable/ForgeTrust.AppSurface.Durable.PostgreSql/README.md#accept-work) failure conventions.
2. Establish a uniquely named operation savepoint before database validation that could abort the transaction. Capture the caller's effective transaction-local scope context. Acquire the shared migration/epoch fence before schema/StoreId/active-epoch validation, then lock scope → Work → dispatch → permit in the existing protocol order; history remains last if a reused path needs it. Do not create a missing scope.
3. Validate active scope/generation; exact Work and ActivityId; attempt, lease generation, owner, epoch; database-clock live lease; effect-permitted state without cancellation; and the exact granted permit. Opted-in Work additionally requires its existing invocation-admission facts and immutable execution deadline. Treat dispatch or permit inconsistencies as refusal, never permission.
4. Establish a callback savepoint after acquiring native locks. Invoke the short callback once. It locks/revalidates application authority and writes its conditional handoff in this transaction. Application authorization must use current locked rows or an equivalent conditional write, not an earlier projection.
5. After a successful callback, recheck invocation lifetime, cancellation, and live database-clock lease/deadline conditions. Sample the clock after all lock waits and callback work. Row/epoch fences prevent competing native writes while time still advances. This final validation is the authority decision.
6. On callback denial, exception, cancellation, or post-callback refusal, roll back the callback savepoint so its writes disappear. On success, release it. Restore the caller's original effective scope context and release the operation savepoint, leaving native locks held through outer completion. On pre-callback validation refusal, roll back the operation savepoint; locks acquired by the refused operation may be released. Earlier caller writes remain outside its savepoint.
7. Cleanup must use a fresh, bounded cleanup token rather than an already canceled caller token. If savepoint rollback/release or context restoration fails, throw, never return success or a clean refusal; the caller must roll back/dispose the outer transaction. Preserve the original callback exception after successful cleanup. A cleanup failure must retain both causes for the caller without putting raw exception text into Durable diagnostics.

The two savepoints separate recoverable validation from callback rollback that retains already acquired native locks. Implementation must prove their behavior, unique naming, caller-savepoint coexistence, and context restoration with Npgsql 10.0.3. PostgreSQL releases locks acquired after a rolled-back savepoint; releasing a savepoint retains its effects in the outer transaction. [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html), [RELEASE SAVEPOINT](https://www.postgresql.org/docs/18/sql-release-savepoint.html), [Npgsql transaction API](https://www.npgsql.org/doc/api/Npgsql.NpgsqlTransaction.html).

`ReadCommitted` is an explicit first-release constraint. An advisory lock does not refresh a pre-existing `RepeatableRead` snapshot. Stronger isolation support requires a separately reviewed current-row/epoch protocol and real proofs; callers never receive silently changed isolation. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [application consistency](https://www.postgresql.org/docs/17/applevel-consistency.html).

## Application obligations and ordering

Every callback authorization read and handoff write must use only the supplied `NpgsqlTransaction` and its exact connection. The callback must not open another connection, begin another transaction, or use ambient/different transactions for those operations: such writes would escape operation savepoints and caller commit/rollback. It performs database work only and must not commit, roll back, dispose, or replace the supplied resources, perform provider I/O, or escape work past invocation exit. An arbitrary C# delegate cannot be technically sandboxed. If application code commits inside the callback or writes through another connection, the framework cannot undo that committed write; such use violates this contract. Detect inactive/replaced supplied resources and fail, but never claim that detection reverses an improper commit.

For a successful preparation, the caller commits promptly, ends the transaction, and releases its connection inside the current invocation before calling a provider. Caller rollback grants no handoff. A failed or ambiguous commit grants no permission to send until the application reconciles its own ledger. Successful final validation does not promise authorization or lease time remains current indefinitely; expiry after it does not retroactively undo a committed handoff. Cancellation/revocation that wins before the transaction's relevant locks rejects; a handoff transaction that wins first serializes the competing writer behind it. Later cancellation cannot recall an external effect; the existing [provider-safety matrix](../../Durable/work-protocol-v1.md#provider-effect-safety) and [execution-policy completion rules](../../Durable/execution-policies-v1.md) remain authoritative.

Call `ExecuteAsync` before acquiring application authority or ledger locks needed by its callback or competing native-first writers. Earlier caller writes are supported only when they do not establish a conflicting acquisition order; use an independent caller-marker row with no authority/ledger foreign-key lock for the rollback-preservation proof. The canonical example begins the caller transaction, writes that unrelated marker, calls the fence to acquire native locks, then takes authority/ledger locks exclusively inside the callback, ends the outer transaction, releases its connection, and finally invokes the fake provider.

Consumers must audit every writer sharing authority/ledger rows, including paths using [transactional Work enqueue](../../Durable/ForgeTrust.AppSurface.Durable.PostgreSql/README.md#accept-work). The handoff path acquires native locks before application locks. A writer that first takes an application lock and then requests a conflicting native lock can deadlock. Document one consistent acquisition order, relevant to the actual consumer, and deterministic ordering for multiple application rows. Callbacks must not introduce native locks out of order. If an enqueue path cannot satisfy that order, restructure that application path; do not silently introduce nested enqueue into the canonical example. Lock timeouts/deadlocks propagate after cleanup; framework callback retries remain forbidden.

Use the existing restrictive runtime principal with separately granted application-table access and both schemas' row-level security (RLS), which limits visible/writable rows according to database policy. Set only the bound transaction-local native scope, restore the caller's effective prior value including the no-scope state on every usable return, and prove pooled-connection cleanup. Never change role, bypass RLS, or use migration-owner permissions in runtime examples. Runtime credentials remain a trusted host capability, not independent application authorization.

## Failure reference

| Condition | Observable behavior |
| --- | --- |
| Null transaction/callback | `ArgumentNullException`; no callback. |
| Inactive/closed/completed transaction, wrong physical target, unsupported isolation, overlapping/reentrant operation | `InvalidOperationException`; no callback. |
| Absent/expired/mismatched invocation marker | Failed result with `ClaimLost` (`ASDUR104`); no callback. |
| Disabled, missing, or changed-generation scope | `ScopeDisabled` (`ASDUR107`), `ScopeNotFound` (`ASDUR113`), or `ScopeGenerationConflict` (`ASDUR114`). |
| Missing/terminal Work, stale identity/permit, canceled state | `WorkNotFound` (`ASDUR111`), `AlreadyTerminal` (`ASDUR110`), or `ClaimLost` (`ASDUR104`), selected by validated facts. |
| Lease expiry or configured deadline expiry | `LeaseLost` (`ASDUR105`) or `ExecutionDeadlineReached` (`ASDUR121`); callback writes removed if already entered. |
| StoreId/schema/active epoch mismatch | Match existing writer exceptions: safe `DurableRuntimeSchemaException` for compatibility; `InvalidOperationException` carrying applicable StoreIdentityMismatch/RecoveryEpochRequired code. |
| Callback false | Successful result with `HandoffPrepared=false`; callback writes removed, earlier caller writes retained. |
| Callback exception/cancellation | Propagate after successful cleanup; prior caller writes retain normal outer-transaction semantics. |
| PostgreSQL, serialization, permission, lock timeout, or transport failure | Preserve the failure; recover to savepoint only where possible. Cleanup failure requires outer rollback/disposal; never report success. |

Codes reuse [DurableProblemCodes](../../Durable/ForgeTrust.AppSurface.Durable/README.md). No new diagnostic family or native metric labels are needed. Diagnostics contain bounded codes and safe guidance, never payloads, family data, recipients, credentials, provider responses, or raw server/exception messages. Exception propagation to the caller is distinct from framework logging.
