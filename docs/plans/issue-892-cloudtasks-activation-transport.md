## Problem and useful outcome

Applications that already use external Durable activation on Google Cloud repeat task construction, credential handling, submission bounds, and failure classification. Supply one optional Google-specific adapter so callers can submit a named empty wake and retain a safe receipt. Applications continue to own accepted Work, application outboxes, recovery, and business decisions.

The useful capability is shared across applications: billing recovery, document processing, and maintenance can wake their existing worker without copying business payloads into Cloud Tasks. A creation receipt never proves which Work ran or that Work completed. No measured maintenance, onboarding, or line-count saving has been established.

## Public API and registration

### Validation before I/O

Reject null values, blank or oversized identifiers, controls, separators that escape resource-name segments, invalid task IDs, and malformed email syntax. Accept provider-documented project forms, including numeric and legacy forms, up to a package limit of 128 characters. Queue IDs use provider syntax with a 100-character limit; task IDs permit letters, digits, hyphens, and underscores up to 500 characters. Location is a nonblank lowercase letter/digit/hyphen segment up to 63 characters; syntax validation is not a network region lookup. Audience is at most 2,048 characters and email is at most 254 ASCII characters. These package limits are explicit validation policy, not claims about every provider's maximum.

Require an absolute HTTPS endpoint with a host, no user information or fragment, and at most the provider's 2,083-character encoded limit. Query text, if present, is fixed host configuration and must carry no Work payload, scope, tenant, or credential. Require an explicit nonblank bounded audience; do not infer it from the endpoint or require string equality. Worker deadlines must be between 15 seconds and 30 minutes and have whole-millisecond precision, rejecting values Google would silently truncate. [Provider field constraints](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues.tasks)

Syntactic validation cannot prove queue existence, region availability, same-project service-account ownership, permissions, or effective routing. In particular, do not compare project strings to email substrings to infer identity. Google requires the OIDC service account to belong to the queue project and the creator to have `iam.serviceAccounts.actAs`. [OIDC contract](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/OidcToken)

## Official-client execution boundary

1. Validate and snapshot the request; compute the exact queue/task names. Check caller cancellation before token acquisition and before invoking the SDK.
2. Start one monotonic submission budget. Obtain the token through the selected source using the linked caller/budget token. Validate token syntax and a finite size limit before adding it to one invocation's authorization metadata.
3. Use the official generated request models and `CloudTasksClient.CreateTaskAsync`. Submit one task with the declared name, `POST`, endpoint, OIDC account/audience, and deadline. Leave the worker body unset so its serialized payload is absent/zero bytes. Request only `BASIC` response view. Do not set task retry configuration or schedule time.
4. Construct one private `Grpc.Net.Client.GrpcChannel` for `https://cloudtasks.googleapis.com` with the bounded package-owned HTTP transport. Supply its `CreateCallInvoker()` result to `CloudTasksClientBuilder.CallInvoker`, together with package-owned `CloudTasksSettings`, then call `Build()`. The channel supplies TLS but has no OAuth call credentials. For each invocation, add exactly one lowercase `authorization` metadata entry with `Bearer ` plus the already acquired token using `CallSettings.FromHeader`, combined with that invocation's cancellation and deadline. Never mutate shared client headers or put token acquisition in an interceptor that could be called repeatedly. Do not use `CloudTasksClient.Create()`, credential builders, application-default lookup, automatic metadata discovery, emulator environment settings, or arbitrary production endpoint overrides. The SDK's [explicit call-invoker construction](https://docs.cloud.google.com/dotnet/docs/reference/Google.Api.Gax/latest/Google.Api.Gax.Grpc.ClientBuilderBase-1) and [per-call header settings](https://docs.cloud.google.com/dotnet/docs/reference/Google.Api.Gax/latest/Google.Api.Gax.Grpc.CallSettings) are the selected mechanisms. Prove builder/resolution and invalid-request paths perform zero credential lookups, and concurrent valid calls each carry only their own token, before freezing the public API.
5. Give the RPC only the remaining submission time and linked cancellation. Set a one-attempt policy explicitly, with no hedging or application/HTTP retry handler. The SDK documents no retry and a 20-second default for creation, but the package must prove its selected configuration rather than rely on that default. [SDK creation settings](https://docs.cloud.google.com/dotnet/docs/reference/Google.Cloud.Tasks.V2/latest/Google.Cloud.Tasks.V2.CloudTasksSettings)
6. Classify only bounded results. Preserve the exact returned success only after validating its task name against the expected name with ordinal comparison. Never fetch an existing task to imply equivalence.

Use private helpers for validation/request projection, invocation budget, SDK transport construction, and receipt classification. They are not a general execution framework. Internal test access follows existing `InternalsVisibleTo` conventions; no reflection into private members.

### Resource limits and feasibility gate

Initial package limits are 64 KiB for received protobuf messages, 16 KiB for response headers/trailers, 16 KiB for metadata JSON, and 8 KiB for a token. Read metadata with a limit-plus-one technique and a bounded JSON depth. Configure request/connect/read bounds, disable redirects and cookies, and prohibit fallback HTML/error-body buffering. Do not log SDK status details, response metadata, tokens, or exception objects.

The [GAX receive-size option](https://docs.cloud.google.com/dotnet/docs/reference/Google.Api.Gax/latest/Google.Api.Gax.Grpc.GrpcChannelOptions) and [.NET gRPC transport controls](https://learn.microsoft.com/en-us/aspnet/core/grpc/configuration) provide relevant mechanisms. Their effective behavior, including compressed responses, error trailers and non-gRPC responses, is an **implementation feasibility gate**. First prove the pinned SDK/channel combination with a local HTTP/2 fixture. Disable transport retries and hedging at both layers and verify observable request counts, including retry-eligible failures. Inspect any transparent pre-commit transport replay separately; it must not silently become a second submission.

If the supported official transport cannot meet these bounds or explicit credential behavior, stop and report the precise failed proof before widening limits or changing architecture. Do not fall back to handwritten REST. Custom token sources must cooperate with cancellation; the adapter does not return early and detach an unfinished source with `WaitAsync` or fire-and-forget work.

### Metadata token source

Use only the documented Cloud Run metadata token endpoint and `Metadata-Flavor: Google`. It obtains the attached runtime identity's OAuth access token, which is distinct from the task's worker OIDC identity. [Cloud Run metadata contract](https://docs.cloud.google.com/run/docs/container-contract#metadata-server)

Own a separate bounded HTTP client with redirects, cookies, automatic decompression, and proxy use disabled. Its timeout is the earlier of the configured metadata limit and remaining submission budget. Require a successful bounded JSON object with `access_token`, `token_type`, and `expires_in`; reject duplicate members for these fields. Do not cache tokens, retry internally, consult credential files, or switch sources. A local test-only handler seam supplies fixtures without introducing a public metadata-URL escape hatch.

Tokens from every source must contain 1–8,192 ASCII characters matching the [RFC 6750 bearer-token grammar](https://datatracker.ietf.org/doc/html/rfc6750#section-2.1): one or more letters, digits, `-`, `.`, `_`, `~`, `+`, or `/`, followed only by optional `=` padding. Reject controls, whitespace, non-ASCII, padding inside the token, and an included `Bearer ` prefix. The ASCII character and byte limits are therefore identical. Invalid custom-source token values return `Rejected/ASCT102` with zero Cloud Tasks calls; no exception or diagnostic echoes the value. Custom sources own token validity and expiry because the public contract returns only a string; syntax checking is not cryptographic verification or a lifetime claim.

For the built-in metadata source, `token_type` must be a JSON string equal to `Bearer` ignoring ASCII case. `expires_in` must be a JSON integer from 1 through `Int32.MaxValue`, not a string or fraction. Capture a `TimeProvider` monotonic timestamp before the metadata request. At validation, subtract the entire elapsed request/read time from `expires_in` conservatively and require strictly more than the remaining submission budget plus a fixed five-second safety margin. Use no wall-clock/JWT timestamp or local clock-skew calculation; `expires_in` is a relative duration. Invalid token fields, token type, expiry type/range, duplicates, or insufficient remaining lifetime produce `Rejected/ASCT102` with zero Cloud Tasks calls. Unsuccessful HTTP, transport/read timeout, exceeded body/depth limits, or unparseable/non-object JSON produce `Rejected/ASCT101`, except caller cancellation and overall submission-budget expiry use the precedence below.

## Receipt, failure, and cancellation rules

Receipt task names always come from validated request intent. Diagnostic codes form a closed, documented package-owned catalog; each code maps to one disposition and remediation. No arbitrary string is accepted as a passing diagnostic. The following assignments are proposed as part of this design: `ASCT001` Created; `ASCT002` AlreadyExists; `ASCT101` token unavailable, `ASCT102` invalid token, and `ASCT103` budget expired before submission, all Rejected; `ASCT201` InvalidArgument, `ASCT202` Unauthenticated, `ASCT203` PermissionDenied, `ASCT204` NotFound, `ASCT205` FailedPrecondition, `ASCT206` OutOfRange and `ASCT207` Unimplemented, all Rejected; `ASCT301` deadline, `ASCT302` unavailable/connection loss, `ASCT303` ambiguous ResourceExhausted, `ASCT304` response limit, `ASCT305` other nonfatal uncertain failure, `ASCT306` missing/mismatched/malformed success, and `ASCT307` unrequested RPC cancellation, all Indeterminate. Invalid arguments, propagated cancellation and fatal exceptions have no receipt/code. Document remediation for each code in the package reference and reject every unlisted disposition/code pair.

| Evidence | Result |
| --- | --- |
| Invalid argument or options | Constructor/argument exception; zero token and provider calls. |
| Nonfatal token failure, invalid token, or budget exhausted before SDK invocation | `Rejected`, with a code explicitly stating no provider submission was attempted. |
| Successful SDK result with exact expected task name | `Created`; acceptance only. |
| Provider `AlreadyExists` | `AlreadyExists`; no content equivalence, current-queue-presence, delivery, or Work-completion claim. |
| Definitive provider `InvalidArgument`, `Unauthenticated`, `PermissionDenied`, `NotFound`, or `FailedPrecondition` | `Rejected`, with a canonical safe code. |
| RPC deadline, unavailable/unknown/internal failure, connection loss, malformed or mismatched success, local message/header limit | `Indeterminate`; creation may have occurred. |
| `ResourceExhausted` without reliable provenance distinguishing provider quota rejection from a local receive limit | `Indeterminate`, including throttling fixtures; never guess from exception text. |
| Caller cancellation before/during token or RPC operation | Propagate a safe `OperationCanceledException` carrying the caller token, with no provider message or inner exception. |

The complete SDK status mapping is: `OK` requires the validated success object (`ASCT001`, otherwise `ASCT306`); `AlreadyExists` maps to `ASCT002`; `InvalidArgument`, `Unauthenticated`, `PermissionDenied`, `NotFound`, `FailedPrecondition`, `OutOfRange`, and `Unimplemented` map respectively to `ASCT201` through `ASCT207`; `DeadlineExceeded` maps to `ASCT301`; `Unavailable` to `ASCT302`; `ResourceExhausted` to `ASCT303`; `Unknown`, `Aborted`, `Internal`, and `DataLoss` to `ASCT305`; and `Cancelled` without a signaled caller or budget token to `ASCT307`. Undefined future statuses map to `ASCT305`. A detected local response-bound failure takes `ASCT304` ahead of a generic status; an indistinguishable receive-limit/quota `ResourceExhausted` remains `ASCT303`. Do not infer provider provenance from message text.

A complete validated SDK return or definitive non-cancellation provider rejection wins over caller cancellation observed only after that return/error; do not rewrite acknowledged evidence through a late cancellation check. For `OperationCanceledException`, `Cancelled`, or `DeadlineExceeded`, check the caller signal first: if signaled, propagate the sanitized caller-token exception even if the budget also fired. Otherwise an expired budget produces `ASCT103` before invocation or `ASCT301` after invocation. With neither source signaled, RPC `Cancelled` is `Indeterminate/ASCT307`, RPC `DeadlineExceeded` is `Indeterminate/ASCT301`, and an unrequested cancellation exception from token acquisition is `Rejected/ASCT101`. An unrequested nonfatal cancellation exception after invocation is `Indeterminate/ASCT307`. Non-cancellation transport failures retain their mapped uncertainty even if cancellation also arrives. The invocation boundary is conservative: it establishes that a submission may have started, not that bytes reached Google. Fatal process exceptions propagate rather than becoming operational receipts.

Google's [canonical error contract](https://docs.cloud.google.com/tasks/docs/reference/rpc/google.rpc#code) allows a deadline failure after a mutation succeeded. Named task creation can conflict with a recently executed/deleted task; an ID can remain reserved after removal. Prefer caller-generated uniformly distributed IDs and keep sensitive domain data out of names. [Task creation semantics](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues.tasks/create)

An `Indeterminate` receipt or canceled call is not a rollback receipt. The application retains its task ID and uses its existing authorized recovery process before deciding on another dispatch. Queue settings can override target URI, method, headers and identity; this client records requested intent and acceptance, not effective configuration. Operators must review that configuration separately. [Queue override contract](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues#HttpTarget)
