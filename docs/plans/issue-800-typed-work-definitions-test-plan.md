# Test plan: typed Durable Work definitions (#800)

Generated by autoplan engineering review on 2026-09-10. Branch at review: `main`; implementation baseline: `48c6db61ac5f742bea9f1ee434860daf72df791c`.

The [approved design](../designs/issue-800-typed-work-definitions.md) defines the contract. The [implementation plan](issue-800-typed-work-definitions.md) adds sequencing and review decisions. Everything below is required implementation evidence, **not a claim that tests have run**. Tests use xUnit, intentional internal seams and ordinary test doubles; do not use reflection to reach private members.

## Surfaces and critical user paths

There are no pages/routes. The affected surfaces are the Durable .NET API, DI composition, existing Flow adaptation, packed NuGet consumers, documentation examples and one bounded PostgreSQL Work path. A module author defines a contract, binds an implementation, registers it, creates a request and verifies its facts. A runtime adopter accepts that request, retries the equivalent direct request as Duplicate, then processes it to terminal success through the existing runtime.

```text
Define
  +-- invalid/null facts --> argument error; no serializer/DI call                    [U01]
  +-- codec getter throws --> same exception                                       [U02]
  +-- valid facts --> one capture/source --> stable definition                      [U02]
        +-- CreateRequest invalid IDs/null Work --> no Encode                       [U04]
        +-- CreateRequest valid --> Encode once --> metadata guard                  [U03,U04]
              +-- mismatch/null/policy/serialization failure --> visible exception   [U03]
              +-- existing constructor --> exact fields/fingerprint/UTC             [U04,U05]
        +-- ExecutedBy --> ordinary/intermediate --> register/reject                [U06]
        +-- ReconciledBy --> correct safety only                                    [U06]
        +-- ExecutedByExit --> ProviderKeyed only                                   [U06]
Bindings + legacy constructors
  +-- captured snapshots --> common registration builder                           [U07]
  +-- exact singleton values; no executor construction                              [U08]
  +-- duplicate Work identity --> catalog rejects before codec enumeration           [U09]
  +-- valid contributions --> source snapshot validation --> codec identity          [U10]
        +-- raw-only -> original source                                             [U10]
        +-- frozen required -> provider-owned canonical view                        [U10]
        +-- manual Register equivalent/upgrade/conflict -> atomic indexes            [U11]
Flow
  +-- exact Work registration + codec provenance --> guarded activity codecs         [U12]
  +-- context registry selection --> check --> decode/encode same selected codec     [U13]
  +-- event registry selection --> wait metadata/resume decode same selected codec   [U14]
Invocation
  +-- prepare -> typed payload + same identity/fence -> transient executor            [U15]
  +-- reconcile / exit / legacy boundary -> existing outcomes                        [U15]
Package
  +-- valid complete old/new/Flow examples -> compile and run                        [P01]
  +-- negative fixture -> restore succeeds -> exact marked compiler error            [P02]
  +-- unrelated error/restore failure/bad positive control -> harness fails           [P02]
PostgreSQL
  +-- factory accepted -> direct replay Duplicate -> same stored facts               [I01]
  +-- conflicting policy/payload -> existing conflict; atomic rollback               [I01]
  +-- bounded pump -> terminal success + exact result; no false completion           [I02]
Docs/API
  +-- managed snippet -> package fixture -> baseline/analyzers/release links          [D01]
```

Legend: U = unit/component, P = packed public API/system proof, I = real database integration, D = documentation/API verification. Existing source tests are regression baselines; all definition/view-specific tests are new and currently unimplemented. No coverage percentage or test-quality star rating can be measured before implementation. There are no LLM changes/eval suites or new hosted/background jobs.

## Execution and evidence collection

Run from the implementation checkout after it contains the pinned exit baseline. Proposed new tests/files above are names to implement, not existing commands guaranteed to match today. First use test discovery to verify nonzero expected test counts; a filter matching zero tests is not a pass.

1. Restore/build affected Durable projects with repository package/analyzer settings; run `dotnet format` for the affected projects using the repository `.editorconfig`, then verify no formatting differences.
2. Run `dotnet test Durable/ForgeTrust.AppSurface.Durable.Tests/ForgeTrust.AppSurface.Durable.Tests.csproj` with normal test logging. This includes existing fingerprints, passivity, replay/Flow and public API baselines as well as the new focused classes.
3. Run affected Provider tests and `dotnet test Durable/ForgeTrust.AppSurface.Durable.PostgreSql.Tests/ForgeTrust.AppSurface.Durable.PostgreSql.Tests.csproj` with the existing Docker/external DB fixture and no skip flag. For early iterations select named new classes plus impacted Work/Flow/exit tests; the final affected suite must include existing regressions. Use the repository's bounded PostgreSQL verification script when validating its workload entry points.
4. Run `bash Durable/verify-packed-consumers.sh`; preserve the existing output and add positive/negative fixture counts. Restore and package failures cannot satisfy negative assertions.
5. Run the existing Markdown snippet tool's `generate` then `verify` on the package README and migration guide that contain managed snippets. Example: `dotnet run --project tools/ForgeTrust.AppSurface.MarkdownSnippets/ForgeTrust.AppSurface.MarkdownSnippets.csproj -- verify --document Durable/ForgeTrust.AppSurface.Durable/README.md`.
6. Run `./scripts/coverage-solution.sh` when practical. Inspect changed-line/branch coverage and add meaningful missing guard/error cases. If unavailable, record the precise environment reason and affected-suite results, leaving solution coverage unverified.

Record commit, SDK/package version, fixture counts, test failures/skips and relevant artifact paths. No planned test result may be labelled passed until its command actually ran. Keep database execution bounded; if a long check needs monitoring, delegate it under the local subagent policy.

## Acceptance and rollback checks

The user-facing proof must show contract facts defined once, deliberate per-request decisions visible, unchanged direct/factory semantics, and real terminal success. Preserve supported historical Work versions and the exit capability rollout matrix from the implementation plan. Do not infer safe rollback from an unchanged database schema.
