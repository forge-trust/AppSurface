## Problem and value

Resource-backed tests repeat creation, build, start, resource-health waiting, endpoint selection, and HTTP polling before their assertions. The pinned [Skoolit gate](https://github.com/forge-trust/skoolit/blob/a589f164ef3346d4ecf8bf39b8a73ec71ea1cb1e/tests/Skoolit.Playwright.Tests/MonitoringReceiptBrowserGateTests.cs) demonstrates the sequence. Nine test files use the QA factory; eight application-test files use the [HTTP probe](https://github.com/forge-trust/skoolit/blob/a589f164ef3346d4ecf8bf39b8a73ec71ea1cb1e/tests/Skoolit.Playwright.Tests/QaEndpointProbe.cs). This is source evidence of duplication, not measured reliability or latency improvement.

One awaited call should return the selected endpoint after native resource health and the declared HTTP condition pass. The reusable capability belongs to [EvidenceHost](../../start-here/evidencehost.md); Aspire supplies the application integration. Ordinary tests need no evidence plan, producer, manifest, or claim to use HTTP readiness.

## Decisions and premises

- Build on the [typed testing builder and configured factory](../../Aspire/ForgeTrust.AppSurface.Aspire.Testing/README.md), preserving their activation, build, and application-before-activation cleanup.
- Use the selected composable fixture: invoke a caller-supplied builder factory exactly once under the shared startup deadline.
- Put transport-neutral HTTP readiness in a new Evidence package. This explicitly revises the earlier existing-package-only distribution premise following the user's branding question and choice A.
- Version one checks one explicit resource, endpoint, and HTTP path. Defaults are two minutes for fixture startup, three seconds per request, 250 ms between attempts, and exact HTTP 200; timing and status acceptance are configurable.
- Readiness deadlines cover cooperative asynchronous work. Synchronous creation/build/callbacks, a transport ignoring cancellation, and cleanup can outlast them. Cleanup is awaited; deadline expiry is not proof that cleanup finished.
- Browser ownership, credentials, fixture data, container composition, and business readiness stay consumer-owned. A successful health URL proves only its configured condition.

## Proposed public API

Signatures below are the intended design, not implemented APIs. Use the neutral namespace `ForgeTrust.AppSurface.Evidence.Readiness` for the probe and its types.

```csharp
Task HttpReadinessProbe.WaitAsync(
    HttpClient client, Uri endpoint, string probePath, TimeSpan timeout,
    HttpReadinessOptions? options = null,
    CancellationToken cancellationToken = default);

Task<AppSurfaceAspireTestFixture> AppSurfaceAspireTestFixture.StartAsync(
    Func<CancellationToken, Task<AppSurfaceAspireProfileTestingBuilder>> createBuilder,
    AspireHttpReadinessTarget target,
    AppSurfaceAspireStartupOptions? options = null,
    CancellationToken cancellationToken = default);
```

- `AspireHttpReadinessTarget` contains required resource name, endpoint name, and probe path. `AppSurfaceAspireStartupOptions` contains `StartupTimeout` (two minutes), `HttpReadinessOptions`, and an optional `Func<Uri, HttpClient> CreateProbeClient`.
- `HttpReadinessOptions` has init-only `RequestTimeout` (three seconds), `RetryDelay` (250 ms), and `Func<HttpStatusCode, bool> IsSuccess` (exact 200). The predicate is synchronous and receives only status; body assertions belong to the test.
- The fixture exposes borrowed `DistributedApplication Application` and the selected base `Uri Endpoint`, and implements `IAsyncDisposable`. The endpoint is returned only after both checks pass. The fixture controls application lifecycle; callers use the borrowed application for assertions/resource access and must not independently build or dispose it.
- The standalone probe requires an explicit finite positive timeout, borrows its client, and never builds, starts, or disposes an application. It sends an absolute URI derived from the endpoint without mutating client configuration.
- Add `EvidenceAspireApplication.CreateHttpReadiness(evidenceResourceId, resourceName, endpointName, probePath, timeout, options)`, returning `IEvidenceResourceReadiness`. It combines native health and HTTP readiness under that timeout and the EvidenceHost resource cancellation token. It resolves the endpoint through Aspire.Hosting application-model APIs under the existing lease, without introducing Aspire.Hosting.Testing.

Validate nulls, blank names, HTTP(S) endpoint, a nonempty relative path, delegate/options values, and finite positive timer-supported durations before acquiring resources. Reject absolute or network-path probe paths and any resolution that changes the endpoint origin. Snapshot option values and delegate references at entry. A pre-cancelled caller prevents factory invocation. Predicate exceptions are terminal configuration failures, not retries.

## Startup, deadlines, and ownership

```text
validate + snapshot
  -> start original deadline
  -> invoke factory once
  -> take ownership of returned active, unbuilt typed builder
  -> existing BuildAsync
  -> application.StartAsync
  -> native resource-health wait
  -> resolve explicit endpoint
  -> HTTP probe
  -> return fixture
failure/cancellation -> await existing builder cleanup -> rethrow primary failure
fixture disposal    -> await existing builder cleanup -> report cleanup failure
```

The factory owns anything it allocates but fails to return. Existing CreateAsync/CreateConfiguredAsync already handle their own failure cleanup. Custom factories must do the same; they must return an exclusive, active, unbuilt builder and must not retain an independent disposer. Returning a built/disposed builder is rejected through an intentional internal lifecycle seam and any transferred builder is cleaned before reporting failure.

Start one monotonic budget before invoking the factory and use linked cancellation for cooperative operations while retaining the original caller token and original deadline as distinct internal inputs. Before each phase and success return, check caller cancellation and deadline expiry. At the HTTP phase, the internal shared probe core receives that same original deadline, caller token and remaining duration; the standalone public probe creates its own deadline and delegates to this core. Never restart the full startup allowance after creation, start, health, or a retry; original caller cancellation wins and deadline exhaustion retains the HTTP last cause.

For every request, the effective timeout is the minimum of request maximum and remaining budget, also subject to the supplied client/handler's shorter timeout. Bound retry delay by remaining time. Check cancellation/deadline again before accepting success, so a late response cannot turn cancellation into success. Caller cancellation takes precedence when both caller and deadline are cancelled.

Use the existing typed builder's DisposeAsync as the cleanup owner; its fallback disposes the application before activation services. Do not add a second application lease or dispose the application independently a second time. Repeated/concurrent fixture disposal joins cleanup, and cleanup exceptions remain visible to every explicit disposal caller. Startup failure preserves its primary exception even when cleanup also fails; expose only safe secondary cleanup information. Support reentrant disposal without waiting on the same cleanup flow, following the existing builder pattern.

## HTTP behavior and diagnostics

Send GET using response-headers completion, evaluate the status, and dispose every response before retry/return. Never read a response body. Retry rejected statuses, HttpRequestException transport failures, and identifiable request timeouts until the budget expires; do not retry caller cancellation, expired overall deadline, predicate failures, or programming/configuration errors.

A shorter HttpClient.Timeout still applies; do not mutate a borrowed client's timeout or install a resilience policy. The default fixture transport uses native Aspire endpoint/client configuration. A custom client factory receives the selected endpoint once and transfers ownership of a fresh client to the fixture. It controls proxy, redirects, certificates, and handlers; no Skoolit-specific proxy setting becomes an SDK default. Dispose owned clients after probing, including on failure; standalone callers retain their clients.

Readiness-generated exceptions carry stable stage/category data, last rejected status or safe HttpRequestError category when applicable, and attempt count. Distinguish creation/build/start deadline, resource-health timeout, status rejection, transport failure, request timeout, and caller cancellation. HTTP budget exhaustion retains its last cause instead of flattening every case into "not ready". Caller cancellation propagates OperationCanceledException with the caller's token.

Generated diagnostics exclude URL/path/query, headers, credentials, response bodies, and raw transport exception messages. Original factory/build exceptions remain the primary exceptions and are not automatically logged or claimed to have been redacted. Diagnostic formatting/sinks cannot replace a primary failure.

The Evidence.Aspire adapter owns its probe client and forwards disposal to its existing application lease; it never creates another owner. Its own repeated cleanup joins one completion. Existing EvidenceHost resource deadlines can shorten the adapter timeout. This does not repair or claim whole-host cleanup terminalization.

## Reuse, alternatives, and independent perspective

[Aspire](https://aspire.dev/testing/accessing-resources/) already supplies native health waiting and endpoint-specific clients; its [HTTP health checks](https://aspire.dev/reference/api/csharp/aspire.hosting/resourcebuilderextensions/methods/) can already cover the same URL/status. Use native APIs directly when they meet the test's needs. This fixture adds an explicit test-side transport/condition under the shared lifecycle budget. [Testcontainers wait strategies](https://dotnet.testcontainers.org/api/wait_strategies/) confirm the established condition/timeout pattern but do not replace typed Aspire profile ownership. [HttpClient timeout rules](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.timeout?view=net-10.0) inform cancellation classification.
