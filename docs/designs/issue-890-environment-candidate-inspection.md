## Problem and design relationship

Application developers need to enforce rules such as requiring a setting to come from a file or an approved secret provider. Before resolving values, they currently have to reproduce AppSurface's environment candidate rules. #890 exposes those rules as metadata while keeping ownership decisions with the application.

This design extends the approved [logical-key contract](https://github.com/forge-trust/AppSurface/blob/main/docs/designs/config-logical-key-contract.md) and [file-declared secret design](https://github.com/forge-trust/AppSurface/blob/main/docs/designs/issue-807-file-declared-secret-references.md). Current source governs existing behavior. Native lookup and direct composition lookup have distinct rules; neither is a replacement for the other. Doing nothing leaves duplicated framework knowledge in consumer policy code.

Evidence is static inspection at `306be6f43ef01942b5b8261ff93a3d85ec5100d9`, plus the issue's earlier static baseline. No implementation tests, coverage, benchmarks, or live-provider checks ran during this design session.

## What makes this useful

A host can ask which environment names might affect `Service:ApiKey` before accessing any values. It can compare those names with an application-owned deployment-name inventory, then keep its own rule for acceptable sources. The framework supplies the spelling and order; the application supplies policy and presence evidence.

The same contract could later power an offline deployment-manifest linter without credentials. That linter, its manifest format, and policy enforcement are separate work. First prove the two neutral policy examples required by #890.

## Accepted premises and decisions

- Remove duplicated candidate-generation knowledge; retain application ownership policy.
- Preserve native typed, native strict-string, and direct composition semantics, including exact spelling, ordering, mapping replacement, aliases, and ordinal de-duplication. Keep the existing translated-member resolution bridge internal and unchanged.
- Inspection performs no environment reads, file reads, provider calls, secret resolution, conversion, or native-claim mutations. A plan proves neither presence, successful resolution, source ownership, nor complete aggregate composition.
- Callers explicitly inspect relevant roots, ancestors, and known member paths. An exact ancestor mapping does not rewrite a descendant's native plan.
- Share one frozen mapping configuration between the built-in inspector and environment provider in a service container. Return immutable backing collections. Ship through the existing Config package/module, with two neutral examples and complete reference, usage, limits, and discovery documentation.
- Choose Approach B: shared pure internal metadata generators. Approach A, a minimal request-based adapter, was declined because it retains a separate projection layer and unnecessary resolution-scope dependency.

## Public API

Add these contracts in `ForgeTrust.AppSurface.Config`; existing provider interfaces gain no members:

```csharp
public enum EnvironmentCandidateScope
{
    Scoped,
    Unscoped,
}

public sealed record EnvironmentNativeCandidate(
    string Name,
    EnvironmentCandidateScope Scope,
    bool IsLegacyAlias,
    bool IsExplicitMapping);

public sealed record EnvironmentNativeKeyPlan(
    AppSurfaceConfigKey Key,
    IReadOnlyList<EnvironmentNativeCandidate> Candidates);

public sealed record EnvironmentCompositionPathCandidate(
    string Name,
    EnvironmentCandidateScope Scope,
    bool IsHierarchical);

public sealed record EnvironmentCompositionPathPlan(
    AppSurfaceConfigKey Path,
    IReadOnlyList<EnvironmentCompositionPathCandidate> Candidates);

public interface IEnvironmentConfigCandidateInspector
{
    EnvironmentNativeKeyPlan InspectNativeKey(
        string environment, AppSurfaceConfigKey key);

    EnvironmentNativeKeyPlan InspectNativeKey(
        string environment, string strictInput);

    EnvironmentCompositionPathPlan InspectCompositionPath(
        string environment, AppSurfaceConfigKey path);
}
```

The records keep the shown positional constructor signatures and compiler-generated deconstruction. For each plan, explicitly redeclare its `Candidates` property with a private readonly `ImmutableArray<TCandidate>` backing field. Initialize that field from the primary constructor's `Candidates` parameter through one copying helper. The public property's getter returns the immutable array as `IReadOnlyList<TCandidate>`; its `init` accessor assigns the field through that same helper. The helper rejects a null collection or null entries and creates an independent immutable array from its input. It never stores the supplied collection. Constructor initialization and `with { Candidates = suppliedList }` therefore both validate and copy.

Explicitly redeclare `Key`/`Path` with a private readonly immutable-key backing field, a null-checking primary-constructor initializer, and a null-checking `init` accessor. Candidate elements are sealed immutable records containing strings, booleans, and the scope enum; changing an element with a record expression creates a separate element.

Use the compiler-generated plan copy constructor, with no custom copy constructor: its shallow field copy is safe because the backing fields contain only immutable keys and immutable arrays. `with { }` may share those immutable values. A `with` assignment to `Candidates` must invoke the copying `init` accessor, so it cannot replace the field with a caller-owned mutable list. Compiler-generated `Deconstruct` reads the explicitly declared public properties. This uses the documented [record copy behavior](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/record) and [init access to readonly fields declared in the same type](https://github.com/dotnet/csharplang/blob/main/proposals/csharp-9.0/init.md). These are the supported construction paths; do not add a mutable-list field or a bypassing constructor. Tests must mutate both a constructor-supplied list and a list assigned through `with`, verify retained plans and deconstructed collections remain unchanged, and cover a plain `with { }` copy.

### Entry-point behavior

| Entry point | Interpretation | Generator and mapping behavior |
| --- | --- | --- |
| Typed native key | Always typed semantics, regardless of hidden parser provenance on a supplied key | Native generator; canonical or exact mapped candidates; no compatibility aliases |
| Strict native string | Parse with `AppSurfaceConfigKey.Parse`; attach strict-string origin | Native generator with existing strict compatibility aliases; no dot-only translation |
| Composition path | Use the supplied literal segments through current direct-path projection | Composition generator; native mappings do not apply |

The string overload stays strict even when the manager's migration options translate dot-only application strings. `Service.ApiKey` is one literal segment here. Refer users needing manager migration behavior to the [logical-key input guidance](https://github.com/forge-trust/AppSurface/blob/main/guides/config-logical-keys.md#application-strings-and-declarations); do not add an ambiguous dotted-path overload.

`Scope` describes the producing lookup layer. `IsLegacyAlias` is native compatibility provenance. `IsExplicitMapping` is true on both native candidates only when an exact mapping replaced convention lookup. `IsHierarchical` identifies the composition producer, rather than inferring shape from underscores in the final name.

### Ordering and examples

Native generation retains scoped then unscoped canonical/mapped candidates, followed by the existing strict aliases. Explicit suffix casing is preserved. Composition generation retains scoped flat, unscoped flat, scoped hierarchical, unscoped hierarchical order. Each family's normalization remains separate, including its existing environment-name rules.

For `Production` and typed `Service:Api-Key`, native inspection returns `PRODUCTION__SERVICE__API-KEY`, then `SERVICE__API-KEY`, both without legacy or mapping flags. Composition inspection returns `PRODUCTION_SERVICE_API_KEY`, `SERVICE_API_KEY`, `PRODUCTION__SERVICE__API__KEY`, then `SERVICE__API__KEY`.

Ordinal de-duplication keeps the first producing candidate and its metadata. For composition path `Service`, the surviving sequence is `PRODUCTION_SERVICE` (scoped flat), `SERVICE` (unscoped flat), `PRODUCTION__SERVICE` (scoped hierarchical). The duplicate unscoped hierarchical `SERVICE` adds no second entry and does not change the flat entry's flag.

An exact mapping of `Service` to `Root_Config` yields native `PRODUCTION__Root_Config` and `Root_Config`. It changes neither the native plan for `Service:ApiKey` nor the composition plan for `Service`.

### Rejection and limits

- Every inspector entry point rejects a null environment and its null key/path/string argument with `ArgumentNullException` naming that argument.
- Malformed non-null strict input uses the existing parser's `FormatException`; no second grammar is introduced.
- A valid logical native key without a supported canonical encoding or exact mapping throws documented `InvalidOperationException`, matching the current generator failure. Never turn failure into an empty successful plan.
- Preserve existing environment normalization, including non-null empty or unusual strings; do not introduce new environment grammar.
- Invalid mapping options fail with the existing `OptionsValidationException` when the shared snapshot is created. Reuse current duplicate, suffix, collision, and positive-capacity validation.
- Full declaration collisions, dynamic reverse claims, current-environment prefix restrictions, presence, conversion, and winning values remain resolver/startup concerns. A syntactically generated plan can exist for a request resolution later rejects. Inspection does not certify native ownership or reserve a name.
- Plans are fully materialized before return, so generation exceptions occur during the call, never later during enumeration. There is no retained per-key cache, claim capacity consumption, or unbounded inspection history.

## Internal architecture and lifecycle

1. Introduce an internal immutable `EnvironmentConfigMappingSnapshot` containing the result of `AppSurfaceEnvironmentConfigOptions.Snapshot()` and the captured `MaxAdHocClaims`. Register it once per service container. Creation reads finalized `IOptions.Value`, after normal Configure/PostConfigure callbacks, at the first inspector/provider construction. Later mutation cannot affect either consumer, including when they are resolved in opposite orders. Separate hosts remain isolated. Configure options before building/using the container; mutation concurrent with first construction is unsupported.
2. The built-in provider and inspector consume that same snapshot. Preserve the provider's existing direct-construction test seam by delegating it through the snapshot creation path. Use an explicit module factory or unambiguous internal constructor to avoid DI constructor selection ambiguity. Preserve resource-option snapshots, declaration validation, startup forcing, provider precedence, and all resolution assertions.
3. Add narrow pure metadata-producing entry points inside `EnvironmentConfigCodec` and `ConfigEnvironmentCandidates`. Move their existing generation logic into those cores; current request-based/native tuple and composition string-only helpers delegate and project names. This is an extraction of current rules, not a new normalization algorithm or a new common rule across families.
4. The native core accepts the environment, key, explicit input-origin/original spelling, and frozen mappings without creating `ConfigProviderRequest` or `ConfigResolutionScope`. Existing resolver adapters pass their actual provenance unchanged. The typed inspector explicitly selects typed origin; strict inspection parses once and explicitly selects strict origin.
5. The composition core attaches scope/shape before the existing ordered ordinal de-duplication. Existing `GetPathCandidates` delegates to it and projects names, preserving all direct-composition callers. Do not parse metadata back out of string prefixes or post-dedup array indexes.
6. Register a default singleton `IEnvironmentConfigCandidateInspector` through `AppSurfaceConfigModule`. Its default implementation depends only on the frozen mapping snapshot and pure generators, never on providers, the declaration registry, resolution scopes, filesystem services, or mutable claim objects. The guarantee covers framework-owned construction and calls; arbitrary application options callbacks remain application code. Construction must not resolve unrelated source services.

Primary change surfaces are the new inspector/contracts and snapshot, [native codec](https://github.com/forge-trust/AppSurface/blob/main/Config/ForgeTrust.AppSurface.Config/EnvironmentConfigCodec.cs), [composition candidates](https://github.com/forge-trust/AppSurface/blob/main/Config/ForgeTrust.AppSurface.Config/ConfigEnvironmentCandidates.cs), [environment provider](https://github.com/forge-trust/AppSurface/blob/main/Config/ForgeTrust.AppSurface.Config/EnvironmentConfigProvider.cs), [module registration](https://github.com/forge-trust/AppSurface/blob/main/Config/ForgeTrust.AppSurface.Config/AppSurfaceConfigModule.cs), focused Config tests, and existing packed-consumer fixtures. Keep internal translated-member resolution behavior unchanged.

## Independent perspective and tradeoffs

A fresh in-host Codex reviewer recommended shared pure metadata generators and a shared snapshot, challenged no accepted premise, and requested explicit rejection behavior, real collection immutability, typed provenance handling, and first-producer composition metadata. Those points are specified above. Claude Code was unavailable, so there is no outside-provider or cross-model verification. The second opinion is static design advice, not a passing implementation test.

Primary .NET research showed that [GetDebugView reads provider values before its redaction callback](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Configuration.Abstractions/src/ConfigurationRootExtensions.cs); it cannot satisfy this zero-read boundary. The [.NET options lifecycle](https://learn.microsoft.com/en-us/dotnet/core/extensions/options) supports freezing after configuration callbacks; choosing one shared immutable copy is our design inference. Conventional planning/execution separation remains appropriate; no broader insight is claimed.

Approach B touches two generator seams and provider construction, so its regression surface is larger than a minimal adapter. Exact expected tables, unchanged existing tests, public parity tests, and construction-order tests are required safeguards. Planning estimate: human 1.5–2.5 days / Codex 4–6 hours plus verification; not measured. There is no data migration. Consumers retain their old guards until caller-level parity passes, and can revert inspector adoption independently.
