## Problem Statement

AppSurface has an [Evidence planner, CLI, and host contract](../../start-here/evidencehost.md), but no AppSurface CI workflow calls `appsurface evidence`. A maintainer cannot point at a live, safe reference run that proves a checked-in policy selected the work for an exact change and that the resulting manifest supports the CI verdict. Current independent workflows still decide what to run in YAML. The AppSurface repository also has no required status check in its active default-branch ruleset, so publishing a green example alone would not create a merge gate.

The first adopter is AppSurface's own maintainers. The intended outcome is a working required PR check plus a release invocation of the same evidence runner. It should be possible to copy the documented pattern later, but this issue does not promise a general reusable workflow interface for other repositories.

## What Makes This Cool

The workflow says *which revisions and policy were evaluated, why a profile was selected, what every obligation required, and whether the evidence actually closed it*. A docs-only change receives an explicit `NoEvidenceRequired` claim. A code change whose selected producer or disposable resource fails cannot become green because some other CI job passed. The console, GitHub summary, and machine manifest render one verdict from one plan. A fork can still be inspected, but it cannot borrow a trusted claim.

## Constraints

- [#777](https://github.com/forge-trust/AppSurface/issues/777) is an AppSurface-owned reference path, not a new CI scheduler, deployment system, generic plugin loader, or cross-job aggregation format.
- The [existing EvidenceHost design](appsurface-evidencehost-contract-first.md) owns the contract boundary: base-owned policy and explicit host registrations; separate trusted-tool and subject checkouts; [coverage core](evidence-coverage-core-extraction.md) reuse; typed producer/resource/obligation closure; bounded cleanup; observation-only execution for untrusted inputs.
- The current [planning CLI](../../Cli/ForgeTrust.AppSurface.Cli/EvidenceCommands.cs) accepts policy and path/diff inputs but has no authoritative base/head arguments. Its run command can execute the built-in coverage producer; it cannot yet execute every resource-backed AppSurface profile. The [plan contract](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/EvidenceContracts.cs) records a normalized diff digest but not base/head or the exact source diff bytes. These are implementation gaps, not values YAML can invent.
- Required-check behavior depends on GitHub event and ruleset semantics. The current default-branch ruleset requires reviews but no CI status. A planned gate must be proven on an actual PR before that ruleset changes.
- No production credentials, mutable release operations, or head-controlled workflow/host/policy instructions enter the evidence run. The reference release profile remains non-mutating.

## Premises

1. **Selection is policy-owned and revision-bound.** The authoritative plan includes full base and head Git object IDs, SHA-256 of the exact captured source diff bytes, normalized change digest, policy digest, profile, and plan digest. CI regenerates and verifies the source diff from those objects with fixed Git options before `explain` and `run`; both commands consume the same immutable snapshot. A self-consistent manifest without this external revision check is insufficient.
2. **Only the manifest decides the gate.** A PR passes only for a verified, current-base-and-head, gate-eligible `TargetedComplete` or explicit `NoEvidenceRequired` claim. `NoEvidenceRequired` is not a synonym for a skipped job. Missing producer, resource, obligation, required artifact, cleanup, or envelope state produces no complete claim and a failed gate. A release pipeline requires `ReleaseComplete` with release eligibility; a PR check cannot reinterpret a targeted claim as release complete. Policy selects the candidate profile from the diff; trusted event context separately determines whether that profile may issue a PR or release claim.
3. **The trusted control plane is base-owned.** The workflow, policy, host registrations, runner, and envelope verifier come from the protected base/trusted-tool revision. The head is only the subject under test. No subject file can choose a command, image, mount, token, network capability, producer, or artifact root.
4. **Fork and other untrusted inputs remain observational.** They receive no privileged capability or complete claim. The required check fails until reviewed content is promoted to a trusted same-repository branch and a new PR-eligible run evaluates that exact promoted head. A manual `workflow_dispatch` report alone cannot satisfy the PR's required check.
5. **The reference proves all AppSurface-selected profiles.** The host must actually run every producer/resource required by the checked-in AppSurface policy, including its non-mutating release profile. Unsupported profile or missing registration fails closed; YAML never silently downgrades the profile.

## Cross-Model Perspective

A fresh `combo/sub` review supported a base-owned evidence path but challenged the original claim that a policy, diff, and plan digest alone identify the tested change. It observed that two revision pairs can yield the same normalized paths and that a GitHub event's merge checkout can differ from the requested head. We accepted the challenge: exact base/head identities and the captured diff-byte digest belong in the plan and manifest contract, and CI must independently regenerate the diff before execution. The reviewer also suggested a trusted manual rerun for forks; GitHub's required-check rules make that insufficient as a PR gate, so promotion to a same-repository branch is the explicit path.

## Approaches Considered

- **A — Narrow live PR gate (M; about 2–4 human days / 4–8 agent hours).** Gets coverage and no-evidence cases live sooner, but leaves resource-backed and release-profile completeness unproved. Rejected because the selected reference would still demonstrate only the easy branch of EvidenceHost.
- **B — Complete AppSurface EvidenceHost gate (L; about 1–2 human weeks / 1–2 agent days). Selected.** Builds one revision-bound runner and explicit AppSurface host registrations, exercises every policy-selected profile, then makes the PR check required after live proof. The extra work is concentrated in real host execution and trust isolation.
- **C — Versioned reusable workflow (XL; about 2–3 human weeks / 3–5 agent days).** Adds a public consumer input/output and compatibility surface before the first live adopter. Deferred until AppSurface's own path is stable.

## Recommended Approach

### 1. Capture and bind the exact change

The PR controller reads the event's target-base tip and head SHA as data, validates full commit IDs, fetches both objects by SHA, and computes a fixed-options `git diff` between them. It records the source bytes once in a bounded file, independently regenerates the same bytes from the fetched objects, and fails if they differ. The comparison is deliberately the explicit pair rather than an implicit checkout, merge commit, or ambient Git state. This may select extra work when the base advances; that is a conservative cost, never a missing-evidence shortcut. The ordinary build workflow remains responsible for merge-commit compatibility. The plan also records the PR number, target-base tip, workflow/run identity, and head SHA as bounded provenance fields, but these are not substitutes for Git object verification. Immediately before the final verdict, the controller rereads the PR's current target-base tip and head via the GitHub API and rejects either mismatch as stale; a completed run is never retroactively reinterpreted for a new pair.

Extend the versioned Evidence contracts and the [CLI](../../Cli/ForgeTrust.AppSurface.Cli/EvidenceCommands.cs) with authoritative `--base-revision`, `--head-revision`, and `--diff-file` inputs. A new schema version records `SourceDiffDigest` separately from the existing normalized `DiffDigest`; plan and manifest digests cover both revisions and both digests. `explain`, `run`, and `verify` use the same canonical plan identity. Gate mode rejects path-only input, abbreviated SHAs, missing Git objects, a mismatched source diff, stale policy, or a head changed since the event. Local non-gate CLI use can keep its existing path/diff ergonomics and must not imply gate eligibility. Publish the schema migration and compatibility rules in the [Evidence contract reference](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/README.md) and [EvidenceHost guide](../../guides/evidencehost-cookbook.md).

### 2. Execute a closed AppSurface policy in one host

Check in an AppSurface policy whose every repository path is accounted for by an explicit rule or conservative fallback. It distinguishes docs-only `NoEvidenceRequired` from code/coverage, resource-backed integration, and non-mutating release profiles. Renames evaluate both sides; deletions and mixed docs/code changes cannot collapse to docs-only. Policy selects only named, base-registered resources, producers, obligations, assertions, and artifact slots. A release profile runs only in a protected release context; selecting it in a PR context fails as an event/profile mismatch rather than issuing a release claim.

A dedicated AppSurface host runner composes the [EvidenceHost bootstrap](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceHostBootstrap.cs) with explicit first-party registrations. It invokes the extracted coverage core through its existing seam, provisions disposable required resources through Aspire adapters, and runs the selected AppSurface integration and package/release evidence as typed producers with bounded readiness, execution, artifact, and cleanup behavior. It does not treat existing separate workflow job conclusions as producer results. The host owns one manifest even on producer failure where the contract permits one. A missing registration or resource returns an incomplete/invalid manifest and nonzero gate exit. Any capability that AppSurface cannot run safely stays outside the policy until a concrete, tested producer exists; the conservative fallback cannot declare it satisfied.

For the protected release invocation, the subject is the peeled commit of a protected annotated release tag, not the workflow's ambient checkout or a user-supplied branch name. The trusted release verifier reads the tag object and commit from Git, checks the tag/version against the existing protected release-publish validation, and records the tag object ID, peeled commit, comparison-base commit, and SHA-256 of each policy-declared release package or archive in the plan and manifest. A package producer hashes the exact output it verified; publishing may consume only those digest-matching artifacts if the claim is used to authorize publication. A changed tag, rebuilt artifact with different bytes, missing declared artifact, or mismatched release event invalidates `ReleaseComplete`. Release policy still selects the candidate profile from the explicit comparison-base/tag-commit diff; the protected event and artifact checks grant release eligibility separately.

### 3. Separate trusted control and subject execution

The PR workflow uses a base-owned, PR-eligible trigger such as `pull_request_target` only after a live pilot verifies event availability, check association with the PR's current head, and repository event policy. It uses pinned actions, minimal read permissions, `persist-credentials: false`, no secrets, and separate read-only trusted-tool and subject checkouts. The supported runner is an ephemeral GitHub-hosted VM. The trusted controller runs outside a rootless OCI subject container pinned by image digest. The container receives only a read-only subject source mount and a dedicated writable scratch mount. It has a non-root UID, read-only root filesystem, dropped capabilities, no-new-privileges, bounded CPU/memory/PIDs, and no token, Docker/Podman socket, host home, trusted-tool mount, or runner credential files. For a profile without dependencies it has no network; a resource-backed profile uses a per-run internal network with only its declared disposable services and explicit egress denial, including denial of the host gateway and cloud metadata endpoint. Trusted code starts the container with argument arrays, validates its exit status and declared artifacts copied out of scratch, and treats all subject output as untrusted data. The base-owned envelope verifier checks this exact mount/network/capability configuration, runner class, root identities, subject/trusted revisions, and capability evidence immediately before resource provisioning. Inputs from PR titles, paths, or head files are never interpolated into shell commands. If the runner cannot enforce these properties, trusted claims are disabled.

The controller owns resource labels and an external supervisor process, independent of the EvidenceHost process, with a per-run 10-minute cleanup deadline. Normal `finally` cleanup and an `if: always()` CI step ask the supervisor to stop containers/services, remove the per-run network and scratch data, and attest completion; failed or timed-out cleanup prevents a complete claim. A forced EvidenceHost-process kill is tested with the supervisor still alive and must converge within the declared deadline. If the entire VM is lost, no final manifest/check success can be issued, and its local-only resources die with the ephemeral VM; provider VM-destruction latency is outside the 10-minute claim. Persistent/self-hosted runners and external shared resources are unsupported until they have a separately demonstrated external reaper.

For fork or otherwise untrusted heads, the workflow may emit a bounded observation report from a dependency-free safe subset; it always records `ObservationOnly` and exits the required gate nonzero. Maintainers can review and promote an exact commit to a same-repository branch, then run the normal PR path on a replacement or updated PR. The fork PR's observation does not become green by approval label or manual dispatch. If GitHub's policy prevents the intended PR trigger or attaches its check to the wrong revision, rollout stops before ruleset activation; use a separately designed base-owned PR-eligible check publisher rather than weakening the trust boundary.

### 4. Derive one bounded output and turn it into a gate

After host completion, verify the manifest against the captured plan, source diff, policy, selected profile, artifact hashes, trust envelope, and current PR head. One renderer produces the terminal verdict, GitHub step summary, and machine JSON from that verified result. It prints claim kind, eligible gate, profile/rule rationale, base/head short IDs, selected/closed/missing obligation IDs, and stable diagnostic codes; it never prints secret values, raw producer logs, arbitrary file contents, or unbounded changed-path lists. It truncates and counts long collections deterministically and stays below GitHub's [1 MiB step-summary limit](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands). Artifact upload and summary writing are presentation steps, not verdict sources; an upload failure cannot turn an incomplete run green. A pre-plan validation failure emits a bounded diagnostic and failed status without inventing a manifest.

The gate job has a stable name, runs on PR `opened`, `synchronize`, `reopened`, `ready_for_review`, and base-target `edited` events without path filters or job-level skipping, and explicitly exits nonzero for `None`, `ObservationOnly`, invalid, incomplete, stale, cancelled, or wrong-scope claims. This avoids GitHub's [skipped-job success semantics](https://docs.github.com/en/pull-requests/reference/status-checks). Keep the existing build/test checks while the new gate runs in observation mode. After successful same-repository, docs-only, failing, and fork PR pilots prove the check attaches to the current PR head, add that exact check to the default-branch ruleset with [strict required-check freshness](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). When the target base advances after a run, GitHub must block merging until the PR branch is updated; that head update emits `synchronize` and a new base/head-bound check. The live pilot must prove this behavior, including a base update while the head is unchanged, before enforcement. If merge queue is adopted, add `merge_group` support and revalidate before queue activation. A manual release invocation uses the same runner and release-specific verifier but is never counted as the PR's required check.

## Success Criteria

1. On a live AppSurface PR, `explain` and `run` report the same plan digest for verified base/head/diff/policy inputs; altering any one makes the gate fail before a complete claim. A new head causes a new run; a base update makes the strict required check stale until the head is updated and rerun. The final verifier checks both current SHAs, so an old manifest cannot satisfy either new revision.
2. Docs-only, code, mixed/renamed/deleted, resource-backed, and release fixtures select their candidate profiles solely from policy; trusted PR or protected release context separately determines claim eligibility. Docs-only produces explicit `NoEvidenceRequired`; unrecognized paths select the conservative profile or fail.
3. Positive host runs yield verified `TargetedComplete` or `ReleaseComplete` claims as appropriate. Injected missing producer, unavailable resource, failed assertion, absent required artifact, cleanup failure, or envelope mismatch yields no complete claim and a failed gate. Release fixtures also prove tag-object/peeled-commit and package-digest binding against the protected release invocation. Fork/untrusted runs yield `ObservationOnly` and a failed required check.
4. Terminal, GitHub summary, and manifest agree on the claim and missing obligations. Secret canaries and oversized/malicious paths do not leak or exceed output limits. Normal cancellation and a forced host-process kill clean up the disposable topology within the in-VM 10-minute bound; entire-VM loss yields no complete claim and leaves no shared resource.
5. A real PR demonstrates the stable evidence check on the current head, a base-advance freshness block, and the default-branch ruleset requires it with strict freshness. The repository can merge a qualifying trusted PR and blocks an incomplete or fork-observation PR. Existing checks remain green, formatting and changed-code branch tests pass, and solution coverage is run when practical.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — completeness

**Problem**

> The release plan records a comparison-base commit, but the design does not define which trusted revision supplies that base or how the release event binds to it. Since policy selects the release profile from the tag-commit diff, different baselines can select different obligations while still producing a revision-bound manifest.

**Remedy**

> Define a deterministic, trusted source and selection rule for the release comparison base, bind that base to the protected release event, and test missing, changed, and mismatched baseline cases before allowing a ReleaseComplete claim.

### R2-2 — completeness

**Problem**

> The design says a changed tag invalidates ReleaseComplete, but it does not specify a final check of the tag ref/object (or an enforced immutability guarantee) between evidence capture, verdict issuance, and publication use. A tag that moves after capture could leave a claim authorizing artifacts for a commit the release tag no longer identifies.

**Remedy**

> Require the trusted verifier to recheck the protected tag ref, tag object ID, and peeled commit immediately before issuing ReleaseComplete and before any publication consumes the claim, or specify and verify an equivalent immutable-tag guarantee; include a retagging race test.

### R2-3 — feasibility

**Problem**

> The subject can write arbitrary content to scratch, and trusted code copies declared artifacts out, but the copy-out boundary has no path-containment, file-type, or size rules. A malicious subject could use symlinks or special files to make the trusted copier escape scratch or process unbounded data, undermining the stated isolation boundary.

**Remedy**

> Specify a no-follow extraction protocol that accepts only normalized relative paths resolving inside scratch and regular files, enforces per-file and aggregate count/size limits, and tests traversal, symlink, special-file, and oversized-artifact cases.

### Prior finding evidence

**R1-3 → R2-3 (persisting)**

> Recommended Approach 3 specifies the ephemeral VM, rootless OCI container, mounts, credential/socket exclusions, resource network and egress limits, and envelope checks, but only says declared artifacts are copied from subject-writable scratch; it does not constrain that transfer so it cannot follow paths outside scratch or expose trusted host data. See R2-3.
