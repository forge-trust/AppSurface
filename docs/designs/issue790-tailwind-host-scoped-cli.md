## Problem Statement

[`ForgeTrust.AppSurface.Web.Tailwind`](../../Web/ForgeTrust.AppSurface.Web.Tailwind/README.md)
currently declares unconditional project dependencies on five native Tailwind runtime
packages. NuGet restores all five and treats their files as ordinary runtime assets,
although the Tailwind executable runs only on the machine performing the build. A
project that merely references a Tailwind-enabled web assembly can therefore receive
native Linux, macOS, and Windows binaries it will never execute.

Issue [#790](https://github.com/forge-trust/AppSurface/issues/790) moves that CLI to
its correct boundary: a host-selected build tool. The normal package must acquire only
the executable for the build host, keep it out of application and project-reference
outputs, and retain generated CSS plus development watch mode without Node.js.

## What Makes This Cool

The good version disappears. A downstream consumer can inspect its output and find no
Tailwind executable at all. Meanwhile, the web project that actually builds CSS gets
one verified `tailwind-<version>/<host-rid>/` cache entry, and watch mode finds the
same host-compatible tool. The integration behaves like an SDK feature rather than a
five-platform runtime bundle.

## Constraints

- Preserve public build properties (`TailwindEnabled`, `TailwindInputPath`,
  `TailwindOutputPath`, `TailwindCliPath`, `TailwindVersion`, and
  `TailwindDownloadCacheRoot`) and the public `AddTailwind` / `TailwindOptions.CliPath`
  escape hatches documented in the [Tailwind package README](../../Web/ForgeTrust.AppSurface.Web.Tailwind/README.md).
- Preserve the compiled MSBuild task and its explicit build policy: it must not search
  `PATH`; explicit `TailwindCliPath` wins; host selection is based on the build host,
  not a consuming application's `RuntimeIdentifier`.
- Preserve the separate watch policy: watch remains development-only and non-blocking
  when no usable CLI can be acquired. It may retain its documented development `PATH`
  fallback after the verified cache and explicit `TailwindOptions.CliPath` checks.
- Support exactly the existing build-host map: `linux-x64`, `linux-arm64`, `osx-x64`,
  `osx-arm64`, and `win-x64`; Windows Arm64 continues to use the supported `win-x64`
  executable under emulation.
- Use only the official Tailwind release binary and `sha256sums.txt` identified by
  [`Tailwind.Common.props`](../../Web/ForgeTrust.AppSurface.Web.Tailwind/Tailwind.Common.props).
  Cache identity remains version + RID + binary name, and every resolver-acquired cache
  executable is hash-checked before use.
- Do not add a public resolver, manifest, CLI command, or diagnostics dashboard.
  A stable build diagnostic and documentation are sufficient recovery surfaces.
- Keep the existing real `.nupkg` consumer proof. Do not replace it with a source-tree
  or mocked package test just to make the suite faster.

### Cache and explicit-path contract

`TailwindDownloadCacheRoot`, when non-empty, is the highest-precedence cache root.
Otherwise the resolver uses, in order, `XDG_CACHE_HOME`, `LOCALAPPDATA`, `HOME`, then
`USERPROFILE`, with the AppSurface Tailwind subdirectory used by the existing cache
helper. It canonicalizes the chosen root before use and rejects unsafe RID and binary
path components. The one canonical entry is
`<root>/tailwind-<TailwindVersion>/<host-rid>/<runtime-binary-name>`; its checksum file
is `sha256sums.txt`, its lock is `<runtime-binary-name>.lock`, and temporary downloads
are `<runtime-binary-name>.partial-<guid>`. A property override therefore always wins
over environment-derived defaults and source-tree and packed consumers use the same
identity.

`TailwindVersion` must be a normalized stable `major.minor.patch` value. It is rejected
before path or URL construction when it contains path separators, `..`, controls,
whitespace, URL-reserved characters, or does not parse as exactly three non-negative
numeric components. A future prerelease-version policy needs a separate documented
parser update; #790 preserves the current stable pinned-release policy. Invalid values
produce `ASTW012` with classification `invalid-version` and no cache or network work.

The cache is user- or CI-owned, not an application output. #790 adds no size limit or
automatic version pruning: a Tailwind version bump creates a new entry and operators
may delete an unused cache root. The resolver must not weaken permissions or silently
move to a broader shared directory. A non-writable root is a recoverable acquisition
failure unless an explicit CLI path is supplied. Every final binary is rehashed before
execution, so stale or poisoned content cannot become trusted merely by remaining in
the cache.

An explicit `TailwindCliPath` or `TailwindOptions.CliPath` resolves relative to its
existing project/content root and is checked for existence before execution. It bypasses
cache lookup, cache writes, and network acquisition. #790 does not attempt to infer a
foreign binary's architecture: an unreadable, non-executable, or wrong-platform override
fails through the existing process-start diagnostic, while a missing override retains
the existing explicit-path diagnostic. Windows has no chmod step; on Unix the resolver
sets the executable bit after hash verification, treating an already-executable file as
a no-op and an ACL/permission failure as an acquisition failure. Explicit overrides are
trusted escape hatches and are not compared to the pinned Tailwind release checksum.

## Premises

1. Package-installed MSBuild targets cannot alter `PackageReference` or
   `PackageDownload` after restore. NuGet explicitly forbids those restore-affecting
   items in package `.props`/`.targets`; the [NuGet MSBuild asset guidance](https://learn.microsoft.com/en-us/nuget/concepts/msbuild-props-and-targets)
   is the boundary.
2. A Tailwind standalone executable is a build-host tool, not a runtime dependency of
   a compiled web assembly or a project that references one.
3. A usable offline build means a cache that was previously populated from the pinned
   source and hash-verified, or an explicit CLI path. A brand-new offline machine must
   fail with a clear recovery diagnostic rather than execute an unverified file.
4. Before coding the resolver, run a bounded five-host restore-graph probe using only
   supported pre-restore NuGet mechanisms. It succeeds only if one universal main
   package automatically produces exactly one host-native dependency edge per *actual
   build host*, needs no second restore or consumer configuration, and keeps native
   payloads out of a non-executing project-reference consumer. Passing `--runtime` or
   setting a consuming project's `RuntimeIdentifier` is not proof because those are
   target-runtime inputs, not build-host discovery. This is evidence gathering, not
   permission to reverse the selected architecture: a positive result returns the
   design to the maintainer for a fresh decision; otherwise the cache resolver proceeds.

## Cross-Model Perspective

The independent fallback reviewer agreed that the useful outcome is “one correct host
binary, no leaked native payloads, verified cache.” Its constructive challenge was to
test, rather than assume, whether a pre-restore host selector could produce one NuGet
runtime edge. That became the explicit proof gate above. The reviewer also suggested
a five-RID selection matrix and retaining the existing packed-package proof.

## Approaches Considered

- **A. Restore-graph host selector:** rejected as the default because package targets
  cannot fix the graph after restore and automatic build-host selection is unproven.
  The bounded restore-graph probe preserves the chance to revisit this with evidence.
- **C. Explicit hermetic companion runtime:** rejected because requiring every consumer
  to select a host package contradicts the chosen invisible-default experience.

### Scope boundary

README, package-chooser, third-party payload inventory, and the CI variables that
currently enforce runtime-package creation are in scope because they make a changed
native distribution model discoverable, auditable, and release-safe. Deleting,
unlisting, or designing a migration policy for already-published companion packages is
not in scope; #790 records their loss of transitive use and flags their lifecycle for a
separate release decision.

## Recommended Approach

### B. Managed verified cache resolver

1. **Prove or rule out the NuGet alternative first.** Add a temporary or narrowly
   scoped harness with these exact gates:

   1. Pack one universal candidate main package into an isolated local feed. It cannot
      contain a host-specific variant and the consumer cannot set a custom Tailwind
      property, direct companion `PackageReference`, `RuntimeIdentifier`, or
      `TailwindTargetRid`.
   2. Restore a clean Razor consumer once on each native supported build host. Capture
      the package `.nuspec`, `obj/project.assets.json`, restore binlog, and a listing of
      build and publish output. A cross-RID restore on a different host is supplemental
      only and cannot pass the gate.
   3. Assert the main package has exactly one host-native dependency edge, no foreign
      native edge, and no native file reaches a two-project non-executing
      project-reference consumer. Record the artifacts with the test evidence.

   If any native host cannot meet that contract automatically, reject the restore-graph
   alternative. Do not use `TailwindTargetRid` as production restore input: it is a
   task-time test override, not a host-discovery contract.

2. **Remove the normal runtime-package graph.** Remove the five unconditional runtime
   `ProjectReference`s from
   [`ForgeTrust.AppSurface.Web.Tailwind.csproj`](../../Web/ForgeTrust.AppSurface.Web.Tailwind/ForgeTrust.AppSurface.Web.Tailwind.csproj).
   The packed main package must contain its targets, task assembly, managed assets, and
   notices, but no `runtimes/<rid>/native` payload and no dependency on a
   `ForgeTrust.AppSurface.Web.Tailwind.Runtime.*` package. Do not delete published
   companion packages in #790; they stop being normal dependencies and any deprecation
   or unlisting is a separate release-managed decision.

3. **Make acquisition an internal, shared host-tool service.** Extend the shared
   `Internal/` source compiled into both the web and task assemblies with an asynchronous
   resolver that:

   - maps the actual build/runtime host with `RuntimeInformation.IsOSPlatform` followed
     by `RuntimeInformation.ProcessArchitecture`, through `TailwindRuntimeMap`; a
     Rosetta-translated process maps as `osx-x64`, an x86 or Arm process remains
     unsupported, Windows Arm64 maps to `win-x64` under the existing emulation policy,
     and the consuming project's `RuntimeIdentifier` is never read;
   - honors the explicit CLI path before any cache or network work;
   - derives the existing default or overridden `TailwindDownloadCacheRoot` for both
     packed consumers and source-tree execution;
   - reads or acquires only the matching version/RID/binary-name cache entry;
   - downloads the pinned checksum file and matching binary with the existing retry
     settings. The parser trims lines, ignores blank/comment lines, splits whitespace,
     removes an optional leading `*` or `./` from the filename, and accepts exactly one
     matching binary-name hash; malformed, missing, or duplicate matches fail closed;
   - validates the named checksum and the binary SHA-256, marks Unix binaries
     executable, and only then makes the final path visible;
   - serializes an entry with an OS-backed exclusive `FileStream` lock on its `.lock`
     file. Contenders attempt once plus `TailwindDownloadRetries` reattempts, waiting
     `TailwindDownloadRetryDelayMilliseconds` between attempts (five total attempts and
     at most 20 seconds of waits at the current defaults). Every successful contender
     rechecks the final binary before doing any network work. Timeout is `ASTW012` with
     classification `lock-timeout`. The operating system releases the lock when a
     process dies, so a stale lock *file* is reusable rather than deleted by PID or
     clock guess;
   - downloads into a GUID-named partial file, verifies it, then atomically moves it to
     the final name while holding the lock. If a prior final file fails verification,
     the lock owner first moves it to `<runtime-binary-name>.rejected-<guid>`; if that
     move fails, acquisition fails without touching a good final file. The owner removes
     its rejected and partial files after a successful final move in a
     `finally` path and, while holding the lock, may best-effort remove abandoned
     partial files. Cleanup failures must not delete a verified final binary or cause a
     second process to execute a partial file.

   The resolver must use .NET platform libraries and existing package dependencies; no
   downloader package is needed. Its deterministic state machine is: validate final
   cache entry; if invalid, reject it while holding the lock; reacquire and verify when
   possible; otherwise fail before a child process starts. Invalid cache content is never
   executed.

   `ASTW001` remains the sole unsupported-host diagnostic, `ASTW002` remains missing
   version metadata, `ASTW003` remains a missing explicit path, and `ASTW005` remains a
   process-start failure for an explicit or acquired executable. Add `ASTW012 Tailwind
   CLI acquisition failed` for invalid version, invalid cache, checksum failure,
   non-writable root, network/retry exhaustion, and lock timeout. Every `ASTW012`
  message includes the safe host RID, version, redacted cache identity, classification,
  concise cause, and recovery using `TailwindCliPath`, `TailwindDownloadCacheRoot`, or
  the README. It must never include credentials, response bodies, an unredacted URL, or
  an absolute configured cache-root path.

4. **Use the resolver in both execution paths without conflating policy.**
   [`RunTailwindBuildTask`](../../Web/ForgeTrust.AppSurface.Web.Tailwind.Tasks/RunTailwindBuildTask.cs)
   replaces its packaged/sibling/project-runtime candidate fan-out with the internal
   resolver. When no explicit `TailwindCliPath` was supplied, it rejects an unknown or
   unsafe RID; an existing explicit path is resolved and validated first and bypasses
   host mapping, cache work, and network work. Build uses the compiled task and never
   searches `PATH`. [`TailwindCliManager`](../../Web/ForgeTrust.AppSurface.Web.Tailwind/TailwindCliManager.cs)
   and [`TailwindWatchService`](../../Web/ForgeTrust.AppSurface.Web.Tailwind/TailwindWatchService.cs)
   use the same cache identity and verification before their existing development-only
   fallback behavior. `TailwindOptions.CliPath` remains the explicit watch override.
   Production selection never reads the consuming project's `RuntimeIdentifier`; all
   test-only RID overrides remain confined to test seams. Windows Arm64 retains the
   existing `win-x64` emulation policy. #790 does not promise to detect emulation: if
   Windows rejects execution, build surfaces the existing process-start diagnostic and
   watch logs its existing non-blocking failure with the explicit CLI override as the
   recovery path.

5. **Document the delivery boundary.** Update the Tailwind README, the
   [package chooser](../../packages/README.md), and
   [`packages/third-party-payloads.yml`](../../packages/third-party-payloads.yml).
   State that normal consumers download exactly one build-host tool into the verified
   cache, explain how a durable CI cache or one connected build prewarms it, describe
   first-use offline recovery, remove claims about transitive runtime packages, and
   inventory the changed third-party distribution posture. Update package and CI
   workflows only where they currently assume runtime-package packing or
   `TailwindRuntimeBinaryResolutionEnabled`.

## Success Criteria

- A fresh `linux-x64` consumer restore/build has no macOS, Windows, or Linux Arm64
  Tailwind package edge or native file. Equivalent selection proof exists for
  `linux-arm64`, `osx-x64`, `osx-arm64`, and `win-x64`.
- The packed main package contains no Tailwind native runtime payload and its `.nuspec`
  does not transitively depend on any Tailwind runtime companion package.
- A project that references a Tailwind-enabled web assembly but does not execute the
  Tailwind target has no `tailwindcss-*` file in build or publish output.
- A packed consumer with the default configuration acquires the current build host CLI,
  generates CSS, and registers the generated static web asset. The actual executable
  integration test runs on its native host; non-host RIDs use controlled cache stubs to
  verify selection rather than attempting to execute foreign binaries.
- `AddTailwind` development watch resolves the same verified host CLI and retains its
  current development-only, non-blocking failure behavior plus explicit CLI override.
- A primed cache works with network access disabled. Missing, malformed, partial, or
  hash-mismatched cache entries never execute; each produces a precise recovery path.
- Existing ASTW diagnostics unrelated to acquisition keep their codes and behavior.
- Documentation explains the cache location, default behavior, CI caching, offline
  bootstrap, explicit overrides, host versus target RID, and the changed package
  boundary.

### First-use and recovery behavior

| Condition | Build mode | Development watch mode | Recovery |
|---|---|---|---|
| Supported host, missing cache, network available | Acquires and verifies one host CLI, then builds CSS. | Acquires and verifies one host CLI before starting watch. | No action required; cache is populated. |
| Supported host, missing cache, network unavailable or non-writable root | Fails hard with the new stable acquisition diagnostic; no child process starts. | Without an explicit watch path, makes the one development-only `PATH` attempt; if it fails, logs the acquisition cause and runs without watch. | Prime the configured cache on a connected machine/CI cache, fix root permissions, or set the explicit CLI path. |
| Cache checksum malformed, missing, mismatched, or final binary hash mismatched | Rejects only the named bad entry under lock, reacquires when possible, then fails with `ASTW012` if no verified final file results; never executes it. | Without an explicit watch path, makes the one development-only `PATH` attempt after resolver failure; if it fails, runs without watch. | Remove the named cache entry or provide an explicit verified CLI path. |
| No explicit CLI override and unsupported host RID | Fails hard with the existing unsupported-RID diagnostic. | May make its one development-only `PATH` attempt, then logs the classified cause and runs without watch. | Use a supported build host or supply an existing compatible explicit CLI path, which is evaluated before host mapping. |
| Explicit CLI override is missing or the OS cannot start it | Retains existing explicit-path/process-start diagnostics; no cache or network fallback occurs. | Retains existing warning/error lifecycle; no cache write occurs. | Correct the explicit path or remove it to use normal host-tool resolution. |

## Reviewer Concerns

The document completed three adversarial review rounds. The following implementation
details remain intentionally open and must be resolved before coding begins:

- **No cache root:** Define `ASTW012` classification `no-cache-root` when neither
  `TailwindDownloadCacheRoot` nor the supported environment locations are available;
  fail before network or process work and document cache-root and explicit-path recovery.
- **Version and diagnostic tests:** Add malformed, path-like, whitespace, prerelease,
  and overflow version tests, plus assertions that `ASTW012` never exposes credentials,
  response bodies, or sensitive configured-path components.
- **Explicit override on unsupported hosts:** State whether an explicit compatible CLI
  may bypass host-RID rejection. The reviewer proposes allowing it, with unsupported-RID
  rejection only when no override is supplied.
- **Invalid-version diagnostics:** `ASTW012/invalid-version` cannot include a cache
  path because cache-path construction is intentionally skipped. Define its safe message
  fields separately.
- **Complete `ASTW012` taxonomy:** Fix and document the finite classifications:
  `invalid-version`, `no-cache-root`, `invalid-cache`, `checksum-failure`,
  `non-writable-root`, `network-failure`, `retry-exhausted`, and `lock-timeout`.
- **Diagnostic path redaction:** Specify a safe rendered cache-path form or omit the
  path when a custom root could expose a username, token, or other sensitive segment.
- **MSBuild async bridge:** Specify how `RunTailwindBuildTask` awaits the asynchronous
  resolver without deadlock, propagates the existing cancellation request through lock,
  download, and process-start phases, and reports cancellation deterministically.
- **Cache filesystem guarantees:** Require a local cache filesystem with exclusive-lock
  and same-directory atomic-rename semantics, or fail closed with a named `ASTW012`
  classification when a network or virtual filesystem cannot provide them.

## Autoplan Phase 1: CEO Review

### System audit and premise challenge

The current main package has five unconditional runtime-project references, while
`RunTailwindBuildTask` selects only one candidate at build time. That is a real
consumer cost, not a packaging proxy: project-reference consumers can receive native
files without executing Tailwind. The selected boundary therefore remains correct.

| Premise | Assessment | Decision |
|---|---|---|
| Package targets can choose a build host after restore. | Invalid. NuGet package build assets cannot introduce restore-affecting package items, and restore has already written the dependency closure. | Keep the bounded five-host probe as evidence only. |
| One standalone CLI is a build-host tool, not a product runtime asset. | Valid. Build task execution, not the consuming application's target RID, chooses the executable. | Preserve the managed verified-cache direction. |
| A primed verified cache supports offline builds. | Valid, provided absence, invalid content, and an unusable cache root fail before child-process start. | Make the recovery diagnostic and explicit override the complete offline contract. |
| An explicit CLI path should be evaluated before host mapping. | Valid and already implied by the task's resolution order. | State it unambiguously: an existing explicit override may run on an otherwise unsupported host; unsupported-host rejection applies only when no override was supplied. |

### Section 1: Architecture and state model

```text
Build target / development watch
            |
            +-- explicit CLI supplied? -- yes --> resolve relative path --> execute
            |                                      | missing/start failure --> ASTW003/ASTW005
            |
            no
            |
            +--> map actual process host --> supported RID? -- no --> ASTW001
            |                                         |
            |                                        yes
            +--> validate version + root + local-cache filesystem --> ASTW012 on failure
            +--> acquire entry lock --> final verified? -- yes --> execute
                              |                  |
                              |                  no
                              +--> obtain checksum trust metadata + binary --> verify --> atomic publish
                                                                  |                |
                                                                  failure          success
                                                                  ASTW012          execute
```

The shared resolver is the one new internal service, not a public feature. Its state
machine is `Unresolved -> Explicit | HostMapped -> CacheValidated -> Locked ->
Acquired -> Verified -> Published -> Executed`, with terminal `Diagnostic` and
`Canceled` states. A final cache file becomes visible only after hash verification and
same-directory atomic rename while the exclusive lock remains held. Missing input,
invalid version/root, a checksum mismatch, a lock timeout, cancellation, and a failed
download are terminal before process start.

The first concrete architecture correction is a package-pinned trust manifest. A
downloaded binary must match the expected SHA-256 embedded with the pinned Tailwind
version and RID/binary map in first-party release metadata. Fetching the official
`sha256sums.txt` remains a consistency/audit check, not the sole trust anchor. A
Tailwind version bump therefore changes both the version and the five expected digests
in one reviewed release change; tests must reject a validly paired but tampered
downloaded binary/checksum file.

### Section 2: Error and rescue registry

| Codepath | Failure mode | Classification / diagnostic | Rescue action | User sees | Test |
|---|---|---|---|---|---|
| Explicit path | missing relative/absolute file | existing `ASTW003` | No cache/network fallback. | Correct the path or remove it. | Existing plus unsupported-host override test. |
| Host map | unknown process OS/architecture without override | existing `ASTW001` | Stop before cache lookup. | Supported host or explicit CLI recovery. | All map branches. |
| Version parser | blank, prerelease, path-like, whitespace, control, overflow | `ASTW012/invalid-version` | Stop before path/URL construction. | Safe version and override recovery; no cache path shown. | Full invalid-version matrix. |
| Cache root | no override or environment-derived root | `ASTW012/no-cache-root` | Stop before network/process work. | Configure root or use explicit CLI. | All-empty environment test. |
| Cache entry | missing, malformed checksum, hash mismatch, incomplete final | `ASTW012/invalid-cache` or `checksum-failure` | Lock, reject named entry, reacquire only when possible. | Redacted identity and recovery. | Missing/malformed/duplicate/hash cases. |
| Acquisition | non-writable root, transport failure, retry exhaustion, lock timeout | `ASTW012/non-writable-root`, `network-failure`, `retry-exhausted`, or `lock-timeout` | Never execute a partial; build fails and watch warns/non-blocks. | Cache/prewarm/explicit-path recovery. | Root, cancellation, retry and contender tests. |
| Async bridge | MSBuild cancel during lock/download/rename | existing cancellation diagnostic | Propagate token and return false deterministically. | Canceled build, no child process. | Cancel every pre-execution phase. |
| Process start | override or verified cache executable cannot start | existing `ASTW005` | Do not fall through to a different candidate. | Correct explicit path / execution environment. | Existing process-start contract. |

Every `ASTW012` contains only the finite classification, safe host RID, stable version
when validation reached it, and a redacted cache *identity* such as
`tailwind-4.1.18/linux-x64/<binary>`. It never renders a custom-root prefix, URL,
credential, response body, exception stack, or cache path for `invalid-version`.

### Section 3: Security and threat model

| Threat | Likelihood | Impact | Mitigation |
|---|---:|---:|---|
| Cache binary or locally stored sums are replaced | Medium | High | Rehash every final binary against package-pinned expected hash before every execution. |
| Transport supplies matching malicious binary and sums | Low | High | Package-pinned expected digest is the authenticity boundary; downloaded sums are never sufficient alone. |
| Version, RID, or binary name escapes the cache root | Medium | High | Parse normalized stable version and allow only known map values / single filename components before path construction. |
| Concurrent writers expose a partial file | Medium | High | Local exclusive lock, partial GUID name, verification before same-directory atomic publish, then rehash by each reader. |
| Custom root leaks a developer/CI secret in an error | Medium | Medium | Never include absolute custom roots or URLs in diagnostics; assert redaction under failure. |
| Explicit foreign/local CLI is unverified | Accepted | Medium | Preserve the existing deliberate trust escape hatch and make its no-cache/no-network behavior explicit. |

No new network endpoint, secret, user data store, or runtime application API is added.
The only changed trust boundary is build-tool acquisition, so its diagnostics and
release-pinned hashes are part of the feature rather than optional hardening.

### Section 4: Data-flow edge cases

```text
version/root/host inputs
      | invalid or missing
      +----------------------------> ASTW012 / ASTW001, no network or process
      |
      v
entry identity --> verified final? --> yes --> rehash --> build executes / watch starts
      | no                                    |
      v                                       +--> process-start failure --> ASTW005
exclusive lock --> retry final check --> download partial --> hash --> atomic rename
      | canceled / timeout / write failure        | mismatch
      +--------------> ASTW012 / cancellation     +--> reject, cleanup, ASTW012
```

Build and watch deliberately differ only after resolution: build treats a failed
normal resolver path as a stable error and starts no child process; development watch
logs the same classified acquisition failure and starts the app without watch, then may
take its existing `PATH` fallback only after verified-cache and explicit-path checks.
An explicit path always wins before host mapping, so it is the only supported recovery
for an otherwise unknown host.

### Section 5: Code-quality constraints

- Keep one internal resolver with injected filesystem, HTTP/download, clock/delay, and
  host-map seams for deterministic tests. Do not duplicate parsing, cache layout, or
  verification in `RunTailwindBuildTask` and `TailwindCliManager`.
- `RunTailwindBuildTask.Execute()` may bridge with `GetAwaiter().GetResult()` only at
  the task boundary; the resolver itself remains fully async, uses
  `ConfigureAwait(false)`, and receives the task cancellation token in every wait,
  download, file operation, and process phase.
- Replace candidate fan-out, version-directory scans, and sibling runtime-package
  layout inference rather than leaving legacy fallbacks that can restore payload
  leakage or select an unintended version.
- Keep test-only RID/host overrides internal and isolated. Production resolution never
  reads `RuntimeIdentifier` or a target-RID property.

### Section 7: Performance and cache budget

The steady state is one full SHA-256 rehash of the host executable and no network request; the
first-use path has a bounded lock wait of the existing retry budget (five attempts and
at most 20 seconds at defaults) plus the bounded downloader retries. Contention is
per version/RID/binary entry, so unrelated hosts and versions do not serialize. There
is intentionally no automatic cache pruning: operator-owned cache retention is safer
than deleting a known-good tool during a build. Documentation must provide deterministic
CI cache keys (`tailwind-<version>-<host-rid>`) and state that cache size/eviction is
the CI or workstation owner's policy.

### Section 8: Observability and supportability

No dashboard or public inspection API is added. The resolver emits stable MSBuild and
watch messages keyed by `ASTW012` classification, safe RID/version/identity, whether
the cache was reused or acquired, and a recovery action. Verbose build logging may
include stage names but not unredacted URLs, response bodies, absolute custom roots, or
hash source credentials. The README becomes the support runbook: each classification
maps to the expected state, safe remediation, and an offline/CI prewarm example.

### Section 9: Distribution, rollout, and rollback

Release changes must remove the five runtime-project references from the main package,
assert its archive and dependency closure are native-free, and update the third-party
payload inventory from package-embedded native assets to a build-host fetched tool with
release-pinned digest metadata. Release notes must call out the changed delivery model,
the first-use network requirement, primed-cache/offline contract, deterministic CI
cache key, and explicit CLI fallback. Existing directly referenced companion packages
remain compatible and are neither removed nor deprecated here.

Rollback is a package-version rollback or a source revert before release. It is safe
because no data migration or persistent application state changes. A failed release is
detected by the packed consumer, archive closure, supported-host, and project-reference
proofs before publication; consumers that need an immediate escape hatch can configure
the existing explicit CLI path.

### Section 10: Long-term trajectory

This is a reversibility score of 4/5: the selected cache directory is user-owned and
version-isolated, companion packages remain published, and users retain explicit
overrides. It establishes a reusable *internal pattern*, not a generic platform. A
future second build tool could justify a shared abstraction only after it demonstrates
the same cache identity, trust, cancellation, and delivery requirements. The
non-negotiable long-term debt guard is that package release metadata must keep version
and expected digest entries synchronized; validation must make drift fail before pack.

### Ownership, manifest, and process boundaries

`TailwindCliResolver` is one authoritative **linked-source** implementation, not two separately maintained resolvers. Its files live in the Tailwind package's existing `Internal/` folder and compile into the web and task assemblies through the existing shared-source arrangement. It accepts narrow internal inputs (release manifest, runtime-map result, root/environment adapter, HTTP adapter, filesystem adapter) and returns only an internal `TailwindResolvedCli { Path, Rid, Version, CacheState }`. It never builds Tailwind arguments or launches a process. There must be no assembly-specific resolution branch; shared contract vectors run the same manifest, root, RID, cache, and error cases through build and watch adapters.

This source-link is intentional: #790 needs one implementation and test contract without adding a public package or resolver API. `RunTailwindBuildTask` owns the build adapter and receives a packed manifest path. `TailwindCliManager` owns the watch adapter and reads the same manifest bytes embedded as an assembly resource. Both use the same stream-based loader; neither parses a second contract.

The repository source of truth is `Web/ForgeTrust.AppSurface.Web.Tailwind/tailwind.release.json`. It is embedded in the web assembly and packed verbatim as `build/tailwind.release.json`. The package target passes that path to `RunTailwindBuildTask` as `TailwindReleaseManifestPath`; source-tree targets locate the same file beside the targets. Schema v1 is:

```json
{
  "schemaVersion": 1,
  "version": "4.1.18",
  "baseUrl": "https://github.com/tailwindlabs/tailwindcss/releases/download/v4.1.18",
  "assets": [
    { "rid": "linux-x64", "binaryName": "tailwindcss-linux-x64", "sha256": "<64 lowercase hex characters>" }
  ]
}
```

The complete file contains the five existing map entries in stable order: `linux-x64`, `linux-arm64`, `osx-x64`, `osx-arm64`, and `win-x64`. The loader rejects an unknown schema, duplicate/missing RID, binary mismatch with `TailwindRuntimeMap`, malformed/non-lowercase digest, noncanonical version, or a version/base-URL mismatch with `tailwind.version` and `Tailwind.Common.props` before cache or network work. The canonical manifest version alone feeds URLs, cache identity, diagnostics, and CI keys.

The fetched official `sha256sums.txt` remains an upstream audit signal, never the trust anchor: its matching digest must equal the package-pinned manifest digest or acquisition fails with `ASTW012/checksum-failure`. A tampered binary paired with a tampered downloaded sums file is therefore still rejected. Release verification changes manifest, version metadata, official URL, and all five digests atomically in one reviewed change. Before pack, a focused test validates those fields against the runtime map and a controlled sums fixture; the package-artifact gate then asserts the packed manifest exists byte-for-byte and matches its embedded resource copy, while the main `.nuspec` has no companion dependency or native Tailwind asset.

`TailwindInvocationBuilder` retains the current argument contract: build uses `-i`, `-o`, and `--minify`; watch retains `--watch`. `TailwindProcessRunner` remains the only launch boundary. It receives the resolved path, existing working directory, inherited environment, bounded stdout/stderr, and cancellation token. Its CliWrap/shim behavior, nonzero-exit treatment, and `ASTW005` mapping remain intact. A launch failure never triggers another resolver candidate, cache rewrite, or `PATH` fallback.


### Resolution, cancellation, and cache safety contract

The resolver validates a supplied explicit path first. An existing override returns a resolved executable without invoking runtime mapping; a missing override is `ASTW003` and is authoritative. Only the no-override branch maps host RID, reads the manifest, selects a root, and considers cache or network work. Build never considers `PATH`.

`TailwindVersion` is canonical only if it matches `^(0|[1-9][0-9]{0,8})\\.(0|[1-9][0-9]{0,8})\\.(0|[1-9][0-9]{0,8})$` using ASCII input and each component parses as `Int32`. Prerelease/build suffixes, leading zeroes, Unicode whitespace, controls, separators, `..`, and all other spellings are rejected. The original canonical text—not a normalized variant—is used in manifest lookup, cache directory, official URL, safe diagnostic identity, and CI key.

The acquisition state machine has these cancellation semantics:

1. Exclusive-lock acquisition opens the `.lock` file without deleting it. A contention retry uses `Task.Delay(..., cancellationToken)`; cancellation exits immediately.
2. HTTP request, response streaming, and partial-file streaming receive the same token. Before and after every non-cancellable `CreateDirectory`, flush, chmod, or atomic rename, the resolver checks cancellation.
3. If the final atomic rename already committed, the verified final remains reusable; cancellation still returns cancellation and no process starts. The owner removes only its GUID partial or rejected file in `finally` for success, mismatch, network failure, and cancellation.
4. Cancellation before launch prevents the child from starting. Cancellation during an already-started child is delegated to `TailwindProcessRunner`, which terminates the child, awaits exit, and disposes handles. The MSBuild bridge returns its established cancellation result (`ASTW007` behavior); normal watch shutdown is silent. Cancellation is never reported as `ASTW012`.

The cache boundary is the user or CI principal that owns the configured root; #790 does not claim to protect against a malicious process running as that same principal. The resolver rejects symbolic-link/reparse-point root components, entry directories, lock file, and final executable where the OS exposes that property, requires the final object to be a regular file, and verifies it immediately before invocation. When required local exclusive locking, same-directory atomic rename, or safe-link inspection cannot be established, it fails closed as `ASTW012/invalid-cache`. Same-principal replacement after the final check is outside this cache's threat model and must not be described as eliminated by hashing. The resolver must neither loosen permissions nor fall back to a broader shared location.

While holding the kernel-backed lock, a process may remove only strict `*.partial-<guid>` or `*.rejected-<guid>` descendants before a new acquisition. It never deletes the lock file by PID or timestamp, never deletes a final binary as generic cleanup, and never selects a partial/rejected artifact. A crashed owner leaves an acquirable lock file; the OS releases the lock and the next owner can conservatively clean matching debris. Failed cleanup cannot invalidate a verified final or hide the primary diagnostic.
