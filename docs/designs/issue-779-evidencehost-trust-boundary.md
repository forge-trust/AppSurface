## Problem Statement

An EvidenceHost manifest can be internally consistent while its policy, registration, verifier, or execution environment came from the tested head. A digest proves that bytes match other bytes; it does not establish who supplied them. The current `observationOnly` switch also changes the final claim without preventing registered resources and producers from running. A consumer therefore needs one admission decision before any resource, producer, or head-controlled code starts, and a hostile-input proof that the decision cannot be bypassed by either the Aspire host or the CLI.

The existing implementation shows the exact seams: [`EvidenceHostBootstrap.RunAsync`](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceHostBootstrap.cs) validates an envelope only for release or an optional targeted setting, then executes all plan resources even when `observationOnly` is true. [`EvidenceAspireApplication.StartAsync`](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceAspireApplication.cs) can start a topology before that validation. The [CLI evidence command](../../Cli/ForgeTrust.AppSurface.Cli/EvidenceCommands.cs) builds a manifest through a separate path and can emit a targeted gate claim without an envelope. [`EvidenceManifestBuilder.Verify`](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/EvidenceContracts.cs) recomputes hashes from a supplied plan but explicitly does not authenticate its origin. These are design inputs, not claims that the current code supplies isolation.

## What Makes This Useful

A platform engineer can inspect one result and know whether it is a protected CI assertion or an untrusted observation. A fork run may still return useful diagnostics, but it never starts PostgreSQL or another privileged dependency, receives an EvidenceHost secret projection, or turns into a PR or release gate. A protected run names the registered verifier and the bounded CI facts it accepted, while saying plainly that it did not attest the sandbox.

## Agreed Premises and Scope

1. The protected base owns policy, registration, verifier, allowed capabilities, and artifact-root selection. The tested head supplies subject inputs only. CI owns checkout separation and the actual isolation properties.
2. Observation is admitted before provisioning and uses an explicitly declared dependency-free profile. It has no sensitive projections and cannot issue a gate-eligible claim.
3. A validated envelope records a registered verifier's acceptance of bounded CI facts. Hashes and a Boolean callback cannot authenticate origin or prove sandbox containment.
4. The AppSurface-owned Docker containment runtime remains a separate pilot under the [parent design](appsurface-evidencehost-contract-first.md#trust-and-untrusted-code-boundary).

This is the user-selected **shared admission contract** approach. The minimal host-only guard was rejected because the CLI has a separate gate-claim path. A CI-only harness was rejected because every consumer could recreate a different library admission rule.

## Threat Model

### Assets, authorities, and paths

| Surface | Authority in trusted mode | Head-controlled input | Required boundary |
| --- | --- | --- | --- |
| Policy, normalized diff interpretation, plan, profile | Protected base tool checkout | Subject paths and contents only | Re-resolve under base policy; compare policy/diff/plan digests and selected obligations before execution. |
| Registration, verifier, producer/resource classes | Protected base registration module | Subject code and test data may be called by an approved producer | Exact registered IDs, versions, declared assertions, resource needs, and capability classes; no assembly or filesystem discovery from head. |
| Runner, checkout and artifact-root identity | Consumer protected CI workflow | Subject checkout | Verifier checks supported workflow/run/ref and distinct trusted-tool, subject, and output roots before admission. CI, not the library, enforces their actual ownership. |
| Privileged dependencies, secrets, sensitive projections | Consumer CI and trusted registration | Head must not choose them | Observation rejects these before any application build/start. A trusted run that can execute subject code also rejects protected secrets and sensitive projections unless CI provides a separately reviewed isolation boundary. |
| Artifacts, diagnostics, manifest | Host-owned collector and CI output channel | Producer output and subject-generated files | Closed slots, relative-path validation, final byte hashes, bounded metadata, secret-safe diagnostics; gate reads through a protected channel. |

The attacker can edit head checkout files, supply misleading policy/plan/envelope-shaped files or environment values, craft path and JSON inputs, make subject code emit forged pass-shaped output, mutate artifacts reachable by the subject, cancel execution, and cause cleanup failures. The attacker cannot edit the protected base checkout or protected CI workflow in the supported trusted mode; if either becomes head-controlled, trusted admission must fail. Tests should make both the attempted action and the absence of a complete claim observable.

### Explicit non-claims

- `ValidatedNotAttested` means one base-registered verifier accepted declared CI facts. It does not authenticate GitHub, prove network denial, confine a process tree, or independently attest an artifact. A malicious in-process subject can read ambient process state, so protected values must not be present in that process.
- The library cannot prove its own assembly or registration callback came from the protected checkout. A protected workflow must supply and test that provenance. A consumer that executes head-controlled host code in the trusted tool process is outside the supported trust claim.
- Observation's “no secrets” guarantee is the supported EvidenceHost projection and CI job configuration: the observation job contains no privileged credentials or sensitive mounts. The API cannot erase an unrelated secret already placed in the process environment by a consumer.
- The final artifact hash detects changes at collection and verification. It is not a race-proof filesystem sandbox against a subject that can concurrently write the output root. The protected workflow must keep that root outside subject control; otherwise the verifier rejects trusted admission.
- A complete claim says the protected, registered producer evaluated its declared assertion and the collector validated the result shape and artifacts. It does not independently prove application correctness or detect a malicious test that is designed to pass. Producer implementation integrity and assertion semantics are trusted-base inputs, covered by protected review and registration rather than inferred from a subject-controlled success string.

## Shared Admission Contract

### Mode and ordering

Introduce a closed `Trusted` / `Observation` execution mode in Evidence.Contracts, with one admission result consumed by the CLI, Aspire bootstrap, and manifest builder. Avoid deriving mode from a branch name, `GITHUB_ACTIONS`, or a producer result. A trusted request must carry a base-owned verifier registration and a protected CI context; observation must name a base-owned observation profile with no resources, privileged producer classes, or sensitive projection keys. The supported observation subset is declared in policy/registration rather than obtained by silently stripping a release plan. Attempting to run a release/resource-backed profile as observation fails before startup and emits no gate claim.

Admission sequence:

0. Validate protected declarative supervision metadata and arm the independent watchdog lease before invoking registration configuration, verifier, application factory, readiness, producer or disposal callbacks. Pure library parsing may occur before arming; callback execution may not. Reject unsupported/inactive supervision in both modes.
1. Read policy, diff, and plan from their declared sources; validate schema, version, canonical hashes, and the base policy identity. Treat a coherent head-provided policy plus recomputed hashes as substitution, not proof.
2. Bind selected producer/resource declarations to the explicit registration catalogue. Reject missing, extra, stale, or capability-incompatible declarations and callbacks.
3. For `Trusted`, invoke exactly one registered verifier against protected CI facts and the resolved plan. Require an accepted, versioned assertion before resource creation. For `Observation`, check the dependency-free allowlist and zero sensitive projections without invoking a trusted verifier.
4. Only after admission create the artifact root and start an Aspire application or producer. `EvidenceAspireApplication.StartAsync` must be moved behind this gate or require an admission lease; a caller cannot obtain a trusted-capable lease before checks pass. The CLI's coverage path consumes the same admission result.
5. Cancel owned work and establish that every active callback, tracked child, and artifact write has stopped before collection or resource disposal. Then collect bounded results and finish cleanup before computing any complete claim. A cleanup failure or timeout is gate-ineligible; if stopped work cannot be established, terminate the host without finalizing a manifest. CI retains the outer job kill switch.

The host owns its Aspire application lease and registrations. A base-owned producer adapter that launches a child owns and tracks that child and its descendants through its existing supervised process runner; an untracked child is an unsupported capability. Admission and verifier work have a 30-second default and maximum, Aspire build/start a 120-second default and maximum, and collection a 60-second default and maximum. Existing positive resource and producer declaration deadlines remain mandatory and cannot exceed the protected workflow's declared job deadline. Cleanup has the parent design's cumulative 10-minute maximum, with a shorter per-run value allowed. Each stage uses a linked cancellation token. Deadline expiry or caller cancellation enters the [stopping rule](#timeout-and-cancellation-disposition); it never merely detaches the task and proceeds to cleanup.

### Timeout and cancellation disposition

This rule applies to both Trusted and Observation execution, including verifier, application build/start, readiness, producer, collection, and disposal callbacks. The host retains every invocation task, child-process lease, output-pump task, and in-flight artifact write until it settles. A callback must expose all work it owns; detached tasks, untracked children, and writes outside the admitted writer are unsupported. Supported in-process callbacks are protected-base code that obeys this ownership contract. The host cannot treat a cancellation request or a cancelled wait as proof that the underlying work stopped.

At a stage deadline or caller cancellation, the host performs this sequence once:

1. **Latch the terminal cause and close admission.** Record the original cancellation or timeout, prevent subsequent stages from starting, reject new child launches and artifact writes, and cancel the active operation's linked token. A late `Passed` result cannot replace the latched cause. Already admitted writes remain tracked until they finish or abort.
2. **Stop and join owned work.** The supervised runner requests termination of owned child trees and waits for its supported exit acknowledgement and output-pump completion. The host also waits for active in-process callbacks and artifact writes to settle. The stopping grace is 30 seconds by default and at most 30 seconds; a protected run may lower it. Stopping and disposal share the configured cleanup budget, so the grace is also capped by its remaining time and the outer job deadline. This wait uses a fresh host-owned stopping token, not the already-cancelled stage or caller token. Even a late callback completion is joined only to establish stopped work; its result cannot restore eligibility.
3. **Choose one terminal path.** If all active work has settled within that grace, the host may dispose resources in the documented order and collect a failure manifest. Producer or stage timeout is `Incomplete` with no claim or gate eligibility; caller cancellation also emits no claim. If an in-process callback, write, output pump, or owned descendant remains active, the host takes the fail-stop path below. It must not begin resource disposal, hash or publish artifacts, or return a terminal manifest while that work remains active.

**Fail-stop is mandatory when stopping cannot be established.** The standalone CLI/EvidenceHost process terminates unsuccessfully through a host-owned fatal termination operation that does not return to user code or execute callback disposal/unwinding. A consumer embedding EvidenceHost in a long-lived process must run the execution in a separately supervised worker process; catch-and-continue is unsupported. The protected supervisor owns the host process/job lifetime and finishes termination of its owned descendants. It may tear down externally owned topology only after confirming the worker and writers have stopped. If it cannot establish that condition, it cancels the job and leaves the run's fresh output root quarantined and ineligible for publication or reuse. The failing host emits no final manifest. The outer supervisor may retain only a bounded, secret-safe timeout diagnostic; any earlier plan or intermediate file remains non-terminal and gate-ineligible. This termination contract relies on the consumer's supervised execution and preserves the [CI-owned containment boundary](#explicit-non-claims).

The fatal termination path is part of the supported execution contract, not a callback that a consumer may replace with a logging function. Admission must reject an embedding or runner that cannot provide this behavior. The supervisor's deadline enforcement must run independently of callback execution, including a synchronous callback that blocks before returning a task; termination cannot depend on that callback's thread making progress. Tests may use an internal termination seam that interrupts the test path, but production termination cannot return. If disposal itself exceeds the remaining cleanup budget, the same fail-stop rule applies; further disposal callbacks must not overlap a disposer that is still active.

**Verification:** Deterministic clock and task barriers cover cooperative cancellation, a callback completing during grace, late pass results, a write already in flight, a child without an exit acknowledgement, and a disposer ignoring cancellation. They assert no dependent resource is disposed and no hash/manifest publication occurs before all active work settles. A separate isolated worker fixture runs a callback that never completes: after the grace, the worker exits unsuccessfully, its resource-dispose marker and final manifest are absent, and the supervisor confirms owned process exit before handling output or topology. The test harness supplies its own outer deadline so a broken fatal termination implementation fails the test without hanging the suite. These checks demonstrate the selected termination behavior; they do not stand in for the deferred Docker containment pilot.

### Supervisor API and output-root binding

The shared host API accepts a protected-base `EvidenceWorkerSupervisionDescriptor` and registered `IEvidenceWorkerSupervisor`. The descriptor contains schema/provider version, run ID, worker identity, non-secret control-channel identity, absolute job deadline, per-stage deadlines, stopping/cleanup budgets and supported child acknowledgement kind. `ArmAsync(descriptor, cancellationToken)` must complete before any consumer callback and returns a host-issued `EvidenceWorkerLease` for that exact descriptor/run/worker; absence, mismatch, expired lease or failed arming rejects before execution. `ArmAsync` belongs to the trusted supervisor implementation and its own external deadline is enforced by the job/launcher, never a callback on the worker it will supervise. These names are planned API shapes, not existing APIs. Do not expose a public constructor or JSON-to-lease factory.

Lease lifecycle is `Armed -> Running -> Stopping -> Exited`, with `Armed -> Rejected -> Exited` for admission failure. Single-use `StartWorkerAsync` selects the protected entrypoint and supplied descriptor, `RequestStopAsync` is idempotent and closes launches/writes, and `WaitForOwnedExitAsync` joins worker, declared descendants and pumps. The consumer launcher owns the independent watchdog and supported process/job termination; the worker owns callback tasks, resource/producer disposal and tracked writes. On missing exit acknowledgement or expired stopping/cleanup budget, the launcher terminates the worker/job and quarantines output without waiting for a blocked worker thread. The production worker fatal operation never returns or unwinds user disposal. Test seams are internal and cannot replace production termination. CLI invokes its protected worker entry through this lease; embeddings launch the same entry in a separate process. Subject code is a separately restricted child, never loaded into the protected worker; the worker submits child leases through the supervisor, which owns their exit acknowledgements. State checks forbid reusing a rejected/exited lease or starting another run on it.

Pre-admission verifier root facts mean the protected **parent/root allocation policy**: canonical trusted-tool and subject roots, protected output-parent identity, allowed platform mechanism and fresh run/slot name. The output directory need not exist yet. After admission, the host exclusively allocates the fresh output directory beneath that protected parent using the admitted link-safe mechanism, obtains its actual handle/identity, and checks it against the admitted parent/run/slot before enabling the artifact writer or invoking any application/subject callback. The final assertion records the actual bound output identity and allocation-policy digest. Allocation failure, changed parent identity, collision, link/alias or changed ownership revokes the admission's execution state and yields no gate; no resource/subject may have started. Keep the verified handle for write/finalization and reject paths that cannot preserve the platform guarantee. This is two-step admission/activation, not retroactive trust in an arbitrary caller path.

Tests exercise missing/stale supervision, synchronous verifier/configuration/factory stall, cooperative stop, stuck worker/disposer/child, reusing a lease and both output-allocation versus cancellation completion orders. Root controls include protected parent with a fresh regular child, substituted parent, occupied name and post-verification alias. Trusted enablement is a release gate: the consumer CI owner records the real protected/fork map and each admitted platform demonstrates denied component loads, protected output and safe allocation. Missing facts keep Trusted unavailable; implementing contracts or passing fake fixtures alone does not mark those external gates complete.

### Runtime admission result

The admission result is a runtime capability, not serialized authority. It cannot be reconstructed by deserializing a head-supplied plan or manifest. Remove the manifest builder's public ability to turn a caller-supplied envelope-status enum into a gate claim: claim construction consumes only a host-issued admission result with an internal constructor. Structural verification remains public but cannot authenticate origin. Public APIs must document how callers obtain admission and which operations require it; internal APIs must document ordering and failure precedence. Tests use the public bootstrap/CLI paths and intentionally exposed seams, without reflection.

### Subject execution and secrets

The supported #779 trusted profile may execute head-controlled subject tests, but its tool process and CI job must contain no privileged CI credential or protected sensitive projection. Base-owned producers may give the subject only disposable, test-scoped credentials whose exposure to head code is explicitly acceptable, such as an ephemeral database password with no access outside the throwaway test topology. Such a value is treated as subject-visible test input, never as a protected secret. The verifier checks this zero-protected-secret policy and the exact ephemeral capability set before admission. If a consumer needs a privileged secret or sensitive projection while subject code runs, admission rejects that profile until a separately reviewed CI-owned execution boundary isolates the subject; this issue neither supplies nor claims that boundary. The two-checkout fixture must prove that the trusted job has no protected secret injection, that subject code cannot load the trusted registration/verifier, and that a hostile subject attempting to read a canary protected value observes none. Two directories alone do not establish the load-prevention property. The supported consumer must execute subject code in a separate supervised process under an identity or filesystem boundary that denies access to trusted tool/registration/verifier and protected final-output roots; the protected collector alone receives bounded subject output. Record and test this consumer-owned boundary in the CI map before enabling Trusted. A head-controlled in-process callback or a same-identity subject with readable trusted components cannot meet this requirement and is rejected for Trusted; the library supplies no sandbox. Prove attempted reads/loads fail and the protected registration actually used has the pinned base identity, with a neighboring allowed subject input test. This is a supported-run restriction, not an assertion that a .NET process can sandbox code it invokes.

### Envelope assertion and claim rule

Replace a bare `Accepted`/`Attested` result with a bounded verifier descriptor and assertion: verifier ID/version, supported runner/workflow/run identity, protected base and subject revisions, root identities, allowed producer/resource classes, sensitive projection-key policy, verification time, and a digest of non-secret capability evidence. The verifier checks every required field against protected CI input and the plan; missing, changed, head-derived, or unsupported fields reject admission. v1 emits only `ValidatedNotAttested` for an accepted trusted assertion; it never emits an `Attested` claim. The manifest records this limited assertion and the selected mode, without secret values or raw capability evidence.

`TargetedComplete`, `ReleaseComplete`, and gate-eligible `NoEvidenceRequired` require `Trusted`, accepted `ValidatedNotAttested`, valid plan/artifact bindings, satisfied obligations, and completed cleanup. `Observation` can emit only `ObservationOnly` with `Informational` eligibility when its contract remains valid; invalid input emits `None`. A downstream gate verifies the manifest and obtains the expected base policy/revision through a protected channel. It never trusts an uploaded plan/manifest pair merely because their hashes agree. Release consumers retain the parent design's explicit opt-in to the limited `ValidatedNotAttested` assertion.

### Producer assertion authority

Only a protected-base registered producer implementation may create a gate-relevant EvidenceProducerResult. Subject code can return test data, process exit status, logs, and artifacts, but cannot supply an assertion ID or outcome directly to the collector. The base-owned adapter evaluates its versioned assertion descriptor against its supported inputs, checks process exit and required artifact bytes, and returns the result through the registered callback. The collector checks exact producer ID/version, selected descriptor IDs, required result shape, declared artifacts, and obligation mapping; unknown, duplicate, stale, missing, or mismatched output is invalid. A consumer producer that merely forwards a subject-authored passed flag is not eligible for Trusted registration. For a browser/E2E assertion whose truth depends on test logic, the protected producer owns the invocation and interpretation contract. The test logic itself is not independently authenticated against malicious modification; completeness asserts the registered procedure, not objective product correctness. The two-checkout fixture feeds a forged success document and a passing but missing-artifact result through subject output and proves neither closes an obligation; a matching protected producer evaluation is the positive control.

### Sensitive output and paths

The host passes only declared projection keys to trusted producers. Observation registration has no sensitive projections and no privileged dependencies; the CI observation job also has no secrets. Diagnostics and summaries contain stable codes, IDs, and sanitized failure classes, never raw values. Artifact slots retain declared root, media type, size, and SHA-256 bounds. Reject absolute paths, traversal, alternate separators, duplicates, pre-existing/symlink or reparse destinations, missing required slots, changed bytes, and hashes that do not match the final file. Use a fresh protected output root and exclusive file creation. If a supported platform cannot enforce the required link/alias checks for a trusted root, admission must reject it rather than claim path containment. Keep raw browser logs/media under the consumer CI retention and sanitization policy.

## Hostile-Input Acceptance Matrix

Each negative case asserts the stable failure class, zero privileged starts or sensitive projections when failure occurs before admission, zero gate eligibility, and cleanup/disposal counts where a run had already started. Positive controls prove that the guard does not reject a supported protected run.

| Input or event | Adversarial fixture and rejection | Supported neighboring control |
| --- | --- | --- |
| Policy substitution | Head supplies a valid-looking weaker policy and recomputes its hashes; reject protected-policy identity before provisioning. | Base policy plus the same subject diff admits Trusted and can reach TargetedComplete. |
| Producer registration substitution | Head supplies a matching name with a different class, version, capability, or assertion; reject before callback. | Exact base registration and descriptor admits Trusted and closes its obligation. |
| Producer result spoofing | Subject emits a passed flag or known assertion ID, or omits the descriptor's required result shape/artifact; base adapter ignores the forged flag and collector invalidates an unsupported result. | Protected producer evaluates the supported exit/result/artifact inputs and returns the exact selected assertion; verified result closes the obligation. |
| Envelope substitution | Head supplies verifier-shaped JSON, runner variables, ref, or alternate root; base verifier rejects and never reports Attested. | Protected runner facts with exact roots/revisions yield ValidatedNotAttested and a complete trusted claim. |
| Capability mismatch | Plan requests an unapproved resource, producer class, projection, mount/image/egress class, or root; fail before Aspire start. | Exact base-declared capabilities admit Trusted; allowed ephemeral test resource becomes ready. |
| Observation privilege attempt | Observation requests resource, privileged producer, release profile, or sensitive projection; reject before any callback. | Explicit dependency-free, no-secret targeted profile runs and yields ObservationOnly / Informational. |
| Path and artifact attack | Traversal, absolute/drive/UNC path, separator trick, link/reparse target, duplicate slot, oversize or changed file; reject write or invalidate result. | Declared relative slot in fresh private root, exact media/size/hash, produces a verified artifact and complete trusted claim. |
| Schema and hash drift | Wrong contract version, duplicate/case-colliding claim field, altered digest or assertion; reject ingestion or verification. Coherent head rehash still fails provenance. | Supported additive optional field and unchanged claim-critical fields pass strict parsing and base-bound verification. |
| Cancellation | Cancel at admission, build/start, readiness, producer, or collection; close further work, cancel and join active tasks/writes/children, then dispose only after stopping is established; no complete claim. | Cooperative callback and writes settle during grace, disposal happens afterward, and a cancellation manifest has no gate eligibility. The corresponding uncancelled run can reach TargetedComplete. |
| Non-cooperative timeout | Callback, write, output pump, or owned child remains active beyond stopping grace; mandatory unsuccessful host termination, no resource disposal race, no final manifest, and output quarantined until the supervisor confirms exit. | Work settles just inside grace; host disposes once after joining it and records the original timeout as Incomplete / None. A late pass never upgrades the run. |
| Cleanup failure | Disposal throws after active work stops; verdict incomplete and eligibility none. A disposer still running at budget expiry triggers fail-stop before further disposal or manifest publication. | Same owned resources dispose once within budget after all callbacks and writes settle; completed cleanup permits TargetedComplete. |
| Trusted positive control | Protected base policy, registration, verifier and CI facts with exact capabilities. | All selected obligations close; manifest records ValidatedNotAttested, never sandbox attestation. |

Use deterministic fake resources, producers, clocks, and verifier inputs for the library matrix; avoid wall-clock sleeps and reflection. Add a small two-checkout consumer fixture that puts protected tool/policy/registration in one checkout and hostile subject files in another, then runs the trusted and fork/observation workflow paths. It must inspect the effective CI job permissions, secret injection, checkout source, artifact root, and the first executable step. No Docker containment test belongs to this issue. Run a packed-consumer test for the public contract/CLI/Aspire package surface and verify current and prior supported schema fixtures according to the [v1 compatibility rules](appsurface-evidencehost-contract-first.md#public-contract-ownership-canonical-form-and-compatibility).

## API, Compatibility, and Rollout

- Evidence.Contracts owns mode, verifier assertion data, admission/manifest shape, canonical serialization, and compatibility rules. Evidence.Aspire and the CLI consume the same admission decision; neither invents an alternate Boolean trust switch.
- New API requests require an explicit mode and admission context. The CLI requires --mode trusted or --mode observation; omission fails with a stable select-a-mode diagnostic before any producer runs. The legacy observationOnly=true and --observation-only flag map only to Observation. Legacy false or omitted bool values do not grant Trusted: without an explicit trusted context they fail before execution with a migration diagnostic. A trusted request with no accepted registered verifier also fails before execution and emits no gate claim. Supplying both the legacy flag and a conflicting new mode is invalid. Document this intentional change for prior targeted CLI gates rather than preserving an unverified gate claim.
- Tighten claim-critical JSON ingestion, including duplicate/case-colliding property handling and unsupported version/enum rejection. Preserve the documented additive-field compatibility rule where ignoring an unknown field cannot change eligibility; update golden fixtures when the schema changes.
- Update the [EvidenceHost start page](../../start-here/evidencehost.md), [Aspire reference](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md), [contracts reference](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/README.md), [CLI reference](../../Cli/ForgeTrust.AppSurface.Cli/README.md), and [cookbook](../../guides/evidencehost-cookbook.md). 1. Every hostile row has at least one negative test and a supported positive control. Tests prove both outcome and non-execution of disallowed capabilities.
2. No observation path, including the CLI, can provision a privileged resource, receive an EvidenceHost secret projection, or emit a PR/release gate claim.

### R3-1 — completeness

**Problem**

> The timeout contract bounds how long the host awaits a stage, but the Shared Admission Contract says an in-process callback that ignores cancellation may continue until the CI job is terminated. The host then attempts cleanup without specifying how the still-running callback is stopped or prevented from using disposed resources and changing output after timeout, leaving terminal cleanup behavior undefined.

**Remedy**

> Specify timeout disposition for non-cooperative callbacks and ensure cleanup and output finalization cannot race with them—for example, require callbacks to run in a terminable supervised process or terminate the job/process when a callback exceeds its deadline.
