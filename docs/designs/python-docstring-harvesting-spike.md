## Problem Statement

Determine whether `ForgeTrust.AppSurface.Docs` can statically document Python that is embedded in or shipped beside a broader .NET codebase. The immediate objective is a credible package-level proof that the product serves more than the direct .NET ecosystem; improving AI answer quality remains a future hypothesis, not this spike's success measure.

## Autoplan Decision Record — 2026-08-21

The CEO challenge found that the original wording could mistake a narrow fixture for general Python support. The user selected **B — bounded cross-language discovery proof**:

This decision record supersedes earlier wording in this document where it implied that `__all__` is the general v1 public-API contract or that a host-to-script relationship is optional.

## What Makes This Cool

A .NET application can show C# and embedded Python as one source-linked documentation surface—navigation, search, source anchors, and diagnostics—without importing, executing, or even requiring a Python runtime. That is a materially different promise from conventional Python documentation generators, which commonly use dynamic import or require a chosen docstring style.

## Constraints

- Parse source files only: do not execute Python, import modules, invoke Python tooling, or depend on a Python runtime.
- In the proof fixture, treat a top-level, literal `__all__` sequence of string names as the intentionally explicit export contract for named module-level classes and functions. Do not infer a general Python visibility rule from this fixture. A module docstring describes the module container; documented members of an exported class are children of that exported API rather than independent module exports.
- Preserve docstring content without interpreting Google, NumPy, Sphinx, or other docstring styles. Remove Python literal delimiters/prefixes, decode the supported literal value, and normalize common indentation so the rendered text is stable without turning it into style-specific structure.
- The negative fixture module with no recognizable `__all__` must emit a nonfatal, actionable public-boundary diagnostic; it must not silently report a successful empty Python API. The diagnostic proves the fixture policy and does not become a blanket product conclusion about every Python module.
- Keep existing path-policy, parser-input-budget, cancellation, source-anchor, health, and diagnostic guarantees intact.
- The proof must use the real Docs aggregation, navigation, and search pipeline beside C#; a parser-only benchmark is insufficient.
- A parser's actual package contents, licenses/notices, runtime identifiers, package-size delta, and package-consumer loading behavior must pass the acceptance gate before it becomes a product dependency. A native load failure must become a structured diagnostic rather than an unhandled harvest exception.
- Do not introduce a generic multi-language harvester abstraction in this spike. The existing JavaScript implementation is the second code-language reference point; generalization can be reconsidered once Python exposes genuine shared seams.

## Premises

- The target environment is a broader .NET codebase with Python embedded or sidecar code; exact production Python conventions are not yet defined.
- The current documentation is largely in code, and Python docstring quality/style is mixed.
- The useful immediate evidence is a small public fixture that shows C# and Python coexisting in the installed package, rather than an internal-source harvest or an AI-answer prototype.
- Python defines a docstring structurally as the first statement of a module, class, function, or method, so raw static extraction is a stable v1 boundary.
- Generated API search qualification is currently JavaScript-specific and must become language-neutral for Python entries to be first-class in search; the proof must also surface the explicit C# host-to-Python ownership relation in both directions.
- Python syntax highlighting is not a spike gate: the current highlighter's safe plaintext fallback avoids a rendering failure while parser and package behavior are proven.

## Cross-Model Perspective

An independent cold read agreed that the fixture can support the claim that AppSurface Docs is an embeddable, polyglot source documentation engine for .NET applications. ## Approaches Considered

### Approach A: Tree-sitter vertical product spike — selected

Only after the parser acceptance gate passes, integrate a Python grammar into a minimal harvester and prove the complete AppSurface Docs product path using C# plus embedded Python fixtures. The proof includes static fixture-local `__all__` filtering, raw docstrings, anchors, generated-API search metadata, an explicit host-ownership link, diagnostics, and installed-package runtime validation.

### Approach B: ANTLR managed-runtime vertical spike — deferred fallback candidate

Deferred because checking in/generated parser source and owning grammar/code-generation and recovery behavior would front-load more uncertainty than the product proof requires, before native-payload risk has been measured. It remains the explicit follow-up candidate if the Tree-sitter package proof fails.

### Approach C: Parser comparison harness before integration — rejected

Rejected because it can select a library but cannot prove that a package consumer receives useful unified C# and Python documentation, navigation, search, and diagnostics.

### Scope

1. **Gate before integration.** Measure the candidate package against the explicit 5 MiB compressed-delta, native-runtime disclosure, license/provenance, and supported-consumer loading requirements. Publish the results. The existing `DocsPackageConsumerProof` is restore/graph-only and explicitly does not build an application, so it cannot be repurposed as native-load evidence: add an isolated child-process package smoke host that restores, builds, initializes the binding, and runs the malformed/budget corpus. Only a pass unlocks the remaining implementation scope; a fail is the complete negative result for this parser candidate.
2. If the gate passes, add a Python source kind, `AppSurfaceDocsPythonHarvestOptions`, path matching, service registration, activation, health participation, and diagnostic integration consistent with the existing code-language harvesters. The options must compose with global path policy and expose `Enabled` (default `true`), empty `IncludeGlobs`/`ExcludeGlobs`, standard default-exclusion controls, `StrictHealth`, and an explicit parser file-size limit. **Python source enumeration requires at least one nonblank, policy-valid `IncludeGlobs` entry:** `Enabled` with no include performs no source reads, publishes no API page, and emits nonfatal `appsurfacedocs.python.missing_include` guidance. This preserves a friction-light, one-setting opt-in while avoiding accidental repository-wide policy warnings before real Python visibility conventions exist. Native-load preflight must occur before source parsing by calling the binding's first native initialization inside a narrow failure boundary; use `NativeLibrary.TryLoad` only if the binding documents the payload name. Failure emits `appsurfacedocs.python.native_load_failed` with the active runtime identifier and safe failure detail, follows normal strict-health participation, and never leaves an unhandled native-load exception. Package inspection must enumerate the candidate's advertised Windows (`x86`, `x64`, `arm64`), Linux (`x86`, `x64`, `arm`, `arm64`), and macOS (`x64`, `arm64`) native assets. Runtime smoke verification must run on the existing Windows and macOS CI lanes plus the existing Linux `x64` container evidence path, recording each actual runtime identifier.
2. Add a Python harvester that parses files statically with the `TreeSitter.DotNet` 1.3.0 candidate binding and its Python grammar; dependency preflight must compile and exercise the package's documented `TreeSitter.Language("Python")` initialization before integration work starts. It must extract module, class, synchronous function, asynchronous function, and method docstrings with source spans. For the spike, a supported docstring is an unprefixed, non-concatenated single- or triple-quoted string; this explicitly excludes `r`/`R`, other prefixed strings, bytes strings, f-strings, and implicit literal concatenation. Preserve source text inside the supported delimiters without Python escape evaluation, then apply a local `inspect.cleandoc`-equivalent normalization: expand tabs at width eight; determine common indentation from subsequent nonblank lines only; remove it; and trim outer blank lines. Comments do not affect the first-statement check; if the first statement in a module, class, function, or method body is not a supported string expression, that entity has no docstring. Traversal tests must cover module and class bodies, module functions, asynchronous functions, class methods, and `decorated_definition` wrappers that contain a class or either function kind; preserve the outer decorated span as the source anchor. Ignore functions and classes nested inside function or method bodies. Convert Tree-sitter's zero-based start row to the Docs source anchor's one-based line number; if a column becomes observable, apply the same one-based conversion. The spike extracts names, hierarchy, source spans, and normalized docstring text only; it does not project structured parameter, annotation, default-value, or return metadata.
3. For the proof fixture only, accept one unannotated top-level literal `__all__ = ["..."]` or tuple equivalent; a type-annotated assignment is invalid in this fixture policy. The boundary publishes matching module-level classes/functions; documented members of an exported class are emitted below their exported parent. An absent boundary emits warning `appsurfacedocs.python.public_boundary_missing` with the repository-relative module path, emits no module API page, and publishes no public symbols. An otherwise empty `__init__.py`—only whitespace, comments, and/or a supported module docstring—is ignored without that warning. Multiple assignments, annotations, `+=`, dynamic expressions, or non-string entries emit warning `appsurfacedocs.python.public_boundary_invalid`, emit no module API page, and publish no public symbols. Names in a valid `__all__` that resolve to a variable, type alias, or import are omitted with `appsurfacedocs.python.export_not_supported`; names with no source declaration emit `appsurfacedocs.python.export_not_found`. Both are warnings. In every boundary failure, the harvester remains nonfatal unless its normal strict-health rules make it blocking.
4. Publish grouped Python API pages beneath `api/python/{module-slug}`. Derive each slug from the policy-approved repository-relative source path, stripping `.py` and a final `__init__` segment, then use the existing URL-safe path-slug rules so segment context survives (for example, `tools/worker.py` becomes `tools-worker` and `tools/__init__.py` becomes `tools`). If two module paths resolve to the same slug, emit warning `appsurfacedocs.python.slug_collision` and publish neither colliding page; never silently merge them. Refactor generated-API search qualification so it validates the existing canonical marker plus language-neutral generated-API provenance and structure, rather than JavaScript-only marker, page-type, and `api/javascript/` predicates. Tests must prove the resulting Python children are marked generated API symbols in search without weakening the existing JavaScript qualification checks.
5. Keep code-fence highlighting on the safe fallback path unless Python grammar registration is genuinely needed to satisfy an existing presentation assertion.
6. Add the fixture to the existing consumer/aggregation test surface:
   - a documented C# host type decorated with the public, source-only marker `[AppSurfacePythonModule("relative/module.py")]`; the Docs output must render a stable reciprocal link between the host's C# symbol anchor and the Python module API page, and each side must be discoverable through generated search;
   - a Python module with a module docstring, literal `__all__`, documented exported class/function, documented method, and excluded internal helper;
   - a separate Python module that omits `__all__` and asserts the boundary diagnostic.
7. Update public/reference documentation and third-party notices for the parser dependency, including a clear statement that harvesting is static and does not execute Python.

### Ownership Boundary

The small relationship proof has one explicit source contract rather than a generic cross-language model:

- `AppSurfacePythonModuleAttribute` is a public .NET marker that may decorate one documented top-level C# type. Its sole argument is one literal, repository-relative `.py` path; it is read from Roslyn syntax and is never instantiated or executed during harvesting.
- Reject a rooted path, a path containing `.` or `..` segments, a non-`.py` path, a nonliteral argument, duplicate markers on one host, or a source path rejected by the shared harvest policy. Each rejection produces a specific nonfatal ownership diagnostic and no link.
- An internal Python-specific ownership linker joins the C# marker's already-proven source anchor with the accepted Python module page after harvesting. It creates reciprocal, HTML-encoded links only when exactly one documented host anchor and one published Python module page match. A missing, unpublished, excluded, or ambiguous target produces a diagnostic and no dangling link.
- Ownership is many-host-to-one-module only if every host independently satisfies the same checks. A Python module never infers a host, no source text is searched heuristically, and no caller/callee/runtime meaning is assigned to the link.
- The linker is deliberately internal and Python-specific. It must not add a public generic relationship field to `DocNode`, `IDocHarvester`, or the search schema; a future language-neutral model needs demonstrated consumers beyond this proof.
- Because harvesters complete independently, the C# marker and Python module source identities must reach the linker through one internal, Python-specific candidate snapshot/provider owned by the aggregation path. It is not a public `IDocHarvester` extension point and must retain only canonical route, source identity, anchor, and validation outcome—not source text or a generic relationship graph.

### Explicit Non-Goals

- Import-time inspection, runtime reflection, Python environment discovery, or executing user code.
- Broad support for dynamically assembled `__all__`, re-exports, wildcard imports, package-level resolution, decorators' runtime effects, or docstring-style semantics.
- A generalized parser framework or a claim of complete Python language/toolchain support.
- Measuring whether harvested docstrings improve AI answers in this spike.

## Success Criteria

- First, the selected parser candidate either passes the explicit package acceptance gate or produces a published, reproducible negative result; a failure does not advance into source integration.
- If the gate passes, a clean package consumer harvests both C# and Python fixtures into one Docs aggregation without a Python runtime installed or Python code executed.
- Exported Python class, function, and method nodes appear with normalized source docstring text, stable source anchors, navigation entries, and generated-API search metadata.
- A symbol absent from literal `__all__` does not appear as public API.
- A module without a recognizable `__all__` emits the agreed nonfatal, actionable diagnostic; no silent successful empty Python harvest occurs.
- A module with a missing or invalid public boundary does not publish an empty Python API page.
- The C# host API page and Python module API page expose reciprocal, source-backed ownership navigation and are both retrievable through generated search; this is a relationship discovery proof, not a runtime call graph.
- Existing path policy, input budget, cancellation, and malformed-source resilience are covered by focused tests.
- The produced NuGet package contains correctly attributed parser assets, records its size delta, enumerates every advertised native asset, and passes loading/harvest verification on the defined Windows, macOS, and Linux evidence paths.
- Package size, build, tests, formatting, analyzers, and documentation checks meet the repository's existing release expectations.

### 1. Architecture Review

**WARNING — accepted design:** two pre-existing harvesters cannot independently express a useful relationship. The plan adds one small, Python-specific post-harvest linker, not a new language framework.

```text
                            package gate (before integration)
NuGet candidate ──measure──> size / native assets / provenance / consumer smoke
                                │ pass                         │ fail
                                ▼                              ▼
 C# source ──Roslyn──> C# host anchor + literal marker      published rejection
                                │                              (stop)
 Python source ──parser──> accepted Python module page
                                │
                                ▼
                 PythonOwnershipLinker (exact, policy-checked join)
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
    C# symbol-anchor link                    Python module link
              └─────────────> nav + generated search <─────────────┘
```

The ownership state is finite and stateless across harvest runs:

```text
Discovered marker ──valid/policy-approved──> Awaiting Python page
      │ invalid                                 │ target published exactly once
      ▼                                         ▼
 Diagnostic + no link <── target absent/ambiguous ──> Reciprocal links emitted
```

At 10× files, shared path policy and each parser's input cap protect discovery; the first scaling limit is total parse time, so the existing cancellation and per-file budget remain mandatory. At 100× files, the package should still avoid retaining full source text after a page is produced. There is no auth, database, network endpoint, user mutation, secret, or new data store. The relevant production failure is a native binding failing to load in a supported consumer: it must produce a redacted diagnostic, strict-health result when opted in, and no unhandled exception. Rollback is a package/version revert or disabling Python harvest; the marker is inert when no Python harvester is present.

### 3. Security & Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Python source executes during documentation harvest. | Low | High | Static parsing only; no interpreter, import, subprocess, or reflection path. |
| Ownership marker escapes repository policy. | Medium | Medium | Literal relative `.py` path only; reject rooted, dot-segment, nonliteral, and policy-excluded values before any read/link. |
| Unsafe source string becomes rendered HTML. | Medium | Medium | Build links only from resolved canonical routes and HTML-encode labels/attributes; never render raw marker text. |
| Native parser supply-chain or ABI vulnerability. | Medium | High | Size/provenance/license/RID gate, consumer smoke, notices, and candidate rejection on native fault. |
| Search metadata privilege bypass. | Low | Medium | Preserve provenance validation; generalize its language predicate rather than make metadata trusted. |

### 4. Data Flow and Interaction Edge Cases

```text
C# attribute / Python file
        │ nil, empty, unsafe, excluded, too large, cancelled, malformed
        ▼
path + syntax validation ──> static parse ──> policy/boundary transform ──> doc nodes ──> linker ──> nav/search
        │                       │                  │                         │              │
        └── diagnostic/no link ─┴── diagnostic ────┴── no empty Python page ──┴── no dangling link
```

There is no new interactive UI flow. Reader-visible edge states are: no Python page when the candidate is rejected; a C# page without a link when the marker is invalid or target is not published; a Python page without a host link when no valid marker resolves; and normal reciprocal links only for the exact match. Tests must assert each state, rather than treating an absent anchor as a successful no-op.

### Magical Moment Specification

The delivery vehicle is a generated Docs link, not a demo video or parser output. In a running Docs host, the maintainer opens a documented C# wrapper, sees **Owned Python module: `scripts/worker.py`**, follows it to `api/python/scripts-worker`, and follows the reciprocal **Owned by C# host** link back. Search finds either side. The two source anchors make the relationship inspectable rather than magical-by-assertion.

### Three-Step Golden Path

After the package candidate has passed and a released Docs package contains the feature:

1. **Bound Python scanning.** Add one opt-in boundary to the existing host configuration:

   ```json
   {
     "AppSurfaceDocs": {
       "Harvest": {
         "Python": { "IncludeGlobs": [ "scripts/**/*.py" ] }
       }
     }
   }
   ```

   Expected result: the host starts without Python execution. If the glob is absent, the harvest view reports `appsurfacedocs.python.missing_include` with the exact configuration key and example.

2. **Declare ownership in source.** Put `[AppSurfacePythonModule("scripts/worker.py")]` on one documented C# host type and make the fixture module's intended exports literal in `__all__`.

3. **See the relationship.** Run the existing Docs host, search for the C# host or Python symbol, then follow the reciprocal generated links and source anchors. Expected result: one C#↔Python relationship, no Python import/process/runtime execution, and a diagnosable no-link state when policy/boundary validation fails.

Target time to this result is **three steps and five minutes or less** for a maintainer who already has an AppSurface Docs host. The first released guide must state that this time excludes a rejected parser candidate and initial app creation.
