# Issue #899: coverage domain identity lifecycle

## Decision

Schema-v1 coverage domains keep the existing native identity mismatch refusal. There is no safe in-place reconciliation for a persisted marker whose identity differs from the current directory because schema v1 has no independent continuity proof. The diagnostic classifies the observed mismatch; it does not explain its root cause or grant ownership.

Operators preserve the entire old private domain as a backup, retain its historical evidence and original provenance, and explicitly choose a separate fresh domain for future work. The CLI command `coverage storage new-domain --output ABSOLUTE [--apply]` previews or atomically creates a private empty domain beneath an existing physical parent. It refuses all existing destinations, bypasses opening the degraded configured store, transfers no history or pins, and does not update `APPSURFACE_ARTIFACT_HOME`. Cancellation or initialization failure preserves created private state; use a different fresh path on retry. See the [coverage storage guide](../../guides/coverage-storage.md#replacing-a-domain-whose-identity-no-longer-matches) for the operator procedure.

## Current and candidate identity semantics

| Platform | Current schema-v1 tuple | Native lifecycle notes | Why it is not an automatic migration key |
| --- | --- | --- | --- |
| macOS/APFS | `st_dev` + `st_ino` from `fstat` on a retained descriptor | Apple documents `ATTR_CMN_OBJID` as a within-volume object ID that need not persist across unmount/mount. It separately defines `ATTR_CMN_OBJPERMANENTID` as intended to persist across unmount/mount. | Permanent-ID availability and APFS behavior need native validation across actual unmount/remount. Volume cloning or copied images can reproduce metadata. An object ID alone does not prove private ownership, expected path, or domain contents. |
| Windows/NTFS | Volume serial + 64-bit file index from `GetFileInformationByHandle` | Microsoft says volume serial plus file ID compare file identity on one computer; NTFS keeps a file ID until deletion, and file IDs may be reused over time. NTFS MFT entries can be reused. | A volume GUID path identifies a volume for path/mount APIs; it is a candidate to investigate, not proven persistence across volume cloning or restoration. Volume/file identifiers alone do not prove ACL ownership or domain contents. |
| Linux/ext4 | `st_dev` + `st_ino` from `fstat` | Linux documents inode numbers as unique within a filesystem, paired with the device identity. Device numbers identify the mounted device instance, not a cross-boot persistent volume UUID contract. Inode numbers can be reused after deletion. ext4 exposes an inode generation through an ioctl, which is intended to change when a new inode is created. | Filesystem UUID plus inode/generation is only a candidate. UUIDs can be duplicated by block-device images, generation availability/semantics vary, and the tuple still does not establish path, owner/mode, or application-store integrity. |

Relevant primary references: Apple's [`getattrlist(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/getattrlist.2.html) documents the persistent vs nonpersistent object-ID attributes; Apple DTS explains [`FSID` vs `FILEID`](https://developer.apple.com/forums/thread/743665). Microsoft's [`BY_HANDLE_FILE_INFORMATION`](https://learn.microsoft.com/en-us/windows/desktop/api/fileapi/ns-fileapi-by_handle_file_information) contract and [NTFS MFT](https://learn.microsoft.com/en-us/windows/win32/fileio/master-file-table) document file-ID scope and MFT reuse; Microsoft describes [volume GUID paths](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-volume) as volume identifiers for mount operations and specifies [`FILE_ID_INFO`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info). Linux [`inode(7)`](https://www.man7.org/linux/man-pages/man7/inode.7.html) and [`stat(3type)`](https://www.man7.org/linux/man-pages/man3/stat.3type.html) define inode/device scope; the [ext4 kernel documentation](https://docs.kernel.org/admin-guide/ext4.html#ioctls) documents its inode-generation ioctl. Treat volume-image duplication as an explicit risk to test: that identifiers copied in a block image could match is an inference from their stored/on-volume nature, not evidence from this test run. A future persistent identity design must separately validate volume and object identifiers against cloned volumes, remount/restart lifecycle, hard links, file-ID reuse, private ownership, permissions, and the expected store root. No candidate is accepted by this change.

## Implemented behavior

PR feedback adds trailing-separator normalization, preview/apply details in text output, and precise creation effects: refusals before native publication report none; failures or cancellation after the root is created report partial and direct the operator to preserve it and choose another fresh path. Windows component acquisition tolerates only error 183 and still reopens and verifies the competing object. Fresh-domain publication never adopts a competing directory. These local fixes do not establish new native Windows evidence until their platform tests execute there.

- Schema-v1 marker comparison uses the native live identity tuple. A later process open accepts the persisted marker when the current live tuple is exactly equal; changed volume/device or object fields remain refused. This same-volume continuation is not an automatic schema migration.
- `IdentityMismatch` and `VolumeIdentityMismatch` are safe diagnostic categories only. A matching file-ID component with a differing volume/device component is still refused.
- `MarkerMissing`, `MarkerInvalid`, `MarkerSchemaUnsupported`, `RegistryInvalid`, `PolicyInvalid`, and `PrivateAccessRequired` retain their separate fail-closed diagnostic categories.
- The optional internal `observeIdentity` argument to `CoverageArtifactStore.Open` and `OpenReadOnly` injects only the marker-comparison observation for deterministic decision tests. It does not replace native handle acquisition, no-follow traversal, binding checks, ownership or permission checks. Simulated observations are not native lifecycle evidence.
- `CoverageArtifactStore.CreateNewDomain(destination, apply, cancellationToken, beforeRegistryPublication = null, onDirectoryCreated = null, beforeDestinationInspection = null)` validates an absolute fresh destination below an existing safe parent. Preview is read-only. Apply atomically creates the private root with no-replace behavior, then initializes marker, child directories, and the empty registry. It never opens the configured old store or changes environment variables and copies no metadata, archives, history, registrations or pins. Multi-file initialization can be interrupted after root publication; such partial private state is preserved and a different fresh path is required on retry. `beforeRegistryPublication` is an optional internal interruption-test seam; production CLI calls omit it. The CLI does not return the raw path, so the operator explicitly selects the same chosen path after successful creation.

There is no schema migration and no marker rewrite. Do not accept an object/file ID alone, waive volume identity, relax owner or ACL/mode checks, regenerate marker data, clear locks, or relabel old evidence as fresh. An operator-selected new domain is separate and empty by design.

## Evidence and limits

Six native lifecycle tests passed on macOS ARM64. They observe identity stability after closing and reopening a handle on the current mount; refuse copied schema-v1 store metadata while preserving both source and copy bytes; detect root and ancestor replacement; reject a linked root; and use native `clonefile` in a temporary directory to verify a distinct object identity and copy-on-write data separation. This demonstrates the current-mount native tuple and exact comparison behavior; it does not launch a second process as a lifecycle proof. The clone test proves host behavior for the current temp volume only. No live user store is touched.

Deterministic injected-observation tests exercise exact identity and volume mismatch classification. Those results simulate the managed comparison decision and are not filesystem or ABI evidence. A separate disposable APFS disk-image experiment was also run under `/private/tmp/issue899-apfs-proof`; it did not use the live shared store. The first 128 MiB image was initialized at one mount path and then detached/remounted, which kept device value `16777239`. After a second temporary APFS image occupied that device number, the first was remounted at the same path and native `fstat` reported device `16777243` with the same inode `16`. The source-built C# CLI returned a store-open refusal classified as `VolumeIdentityMismatch` with unavailable data and `sideEffects=none`. Preview and apply of a fresh domain succeeded while the old mismatched root remained selected. Both disk images were detached after the test. The post-run marker SHA-256 was `b88a65bd8d02a95785bba2c47aaec2f3b356ad22f80ae909b5e6fed043bcceb7`; registry SHA-256 was `0ed7b324ea94152a523fbe7666c62f9305932a72d44cb69ed759baa3dbf3fb92`. These hashes were recorded after the experiment; no before/after equality is asserted. This demonstrates a possible device-reassignment cause on this macOS host, not the original observed mismatch's cause. It is not a reboot test or evidence for other filesystems. Those initial local observations did not include Windows or Linux execution. Automatic schema-v1 continuity across remount/device reassignment remains unsupported.

The first [Ubuntu coverage-security job](https://github.com/forge-trust/AppSurface/actions/runs/40515590537/job/122228600607) and [macOS coverage-security job](https://github.com/forge-trust/AppSurface/actions/runs/40515590537/job/122228600732) for PR #900 passed at revision `6a1af276`. The [Windows job](https://github.com/forge-trust/AppSurface/actions/runs/40515590537/job/122228600558) exposed a test setup assumption: the OS refused an ancestor rename while a descendant handle was retained, even with delete sharing. The lifecycle test now checks that Windows prevention, unchanged binding/identity and sentinel bytes, then verifies the same rename succeeds after releasing the lease. Unix still checks detection after an actual ancestor replacement and preserves the original bytes. This changes only the native test expectation; production handle sharing and ownership checks are unchanged. The repaired [Windows coverage-security job](https://github.com/forge-trust/AppSurface/actions/runs/40523207116/job/122255608363) passed at c281c2ad, as did the [Ubuntu/macOS coverage-security lanes](https://github.com/forge-trust/AppSurface/actions/runs/40523207116) and the [three-platform EvidenceHost acceptance matrix](https://github.com/forge-trust/AppSurface/actions/runs/40523207264). These results predate the later local PR-feedback fixes; their new Windows component-race tests still need a fresh Windows run. These observations do not establish persistent continuity across reboot, migration or cloned volumes.

## Recovery procedure

1. Preserve the whole old private domain, including `store.json`, registry, policy, archives, staging and locks. Keep its reports and provenance as historical evidence.
2. Select a new absolute destination under an existing nonlinked parent and run preview: `appsurface coverage storage new-domain --output ABSOLUTE`.
3. Review the path and explicitly apply: `appsurface coverage storage new-domain --output ABSOLUTE --apply`.
4. If creation is interrupted or fails after making the directory, preserve that private state and choose another fresh destination.
5. Configure future commands explicitly with `APPSURFACE_ARTIFACT_HOME` to the successfully initialized fresh path. The command itself does not alter process or user environment.

Do not delete or edit the old marker, rewrite registry identities, combine old pins with the fresh domain, or describe the new domain as a recovery of old history. This change adds no cross-domain history import; retain the old domain and its archives intact.
