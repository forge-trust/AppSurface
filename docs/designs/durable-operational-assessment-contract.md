## Scope Relationship

This document is the implementation design for [issue #794](https://github.com/forge-trust/AppSurface/issues/794), the first correctness case under [epic #793](https://github.com/forge-trust/AppSurface/issues/793). It refines the “canonical operational assessments” section of the parent [executable-contract adoption rail](durable-executable-contract-adoption-rail.md) without changing the rail’s later cases or ownership boundary.

## Problem Statement

`DurableRuntimeHealthSnapshot` exposes compatibility and worker facts but leaves consumers to decide whether activation may be enabled, a pump may be attempted, or the runtime is ready. Skoolit reconstructed that decision in seven endpoints and treated compatibility as readiness.

The current PostgreSQL implementation also reports connection and timeout failures as `Incompatible` with `ASDUR403`. That claims the store disproved compatibility when the store was not observed. Meanwhile, `IDurableRuntimePump.RunOnceAsync` returns an identical empty result for:

- a genuinely completed pass that found no work;
- a process admission gate closed during shutdown; and
- store admission refusing a draining or already-active pass.

Process-local overlap is a fourth admission outcome but currently throws. External activators therefore cannot distinguish “completed” from “did not run” without reproducing provider logic.

There is also a cancellation race after application execution returns: caller cancellation can cancel successful-sweep bookkeeping and rewrite completed provider work as a canceled or failed pass.

## What Makes This Cool

The new pump attempt is proof-carrying:

- `Completed` certifies that execution returned and terminal heartbeat bookkeeping completed.
- `Refused`, `Unavailable`, and `Incompatible` certify that this invocation did not enter `RunPassAsync`.

This is stronger than adding convenience booleans or friendly error categories. A host can make a new, policy-controlled admission attempt after a returned pre-execution outcome without guessing from zero counts, exception messages, or PostgreSQL details. It does not prove the status of an earlier invocation whose response was lost, another process, or item-level effects.

## Evidence

- A real adopter hand-wrote the operational decision in seven endpoints.
- `PostgreSqlDurableRuntimeHealth.GetAsync` currently catches broad PostgreSQL and timeout failures and returns `Incompatible`/`ASDUR403`.
- Worker and due-dispatch facts currently come from two connections and two statements.
- `PostgreSqlDurableRuntimePump` already contains the correct authority: a process-local pass slot, process admission gate, schema validation, epoch and worker fencing, durable pass admission, execution, and heartbeat finalization.
- The checked-in adoption measurement passes its filing gate; this case does not need another consumer abstraction.

Prior learning applied: `durable-adoption-decision-rule` (confidence 10/10, 2026-09-06). Genericise canonical interpretation and reusable mechanics while keeping routes, authentication, deployment consequences, wake transport, and domain recovery policy host-owned.

## Constraints

1. Preserve the source and binary shape of `IDurableRuntimePump.RunOnceAsync` and `DurableRuntimePumpResult`.
2. Preserve legacy pump behavior except for the documented post-provider-return cancellation correction.
3. Add no HTTP endpoint, route, authorization rule, restart policy, deployment controller, Cloud Tasks type, or host orchestration API.
4. Keep the new public contracts provider-neutral; PostgreSQL-specific classification remains internal to the PostgreSQL package.
5. Use one internal pump attempt machine. The two public APIs must not preflight and then enter the same gate a second time.
6. Classify failures through an explicit allowlist and propagate by default.
7. Do not parse problem codes or state from exception messages.
8. Do not add a fifth public “indeterminate” outcome. Once execution begins, uncertainty remains an exception and durable-state concern.
9. Keep passive provider registration passive. This case starts no worker and applies no migration at runtime.
10. Fully document changed public and internal APIs and verify success, failure, race, and cancellation branches without reflection.
11. Keep implementation provider-first, but do not freeze `IDurableRuntimePumpAdmission` until a runnable packed consumer directly exercises every attempt kind and verifies the no-execution distinction.

## Premises

1. This is a correctness problem, not speculative DX: an adopter reconstructed readiness incorrectly and the provider reports false incompatibility during outages.
2. Health interpretation and provider pump admission form one operational truth boundary. Fixing only the health precheck would still leave hosts inferring whether a pump ran.
3. The public change is additive: preserve the legacy pump and add an opt-in admission-aware interface.
4. The health classifier, atomic observation, pump attempt, and cancellation correction belong in one case because later consumers require truthful outcomes across the whole boundary.
5. `Refused`, `Unavailable`, and `Incompatible` mean `RunPassAsync` was never invoked.
6. Once the pump core invokes `RunPassAsync`, any exception escaping that method and any later finalization failure propagates; exceptions that existing per-surface execution code already converts into durable completion or ambiguous-outcome state retain that behavior.
7. After `RunPassAsync` returns, caller cancellation no longer controls bounded finalization.
8. Host liveness is not durable-store health. No `IsLive` property is added.

## Decisions

- Append `DurableRuntimeHealthState.Unavailable = 5`; do not renumber existing enum values.
- Add `WasStoreObserved`, `CanEnableActivation`, `CanAttemptPump`, and `IsReady` as computed properties. Do not add cross-field constructor validation that would break synthetic or existing snapshots.
- Add the four-kind `DurableRuntimePumpAttempt` contract exactly once in the Provider package.
- Implement `IDurableRuntimePump` and `IDurableRuntimePumpAdmission` on the same PostgreSQL singleton.
- Use one explicit private attempt machine with phase-aware, operation-aware classification.
- Preserve original pre-execution exceptions internally so the legacy projection can rethrow them without message parsing.
- Represent epoch incompatibility and each refusal reason as typed internal outcomes at their origins while preserving every legacy exception type and message.
- Replace the two health reads with one PostgreSQL command and one result row.
- Add `0010_runtime_health_observation.sql`, increasing the required schema version from 9 to 10. It replaces, rather than edits, the shipped due-health function. The function becomes `STABLE`, uses `statement_timestamp()` so its filtering and the returned observation time share one timestamp and statement snapshot, and corrects Schedule due health to count only claimable or reclaimable dispatches.
- Budget hosted shutdown against the worst-case `TimeBudgetPerPass + (2 * ShutdownReserve)` and cancel an active pass no later than `shutdownStart + ShutdownTimeout - (2 * ShutdownReserve)`.

## Public Contract

### Health state and predicates

Add the enum member after the existing values:

```csharp
public enum DurableRuntimeHealthState
{
    Healthy = 0,
    NotStarted = 1,
    Stale = 2,
    Draining = 3,
    Incompatible = 4,
    Unavailable = 5,
}
```

Add these computed properties to `DurableRuntimeHealthSnapshot`:

```csharp
public bool WasStoreObserved =>
    State != DurableRuntimeHealthState.Unavailable;

public bool CanEnableActivation =>
    State != DurableRuntimeHealthState.Unavailable
    && State != DurableRuntimeHealthState.Incompatible
    && SchemaCompatible
    && EpochCompatible;

public bool CanAttemptPump =>
    CanEnableActivation
    && State != DurableRuntimeHealthState.Draining;

public bool IsReady =>
    State == DurableRuntimeHealthState.Healthy
    && CanEnableActivation;
```

Their meanings are deliberately distinct:

- `WasStoreObserved` exposes the snapshot's declared provenance without requiring consumers to infer it from `ObservedAtUtc`. Provider-created snapshots return `false` only when the assessment could not observe the store. Manually constructed snapshots assert provenance through their selected state.
- `CanEnableActivation` says the current assessment authorizes activation; it is not a permanent deployment toggle.
- `CanAttemptPump` is a host precheck. PostgreSQL admission remains authoritative.
- `IsReady` is provider runtime-control-plane readiness. It does not prove application traffic readiness, dependency liveness beyond the observation, or successful business work.

`NotStarted` may enable activation and attempt a pump so a scale-to-zero worker can establish its first heartbeat. `Stale` may attempt a pump so PostgreSQL can apply guarded takeover. `Draining` may remain activation-compatible while refusing new pump attempts.

### Pump attempt

Add:

```csharp
public enum DurableRuntimePumpAttemptKind
{
    Completed = 0,
    Refused = 1,
    Unavailable = 2,
    Incompatible = 3,
}

public sealed record DurableRuntimePumpAttempt
{
    public DurableRuntimePumpAttempt(
        DurableRuntimePumpAttemptKind kind,
        DurableRuntimePumpResult? result,
        string? problemCode);

    public DurableRuntimePumpAttemptKind Kind { get; }
    public DurableRuntimePumpResult? Result { get; }
    public string? ProblemCode { get; }
}

public interface IDurableRuntimePumpAdmission
{
    ValueTask<DurableRuntimePumpAttempt> TryRunOnceAsync(
        DurableRuntimePumpRequest request,
        CancellationToken cancellationToken = default);
}
```

The constructor validates the closed algebra:

| Kind | Result | Problem code |
| --- | --- | --- |
| `Completed` | Required | Must be null |
| `Refused` | Must be null | Must be null |
| `Unavailable` | Must be null | Must equal `ASDUR103` |
| `Incompatible` | Must be null | Must be `ASDUR108` or `ASDUR400`–`ASDUR403` |

Undefined enum values, invalid combinations, and invalid problem codes throw argument exceptions. A completed empty pass contains a non-null, zero-valued `DurableRuntimePumpResult`; it is never represented as `Refused`.

No static factory API, fifth outcome, transport type, or host policy is added in this case.

`IDurableRuntimePumpAdmission.TryRunOnceAsync` both attempts authoritative admission and, when admitted, executes one bounded pass. The `Try` prefix applies only to expected pre-execution admission outcomes: caller cancellation, application execution failures, finalization failures, malformed provider state, and unclassified exceptions still propagate. `Completed` means the bounded pass and terminal bookkeeping completed; inspect its result counts to determine whether individual work succeeded. The first example must call this API directly rather than gating it on a prior rich health read.

## Normative Health Truth Table

| State and facts | Store observed | Enable activation | Attempt pump | Ready |
| --- | ---: | ---: | ---: | ---: |
| Compatible `NotStarted` | Yes | Yes | Yes | No |
| Compatible `Healthy` | Yes | Yes | Yes | Yes |
| Compatible `Stale` | Yes | Yes | Yes | No |
| Compatible `Draining` | Yes | Yes | No | No |
| Schema or epoch incompatible | Yes | No | No | No |
| Store `Unavailable` | No | No | No | No |
| Synthetic `Healthy` with either compatibility flag false | Yes, as declared by its state | No | No | No |

`Unavailable` is dependency uncertainty, not proof of incompatibility and not a process-liveness verdict.

## Unavailable Snapshot Semantics

Unavailable snapshots follow an explicit provenance contract:

| Snapshot field | Schema-status read failed | Runtime observation failed after schema status | Successful runtime observation |
| --- | --- | --- | --- |
| `State` / `ProblemCode` | `Unavailable` / `ASDUR103` | `Unavailable` / `ASDUR103` | Derived from validated store facts |
| `WasStoreObserved` | `false` | `false` because no complete assessment was published | `true` |
| `SchemaCompatible` / `EpochCompatible` | `false` / `false` | `false` / `false` because the current complete assessment failed | Derived from validated store facts |
| `InstalledSchemaVersion` | `0` | Preserve the successfully observed schema-status value | Preserve the successfully observed schema-status value |
| `RequiredSchemaVersion` | Package required version | Preserve the schema-status value | Preserve the schema-status value |
| `ConfiguredRuntimeEpoch` | Local configuration | Local configuration | Local configuration |
| `ActiveRuntimeEpoch` | `null` | `null`; do not publish a partial runtime row | Validated runtime row |
| `WorkerId` | Local configuration | Local configuration | Local configuration |
| `WorkerInstanceId` | `null` | `null` | Validated runtime row, nullable when no heartbeat exists |
| `HostedSurfaces` | Local configuration | Local configuration | Validated worker value, or local configuration when no heartbeat exists |
| `ObservedAtUtc` | One process UTC timestamp captured in the classification catch | One process UTC timestamp captured in the classification catch | Captured database statement timestamp |
| Start, heartbeat, and sweep times | `null` | `null` | Validated runtime row |
| `IsDraining` / `IsPassActive` | `false` / `false` | `false` / `false` | Validated runtime row |
| Due count, oldest due time, and age | `0` / `null` / `null` | `0` / `null` / `null` | Validated due observation |

There is no per-field partial-row accumulator. Runtime-row facts become publishable only after the one result row passes cardinality, type, nullability, enum, and cross-field validation. The store identity is not part of `DurableRuntimeHealthSnapshot` and is never added to an unavailable snapshot.

`ObservedAtUtc` remains non-null for source compatibility. Its XML documentation changes from “authoritative store observation time” to “time of this assessment; database statement time when `WasStoreObserved` is true, otherwise process time for `Unavailable`.” `WasStoreObserved` is the public provenance signal; consumers must not infer provenance from timestamp origin.

The snapshot constructor remains source compatible and does not reject contradictory component facts. The computed predicates fail closed over those facts.

## Internal Pump Architecture

Use a private internal outcome algebra and explicit phase enum. Names may follow repository conventions, but the phases and transitions are normative:

```text
LocalSlotPending
    │ nonblocking process-local slot acquired
    ▼
ProcessAdmission
    │ runtime admission gate entered
    ▼
StoreAdmission
    │ schema, epoch, worker generation, drain, and pass-active checks succeed
    ▼
Executing
    │ RunPassAsync is invoked
    ▼
ProviderReturned
    │ caller cancellation stops owning the operation
    ▼
Finalizing
    │ successful-sweep bookkeeping under provider connection/command bounds
    ▼
Completed
```

The core can return only:

- completed with the exact pump result;
- refused with an internal refusal reason;
- unavailable with `ASDUR103` and the original exception;
- incompatible with an exact allowed code and the original legacy exception.

Unexpected exceptions do not become internal outcomes. They propagate.

The internal refusal reason is a closed, typed set: `LocalPassOverlap`, `ProcessAdmissionClosed`, `Draining`, `StorePassActive`, and `LostWorkerGeneration`. `EpochMismatch` is a distinct typed incompatibility. The carrier may hold `ExceptionDispatchInfo` where the legacy projection must preserve an original exception and stack. These reasons are not exposed publicly and no projection inspects exception text.

### Process-admission linearization

`DurableRuntimeAdmissionGate.TryEnter()` returning `true` while holding its existing lock is the process-admission linearization point. If `TryEnter()` wins the lock before `Close()`, that one already-serialized invocation is admitted and may continue; `Close()` rejects only attempts whose `TryEnter()` linearization occurs afterward. Closing the gate does not revoke an admitted pass or cancel it directly. Hosted shutdown owns cancellation through its active-pass token and the shutdown budget.

Tests pause both sides of the lock and prove both legal orders: close-first yields `Refused` with zero executor calls, while enter-first permits exactly that invocation and rejects the next one. No separate reservation handle or second gate is introduced.

### Execution-boundary test seam

Add an internal-only pass-executor delegate or interface used at the sole transition into `Executing`. The production constructor binds it directly to `RunPassAsync`; an internal constructor used through the existing test assembly friendship can inject a counting or blocking executor. The seam is not registered publicly and cannot change provider authority.

Every returned non-completed admission-outcome test asserts that the executor invocation count remains zero. Completed-path tests assert exactly one invocation. Pump-level cancellation or exception tests distinguish phase explicitly: failures before `Executing` assert zero invocations, while failures after the transition assert exactly one. Tests use this intentional internal seam and `InternalsVisibleTo`; reflection is prohibited.

### Legacy projection

`RunOnceAsync` maps the one core result as follows:

| Core outcome | Legacy behavior |
| --- | --- |
| Completed | Return the exact result |
| Local overlap refusal | Throw the existing `InvalidOperationException` with the existing `ASDUR405` message |
| Closed process gate, draining, or active-pass refusal | Return the existing empty result |
| Worker-identity conflict refusal | Rethrow the original `InvalidOperationException` beginning with `ASDUR405` |
| Unavailable | Rethrow the original exception |
| Incompatible | Rethrow the original schema or epoch exception |

Use `ExceptionDispatchInfo` or an equivalent typed internal carrier when necessary to preserve the original exception and stack. Do not reconstruct legacy failures from problem-code strings.

The compatibility contract is:

| Existing path | Required legacy exception/result | Inner exception and stack | Failed-pass cleanup |
| --- | --- | --- | --- |
| Null request | Existing `ArgumentNullException` | Preserve normal argument stack | No |
| Caller canceled before slot acquisition | Existing `OperationCanceledException` | Preserve caller token association | No |
| Process-local overlap | `InvalidOperationException` with the existing exact `ASDUR405: This runtime instance already has an active Pass.` message | No synthesized inner exception | No |
| Process admission closed | Existing zero-valued pump result | Not applicable | No |
| Observed schema incompatibility | Original `DurableRuntimeSchemaException` with the same `Status`, message, and existing inner exception | Rethrow through `ExceptionDispatchInfo` if carried as an internal outcome | No |
| Pre-execution store outage | Original `NpgsqlException`, `PostgresException`, or `TimeoutException` | Preserve concrete type, inner exception, SQLSTATE, and stack | No |
| Package-owned provider deadline or typed `57014` before execution | Rethrow the original cancellation or provider exception | Preserve concrete type, inner exception, token association, SQLSTATE, and stack | No |
| Runtime epoch mismatch | `InvalidOperationException` with the existing exact `ASDUR108: The configured runtime epoch is not active in PostgreSQL.` message | No message parsing or synthesized inner exception | No |
| Worker identity conflict | Original `InvalidOperationException` with the existing exact `ASDUR405: This worker generation no longer owns the configured worker identity.` message | Preserve original stack | No |
| Exception escaping `RunPassAsync` | Rethrow the original exception | Preserve concrete type, inner exception, and stack | Yes; cleanup failure is suppressed |
| Successful-sweep finalization failure | Rethrow the original finalization exception | Preserve concrete type, inner exception, and stack | Yes; cleanup failure is suppressed |

Exceptions captured inside existing Work, Flow, or Schedule execution logic retain their current durable transition and counting behavior; this case does not promote them into pump-level exceptions.

### Admission-aware projection

`TryRunOnceAsync` maps:

| Core outcome | Attempt |
| --- | --- |
| Completed, including an empty pass | `Completed` with the exact result |
| Local overlap, closed process gate, drain, or active-pass refusal | `Refused` |
| Worker-identity conflict before execution | `Refused`; the executor invocation count remains zero |
| Classified pre-execution store failure | `Unavailable` + `ASDUR103` |
| Observed schema or epoch incompatibility | `Incompatible` + the exact code |

Worker-identity conflict is an admission refusal, not schema or epoch incompatibility. Caller cancellation and every failure escaping `RunPassAsync` after entry into `Executing` propagate from both public APIs. Exceptions intentionally captured by existing per-surface execution logic retain their established durable completion or ambiguous-outcome behavior and are not promoted to pump-level failures.

### Dependency injection

Register `PostgreSqlDurableRuntimePump` as one concrete singleton, then resolve both public interfaces from that singleton:

```csharp
services.TryAddSingleton<PostgreSqlDurableRuntimePump>(CreatePump);
services.TryAddSingleton<IDurableRuntimePump>(
    static provider => provider.GetRequiredService<PostgreSqlDurableRuntimePump>());
services.TryAddSingleton<IDurableRuntimePumpAdmission>(
    static provider => provider.GetRequiredService<PostgreSqlDurableRuntimePump>());
```

This is required so both interfaces share the same process-local pass slot and cannot admit concurrent passes through separate pump instances.

Preserve the package’s existing `TryAdd` override convention. The default registration guarantees that the concrete service and both public interfaces are reference-equal. A consumer replacing pump behavior must pre-register the same singleton under both public interfaces before calling `AddAppSurfaceDurablePostgreSql`; partial pump overrides are unsupported for concurrent use and are documented as such. Package registration does not overwrite a pre-registered interface, preserving existing override behavior.

Tests cover the default reference identity, a complete two-interface custom override, and each partial override. A legacy-only override remains usable through `IDurableRuntimePump`, preserving existing behavior. When a consumer with that override first resolves the package-default `IDurableRuntimePumpAdmission`, its factory must fail with an actionable composition error before any pump invocation because the two interfaces would not share a process-local slot. The adoption guide supplies a complete two-interface replacement example and a provider-resolution assertion for custom composition. A pre-registered admission-only override is also documented and tested as unsupported with the default legacy pump; because it is new surface with no existing compatibility obligation, release verification may reject that composition during registration if it can do so without constructing the provider.

## Phase-Aware PostgreSQL Failure Classification

Create one internal classifier shared by health observation and the pre-execution sections of the pump core. Its inputs include:

- the operation: health observation, schema admission, or runtime admission;
- the exception;
- the caller token;
- typed provider-timeout evidence when SQLSTATE `57014` is considered.

Do not call the classifier around application execution, failed-pass cleanup, or successful-sweep finalization.

An internal control-plane command helper produces `PostgreSqlDurableTimeoutEvidence` with only `None` or `ProviderDeadlineElapsed`. It receives an already-created `NpgsqlCommand`, reads its positive inherited `CommandTimeout`, creates a sidecar deadline token for that duration, and links it only with the caller token for the command invocation. It does not assign `CommandTimeout`, add another package timeout option, or alter connection-string settings. If command timeout is disabled with zero, it creates no package deadline evidence and relies on provider exception evidence. Connection opening retains the runtime data source’s configured connection timeout and is classified only from its exception shape.

The helper is used by every command in schema-status validation, health observation, and pre-execution runtime admission, including the schema manager’s internally created status commands. A wrapper around `ValidateAsync` alone is insufficient because those commands are otherwise opaque to the caller. Add an internal schema-manager execution seam without changing `IDurableRuntimeSchemaManager`. The helper is never used by application execution, failed-pass cleanup, or successful-sweep finalization; only Npgsql enforces the command timeout.

Evidence is `ProviderDeadlineElapsed` only when that package-owned deadline fired, or the exception chain contains a provider-generated `TimeoutException`. The wrapper records caller and provider deadline signals separately before disposing the linked token. It never accepts application-supplied evidence and is not used inside `RunPassAsync`.

Cancellation precedence is deterministic:

1. An `OperationCanceledException` with the caller token canceled propagates as caller cancellation, even if the provider deadline also expired.
2. When the caller token is not canceled and the package-owned operation deadline fired, cancellation or `57014` is provider-timeout evidence and maps to `Unavailable`.
3. Server `statement_timeout`, administrative cancellation, or bare SQLSTATE `57014` without typed evidence propagates. The classifier does not inspect localized messages.
4. A non-cancellation exception is never relabeled as caller cancellation merely because the caller token happened to become canceled before the catch executed.

| Evidence | Result |
| --- | --- |
| `OperationCanceledException` while caller token is canceled | Propagate caller cancellation |
| Package-owned provider deadline elapsed before execution, including its `OperationCanceledException` | `Unavailable` + `ASDUR103` |
| Provider-generated `TimeoutException` before execution | `Unavailable` + `ASDUR103` |
| Transport-level transient `NpgsqlException` before execution | `Unavailable` + `ASDUR103` |
| SQLSTATE class `08`, `53300`, `57P01`, `57P02`, or `57P03` before execution | `Unavailable` + `ASDUR103` |
| SQLSTATE `57014` with typed `ProviderDeadlineElapsed` evidence | `Unavailable` + `ASDUR103` |
| SQLSTATE `42501` while reading health or admission state | `Unavailable` + `ASDUR103` |
| `DurableRuntimeSchemaException` or observed incompatible schema status | `Incompatible` + its exact existing code |
| Typed internal epoch mismatch | `Incompatible` + `ASDUR108` |
| Bare `57014`, administrative cancellation, undefined relation/function, malformed row, invalid enum/value, contradictory provider result, unrelated cancellation, or unclassified exception | Propagate |

`NpgsqlException.IsTransient` may support transport classification but does not replace the SQLSTATE allowlist. In particular, a `PostgresException` with an unlisted SQLSTATE propagates even if a broad provider property could call it transient.

Exceptions escaping `RunPassAsync` occur after the transition to `Executing` and always propagate. Exceptions thrown by an already-permitted application invocation that existing per-surface code captures continue through the current durable `AmbiguousExternalOutcome` or other established completion path; the classifier never sees them.

The existing epoch check must stop requiring downstream message parsing. It should produce a typed internal mismatch at the admission origin while allowing the legacy projection to throw the same `InvalidOperationException` type and message as today.

The classifier also returns an internal, fixed cause of `Transport`, `ProviderDeadline`, or `PermissionDenied` whenever it produces public `Unavailable` / `ASDUR103`. Health and pump call sites emit one structured warning through `ILogger` with a stable event id, the fixed operation and phase, that cause, `ASDUR103`, and the canonical troubleshooting anchor. Refusals use a separate stable event and the fixed internal cause `LocalPassOverlap`, `ProcessAdmissionClosed`, `Draining`, `StorePassActive`, or `LostWorkerGeneration`; expected local/store contention is Debug-level, while lost worker generation is Warning-level. The event must not include SQL text, exception messages, connection strings, role names, payload identifiers, scope identifiers, or aggregate identifiers. Documentation maps transport to connectivity/retry checks, provider deadline to query/pool/backlog investigation, permission denial to the runtime-role recipe, and each refusal to whether waiting, shutdown completion, or worker replacement is appropriate. The coarse provider-neutral public contract does not grow a PostgreSQL cause field.

## Atomic PostgreSQL Health Observation

Schema status remains a bounded precheck. This design does not claim a serializable transaction across schema validation and later worker observation; pump admission validates schema and epoch again.

After compatible schema status:

1. Open one runtime connection.
2. Execute one SQL statement.
3. Capture `statement_timestamp()` once as the observation time.
4. Read store metadata, optional worker heartbeat, and selected-surface due facts into one result row.
5. Construct the snapshot only after the entire row validates.

The statement has this normative shape:

```sql
WITH observed AS
(
    SELECT statement_timestamp() AS observed_at_utc
)
SELECT observed.observed_at_utc,
       metadata.active_runtime_epoch,
       heartbeat.worker_instance_id,
       heartbeat.runtime_epoch,
       heartbeat.hosted_surfaces,
       heartbeat.started_at,
       heartbeat.last_heartbeat_at,
       heartbeat.last_successful_sweep_at,
       heartbeat.draining,
       heartbeat.pass_active,
       due.due_count,
       due.oldest_due_at
FROM observed
JOIN appsurface_durable.store_metadata AS metadata
  ON metadata.singleton
LEFT JOIN appsurface_durable.runtime_heartbeat AS heartbeat
  ON heartbeat.worker_id = @worker_id
CROSS JOIN LATERAL
    appsurface_durable.runtime_due_dispatch_health(@surfaces) AS due;
```

The command must yield exactly one row. Zero rows, a second row, `NULL` in a required column, the wrong provider type, an undefined or invalid hosted-surface value, a negative due count, `due_count = 0` with a non-null oldest time, `due_count > 0` with a null oldest time, or an oldest due time after the captured observation time is malformed provider state and propagates as `InvalidDataException` or the original provider conversion exception.

`EpochCompatible` is computed only from `metadata.active_runtime_epoch == ConfiguredRuntimeEpoch`. A heartbeat row from an older epoch or different worker instance is valid stale-generation evidence, not malformed state: when the metadata epoch authorizes this runtime, the existing resolver returns `Stale`/`ASDUR405` and provider admission retains its guarded takeover rules. When no heartbeat row exists, the application reader maps its nullable left-joined timestamps and identifiers to null and maps nullable `draining` and `pass_active` to false. When a heartbeat row exists, its worker instance, runtime epoch, hosted surfaces, start time, and heartbeat time must be non-null and correctly typed; only the successful-sweep time remains lifecycle-nullable.

Column requirements are:

| Column group | PostgreSQL type | Nullability |
| --- | --- | --- |
| Observation time | `timestamp with time zone` | Required |
| Active epoch | `uuid` | Nullable |
| Worker instance and heartbeat epoch | `uuid` | Both nullable only when no worker row exists |
| Hosted surfaces | `smallint` | Nullable only when no worker row exists; otherwise one non-empty defined mask |
| Start, heartbeat, and sweep times | `timestamp with time zone` | Nullable according to worker lifecycle |
| Drain and active-pass flags | `boolean` | Nullable only through the absent left-joined worker row and normalized to false |
| Due count | `bigint` | Required and nonnegative |
| Oldest due time | `timestamp with time zone` | Nullable exactly when due count is zero |

Add `0010_runtime_health_observation.sql`, raising `RequiredSchemaVersion` to 10, and use `CREATE OR REPLACE FUNCTION` for `runtime_due_dispatch_health(integer)`:

- do not edit migration `0005_runtime_heartbeat.sql`;
- declare the read-only function `STABLE`, ensuring its internal reads use the calling statement snapshot under PostgreSQL function-volatility rules;
- replace each due comparison against `clock_timestamp()` with `statement_timestamp()`;
- define “due” as claimable or reclaimable at that statement timestamp: Work and Flow continue using their dispatch `due_at`, which is advanced to the lease expiry when claimed; Schedule uses `due_at` only while `available` and `lease_expires_at` while `leased`, so an active Schedule lease is not counted as due;
- add a selective partial Schedule lease-expiry index if the exact nested plan cannot use an existing index for the reclaimable predicate;
- preserve the function signature, owner, security-definer boundary, and fixed search path;
- explicitly `REVOKE ALL ... FROM PUBLIC` after replacement, add the same reconciliation to `configure-postgresql-roles.sql`, and verify that only the runtime role can execute the function;
- preserve reader compatibility for the last supported schema-9 package, then rerun the canonical role recipe after applying migration `0010` to reconcile and verify runtime-role grants.

## Cancellation and Finalization

Cancellation ownership changes at one explicit boundary:

- Before and during `RunPassAsync`, the caller token propagates normally.
- The linearization point is the continuation immediately after the awaited `RunPassAsync` completes successfully and before any finalization await begins. The machine irreversibly records `ProviderReturned` there without re-reading the caller token.
- Create and dispose a fresh finalization `CancellationTokenSource` with `_registration.Options.ShutdownReserve` as its total wall-clock bound. It is never linked to the caller token and is created even when that token is already canceled.
- Pass the finalization token to connection opening, transaction creation, epoch validation, heartbeat update, and commit. Existing Npgsql connection and command timeouts remain additional, potentially earlier bounds.
- If caller cancellation arrives after `ProviderReturned`, finalization continues and a successful finalization returns `Completed`.
- If the finalization deadline expires, propagate its `OperationCanceledException` as a pump-level finalization failure. Do not return `Unavailable`, `Incompatible`, or caller cancellation because application work may already have executed.
- Attempt failed-pass cleanup with a separate fresh `ShutdownReserve` token, without the caller token and without replacing the original execution or finalization exception.

This is the only intentional legacy behavior correction. It requires a release note and an exact regression test. Let `H = HostOptions.ShutdownTimeout`, `T = TimeBudgetPerPass`, and `R = ShutdownReserve`. Hosted registration requires `T + (2 * R) <= H`; reject non-positive effective pass time and compute the doubled reserve without overflow. On shutdown, cancel the active pass no later than `shutdownStart + H - (2 * R)`. `TimeBudgetPerPass` bounds discovery and beginning additional work; it is not a total method timeout. After execution returns, successful finalization may consume one `R`. If finalization fails, cleanup may consume one additional fresh `R`, so the worst-case provider-owned post-return wait is two reserves plus scheduling overhead. An outer host deadline can still terminate the process before best-effort cleanup finishes.

The hosted-service cancellation catch must identify the cancellation token/phase that ended application execution; it must not swallow a finalization `OperationCanceledException` merely because the earlier pass token is also canceled. A race test first cancels the pass token, then expires finalization, and proves that the finalization failure escapes.

If the store-admission update or commit was sent but its acknowledgement is lost, the invocation still has not entered `RunPassAsync`, but `pass_active` may have committed. The core records this as an internal indeterminate-admission phase and attempts one ownership-scoped failed-pass cleanup with a fresh reserve before projecting the classified pre-execution result. Cleanup failure is logged and suppressed, never changes the public outcome or legacy original exception, and a later stale-worker takeover remains the durable fallback.

## Approaches Considered

- **Inline core extraction:** rejected because phase safety would remain encoded primarily in local control flow and catch placement, making later regressions easier.
- **Explicit internal attempt machine:** selected because it makes the no-execution proof, cancellation handoff, classifier boundary, and legacy projection reviewable and testable.
- **PostgreSQL admission protocol:** rejected because it expands the migration and rollout surface without improving the intentionally collapsed public `Refused` outcome.

## Recommended Approach

Implement the explicit internal attempt machine. Keep all phases and internal outcomes private to the PostgreSQL package; the only new public concepts are the three health predicates, `Unavailable`, and the four-kind admission-aware pump attempt.

This is the smallest architecture that makes the central promise mechanically difficult to violate:

> Every returned non-completed attempt proves that this invocation did not enter `RunPassAsync`.

| Pump before `Executing` | Schema/epoch incompatibility | Public `Incompatible`; legacy original exception | Yes | Do not enter executor | Exact compatibility code/status |

No catch-all converts unknown failures into a safe result. The only swallowed errors are best-effort cleanup failures that would otherwise mask the authoritative exception.

### Section 3 — Security & Threat Model

One medium-likelihood, high-impact issue was found: SQLSTATE `42501` is correctly evidence that the store was not observed, but treating it like a retryable network outage can create noisy retries and hide a role misconfiguration. The public provider-neutral state remains `Unavailable`; PostgreSQL documentation and safe diagnostics must identify permission configuration as an operator-action cause without exposing SQL, connection strings, role names supplied by users, payloads, scope ids, or aggregate ids.

No new endpoint, secret, untrusted string interpolation, application assembly loading, or authorization boundary is added. The migration retains the existing `SECURITY DEFINER`, fixed `search_path`, owner, revoke, and explicit-grant posture.

### Section 4 — Data Flow and Edge Cases

Three issues were found: retry language did not cover lost responses, the unavailable snapshot reused a timestamp with different provenance, and rich health cost was not tested under backlog. Retry language and scale evidence are accepted, and the approved computed `WasStoreObserved` property makes provenance explicit.

```text
request
  │ null/invalid ──▶ reject before slot
  ▼
local slot
  │ overlap ───────▶ Refused / legacy ASDUR405
  ▼
process + store admission
  │ closed/busy ───▶ Refused
  │ unobserved ────▶ Unavailable / ASDUR103
  │ incompatible ─▶ Incompatible / exact code
  ▼
RunPassAsync
  │ throws ────────▶ original exception + bounded cleanup
  │ empty result ──▶ Completed with non-null zero result
  ▼
provider-bounded finalization
  │ fails ─────────▶ original finalization exception + bounded cleanup
  ▼
Completed
```

Safe retry means only that the caller may make a new admission attempt after a returned pre-execution outcome according to host policy. It does not prove the status of an earlier invocation whose response was lost, another concurrent process, or item-level external effects.

### Section 5 — Code Quality Review

Three issues were found and resolved:

- Keep one private state machine and one classifier; do not duplicate catch filters in health and pump methods.
- Name phases for authority boundaries, not incidental methods, and make invalid transitions impossible through one internal result carrier.
- Keep `RunPassAsync` as the single execution seam so tests can count entry without reflection.

The anticipated branch count belongs in small transition/classification helpers rather than one deeply nested method. The public algebra remains small; provider-specific evidence and legacy exception carriers stay internal.

### Section 6 — Test Review

Four missing proofs were added:

- Migration-first mixed-version compatibility plus old-binary rollback.
- Lost-response/retry wording and outcome-matrix contract tests.

The hostile test cancels the caller at each await boundary while independently blocking the executor and finalizer. ### Section 7 — Performance Review

One high-priority issue was found. `count(*)` plus `min(due_at)` is exact work over all due rows even with partial due indexes; a one-statement snapshot improves consistency but does not make this cost constant. Extend `PostgreSqlScaleIntegrationTests` to prove index use and record bounded latency at production-shaped backlog. Do not add a cache: readiness and admission require current state, and stale cached compatibility would be more dangerous than a bounded failure.

### Section 9 — Deployment and Rollout Review

Two risks were found and accepted into the release proof:

```text
1. Build and pack Provider + PostgreSQL packages.
2. Apply the new numbered migration with the migration owner.
3. Verify function signature, owner, grants, volatility, and statement-time behavior.
4. Run old package binary against the upgraded store.
5. Deploy the new package binary.

```

Rollback:

```text
new binary unhealthy?
  ├── public/API regression ──▶ redeploy old binary; additive migration remains compatible
  ├── function semantic defect ▶ CREATE OR REPLACE with a reviewed corrective forward migration
  └── store integrity concern ─▶ stop activators, retain evidence, restore/repair under migration-owner procedure
```

Do not delete migration history or edit migration `0005`. Database rollback is forward-fix because numbered migration history is immutable; binary rollback is supported by the compatibility range and unchanged function signature.

Architecture findings:

1. **P1 / high confidence — Finalization cancellation can be swallowed by the hosted loop.** The current catch checks only whether the earlier pass CTS is canceled. Once finalization uses a separate token, that condition may still be true and incorrectly turn a finalization failure into a clean loop exit. Require phase/token identity and a race test.
2. **P1 / high confidence — Shutdown accounting was internally inconsistent.** Two sequential post-return reserves require `T + 2R <= H`, not `T + R <= H`. Active execution must be canceled at `H - 2R`.
3. **P1 / high confidence — A caller-level timeout wrapper misses schema-manager commands.** The helper must sit at command execution inside schema status, health, and admission. It observes inherited `CommandTimeout`; it does not configure a competing timeout.
4. **P1 / high confidence — Schedule due health is currently false for active leases.** Unlike Work and Flow, Schedule keeps the original `due_at` while leased. Migration 0010 must use `lease_expires_at` for leased Schedule rows and prove an eligible plan.
5. **P1 / high confidence — Compatibility cannot be inferred from the schema range alone.** An actual v0.2.0-preview.8 binary must run against schema 10 with reconciled roles and exercise status, health, heartbeat, and real work.
6. **P1 / high confidence — Function replacement does not repair privilege drift.** Migration 0010 and the role recipe explicitly revoke `PUBLIC`; preflight checks ownership before replacement.
7. **P1 / medium-high confidence — Lost store-admission acknowledgement can strand `pass_active`.** The no-execution proof remains true, but the machine needs a bounded, ownership-scoped cleanup attempt and durable stale-takeover fallback.
8. **P2 / high confidence — DI compatibility needs a runtime identity assertion.** Existing `TryAdd` behavior must remain, but unsupported partial composition must fail before admission invocation.
9. **P2 / high confidence — Closing admission does not revoke a winner.** This is safe once documented: `TryEnter()` true is the winner, `Close()` rejects later attempts, and hosted cancellation handles the admitted pass.
10. **P2 / high confidence — Public provenance needs an explicit projection.** The approved computed `WasStoreObserved` removes state-dependent timestamp interpretation without changing constructor compatibility.

No new public PostgreSQL type, second pump, transport abstraction, or host service is needed.
