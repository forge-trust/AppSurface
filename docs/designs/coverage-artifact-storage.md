## Problem and product promise

AppSurface promises to remove friction from highly agentic development. Repeated tests across many worktrees currently accumulate large coverage reports and require manual cleanup. The user called this a failure to deliver “champion tier DX” and set the adoption requirement: “They should upgrade and appsurface's new defaults should help unless they have their usage patterns differ. If they do have large amounts of stored materials we should warn them.”

The observed cross-repository audit found 3,675 coverage.cobertura.xml files with 43.08 GB reported allocation, and 30.26 GB of QA XML with timestamps within seven days. Those are inventory measurements, not guaranteed reclaimable bytes. A separate read-only experiment in this checkout compressed 468 reports from 1.31 GB to 74.6 MB, with matching SHA-256 after decompression. An affected downstream sample compressed from 34.83 MB to 1.88 MB. Neither experiment changed files or ran a coverage gate.

The desired experience is an afternoon of parallel agent work with complete coverage verification, retrievable debugging evidence, predictable retained history, and clear warnings when custom usage falls outside managed behavior. Upgrading the existing CLI is the normal adoption path.

## Decisions and boundaries

- Approach B is selected: a shared local artifact manager behind existing commands, without a daemon or mandatory service.
- Keep the existing [public coverage commands](https://github.com/forge-trust/AppSurface/blob/main/Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-run) and [shared private engine](https://github.com/forge-trust/AppSurface/blob/main/Evidence/ForgeTrust.AppSurface.Evidence.Coverage/README.md). Do not introduce a second coverage implementation or a public coverage-engine package.
- Preserve test selection, instrumentation, exclusions, aggregate and patch metrics, thresholds, tolerance, watchdog behavior, cancellation, and failure semantics. A storage warning cannot turn incomplete evidence into a pass.
- Preserve current report paths and bytes for gates, package proof, external readers, and CI upload. A test-process exit is not proof that every consumer has finished.
- Manage only explicitly registered AppSurface outputs and the manager's own archives. Diagnose other stored material without assuming ownership, rewriting projects, or deleting it.
- Run automatic inspection and maintenance within bounded time and traversal budgets. No whole-home scan or required cleanup schedule.

The rejected alternatives are independent per-output retention, which multiplies limits across worktrees, and CI-centered history, which requires consumer infrastructure and does not cover local-only work. Remote export remains possible through existing consumer upload steps; it is outside this delivery.

## Architecture and lifecycle

```text
existing coverage run / merge / gate / Evidence
                |
       shared private artifact manager
        /                       \
registered output directories    user-local history store
current XML and diagnostics      verified compressed snapshots
existing paths remain usable     shared byte and age policy
```

Use the platform's per-user local application-data directory under ForgeTrust/AppSurface/artifacts/v1. Keep it outside Git and avoid roaming or shared network storage by default. APPSURFACE_ARTIFACT_HOME is a proposed optional override for isolated CI or custom local storage; an override creates a separate management domain and budget. A user-scoped settings file in that domain owns shared limits so repositories cannot silently impose conflicting global policy.

Each participating invocation registers the physical output identity, repository/worktree identity, owner schema, run ID, producing CLI version, timestamps, outcome, known artifact inventory, and accounting status. Do not derive identity solely from a remote URL or basename. Store versioned, bounded per-output/per-run JSON with atomic replacement and interprocess locking; use the standard library and existing filesystem helpers before adding a database dependency. Missing registrations can be reconstructed from valid new run manifests. Unknown schema versions are preserved and reported as unsupported, never interpreted as deletion authority.

Lifecycle:

1. **Running:** hold an output writer lease for the entire mutation period. Distinct outputs run concurrently; a conflicting writer to the same output fails clearly before cleanup.
2. **Current:** publish the canonical XML, project manifests, logs, timings, and reports at their existing locations. Current output remains excluded from global reclamation even after commands return.
3. **Superseded:** when a later normal clean invocation is about to replace that same output, attempt a stable compressed snapshot of the previous run before the existing cleanup. This is the replacement boundary consumers already have today, not a new idle-time expiry of current reports. A gate must not mark the output globally reclaimable: it cannot know about later external readers.
4. **Archived:** publish a history manifest only after the snapshot has passed integrity checks. A restored archive is a historical copy, never current coverage evidence for a new source revision.
5. **Expired:** remove eligible, unpinned manager-owned archives according to the shared policy. Preserve a bounded receipt explaining expiry; receipts and abandoned staging files must also have explicit count/byte limits.

AppSurface run, merge, gate, Evidence, explicit cleanup, snapshot, restore, and pin operations participate in the same protocol. Internal calls reuse a lease context to avoid reacquiring their own lock. Readers take shared leases; mutation and reclamation take exclusive leases. No global lock is held while tests run or payloads compress. A short metadata lock selects work, then each candidate is revalidated under its own lease before mutation. Lock acquisition order is fixed and tested.

External programs do not automatically participate in AppSurface leases. Current paths therefore remain available until their documented replacement or explicit cleanup, and no global background operation removes them. Existing instructions to avoid starting a replacement run while an external tool reads the same output still apply. Unknown or older CLI writers are not assumed to cooperate; outputs without a compatible run manifest receive legacy treatment. Mixed-version use does not authorize retroactive cleanup.

## Storage defaults

These are proposed shipping defaults to validate in the consumer fixture, not measured optimums:

| Behavior | Default |
| --- | --- |
| Current output | Existing uncompressed canonical paths; never evicted by the shared archive budget |
| Historical payload | Streaming gzip-compressed run archive with original relative paths and per-file SHA-256/length |
| Shared unpinned history budget | 2 GiB of stored archive and metadata bytes across registered outputs |
| Historical age limit | Seven days from archival; eligible unpinned runs expire sooner if the byte budget requires it |
| Eviction order | Oldest eligible successful history first, then oldest eligible failed/interrupted history |
| Protected data | Active operations, current outputs, pinned archives, explicit preservation mode, and unknown ownership/schema |
| Routine repository inspection | At most one second and 10,000 entries per invocation; incomplete results labeled as lower bounds |
| Routine maintenance | At most two seconds per invocation, cooperative cancellation, and bounded staging; explicit maintenance can do a full pass |
| Large-storage warning | At least 1 GiB observed in one repository or 2 GiB observed across registered current outputs and history |
| Repeat warning | Once per condition per 24 hours; sooner after at least 25% and 256 MiB growth, or a new inspection failure |

The shared budget is a target for eligible managed history, not a hard cap on the machine, current output, or deliberately pinned material. Account for those categories separately and warn when they dominate. A single new output directory per invocation is a custom retention pattern: register and count it, but do not silently reclaim its current contents. This limit is part of the public product contract.

Retain complete failed-run snapshots while they remain in history. Successful-first eviction improves diagnosis but cannot promise to keep every failure indefinitely within a finite budget. Pin the run for investigations or release evidence that must survive automatic expiry. No default minimum-count rule may silently defeat the byte budget.

Archive failure is secondary: normal run/gate outcomes remain authoritative. If a best-effort historical snapshot cannot finish before its budget or disk space runs out, do not publish a completed archive or promise recoverability. Warn that history was not saved; the existing normal clean replacement can continue. An explicit pin operation succeeds only after a complete verified archive exists, otherwise it fails without claiming protection. Pins protect the archived copy, not a future replacement of the current output path.

If shared state is read-only, locked, corrupt, full, or on an unsupported filesystem, continue the existing coverage workflow with local ownership protections and report reduced storage-management capability. Do not invent a second unmanaged history directory as a fallback. An inability to prepare the required current output still fails normally; a storage warning cannot hide missing required reports.

## Eliminate redundant current-run storage

Keep exactly the established canonical per-project report and top-level merged report. After successful normalization, verify raw/canonical equivalence and remove only the redundant collector XML owned by that invocation. Preserve other collector attachments, VSTest sequences, and failure diagnostics. Do not remove the raw file on validation, promotion, or cleanup failure; preserve the primary outcome and report the secondary condition.

After validated top-level publication, remove a duplicate ReportGenerator Cobertura payload only where no existing consumer contract requires that intermediate file. Preserve staged public coverage-merge inputs checked by the packed proof in this delivery. Do not change their artifact contract merely to claim a higher saving. Custom attachment references need a documented full-retention compatibility option.

Existing --no-clean continues to mean preservation: it disables automatic removal or compression inside that output and emits a throttled growth warning if necessary. A new optional full-retention mode must also retain current-invocation duplicate XML for consumers explicitly depending on raw collector paths. Neither mode changes instrumentation or metrics. Archived copies are lossless; whitespace stripping, dropping methods/conditions, SingleHit changes, and narrowed coverage filters are excluded.

## Warnings that help humans and agents

Inspect automatically during normal coverage preflight and at terminal artifact publication, with shared support for the first-party Evidence path. Reuse evaluated project capabilities to obtain RunSettingsFilePath and collection-related properties for the selected configuration/framework. Parse the effective regular settings file safely, without DTD/external resolution. Identify a configured, enabled XPlat collector as a risk that ordinary dotnet test can collect coverage. Do not diagnose from the filename alone, infer that every command used it, or modify it automatically.

Inspect known coverage/test-output locations within the current repository and directly registered outputs. Skip Git metadata, build dependencies, links, special files, and nested repositories. Do not enumerate other home directories or arbitrary worktrees. Aggregate cross-worktree totals from registrations, including observation age and missing/unreadable entries. Unregistered old data is found only within the bounded repository scan or an explicit inspection root.

A warning contains a stable diagnostic identifier, measured bytes and file/run counts, scope, observation time/completeness, the largest contributing paths, and one next action. Human warnings go to stderr and a linked summary; bounded structured diagnostics support agents and CI. They never change test/gate exit codes or grant permission to delete. New optional fields are additive and schema-versioned; do not insert host paths or test contents into public Evidence claims.

Example wording:

> Coverage storage: at least 8.4 GiB observed in 241 reports under tests/*/TestResults; inspection reached its entry limit. Your effective settings enable coverage during ordinary test runs. AppSurface manages its own outputs; these reports need a separate retention decision. Inspect the listed paths and follow the linked explicit-collection migration.

Show retained bytes, archives expired, skipped protected bytes, and maintenance capability in the normal completion summary. Keep the healthy summary short. Persist only bounded local diagnostics and warning-throttle state; there is no outbound telemetry.

## Optional control and retrieval surface

The following CLI names are proposed new surfaces, not commands available today:

- **coverage storage:** show the effective domain, limits, current/history/protected bytes, observation completeness, and management capability; no mutation.
- **coverage storage inspect --root <repo>:** perform an explicit cancellable inspection, including unmanaged TestResults, without deleting or adopting them.
- **coverage storage maintain:** finish a full pass over eligible owned history under the same safety policy. Normal commands already do bounded maintenance.
- **coverage storage restore --run <id> --output <fresh-directory>:** verify and extract a historical snapshot into a new non-linked destination, without overwriting current reports.
- **coverage storage pin/unpin --run <id>:** control expiry of a verified archive. Pinning a current run first creates and verifies its snapshot under a reader lease. A corrupt or missing archive cannot be pinned successfully.

The current [coverage clean preview/apply commands](https://github.com/forge-trust/AppSurface/blob/main/Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-clean) remain explicit recovery tools. Do not automatically run the broad --all sweep. Documentation must distinguish shared-history expiry from worktree cleanup, and make effects on pinned archives explicit before a new archive-deletion command is introduced.

## Integrity, interruption, and resource behavior

Stream compression and hashing. Stage within the managed store, flush, verify decompressed length and hash, then atomically publish metadata. Never remove the sole source as part of archive publication. Recheck source identity and modification state; concurrent changes invalidate the snapshot. Hashes describe the original bytes, with separate stored-payload hashes where needed.

Restore rejects absolute paths, parent traversal, duplicate destinations, symlink/reparse entries, and non-regular files. Bound manifest size, entry count, and decompressed bytes using the inventory; reject corruption or expansion beyond the recorded limit. Production archive limits must not be applied as new limits on coverage collection: an oversized snapshot is skipped with a warning, while required coverage artifacts remain governed by their existing contract.

Every automatic deletion requires a valid store marker, known schema, current filesystem identity, and an exclusive candidate lease. A stale PID or elapsed timestamp alone never proves inactivity. Unknown state is preserved. Pins and active leases win over a budget target. Metadata-only lock contention skips optional maintenance; it never waits indefinitely or serializes distinct test runs.

Crashes can leave unpublished staging data and interrupted output registrations. A subsequent maintenance pass can remove only manager-owned staging under a matching schema and proven-unused lease. It cannot reinterpret incomplete coverage as successful history. Keep registry, warning state, receipts, and crash remnants bounded, not just XML. If no safe maintenance can complete, report the failure and observed growth.

## Acceptance evidence required before shipping

1. **Quality equivalence:** the existing full-solution gate and packed collector semantic proof pass unchanged; a deliberately failing gate still fails and writes its reports. Compare line/branch facts and original-byte hashes before/after compression.
2. **Upgrade path:** run an installed old/new tool against a representative consumer fixture, with the same commands and no setup changes. Verify current paths, project manifests, staged merge inputs, JUnit, logs, timings, and Evidence claims remain usable. Exercise collector and explicit MSBuild compatibility paths.
3. **Agent repetition:** execute at least 100 synthetic runs across ten output/worktree identities, including failures and parallel operations. Eligible compressed history converges under an artificially small shared budget; current, pinned, unsupported, and unmanaged data remain unchanged and separately accounted for.
4. **Readers and writers:** prove a live gate/restore/pin prevents conflicting mutation, different outputs remain concurrent, a second same-output writer fails before cleanup, internal Evidence does not deadlock, and a simulated older writer is never mistaken for safe archive authority.
5. **Failure recovery:** exercise kill during staging/promotion, file replacement, read-only/full store, denied cleanup, corrupt/unknown manifests, low free space, stale registrations, cancelled scans, and decompression abuse. No secondary maintenance outcome masks the primary test/gate result.
6. **Consumer warnings:** an inherited enabled collector plus repeated GUID outputs triggers a useful warning automatically. Small healthy usage stays quiet apart from the short summary; repeated warnings throttle; major growth re-warns. Partial scans report lower bounds and failures, never zero usage. Assert stable structured diagnostics and exit-code preservation.
7. **Retention compatibility:** --no-clean and full-retention mode preserve promised raw artifacts; successful duplicate elimination preserves the canonical report and noncoverage attachments; failed normalization retains raw evidence. Restore reproduces archived bytes, pin failure reports no false protection, and metadata itself stays bounded.
8. **Cost:** measure cold/warm inspection, maintenance time, peak working space, bytes written, and peak memory on the consumer fixture. Enforce the stated routine budgets; report skipped maintenance honestly. The measured 94% compression ratio is motivating evidence, not a universal release threshold.

Use public commands and intentional internal seams, without reflection. Documentation, cross-links, formatting, introduced-warning resolution, and branch verification for new lifecycle paths are part of the feature. No implementation or runtime validation is claimed by this design.

### Section 1: Architecture Review

The existing linked coverage sources provide the right integration boundary. Add one private lifecycle coordinator with explicit archive, filesystem, inspection and diagnostic seams; do not create a public engine package or a daemon. A global registry is a capacity and discovery aid, never authority to remove current outputs. Its failure must therefore leave required coverage paths usable with a warning.

```text
CLI run/merge/gate ----+                       before: run -> XML -> gate
Evidence adapter -----+-> linked private core  after:  run -> canonical XML -> same gate
                              |                           |
                  output operation leases            producer inventory
                              |                           |
                   existing ownership guard <--- lifecycle coordinator
                                                     /       \
                                                scanner    archive store
                                                           verified gzip + JSON
```

At 10x load, unique current roots and pins grow while eligible history still has a shared target. At 100x, registry/inventory admission limits and the maintenance budget degrade optional management explicitly. No database, connection pool or remote availability dependency is introduced. This avoids turning the storage feature itself into a required test service.

### Section 2: Error & Rescue Map

Each optional failure returns a typed capability/diagnostic result; required output errors retain existing failure behavior. IOException and UnauthorizedAccessException are secondary only within optional operations, not blanket catches around collection. Cancellation of the caller remains cancellation; exhaustion of a private maintenance budget means a visible skipped snapshot, never a successful archive.

| Proposed codepath | Trigger / class | Rescue and user result | Required proof |
| --- | --- | --- | --- |
| ResolveStore | Invalid root, ArgumentException/NotSupportedException | Reject override for management; warn; no fallback history tree | malformed, linked, root, unsupported |
| RegisterRun | JSON/schema/size failure, JsonException/InvalidDataException | preserve unknown data, disable optional registration | corrupt/unknown/overflow |
| AcquireOperation | conflicting writer, IOException/lock-busy result | fail same-output writer before cleanup; different outputs proceed | actual two processes |


### Section 3: Security & Threat Model

The storage domain belongs to the local user and may contain test diagnostics, so create private directories/files and never upload contents or host paths into public Evidence claims. The important destructive boundary is filesystem identity: marker, schema, physical root and candidate lease must all hold at mutation time. Traversal, symlink/reparse redirection and archive expansion have high impact and are mitigated by existing regular-file/handle helpers plus explicit restore limits and adversarial tests. A same-user process can still run an older nonparticipating CLI; mixed-version tests must prove preservation/diagnosis rather than promise a lock that the older binary does not take.

No new credentials, SQL, HTTP routes or remote SDKs are needed. New command inputs (IDs, output paths, byte settings and enum-like strings) require validation before mutation, checked arithmetic and bounded diagnostic strings. Unknown metadata must not become a cleanup permission simply because it is under the store root.

### Section 4: Data Flow & Interaction Edge Cases

```text
INPUT -> VALIDATION -> TRANSFORM -> PERSIST -> OUTPUT
run   -> own/lease  -> collect   -> canonical -> existing readers
  nil solution/output -> existing validation failure, no cleanup
  empty XML -> failed normalization, keep raw evidence
  upstream test error -> failed outcome + actual produced-file inventory
snapshot -> inventory/identity -> stream+verify -> atomic archive -> retrievable history
  missing inventory/changed source -> no publication + history-miss diagnostic
  empty inventory -> explicit no-archive-needed result, never fabricate coverage
restore -> id/schema/path limits -> verify+extract -> fresh destination -> historical copy
  wrong type/traversal/duplicate/corrupt -> explicit failure; current untouched
```

Repeated maintain/pin/unpin calls need idempotent results, meaning a retry must produce the same protected state rather than duplicate storage. Ctrl-C leaves identifiable staging and retains caller cancellation. A stale root or changing list produces partial observation; a removed registration never authorizes deletion of a newly created directory at the same path.

```text
gate reader        replacement writer       archive evictor        invariant
acquire shared     try exclusive -> busy    no current candidate   current bytes remain
release            acquire -> snapshot     lease archive -> recheck
                   publish -> clean        only unpinned archive  no sole-source deletion

pin wins archive lease -> commit pin -> eviction rechecks and skips
eviction wins lease -> removes archive -> pin returns missing, never success
```

Both orders require controlled pause/release tests, not time-based sleeps. A same-output second writer fails before cleanup; the Evidence parent retains/reuses context through nested run and gate. External readers retain their existing replacement boundary and are not assumed to participate in these leases.

The Friday-night shipping test is an unchanged installed consumer run/gate/reader sequence followed by parallel replacements, byte restoration and a deliberately failing gate. Hostile QA replaces a file or pins an archive exactly between candidate selection and mutation. The chaos test kills publication at every commit boundary, reopens the store and confirms there is neither a false completed archive nor an altered primary result. Use deterministic clocks, counters and barriers; avoid random timing and new external-service flakiness.

### Section 7: Performance Review

The three costly new paths are repository observation, archive compression/verification and explicit restore. Routine observation is bounded to one cumulative second/10,000 entries, routine maintenance to two seconds, with bounded streaming buffers and admission limits. These are proposed budgets, not measured p99 latency. Record actual cold/warm distributions and representative archive success rates before release; do not hide routine history misses behind a passing coverage gate. There is no ORM/database query or connection-pool impact.

### Section 8: Observability & Debuggability Review

The product's operational view is the existing command summary plus coverage storage inspection: current/history/protected/unmanaged bytes, last observation age/completeness, maintenance capability and one action. This is sufficient local observability without a telemetry backend or dashboard server. Stable diagnostics must distinguish history not saved, partial inspection, unsupported store, protected growth and pin/restore failure. Bounded receipts support explaining expiry; they cannot promise a forensic timeline after their own retention expires. The guide must include recovery for full/read-only/corrupt stores and emphasize that safe management may pause while coverage still runs.

### Section 9: Deployment & Rollout Review

```text
freeze consumer baseline + package reader contracts
 -> prove archive resource envelope -> coordinated CLI/private Evidence package
 -> installed old/new proof + native filesystem lanes + full coverage
 -> release defaults/docs -> separately verify real consumer adoption
rollback: stop new optional management -> install previous coordinated version
 -> leave new history/schema untouched -> existing current reports stay readable
```

A mixed old/new deployment has a real risk: an older writer ignores coordination and can change bytes behind a compatible-looking run manifest. Version and hash mismatches must disable historical publication rather than imply cooperation. Do not migrate arbitrary old output trees or force a shared schema downgrade. Rollback changes the local tool/package version; archive preservation and warnings must still be explainable after rollback.

### Section 10: Long-Term Trajectory Review

Reversibility is 4/5: current report contracts remain stable and archive schema can be ignored by older tools, but published diagnostics/options and retention promises become compatibility obligations. The main new debt is platform lock/filesystem code and the format/resource contract, paid for with native lanes and canonical documentation. Remote/team history stays a separately justified follow-up. The right next step is actual consumer adoption proof, not building a general artifact platform before evidence supports it.
