## Problem and evidence

Skoolit's normal local login needs a confidential client, exact loopback or approved tunnel callbacks, an optional Google broker and mappers, its existing named Keycloak data volume, and application-owned identities. Its generic realm setup should become a supported AppSurface capability. A healthy container or a public-client baseline subsequently changed by an application seed cannot establish that this configuration is ready.

## What this enables

A second application can declare a different local realm and retain its own account model while using the same startup guarantee: the intended generic configuration is verified before its seeds run. A failed restart explains which operation needs correction and preserves the existing data. Developers can continue editing read-only theme assets without restarting identity configuration.

## Decisions and alternatives

- **Select Approach B:** keep the existing finite worker executable, move its configuration/reconciliation execution core into the existing Aspire-free library, and leave resource graph, execution bindings and volume ownership in the AppHost adapter. This makes the packaged worker's dependencies explicit and keeps runtime web apps free of Aspire.
- **Reject Approach A:** extending reconciliation through the worker's current adapter reference gives a smaller initial diff but retains unnecessary AppHost coupling in its executable path.
- **Keep safe defaults:** public client, loopback callbacks, no broker and existing scaffold-user behavior. New identity capabilities require explicit options; the existing generated proof remains supported.
- **Keep the ownership boundary:** AppSurface owns supported generic managed fields and verification. Skoolit owns provider enablement/removal policy, credentials, application subjects/founders, database migrations and production authority. Seeds must preserve the verified generic fields as a supported consumer contract; AppSurface does not sandbox privileged host code.
- **Prove before freezing APIs:** neutral and Skoolit fixtures must establish ownership, credential custody, lifecycle and worker dependency closure before public names or platform support are committed. The provisional 1–2 human weeks / 3–4 agent-assisted working days is a new independent estimate of remaining #888 work, not its allocation from the issue's older combined #887/#888 estimate. #895 has since merged, and this estimate includes the newly explicit daemon-alias, credential-custody and worker-closure proofs. It supersedes the older estimate for #888 planning only, excludes owner/publication wait, and must be re-estimated after those proofs; it is not measured delivery performance.

## Contract and package boundary

`KeycloakDesiredConfiguration` is a proposed immutable, nonsecret snapshot for one AppHost run. It describes the supported realm defaults, client mode and identifier, exact issuer/authority, callbacks/logout destinations, approved origins, broker aliases, mapper declarations and managed-field policy. Initial generation, reconciliation, effective readback, challenge expectations and nonsecret OIDC projection use this same snapshot. A configuration change requires a new run.

Validation rejects null/empty/wrong-shaped/oversized data, duplicate identities, broad wildcard origins, unsupported settings and partial bindings before mutation. Callback and issuer rules distinguish exact approved HTTPS tunnel destinations from the local loopback defaults. Provider enablement, deletion and mapper semantics are explicit host choices; no generic default authorizes account provisioning or external-provider access.

The existing pure library owns validation, reconciliation operations and typed safe results without referencing Aspire. Reuse appropriate [failure/effect/recovery concepts](https://github.com/forge-trust/AppSurface/blob/f8c25bed/Auth/ForgeTrust.AppSurface.Auth.Keycloak/Models.cs), without mislabelling realm failures as security-recipe operations. Stable codes and final public type names are an engineering-design decision after feasibility. Do not create a second pure package or a general production controller.

The Aspire adapter snapshots options, owns the local lease and graph, and supplies execution bindings. The finite worker references the pure execution core instead of the Aspire adapter. `RealmReady()` remains lazy and cached per wrapper; `WithLocalSeed` remains an ordered finite-project API. A web host receives only its allowlisted nonsecret OIDC projection plus its separate secure client-credential binding.

## Lifecycle and readiness

Registration validates and constructs the graph without writing mutable import/bootstrap files. Immediately before the first such write or container start, acquire and persist ownership. The exact supported Aspire lifecycle hook must be demonstrated before committing the API.

The adapter is supported only for Aspire `Run` in `Development`, `Test` or `Testing`, with an explicit local-environment extension following the existing seed policy. Reject `Publish` and manifest-generation operations with a typed unsupported-operation failure before graph materialization, secret resolution, lease acquisition or bootstrap writes. Never emit a manifest pointing at an unwritten run-only import directory. This explicitly defines the local-proof adapter's boundary; the pure contracts grant no production mutation authority. Test both default and configured registration under rejected operations for zero effects.

This is an intentional registration-policy breaking change, including for the default overload: the current `AddCore` has no operation/environment guard. “Keep safe defaults” preserves the public-client/loopback/no-broker proof within supported local execution; it does not preserve previously unguarded publish or other-environment calls. Migration: guard local Keycloak registration with the existing Aspire Run-operation check before calling the adapter; publish hosts configure their external identity dependency separately. Hosts using another genuinely local environment name explicitly extend the local environment allowlist before registration; no allowlist entry enables Publish. Require maintainer acceptance and a coordinated release migration note for this break in Open Gate 1. Verify the unchanged default local proof, migrated Run-only registration, explicit local-name opt-in and zero-effect rejection cases before release.

```text
validate/freeze -> acquire lease and active marker -> stage safe bootstrap
  -> start owned Keycloak -> transport ready
  -> finite generic reconcile -> effective readback + authorization challenge
  -> required application seeds -> verified seed completion -> dependent web
```

The worker updates only declared managed fields. Unmanaged realm/client attributes and application identities remain untouched. Managed removal/disable is explicit and has repeat-start and config-change tests. An existing realm is reconciled through the supported admin operations; an import on disk alone is not effective-state evidence. No public-to-confidential conversion occurs after readiness.

Across new runs, public-to-confidential conversion of the same persisted client is supported before that run's readiness and requires an explicit confidential desired mode plus its required secret binding. Confidential-to-public is rejected unless an explicit downgrade policy is set alongside the public desired mode; default public settings alone never authorize a downgrade. An approved downgrade removes the web/worker's confidential binding, verifies effective public-client authentication settings and preserves realm, users and subjects. Dormant server-side credential data is neither exported nor claimed erased. Failed or unsupported transitions block startup with a correction to retain the existing mode or explicitly authorize the supported transition. Test fresh/repeat modes and both allowed and denied transitions without replacing the volume.

The generic worker has one 120-second execution budget, including its requests, waits, readback and backoff, with at most two transient retries delayed by 0.5s and 1s. Every operation uses cancellation and remaining time. Invalid configuration and authorization errors fail immediately. An unknown write outcome requires readback before another write; if masked credentials or other incomplete state cannot resolve the outcome, fail with an explicit recovery request rather than blindly retrying. This is not a 120-second promise for image pulls, overall AppHost startup or human login; transport scheduling and seed deadlines must be separately bounded in the feasibility resource graph and documented.

Readiness establishes effective nonsecret configuration and a valid authorization challenge. It does not establish successful user authentication or Google acceptance. The acceptance fixture performs an actual authorization-code exchange after its required seed has created the user, then checks exact issuer, callback/logout and mapper behavior. No password grant, extra client-credentials grant or demo identity is enabled to manufacture this evidence.

Permit explicit zero scaffold users only when the graph includes a required host identity seed. That seed owns deterministic subjects and founder/account mapping and verifies its own completion. Failed/cancelled/nonzero seeds block dependents; web also waits for required database migrations. The seed contract prohibits writes to generic client/broker/mapper fields after readiness. A seed receiving full administration rights can violate that contract: there is no claim of sandboxing or runtime prevention of arbitrary privileged writes. The adoption proof compares managed fields after the real required seeds complete, before accepting the normal web/login proof, and fails on drift; an adversarial seed must demonstrate that detection. A drifting consumer is unsupported until its seed is corrected; the generic worker does not silently reconcile after seeds to hide the violation.

## Persistent ownership and recovery

Add an explicit persistent volume name so adoption retains the existing volume and logical identities. Do not silently generate a replacement, reset data, rewrite accounts on page load or recommend volume deletion as recovery.

The default non-persistent mode uses fresh disposable container state and no persistent-volume lease or crash marker. Every run still atomically creates its own private import/bootstrap directory under a collision-resistant run ID; resource names and sibling worktrees cannot share that directory. Cleanup owns only that run's files. Existing port conflicts fail startup without reusing data. A nonblank explicit volume-name option selects persistent mode. Legacy `UsePersistentDataVolume=true` without a name retains the exact name that the existing supported Aspire `WithDataVolume()` naming path resolves, then takes the same lease as a named volume. Prove name equivalence and existing-volume reuse through supported APIs; if the old name cannot be resolved unambiguously before effects, fail with a request for that exact existing name rather than guess or create a replacement. Test disposable/disposable concurrency, legacy-to-explicit same-name restart and legacy/explicit contention. Blank explicit names are invalid.

One AppHost holds a nonblocking exclusive OS handle for the **physical volume**, independent of realm name, through its complete lifetime. Cooperating sibling worktrees for the same local OS user share one private stable application directory. Resolve supported local runtime aliases to the same daemon identity and volume name before taking the handle. Record the observed volume generation/creation identity to detect replacement, but never let generation changes bypass an active marker for the same name. For a missing volume, reserve that same name before creating it.

This is an explicit proposed amendment to #888 acceptance criterion 7, whose original key includes realm. A realm-qualified key permits two different realms to acquire separate handles for the same physical volume. The amended criterion excludes realm and normalizes daemon aliases. Record maintainer acceptance of this stricter exclusion domain in Open Gate 1 before API commitment; design approval alone does not rewrite the GitHub issue.

Fail before mutation on contention, an active crash marker, uncertain runtime/volume identity, unsupported locking/filesystem, remote/shared endpoint or a volume attached to unexpected workloads. A preflight attachment check is evidence about the current state, not an atomic fence against an administrator. Initial support is cooperative local ownership under one OS user and one proven local daemon; it provides no distributed or privileged-administrator exclusion.

Persist an opaque run/owner identifier and active marker durably before any import/container mutation. The private record contains only the safe identifiers needed to inspect recorded owned resources, no credentials or raw configuration. If handle acquisition or marker persistence is uncertain, start nothing. If startup fails after effects begin, perform owned teardown while still holding the handle. Write clean only after proving all owned workers, seeds and container stopped, then release. Unknown teardown leaves active state and an actionable failure.

A crash releases the OS handle but leaves the active marker. The next startup must block even if no process appears active. Recovery requires the operator to verify the recorded daemon/resources stopped and clear only that verified lease record. Never steal by timeout, terminate an unverified process or remove the volume. The proof must cover daemon aliases, different realm names, both startup orders, interruption before/after marker persistence and shutdown races. If supported Aspire APIs cannot prove stop-before-clean, return a feasibility failure and revised alternatives; do not weaken the ownership guarantee.

Use a stable lease directory under the platform local-application-data root, `AppSurface/Keycloak/leases/<canonical-key>/`, containing a persistent `owner.lock` handle file and a distinct `active.json` marker. The failure reports the resolved private record location, expected owner ID and recorded daemon/resource identities. The supported clearing action is a proposed typed recovery-only request on the existing AppHost options, `VerifyStoppedAndClear(expectedOwnerId)`, not a new CLI/dashboard. It acquires the same nonblocking handle, re-reads the exact expected owner and volume identity, verifies all recorded container/worker/seed identities stopped (including process-birth identity where needed), and clears only `active.json`. Mismatch, unverifiable liveness, contention or changed volume identity fails without clearing. It never unlinks `owner.lock`, starts workloads or continues normal startup. Return an explicit recovery-only success; the operator then removes that one-shot request and starts normally, which confirms marker absence under the handle before recording a fresh owner. Document the host's actual existing invocation/configuration wiring and this verification sequence; manual deletion without this guarded operation is unsupported.

## Secret custody and optional brokers

Desired state, ordinary configuration, generated imports, manifests, projection, evidence and logs contain no secret values. Bind admin/client/broker credentials through typed secret resources only at execution. Validate identity and secret metadata without resolving values during registration. Keep the web client's credential channel separate from worker administration and seed-specific credentials. Do not reuse the current example's local constant as the confidential binding design.

For a confidential client, the worker manages the client secret from the same single typed secret resource that feeds the web's separate secure channel. Capture that value once per run inside protected custody so delayed web startup cannot resolve a newer value than reconciliation; rotation requires a new run. Reject a different worker/web parameter identity before effects. The worker writes that managed secret and compares a credential-authorized admin readback with the captured value in constant time, without logging, exporting or placing either value in ordinary desired state. The upstream [client-secret readback API](https://www.keycloak.org/docs-api/latest/rest-api/#_get_adminrealmsrealmclientsclient_uuidclient_secret) is a documented mechanism, not proof for the pinned fixture: prove its exact-version permissions/value behavior. Masked, absent, unreadable or unequal readback blocks readiness with a sanitized credential-verification failure and a correction to the binding/read permission. This proves configured secret agreement, not successful end-user token exchange or external-provider acceptance; those remain separately observed. Static binding-pair validation precedes effects; execution values are checked before credential-dependent realm mutation.

The concrete transport is a feasibility gate, not an assumed benefit of a secret flag. Prove dashboard, child-process environment/arguments, serialization, crash, nested-exception and cleanup behavior. Prefer private process-scoped delivery without arguments or ordinary environment disclosure; if restricted private bootstrap material is necessary, define custody, owner-only access and cleanup before accepting it. Never place values in the design, fixture cards or released diagnostics. An unsupported secure path blocks that platform instead of silently falling back to an ordinary variable.

Preserve the host's Google states: no pair means no broker; a partial pair fails before mutation; a full pair enables only declared broker/mappers; explicit disable follows the host's chosen managed disable/removal policy. Existing disabled/provider-absent resources are reconciled according to that explicit policy, not guessed from missing credentials. Masked secret readback does not prove Google accepted it. Automated Google proof stops at the provider redirect; real human-provider acceptance is recorded separately. Google identity grants no Gmail/Calendar authorization.

## Failures and developer feedback

SDK callers receive typed failures; AppHost resources show failure; executables/scripts use safe stderr and nonzero exit. Each failure names a stable code, operation, safe field/alias and concrete correction or precise operator request. Partial/uncertain failures include side-effect state, recovery class, bounded retry metadata, safe version context and correlation ID. Sanitize and bound nested causes; retain no raw admin response or secret-bearing provider error. Automation never prompts for input.

Cover validation, lease acquisition/recovery, reconciliation/auth, readback/challenge, required seed, worker payload and shutdown failures. The correction must preserve existing data. Document the first useful action and how to confirm recovery, rather than merely telling the developer to inspect logs.
