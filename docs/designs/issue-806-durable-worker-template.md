## Problem and intended outcome

A first Durable adopter currently assembles packages, typed Work, provider registration, PostgreSQL privileges and schema setup, authentication, health routes, telemetry, and tests. The [adoption evidence](../../Durable/evidence/executable-contract-adoption.md) records repeated composition across Skoolit's worker lanes and explicitly leaves real time to first completion unmeasured. A compiled sample or an accepted request is insufficient evidence that the worker can execute safely.

Publish `ForgeTrust.AppSurface.Durable.Templates` with the short name `appsurface-durable-worker`. It creates a small application-owned ASP.NET Core host and test project. Three commands install it, generate the solution, and prove one authenticated activation produces persisted terminal Work, a readiness transition, and an exported activity without a source checkout:

```console
dotnet new install ForgeTrust.AppSurface.Durable.Templates@<version>
dotnet new appsurface-durable-worker -n FirstDurableWorker
dotnet test FirstDurableWorker --filter FullyQualifiedName~FirstDurableWork --logger "console;verbosity=detailed"
```

The proof requires .NET 10 and a running Docker daemon. With NuGet artifacts and the pinned PostgreSQL image cached, it is the primed path; it is never described as a zero-prerequisite cold start. `<version>` is an explicit released version, including the prerelease suffix when applicable. The supported installation separator is `@`, as documented by [Microsoft's installation reference](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-new-install).

The useful capability is a reproducible installation certificate: a developer can distinguish a working Durable composition from a project that merely compiles, then replace the sample Work while retaining visible host decisions. No new runtime, scheduler, installer, feed, or deployment service is created.

## Host behavior and security

### Passive composition and data sources

Register typed Work, the PostgreSQL provider, `AddDurableExternalActivation()`, and host telemetry. Do not call `AddWorkerHost()` or create another background execution authority. The host receives only distinct dispatcher/runtime connection settings and the explicitly provisioned StoreId/epoch settings; provisioning/owner credentials never enter its runtime graph. The dispatcher is the `work_only` manifest role and is used only for payload-free global discovery. The runtime role owns the existing scoped mutation/heartbeat operations. Prove data-source routing and denied dispatcher reads through real restricted-role integration tests, not just DI type names.

Normal startup uses published read-only schema/epoch validation and fails with safe, actionable configuration diagnostics. It does not initialize the store or epoch, change roles, rotate credentials, or apply migrations. Keep complete reviewed-manifest preflight as an explicit operator action, documented through the [schema-11 deployment guide](../../Durable/heartbeat-retention-operations.md); normal health compatibility does not claim the full privilege/deployment certificate.

### Authentication and direct routes

Every activation route requires the named `ActivationAuthorization` policy and an authenticated principal independently of that policy's other requirements. Production composition supplies a real application-selected scheme and policy. Validate that the policy exists and its selected scheme(s), or the applicable default, resolve before listening. Missing/unregistered scheme or missing policy fails startup with the exact composition location and canonical start-page link, before attempting database access. Registration validates presence, not arbitrary identity-provider security; the application owns claim/permission meaning.

The built-in sample bearer scheme is enabled only for `Development` with a nonempty `APPSURFACE_TEMPLATE_ACTIVATION_TOKEN`. It has no default value, compares a bounded token in fixed time, rejects malformed/missing/wrong tokens, and is rejected in every other environment even if a production scheme is configured. The Development path without a token fails closed. The fixture injects a random per-run value through the same configuration key on its own builder, avoiding shared process-environment mutation. The generated .NET caller sends that value and never prints it. Production hosts configure their scheme in the documented composition seam, with the sample token unset.

Preserve #804's empty-body wake contract, bounded safe JSON projections, auth-before-body/service ordering, and all ten activation outcome mappings. Do not infer terminal Work state from `Completed`, which reports a completed pump invocation and aggregate. Unknown-length body handling is subject to host request/body-read deadlines; an idle sender must not wait forever before the service budget starts.

| Route | Meaning |
| --- | --- |
| `GET /live` | HTTP 200 for the running process, including a store outage; no database read. |
| `GET /compatibility` | HTTP 200 only when canonical activation compatibility allows an attempt; `NotStarted` may qualify. |
| `GET /ready` | HTTP 200 only for `Healthy`/`IsReady`; `NotStarted`, `Stale`, `Draining`, `Incompatible`, and `Unavailable` remain 503. |
| `POST /private/durable/activate` | Authorized empty wake invoking `IDurableExternalActivationService` once with a Work-only pump request; safe outcome projection follows the reference contract. |

Start with the reference host's explicit defaults: 32 maximum items, two-second pump discovery budget, ten-second activation-service request budget. Document that the service budget is cooperative and distinct from ingress/body deadlines, executor behavior, and terminal bookkeeping/cleanup. It does not guarantee preemption of an arbitrary executor. The [activation contract](https://github.com/forge-trust/AppSurface/blob/416b30919e6c4d03b634d9d3fe558884b02f0b91/Durable/external-activation-v1.md) remains canonical for exact result fields, statuses, cancellation classification, and recovery actions.

`FirstDurableWork` performs the following ordered assertions through the generated application:

1. Announce that the disposable fixture owns provisioning, then establish an unchanged schema/role catalog before ordinary host startup. Verify startup neither changes that catalog nor starts a Durable worker loop.
2. Before any runtime heartbeat, assert `/live` is 200, `/compatibility` reports compatible `NotStarted`, and `/ready` is 503 with `isReady=false`.
3. Accept one typed Work request through the separate producer/client path and assert the persisted record is Ready. Send missing/wrong-token requests and prove they cannot invoke health/admission or execute Work.
4. Send the per-run bearer token with an empty HTTP wake. Assert the authorized route's exact returned outcome/aggregate and inspect the persisted Work/result until its terminal success is proven; never equate acceptance or a zero-count pump with completion.
5. Assert the heartbeat makes `/ready` report `Healthy`, flush the SDK provider, and inspect the exported activation activity. Recheck schema, StoreId, epoch, and role catalog invariants.
6. Emit each checkpoint only after its associated assertion passes:

```text
[first-work] authorized activation accepted
[first-work] Work reached terminal completion
[first-work] readiness: NotStarted -> Healthy
[first-work] exported appsurface.durable.runtime.activation
```

The integration test is tagged `PostgreSql`; its fully qualified name includes `FirstDurableWork`. A missing Docker daemon causes a quick failed test with the prerequisite, exact retry command, and canonical local-proof link. It never becomes a skip or false PASS. Non-Docker CI uses the explicit opposite category filter. The generated caller and checks are .NET code on all platforms.
