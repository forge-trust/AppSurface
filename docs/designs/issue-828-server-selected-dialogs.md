## Problem and appeal

A server response to Save or Check status can update a target far from the control the user pressed. The result is technically on the page but easy to miss. RazorWire should let the server explicitly present a response in an accessible dialog, including a form that can validate, submit again, update the page, and close on a later server response. The same controller endpoint must provide a usable full page when JavaScript is unavailable.

The useful capability is a server-composed interaction: one response can update a page region and present a focused result without every application building a dialog shell, focus manager, and Turbo action. The response remains app-owned Razor content inside a small RazorWire-owned shell. This is an option for any response; it is never inferred from the presence of a form or a particular status code.

## Decisions and premises

- **Explicit presentation.** Only `OpenDialog*` opens a dialog. `ReplaceDialog*` changes the one pending dialog in the builder buffer before it is sent. `CloseDialog()` is an explicit server command. Routine acknowledgements may use inline feedback; this is guidance, not a restriction.
- **One shell and one buffered dialog action.** RazorWire creates one native `<dialog>` on demand. An accepted open replaces an existing shell across responses; dialogs do not stack. The builder holds at most one pending open or close action. Open, replace, and close mutate that slot; one response emits at most one final dialog stream frame. The package supplies the heading, Close control, focus behavior, and scoped themeable CSS. The application supplies the body and its form markup.
- **Turbo transport.** GET links opt into streams with `data-turbo-stream`; non-GET Turbo forms already request streams. Open and close do not navigate or add history entries. Server-pushed dialogs are deferred.
- **Flow ownership.** A response must not replace or close a dialog opened by a later interaction. A response from a form inside a dialog must not change a dialog that has since been replaced or dismissed.
- **Fallback.** The same GET or POST endpoint chooses an HTML page when the request does not accept Turbo Streams. No raw stream markup is served as the no-JavaScript page.
- **Distribution.** This ships in the existing `ForgeTrust.RazorWire` package and its built assets. The package is not yet publicly published as v0.1; use the existing configured feed or source build and [MVC example](../../examples/razorwire-mvc/README.md) until that release path is live.

## Independent review

The independent `combo/sub` read agreed that native `<dialog>` and Turbo Streams provide the core primitives. It found a gap in the filed spec: builder order only orders actions in one response. If two requests finish out of order, an older response could otherwise replace or close the newer dialog. It recommended retaining the small stream API while defining request ownership and stale-response behavior before shipping forms.

## Alternatives considered

- **A, small stream extension:** add the proposed builder methods and let the last response processed win. Fastest to implement, but an older form result could alter a newer dialog.
- **B, flow-scoped stream extension (chosen):** retain the proposed builder methods and one shell; add explicit buffer-replacement variants, a public queued-dialog check, and request and flow metadata to reject stale dialog actions and stale updates within dialog content. This solves the interaction race without a new response type or multiple dialog frames per response.
- **C, first-class dialog result:** make a result type own stream/HTML negotiation and flow identity. It reduces endpoint branching but creates a larger public API before the stream extension has been exercised.

## Public server API

Keep the filed [#828](https://github.com/forge-trust/AppSurface/issues/828) builder shape and add explicit replacement variants:

```csharp
OpenDialog(string title, string? message)
OpenDialogPartial(string title, string viewName, object? model = null)
OpenDialogComponent<T>(string title, object? arguments = null)
OpenDialogComponent(string title, string componentName, object? arguments = null)
ReplaceDialog(string title, string? message)
ReplaceDialogPartial(string title, string viewName, object? model = null)
ReplaceDialogComponent<T>(string title, object? arguments = null)
ReplaceDialogComponent(string title, string componentName, object? arguments = null)
CloseDialog()
bool HasActiveDialog { get; }
```

The methods return `RazorWireStreamBuilder` and can be combined with ordinary page actions. `HasActiveDialog` is a read-only public property: it is true exactly when this builder currently has a pending open payload, and false initially or after a queued close. It reports the response buffer, not whether a browser currently shows a dialog. App code may check it before choosing `OpenDialog*` or `ReplaceDialog*`. A second `OpenDialog*` while one is pending throws immediately; callers must use `ReplaceDialog*` for an explicit replacement. `ReplaceDialog*` requires a pending open and overwrites its title, body, and rendering source in the same slot. Repeated replace calls keep only the last payload. `CloseDialog()` changes the slot to close, so `HasActiveDialog` becomes false; a later `OpenDialog*` changes it back to open. Thus open-then-close emits only a close, and close-then-open emits only an open. Repeated close calls are idempotent. The final `BuildResult()` or `RenderAsync(...)` snapshot emits at most one dialog stream action, and overwritten partials or components are not rendered. Ordinary page actions keep their relative order and the dialog slot stays at the position of the first dialog operation; an action between dialog mutations executes after the final open or close at that slot. If it targets inside the shell after a final open, it must target the final dialog body. `title` must be nonblank. `message` is plain text and HTML-encoded; `null` means an empty body. Partials and components use MVC rendering, with the existing trusted Razor markup boundary. The partial/component variants require `BuildResult()` or `RenderAsync(...)`. There is no raw HTML dialog overload. The caller returns an ordinary `RazorWireStreamResult` from `BuildResult()` for request-scoped responses; the app does not pass request IDs to these methods.

`Build()` has no request context. If a builder contains any dialog command, it fails with a clear error directing the caller to `BuildResult()` or `RenderAsync(viewContext)`; it must not emit an unscoped command. Raw `RazorWireStreamResult(string)` and arbitrary manually rendered streams are outside the scoped-dialog guarantee. `IRazorWireStreamHub` replay and live-push commands remain out of scope.

## Flow protocol and browser behavior

The client assigns each supported Turbo request a unique opaque request token and a monotonic tab-local start order in `turbo:before-fetch-request`. This covers stream GET links and forms, including forms inside the dialog. The token is sent in a bounded request header. On each accepted new flow, the browser creates a separate opaque flow token using `crypto.randomUUID()`, stores it in RazorWire's shell state, and binds it to the dialog body. When a fetch originates from a control or form inside that shell, the request hook sends the current flow token in a second bounded header; the server echoes that origin token on scoped stream actions. An outside request carries no origin flow token. These values are UI correlation metadata, never authorization or idempotency keys. Server rendering validates header syntax and encodes the echoed tokens as attributes; malformed or absent metadata makes a dialog command invalid rather than silently unscoped. A normal page stream without dialog commands continues to work without the metadata.

An accepted final open creates a new flow and replaces any existing content in the one shell. An in-dialog form carries that flow for validation or close; ordinary scoped stream updates can redraw fields and errors without replacing the dialog. `ReplaceDialog*` changes only the unsent builder payload: `OpenDialog(A).ReplaceDialog(B)` emits one open action containing B, and A never creates a browser flow. `CloseDialog().OpenDialog(B)` likewise emits only B's open action; the old on-screen dialog is replaced without an intermediate close. `OpenDialog(A).CloseDialog()` emits only a close, so A never appears. A final close action closes the eligible live dialog; a close with none open has no visible effect. An inside close applies only to its matching live flow. An outside close applies only when its request started after the current flow's opener.

The browser keeps the latest accepted flow order and tombstones for dismissed or replaced flows. For the response's sole dialog action it checks the request token and original ownership: an outside response started before the current or last dismissed flow is stale; an inside response whose origin token is no longer live is stale. For concurrent submissions inside one flow, only the most recently started submission is eligible. An accepted open generates and stores one fresh flow token. An accepted close tombstones the eligible flow. User dismissal tombstones it immediately, so later validation cannot resurrect it. The request token is one-use for the dialog action; a repeated, unknown, or malformed token is ignored safely. Navigation destroys the shell state, and `turbo:before-cache` closes and clears it so Turbo cannot restore an open dialog.

All RazorWire builder actions emitted for an in-dialog form response carry flow metadata. Before the final open slot, a dialog-target action refers to the request's origin flow; after that slot, it refers to the new flow created by the one emitted open. After a final close action, no dialog-target action is eligible. Before rendering an action aimed at a node inside the dialog, the runtime checks this resolved flow and request order; a stale action is skipped even if a later dialog happens to contain the same target ID. Ordinary actions aimed at page targets outside the dialog still execute, including those accompanying an ignored dialog command. This is a **presentation** guarantee: it does not undo a server mutation or impose ordering on concurrent saves. Applications with conflicting writes still need server-side concurrency or idempotency rules. The browser must prove the installed Turbo version exposes the required fetch and pre-render hooks for both GET streams and form responses; if it cannot, revise the protocol before implementation rather than weakening the guarantee.

Use the existing `RazorWireStreamResult` request context to render metadata and preserve the final dialog slot among page actions. Its parallel rendering preserves output order, but the browser must prove or enforce application order when a page action targets the new dialog. Add tests for a slow partial followed by `CloseDialog()` and for open-then-replace with intervening page actions. Do not infer request ownership from a global variable while separate responses are being processed.

### Interaction example

1. A status GET starts; request `A` is assigned order 1. A second status GET starts; request `B` gets order 2.
2. `B` opens a dialog first. The shell shows B's title and content and remembers B's flow.
3. `A` arrives later with an open command. RazorWire ignores A's dialog command; B remains visible.
4. A form in B's dialog submits with B's flow token. A `422` handled validation stream updates errors inside B and leaves B open. A later successful response updates the page and calls `CloseDialog()`, which closes B.
5. If the user dismissed B, or a newer outside request replaced it before that form response arrived, the old validation and close are ignored. Page-target updates remain eligible to render.
6. A later response may call `OpenDialogPartial(A).ReplaceDialogPartial(B)`; the builder emits one open frame containing B, and B is the only active dialog. `CloseDialog().OpenDialogPartial(B)` also emits one final open frame. A second plain open while a dialog is pending fails immediately; `HasActiveDialog` lets the controller check the pending buffer state.

## Dialog shell and form states

The shell has a visible heading bound to the dialog's accessible name, a visible Close button, a focusable content region, and scoped CSS variables for surface, text, border, spacing, size, backdrop, and focus ring. It uses `showModal()` for browser modal behavior. Focus moves to the first meaningful form control when present, otherwise the heading or content; on dismissal it returns to the connected initiating control, otherwise a safe page landmark. Escape and Close dismiss immediately. An accepted open changes content without an intermediate focus jump to the old trigger; replacing the unsent buffer payload causes no intermediate browser dialog. Backdrop clicks do not dismiss by default. The shell fits a narrow viewport and respects reduced motion. The package does not style app-authored form fields.

An in-dialog form has these visible states: submitting (retain the dialog and its Turbo pending state; coordinate any added indicator with [#827 form loading feedback](https://github.com/forge-trust/AppSurface/issues/827)), handled `422` validation (retain form and errors), unhandled failure (use the existing [form-local failure fallback](../../Web/ForgeTrust.RazorWire/Docs/form-failures.md) inside the dialog), and success (remain open unless the response explicitly closes it). On an accepted validation update, focus the first invalid field or error summary according to the existing form contract; do not send focus back to the page. Dismissal while a request is pending does not cancel a server mutation. Reopening requires a new explicit open response.

The approved low-fidelity [interaction sketch](./issue-828-dialog-wireframe.png) shows the trigger, server-selected dialog, and handled validation state. It illustrates the shell and focus flow; host applications own their own typography, colors, and form layout.

## Open risks and next steps

- The request-correlation hooks must be verified against the bundled Turbo version. The flow guarantee depends on GET stream requests and form submissions carrying correlation metadata through response rendering, and on page actions targeting the new dialog executing after the final open slot. Buffer replacement emits no intermediate dialog frame, so there is no A-to-B browser transition to coordinate.
- An ordinary page action from a stale response may still reflect a conflicting server write. That is an application concurrency concern and should be made explicit in the guide.
- The initial issue estimates 24–31 hours for an unscoped shell. Flow correlation, race tests, and docs add work; re-estimate after the protocol spike rather than inheriting that estimate.

Build sequence: (1) prove Turbo request/header and stream pre-render hooks with a controlled out-of-order integration test; (2) implement server metadata and command serialization; (3) implement one shell, flow gating, focus, cache cleanup, and form behavior; (4) add MVC examples, no-JavaScript branches, tests, and documentation; (5) run packaging and coverage gates and trial one real consumer flow.

Findings below are retained from the last completed review; the current document remains unreviewed.

### R1-1 — consistency

**Problem**

> The stale-flow rule can reject command chains the design explicitly allows. A form response inside the old flow may run CloseDialog().OpenDialog*(), and OpenDialog*.ReplaceDialog*() is also declared valid. After the first command changes or tombstones that flow, the later command still appears to claim the request's original flow, which the general rule says is no longer live. The document does not say whether eligibility is checked against the response's initial state or re-evaluated for each command.

**Remedy**

> Define response-level eligibility and ordered state transitions so a response is first accepted or rejected against its initial ownership, then its commands execute in sequence with subsequent commands bound to flows created or retained earlier in that response. A stale response must still be unable to affect a newer dialog.

### R1-2 — completeness

**Problem**

> The protocol requires opaque flow tokens on requests originating inside a dialog, but does not define how a fresh token is created, placed on the shell, or propagated to those requests. A request token alone cannot distinguish multiple new flows opened by separate OpenDialog* commands in one response, a sequence the builder permits.

**Remedy**

> Specify flow-token creation and propagation, including a distinct token for each accepted new flow, how the token reaches requests from that dialog, and whether each replace operation retains the current flow or starts a new one in both same-response and later-response cases.
