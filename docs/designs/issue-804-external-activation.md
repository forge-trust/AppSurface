## Problem and useful outcome

The [pinned adopter evidence](../../Durable/evidence/executable-contract-adoption.md) found repeated activation and health decisions across seven downstream lanes. The existing [PostgreSQL example](../../examples/durable-postgresql/README.md) demonstrates local composition and hosted execution, but does not give an adopter a complete passive external-activation host with authorization, separate deadlines, outcome mapping, and exported telemetry.

The useful result is one runnable proof: a compatible `NotStarted` runtime accepts an authorized, payload-free wake, attempts one provider-admitted pass, completes real typed Work, becomes `Healthy`, and exports the activation activity. A future scheduler, webhook, or CLI can consume the same service without acquiring HTTP dependencies or a second execution protocol. The design phrase remains: “Define the Work once, map the host once, and prove the lifecycle once.”

Doing nothing leaves each host to reconstruct cancellation and failure policy and leaves the exporter claim unproved. This design does not claim measured onboarding speed or cold-start improvement; the [template case #806](https://github.com/forge-trust/AppSurface/issues/806) owns those clocks.

## Agreed premises and decisions

- Keep activation contracts, service, and registration in the existing [Durable.Provider package](../../Durable/ForgeTrust.AppSurface.Durable.Provider/README.md). Its existing transitive graph is intentional; no contracts-only package is introduced.
- Use **approach B**, a small internal per-invocation object owning its clock, cancellation sources, invocation phase, and activity. Centralize validated result mapping so every exit has the same rules. The object is an observation lifecycle, not provider admission or persisted execution state.
- Preserve the parent's public shape, outcome numbers, cancellation precedence, and safe failure mapping. One successful precheck permits exactly one `IDurableRuntimePumpAdmission.TryRunOnceAsync` invocation. Expected precheck rejection permits zero calls. No queue, retry loop, service semaphore, cached readiness gate, or legacy-pump fallback is added.
- Keep routes, HTTP status/body, authentication, authorization, deployment enablement, and application preparation/cleanup host-owned. Wake messages contain no Work payload, identity, lane, or caller-selected pump limits.
- Explicitly validate the reference host before listening. This qualifies the parent's unconditional “when the service provider is built” wording: the package supplies a constructor-visible dependency graph; the host enables validation and resolves the service. An `IServiceCollection` extension cannot make arbitrary containers validate opaque factories.
- Deliver service, host, complete failure/race proofs, packed-consumer execution, API documentation, and release guidance together. The later [ASP.NET adapter case #805](https://github.com/forge-trust/AppSurface/issues/805) consumes these types and this service unchanged.

**Alternative ruled out:** A, one compact `ActivateAsync` method with local state, would cover the same behavior with fewer internal files; B was selected because clock, phase, and activity ownership stay visible as the failure matrix evolves.

## Public API and registration

The four public contract types have the exact names, members, constructor argument order, and enum values in the [normative parent contract](durable-executable-contract-adoption-rail.md#normative-external-activation-flow):

| Type | Contract |
| --- | --- |
| `DurableExternalActivationRequest` | `PumpRequest`, `RequestBudget`; explicit validated constructor, sealed record with get-only properties. No request-budget default. |
| `DurableExternalActivationOutcomeKind` | `Unavailable=0`, `Incompatible=1`, `Draining=2`, `Busy=3`, `CanceledBeforeAdmission=4`, `RequestBudgetExceeded=5`, `Completed=6`, `ActivationFailed=7`, `PumpCanceled=8`, `PumpFailed=9`. |
| `DurableExternalActivationResult` | Constructor `(kind, observedHealthState, problemCode, pumpResult)`; sealed record, get-only properties; impossible combinations rejected before use. |
| `IDurableExternalActivationService` | `ValueTask<DurableExternalActivationResult> ActivateAsync(DurableExternalActivationRequest request, CancellationToken callerCancellation = default)`. |

`PumpRequest` is non-null and preserved by reference. `RequestBudget` must be positive and no greater than `TimeSpan.FromMilliseconds(uint.MaxValue - 1)`; zero, negative, infinite, and larger values are constructor errors. This is the [pinned .NET 10 timer bound](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/Threading/CancellationTokenSource.cs), not a relation to the pump budget. Sub-millisecond timer precision is platform-dependent and gives no minimum execution entitlement. Null service requests fail as argument errors, outside operational failure mapping.

`AddDurableExternalActivation()` returns the same service collection and uses repeat-safe `TryAdd` registration for the singleton service and `TimeProvider.System`. Existing host clock/service registrations win; provider health and pump registration may occur before or after it. Supply standard logging registration without imposing sinks or levels. Use the process-shared canonical `ActivitySource` directly and never dispose it or replace a host's arbitrary `ActivitySource` service.

The implementation constructor exposes `IDurableRuntimeHealth`, `IDurableRuntimePumpAdmission`, `TimeProvider`, and `ILogger<...>` to DI. Registration constructs no service provider, opens no database connection, applies no migration, starts no timer, maps no route, and installs no worker/background loop. Activation state is per-call; health/pump dependencies must meet their published concurrency/lifetime contracts. A host using the default service needs both required interfaces; it fails at graph validation or resolution if either is absent.

The reference host explicitly enables `ValidateOnBuild` and `ValidateScopes` in every environment, then resolves `IDurableExternalActivationService` before starting to listen. Tests distinguish missing constructor dependencies caught at build from a broken factory caught at resolution. The same guidance applies to custom containers through their own validation facilities. [.NET 10 DI validation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.DependencyInjection/src/ServiceProvider.cs) is conditional and does not execute opaque factory bodies at build.

## Invocation lifecycle and precedence

```text
ActivateAsync entry: capture clock, create invocation/activity
  -> check caller/budget cancellation
  -> health read using linked caller/budget token
  -> recheck cancellation, classify current health observation
  -> eligible: recheck cancellation, mark PumpInvoked
  -> exactly one TryRunOnceAsync using linked token
  -> preserve returned attempt or classify exception by phase
  -> write terminal safe tags, dispose activity and cancellation sources
```

The entry timestamp uses `TimeProvider` monotonic timestamps. Timer construction subtracts elapsed setup time from the original budget; setup does not reset the clock. No asynchronous logging/export flush occurs on the service path. Once the budget is elapsed, its cancellation source is treated as canceled even if timer delivery is delayed. The host's own clock/identity is not sent to the activity.

Internal states are `PreAdmission`, `PumpInvoked`, and `Completed`. Mark `PumpInvoked` atomically immediately before calling the admission interface. Cancellation callbacks signal sources; they do not mutate phase or construct a second result. The mark denotes invocation, not successful provider admission or a claim. Cancellation arriving after the final precheck and boundary follows the post-invocation rule even if the provider never enters application execution.

Before any operational pre-admission return, check caller cancellation first and budget second. Caller cancellation wins if both have fired at the classification point. It maps to `CanceledBeforeAdmission`; budget alone maps to `RequestBudgetExceeded`. This includes cancellation before entry, during health observation, after a health read, and immediately before the invocation boundary. A health reader that ignores cancellation must still be checked after return.

After `PumpInvoked`, an `OperationCanceledException` with either source canceled maps only to `PumpCanceled`. An unrelated `OperationCanceledException`, with neither source canceled, maps to `ActivationFailed/ASDUR407` before invocation or `PumpFailed/ASDUR407` after it. Do not classify from exception message or exception-token identity. A non-cancellation exception stays a mapped failure even when a cancellation source also happens to be signaled.

If the admission call returns `Completed`, preserve the exact `DurableRuntimePumpResult` reference, counts, elapsed time, next due time, and `HasMore`; do not check caller cancellation again. The provider already owns completion and bounded non-caller-cancelable terminal bookkeeping. A returned expected non-completed attempt is also mapped from that authoritative return, rather than rewritten by a subsequent token check. A bookkeeping exception remains `PumpFailed`; it is not successful completion. This service does not change the existing PostgreSQL pass state machine or the legacy pump projection.

Request budgets are cooperative cancellation deadlines. Never use `Task.WhenAny`, `WaitAsync`, or fire-and-forget pumping to return while an ignored cancellation leaves the invocation running. Provider execution/finalization may outlast a request budget; infrastructure must allow its own execution and cleanup bounds. An HTTP disconnect or missing response establishes no truth about external effects. Read [durable Work state and typed exits](../../Durable/work-protocol-v1.md) for that truth.

## Closed outcome and validation matrix

After a successful health read, retain its defined `State` as `ObservedHealthState`. Before one succeeds, it is null. Reject undefined outcome/health enums and every unlisted code or contradictory result combination. Strings use exact ordinal canonical spelling. Only `Completed` has a pump result, which is required; all other kinds require null.

| Observation | Result kind | Required/allowed problem code |
| --- | --- | --- |
| Health `Unavailable` | `Unavailable` | Required `ASDUR103`; observed state must be `Unavailable`. |
| Health `Incompatible`, or observed flags make `CanEnableActivation` false | `Incompatible` | Required observed `ASDUR108` or `ASDUR400`–`ASDUR403`; observed state is non-null and not `Unavailable`. |
| Compatible health `Draining` | `Draining` | None; observed state must be `Draining`. |
| Compatible `NotStarted`, `Healthy`, or `Stale` | Continue to authoritative admission | No service authorization inferred from that earlier observation. |
| Admission `Refused` | `Busy` | None, except retained stale `ASDUR404`/`ASDUR405`. |
| Admission `Completed` | `Completed` | None, except retained stale `ASDUR404`/`ASDUR405`; exact non-null pump result. |
| Admission `Unavailable` | `PumpFailed` | Required `ASDUR103`. |
| Admission `Incompatible` after the precheck | `PumpFailed` | Required admission `ASDUR108` or `ASDUR400`–`ASDUR403`. |
| Pre-invocation caller/budget cancellation | `CanceledBeforeAdmission` / `RequestBudgetExceeded` | None, except retained stale `ASDUR404`/`ASDUR405` after a successful read. |
| Post-invocation observed cancellation | `PumpCanceled` | None, except retained stale `ASDUR404`/`ASDUR405`. |
| Unexpected nonfatal failure, or unrelated cancellation exception | `ActivationFailed` before invocation / `PumpFailed` after | Required `ASDUR407`, replacing any stale observation code. |

`Busy`, `Completed`, `PumpCanceled`, and `PumpFailed` require a non-null observed state from the eligible set (`NotStarted`, `Healthy`, `Stale`). Pre-admission cancellation can retain any successfully read state, because cancellation takes precedence over a later health classification. `ActivationFailed` can have null or any defined observed state. Stale codes are legal only with observed `Stale`; they describe the observation, not a failed pass. An unknown/unexpected health code or inconsistent health evidence that cannot form a valid normative result fails closed as `ActivationFailed/ASDUR407` without invoking the pump. A false compatibility predicate never becomes permission to pump.

`ASDUR106` and `ASDUR109` remain item-level durable facts and contribute to the unchanged aggregate `Failed` count; do not select an item code to represent activation. Add the bounded provider-neutral `ASDUR407` diagnostic for unexpected activation orchestration failure, with phase/remediation guidance and no exception text in the result.

Catch cancellation separately. The mapped-failure filter excludes `StackOverflowException`, `OutOfMemoryException`, and `AccessViolationException`; those propagate. Safe structured service logs contain phase, outcome, observed state, and bounded code only. Never log request data, arbitrary provider values, or exception text through this service's diagnostic path. Logging cannot add another await between the final cancellation check and the invocation mark.

## Reference host

Add focused `examples/durable-external-activation/` and `examples/durable-external-activation.tests/` projects. Keep the existing hosted PostgreSQL example intact so adopters can compare the two hosting choices. Use a single typed Work definition with deterministic input/result and an executor that can be controlled by integration-test barriers. Accept test Work through the public client before activation; the wake endpoint itself never accepts/enqueues Work.

Register separate dispatcher/runtime data sources, typed Work, passive PostgreSQL storage, the activation service, and [AppSurface OpenTelemetry registration](../../Observability/ForgeTrust.AppSurface.Observability/README.md). Do not call `AddWorkerHost()`. Out-of-band disposable-database setup owns schema/epoch initialization and role provisioning using the [canonical PostgreSQL role recipe](https://github.com/forge-trust/AppSurface/blob/ecd81417065982d1803d26000fc7618a7c06108e/Durable/configure-postgresql-roles.sql); normal host build/startup performs no DDL.

| Example endpoint | Behavior |
| --- | --- |
| `GET /live` | 200 if the process handles the request; no Durable resolution or database query. |
| `GET /compatibility` | Current `GetAsync` assessment, 200 iff `CanEnableActivation`, otherwise 503. |
| `GET /ready` | Current assessment, 200 iff `IsReady`, otherwise 503. This is Durable control-plane readiness only. |
| `POST /private/durable/activate` | Require named policy `DurableActivation`; reject a nonempty wake body with 400; call the real service once with host-configured pump limits and budget. |

These paths and JSON/status shapes are sample-owned. Emit safe enum names, bounded code, and aggregate pump facts only; health responses do not serialize the full snapshot or worker identity. Compatibility does not automatically enable deployment, and readiness must not prevent routing the initial authorized activation to a compatible `NotStarted` runtime. An operator chooses the correct platform probe independently.

### Exact sample response contract

Successful and mapped-error JSON responses use `application/json`, UTF-8, the exact lower-camel-case field names below, and no additional fields. Every listed field is present, including explicit JSON `null` for nullable values; none is omitted. JSON member order and whitespace are insignificant. Enum values are case-sensitive names, never numbers. Tests compare complete parsed objects, field types, and content type rather than byte order. The sample projects DTOs explicitly instead of serializing provider objects.

`GET /live` returns status 200 with exactly `{"status":"Live"}` and does not resolve health, activation, or database services on the request path. Both health probes use this assessment body:

```json
{"outcome":"Assessment","observedHealthState":"NotStarted","canEnableActivation":true,"isReady":false,"problemCode":null}
```

For a valid assessment, substitute its exact defined state name, current `CanEnableActivation`/`IsReady` boolean values, and nullable canonical problem code. Only `ASDUR103`, `ASDUR108`, and `ASDUR400` through `ASDUR405` may appear in an assessment response. Validate the state/code evidence against the closed health classification above; unknown codes or contradictory evidence use the probe-failure path rather than leaking an arbitrary string. `/compatibility` selects 200 or 503 from `canEnableActivation`; `/ready` selects 200 or 503 from `isReady`. Thus the shown `NotStarted` assessment returns 200 for compatibility and 503 for readiness with the same body.

If `GetAsync` throws a nonfatal exception, either probe returns 503 with exactly `{"outcome":"ProbeFailed","observedHealthState":null,"canEnableActivation":null,"isReady":null,"problemCode":"ASDUR407"}`. This records failure to obtain an assessment and does not invent `Unavailable` health evidence. A provider-returned `Unavailable` assessment instead remains `Assessment` with state `Unavailable`, both booleans false, and `ASDUR103`. An `OperationCanceledException` when the request token is signaled returns 408, if a response can still be written, with exactly `{"outcome":"ProbeCanceled","observedHealthState":null,"canEnableActivation":null,"isReady":null,"problemCode":null}`; unrelated cancellation exceptions follow `ProbeFailed`. The same fatal-exception exclusions as the service propagate to the host error boundary, without a sample JSON guarantee. Probe failure logs use only the bounded outcome/code, never exception text or partial snapshot values. `/live` remains 200 through all health-reader failure cases because it never calls that dependency.

For an authorized activation with an empty body, every returned service result maps to this exact envelope: `{"outcome":"<kind>","observedHealthState":<state-or-null>,"problemCode":<code-or-null>,"pumpResult":<aggregate-or-null>}`. Substitute only the validated service values from the outcome matrix. `pumpResult` is JSON `null` for every kind except `Completed`; that kind contains exactly `discovered`, `claimed`, `processed`, `deferred`, and `failed` as nonnegative integer counts, `hasMore` as a boolean, `nextDueAtUtc` as a UTC ISO 8601 string with seven fractional digits and `Z` suffix or explicit `null`, and `elapsedTicks` as a nonnegative 64-bit integer in 100-nanosecond ticks. This projection preserves every aggregate fact without floating-point duration rounding. An empty completed pass with no next due time and zero elapsed duration is:

```json
{"outcome":"Completed","observedHealthState":"Healthy","problemCode":null,"pumpResult":{"discovered":0,"claimed":0,"processed":0,"deferred":0,"failed":0,"hasMore":false,"nextDueAtUtc":null,"elapsedTicks":0}}
```

| Activation outcome | HTTP status | Body |
| --- | --- | --- |
| `Unavailable` | 503 | Activation envelope, `Unavailable` state, `ASDUR103`, null aggregate. |
| `Incompatible` | 503 | Activation envelope with the validated observed state and compatibility code, null aggregate. |
| `Draining` | 503 | Activation envelope, `Draining` state, null code and aggregate. |
| `Busy` | 409 | Activation envelope with the validated observed state/code, null aggregate. |
| `CanceledBeforeAdmission` | 408 | Activation envelope with the validated nullable observed state/code, null aggregate. |
| `RequestBudgetExceeded` | 504 | Activation envelope with the validated nullable observed state/code, null aggregate. |
| `Completed` | 200 | Activation envelope with the exact projected aggregate, including when its `failed` count is positive. |
| `ActivationFailed` | 500 | Activation envelope with the validated nullable observed state, `ASDUR407`, null aggregate. |
| `PumpCanceled` | 408 | Activation envelope with the validated observed state/code, null aggregate. |
| `PumpFailed` | 503 for `ASDUR103`, `ASDUR108`, or `ASDUR400`–`ASDUR403`; otherwise 500 | Activation envelope with the validated observed state/code, null aggregate. |

Authentication/authorization runs before body validation or service resolution. The sample's 401 challenge and 403 forbid responses have zero body bytes; the development 401 includes `WWW-Authenticate: Bearer`. An authorized nonempty body returns 400 with exactly `{"error":"WakeBodyMustBeEmpty"}` and makes zero health/pump calls. Host-owned unexpected nonfatal endpoint failures outside a returned activation result return 500 with exactly `{"error":"HostFailure"}`, with no fabricated service outcome or exception detail. A disconnected client may receive no response at all, including for the cancellation cases. No automatic retry, blanket success, or external-effect claim follows any status.

The runnable local sample has an explicit Development-only bearer scheme requiring an injected token; no checked-in token or anonymous fallback. A missing token fails startup. Non-Development startup requires an explicitly supplied host authentication scheme/policy composition and otherwise fails before listening. Document that the development scheme is a local example; do not claim production OIDC or cloud authorization setup. Policy tests use intentional test identities to distinguish unauthenticated 401 from authenticated-without-permission 403; the real lifecycle/exporter test uses the sample's real authentication path.

Illustrative sample limits are Work-only pumping, 32 items, two-second discovery budget, and a separate ten-second service request budget. The infrastructure/request transport limit is host-configured and must leave room for the provider's independent execution/finalization bounds; no maximum response-time guarantee is inferred from these numbers. Pass the caller/transport token as `callerCancellation` and the service budget separately. Do not wrap both in one timeout token and pretend their identities survive. [ASP.NET request-timeout middleware](https://learn.microsoft.com/en-us/aspnet/core/performance/timeouts?view=aspnetcore-10.0) cancels `RequestAborted`; if it is used externally, its cancellation is documented as caller/transport cancellation from this service's perspective.

Application materialization, reconciliation, continuation, and cleanup stay outside the endpoint/service example. They may be shown later in an application-owned wrapper with separate bounded tokens; their failures must never be fabricated as pump outcomes.

## Telemetry contract version 1

Emit operation `appsurface.durable.runtime.activation`, with `ActivityKind` value `Internal`, through `AppSurfaceActivitySources.Instance` (`ForgeTrust.AppSurface`). One valid operational activation produces at most one activity, only when a listener enables it. Argument validation happens before activity creation. The service never builds or flushes a tracer provider.

| Exact activity tag | Value / omission rule |
| --- | --- |
| `appsurface.durable.activation.contract_version` | Integer `1`, always on an emitted activity. |
| `appsurface.durable.activation.phase` | `pre_admission`, `pump_invoked`, or `completed`; the final observation boundary, with `completed` only for a returned completed attempt. |
| `appsurface.durable.activation.outcome` | Exact enum name (`Completed`, etc.) for returned operational results. Omit for a propagated fatal exception because no operational result exists. |
| `appsurface.durable.activation.health_state` | Exact defined health-state name after a successful read; omit before one. |
| `appsurface.durable.activation.problem_code` | The final validated result code when present; otherwise omit, never use empty/null string sentinels. |

A fatal exception leaves the last phase and any observed health, omits outcome/problem code, and disposes the activity while propagating. For returned `ActivationFailed`/`PumpFailed`, set error status without a description. Do not record exception events, stack traces, payload, scope, Work/worker identity, route, principal, pump counts, or arbitrary baggage as activation attributes. Test the exact allowlist of tags and zero events, rather than checking only a few forbidden names. Host request spans/resources are separate telemetry and not this activation-contract assertion.

The host registers AppSurface observability with OTLP export disabled for deterministic local tests. A dedicated test-owned provider uses `Sdk.CreateTracerProviderBuilder()`, `.AddSource(AppSurfaceActivitySources.ActivitySourceName)`, `AlwaysOnSampler`, and an in-memory exporter. Invoke the real service through the authorized reference endpoint, await response/result completion, call `ForceFlush`, require successful flush, and inspect exporter-owned received activities. Dispose the provider and clear only the test's collection; isolate these process-global source-listener tests from parallel runs. The SDK configuration ensures a non-recorded HTTP parent does not silently drop the child; [OpenTelemetry's sampling guidance](https://github.com/open-telemetry/opentelemetry-dotnet/blob/main/docs/trace/customizing-the-sdk/README.md) distinguishes this deterministic test setting from normal production sampling.

Separately prove (1) no listener means no activity, (2) a listener observes the activity, and (3) an exporter receives it. The release proof must fail if the exporter is removed even if the route and listener tests pass. This proves external-activation instrumentation and standalone host listener/provider/exporter composition; native Work claim/execution spans remain [a separate observability case #685](https://github.com/forge-trust/AppSurface/issues/685).

```text

Operator/setup ------> schema/epoch + role recipe (out of band)
HTTP host -> auth -> empty-body guard -> ActivationService
                                      |-> per-call invocation -> clock/tokens/activity

                                      `-> IDurableRuntimePumpAdmission -> existing pump kernel
```

Happy path: accepted Work + authorized wake + eligible health → one admission attempt → exact aggregate → JSON.
