## Problem and decision

The mapped [Google Secret Manager provider](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerConfigProvider.cs) exposes synchronous configuration resolution and calls a synchronous Google client. On a cache miss, it currently queues `Fetch` with `Task.Run` and blocks the resolving caller on the task. A cold startup therefore needs a second thread to do each winning synchronous lookup. There is no recorded production startup or thread-pool baseline, so this design does not promise a measured speedup.

Use a **provider-local, resource-keyed flight holder**. Publish a waitable holder before starting the remote call. The winning ordinary request without a cancellable token executes the bounded synchronous `Fetch` on its initiating thread. A winning audit request or ordinary request with a cancellable token schedules the fetch so its caller can stop waiting promptly. Requests joining a flight share its outcome and retain their own cancellation semantics. No public async provider/client API or refresh behavior is added.

The user selected prompt cancellation for token-bearing ordinary reads and accepted the precise owner-based inline promise. A startup caller joining a flight already started by an audit or cancellable caller may wait for that worker-owned flight. It must not start a second lookup merely to force inline execution.

## Current contracts and evidence

- `IConfigProvider.Resolve<T>` and `IAppSurfaceGoogleSecretManagerClient.AccessSecretVersion` are synchronous. The [Google adapter](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerClientAdapter.cs) passes the configured lookup timeout to the SDK call.
- [The provider](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/GoogleSecretManagerConfigProvider.cs) currently stores `Lazy<Task<PayloadResult>>` by ordinal-exact version resource. `GetPayload` waits with the request token; `Fetch` owns response-name validation, resource claims, cache publication, and value-safe failure mapping.
- [The scope](../../Config/ForgeTrust.AppSurface.Config/ConfigProviderRequest.cs) owns one aggregate audit deadline, remote-lookup budget, and concurrency semaphore. Its present lease is released when the *caller* stops waiting, even if the queued synchronous fetch is still active. A scope whose deadline or caller token has cancelled rejects further lookup reservations, so an expired scope cannot schedule a new worker after releasing a lease.
- The [provider reference](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager/README.md) promises one shared fetch for concurrent misses, isolated waiter cancellation, failure eviction, exact resolved-version provenance, cache-generation-safe eviction, and incomplete audit diagnostics.
- Existing [concurrency tests](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager.Tests/GoogleSecretManagerConcurrencyContractTests.cs) exercise claims, cache identity, cancellation, and retry; [provider tests](../../Config/ForgeTrust.AppSurface.Config.GoogleSecretManager.Tests/GoogleSecretManagerConfigProviderTests.cs) exercise audit deadlines. They need owner-thread and mixed-winner cases for this change.
- The file-declared `Secret<T>` path already calls the synchronous client directly with a remaining-time budget. It does not use the mapped provider's flight dictionary and is outside this scheduling change.

Microsoft documents that wrapping synchronous work in `Task.Run` moves blocking to another thread and adds scheduling overhead; it does not make I/O asynchronous. It also documents that `ConcurrentDictionary.GetOrAdd` may run a value factory more than once. Those are design constraints, not a performance measurement: [async wrapper guidance](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/async-wrappers-for-synchronous-methods), [dictionary contract](https://learn.microsoft.com/en-us/dotnet/api/system.collections.concurrent.concurrentdictionary-2.getoradd?view=net-10.0). Cancelling a wait need not cancel the underlying operation: [cancellation guidance](https://learn.microsoft.com/en-us/dotnet/standard/asynchronous-programming-patterns/cancel-non-cancelable-async-operations).

## Premises

1. Startup resolves explicit, immutable version resources; updated values are adopted on restart. Runtime refresh and new version selection remain outside #819.
2. A no-token ordinary caller that **wins a new flight** must perform the synchronous client call itself. A joiner follows the existing flight's execution mode.
3. A caller with an explicitly cancellable token, or an audit deadline, may stop waiting while a shared remote call continues. The synchronous client seam cannot preempt that call; its own configured timeout bounds it.
4. Per-resource sharing, exact-version identity, cache-generation ownership, terminal diagnostics, and audit incomplete-coverage semantics take priority over a stronger “every startup caller executes inline” claim.
5. Performance claims require the same repeatable workload on the baseline and changed revisions. A structural thread reduction is an expectation to test, not a measured result.

## Independent review

A fresh-context `combo/sub` review supported an owner-owned flight holder and identified the winner-order race: a cancellable caller may publish a worker-owned flight just before a no-token startup caller joins it, or the startup caller may publish an inline flight before an audit joins. Both orders need deterministic tests. The review proposed an internal async Google client as a longer-term ideal; that changes the client seam and falls outside the issue's explicit synchronous-contract boundary.

## Approaches considered

### A. Provider-local flight holder (selected)

Replace the `Lazy<Task<PayloadResult>>` dictionary value with a small holder containing a completion source configured with `RunContinuationsAsynchronously`. Constructing a candidate has no side effects. The winner publishes the holder, then starts `Fetch` inline or schedules it according to that winner's request. Joiners wait on the published completion with their own token. Completion removes only the matching holder, so a late cleanup cannot evict a replacement flight.

Effort: M, roughly 1–2 human days / 2–4 CC hours. Risk: medium, concentrated in publication and cleanup ordering. This reuses `Fetch`, the current cache and claim logic, and existing test seams. It keeps the change local to the provider, but mixed-caller races and background-work lifetime require explicit proof.

### B. Separate internal flight coordinator

Move publication, winner selection, completion, and exact-entry cleanup to an internal type; keep provider-specific `Fetch`, conversion, cache, and diagnostics in the provider. Effort: L, roughly 2–3 human days / 4–6 CC hours. Risk: medium. Ownership would be clearer if other synchronous secret paths later needed sharing, but it adds an abstraction and test surface without an adopter in #819. The user chose A for this scoped follow-up.

### Deferred: Internal asynchronous Google client operation

The Google SDK offers async access, but introducing an internal async seam while keeping the public synchronous client contract would create two execution paths or a compatibility adapter. This deserves a separate design if measured startup latency or cancellation requirements justify changing the client boundary.

## Selected behavior and ordering

1. Run the existing cancellation check, reference/claim validation, and warm-cache check in their current order. Keep cache keys and flight keys as ordinal-exact full version resources. Do not put network work in `ConcurrentDictionary.GetOrAdd`'s factory.
2. Obtain a candidate holder, atomically publish or join by resource, and identify the actual published winner by reference identity. A joiner must never start work. If it observes a completed holder left in the dictionary, compare-remove that exact holder and retry; this prevents a later uncached read from reusing an old result while preserving a replacement generation.
3. The winning no-token, non-audit caller executes `Fetch` inline and completes the holder in a `finally`-safe path. Its own `Resolve` returns the same result. An audit or explicitly cancellable winner schedules `Fetch` and waits with its request token. All waiters use the holder's published completion, so joining an inline fetch never blocks inside a lazy initializer before applying an audit deadline.
4. Complete the holder with the existing `PayloadResult`, or with the same exception outcome if an unhandled fatal exception escapes `Fetch`; never strand waiters. Remove the exact holder after completion. Only the winner owns completion and cleanup. A cancelled waiter never cancels the shared fetch and never removes an active holder.
5. Preserve `Fetch`'s configured per-call timeout, diagnostic mapping, exact response-version validation, claim-poison recheck, defensive payload copies, and cache-generation comparison. The new holder must not become a cache: once the fetch completes, a later uncached read starts a new flight; a warm successful cache hit bypasses flight creation.
6. Keep the audit's configured remote-lookup count, deadline, and caller-owned concurrency lease. Schedule an audit-owned worker only after the scope grants a lease. While the aggregate deadline remains live, that lease stays with the waiting caller and bounds concurrent starts. When the scope token is cancelled, its waiter can return and release the lease, but no later request in that scope can reserve a slot or start new work. Thus active audit-owned calls can finish after the report deadline yet cannot grow past the operation's configured maximum. An audit joining a startup-owned inline flight keeps the existing caller-side budget behavior but creates no audit worker. No new scope-lifetime API is required.
7. Scope the promise precisely: for an ordinary uncancellable winner, no `Task.Run` precedes its remote lookup and the client sees the initiating managed thread. A no-token joiner may block waiting for the winner, which is required for one fetch per resource.

## Proof and measurement

| Area | Required evidence |
| --- | --- |
| Inline owner | A dedicated resolver thread wins a cold no-token flight; fake client records the same managed thread and one call. A warm cache hit makes no new flight or call. |
| Sharing and winner order | Gated fake client proves one call and identical safe outcome for many same-resource callers. Repeat with no-token winner first, cancellable winner first, and audit winner first; assert each joiner can reach its own wait without blocking in publication. |
| Cancellation and deadline | Pre-cancelled requests stop before claims/cache/client; cancelling either an owner or joiner stops only that wait; audit deadline returns `config-audit-deadline` promptly while another caller may still receive the shared result. Observe background completion before disposing test gates. |
| Audit limits | With `MaxAuditConcurrency = 1`, hold an audit-owned client call and start a second distinct-resource request **before** the same scope's deadline expires. Prove the second call does not enter the client until the first completes or the aggregate deadline cancels the scope. After deadline, prove another request starts no work and returns incomplete coverage; observe the first worker's eventual completion before disposing its fake gate. Verify the remote lookup count and existing diagnostics. |
| Failure, cache, identity | Remote timeout and RPC failures keep their diagnostic class; all waiters see one failed flight; a later request retries. A delayed failed conversion cannot evict a newer cache generation. Exact resolved version/provenance and resource-collision poisoning remain unchanged. |
| Quality gates | Run focused Google and Config tests, scoped formatting, warning-free builds, and the repository's solution coverage script when practical. Update package and repository documentation for changed internal behavior, cancellation caveat, and observed measurements. |

Measure before implementation on a pinned baseline revision (prefer current `origin/main`), then on the changed revision. Use one fixed, credential-free fake-client workload with a start barrier, specified resource count, caller count, fake lookup latency, cache setting, runtime, processor count, and ThreadPool minimum. Include distinct-resource cold reads and same-resource contention, plus a warm-cache control. Repeat runs under the same conditions and report median and spread of elapsed time, peak active fake-client calls, sampled `ThreadPool.ThreadCount`, and sampled process thread count; state sample interval and baseline/candidate commit IDs. Thread counts are process-level indicators, not proof that a particular thread executed a lookup. The thread-identity test supplies that proof. Report raw results even if elapsed time does not improve. Do not infer production latency from the fake workload.

### R1-1 — completeness

**Problem**

> The audit concurrency proof starts a second request in the same operation only after the first request's audit deadline has expired. Because the scope owns that deadline, the second request can return `config-audit-deadline` before reaching the client even if the first worker prematurely released its slot. The stated assertion that active audit-owned calls never exceed the limit therefore does not distinguish correct lease retention from the defect this test is meant to catch.

**Remedy**

> Revise the proof to observe that the execution lease remains held after the waiter deadline and is released only when the underlying fetch finishes, using an appropriate test seam. If the intended deadline is per request rather than scope-wide, state that contract and keep the second request's deadline live while it contends for the same slot.
