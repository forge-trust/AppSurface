## Problem Statement

Skoolit QA needs per-test configuration and dependencies before AppSurface constructs the Aspire profile and composes its graph. The existing factory returns too late: changes to the returned builder cannot change constructor injection or composition decisions already made.

The smallest useful delivery is a configured factory with three ordered hooks, preserving the existing factory and its lifecycle. Completion requires a demonstrated Skoolit migration, not just a new package API.

## Demand Evidence and Target User

The stated purpose is “internal company project to unblock Skoolit QA.” The immediate users are engineers authoring Skoolit QA fixtures and scenarios. The [filed specification](https://github.com/forge-trust/AppSurface/issues/866) and pinned consumer source show the concrete integration gap. No named adopter, measured time savings, revenue, or runtime reproduction was supplied; those are not claimed.

Evidence is source inspection against AppSurface commit `40de2ef62ad9e697929ef4bd56f0bfda2d813d72` and Skoolit commit `a589f164ef3346d4ecf8bf39b8a73ec71ea1cb1e`. The filed spec used AppSurface commit `c2f062f2a22afeff972c5c6512f1f34dd182db90`. This document proposes behavior; it does not report implementation, passing tests, or a published package.

## Status Quo

## Premises and Chosen Approach

The user approved these decisions:

- Graph selection belongs to each factory call. Process-wide runtime switches may still require serialized tests.
- Hook order is activation configuration, activation services after module registrations, profile construction, Aspire builder customization, then graph composition.
- Preserve public validation, the unstarted activation host, one-build behavior, and cleanup ownership. Callbacks must not bypass lifecycle guards.
- Completion includes overlapping on/off graphs, removal of scenario environment save/set/restore, a packed consumer, API and ordering documentation, and recorded source/package identities.
- Choose approach A: `CreateConfiguredAsync` with guarded preparation, reusing the existing wrapper and activation lease.

Approach B, a separate borrowed builder facade plus creation plan, was rejected because it adds another forwarding surface and lifetime mechanism without improving the agreed first delivery.

Estimated implementation and verification: 2–3 engineering days, or 4–8 agent hours with dependencies available. Risk is medium, concentrated in lifecycle transitions and cleanup before the activation lease exists.

## Cross-Model Perspective

An independent `combo/sub` cold read identified three useful risks: a raw Aspire builder permits premature build; hook failures can occur before lease ownership; and an options overload named `CreateAsync` can make `CreateAsync(default)` ambiguous. It also warned that custom-container registrations can override earlier service-collection changes.

The chosen design addresses these through the existing guarded wrapper, explicit creation ownership, a distinct method name, and documented provider boundaries. Its proposed receipt-resource presence test was corrected: the pinned consumer always adds `skoolit-web`; monitoring receipts change settings on that resource. Claude Code was unavailable, so this was an in-host independent review, not completed outside-model coverage.

## Public API and Defaults

Add a public options type in the testing package:

```csharp
public sealed class AppSurfaceAspireTestingOptions
{
    public Action<IConfigurationBuilder>? ConfigureActivationConfiguration { get; init; }
    public Action<IServiceCollection>? ConfigureActivationServices { get; init; }
    public Action<IDistributedApplicationBuilder>? ConfigureAspireBuilder { get; init; }
}
```

Add a distinct generic factory method, retaining the existing generic constraints:

```csharp
CreateConfiguredAsync<TAppHost, TModule, TProfile>(
    AppSurfaceAspireTestingOptions options,
    CancellationToken cancellationToken = default)
```

Its return type matches the existing `CreateAsync<TAppHost, TModule, TProfile>`. The existing cancellation-token-only overload keeps its signature and behavior. Calls using no arguments, a cancellation token, or `default` remain unambiguous.

Null options throws `ArgumentNullException`; null hooks are no-ops. After a valid options reference is obtained, preserve cancellation-before-type-validation behavior. Each hook runs once, synchronously, in the stated order. Snapshot the three delegate references at entry. Init-only properties prevent ordinary later reassignment; they do not freeze captured objects. Callers must provide per-call state or thread-safe captures.

These hooks do not bind profile command arguments, replace the root module constructor, or start an application. They are synchronous actions: asynchronous work and `async void` callbacks are unsupported. Do not call `BuildServiceProvider` inside the services hook; that creates another provider with different ownership.

## Ordered Creation and Provider Boundaries

| Phase | Operation and boundary |
| --- | --- |
| 1 | Validate options, cancellation, marker/module/profile types, command metadata, and generated project path using existing rules. Invalid inputs run no hooks. |
| 2 | Build activation configuration through the existing startup path. Append the configuration hook after module host customization; add sources before configuration and the activation provider are built. |
| 3 | Run the activation-services hook after the complete module service-registration sequence and all module-added service callbacks, before activation-provider construction. |
| 4 | Build the activation host without starting it; resolve the profile using that host's services. |
| 5 | Create the Aspire builder with existing profile arguments, assembly/project identity, and dashboard defaults; wrap it in preparation state and invoke the Aspire hook. |
| 6 | Compose the profile graph through that same guarded wrapper, then transition to the existing active state and return it. |

The configuration hook changes application configuration used by activation; it does not replace host identity or bypass project-path validation. Later-added configuration sources have the usual source precedence. The services hook can remove or replace descriptors before the default .NET provider is created.

A custom container may add registrations later through `ConfigureContainer`. In particular, the repository's Autofac module uses that phase. Preserve the selected provider and its rules; do not promise that a service-collection replacement overrides every container registration. Document and test this distinction. Provider-specific last-wins behavior is outside this API's guarantee.

The Aspire hook receives the guarded `IDistributedApplicationBuilder`, never the raw inner builder. Its configuration, services, and resources affect the Aspire application and graph. Its services cannot retroactively change the activation provider.

These boundaries follow the [Generic Host lifecycle](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host?tabs=hostbuilder) and the pinned [HostBuilder implementation](https://github.com/dotnet/runtime/blob/v10.0.8/src/libraries/Microsoft.Extensions.Hosting/src/HostBuilder.cs). Aspire's [test-host guidance](https://aspire.dev/testing/manage-app-host/) provides context, but switching to an entrypoint-based test factory would not provide this typed profile activation contract.

## Guarded Preparation and Ownership

Extend [the existing testing wrapper](https://github.com/forge-trust/AppSurface/blob/40de2ef62ad9e697929ef4bd56f0bfda2d813d72/Aspire/ForgeTrust.AppSurface.Aspire.Testing/AppSurfaceAspireProfileTestingBuilder.cs) with an internal `Preparing` state and factory-only completion/abort operations.

- During preparation, configuration/service/resource access and graph mutation are allowed. `Build`, `BuildAsync`, public `Dispose`, and public `DisposeAsync` throw `InvalidOperationException` without changing ownership.
- Preparation lasts through both the Aspire callback and profile composition. Completion atomically enables the existing active/build lifecycle; callbacks cannot complete preparation.
- A callback may catch a rejected early build/disposal and continue. If it lets the rejection escape, creation fails and the factory aborts preparation.
- On failure, an internal abort disposes owned builder/partial-provider resources and then the activation lease, retaining existing suppression of secondary cleanup failures. The public disposal guard must not block factory cleanup.
- After return, retain the existing building, built, faulted, disposing, and disposed behavior, including concurrent-build rejection and idempotent disposal. Retained mutable references are subject to the same unsupported post-build mutation restrictions as today.

Before the activation lease exists, a creation guard owns the activation host as soon as build returns it. Hook wrappers also record factory-owned configuration roots and the hosting content-root file provider exposed through public host context. If a new hook fails before a host is returned, dispose captured owned objects once, in reverse acquisition order; after host ownership transfers, defer their cleanup to the host. De-duplicate references and never dispose caller-owned configuration sources or singleton instances supplied by the caller. Prove this acquisition/transfer logic using intentional internal test seams, without reflection or process-global diagnostic interception.

Check cancellation before and after each hook, before profile resolution, and around composition using existing cancellation checkpoints. A synchronous callback cannot be preempted. Preserve `OperationCanceledException`; wrap other nonfatal failures with the phase, marker/module/profile types, and original exception. Preserve existing fatal-exception handling. Cleanup failures must not replace the primary failure. No failed creation returns a usable builder, and no activation hosted service starts.

## Skoolit Migration and Observable Proof

Introduce a consumer-owned immutable QA scenario value and inject it into the component that selects graph settings. Register it through `ConfigureActivationServices`, or derive it from per-call activation configuration before registering it. Preserve direct-run defaults through the consumer's existing runtime path; QA explicitly supplies its own scenario.

Migrate scenario selection away from process environment save/set/restore. Environment values emitted into child resource configuration remain legitimate output. Unrelated process runtime defaults in the fixture remain explicitly documented and serialized where required.

The first proof creates two factories with distinct scenario objects whose preparation/composition actually overlaps. Inspect their `skoolit-web` graph annotations before application start:

| Emitted child setting | Receipts on | Receipts off |
| --- | --- | --- |
| `Skoolit__Inbox__MonitoringReceipt__Enabled` | `true` | `false` |
| `Skoolit__Inbox__MonitoringReceipt__Cohort` | `SeededInternal` | `Disabled` |
| `Skoolit__Inbox__MonitoringReceipt__SeededInternalHouseholdIds__0` | `household_dev_billing` | empty |

Both graphs contain `skoolit-web`. Assert scenario selection does not write the test process environment. Use per-call probes and a bounded synchronization barrier on independently executing tasks; `Task.WhenAll` alone is insufficient when factory work completes synchronously. No static scenario selector or shared mutable configuration may decide these assertions.
