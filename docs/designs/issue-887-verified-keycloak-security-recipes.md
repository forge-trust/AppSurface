## Problem statement and evidence

Skoolit currently maintains a Keycloak Dockerfile and Python archive repair to align Java libraries, select a separate runtime and signed OS snapshot, remove unwanted packages/helpers, and repair Jackson inside the admin CLI. Moving only its theme upstream would preserve most of that maintenance burden. AppSurface should execute these supported operations from a reviewed recipe and inspect their actual output, while consumers retain pin selection and operational authority.

Static review used AppSurface `origin/main` at `604ec9b074008d45512911bfbabc15d50aa5fc1a` and [Skoolit fixture `965ccdba`](https://github.com/forge-trust/skoolit/tree/965ccdbaefbee5814e806c5981bdeab100922e8c/deploy/keycloak), which uses AppSurface preview.14 and Keycloak 26.7.2. This checkout is on diverged HEAD `9612cdeb`; the inspected Keycloak implementation matches the recorded main baseline. Refresh both repositories and fixture identities before implementation. No feasibility build, vulnerability assessment, runtime test, release, or downstream adoption occurred in this design session. Maintenance time and savings remain unmeasured.

The existing [theme build contract](../../Auth/ForgeTrust.AppSurface.Auth.Aspire.Keycloak/AppSurfaceKeycloakThemeBuildContract.cs) stages verified files and publishes an atomic context. The [release evidence factory](../../Auth/ForgeTrust.AppSurface.Auth.Aspire.Keycloak/AppSurfaceKeycloakThemeReleaseEvidence.cs) binds a supplied image reference to manifests but does not inspect the image. Existing CI also computes some expectations separately in shell. Reuse the useful machinery and replace that split definition with the selected captured plan.

## What makes this useful beyond Skoolit

A second application can declare different reviewed pins and receive the same supported execution, failure handling, and evidence. An application maintainer can manually compare the portable evidence from two inspections and identify which observed modules or runtime packages changed before deciding whether to promote an image. No built-in diff tool is included. The result remains a small package capability and portable evidence file, without a new controller or dashboard.

## Decisions and accepted premises

- Build on #658 with an explicit boundary expansion because its snapshot, manifest, image-reference, and atomic-output patterns already fit the problem.
- Select Approach B, a captured plan shared by execution and inspection, because each requested change needs one definition of inputs, ordering, limits, and expected results. Direct profile-to-Containerfile generation, Approach A, was rejected because generation and inspection would need separately maintained mappings.
- Support all three operation families in the neutral and accepted Skoolit fixtures. Unsupported profiles fail explicitly; no family can become a consumer shell escape hatch.
- Capture immutable execution inputs before transformation or context generation. Later workspace changes cannot alter execution or certify different output.
- Produce passing evidence only after actual final-image inspection. A label, declaration, generated context, or earlier theme tuple cannot satisfy this requirement.
- AppSurface owns supported recipe validation, execution, inspection, and safe failures. Hosts choose pins and retain image-builder invocation, credentials, registry push, scan policy, deployment, and traffic authority.
- Completion includes coordinated publication and a clean consumer of published package bytes, alongside retained system gates. Feasibility comes before public API commitment; release-owner authorization comes before publication.

## Recommended approach

### Package boundary and proposed contract

Create the one proposed `ForgeTrust.AppSurface.Auth.Keycloak` library without Aspire dependencies. It owns recipe/operation records, validation, capture, bounded archive transformation, context materialization, inspection, typed failures, and evidence. #888 adds its desired-configuration contracts to that same library through a coordinated change. This design does not implement #888's identity lifecycle.

The existing [Aspire Keycloak package](../../Auth/ForgeTrust.AppSurface.Auth.Aspire.Keycloak/README.md) adapts the shared contracts and retains local theme iteration. Production web applications continue using their host-owned authentication stack. Preserve the theme extension restrictions; JAR support belongs to the security operations, not the theme-source allowlist.

Names below describe the proposed API shape and may follow repository naming conventions after feasibility:

| Contract | Behavior and constraints |
| --- | --- |
| `KeycloakSecurityRecipe` | Immutable source-image/platform identity, supported runtime/archive profile identities, ordered operation declarations, theme and reviewed template-baseline references. No arbitrary commands, callbacks, or plugins. |
| `CaptureAsync(recipe, trustPolicy, ownedDirectory, cancellationToken)` | Validates and resolves policy-approved inputs into a private content-addressed snapshot; returns a captured plan only after all bytes, identities, and source authorizations verify. Caller supplies an absent output location. |
| `CapturedKeycloakPlan` | Read-only snapshot handle, canonical digest, finite operations and expected observations. Local paths remain private implementation details. Cannot be constructed as a passing result from caller-supplied metadata. |
| `MaterializeAsync(plan, absentContext, cancellationToken)` | Revalidates captured content and emits a deterministic staged context/Containerfile from supported handlers; executes bounded archive repair as required. No workspace rereads. |
| `InspectAsync(plan, immutableImage, cancellationToken)` | Inspects the exact platform image and returns observed inventories or a typed failure. The host must supply a supported image-runtime/OCI inspection environment. |
| `VerifiedKeycloakImageEvidence` | Created only by successful inspection, with atomic output writing. A separate release record links this observation to scan, CLI, rendering, upgrade/restore, and publication results. |

There is no default runtime security pin, live package index, implicit platform, or automatic upgrade. The neutral sample supplies an explicit checked-in recipe. A closed supported profile selects built-in behavior, not an arbitrary executor. Validate duplicate operation IDs, overlapping destinations, missing alignment members, unexpected ordering, and unsupported profile versions before mutation. The plan is a finite sequence with validated dependencies, not a general workflow engine.

The consumer's designated maintainer approves a separate immutable `KeycloakMaterialTrustPolicy` as host policy; a recipe cannot authorize its own sources. It binds permitted HTTPS origins and coordinate namespaces to approved material digests, permitted mirror mappings, and repository signing-key fingerprints/trust rules. AppSurface validates and enforces this policy without choosing the consumer's pins. The reviewed fixture card records the approving owner, policy version/digest, and exact allowed origin/coordinate/key associations; its approval reference is provenance, not an AppSurface-issued trust certificate. An untrusted recipe cannot broaden the host-supplied policy.

Capture checks requested and final download origin against that policy, permits redirects only within explicitly authorized mappings, verifies TLS without bypass, and verifies coordinate/module identity and content digest. For OS materials, verify signed repository metadata and its package hash chain using only the policy-approved key identities and the declared snapshot rules; no implicit trust-on-first-use or live key discovery. Capture binds the policy digest and actual verified origin/key identities into the plan. Missing approval, an unapproved redirect/key, or unverifiable provenance fails before snapshot commitment or build transformation; temporary capture files remain untrusted and are cleaned. Mirror unavailability does not authorize a substitute origin.

### Capture, execution, and inspection lifecycle

`Recipe -> validate/resolve -> private captured plan -> materialized context -> host image build -> exact-image inspection -> evidence -> retained system gates -> authorized release/adoption`

1. **Resolve and capture.** Resolve each image index to its exact platform manifest and record both identities. Acquire approved artifacts and signed repository metadata/package closure under explicit limits; verify digests and identities while copying. Capture recipe, source/runtime references, package versions/removals, trust metadata, transformer version/digest, theme files/manifests, reviewed baseline, and generated-input policy. Snapshot identity excludes machine-local paths and uses canonical ordering and serialization. Capture is all-or-nothing in an owned staging directory; symlinks/reparse escapes and changes during capture fail.
2. **Seal inputs.** Finalize by an atomic move to a private read-only snapshot. A digest is a consistency boundary, not a sandbox against a privileged local administrator. Before use, verify captured bytes through opened handles or private verified copies so an altered snapshot cannot be used after an earlier hash check. Reject changed or missing materials; never silently refetch different bytes. Package and builder prerequisites must be identified before execution.
3. **Execute supported handlers.** Materialize only from the captured plan. Order source inspection, archive transformation and artifact staging before final runtime/theme assembly. Generate build instructions from validated values and fixed templates; external process invocation uses argument lists without host-shell interpolation. Framework-generated package-manager instructions may use shell syntax, but consumers cannot inject shell text. The host invokes its builder on the captured context. Record actual builder/frontend identity and output manifest for evidence correlation.
4. **Inspect the final output.** Resolve the supplied immutable platform image, export/read the same verified OCI content for all static checks, and bind runtime probes to that digest. Inspect the merged filesystem with correct layer deletion/whiteout semantics and safe bounded extraction; do not infer final files from individual layers or labels. The package's supported adapter performs digest verification and the inspection; a caller-provided report or directory cannot mint verified evidence. A failed or unsupported inspection produces no passing evidence.
5. **Publish observations atomically.** Verify all expected observations and write evidence to a fresh caller-owned path. Detect an existing destination and preserve it. Failures may emit a clearly failed diagnostic result, never a success-shaped partial record. Image inspection proves observed conformance under the declared tool trust boundary; it does not attest a hostile builder's honesty or establish vulnerability freedom.

Deterministic archive output and immutable workspace isolation are required. Byte-identical whole-image reproduction across builders is not promised. Record builder/frontend/compression versions and compare two clean runs during feasibility; explain differing image metadata rather than converting an unexplained difference into a reproducibility claim.

### Supported operation families

| Operation | Required inputs | Execution and observable result |
| --- | --- | --- |
| `ArtifactReplacementGroup` | Exact source image/platform; approved artifact origin and Maven group/artifact/version/classifier; expected original digest and module identity; replacement digest/identity; destination; complete declared alignment group. | Read originals from the captured source. Require every member and reject extras/colliding targets. Verify replacement bytes and Maven/module metadata. Preserve the original classpath-required filename deliberately while recording the new internal identity. Inspect the final image for the exact replacements, required copies, and absence of stale selected payloads. |
| `RuntimeProfile` | Digest-pinned runtime per platform; signed dated repository snapshot, suites/components/trust identity; exact package/dependency closure and removals; supported user/ownership/entrypoint expectations. | Built-in profile installs only the captured signed snapshot closure and never falls back to live repositories. Inspect complete installed inventory, changed package files, required removals, runtime version, trust stores, user/permissions, and startup behavior. Unsupported package/snapshot/platform combinations fail before producing an accepted image. |
| `EmbeddedArchiveReplacement` | Captured source/replacement digests and Maven identities; declared class prefixes, versioned classes, service paths and metadata; versioned transformation profile and numeric limits. | Stream validated entries into a separate deterministic archive, preserve unrelated payloads and manifest exactly, replace complete declared module content and metadata, reopen/verify output, then atomically publish. Inspect the final embedded archive and execute the retained CLI gate on the exact output image. |

The initial proof fixture maps the complete Skoolit inventory: Micrometer, Netty, and Bouncy Castle aligned sets; server and CLI library copies; JDBC and FreeMarker replacements; embedded Jackson core/databind; separate Temurin/Ubuntu runtime and OpenSSL package set; libcurl/curl removal; unused helper removal; nonroot UID/ownership and certificates; theme manifest and reviewed baseline. Fixed profile behavior covers the required user/helper changes. A migration matrix must account for every current Dockerfile/script operation, including apparently incidental ones.

Host-owned application entrypoint files remain captured, reviewed build inputs under the host's composition policy. They do not become a recipe shell hook. If host composition adds layers after the supported context, inspect the final composed digest and run retained gates against it. Any operation that cannot be represented safely returns with evidence and revised alternatives before API commitment; it is not silently omitted.

### Archive integrity, resource bounds, and failure behavior

Use the .NET ZIP APIs in seekable `Read` mode and a fresh `Create` output. Preflight bounded central-directory metadata before materializing an unbounded entry collection; enforce count/name/metadata budgets as well as compressed input, per-entry and total expanded bytes while reading. Do not use `Update`, unseekable input buffering, recursive extraction, or whole-archive dictionaries of payload bytes. Validate actual lengths/CRC and declared sizes with overflow-safe counters.

For the bounded feasibility proof, start with explicit ceilings per archive: 256 MiB compressed input, 65,536 entries, 1 KiB UTF-8 entry name, 16 MiB central-directory metadata, 64 MiB expanded per entry, 1 GiB expanded total, and 1 GiB output. These are provisional engineering bounds, not measured support claims. Profiles record exact numeric values; implementation must measure both fixtures and ratify or explicitly revise limits before support is advertised. Count replacement inputs and temporary output against a declared execution disk/memory budget; interruption and disk exhaustion preserve previous output.

Require canonical safe entry names; reject duplicates, alias/path collisions, malformed/truncated archives, unsupported compression/encryption, unexpected provenance, and unsupported signatures, including case-insensitive `META-INF/SIG-*` and standard signature extensions. Check both source and replacement archives; a signed replacement is rejected unless an explicitly reviewed profile handles its semantics. Preserve the source manifest byte-for-byte; versioned classes and unversioned services have separate declared rules. Sort entries and normalize output timestamps/permissions/compression settings under the recorded transformer version. No signature stripping or ad hoc metadata merge is inferred.

Each supported archive profile declares a manifest-preservation policy for the exact source CLI identity. Preserve only source-level facts that remain true, such as the CLI's own `Main-Class`, `Class-Path`, and Keycloak implementation identity, along with allowed unchanged attributes. Parse and validate main attributes and entry sections: reject digest/signature attributes covering transformed entries, module/library version or sealing declarations made stale by replacement, ambiguous duplicate attributes, and unsupported identity-bearing attributes. Keep `Multi-Release` unchanged only when it truthfully describes the resulting versioned-class layout; a repair that would require adding or changing it is unsupported. Preserve unchanged entry sections only when their referenced bytes and semantics remain unchanged. Reopen the output and verify its identical manifest against the resulting module inventory and payload hashes. No manifest attributes are recomputed in this preservation profile: if correctness requires rewriting one, reject the input and request a supported upstream rebuild or an explicitly reviewed future profile. Tests include stale per-entry digests and module-version attributes as rejection cases, plus the accepted fixture's byte-identical manifest.

Write to a unique owned temporary file on the destination filesystem. Close, flush, and verify it before the atomic publication step; never overwrite the source in place. The API explicitly distinguishes an absent destination from an authorized replacement of a prior output and validates that source/destination do not alias. Failure or cancellation before commit preserves the previous destination; failures after uncertain commit report side-effect state and require inspection before retry. Owned temporary cleanup must not hide the primary failure or delete unrelated files.

### Inspection evidence and actionable failures

Evidence binds the final platform manifest/config identity to the captured plan digest; source/runtime image identities; resolved package inventory and removals; replacement/module and repaired archive hashes; transformer/profile versions; theme manifests and reviewed baseline; actual builder/inspector identities; and individual observed-check results. Portable output contains safe artifact coordinates and image-internal identities, no credentials, raw realm/config data, machine-local paths, or unsanitized subprocess output. Canonical inventory hashes can be deterministic; timestamps and correlation IDs are separate observation metadata.

Adapt the pre-alpha theme evidence directly into this stronger model and update the existing sample/callers. Existing theme-only behavior remains supported and correctly labeled. Do not introduce a second public evidence hierarchy or compatibility facade without an identified consumer requirement. A legacy tuple cannot be reclassified as inspected security evidence.

Every failure supplies a stable documented code, operation ID, safe field/artifact identity, and first/last-line corrective action or precise maintainer request. Partial or unexpected failures add side-effect state (`none`, `staged`, `committed`, `unknown`), recovery class, bounded retry guidance, safe profile/version context, and a compact correlation ID. Sanitize nested causes and bound logs. Validation is noninteractive; SDK callers receive typed failures, packaged executables use stderr/nonzero, and no automated run waits for terminal input. Validation/digest/provenance/unsupported-profile failures are not blindly retried. Unknown outcomes require inspection, then a corrected fresh execution; no automatic deployment rollback is implied.

The design retains workspace isolation, requires deterministic archive bytes, and limits image reproducibility claims to what future runs actually observe. Primary sources support the chosen mechanisms: [Keycloak container customization](https://www.keycloak.org/server/containers), [Ubuntu snapshot selection and trust configuration](https://snapshot.ubuntu.com/), [Java 21 JAR/versioned-class/signature semantics](https://docs.oracle.com/en/java/javase/21/docs/specs/jar/jar.html), [.NET archive bounds and streaming guidance](https://learn.microsoft.com/en-us/dotnet/standard/io/zip-tar-best-practices), and [BuildKit provenance](https://docs.docker.com/build/metadata/attestations/slsa-provenance/). Snapshot service availability is not indefinite retention. Build provenance can supplement inspection, and detailed provenance exposes build arguments; sanitize before any release record and keep credentials out of arguments. No new hosted evidence service is required.
