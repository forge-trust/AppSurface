Implemented on the issue #782 branch. The public-Aspire feasibility gate passed with the pinned Aspire hosting
packages: a finite package-owned realm-ready executable and finite consumer `ProjectResource` stages compose through
`WaitForCompletion`, and typed secret parameters remain value-free and scoped to their declared seed project. The
implemented surface is `RealmReady()` plus `WithLocalSeed(...)`; live and focused-test evidence is maintained in the
[executable test plan](auth-aspire-keycloak-local-seeds-test-plan.md).

## Problem Statement

`ForgeTrust.AppSurface.Auth.Aspire.Keycloak` already creates a deterministic local Keycloak realm, public client, baseline users, secret-safe OIDC projection, and multi-signal proof readiness. A consumer sometimes needs application-owned local work only after that realm is available: optional external-identity broker setup from local credentials, deterministic test identities or attributes, and companion application fixtures after a known external subject exists. A browser proof must wait until the required work finishes.

Today each consumer builds a bespoke process/container, ordering model, secret path, and diagnostics. Issue #782 adds an AppHost-only lifecycle contract for that gap. It must remain local, explicit, ordered, idempotency-friendly, and consumer-owned. It must not become production Keycloak administration, a provider-neutral seeding platform, an AppSurface-owned Keycloak client, or a runtime web dependency.

## What Makes This Cool

The AppHost graph becomes an honest proof chain: Keycloak is healthy, AppSurface proves its expected realm/client baseline, two named consumer workers finish in order, then the browser proof starts. A developer sees the failing stage without making the framework own their provider policy, persistence, or application data.

## Constraints

- Extend the existing [`AddAppSurfaceKeycloak`](../../Auth/ForgeTrust.AppSurface.Auth.Aspire.Keycloak/README.md) wrapper established by #536 and #658. Do not introduce a second resource model or provider-neutral framework.
- Keep all new API AppHost/dev/test-only. Runtime web/auth projects remain free of the Keycloak package, Aspire hosting packages, Keycloak SDKs, containers, and a runtime seed library.
- Keycloak health is necessary but insufficient. The package baseline is metadata, generated-realm evidence, and public-client challenge evidence. It does not prove a consumer's admin capability.
- Keycloak startup realm import skips existing realms, so persistent local data and post-ready work require a separate completion path. [Keycloak import/export](https://www.keycloak.org/server/importExport)
- Do not use Aspire dashboard `WithProcessCommand` for seed execution. It is AppHost-machine interactive tooling whose stdout/stderr is surfaced in dashboard logs. [Aspire custom resource commands](https://aspire.dev/fundamentals/custom-resource-commands/)
- AppSurface receives only a typed `ParameterResource` identity and its `Secret` metadata. It never reads a value or arbitrary consumer configuration. Secret values must never appear in framework-owned manifests, logs, diagnostics, evidence, or web configuration. A framework-required parameter name/reference may appear in an Aspire manifest only if it has no value and the declared seed project is its sole consumer.
- Consumer workers own their Keycloak Admin API client, credentials, retries, idempotence, schema knowledge, external-provider policy, application data, packaging, logs, and evidence. AppSurface owns only AppHost registration, baseline proof, graph dependencies, and its own redacted diagnostics.
- Version 1 supports only consumer-owned finite `ProjectResource` workers, typically a console project. No long-running web/service project, arbitrary executable, dashboard command, or container worker is in v1.

## Premises

1. Aspire's public API can express a completion-bearing realm-ready gate and make a project wait for its successful completion. [Aspire `WaitForCompletion`](https://aspire.dev/fundamentals/annotations-overview/)
2. A finite consumer `ProjectResource` can exit `0` after successful seed work and nonzero on failure, giving downstream resources a native completion signal.
3. A package-local registry can validate its own wrapper handles: same `IDistributedApplicationBuilder` identity, unique names, and a strict linear predecessor relation.
4. Existing public-preview Keycloak consumers must retain unchanged behavior when they register no seeds.
5. The public-Aspire completion and typed-secret-binding gates passed before this contract was implemented. If either
   becomes unavailable, scope-unsafe, or inconclusive in a supported future Aspire version, this contract does not gain
   a callback fallback: a new design review is required.

## Cross-Model Perspective

The initial Codex cold-read returned no text, so an independent fallback reviewed the same boundary. It agreed that completion-bearing graph resources are essential and identified three risks: public OIDC readiness does not prove every consumer admin capability; secret parameter binding needs manifest-level proof; and persistent data makes consumer idempotence mandatory.

The fallback proposed a package-managed callback with a Keycloak `HttpClient`. This design rejects it: that would make AppSurface own token acquisition, client behavior, retries, callback execution, and secret redaction. No observed evidence established that a consumer project behind a real completion gate cannot work. The feasibility gates below are the only path to reconsider that decision.

## Approaches Considered

- **Consumer worker convention, rejected as the primary design:** document that each worker calls `Readiness.CheckOnceAsync` after Keycloak. This is the explicit fallback if public Aspire cannot represent the gate, but it leaves the central lifecycle rule voluntary.
- **Package-managed callbacks, rejected:** a callback with an AppSurface Keycloak client shortens host code but violates the chosen consumer-ownership boundary and creates a local administration runtime.

## Recommended Approach

Build a thin local-seed extension in `ForgeTrust.AppSurface.Auth.Aspire.Keycloak`. The feasibility gates passed, so the
implemented public names are `RealmReady()`, `WithLocalSeed(...)`, `AppSurfaceKeycloakLocalSeed`, and
`AppSurfaceKeycloakLocalSeedContext`.

### Execution branch

### Proposed public contract after the gates pass

| Element | Registration-time behavior | Safe surface | Forbidden surface |
| --- | --- | --- | --- |
| `AppSurfaceKeycloakRealmReady` | `keycloak.RealmReady()` lazily creates one package-owned, finite completion gate for its wrapper; repeated calls return the same handle. `WithLocalSeed` calls it automatically, so callers never need to order a seed against the gate manually. | Stable resource name and completion handle only. | Tokens, admin credentials, raw realm JSON, source paths, provider config. |
| `AppSurfaceKeycloakLocalSeedContext` | Passed synchronously once to the caller's factory while the AppHost graph is constructed. The factory must create the project with `ResourceName` and explicitly bind any safe, nonsecret metadata it needs through the public `WithEnvironment`-equivalent proved by the spike. It returns `IResourceBuilder<ProjectResource>`. | Deterministic resource name, authority, realm name, public client ID, and wrapper identity. | Secret values, claims, external subject, provider aliases, database handles, arbitrary configuration. |
| `AppSurfaceKeycloakLocalSeedOptions` | Receives only `.After(AppSurfaceKeycloakLocalSeed)` and zero or more `.WithRequiredSecretParameter(configurationKey, secretParameter)` calls. | One prior-seed handle; parameter identity and `Secret=true` metadata. | Parameter value or any general-purpose Keycloak/admin configuration. |
| `AppSurfaceKeycloakLocalSeed` | Returned immediately after synchronous factory registration. It wraps the same `ProjectResource` that the consumer created. | Validated name and completion-bearing resource. | Consumer worker output or provider-specific error interpretation. |
| `WithLocalSeed(...)` | Validates before `Build()`: local execution policy, nonblank unique name, same builder/wrapper for every handle, `ProjectResource` type/name, required immediate predecessor, and secret parameter metadata. | One project worker registration and its native completion dependency. | Implicit resource discovery, arbitrary graph scanning, cycles, cross-wrapper dependencies. |

Illustrative signature, conditional on the spike:

```csharp
AppSurfaceKeycloakLocalSeed WithLocalSeed(
    string name,
    Func<AppSurfaceKeycloakLocalSeedContext, IResourceBuilder<ProjectResource>> factory,
    Action<AppSurfaceKeycloakLocalSeedOptions>? configure = null);
```

The factory runs once during AppHost registration, never at seed runtime. It receives nonsecret metadata only; the package injects no hidden worker configuration. The worker must be a finite console-style project: it exits `0` only after all mutation/check work succeeds, exits nonzero on failure, and does not expose a service endpoint or remain running.

The package validates `ProjectResource` type, wrapper/builder identity, exact resource name, predecessor, and parameter metadata. It first performs all validation that needs no factory result, then invokes the factory, validates its return, applies options, and appends to its registry last. A thrown factory, a `null` return, an other-builder resource, or a resource whose name differs from `ResourceName` fails the registration call with a stable redacted `ASKEYC` validation diagnostic; no seed-registry entry survives. Aspire exposes no documented rollback for graph nodes a consumer factory may already have added, so the package does not attempt one: the unbuilt AppHost is failed immediately and cannot run. A project becoming a long-running service or adding an endpoint after registration is a runtime consumer violation, not a property AppSurface can safely infer through public APIs. The spike and sample therefore enforce a bounded finite-process test.

### Complete host composition example

```csharp
var keycloak = builder.AddAppSurfaceKeycloak("auth");
var brokerEnabled = builder.Configuration.GetValue<bool>("LocalIdentity:BrokerEnabled");
var brokerCredential = builder.AddParameter("local-broker-credential", secret: true);

// RealmReady is lazy; calling it here is optional and returns the cached handle.
var ready = keycloak.RealmReady();

AppSurfaceKeycloakLocalSeed? identity = null;
if (brokerEnabled)
{
    identity = keycloak.WithLocalSeed(
        "identity-bootstrap",
        seed => builder.AddProject<Projects.IdentityBootstrap>(seed.ResourceName)
            .WithEnvironment("LOCAL_SEED__AUTHORITY", seed.Authority)
            .WithEnvironment("LOCAL_SEED__REALM", seed.RealmName)
            .WithEnvironment("LOCAL_SEED__CLIENT_ID", seed.PublicClientId),
        options => options.WithRequiredSecretParameter(
            "LOCAL_IDENTITY__BROKER__CREDENTIAL", brokerCredential));
}

var fixture = keycloak.WithLocalSeed(
    "candidate-fixture",
    seed => builder.AddProject<Projects.CandidateFixture>(seed.ResourceName)
        .WithEnvironment("LOCAL_SEED__AUTHORITY", seed.Authority)
        .WithEnvironment("LOCAL_SEED__REALM", seed.RealmName)
        .WithEnvironment("LOCAL_SEED__CLIENT_ID", seed.PublicClientId),
    options =>
    {
        if (identity is not null)
        {
            options.After(identity);
        }
    });

var web = builder.AddProject<Projects.Web>("web")
    .WaitForCompletion(fixture.Resource);
```

`configurationKey` is an uppercase environment-variable key made of `A-Z`, `0-9`, and `_`, with `__` as the .NET configuration path separator. It is validated at registration. The parameter must be marked secret at registration; a missing runtime secret is a resource-configuration failure before the worker is launched. A parameter may bind to exactly one v1 seed and each configuration key is unique within that seed. Multiple required credentials are permitted through repeated calls; parameter reuse and duplicate/colliding keys fail registration.

### Ordering grammar and ownership

Every seed implicitly waits for its wrapper's lazily cached realm-ready gate. The first seed has no additional predecessor. Every seed after the first **must** name the immediately preceding returned `AppSurfaceKeycloakLocalSeed` from the same wrapper with `.After(previous)`; a prior-but-not-immediate handle, no handle, or any other wrapper/builder fails registration. The optional example above therefore has one seed when the broker is disabled, and the fixture must name `identity` when the broker seed is enabled. The package keeps an append-only registry keyed by `(IDistributedApplicationBuilder reference, Keycloak resource name)` and then seed name, so multiple Keycloak wrappers on one AppHost are distinct, branches and cycles are impossible in v1, and cross-builder/cross-wrapper handles fail at registration.

```text
Keycloak health
    -> package realm-ready gate: metadata + generated baseline + public challenge
    -> consumer project seed 1
    -> consumer project seed 2
    -> dependent web project launches after seed 2 reports successful completion
```

The dependent project is created in the AppHost graph but its process must remain pending and unlaunched until every required predecessor completes successfully. Gate/seed failure or cancellation produces no successful completion signal and leaves the dependent blocked. The feasibility spike must prove the exact public Aspire state transitions before the package claims this behavior.

### Credentials and opt-out

The package has no optional-secret API. A host enables an optional integration through an explicit nonsecret local opt-in and calls `WithLocalSeed` only when the integration should exist. If opt-in is off, no seed is registered, no broker mutation occurs, and the dependent waits on the last required predecessor.

For a registered seed, every declared credential is required. `WithRequiredSecretParameter` accepts only an `IResourceBuilder<ParameterResource>` whose resource is marked `Secret`; an absent/invalid required binding fails resource configuration before worker mutation. The package validates identity and secrecy metadata only. The consumer project receives the binding through the exact public Aspire API proven by the spike and performs its own capability-specific check before mutation.

No worker hands an external subject, claim, token, or provider response through AppSurface to another worker. The sample chooses one deterministic route: its consumer-owned local fixture store has a `LocalIdentitySubjectMap` record keyed by the stable local user name `founder`. The identity-bootstrap worker upserts that record with the synthetic nonsecret expected subject `subject-founder-001`; the candidate-fixture worker independently reads exactly one `founder` record, verifies that subject, and then upserts its `CandidateFixture` record by the natural key `candidate:founder`. The consumer owns the fixture-store schema, connection/configuration, and any source/repository artifacts. Missing, duplicate, or unexpected mappings make the fixture worker exit nonzero. `AppSurfaceKeycloakLocalSeedContext` carries none of this data.

The persistent-rerun test injects failure in the candidate-fixture worker after the identity worker has converged its Keycloak broker-alias upsert and `LocalIdentitySubjectMap` write, but immediately before the fixture record upsert. The first run therefore blocks the web project. A complete rerun must yield exactly one broker alias, one `founder -> subject-founder-001` map, and one `candidate:founder` fixture record. AppSurface supplies neither cleanup nor compensation; the consumer workers use natural-key upserts/constraints to converge.

### Lifecycle and failure ownership

| Component | Success | Failure | Cancellation/retry/rerun | Owner |
| --- | --- | --- | --- | --- |
| Realm-ready gate | Existing bounded baseline probe completes. | Stable redacted `ASKEYC` diagnostic for metadata, import, or public-client baseline failure. | Uses the existing readiness timeout. Whether Aspire restarts it and the exact cancellation state are not package contracts until the spike proves them. | AppSurface |
| Consumer seed project | Process exits `0` after its own idempotent work and capability checks. | Process exits nonzero. AppSurface reports only the seed name and `seed-completion` stage; it never parses provider errors or worker output. | The consumer must enforce any timeout by exiting nonzero. A worker that simply hangs remains non-completed, and later resources remain blocked until AppHost cancellation. Retry/restart behavior is not assumed or promised until the spike records the public runtime behavior. Partial mutation is never rolled back by AppSurface: the worker must compensate or converge on rerun. | Consumer |
| Dependent project | Launches only after required predecessor completion succeeds. | Receives no completion signal and stays blocked. | Cancellation, failure, and a hung predecessor keep it blocked; exact public resource states and restart behavior are spike assertions. | Aspire graph |

AppSurface guarantees non-resolution and non-emission of secret values by framework-owned manifest generation, application configuration projection, `ASKEYC` diagnostics, and evidence. Aspire may capture consumer stdout/stderr or dashboard logs; AppSurface does not control those surfaces. Consumer workers and their tests remain responsible for their own output, log, and evidence hygiene. The sample uses the sentinel `LOCAL_TEST_SECRET_SENTINEL`, emits no secret, and scans every available worker-output/dashboard artifact for that sentinel.

Seed registration is legal only under this fail-closed policy, evaluated before the factory, `RealmReady`, or any seed graph materialization: (1) `builder.ExecutionContext.Operation` must equal `DistributedApplicationOperation.Run`; `Publish` and every other operation deny registration regardless of environment. (2) The nonempty `builder.Environment.EnvironmentName` is then matched case-insensitively against `LocalSeedOptions.AllowedEnvironmentNames`, which defaults to `Development`, `Test`, and `Testing`; an unknown environment denies registration. This precedence makes publish/deployment impossible even if a deployment environment happens to be named `Development`. A denied call fails with a local-only `ASKEYC` diagnostic, contributes no deployment/publish annotation or runtime package dependency, and never invokes the factory. The spike must verify these exact public inputs and the generated deployment artifacts contain no seed worker.

### Feasibility gate

Before final API names or implementation tasks are accepted, build an isolated AppHost integration spike using only documented public Aspire APIs. It must prove:

1. Exact public types/annotations that register a finite realm-ready completion gate after Keycloak health.
2. Successful gate completion launches a finite consumer project; gate failure, worker nonzero exit, cancellation, a consumer-enforced timeout, and a hung worker each leave the dependent web project unlaunched/blocked.
3. The actual terminal states and restart behavior for gate, seed, and dependent resources. In particular, prove or reject exactly-once/no-restart claims for success, nonzero exit, timeout, and cancellation; no claim may rely on assumed DCP/private behavior.
4. The documented public `WithEnvironment`-equivalent can bind `Authority`, `RealmName`, and `PublicClientId` to only the returned consumer project, while the parameter path binds one or multiple typed secret parameters only to their declared consumer project. Generated manifests may contain the framework-required parameter name/reference but never a value; web projection, framework diagnostics, and framework evidence contain neither. Capture available consumer stdout/stderr/dashboard artifacts for the sentinel test, but do not elevate them to a framework guarantee. Missing, nonsecret, duplicate-key, and reused-parameter cases must fail before worker launch.
5. Wrapper-local name/owner/predecessor validation works without scanning arbitrary Aspire graph state, including factory throw/null/other-builder/wrong-name failures and proof that none append a registry entry.
6. A persistent-data rerun launches the finite seed again, while the sample injects the defined pre-fixture failure and proves one broker alias, one `founder -> subject-founder-001` map, and one `candidate:founder` record after rerun.
7. The operation-first local-execution policy reads the documented public inputs, permits only `Run` plus the case-insensitive `Development`/`Test`/`Testing` default allow-list (or configured explicit entries), rejects unknown environments without invoking the factory, and excludes registration from publish/deployment artifacts.

The plan is not a proxy for #772 because it controls AppHost startup work rather than request-time DevAuth personas.

### Engineering Review: Full Review

The existing package is a narrow `AppSurfaceKeycloakResource` wrapper around `IResourceBuilder<KeycloakResource>`. `AppSurfaceKeycloakHostingExtensions` constructs static realm evidence and `AppSurfaceKeycloakReadinessProbe` supplies bounded in-process checks; hosting-extension tests already inspect environment annotations through `DistributedApplicationExecutionContext(DistributedApplicationOperation.Run)`.   |                                          +--> seed 1 ProjectResource
  |                                                   |
  |                                                   +--> seed 2 ProjectResource
  |                                                            |
  +------------------------------------------------------------+--> web WaitForCompletion

Secret values: ParameterResource reference -> declared seed project only

#### Engineering Findings and Auto-Decisions

1. **P1, mechanical:** Build a focused public-Aspire spike before the package API. `WaitForCompletion` is documented for finite one-shot projects, but the plan needs a package-owned realm-ready gate whose resource lifecycle is proven rather than inferred. This is a feasibility blocker, not a reason to add a callback runner.
2. **P1, mechanical:** Keep `WithLocalSeed` registration synchronous and append its internal registry record only after factory result, options, identity, name, and parameter validation complete. Aspire graph nodes are not rolled back; an invalid factory must fail the unbuilt graph rather than promise cleanup it cannot perform.
3. **P1, mechanical:** Test the public operation/environment guard before the factory executes, including `Publish` paired with `Development`, unknown environments, and custom allow-list values. This protects the AppHost-only boundary rather than merely omitting deployment documentation.
4. **P1, mechanical:** Treat a hung worker as non-completed until cancellation, not as a package timeout. The consumer worker owns a bounded timeout and must exit nonzero; the spike records the runtime's actual restart/terminal behavior.
5. **P2, mechanical:** Add versioned evidence to the spike: Aspire package version, manifest snippets with values redacted, resource state timeline, and test command. This gives maintainers a cheap upgrade alarm when Aspire behavior changes.
