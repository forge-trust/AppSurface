## Problem Statement

A review of seven AppSurface Durable worker lanes in the downstream Skoolit application found that the core protocol is being consumed safely but the adoption layer asks every host to reconstruct too many decisions.

The safe parts should stay unchanged:

- PostgreSQL remains authoritative for discovery, claims, leases, fences, effect permits, completion, recovery, and history.
- Durable acceptance can share the caller's exact `NpgsqlTransaction` with application state.
- Storage registration is passive. Continuously live workers opt into `AddWorkerHost()`, while externally activated workers call the same bounded `IDurableRuntimePump.RunOnceAsync` primitive.
- Wake requests are payload-free latency hints. The database remains the source of truth.
- Provider-keyed work and reconcile-before-retry work preserve their existing safety contracts.
- Application-owned routes, authorization, activation outboxes, lane selection, reconciliation ordering, and provider policy remain outside AppSurface.

The review found these upstream concerns:

1. Every Skoolit lane treats `SchemaCompatible && EpochCompatible` as its main HTTP success decision. That can return success while the runtime is `NotStarted`, `Stale`, or `Draining`, even though AppSurface documents `Healthy` as the only ready state.
2. Scale-to-zero rollout needs a compatibility gate before activation is enabled. Requiring a current worker heartbeat at that stage would create a startup deadlock: activation is disabled, so no pump can establish the heartbeat required to enable activation.
3. Seven lanes repeat Work registration facts when they construct requests. `DurableWorkRequest` currently accepts nine arguments, including identity, version, encoded payload, provider safety, retry policy, and due time.
4. At least 26 downstream tests directly construct Durable health, pump, registration, and host objects because no first-party Durable testing package exists.
5. `runtime_heartbeat` is keyed by worker identity and has no bounded cleanup path. Process-plus-GUID identities are valid, so normal deployments can accumulate stale rows indefinitely.
6. A standalone worker can emit AppSurface activities without exporting them if its host does not install an OpenTelemetry listener, provider, and exporter.
7. A downstream lane used the pump's `TimeBudget` as a hard cancellation deadline around materialization, enqueue, pump, and reconciliation. The contract actually bounds discovery and the start of additional pump items; it does not promise a hard stop for already-started provider work.
8. Seven private external-activation routes repeat compatible orchestration. The repetition may justify an ASP.NET Core adapter, but only if the adapter remains transport-neutral and does not absorb Cloud Tasks, OIDC, application outboxes, lane policy, or domain recovery behavior.

The program should turn those facts into one supported adoption promise:

> Define the Work once, map the host once, and prove the lifecycle once.

## What Makes This Cool

The useful outcome is not a shorter constructor by itself. One immutable Work definition becomes the source for registration, request creation, test setup, safe diagnostics, and later inspection tooling. A developer should be able to see explicit Work identity, codec, retry, and provider-safety facts without repeating them at each call site or replacing them with runtime method serialization.

The host path becomes equally legible:

```text
store/schema/epoch compatible
        |
        +--> activation may be enabled
        |
        +--> pump heartbeat current and state Healthy
                 |
                 +--> runtime is ready
```

An externally activated host can remain at zero instances until a payload-free wake hint arrives, execute the same bounded pump used by a hosted worker, export the expected activities, and test the whole path without inventing a second state machine.

## Constraints

- Preserve the public-preview protocol and its explicit Work name, version, codec, retry, lease, provider-safety, scope, command, and idempotency facts.
- Do not use reflection, assembly scanning, expression-tree method serialization, or execution of a consumer assembly to discover Work.
- Do not make a notification, HTTP route, broker receipt, or application outbox authoritative for durable execution.
- Do not add a default anonymous management endpoint or a Durable-owned operator control plane.
- Do not make `AddAppSurfaceDurablePostgreSql(...)` start a worker, open a connection, or apply migrations.
- Do not infer that an effect was absent from an exception, timeout, or cancellation. Issue #783 owns explicit typed Work exits; issue #765 owns persisted retry plans and execution deadlines.
- Do not expose connection strings, credentials, payloads, scope IDs, aggregate IDs, trace context, provider responses, or arbitrary exception text through health, diagnostics, manifests, or CLI output.
- Keep liveness host-owned. A Durable store query must not become the reason an orchestrator restarts an otherwise functioning process during a dependency outage.
- Keep application route names, HTTP status policy, authorization policy, materialization, continuation, reconciliation order, lane selection, kill switches, and provider rehearsal outside Durable core.
- Keep every implementation case independently reviewable with full public/internal API documentation, failure-path tests, packed-consumer proof, formatting, and affected solution verification.
- A generated contract manifest may land only if it is derived from the same typed definition without a second hand-maintained identity source and without loading consumer code into the CLI.

## Premises

1. Compatibility for activation and runtime readiness are different decisions. A configured runtime can be compatible before it has started, but it is ready only while its state is `Healthy`.
2. The safest first public change is canonical interpretation of existing health facts, not an AppSurface-owned HTTP endpoint.
3. Repeated identity, version, codec, provider-safety, and default retry facts belong in one immutable typed definition. Per-request scope, command, idempotency key, payload, optional due time, and explicit policy override remain request facts.
4. Testing support must exercise public contracts and real provider composition. It must not implement a fake durable state machine that disagrees with PostgreSQL.
5. Heartbeat cleanup is provider-owned maintenance. Runtime callers should not receive direct table `DELETE` privileges.
6. OpenTelemetry emission and host export activation are separate responsibilities. AppSurface should make correct activation copyable and prove it end to end.
7. A transport-neutral external-activation service is the stable low-level host seam proved by the reference host. An experimental `ForgeTrust.AppSurface.Durable.AspNetCore` adapter may reduce HTTP mapping around it; adapter stabilization requires a second distinct host or adopter and a complete failure matrix.
8. A provider-neutral wake-dispatch interface is premature with only one Cloud Tasks-shaped adopter. Record it as a future evidence gate, not an implementation case.
9. The existing `ForgeTrust.AppSurface.Workers` projection contract and `ForgeTrust.AppSurface.Flow.DurableTask` adapter remain separate products. Adoption docs must distinguish them from native AppSurface Durable.

## Landscape Check

The external convention check supports the health split without changing AppSurface's architecture:

- [ASP.NET Core health checks](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/health-checks?view=aspnetcore-10.0) and [.NET Aspire health checks](https://learn.microsoft.com/en-us/dotnet/aspire/fundamentals/health-checks) distinguish readiness from liveness and let hosts select checks by endpoint.
- [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/) give startup, readiness, and liveness different operational consequences. A wrong mapping can either admit traffic too early or restart a process during a recoverable dependency failure.
- [Quartz ASP.NET Core integration](https://www.quartz-scheduler.net/documentation/quartz-4.x/packages/aspnet-core-integration.html) separates scheduler hosting from health registration, matching AppSurface's passive provider registration.
- [MassTransit testing](https://masstransit.io/documentation/concepts/testing) demonstrates the value of a first-party asynchronous test harness. Its separate overall and inactivity timeouts are also a useful warning against reusing one budget for every phase.
- [MassTransit observability](https://masstransit.io/documentation/configuration/observability) demonstrates copyable `AddSource(...)` and exporter activation for both ASP.NET Core and console hosts.

The first-principles conclusion is narrower than the common framework pattern. AppSurface already exposes the required facts. It should genericise the correct decisions and proof tools while leaving HTTP and deployment consequences with the host.

## Cross-Model Perspective

The independent Codex cold read proposed a Durable "executable contract kit": one `DurableWorkDefinition<TWork, TResult>` feeding registration, request creation, compatibility expectations, tests, telemetry names, diagnostics, optional host mapping, and later CLI/template tooling.

Its strongest formulation was:

> Define the work once, map the host once, prove the lifecycle once.

It recommended MassTransit as the developer-experience benchmark for typed registration, health, instrumentation, testing, and examples, while retaining AppSurface's explicit persisted identity, version, codec, schema, epoch, fence, permit, and recovery model.

It also challenged the original decision to wait for a proven ASP.NET adapter contract before building an adapter. That premise was revised: an explicitly experimental adapter will be used to prove the contract after health interpretation, typed definitions, and the initial testing package exist. Public stabilization remains gated on a second distinct host or adopter.

## Approaches Considered

- **Safety patch train:** rejected as the final program because it fixes health interpretation, heartbeat retention, and documentation but leaves registration, testing, host orchestration, and first-run developer experience fragmented.
- **Staged executable-contract adoption rail:** selected because it completes the adoption path through bounded, dependency-ordered cases and keeps each public commitment reviewable.
- **Host-first proving ground:** retained as a technique inside the selected rail through the reference host and experimental adapter, but rejected as the program order because already-proven health and definition improvements should not wait for the experiment.

## Recommended Approach

Create one tracking case and nine independently shippable child cases, grouped into three tracks. The tracking case owns only the user outcome, boundaries, measurement harness/report, dependencies, and deliberate deferrals. It contains no runtime or package implementation.

- **Track A — operational correctness and storage:** cases 1 and 4. These may ship without the rest of the rail.
- **Track B — contract and proof:** cases 2, 3, and 6. These establish the stable developer path.
- **Track C — adoption tooling:** cases 5, 7, 8, and 9. Cases 5 and 7 are experimental/evidence-gated; cases 8 and 9 consume only accepted stable/public-preview contracts. None blocks Tracks A or B.

The tracking case is a roadmap, not a promise to ship all nine children in one release train. Track A remains independently
valuable. Track B is the minimum competitive wedge: one typed Work, one registration, one authorized activation, and one
deterministic lifecycle proof. Track C children become implementation commitments only when their named dependency and
evidence gates are met. A child that fails its evidence gate is closed with the evidence and decision rather than kept alive
as indefinite preview surface.

### Program invariants

1. A definition is configuration, not durable authority. Acceptance still snapshots exact request facts into PostgreSQL.
2. A scenario is proof, not a simulated provider. Provider-sensitive assertions run against the real PostgreSQL implementation.
3. An external activator is a latency path, not a queue-backed source of truth.
4. A doctor is non-mutating by default and never loads or executes application assemblies.
5. A template teaches the stable path only. Experimental APIs do not enter a template until their graduation gate passes.
6. Definitions carry only today's registration and request defaults. They carry no #765 stored attempt plan or execution deadline and no #783 terminal-exit value.
7. Activation outcomes report only what the host adapter observes. They never infer provider-effect truth, recovery state, or a typed Work exit.

### Normative external-activation flow

Cases 3, 6, 7, and 9 use the same phases and outcomes:

| Phase | Input/condition | Required behavior | Observable outcome |
| --- | --- | --- | --- |
| Health precheck | `Unavailable` | Do not call the pump | `Unavailable` |
| Health precheck | Schema or epoch incompatible | Do not call the pump | `Incompatible` |
| Health precheck | `Draining` | Do not call the pump | `Draining` |
| Health precheck | Compatible `NotStarted`, `Healthy`, or `Stale` | The host may attempt one bounded pump; provider admission remains authoritative | Continue |
| Request admission | Request canceled before pump invocation | Do not call the pump | `CanceledBeforeAdmission` |
| Request admission | Host request budget expires before pump invocation | Do not call the pump | `RequestBudgetExceeded` |
| Provider admission | `IDurableRuntimePumpAdmission` refuses an overlapping, draining, or conflicting pass | Return without treating work as processed | `Busy` |
| Pump | Pump returns its aggregate result, including `HasMore` or failed/suspended counts | Preserve the aggregate result exactly | `Completed` |
| Pump | Pump throws or observes cancellation after invocation starts | Do not infer effect or recovery truth | `PumpFailed` with a bounded safe code, or code-free `PumpCanceled` |

`DurableRuntimePumpRequest.TimeBudget` controls discovery and the start of additional items; it is not the host request deadline. Application materialization, continuation, reconciliation, and cleanup execute outside this generic flow and own their own host-defined cancellation tokens. A host must consult the existing durable record and, after #783, typed exits for provider-effect or recovery truth.

Case 6 owns one transport-neutral public-preview contract used by the direct reference endpoint, the stable direct template, and case 7's ASP.NET adapter:

```csharp
public sealed record DurableExternalActivationRequest(
    DurableRuntimePumpRequest PumpRequest,
    TimeSpan RequestBudget);

public enum DurableExternalActivationOutcomeKind
{
    Unavailable = 0,
    Incompatible = 1,
    Draining = 2,
    Busy = 3,
    CanceledBeforeAdmission = 4,
    RequestBudgetExceeded = 5,
    Completed = 6,
    ActivationFailed = 7,
    PumpCanceled = 8,
    PumpFailed = 9,
}

public sealed record DurableExternalActivationResult(
    DurableExternalActivationOutcomeKind Kind,
    DurableRuntimeHealthState? ObservedHealthState,
    string? ProblemCode,
    DurableRuntimePumpResult? PumpResult);

public interface IDurableExternalActivationService
{
    ValueTask<DurableExternalActivationResult> ActivateAsync(
        DurableExternalActivationRequest request,
        CancellationToken callerCancellation = default);
}
```

The service's object-level dependency surface is limited to `IDurableRuntimeHealth`, `IDurableRuntimePumpAdmission`,
`TimeProvider`, the canonical AppSurface `ActivitySource`, and logging. This does not create a new lightweight package
boundary: `ForgeTrust.AppSurface.Durable.Provider` already references `ForgeTrust.AppSurface.Durable`, which in turn
references Flow, Core, and Workers. Keep that intentional package graph for this rail, version the public-preview Durable
package family together, and add an architecture test proving the activation contracts expose no PostgreSQL, ASP.NET Core,
or application types. Split a contracts-only package only after an independent activator proves that the transitive graph is
a real adoption blocker.

The request-budget clock starts at `ActivateAsync` entry and the linked caller/budget token is passed to both the health read
and the admission-aware pump. The service records an atomic `pumpInvocationStarted` phase immediately before invoking
`IDurableRuntimePumpAdmission`; the name deliberately means invocation, not that provider admission or a durable claim
succeeded. Cancellation classification is deterministic: caller cancellation wins if both sources are canceled before
`pumpInvocationStarted`; otherwise budget cancellation before that point is `RequestBudgetExceeded`; after that point either
or both sources produce `PumpCanceled`. An `OperationCanceledException` with neither source canceled is `ActivationFailed`
before `pumpInvocationStarted` and `PumpFailed` after it, both with `ASDUR407`.

The PostgreSQL implementation uses one internal pass state machine for both public pump entry points:

```text
SlotPending
   │ owns process-local slot
   ▼
RuntimeAdmitted
   │ schema/epoch valid + TryBeginPass succeeds
   ▼
ProviderPassBegun
   │ RunPassAsync returns
   ▼
ProviderPassCompleted
   │ bounded non-caller-cancelable heartbeat bookkeeping
   ▼
Completed
```

`RunOnceAsync` and `TryRunOnceAsync` call that core once; neither preflights and then re-enters the same gate. The legacy
method preserves its overlap exception and other empty-result refusals, while the admission-aware method maps those exact
states to `Refused`. Once `RunPassAsync` returns, caller cancellation cannot rewrite completed provider work as canceled:
successful-sweep bookkeeping uses a non-caller-cancelable token while retaining the provider command timeout. A real
bookkeeping failure remains a pump failure, preserves the original exception, and attempts failure cleanup without masking
it. This is an intentional correction to the legacy post-pass cancellation race and requires release notes plus a regression
test; all other legacy outcomes remain unchanged.

Registration is explicit and single-purpose:

```csharp
services.AddDurableExternalActivation();
```

The extension registers the service, safely supplies `TimeProvider.System` only when the host did not register a clock,
and validates the required health and admission-aware pump dependencies when the service provider is built. It does not map
a route, choose authentication, start a worker, or apply DDL. The Provider package documentation must describe runtime hosts
and external activators as supported consumers while continuing to steer producer-only applications to the adopter package.

`PumpResult` is required only for `Completed`; `ObservedHealthState` is present only after a successful health read.
`ProblemCode` accepts only `ASDUR103`, `ASDUR108`, `ASDUR400`–`ASDUR405`, or new `ASDUR407`. It is required for
`Unavailable`, `Incompatible`, `ActivationFailed`, and `PumpFailed`, and may preserve `ASDUR404`/`ASDUR405` from a
stale health observation on another outcome. Constructor validation rejects every contradictory combination.

| Source observation | Activation result |
| --- | --- |
| Health `Unavailable` | `Unavailable` + `ASDUR103` |
| Health `Incompatible` | `Incompatible` + observed `ASDUR108` or `ASDUR400`–`ASDUR403` |
| Health `Draining` | `Draining` |
| Stale health | Continue to provider admission; preserve observed `ASDUR404`/`ASDUR405` |
| Pump attempt `Refused` | `Busy` |
| Pump attempt `Completed` | `Completed` with the exact result |
| Pump attempt `Unavailable` | `PumpFailed` + `ASDUR103` |
| Pump attempt `Incompatible` after the health precheck race | `PumpFailed` + corresponding `ASDUR108` or `ASDUR400`–`ASDUR403` |
| Caller/budget cancellation | Apply the cancellation-precedence rules above |
| Unexpected non-fatal exception before `pumpInvocationStarted` | Log through the host logger; return `ActivationFailed` + `ASDUR407` |
| Unexpected non-fatal exception after `pumpInvocationStarted` | Log through the host logger; return `PumpFailed` + `ASDUR407` |

`ASDUR106` and `ASDUR109` are item-level durable outcomes, not activation-service exceptions. They remain in authoritative Work state and contribute to the unchanged aggregate pump `Failed` count. The service must not select one item code to represent a pass.

The bounded catch filter excludes `OperationCanceledException`, `StackOverflowException`, `OutOfMemoryException`, and
`AccessViolationException`; cancellation follows the phase rules and fatal process failures are not relabeled as an
HTTP-capable result.

## Copy-Ready Case Drafts

### Case 0: `epic(durable): ship an executable-contract adoption rail`

#### What problem should this solve?

The native Durable protocol is safe and complete enough for production-shaped use, but a real adopter had to repeat operational-state interpretation, Work identity facts, request construction, pump orchestration, OpenTelemetry activation, and test fakes across seven worker lanes. That repetition produced one correctness-level readiness bug and made the supported scale-to-zero path much harder to discover than the protocol itself.

This case coordinates a dependency-ordered adoption rail without moving application deployment policy into AppSurface.

#### Intended outcome

An adopter can:

- define one immutable typed Work contract;
- register an executor without restating contract facts;
- create requests without manually copying name, version, codec, or provider safety;
- distinguish activation compatibility from runtime readiness;
- test host and lifecycle behavior through a first-party package;
- run either a hosted worker or an authorized external activator through the same bounded pump;
- prove AppSurface activities reach an exporter;
- diagnose schema, epoch, heartbeat, and host-composition problems without exposing secrets;
- start from a generated direct-mapping worker template while the adapter remains experimental.

- [ ] Case 1: canonical operational assessments.

- [ ] Case 3: Durable testing package.
- [ ] Case 4: bounded PostgreSQL heartbeat retention.
- [ ] Case 5: configured-target equivalence experiment.
- [ ] Case 6: external-activation service and reference host.
- [ ] Case 7: experimental ASP.NET Core activation adapter.

### Case 1: `fix(durable): make compatibility and readiness decisions explicit`

#### What problem should this solve?

`DurableRuntimeHealthSnapshot` exposes schema compatibility, epoch compatibility, and the runtime states `Healthy`, `NotStarted`, `Stale`, `Draining`, and `Incompatible`. Consumers still have to reconstruct which combinations authorize deployment, permit a pump attempt, and mean the worker is ready. A real consumer used compatibility as readiness in seven endpoints.

The PostgreSQL implementation also maps a timeout or unavailable database to `Incompatible` with the schema-inconsistent problem code. That collapses “the store disproved compatibility” and “the store could not be observed,” which prevents a doctor or host from giving the correct remediation.

Scale-to-zero also proves that readiness cannot replace compatibility: a deployment may need to validate schema and epoch before external activation is enabled and before a pump heartbeat exists.

#### Proposed shape

Add `DurableRuntimeHealthState.Unavailable`. PostgreSQL connectivity and command-timeout failures map to `Unavailable` with the existing `DurableProblemCodes.StoreUnavailable` (`ASDUR103`) only when the caller's token was not canceled; caller cancellation still propagates. Observed schema or epoch mismatches remain `Incompatible`. Under `Unavailable`, compatibility flags are false because compatibility was not established, not because an incompatibility was observed. Document that distinction on the properties and state.

Add three canonical computed properties to `DurableRuntimeHealthSnapshot`:

```csharp
public bool CanEnableActivation =>
    State != DurableRuntimeHealthState.Unavailable
    && State != DurableRuntimeHealthState.Incompatible
    && SchemaCompatible
    && EpochCompatible;

public bool CanAttemptPump =>
    CanEnableActivation
    && State != DurableRuntimeHealthState.Draining;

public bool IsReady =>
    State == DurableRuntimeHealthState.Healthy
    && CanEnableActivation;
```

`CanEnableActivation` is a deployment/configuration gate. `CanAttemptPump` is only a host admission precheck: the provider remains authoritative and may still reject a concurrent pass or identity takeover. It deliberately permits `NotStarted` so cold activation can establish the first heartbeat and permits `Stale` so the provider can apply its existing guarded takeover rules. `IsReady` is the traffic-readiness decision.

Keep the full state and component facts available for diagnostics. Do not add `IsLive`: process liveness belongs to the host and should not require a durable-store query.

Preserve `IDurableRuntimePump.RunOnceAsync` exactly, including its current process-local overlap exception and empty results from other closed-admission paths. Add a separate opt-in admission-aware contract:

```csharp
public enum DurableRuntimePumpAttemptKind
{
    Completed = 0,
    Refused = 1,
    Unavailable = 2,
    Incompatible = 3,
}

public sealed record DurableRuntimePumpAttempt
{
    public DurableRuntimePumpAttempt(
        DurableRuntimePumpAttemptKind kind,
        DurableRuntimePumpResult? result,
        string? problemCode);

    public DurableRuntimePumpAttemptKind Kind { get; }
    public DurableRuntimePumpResult? Result { get; }
    public string? ProblemCode { get; }
}

public interface IDurableRuntimePumpAdmission
{
    ValueTask<DurableRuntimePumpAttempt> TryRunOnceAsync(
        DurableRuntimePumpRequest request,
        CancellationToken cancellationToken = default);
}
```

`Completed` requires a non-null result and null problem code, including for a legitimate empty pass. `Refused` requires both nullable fields to be null. `Unavailable` requires `ASDUR103`; `Incompatible` requires `ASDUR108` or `ASDUR400`–`ASDUR403`; both require a null result. PostgreSQL implements the new interface and:

- returns `Refused` when the process-local pass slot, runtime admission gate, or `TryBeginPassAsync` guard refuses entry;
- translates a non-caller-canceled Npgsql/timeout failure to `Unavailable`;
- translates `DurableRuntimeSchemaException` to `Incompatible` with the existing schema/epoch code;
- lets caller cancellation and unexpected programming failures propagate.

One internal PostgreSQL failure classifier is shared by health observation and admission-aware pump translation. It is an
allowlist with a propagate-by-default arm:

| Evidence | Classification |
| --- | --- |
| `OperationCanceledException` and the caller token is canceled | Propagate caller cancellation |
| Provider command timeout, SQLSTATE `57014` caused by that timeout, Npgsql transient connection failure, SQLSTATE class `08`, `53300`, `57P01`, `57P02`, or `57P03` | `Unavailable` + `ASDUR103` |
| SQLSTATE `42501` while reading runtime health or admission state | `Unavailable` + `ASDUR103`; diagnostics identify permission configuration without exposing SQL |
| `DurableRuntimeSchemaException` or an observed schema/epoch status | `Incompatible` + the existing specific code |
| Undefined relation/function, malformed row shape, invalid enum/value, contradictory result, unrelated `OperationCanceledException`, or any unclassified exception | Propagate; this is a package/data-contract defect, not an outage |

Tests pin every row and the default arm so a future broad `catch (NpgsqlException)` cannot silently turn malformed schema or
programming failures into an outage. Only observed schema/epoch mismatches become `Incompatible`; provider failures that
prevent an observation become `Unavailable`.

Health is explicitly a bounded best-effort observation, not a serializable transaction over schema and worker state. After
schema validation, worker heartbeat and due-dispatch facts are read through one runtime connection and one SQL statement,
using one captured database observation time and one MVCC statement snapshot. A partial read cannot produce a mixed

### Case 2: `feat(durable): add immutable typed Work definitions`

#### What problem should this solve?

Registration and request construction currently repeat Work name, version, codecs, and provider-safety facts. `DurableWorkRequest` accepts nine arguments and relies on callers to copy the registration facts correctly. The runtime still fails safely on mismatches, but the supported path makes drift easy to author.

#### Proposed shape

Add an immutable `DurableWorkDefinition<TWork, TResult>` that owns:

- Work name and version;
- typed Work and result codecs;
- provider-safety class;
- default retry policy for future requests;
- the existing `DurableWorkContractIdentity` derived from name and version.

Per-request facts remain outside the definition:

- scope ID;
- command ID;
- idempotency key;
- typed payload;
- optional due time;
- an explicit retry-policy override when the caller intentionally needs one.

    DurableCommandId commandId,
    string idempotencyKey,

### Case 4: `fix(durable-postgresql): bound runtime-heartbeat retention`

#### What problem should this solve?

`runtime_heartbeat` keeps one row per configured worker identity. Process-plus-GUID identities are valid, and abrupt process loss cannot clean up its own row. No migration, provider path, or operator API currently prunes stale identities, so normal deployment churn can grow the relation without bound.

#### Proposed shape

Add provider-owned, opportunistic heartbeat maintenance:

- default retention horizon: 30 days;
- default maintenance cadence: 24 hours per process;
- default delete batch: 500 rows;
- retention must be from 24 hours through 3,650 days and longer than the configured stale threshold (currently bounded to one hour); provider validation must reject an unsafe relationship;
- never select the caller-declared current worker instance, a row with a heartbeat at or after the cutoff, or a row whose
  heartbeat renewal/takeover already owns the row lock;
- acquire a non-blocking provider advisory lock so only one process performs a batch at a time;
- expose low-cardinality attempted/deleted/failure telemetry without worker identifiers.

The physical model stays one row per `worker_id`; takeover overwrites the row's `worker_instance_id`. This case bounds stale
worker identities, not a history of worker generations. Process-plus-GUID deployments create many distinct worker IDs and
therefore exercise retention, while repeated generations of one stable worker ID exercise overwrite/takeover races.

The current-worker arguments are a correctness guard against accidental self-pruning, not an authenticated security
boundary. Migration 0005 already documents and enforces that the isolated runtime credential is trusted for the entire
unscoped heartbeat table through `USING (true)` and `WITH CHECK (true)`. Granting this function lets that same trusted
principal delete only old rows in bounded batches. A compromised runtime credential can already forge heartbeat metadata;
it can now also prune all eligible stale rows through repeated valid calls. Document that blast radius explicitly, test
arbitrary exclusion arguments and repeated batches, and keep the credential unreachable from request-controlled code. A
dedicated maintenance principal is a separate follow-up if an adopter cannot accept that existing trust model.

Use exact migration `0010_runtime_heartbeat_retention.sql`. It is applied while holding the existing package migration lock and contains:

```sql
SET LOCAL lock_timeout = '5s';

CREATE INDEX ix_runtime_heartbeat_retention
    ON appsurface_durable.runtime_heartbeat (last_heartbeat_at, worker_id);

CREATE FUNCTION appsurface_durable.prune_runtime_heartbeats(
    p_retention interval,
    p_maximum_rows integer,
    p_current_worker_id text,
    p_current_worker_instance_id uuid)
RETURNS integer
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, appsurface_durable, pg_temp
AS $$
DECLARE
    v_cutoff timestamp with time zone;
    v_deleted integer;
BEGIN
    IF p_retention IS NULL
       OR p_retention < interval '24 hours'
       OR p_retention > interval '3650 days' THEN
        RAISE EXCEPTION 'p_retention must be between 24 hours and 3650 days.'
            USING ERRCODE = '22023';
    END IF;
    IF p_maximum_rows IS NULL OR p_maximum_rows NOT BETWEEN 1 AND 5000 THEN
        RAISE EXCEPTION 'p_maximum_rows must be between 1 and 5000.'
            USING ERRCODE = '22023';
    END IF;
    IF p_current_worker_id IS NULL
       OR length(p_current_worker_id) NOT BETWEEN 1 AND 200
       OR p_current_worker_id !~ '^[A-Za-z0-9._:-]+$' THEN
        RAISE EXCEPTION 'p_current_worker_id is invalid.'
            USING ERRCODE = '22023';
    END IF;
    IF p_current_worker_instance_id IS NULL
       OR p_current_worker_instance_id =
          '00000000-0000-0000-0000-000000000000'::uuid THEN
        RAISE EXCEPTION 'p_current_worker_instance_id is invalid.'
            USING ERRCODE = '22023';
    END IF;

    -- Two-int advisory namespace "ASDU"/"RHBR"; it is distinct from the
    -- one-bigint schema migration lock and from hashed per-scope locks.
    IF NOT pg_try_advisory_xact_lock(1095976021, 1380467282) THEN
        RETURN 0;
    END IF;

    v_cutoff := clock_timestamp() - p_retention;
    WITH candidates AS
    (
        SELECT heartbeat.worker_id, heartbeat.worker_instance_id
        FROM appsurface_durable.runtime_heartbeat AS heartbeat
        WHERE heartbeat.last_heartbeat_at < v_cutoff
          AND NOT
          (
              heartbeat.worker_id = p_current_worker_id
              AND heartbeat.worker_instance_id = p_current_worker_instance_id
          )
        ORDER BY heartbeat.last_heartbeat_at, heartbeat.worker_id
        FOR UPDATE SKIP LOCKED
        LIMIT p_maximum_rows
    )
    DELETE FROM appsurface_durable.runtime_heartbeat AS heartbeat
    USING candidates
    WHERE heartbeat.worker_id = candidates.worker_id
      AND heartbeat.worker_instance_id = candidates.worker_instance_id
      AND heartbeat.last_heartbeat_at < v_cutoff;

    GET DIAGNOSTICS v_deleted = ROW_COUNT;
    RETURN v_deleted;
END;
$$;

REVOKE ALL ON FUNCTION appsurface_durable.prune_runtime_heartbeats(
    interval, integer, text, uuid) FROM PUBLIC;
```

The migration must run as the documented `migration_owner_role`; the schema tests assert that this role owns the function after migration and role-recipe application. The role recipe must:

- add `'appsurface_durable.prune_runtime_heartbeats(interval, integer, text, uuid)'::regprocedure` to the runtime role's exact function allowlist;
- execute `REVOKE ALL ON FUNCTION ... FROM PUBLIC`, dispatcher, and retention-operator roles;
- execute `GRANT EXECUTE ON FUNCTION ... TO :runtime_role`;
- continue rejecting effective function privileges outside the complete allowlist;
- leave table `DELETE`, ownership, grant options, and role membership prohibited.

The role-recipe delta is explicit:

The function intentionally ignores `pass_active` because an abruptly lost process may leave that flag true. PostgreSQL
[documents `SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html) as a queue-like contention primitive,
not a consistent general-purpose read; that is appropriate
here because another maintenance pass may reconsider skipped rows. A renewal/takeover that locks first is skipped and
survives. If pruning locks the old stale identity first, a later renewal may wait only within its existing command timeout;
the old identity may be deleted, and takeover must retry/re-register safely. Do not claim that both lock orderings preserve
the old row or that pruning can never delay a later writer. The exact identity join and one cutoff prevent a different
generation from being deleted after replacement. The two-int advisory namespace avoids collision with the existing
one-bigint migration lock; lock refusal is a successful no-op.

The runtime calls the function at most once per configured cadence after it has established its current heartbeat. The
command uses the provider's existing bounded command timeout and cancellation; the maintenance advisory lock never waits,
prelocked candidate rows are skipped, and a timeout rolls back the entire batch. The provider remains safe if maintenance
never runs; cleanup is capacity management, not correctness.

The package migration lock is also bounded. Replace blocking `pg_advisory_lock` in both `ApplyAsync` and generated scripts
with one shared `pg_try_advisory_lock` retry contract: 100 ms bounded-jitter retries, a 30-second default deadline, caller
cancellation, and a stable operator-safe timeout diagnostic containing only elapsed time and the fixed lock namespace.
Never emit another session's query, application name, host, or credentials. `lock_timeout` does not bound advisory-lock
acquisition; it remains in migration 0010 to bound the ordinary index's table-lock wait.

Deployment uses an explicit two-phase gate:

1. Pack and pre-stage the schema-10-capable package while activation stays on the old deployment.
2. Prove in CI that the immediately previous package binary remains compatible with schema 10. Migration 0010 is additive,
   so it intentionally preserves the metadata range that includes that prior reader/writer version.
3. Drain and stop old runtimes, run `durable schema preflight`, acquire the bounded migration lock, apply 0010 as migration
   owner, reapply the exact role recipe, and rerun preflight as the runtime role.
4. Deploy the new binary and resume activation only after compatibility, owner, role, and health checks pass.

If the strict previous-binary test fails, the release must raise migration 0010's minimum reader/writer version to 10 before
publication and switch the post-commit recovery instruction to activation-closed roll-forward only. If it passes, a failed
new-package deployment may safely redeploy that exact prior binary; arbitrary older binaries are never inferred compatible.
No down-migration is supported.

Preflight flags 0010 as a downtime migration while pending. Afterward it verifies function owner, `prosecdef`, the exact
`proconfig` search path including `pg_temp` last, `PUBLIC` revoke, runtime execute grant, and index structure. Index
verification reads `pg_index`, `pg_class`, `pg_attribute`, and operator-class catalogs; it does not compare
`pg_get_indexdef` formatting across PostgreSQL releases.

### Case 5: `design(durable-postgresql): prove configured-target equivalence without exposing credentials`

#### What problem should this solve?

#### Proposed shape

### Case 7: `feat(durable-aspnetcore): prototype authorized external activation`

#### What problem should this solve?

Seven downstream routes repeat the same outer sequence around a bounded pump, but they also contain application-owned materialization, continuation, reconciliation, and deployment policy. AppSurface needs evidence that a thin ASP.NET Core adapter can remove the mechanical repetition without taking ownership of those policies.

#### Proposed shape

Add an explicitly experimental `ForgeTrust.AppSurface.Durable.AspNetCore` package. The mapping API must require:

- an explicit route pattern;
- an explicit host authorization policy;
- a bounded transport-neutral activation request or factory;
- an application response mapper over a transport-neutral activation outcome.

Consume case 6's public-preview `IDurableExternalActivationService`, request, result, outcome enum, cancellation precedence, and failure mapping unchanged. This case owns no second health-to-outcome or exception-to-code mapping. Only the ASP.NET package and mapping carry the .NET `[Experimental]` diagnostic until the graduation gate passes.

The ASP.NET mapping is a thin transport layer:

```csharp
RouteHandlerBuilder MapDurableExternalActivation(
    this IEndpointRouteBuilder endpoints,
    string pattern,
    string authorizationPolicy,
    Func<HttpContext, DurableExternalActivationRequest> requestFactory,
    Func<HttpContext, DurableExternalActivationResult, IResult> responseMapper);
```

It resolves the pre-composed service, passes `HttpContext.RequestAborted`, invokes the response mapper, and applies `RequireAuthorization(authorizationPolicy)`. It has no before/after/recovery participant model. Application materialization, continuation, reconciliation, cleanup, outbox acknowledgement, and domain transitions compose outside this call with host-owned tokens and errors.

The mapping returns `RouteHandlerBuilder` so the host can add metadata and stricter authorization. It must never default to anonymous access.

The canonical result remains payload-free and carries no scope/aggregate identity, provider response, arbitrary exception, HTTP status, or recovery verdict. The host's response mapper decides status codes and body shape. Unexpected request-factory or response-mapper exceptions remain ordinary host exceptions; the adapter does not relabel application failure as Durable state.

#### Graduation gates

The package remains experimental until:

1. the reference host and one distinct host/adopter use the same public contract;
2. the representative downstream lane is first mapped directly over case 6's service, then through the adapter; the measured adapter region shrinks by at least 30% from that same-lane direct baseline and remains at or below 25 nonblank lines, without importing application types;
3. every row in the normative activation flow, including unavailable health, stale takeover, busy admission, exhausted request budget, pump `HasMore`, outer cancellation, and cancellation after pump invocation, has deterministic tests;
4. no required composition point needs a Cloud Tasks, OIDC, lane, outbox, cleanup, or domain-state concept;
5. security review confirms explicit authorization and bounded diagnostic output;
6. API review confirms that the transport-neutral result is useful outside HTTP.

If those gates fail, keep the proof code example-internal or remove the package before stable publication.

#### Acceptance criteria

- Mapping without a named authorization policy fails during startup with an actionable diagnostic.
- `RequestBudget` and pump `TimeBudget` are validated for positive bounds and documented ownership; pump `TimeBudget` is never converted into the outer hard deadline.
- Case 6's service contract tests remain the sole proof of phase order, cancellation precedence, and exception mapping; this package neither copies nor overrides them.
- Endpoint tests feed each canonical result from a fake service and prove the exact same value reaches the host response mapper without reclassification.
- Cancellation tests prove `HttpContext.RequestAborted` is forwarded as the service caller token; request-budget ownership remains in the canonical service.

### Case 8: `feat(cli): add non-mutating Durable runtime doctor diagnostics`

#### What problem should this solve?

Durable startup, health, CLI, logs, and tests expose related facts but do not give an adopter one non-mutating diagnosis containing the problem, likely cause, safe fix, and canonical documentation link. The first doctor should diagnose the connected store and runtime configuration only. Definition discovery, host telemetry configuration, and physical target equivalence require evidence the CLI does not possess.

#### Proposed shape

Extend the existing `appsurface durable` command family with:

```console
appsurface durable doctor \
  --connection-env APPSURFACE_DURABLE_CONNECTION \
  --runtime-epoch-env APPSURFACE_DURABLE_RUNTIME_EPOCH \
  [--worker-id <privacy-safe-id> --stale-after <duration>] \
  [--timeout <duration>] \
  [--format text|json]
```

`--connection-env` reuses the existing schema-command behavior and defaults to `APPSURFACE_DURABLE_CONNECTION`; no connection-string argument is accepted. For doctor, it must resolve to the restricted runtime-role credential, not migration owner. `--runtime-epoch-env` defaults to `APPSURFACE_DURABLE_RUNTIME_EPOCH` and must resolve to a nonempty GUID. `--worker-id` and `--stale-after` must appear together; the latter is the host's actual configured stale threshold, not a CLI guess. `--timeout` defaults to ten seconds and accepts one second through two minutes. `--format` defaults to `text`.

The command may read:

- schema compatibility and migration status;
- configured and active runtime epoch;
- provider StoreId or equivalent authoritative connected-store identity;
- the selected worker's heartbeat age and state, when a worker ID is supplied;
- whether migration 0010's heartbeat-retention capability is installed.

Retention capability is not inferred from migration number alone. One bounded catalog query resolves exact regprocedure `appsurface_durable.prune_runtime_heartbeats(interval,integer,text,uuid)` and verifies:

- the function owner equals the `appsurface_durable` schema owner;
- `prosecdef` is true;
- `proconfig` contains exactly the required fixed search path;
- the current runtime credential has `EXECUTE`;
- the function ACL has no `PUBLIC` grantee and grants no grant option to the current credential;
- `ix_runtime_heartbeat_retention` exists on the exact table and `pg_get_indexdef` matches `(last_heartbeat_at, worker_id)`.

The command reports capability unavailable if any invariant fails; it never calls the pruning function. Existing role checks reject a current credential that owns Durable objects, has `BYPASSRLS`, or holds grant options, with guidance to supply the runtime role.

Heartbeat observation uses one SQL statement that captures `clock_timestamp()` once as `observed_at_utc` and computes nonnegative age from that same value. Rendering receives an immutable observation and never calls the process clock. Unit snapshots use a fixed observation; PostgreSQL integration tests assert the database timestamp within a bounded wall-clock range rather than snapshotting a live timestamp.

The command does not accept or compare a second connection string, infer host OpenTelemetry listener/exporter state, or inspect Work definitions. A later manifest case may be designed only if case 2 can produce a deterministic compile-time artifact from the same source facts without loading or executing a consumer assembly. That future case is not part of this rail's success.

Use one stable diagnostic descriptor model across health guidance, CLI output, logs, testing assertions, and `troubleshooting/durable-diagnostics.md`:

```text
code
problem
likely cause
safe fix
canonical docs link
```

Every text finding ends with the exact next applicable command, such as rerunning `durable schema preflight`, supplying the
paired worker arguments, or invoking the generated application's end-to-end verifier. JSON output carries the same next
action and documentation URL as stable fields. A clean doctor result says “store/runtime checks passed” rather than “worker
ready,” and links to the application-composition verifier because the doctor deliberately cannot prove registration,
authorization, activation routing, or exporter delivery.

#### Acceptance criteria

- The default command is non-mutating and never applies migrations, rotates epochs, drains workers, retries Work, or changes retention.
- Human and JSON output are deterministic, bounded, secret-free, and covered by snapshots.
- With worker inputs, diagnostics distinguish not-started/worker-not-found, current, stale, draining, schema incompatible, epoch incompatible, retention capability absent, and unavailable database. Without worker inputs, the command makes no heartbeat/readiness claim.
- Exit code 0 means no finding in the requested checks, 2 means an actionable compatibility or worker finding, 3 means invalid input, and 4 means the dependency was unavailable. Unexpected CLI failure retains the CLI's existing general failure code.
- Raw connection strings, credentials, payloads, scope/aggregate IDs, arbitrary exceptions, and trace context never appear.
- Tests prove the exact connection/epoch/optional-worker inputs from command line and environment, precedence rules, bounded timeouts, cancellation, unavailable dependencies, and no interactive prompts.
- Catalog mutation tests independently break function signature, owner, security-definer flag, search path, runtime execute privilege, `PUBLIC` ACL, grant option, index presence, and index shape; each produces one bounded diagnostic without invoking maintenance.
- Text and JSON snapshot tests inject one fixed database observation so heartbeat age and timestamps are byte-deterministic.
- Documentation states what the doctor cannot prove, including registered Work definitions, physical target equivalence, provider-effect truth, application authorization, and Activity listener/exporter delivery.

#### Dependencies and coordination

Depends on cases 1 and 4. It does not depend on definitions, target comparison, the reference host, or the experimental adapter.

#### Section 4 — Performance

1. Health remains constant work, not N+1, but current worker and due facts use separate connections. Case 1 combines them
   into one statement snapshot after schema validation. No cache is added because readiness and admission require current
   state and the existing query is bounded.
2. Migration lock acquisition currently has no deadline. The shared try-lock contract bounds runtime and generated-script
   waits to 30 seconds, supports caller cancellation, and avoids sensitive holder diagnostics.
3. Retention uses one ordered index, non-blocking maintenance lock, `SKIP LOCKED`, and bounded batches. Release proof uses
   100,000 stale plus 1,000 recent rows and records query plan, buffers, duration, and heartbeat p50/p95 under both lock
   orderings. Public defaults remain evidence-gated.
4. Activation adds one health observation, one provider attempt, and one low-cardinality activity. It introduces no polling
   loop, queue, materialization, or unbounded collection. The host request budget includes health time; pump discovery keeps
   its separate item/time bounds.
5. Template speed is measured with separate cold and primed clocks. The primed release target remains median under two
   minutes and maximum under three across five runs; cold setup is reported, not hidden.

Performance issues found: **3**. All have a measurable release gate; no speculative cache or parallel pump is added.
