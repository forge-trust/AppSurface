## Scope Relationship

This document is the implementation design for [issue #807](https://github.com/forge-trust/AppSurface/issues/807). It extends the approved LocalSecrets direction from `andrew-main-design-20260612-021329-local-secrets-autoplan.md`: configuration keeps logical-key continuity across file, local, remote, and environment sources while secret failures remain fail-closed and diagnostics remain value-safe.

The issue began as Google Secret Manager child patching for object-valued `Config<T>`. The consumer evidence supports a stronger center: a configuration model marks secret destinations with `Secret<T>`, and trusted file configuration declares the secret key, optional provider constraint, version, and static activation beside the surrounding non-secret values.

No implementation is part of this office-hours output.

## Problem Statement

AppSurface currently resolves an entire `Config<T>` from one ordinary provider and then lets only `EnvironmentConfigProvider` patch child members. `GoogleSecretManagerConfigProvider` can resolve an exact code-configured logical mapping, but it cannot satisfy one secret child inside an object assembled from file or LocalSecrets.

Applications therefore duplicate configuration paths outside the configuration they describe. Skoolit has two checked-in secret-mapping manifests whose rows repeat:

- the AppSurface dotted path;
- the equivalent `IConfiguration` colon-delimited path; and
- a pinned Google Secret Manager version resource.

Skoolit also owns a manifest parser and validator, translates every row into `MapSecret(...)`, and maintains an `IConfiguration` bridge that checks the corresponding `__` environment variable before AppSurface. This is working application code whose only purpose is to supply declaration, precedence, and compatibility behavior missing from the framework.

There is a second operational problem. Applications need to commit the intended secret configuration before every referenced resource exists. Treating “not found” as optional would hide misspellings, incomplete provisioning, deleted versions, and IAM failures. The design needs a deliberate disabled state that performs no access to that declared resource without weakening enabled fail-closed behavior.

## What Makes This Cool

The configuration file becomes an inspectable secret plan without containing a secret value:

```csharp
public sealed class ServiceOptions
{
    public required string Endpoint { get; init; }

    public required Secret<string> ApiKey { get; init; }
}
```

```json
{
  "Service": {
    "Endpoint": "https://service.example",
    "ApiKey": {
      "key": "demo-key",
      "version": "4",
      "enabled": false
    }
  }
}
```

The C# type identifies the sensitive destination. The adjacent file object identifies what should eventually satisfy it. AppSurface can validate the path and declared shape without retrieving a payload, explain whether the reference is disabled, resolved, environment-supplied, or failed, and later support deployment preflight from the same compiled plan.

The real measure of success is deletion: Skoolit should be able to retire its repeated path mapping, mapping translator, and environment-precedence bridge as it adopts the framework contract.

## Consumer Evidence

- Skoolit's web manifest currently contains dozens of full numeric Google Secret Manager resources and duplicate dotted/colon paths.
- Its durable-worker manifest repeats mappings per worker lane.
- `RuntimeConfigurationProfile` performs application-owned schema, path, duplicate, and pinned-version validation before calling `options.MapSecret(...)`.
- `RuntimeConfigurationBridge` reimplements environment-first resolution for consumers still on `IConfiguration`.
- Skoolit already gates some mappings behind feature activation because referenced resources do not exist yet.

This is not hypothetical convenience work. A real adopter independently built the declaration and compatibility layers proposed here.

## Constraints

1. AppSurface-controlled source files, audit output, diagnostics, exception text, logging, `ToString()`, debugger display, and default System.Text.Json serialization of `Secret<T>` must never reveal a secret payload.
2. Inline references are recognized only at destinations typed as `Secret<T>`. Ordinary objects with `key`, `version`, `enabled`, or `provider` properties remain ordinary objects.
3. The first release supports `Secret<T>` only when `T` is a scalar type already accepted by `ConfigValueConverter`. Arrays, collection elements, dictionaries, object-valued secret payloads, and reference fragments are rejected. Ordinary arrays, collections, and dictionaries may remain elsewhere in the containing root and continue through normal binding and validation; only placing a `Secret<T>` destination inside them is unsupported.
4. File declarations are explicit. The feature adds no secret enumeration, naming convention, inference, interpolation, or implicit environment-variable expansion.
5. An enabled declaration claims its exact destination path. Missing, denied, unavailable, invalid, ambiguous, provider, and conversion failures remain terminal unless an exact valid environment value rescues that same path.
6. A sibling environment override cannot rescue another path's failure. Every unrescued secret failure blocks delivery of the requested object.
7. A disabled declaration makes no `IConfigSecretProvider.Resolve` call for that reference. Base-source selection may still occur. Disablement is not equivalent to optional lookup and does not convert an enabled missing result into fallback.
8. Direct environment root values retain their existing highest-priority behavior. Descendant environment values remain the last composition layer.
9. Existing direct `MapSecret(...)` behavior remains source-compatible and behavior-compatible when it does not overlap an inline declaration.
10. Runtime and audit execute the same composition algorithm. Audit may run it independently, but it must not maintain a second interpretation of precedence, rescue, or failure.
11. The core Config package must not depend on Google types. Secret-provider contracts are provider-neutral; Google-specific resource validation and access remain in the Google package.
12. No new package, background refresh service, secret writer, IAM manager, deployment command, or UI is introduced.
13. All changed public and internal APIs require XML documentation, package guidance, decision guidance, and pitfall guidance. Changed branches require success and failure verification without reflection.

## Premises

1. The right abstraction is a typed secret destination plus a declarative reference, not a Google-specific object patcher.
2. `Secret<T>` is required for every inline declaration. This makes sensitivity and activation visible to application code and prevents an ordinary scalar property from silently becoming secret-backed.
3. The reference fields sit directly on the `Secret<T>` property. A nested `$secret` object would duplicate the type discriminator without adding safety.
4. `provider` is an optional constraint. Omitting it asks every compatible registered secret provider; specifying it restricts resolution to that one provider.
5. Providerless lookup is set-based, not priority-based. It succeeds only when exactly one provider resolves and no provider reports an uncertain terminal failure.
6. Static `enabled: false` is sufficient for the first release. Conditional expressions, feature-key dependencies, and `enabledWhen` are deferred.
7. The file declaration and its destination type can be compiled into a value-free plan before secret access. Payload conversion and runtime model validation still require resolution.
8. File and LocalSecrets may supply the lower object, enabled remote references patch exact `Secret<T>` children, and environment values patch last.
9. Secret sensitivity belongs to the destination. It remains sensitive even when an environment value is the winner.

## Decisions

- Add a provider-neutral `Secret<T>` runtime value in `ForgeTrust.AppSurface.Config`.
- Add provider-neutral secret reference and resolver contracts in the core Config package; the Google package implements the first remote resolver.
- Use direct descriptor fields: `key`, optional `version`, optional `provider`, and optional `enabled`.
- `enabled` defaults to `true`.
- A checked-in disabled declaration should still identify the intended key and version. File-layer replacements must repeat the complete descriptor.
- The canonical Google provider id is a documented stable constant owned by the Google package, not a free-form application convention.
- Provider ids are unique case-insensitively. Duplicate registrations fail during configuration validation.
- A specified provider must be registered and must accept the descriptor shape, including when the reference is disabled. Validation is local and performs no secret read.
- A providerless disabled declaration is compiled and reported without resolving. Local validation still requires at least one compatible registered provider, but uniqueness is enforced only when enabled.
- Only `Unclaimed` and `Missing` allow providerless lookup to continue.
- `AccessDenied`, `Unavailable`, `InvalidReference`, `ProviderFailed`, and equivalent uncertain results are terminal even if another provider returns a value.
- Exactly one clean success resolves. Zero-success states use deterministic classifications defined below, and multiple successes fail as ambiguous. Registration order never chooses a winner.
- Conversion runs once after a unique provider succeeds.
- `MapSecret(...)` remains available. A legacy mapping and an inline declaration may not target equal, ancestor, or descendant paths within the same requested root.
- Secret descriptors are atomic across file layers. A higher file layer replaces the whole descriptor rather than deep-merging `key`, `version`, `provider`, and `enabled`.
- Existing Google conventions are not extended to discover child references. A convention may still claim the requested root through its current behavior; that root claim conflicts with any descendant secret declaration.
- Standalone deployment preflight is enabled by the plan architecture but deferred from issue #807.
- A direct environment root is a complete emergency override. It binds and validates without compiling file declarations, resolving secret providers, or applying environment descendants.
- When no inline descriptor exists, a `Secret<T>` destination is enabled by default and may be satisfied by a recognized secret-capable lower source or an exact environment value. No reference lookup occurs because no key was declared.

## Public Runtime Contract

`Secret<T>` is immutable outside the configuration engine. Its minimum public behavior is:

```csharp
public sealed class Secret<T>
    where T : notnull
{
    public Secret();

    public bool Enabled { get; }

    public bool HasValue { get; }

    [JsonIgnore]
    public T Value { get; }

    public bool TryGetValue([MaybeNullWhen(false)] out T value);

    public string? ResolvedProvider { get; }
}
```

Behavior:

- `Enabled` reports whether the secret destination is active. It is false only when the winning inline declaration explicitly sets `enabled: false`; a descriptor-absent destination defaults to true. It does not mean a value is present.
- `HasValue` reports whether composition produced an effective value.
- `Value` returns the effective value or throws a value-safe `InvalidOperationException` when `HasValue` is false.
- `TryGetValue` supports optional-feature checks without exceptions.
- `ResolvedProvider` reports the winning source identity: an `IConfigSecretProvider` uses its canonical id, while a lower base or environment value uses the existing `IConfigProvider.Name`. It is null when no value resolved.
- The configured provider constraint is plan and audit metadata. The effective source may be that provider, a secret-capable lower source, or environment depending on activation and precedence; an exact environment value may win even when the declaration is enabled.
- `ToString()` reports only enabled/disabled, has-value, and provider metadata. It never formats `Value`.
- `Value` and its backing storage carry `[JsonIgnore]`, and the package registers no converter that serializes them. Documentation still warns that third-party serializers and direct access can expose a consumed secret.
- A null contribution never sets `HasValue`. An empty or whitespace string is a present `string` value when `ConfigValueConverter` accepts it; normal validation may reject it.
- `T` has a `notnull` contract. A provider returning null is invalid, and a JSON null never represents a successful secret even if a caller suppresses nullable warnings and writes `Secret<string?>`.
- The public parameterless constructor creates the safe empty state: `Enabled=true`, `HasValue=false`, and `ResolvedProvider=null`. It lets model initializers and `Config<T>.DefaultValue` construct a non-null destination without supplying secret material.
- Value-bearing and disabled factories are internal. The configuration engine materializes one non-null `Secret<T>` wrapper for every supported discovered destination in a resolved root. Application code can create an empty destination but cannot forge a resolved, environment-supplied, provider-supplied, or file-disabled state.

The redaction guarantee ends at the AppSurface boundary. Application code and provider implementations are trusted because they must eventually handle the plaintext to use or return it. Reflection, a third-party serializer that ignores `[JsonIgnore]`, a debugger inspecting private fields, or application logging of `Value` can disclose it. Managed strings also cannot be reliably zeroed. AppSurface minimizes copies and retention, never places payloads in the compiled plan or audit trace, and documents safe consumption, but it does not claim process-memory secrecy.

The type deliberately separates activation from availability:

| Declaration | Effective source | `Enabled` | `HasValue` |
|---|---|---:|---:|
| enabled, provider succeeds | secret provider | true | true |
| enabled, provider fails, exact environment rescue succeeds | environment | true | true |
| disabled, environment supplies migration value | environment | false | true |
| disabled, no lower or environment value | none | false | false |
| absent, LocalSecrets supplies a non-null value | LocalSecrets | true | true |
| absent, exact environment value supplies a non-null value | environment | true | true |
| absent, no source supplies a value | none | true | false |

This permits a staged Skoolit migration, but the minimum safe migration unit is one requested configuration root rather than one property. Register the intended provider, convert every mapped destination inside that root to `Secret<T>` or remove mappings that are outside the new composition contract, replace overlapping claims with complete disabled references in the same reviewed change, keep current environment values temporarily, and provision the remote resources. Then enable the references and run a bounded verification deployment with the exact environment rescues removed so Google is the effective source before calling the migration complete. A disabled reference or an enabled reference whose effective source remains environment does not prove remote readiness.

### Supported destination object model

The new composition path owns one explicit `ConfigCompositionJsonContract`. It contains an immutable structural serializer profile cloned from the platform defaults before first use plus cached value-free type metadata. Plan discovery uses that structural profile. Each execution creates a short-lived `JsonSerializerOptions` clone from the same structural settings, installs an invocation-owned `Secret<T>` converter factory that captures only that execution's binding context, makes the clone read-only, binds once, and releases the clone and slot references. Cached plans are keyed by structural-contract identity; invocation options and converters are never cached or shared. The contract is never `JsonSerializerOptions.Default` itself because the platform default instance cannot be mutated. The first release does not accept DI-provided serializer options, a custom naming policy, or a generated serializer context. File, LocalSecrets, Google raw-root, direct environment-root, plan discovery, audit topology, and final composition binding use the same naming and metadata policy after they enter the new path. Existing roots without `Secret<T>` keep their current provider-specific conversion paths.

The compiler discovers members from `System.Text.Json` metadata produced by the shared structural contract. Execution metadata must be behaviorally equivalent but is invocation-owned so its converters can safely capture that execution:

- public properties, inherited properties, records, primary-constructor parameters, init-only properties, and `[JsonInclude]` fields are supported when the default System.Text.Json contract can bind them;
- `[JsonPropertyName]`, `[JsonInclude]`, and ordinary default scalar converters are honored because discovery and binding share the same metadata;
- private setters work only when the default System.Text.Json contract exposes them;
- a custom converter for the containing object, polymorphic contract that hides the concrete property graph, extension-data destination, or member name containing `.` or `:` is rejected when it prevents deterministic discovery;
- a custom converter for inner scalar `T` is outside the first release; `ConfigValueConverter` is the conversion authority; and
- a `Secret<T>` member inside an array, collection, dictionary, or object-valued `Secret<T>` is rejected with a stable unsupported-destination diagnostic.
- `ConfigStruct<T>` roots containing `Secret<T>` are rejected in the first release; supported composition roots use `Config<T>` and reference types; and
- recursive member paths that can reach a secret destination are rejected. Discovery uses an active traversal stack, not a global visited-type set, so repeated acyclic occurrences of the same type remain supported. The compiler enforces the existing audit-style graph bounds with explicit maximum depth and node/slot counts and reports a stable no-I/O diagnostic on self-recursive, mutually recursive, or over-budget graphs.

`DefaultConfigManager.GetValue<T>` detects the supported `Secret<T>` graph and delegates that request to the shared composition engine after direct-root environment probing. `Config<T>.Init` remains unchanged and receives either the final typed `T` or `null`. Final composition binding uses an invocation-owned binding context passed by constructor to that invocation's internal converter factory; opaque slot ids map to already-classified `Secret<T>` instances. The context is never ambient static state, `AsyncLocal`, or shared mutable singleton state, so concurrent runtime/audit executions and nested serializer calls cannot cross-contaminate payloads. A `try/finally` releases all slot references after success or exception. Payloads are never inserted into the value-free plan or a format-capable declaration node. This is a new binding stage for opted-in roots, not an extension of the current provider-returned typed-object path.

## File Declaration Contract

Canonical providerless form:

```json
{
  "ApiKey": {
    "key": "demo-key",
    "version": "4"
  }
}
```

Provider-constrained form:

```json
{
  "ApiKey": {
    "provider": "google-secret-manager",
    "key": "demo-key",
    "version": "4",
    "enabled": true
  }
}
```

Static disabled form:

```json
{
  "ApiKey": {
    "key": "demo-key",
    "version": "4",
    "enabled": false
  }
}
```

Rules:

- `key` is required and nonblank.
- `version` is optional at the core contract because provider capabilities differ. A provider may require it, reject it, or apply an existing explicit provider default. Google keeps its current short-id, full-resource, default-version, alias, and production-safety validation.
- `provider` is optional and matches a canonical registered provider id case-insensitively.
- `enabled` is optional and defaults to `true`.
- Descriptor member names use ordinal case-insensitive matching so normal System.Text.Json naming behavior is unsurprising. Unknown members, wrong member types, and duplicate members differing only by case fail plan compilation.
- The descriptor is interpreted only because the destination is `Secret<T>`.
- Before any provider validation or resolution, the compiler requires inner `T` to be one of the existing `ConfigScalarTypes` shapes, including supported nullable scalar forms. Object, array, collection, dictionary, and nested-secret payloads fail with `secret-destination-type-unsupported` and make zero provider calls.
- A plain file scalar at a `Secret<T>` path is rejected. Checked-in configuration cannot masquerade as a secret source.
- A value arriving from a recognized secret-capable base source such as LocalSecrets, or from an exact environment override, may be wrapped as the effective `Secret<T>` value.

A “complete descriptor” contains the required nonblank `key`, contains only recognized members, and satisfies the specified provider's local validation or, when `provider` is omitted, at least one registered provider's local validation. Omitted optional fields take their documented defaults. For Google, completeness also means the key/resource and `version` or configured `DefaultVersion` satisfy the existing Google options policy. Atomic replacement never means every optional field must be written.

## Compiled Composition Plan

Register one singleton `ConfigCompositionEngine` used by both `DefaultConfigManager` and `ConfigAuditReporter`. The engine owns one `ConfigCompositionPlanCompiler`, one `ConfigCompositionExecutor`, the immutable `ConfigCompositionJsonContract`, and one immutable-snapshot `ConfigSecretProviderRegistry`. Every multi-capability Google or LocalSecrets registration aliases the same concrete singleton instance; it is never constructed once per interface. Runtime, audit, and startup validation obtain the same engine, registry entries, file snapshot source, environment candidate service, and legacy-claim inspectors. DI identity tests must prove these aliases and reject duplicate canonical provider ids before any plan or provider I/O.

The value-free plan records:

- requested environment, root logical key, and destination type;
- every `Secret<T>` destination path and scalar target type;
- merged file declaration metadata and source location;
- matching legacy code mappings;
- static enabled state;
- optional provider constraint;
- compatible registered provider ids;
- overlap and unsupported-shape diagnostics;
- precedence and exact environment-rescue edges; and
- sensitivity and audit metadata for every secret destination.

The plan never contains a secret payload. Runtime execution owns payloads only long enough to convert and assemble the requested object. Plans are immutable and cacheable only by a key that includes requested environment, root logical path, destination structural-contract identity, file snapshot generation, ordered provider registration instances and canonical ids, relevant legacy mapping/configuration fingerprint, and any options that change validation or providerless budgeting. Payloads, invocation serializer options, provider runtime outcomes, environment values, and audit traces are never cached in the plan. A new snapshot or changed registration/options fingerprint produces a new plan; concurrent callers may share only the immutable compiled metadata.

### Execution algorithm

The executor keeps one internal slot per discovered `Secret<T>` path. A slot carries declaration state, lower-source state, provider outcome, exact environment outcome, effective source, and at most one unrescued terminal diagnostic. The value-bearing fields exist only in the execution frame.

```text
if a direct environment root parses:
    bind it in sensitive-environment mode
    return the typed root to the existing Config<T> validation path

plan = compile type graph + file layers + code mappings + provider registrations
reject plan-global shape, duplicate-id, and overlap errors

base = resolve raw-capable providers by existing priority, then file
buffer = selected raw base or an empty bindable object
slots = initialize every discovered Secret<T> destination

for each slot:
    capture a non-null lower value only when its source is secret-capable
    if a descriptor exists and is enabled:
        evaluate every required provider outcome
        retain a success or a path-terminal failure
    if an exact parseable environment value exists:
        replace the slot value and clear its path-terminal failure
    if a path-terminal failure remains:
        mark the requested root failed
    create the immutable Secret<T> instance for the slot

if any path failed:
    throw one value-safe configuration resolution failure with per-path diagnostics

bind the ordinary object once using opaque slot ids for Secret<T> members
return the typed root to the existing Config<T> validation path
```

Plan-global errors such as malformed descriptors, unsupported object shapes, duplicate provider ids, provider `Invalid` validation results, and overlapping declarations are not rescued by descendant environment values. A direct environment root remains the only complete short circuit. Enabled per-path resolution errors, including missing, denied, unavailable, `InvalidReference` returned during remote resolution, ambiguous provider, budget exhaustion, and conversion failure, may be cleared only by a valid exact environment value.

The executor separately tracks whether any root contribution exists. A selected base, a file or code declaration, a resolved exact environment descendant, or a resolved provider child can establish root presence. Merely discovering `Secret<T>` in the destination type cannot. If no contribution exists, return `null` exactly as today so `Config<T>.DefaultValue` and required-root presence semantics remain intact. When a default object is selected by `Config<T>`, its model initializer can use the public empty `Secret<T>` constructor; AppSurface does not reinterpret that application-authored default as a provider resolution.

The executor returns one internal `ConfigCompositionExecutionResult<T>` with:

- `Missing`, `Resolved`, or `Failed` root state;
- the transient effective `T` only for `Resolved`;
- every provider outcome actually observed in invocation order;
- one terminal failure per unresolved secret path plus any plan-global failure;
- safe plan, provider, and conversion diagnostics; and
- a value-free provenance and secret-slot trace.

Runtime and audit invoke the same providers in the same order and consume that same result shape. Runtime maps `Missing` to `null`, returns the effective `T` for `Resolved`, and throws a new sealed, value-safe `ConfigurationCompositionException` for `Failed`; the existing sealed `ConfigurationResolutionException` and its serialized/message behavior remain unchanged for legacy roots. The new exception exposes `EnvironmentName`, `RootKey`, and an immutable ordered list of `ConfigCompositionFailure` records. Each record carries only canonical destination path, stable code, provider ids/roles when safe, retryability, source location, and the existing problem/cause/fix/documentation fields. It cannot carry a payload, raw exception text, or parent-object serialization, and its `Message`, `ToString()`, debugger display, and JSON shape are snapshot-tested.

`Config<T>.Init` then performs its unchanged presence, DataAnnotations, and scalar/custom-hook validation. Audit maps a failed composition root to `ConfigAuditEntryState.Invalid`, emits one opaque child entry per secret destination using the existing append-only entry/source/diagnostic contracts, and places plan-global failures on the root. A fully resolved single-source root remains `Resolved`; a resolved root with base plus slot/environment contributions is `PartiallyResolved`; missing remains `Missing`. Per-slot state names live in stable diagnostic codes rather than extending the public `ConfigAuditEntryState` enum. Audit passes a resolved `T` through the existing `IConfigInspectable.Inspect` validation projection and renders the safe trace. It does not continue to lower providers after the shared executor stopped and does not run a second precedence algorithm. Existing roots without `Secret<T>` retain their current runtime and audit paths in this issue.

### File-layer preservation

`FileBasedConfigProvider` currently stores a merged `JsonNode`. Direct descriptors cannot be merged safely before the destination type is known because an ordinary object may legitimately contain the same property names.

Extend the internal `ConfigFileProviderSnapshot` with `Layers`, an immutable ordered list of `ConfigFileLayer` records, and `LoadEvents`, an immutable ordered list containing both successful layers and file-load failures. Each successful layer owns a deep clone of the parsed `JsonObject` plus its environment, full source path, deterministic order, and source-location map. Each failure contains only a stable code, affected environment when derivable, safe display path, deterministic order, and sanitized parse/read classification. Keep the existing `Environments`, `Origins`, `Diagnostics`, and `SourceLocationMaps` members and their current merge construction unchanged. Existing `GetValue<T>`, audit enumeration, and ordinary diagnostics continue to read those existing merged members. Only the new type-aware plan compiler reads `Layers` and `LoadEvents`.

During type-aware plan compilation:

1. ordinary object paths keep existing merge behavior;
2. paths typed `Secret<T>` are interpreted as descriptors;
3. each descriptor is validated independently; and
4. the highest file layer replaces the complete lower descriptor atomically.

For example, an environment-specific file cannot supply only a new `key` and accidentally inherit an old `version`. It must repeat the complete intended reference. Source locations identify the winning declaration.

Per-layer behavior at a `Secret<T>` path is exact:

- no property in the higher layer preserves the complete lower declaration;
- a complete descriptor object atomically replaces the lower declaration;
- `null`, a scalar, an array, an incomplete descriptor, or a descriptor with invalid members atomically replaces the lower declaration and fails plan compilation; and
- there is no null tombstone or partial descriptor merge in this release.

`Layers` is authoritative for every discovered `Secret<T>` path. A present JSON null is retained as a layer event and causes replace-and-fail there even though the legacy merged `Environments` view continues its current null-skipping behavior for ordinary paths. Regression tests snapshot existing ordinary-object merges, null handling, `Environments`, `Origins`, and audit enumeration before and after `Layers` is populated. The new history is additive internal state, not a replacement file-provider algorithm.

When file is the selected base, the executor starts from the existing merged root for ordinary members but replaces every discovered `Secret<T>` node with an opaque slot marker before final binding. Descriptor contents come only from `Layers`; the deep-merged descriptor-shaped node is never treated as an effective secret value. This prevents an omitted optional field in a higher complete descriptor from leaking in from the lower merged node.

The loader performs a streaming duplicate-member scan before building each `JsonObject`, using ordinal case-insensitive member comparison independently inside every object. Exact duplicates and case-only duplicates are retained as a failed load event instead of silently taking a winner. If two discovered file paths collapse under ordinal case-insensitive full-path comparison, the snapshot records a deterministic collision failure rather than depending on host filesystem behavior. Successful files continue in ordinal-ignore-case order with ordinal spelling as the tie-breaker. For opted-in roots, an applicable malformed or unreadable file event is a plan-global failure. If parsing failed before the loader can determine which roots the file contains, every opted-in root for that file's environment fails safely; direct environment root success still bypasses file compilation, and legacy roots retain the current skip-and-diagnostic behavior.

### Base contribution

One table is authoritative for root selection:

| Order | Source | Behavior |
|---:|---|---|
| 1 | Parseable direct environment root | Complete emergency short circuit. Bind and validate the root; do not compile file declarations, call secret providers, or apply environment descendants. |
| 2 | Non-environment providers in descending existing `Priority` | First `Resolved` root wins; a terminal provider state stops. Google direct mappings remain priority 10 and LocalSecrets remains priority 5. |
| 3 | File | Existing priority 1 base when no higher provider resolves. |
| 4 | Enabled inline secret references | Patch only discovered `Secret<T>` paths on the selected raw base. |
| 5 | Exact environment descendants | Last writer at their exact paths; may override a success or rescue a failure. |
| 6 | Final bind, then existing `Config<T>` validation | Deliver a typed root to the existing wrapper validation path only when every terminal composition path is resolved or exactly rescued. |

File declarations are policy metadata, not ordinary file values. They are compiled separately even when LocalSecrets supplies the priority-5 base. This is how a file-declared Google child can patch a LocalSecrets object without deep-merging file and LocalSecrets roots.

When the requested type contains `Secret<T>`, built-in providers that can supply a lower object participate through a raw, provenance-bearing composition contribution rather than prematurely deserializing the object. The first implementation needs this adapter for file, LocalSecrets, and the existing Google direct-mapping path:

```csharp
public interface IConfigCompositionValueProvider
{
    ConfigCompositionValueResolution ResolveRaw(string environment, string logicalKey);
}

public interface IConfigProviderClaimInspector
{
    ConfigProviderClaim InspectClaim(string environment, string logicalKey);
}

public enum ConfigProviderClaim
{
    Unclaimed,
    MayClaim
}
```

`ConfigCompositionValueResolution` distinguishes `Unclaimed`, `Missing`, `Resolved`, and `TerminalFailure`; exposes provider name, priority, and sensitivity; carries raw UTF-8 text or a cloned JSON node through an internal non-formatting accessor; and uses public named factories whose `ToString()` is value-safe. It never accepts an already-typed application object. `Missing` falls through exactly as the existing provider does. A found JSON `null` is a resolved raw contribution, not provider absence; at an inner `Secret<T>` path it produces no value and therefore `HasValue=false`. A malformed found root is a terminal conversion failure.

The engine normalizes every resolved raw base into one internal composition tree containing only object, array, scalar, and null nodes plus per-path provenance and sensitivity. For an object-valued destination, provider text must parse as a JSON object. Arrays and collections may remain ordinary nodes, but no secret slot may be discovered inside them. At each discovered secret path, a file descriptor node is removed, while a scalar from a sensitive raw base is captured as a lower candidate. A non-scalar lower value at `Secret<T>` is a conversion failure because the first release accepts scalar `T` only. Only the final binder constructs `Secret<T>` instances.

`IConfigCompositionValueProvider` is public because third-party base providers need an implementable migration seam. The built-in adapters are concrete:

- File returns a clone of the existing merged root and exposes ordered declaration events separately through `Layers`.
- LocalSecrets runs its existing posture and identity checks, calls the store once, and returns the found stored text before `T` conversion. Its current missing and terminal statuses map directly to the raw result.
- Google raw-base resolution is only for the current exact requested-root mapping or root convention. It performs the existing access, timeout, cache, strict UTF-8 decoding, and failure mapping, but defers `T` conversion.
- Google child-reference resolution is separate and goes through `IConfigSecretProvider`; LocalSecrets does not implement that child-reference seam in this issue because it lacks a version contract.

The File, LocalSecrets, and Google modules register their existing singleton provider instance under every capability it implements, preserving store/client state, caches, priorities, and terminal diagnostics rather than creating a second provider instance.

Base providers remain whole-root alternatives rather than deep-merged peers. The first highest-priority non-missing base wins, preserving current behavior. File declaration metadata is compiled separately and may patch `Secret<T>` destinations on that selected base.

Existing third-party `IConfigProvider` implementations keep their legacy whole-value behavior when no inline or descendant composition is required. For an opted-in root, a raw-capable provider participates normally. A legacy typed provider may implement the local-only `IConfigProviderClaimInspector`; if it reports `Unclaimed` for this root, the planner safely excludes it. If it reports `MayClaim`, or exposes no claim inspector, plan compilation fails with `config-composition-provider-unsupported` and migration guidance because invoking and cloning an arbitrary typed object would be unsafe. This is the explicit opt-in compatibility boundary for `Secret<T>` roots; unrelated providers can preserve eligibility with the lightweight claim inspector without implementing raw resolution.

The composition engine rejects a plain file value at a secret destination. It may wrap a value from LocalSecrets because that source is already sensitive and fail-closed.

### Secret resolution

Provider compatibility is a local predicate:

- with `provider`, only the case-insensitive id match is considered; it is compatible only when `ValidateReference` returns `Supported`;
- without `provider`, every registration whose `ValidateReference` returns `Supported` is compatible;
- `Unclaimed` means the provider does not own that reference shape and is excluded;
- `Invalid` means the provider recognizes the shape but rejects it and is immediately terminal; and
- scalar `T` compatibility is checked once by the plan before provider validation because providers return text and `ConfigValueConverter` owns destination conversion.

The core evaluates all applicable `ValidateReference` calls before any `Resolve` call. For a providerless descriptor, any `Invalid` result makes plan compilation fail even when another provider reports `Supported`; `Unclaimed` results are ignored. This prevents a provider success from hiding a locally recognized but malformed interpretation of the same unconstrained declaration.

For each enabled reference:

1. Validate its descriptor locally against registered providers.
2. If `provider` is set, invoke only that provider.
3. Otherwise invoke compatible registered secret providers in canonical provider-id order until all have answered or a terminal outcome fixes the result. The order exists only for deterministic diagnostics, not precedence.
4. Collect structured outcomes without formatting payloads.
5. Continue past only `Unclaimed` and `Missing`; a terminal runtime outcome stops later provider calls because the final result is already fixed as failure.
6. Fail if any provider reports a terminal or uncertain result.
7. Classify a zero-success outcome using the complete truth table below.
8. Fail as ambiguous if more than one provider resolves.
9. Convert the unique payload to the inner `T` through `ConfigValueConverter`.
10. Wrap the value and safe source metadata in `Secret<T>`.

Disabled references skip steps 2 through 9. Lower secret-capable and environment contributions may still establish `HasValue`; the reference itself contributes neither a value nor a failure.

A `Secret<T>` destination with no descriptor performs no secret-reference lookup. It starts as `Enabled=true`, takes a non-null value from the selected secret-capable base when present, and may then be replaced by an exact environment value.

Zero-success classification:

| Validation vector | Resolution vector | Result |
|---|---|---|
| No registrations | none | `secret-provider-not-registered` |
| `Invalid`, `Invalid + Unclaimed`, or `Invalid + Supported` | no provider is resolved | terminal `secret-reference-invalid` |
| All registrations `Unclaimed` | none | `secret-reference-unsupported` |
| At least one `Supported` | all invoked outcomes `Unclaimed` | `secret-reference-unsupported` |
| At least one `Supported` | one or more `Missing`, remainder `Missing` or `Unclaimed` | `secret-not-found` |

For an explicit provider, no id match is `secret-provider-not-registered`, `Unclaimed` is `secret-reference-unsupported`, `Invalid` is `secret-reference-invalid`, and `Missing` is `secret-not-found`.

### Environment rescue and final validation

After provider resolution, apply environment descendants through the same path and conversion machinery:

- an exact valid environment value always replaces a successfully resolved provider value;
- an exact environment value at a failed secret path may replace that path's failure;
- an exact environment value at a disabled secret path may provide a migration value while `Enabled` remains false;
- an invalid exact environment value does not erase a valid provider value, matching the existing environment patcher's first-parseable-candidate behavior, and emits its existing safe conversion diagnostic;
- a sibling override does not clear the failure;
- all failures must be rescued before the object is delivered; and
- sensitivity remains attached because the destination remains `Secret<T>`.

Bind the completed object once, then return it to the existing `Config<T>` presence, DataAnnotations, and scalar validation path. A disabled secret is not automatically invalid. The application can express feature-dependent requirements by inspecting `Enabled` and `HasValue` in its existing object validation boundary.

“Exact environment value” means a value found from the complete canonical destination path, not a parent or sibling. For `Service.ApiKey` in `Production`, retain the current first-parseable candidate order:

1. `PRODUCTION_SERVICE_APIKEY`
2. `SERVICE_APIKEY`
3. `PRODUCTION__SERVICE__APIKEY`
4. `SERVICE__APIKEY`

Names are generated in uppercase by the existing normalizer; actual key lookup semantics remain those of `IEnvironmentProvider` and the host platform. An invalid earlier candidate records the existing conversion diagnostic and allows the next candidate. The first parseable candidate wins; later candidates do not create ambiguity because this preserves current environment compatibility.

Environment sources supply effective values, not reference declarations. At a `Secret<T>` destination, a direct-root member or exact descendant must contain a scalar representation of `T`; an object containing `key`, `version`, `provider`, or `enabled` is not interpreted as a descriptor and fails ordinary scalar conversion.

Direct-root probing means the complete existing `BuildDirectCandidates` sequence for the requested root: environment-scoped legacy name, unscoped legacy name, environment-scoped hierarchical name, then unscoped hierarchical name, with ordinal duplicate removal. For `Production` and dotted key `Service.Options`, those are `PRODUCTION_SERVICE_OPTIONS`, `SERVICE_OPTIONS`, `PRODUCTION__SERVICE__OPTIONS`, and `SERVICE__OPTIONS`. A simple key such as `Service` deduplicates the two unscoped forms. Invalid earlier candidates emit safe conversion diagnostics and do not block a later candidate. The first parseable complete root suppresses providers and every descendant variable; if no root candidate parses, normal base selection and descendant patching continue.

A direct-root example is:

```text
PRODUCTION__SERVICE={"Endpoint":"https://service.example","ApiKey":"demo"}
```

For `Config<ServiceOptions>`, that parseable root bypasses the file descriptor and all remote reads. The internal environment binding mode interprets the raw `ApiKey` only because its destination is `Secret<string>`, producing `Enabled=true`, `HasValue=true`, and `ResolvedProvider=EnvironmentConfigProvider`. A separately set `PRODUCTION__SERVICE__APIKEY` is ignored because direct root already won.

## Secret Provider Contract

The provider-neutral public seam has an implementable minimum shape:

```csharp
public interface IConfigSecretProvider
{
    string Id { get; }

    ConfigSecretReferenceValidation ValidateReference(ConfigSecretReference reference);

    ConfigSecretProviderResolution Resolve(
        ConfigSecretReference reference,
        ConfigSecretResolutionContext context);
}

public interface IConfigSecretDeclarationSource
{
    IReadOnlyList<ConfigSecretConfiguredClaim> InspectClaims(
        string rootLogicalPath,
        IReadOnlyList<string> secretDestinationPaths);
}

public enum ConfigSecretConfiguredClaimKind
{
    ExactMapping,
    RootMapping,
    RootConvention
}

public sealed record ConfigSecretConfiguredClaim(
    ConfigSecretConfiguredClaimKind Kind,
    string LogicalPath,
    string ProviderId,
    string Key,
    string? Version);

public sealed record ConfigSecretReference(
    string Environment,
    string LogicalPath,
    string Key,
    string? Version);

public sealed class ConfigSecretResolutionContext
{
    public TimeSpan Remaining { get; }
}

public sealed class AppSurfaceConfigOptions
{
    public TimeSpan ProviderlessResolutionBudget { get; set; }
        = TimeSpan.FromSeconds(30);

    public int MaxCompositionGraphDepth { get; set; } = 32;

    public int MaxCompositionGraphNodes { get; set; } = 4096;

    public int MaxSecretDestinationsPerRoot { get; set; } = 256;
}

public enum ConfigSecretReferenceValidationStatus
{
    Supported,
    Unclaimed,
    Invalid
}

public enum ConfigSecretProviderResolutionStatus
{
    Unclaimed,
    Missing,
    Resolved,
    AccessDenied,
    Unavailable,
    InvalidReference,
    ProviderFailed
}
```

All four `AppSurfaceConfigOptions` properties are validated eagerly as positive. Depth, node, and secret-destination limits apply during value-free plan discovery before provider I/O. The defaults are intentionally above normal configuration models but bound accidental or hostile metadata expansion. Provider registrations remain trusted host code rather than file-controlled input.

The core owns `provider` filtering and `enabled` state. It passes only the descriptor's environment, canonical destination path, opaque key, and version to provider validation. Disabled descriptors still call `ValidateReference` on the selected registration set but never call `Resolve`; enabled descriptors call `Resolve` only after all local validation succeeds. Providers therefore do not need, and cannot reinterpret, the activation flag or provider constraint.

`IConfigSecretDeclarationSource` is a provider-neutral, local-only compatibility seam for existing code-configured mappings. It performs no secret-store I/O. The Google implementation inspects its already-validated options and reports:

- an exact root mapping or current root convention claim, which remains a whole-root Google base claim;
- every exact configured mapping below the requested root, plus mappings equal to or above it, regardless of whether the mapped child is already typed `Secret<T>`; and
- safe mapping origin metadata for overlap diagnostics.

An exact `MapSecret(...)` claim at a discovered `Secret<T>` destination becomes an enabled, Google-constrained plan reference when no inline descriptor exists. Its secret id/resource and version become `key` and `version`; its provider is the Google canonical id. The same-path mapping plus an inline descriptor is a duplicate claim. Root, ancestor, or descendant intersections are overlap failures. A mapping aimed at a plain destination under a root that has entered the new composition path fails with guidance to migrate the containing requested root as one unit: convert every mapped child intended for composition to `Secret<T>` and remove or relocate incompatible claims. Google does not report descendant convention matches, so this feature does not broaden convention discovery. Other secret-provider packages need not implement this seam unless they already expose a legacy mapping API.

Supporting sealed result types use named factories rather than public positional constructors:

- validation returns `Supported`, `Unclaimed`, or `Invalid` plus a stable safe code;
- resolution returns one status, canonical provider id, retryability, and bounded safe metadata;
- `Resolved(string sensitiveValue, ConfigSecretSourceMetadata source)` accepts a payload but stores it behind an internal non-formatting accessor used by the core Config assembly;
- non-success factories cannot carry a payload;
- `ToString()`, equality diagnostics, and debugger display redact payload presence; and
- `ConfigSecretSourceMetadata` contains canonical provider id and a provider-owned allowlisted source kind. Provider-normalized identity and requested version remain internal sensitive-support metadata and are omitted from default exception, log, text-audit, and JSON-audit rendering. A provider may emit a bounded opaque correlation token only through an explicit safe-metadata factory; arbitrary key/resource text is never presumed safe.

Provider ids use lower-case kebab-case, compare case-insensitively, and must be unique. Registration uses ordinary DI enumeration of `IConfigSecretProvider`; Config validates ids before compiling a plan. Providers must not perform I/O from `ValidateReference`.

The current configuration API is synchronous and has no cancellation token. The resolver seam remains synchronous for this release. `ConfigSecretResolutionContext` exposes a monotonic remaining budget and requires the provider to cap its native synchronous timeout to the smaller of its configured per-call timeout and that remaining budget. Implementations must not block on an asynchronous task. Google clamps `LookupTimeout`, uses its synchronous client adapter, and retains its successful-value cache. Cache ownership and lifetime remain provider-specific; the composition engine adds no cache.

Providerless candidates execute sequentially in canonical provider-id order so diagnostics and tests are deterministic. Secret destinations also execute in canonical path order; one root owns one providerless deadline across all of them. Every compatible provider after a success must still run to detect ambiguity unless a terminal outcome already fixes failure. All providerless references in one requested root share `AppSurfaceConfigOptions.ProviderlessResolutionBudget`, defaulting to 30 seconds and validated as positive during options validation. The core uses `TimeProvider.GetTimestamp()` and elapsed-time APIs for the monotonic deadline, checks the deadline before every call, passes the remaining duration to the provider, and fails unresolved providerless paths with `secret-providerless-resolution-budget-exceeded` when exhausted. A non-positive remaining duration is never passed to a provider. There is no parallel fan-out in the first release. Provider registrations are trusted application code and are not statically capped, but execution is only cooperatively budgeted because the synchronous contract cannot preempt a non-conforming provider. Applications with a tighter startup SLO should lower the budget or specify `provider`.

The synchronous budget is cooperative, not preemptive: core cannot interrupt a provider that ignores `Remaining`. It checks the deadline again after every call. If the deadline expired before uniqueness was established, the root fails budget-exceeded and does not accept a late success. Provider documentation and conformance tests must prove that built-in implementations cap their native timeout to `Remaining`; third-party implementations that cannot do so must reject the contract during local validation rather than overrun it.

Provider-id/options validation is eager at host startup. Config registers an options validator and a small hosted startup validator that enumerates secret-provider registrations and known `Config<T>` roots, validates unique canonical ids, and compiles every discovered secret plan whose direct-root environment short circuit does not already win. Configuration wrapper values remain lazily resolved when DI activates them, preserving existing behavior, but invalid ids, unsupported destination graphs, descriptor conflicts, and local reference validation fail before the host reports ready. Disabled plans still perform only local validation. This startup service never performs enabled secret resolution; applications that require fail-fast payload availability must explicitly resolve their required config wrapper during startup, as shown in the golden-path example.

The core catches unexpected non-fatal provider exceptions and emits a generic `ProviderFailed` diagnostic containing only the provider id, retryability, and stable framework-owned failure details. It never copies the exception type name, `Exception.Message`, stack data, or arbitrary provider text. Process-fatal `OutOfMemoryException`, `StackOverflowException`, and `AccessViolationException` are allowed to escape the provider boundary so the composition engine does not relabel process-level failures as ordinary provider failures. Provider-returned codes, identity/version metadata, and documentation hints are length-bounded, stripped of control characters, and passed through the existing value-safe diagnostic constructors before audit or logging.

The Google package adapts its existing option validation, resource construction, client, status taxonomy, timeout, and successful-value cache to this seam. Its canonical id is a public constant. Existing exact `GoogleSecretManagerConfigProvider` behavior remains available. Child-reference cache identity uses a distinct key containing the provider id, environment, canonical Google version resource name, and a fingerprint of provider settings that affect resource interpretation or access; project, secret id, and requested version/alias therefore cannot collide with a prior descriptor. A changed file key/version or relevant options snapshot cannot reuse the previous descriptor's payload. The implementation uses the existing provider singleton and cache, injects `TimeProvider` so TTL tests do not depend on wall-clock timing, and never shares the legacy logical-path cache entry with the child-reference cache.

The composition core does not memoize one provider result across different logical destinations because `ConfigSecretReference.LogicalPath` is provider-visible policy input. Two destinations may name the same external key yet have different authorization or validation meaning. A provider may deduplicate safe equivalent remote work behind its own canonical cache; the Google adapter therefore receives two contract calls but performs one remote access when both references normalize to the same child cache identity. Tests distinguish provider-call parity from remote-client call count.

The LocalSecrets package participates as a lower object contribution in this issue. Registering LocalSecrets as a providerless inline resolver is deferred because its current store has no runtime version contract. AppSurface must not silently satisfy a version-pinned declaration with an unversioned local value. The existing materialized-remote attestation may support a future explicit design.

## Path Identity and Overlap

The plan uses one segment model:

- the canonical AppSurface logical path starts with the key produced by `ConfigKeyAttribute`, normalized to colon-delimited segments;
- nested members append the serialized JSON member name from the structural `JsonTypeInfo`; `[JsonPropertyName]` therefore changes file, diagnostic, mapping, and environment destination identity while the CLR member name remains code-only metadata;
- logical-path comparison is ordinal case-insensitive, matching AppSurface configuration identity across file, environment, and code-mapping spellings;
- `.` and `:` are accepted as separators when parsing a logical path for overlap, but the original source spelling and legacy direct lookup behavior are preserved;
- distinct file declarations that collapse to the same canonical logical path fail as a same-layer collision before provider-specific normalization;
- empty segments and literal `.` or `:` inside a secret-destination member name are unsupported because this release adds no escape syntax;
- environment names are derived from the canonical segments through the existing `EnvironmentConfigProvider` normalization, including its current `__` hierarchical candidates; and
- arrays, numeric index segments, dictionaries, and collection-item references are outside the first release.

Overlap compares segment arrays, never raw string prefixes. Two claims overlap when their normalized paths are equal or when one complete segment array is an ancestor of the other. Sibling paths do not overlap. A current Google convention conflicts only when its existing predicate claims the requested root and the plan also contains a descendant secret claim. The compiler never asks a convention to discover descendant matches, so convention scope does not broaden.

Canonical logical identity and environment aliases are separate collision domains. During compilation, the shared environment candidate service generates every scoped, unscoped, legacy-flat, and hierarchical candidate for each secret destination and maps each candidate back to its canonical path. If one environment variable candidate can target two distinct secret destinations, the opted-in root fails with `secret-environment-alias-collision` before provider I/O. The diagnostic names both canonical paths and the colliding variable name but never a value. Existing legacy roots retain their current behavior. Tests cover underscores, hyphens, `:`/`.` separators, scoped/unscoped forms, `[JsonPropertyName]`, and two simultaneously failing destinations so one environment variable can never rescue both.

The secret provider's `key`, version, and other external resource identifiers are opaque provider input. Their spelling and case are preserved, and they are never parsed or normalized as AppSurface logical paths.

## Failure and Rescue Matrix

| Situation | Result |
|---|---|
| Valid `enabled: false` | Local descriptor validation, zero inline secret-reference `Resolve` calls, plan reports `DeclaredDisabled`; lower-base resolution may still run |
| Disabled providerless declaration has no compatible registered provider | Plan validation failure without remote access |
| Explicit provider is not registered | Plan validation failure, including when disabled |
| Explicit provider returns missing | Terminal missing |
| Providerless lookup has zero registered providers | Terminal `secret-provider-not-registered` |
| Registered providers all reject the shape as unclaimed | Terminal `secret-reference-unsupported` |
| At least one compatible provider returns missing and all others are missing or unclaimed | Terminal `secret-not-found` |
| Exactly one provider resolves and all others are unclaimed or missing | Resolve and convert |
| More than one provider resolves | Terminal ambiguous-provider failure |
| One provider resolves and another is denied, unavailable, invalid, or fails | Terminal uncertain-provider failure |
| Providerless root budget expires before uniqueness is established | Terminal `secret-providerless-resolution-budget-exceeded`; exact environment rescue remains path-specific |
| Unique payload cannot convert to inner `T` | Terminal conversion failure |
| Exact valid environment value targets the failed path | Failure rescued; validate completed object |
| Environment value targets only a sibling | Original failure remains terminal |
| Two secret paths fail and environment rescues one | Unrescued path blocks the object |
| Inline declaration overlaps a legacy mapping or convention | Plan validation failure |
| Two secret destinations generate the same environment candidate | Plan-global `secret-environment-alias-collision` before provider I/O |
| Parseable direct environment root exists | Bind and validate it; ignore file declarations, secret-provider lookup, and environment descendants |
| Higher file layer omits the property | Preserve the lower complete descriptor |
| Higher file layer supplies null, scalar, array, or malformed descriptor | Replace-and-fail; never inherit lower descriptor fields |
| Higher applicable file is unreadable or malformed before root attribution | Opted-in roots in that environment fail plan compilation; legacy roots keep current skip behavior |
| Supported-type discovery reaches a recursive secret-capable path or graph budget | Plan-global unsupported-destination failure before provider I/O |

There is no `optional: true`, fallback payload, “ignore denied,” “first provider wins,” or “missing means disabled” behavior.

## Audit, Diagnostics, and Redaction

The shared executor emits a value-free trace consumed by audit:

- declaration path and source file location;
- requested provider constraint, if any;
- providers considered;
- canonical winning provider, if any;
- a provider-approved opaque correlation token when explicitly classified safe; raw key/resource identity and requested version are omitted by default;
- enabled, disabled, resolved, rescued, missing, ambiguous, and terminal states;
- provider priority or role where relevant; and
- existing stable remediation and documentation hints.

Compiled secret-slot metadata is the authoritative sensitivity signal. `ConfigAuditValueTraverser` treats every `Secret<T>` as an opaque leaf, emits only `Enabled`, `HasValue`, and safe source metadata from the slot trace, and never invokes or reflects over `Value` or its backing field. It marks the destination and any emitted metadata sensitive regardless of path naming, source, or the existing heuristic redactor. A regression fixture uses a non-secret-looking member name and a unique payload sentinel to prove traversal, rendering, exceptions, and diagnostics never read or contain the payload.

The trace never contains:

- provider payloads;
- converted `Secret<T>.Value`;
- environment override contents;
- raw provider exceptions;
- serialized parent objects containing secret values; or
- values returned by competing providers during ambiguity detection.

Runtime and audit call the same plan compiler and executor. Remove or route around duplicated environment patch interpretation in `ConfigAuditReporter` for this path rather than reimplementing the new rules there.

The existing effective-audit entry point remains the API for this release; no renamed or separately required effective-resolution request is introduced. Its reference documentation, command help, and examples must state before invocation that effective-value audit performs the same enabled remote reads as runtime and therefore has the same IAM, timeout, latency, and network side effects. It uses each provider's existing cache when available; the audit layer adds no cache and never persists a payload. Disabled and direct-environment-root paths perform no remote read for the inline reference. A disabled reference may still allow whole-root base-provider selection, as described in the composition table; audit must distinguish those base reads from inline-reference reads. A future separately named compile-only preflight is outside this issue and recorded in `TODOS.md`.

Runtime and audit are separate observations. With the same immutable file, environment, registration, mapping, and fake-provider outcomes, they must emit the same semantic trace. They are not guaranteed to name the same winner or failure across two real executions when a remote secret, IAM policy, network, or provider cache changes between calls.

Each resolved payload remains reachable only inside the provider result and current execution frame until unique-provider selection, conversion, and wrapper construction complete. Competing payloads from an ambiguity are never converted, traced, or formatted and are released immediately after classification. The plan and audit trace retain only safe metadata.

## Compatibility and Migration

### Existing AppSurface consumers

- Existing `Config<string>` and object configurations without `Secret<T>` use the current path.
- Existing built-in Google `MapSecret(...)` calls targeting plain scalar or object destinations retain their current provider path and behavior.
- Existing environment direct-root behavior remains unchanged.
- Adding `Secret<T>` is an explicit source change. AppSurface does not silently wrap existing plain properties.
- A third-party typed-only provider on a `Secret<T>` root must either implement raw composition or locally prove the root unclaimed through `IConfigProviderClaimInspector`; otherwise the new root fails with migration guidance. This is the sole intentional opt-in compatibility boundary.
- When a requested object contains a `Secret<T>` descendant, a code mapping aimed at that exact descendant may become a plan declaration for compatibility with issue #807's original mapping proposal.
- A code mapping does not become an inline declaration merely because it is under the same root. The target must resolve to `Secret<T>`.
- Equal or hierarchical overlap between a plan-participating code mapping, inline declaration, or claiming convention is rejected. Unrelated legacy direct mappings remain outside the new conflict set.

### Skoolit migration sequence

1. Register the intended secret-provider module; disabled means no resource access, not deferred provider-schema validation.
2. Choose one requested configuration root as the migration unit. Enumerate every mapping at, above, or below it, convert every mapped child that will participate in composition from `string` to `Secret<string>`, and update all typed consumers in that root.
3. In the same reviewed change, remove every overlapping or plain-child `MapSecret(...)`/manifest claim inside that root and place each key and pinned version beside its surrounding configuration. Leaving either a duplicate claim or a mapped plain sibling is a compile-time failure, even when every inline declaration is disabled.
4. Set `enabled: false` while the current environment variable remains the effective value.
5. Verify audit reports `Enabled=false`, `HasValue=true`, and environment as the winner without contacting Google for the inline reference.
6. Provision the resource version and IAM.
7. Enable the reference in an environment-specific file. The environment override may remain for an initial safety deployment, but that deployment is not proof that Google is the effective source.
8. Run a bounded verification deployment with the exact environment override removed; require Google as the effective source and successful application validation.
9. Delete the now-unused environment-bridge precedence branch for the migrated typed consumer.
10. Repeat root by root, then remove the application-owned manifest infrastructure when no rows remain.

Rollback deploys the previously built application artifact together with its matching AppSurface package set and restores the matching environment/mapping configuration when required. Merely pinning an older package under an application binary compiled against `Secret<T>` is not a valid rollback. Rollback never changes or deletes the remote secret version. Release rehearsal must prove this artifact-level rollback before stable publication.

## Cross-Model Perspective

The independent cold review identified the strongest version as an inspectable configuration plan compiled before application start. It emphasized that a secret claim must survive failure, sensitivity must remain attached even when environment wins, and declaration objects must merge atomically.

It also identified [`helmfile/vals`](https://github.com/helmfile/vals) as conceptual prior art for committed external references. AppSurface still owns the harder half: destination-aware C# conversion, path-specific terminal failures, exact rescue, preserved siblings, provider ambiguity, and one runtime/audit engine.

Its proposed first slice matches this design: one nested scalar reference through the real `Config<T>` and audit paths, with file and LocalSecrets bases, all fail-closed outcomes, exact environment rescue, and a Skoolit-shaped deletion criterion.

## Approaches Considered

- Standardized sidecar manifest: rejected because it would productize Skoolit's duplicated-path workaround rather than remove it.
- URI reference expansion: rejected because a `ref+...` string is less explicit, harder to validate structurally, and still needs the same composition engine.
- Compiled inline-reference plan: selected because it co-locates intent, makes sensitivity typed, and gives runtime and audit one semantic authority.

## Recommended Approach

Build the compiled inline-reference plan with direct descriptors on `Secret<T>`. Keep provider-neutral contracts in Config, adapt Google through its existing client and diagnostics, preserve direct mappings, and treat static disablement and providerless uniqueness as first-class plan states.

Do not start by building a standalone preflight command. First prove that one object resolves correctly, fails correctly, explains itself correctly, and replaces real Skoolit glue. The value-free plan is the seam from which preflight can follow without redesign.

## Minimum Issue #807 Acceptance Slice

Implement in two bounded stages without shipping a half-defined public contract:

### Stage 1: one complete vertical

- `Secret<string>` on one nested object property;
- one provider-constrained file declaration with `"provider": "google-secret-manager"` and a file-supplied lower object;
- Google as the only registered secret provider;
- enabled, statically disabled, resolved, missing, denied, unavailable, invalid, and conversion outcomes;
- successful provider value overridden by exact environment value;
- failed provider value rescued only by exact environment value;
- one shared runtime/audit executor; and
- redacted `Secret<T>` formatting and serialization.

This stage proves the central semantics but is not a package release boundary. Providerless syntax, third-party raw providers, and LocalSecrets raw-base composition are not advertised or supported until Stage 2 closes their contracts.

### Stage 2: architecture closure

- providerless zero, unique, terminal-plus-success, and ambiguous outcomes using fake providers;
- LocalSecrets as a raw lower-object contribution;
- descriptor-absent `Secret<T>` states;
- atomic multi-file replacement;
- direct-root environment short circuit;
- legacy direct mapping preservation and descendant compatibility mapping;
- exact, ancestor, descendant, and convention overlap rejection; and
- package documentation plus a Skoolit-shaped migration example.

The repository-level Skoolit-shaped fixture is an implementation acceptance criterion. Stable package publication has an additional real-consumer gate: migrate one bounded Skoolit configuration root in a prerelease rehearsal, remove its real manifest rows and bridge branch, verify Google as the effective source with exact environment rescues removed, measure the deleted glue, and prove artifact-level rollback with the previous application/package/configuration set. This cross-repository rehearsal may occur after the AppSurface implementation is complete, but the package remains prerelease until the evidence is recorded.

### Scope rationale

The public design is wider than a Google-only child patch because each additional part closes an explicit requirement rather than speculative infrastructure:

- `Secret<T>` and static disablement provide the application-visible state required for staged provisioning.
- Optional `provider` requires provider-neutral validation plus zero, unique, ambiguous, and uncertain multi-provider semantics.
- File and LocalSecrets raw contributions preserve the already-approved source order.
- Legacy descendant mappings preserve issue #807's original code-configured use case while files become the preferred declaration.
- One executor for runtime and audit removes an existing semantic fork that would otherwise make the new failure rules unreliable.

Implementation may land as linked pull requests or commits matching Stage 1 and Stage 2, but the public guide waits for Stage 2 and stable package publication additionally waits for the bounded Skoolit rehearsal. Conditional activation, object-valued secrets, LocalSecrets as a version-aware inline resolver, parallel fan-out, refresh, and standalone preflight remain separate future decisions.

## Success Criteria

1. A file-based object with ordinary siblings and one enabled `Secret<string>` child resolves through Google and passes existing `Config<T>` validation.
2. The same composition works when LocalSecrets supplies the lower object.
3. Multiple independent secret children resolve without changing untouched siblings.
4. `enabled: false` performs zero inline secret-reference `Resolve` calls and emits `DeclaredDisabled`; a configured lower-base source may still be evaluated.

### Section 4 — Data Flow and Interaction Edge Cases

The review mapped ten high-risk interactions:

1. A parseable direct environment root bypasses file compilation, base providers, secret providers, and descendants.
2. An invalid earlier direct-root candidate allows the next parseable candidate and never falls through after a successful root.
3. A higher file layer omitting a secret property preserves the lower complete descriptor.
4. A higher layer touching the secret property replaces the entire descriptor; null and malformed replacements are retained as failing events.
5. A disabled declaration validates locally but makes zero `Resolve` calls; lower sensitive and exact environment values may still produce `HasValue=true`.
6. A descriptor-absent `Secret<T>` makes no inline lookup and can be satisfied only by a recognized sensitive base or exact environment source.
7. Multiple independent secret failures are tracked per path; rescuing one never clears another.
8. Adding a compatible provider to a providerless deployment can create ambiguity or uncertainty; registration-set coupling must be documented.
9. Validation and audit traversal must treat `Secret<T>` as an opaque leaf and never invoke `Value`.
10. Collections, dictionaries, polymorphic hidden graphs, custom containing-object converters, and delimited member names fail before access.

All ten are handled by explicit plan rules and require tests. No edge case is left as “provider-specific behavior.”

- `Secret<T>` inside arrays, collections, or dictionaries — path identity and binding are not defined.
- Custom containing-object converters or serializer options — one default System.Text.Json contract owns discovery and binding.
- LocalSecrets as a version-aware inline resolver — no version contract exists.
- Providerless parallel fan-out — deterministic sequential execution is sufficient and bounded.
- Background refresh or secret rotation service — provider cache ownership remains unchanged.
- Secret writing, provisioning, IAM management, or deletion — resolution is read-only.
- Standalone compile-only preflight — enabled by the plan, deferred to a separate issue.
- Deployment-time injection unification — a valid alternative for some services, but not required to solve application-visible state and audit.
- General convergence of legacy runtime and audit paths — only the new opted-in path must share one engine.

### Section 1 — Architecture Review

The architecture has one semantic authority and three kinds of state: cached value-free structure, immutable source/registration snapshots, and invocation-owned sensitive execution state.

```text
                              host startup
                                   |
                     local-only composition validator
                                   |
          +------------------------+------------------------+
          |                                                 |
   Config<T>/manager                                ConfigAuditReporter
          |                                                 |
          +------------------ same singleton ----------------+
                                   |
                         ConfigCompositionEngine
               +-------------------+--------------------+
               |                   |                    |
        PlanCompiler          Executor          JsonContract
        (value-free)       (invocation state)   structural metadata
               |                   |                    |
      +--------+---------+         |          invocation-owned options
      |        |         |         |          + context converter
      v        v         v         |
 file load  logical/  provider     +------------------------------+
  events    env paths  registry                                    |
      |        |         |                                        |
      |        |    same singleton aliases                         |
      |        |         |                                        |
      +--------+---------+--------> base providers                 |
                              +---> secret providers -- cache ----> remote store
                              +---> exact environment rescue        |
                              +---> bind opaque slots <--------------+
                                           |
                              ConfigCompositionExecutionResult<T>
                                  /                       \
                     runtime value/exception         audit entries/trace
```

Architecture decisions:

1. **One singleton authority.** `ConfigCompositionEngine`, its registry, and built-in capability aliases have one DI identity. Accepted under P4/P5 because duplicate instances would split cache and diagnostic truth.
2. **Structural versus invocation serializer state.** Cache only value-free metadata. Create context-bearing options/converters per execution. Accepted under P1/P4 because shared converters can cross-contaminate payloads.
3. **Separate public composition exception.** Preserve the sealed legacy exception; expose deterministic ordered failures for opted-in roots. Accepted under P2/P4 because forcing multiple paths into a one-provider shape would be lossy and breaking.
4. **Successful and failed file events.** A malformed higher layer remains evidence, not absence. Accepted under P1 because silent fallback violates atomic replacement.
5. **Two path collision domains.** Canonical logical paths and generated environment aliases are both compiled and independently collision-checked. Accepted under P1/P4 because exact rescue depends on one-to-one destination identity.
6. **Finite supported object model.** Scalar slots, reference-type `Config<T>` roots, active-stack recursion rejection, and explicit graph limits. Accepted under P2/P5 rather than inventing recursive path semantics.
7. **Root-sized migration.** Once a root opts into composition, all descendant mappings are inspected and incompatible mapped siblings must migrate together. Accepted under P1 because a one-property transition cannot satisfy overlap rules.

Scaling is bounded by `O(graph nodes + file-layer nodes + secret slots × compatible providers)`. Graph and slot counts have validated limits. Provider calls are sequential and cooperatively deadline-bound; built-in provider conformance is mandatory because a synchronous interface cannot hard-cancel arbitrary third-party code.

Security boundaries remain clear:

```text
untrusted file syntax ------ duplicate/shape/bounds scan -----> value-free plan
trusted DI registrations --- id/capability validation --------> immutable registry
provider metadata ---------- allowlist/sanitize/bound --------> safe trace
provider/environment value - invocation-owned execution ------> Secret<T>.Value
                                                                (never plan/trace)
```

### Section 2 — Code Quality Review

1. **Candidate-generation duplication.** `DefaultConfigManager`, composition, and audit must call one environment candidate service; copying `BuildDirectCandidates` or flattening rules is rejected.
2. **Path-string drift.** Use one internal segment value type carrying canonical serialized names plus original source spelling; raw string-prefix overlap checks are rejected.
3. **Serializer cleverness.** No `AsyncLocal`, mutable singleton converter, hidden static context, reflection-only binder, or payload-bearing plan marker. Invocation context is a normal constructor dependency with `try/finally` cleanup.
4. **Result-state invalid combinations.** Use sealed results and named factories. Non-success cannot carry a payload; success cannot carry null; plan failures and path failures are distinct.
5. **Provider registration drift.** Register the concrete provider once and alias interfaces to it. Tests assert reference identity, canonical id uniqueness, option snapshot identity, and one cache.
6. **Public contract clarity.** Fully document `Secret<T>`, provider contracts, options, result/metadata types, composition exception, audit behavior, defaults, unsupported shapes, cooperative timeout limits, and migration-unit constraints.
7. **Audit compatibility.** Keep `ConfigAuditEntryState` append-only and map slot detail through existing child/source/diagnostic contracts. Snapshot the public JSON and text formats.

No reflection-based tests may access private state. Internal test seams should expose plan summaries, fake providers, fake time, and call traces intentionally.

### Section 4 — Performance Review

1. **Providerless complexity.** Worst-case calls are secret destinations × compatible providers. Slot count is bounded, ordering is deterministic, and one monotonic budget is shared. Built-ins must cap native timeouts; third-party conformance is documented and tested. Explicit `provider` remains the production-latency recommendation.
2. **Metadata and serializer allocation.** Structural type metadata and value-free plans are cached. Context-bearing options/converters are short-lived per invocation by design; benchmark concurrent composition to ensure isolation cost remains below remote-access latency and does not retain slot payloads.
3. **File snapshot memory.** Retaining layers and failures duplicates some JSON nodes. Snapshot ownership is immutable and generation-scoped; old snapshots become collectible. Benchmarks cover many files, maximum graph nodes, and repeated reload generations.
4. **Cache correctness before hit rate.** The Google child cache includes provider/environment/canonical resource/version/options identity and is separate from legacy cache entries. A safe miss is preferred to a stale cross-version hit.
5. **Startup validation.** Plan compilation is local-only and cached. It must not perform remote reads or eagerly construct application config values. Measure startup with maximum supported roots and slots.

No database or request-path N+1 risk exists. The operational cost is startup/audit CPU plus bounded provider latency.

## Cross-Phase Themes

1. **One semantic authority.** CEO found runtime/audit drift, DX found contradictory observable outcomes, and Engineering found separate DI instances and context-bearing serializers could recreate the drift. The final plan has one singleton engine, one immutable registry/snapshot view, and one execution result consumed by runtime and audit.
2. **Migration proof must delete real complexity.** CEO and DX both rejected a fixture as proof of consumer deletion; Engineering found that even the proposed one-property migration was invalid when mapped siblings remained. The framework fixture proves root-sized behavior, and stable publication now waits for one real bounded Skoolit rehearsal.
3. **Sensitive data safety is structural.** Every phase independently required `Secret<T>` to be opaque, payloads to remain invocation-local, diagnostics to be value-safe, and audit to avoid reflective getters. Engineering extended this to metadata default-deny and concurrent binding isolation.
4. **Exact path identity is load-bearing.** CEO corrected logical path identity, DX required actionable exact-rescue diagnostics, and Engineering found a second collision domain after environment normalization. Both logical and generated-environment aliases are now compiled before I/O.
5. **Provider omission is useful but operationally expensive.** All phases kept providerless exhaustive uniqueness while recommending explicit providers in production. Engineering made the 30-second limit honestly cooperative, bounded graph/slot work, and required built-in timeout conformance.
6. **Shipped-package and rollback evidence matter.** DX required a packed consumer; Engineering showed package pinning alone cannot roll back a consumer compiled against `Secret<T>`. The release proof now includes a matching application/package/config artifact rollback.
