## Problem and outcome

[DevAuth](../../Auth/ForgeTrust.AppSurface.Auth.AspNetCore.DevAuth/README.md) already selects configured local personas using a protected cookie. Hosts currently prepare persona fixtures through a second seed request, startup seeding of every fixture, or lazy work hidden in an unrelated product route. Selecting a persona should instead await host-owned fixture preparation before continuing to the host's existing safe destination.

The concrete proof has two local operators, `labeler` and `reviewer`, and one fully synthetic candidate. Selecting `labeler` creates that candidate if needed. Selecting `reviewer` reaches the same candidate and preserves the labeler's work while allowing a separate review. Repeated or concurrent selections do not create another candidate or reset progress. This is the useful effect: the existing persona control becomes the entrance to a ready local QA scenario without a separate seed request.

This document extends the DevAuth lineage from [#420](https://github.com/forge-trust/AppSurface/issues/420). It is a new feature decision record, not a replacement for unrelated designs on `main`. The [Keycloak local-seed design](auth-aspire-keycloak-local-seeds.md) concerns finite startup-time AppHost workers; #772 concerns an explicit persona selection during an HTTP request.

## Decisions and boundaries

- **D1, build on DevAuth:** retain its named fake authentication scheme, configured personas, protected cookie, existing local/proof guards and navigation. These already solve the identity and control-flow parts of the issue.
- **D2, generalized public research:** use official ASP.NET Core patterns to check asynchronous request flow and test-host support, without sending the specific feature idea in search queries. The conventional approach fits this feature.
- **D3, ownership and identity premises:** the host owns fixture schemas, persistence, scenario identity, repeat/concurrent-selection safety, logging, failure recovery and deadlines. AppSurface supplies one awaited selection extension point and no fixture engine, provider client, global lock, retry loop or data schema. Pass the validated configured persona directly: queuing a response cookie does not replace the incoming request's cookies or `HttpContext.User`, and neither represents a guaranteed newly selected identity during activation.
- **D4, independent second opinion:** obtain a fresh in-host perspective before choosing the API; its handler and shared-scenario suggestions informed the alternatives, without transferring the user's decision authority to the reviewer.
- **D5, cookie ordering retained after review:** queue the protected persona cookie before activating fixtures, as #772 requests. Successful navigation waits for activation; cookie delivery and fixture writes are not one transaction.
- **D6, request-scoped handler selected:** constructor injection provides the host's persistence services in the current request scope. No handler registration retains existing selection behavior. Activation is not invoked by ordinary authenticated requests, GET control/status routes, or clearing a persona.

Activation remains behind the configured [DevAuth environment and loopback policy](../../Auth/ForgeTrust.AppSurface.Auth.AspNetCore.DevAuth/README.md), with the existing same-origin mutation guard. The default environment is `Development` and loopback control requests remain required by default. Explicit host policy overrides retain their current meaning; the new hook does not weaken or independently bypass them. Production identity, tenant provisioning, durable user mapping and external-provider calls remain outside this local proof feature.

## Public contract and registration

Add one public interface in the existing `ForgeTrust.AppSurface.Auth.AspNetCore.DevAuth` namespace and package:

```csharp
public interface IAppSurfaceDevAuthPersonaSelectionHandler
{
    ValueTask ActivateAsync(
        AppSurfaceDevAuthPersona persona,
        HttpContext httpContext,
        CancellationToken cancellationToken);
}
```

The host opts in using normal registration; `LocalFixtureActivation` below is a host-owned implementation, not a new framework type:

```csharp
builder.Services.AddScoped<
    IAppSurfaceDevAuthPersonaSelectionHandler,
    LocalFixtureActivation>();
```

The method completes only when the fixtures required for this selection are ready. `persona` is the configured entry found after normalization and lookup, not an arbitrary route value, protected-cookie payload, production identity, or newly authenticated principal. `httpContext` is the current selection request, including its `RequestServices`. The supplied cancellation token is `httpContext.RequestAborted`. A handler may use scoped persistence services through constructor injection and must not retain the request context, mutate configured persona metadata, start background work that outlives the request, or write/start/redirect the HTTP response. DevAuth owns the response and safe navigation.

The endpoint resolves an optional, unkeyed handler using `httpContext.RequestServices.GetService<IAppSurfaceDevAuthPersonaSelectionHandler>()` inside the validated selection flow. It does not inject the optional service as a required endpoint parameter, resolve it from the root provider, capture it in singleton options, instantiate it during startup, or add a new scope. Register one scoped implementation. AppSurface invokes one resolved service rather than enumerating a handler pipeline; hosts needing several fixture steps compose them within that implementation. Host-container registration behavior applies to duplicate registrations; this feature adds no ordering or multi-handler semantics.

No new options, registration helper, package, or dependency is required. Existing [Auth.AspNetCore service registration](../../Auth/ForgeTrust.AppSurface.Auth.AspNetCore/AppSurfaceAspNetCoreAuthServiceCollectionExtensions.cs) supplies the nearby scoped-service convention. [.NET dependency injection](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/overview#scope-validation) explains why resolving scoped services from the request matters.

## Execution, navigation and failure contract

The existing [selection endpoint](../../Auth/ForgeTrust.AppSurface.Auth.AspNetCore.DevAuth/AppSurfaceDevAuthEndpointRouteBuilderExtensions.cs) becomes asynchronous at the narrow point where it already has a validated persona:

```text
existing environment / loopback / same-origin guards
    -> normalize and look up configured persona
    -> queue protected response cookie
    -> resolve optional handler from this request
    -> if present: observe cancellation, await ActivateAsync,
                   observe cancellation again
    -> resolve existing safe target
    -> return local redirect or existing control-page result
```

Guard failures and invalid/stale personas neither resolve nor invoke the handler. Resolution is after cookie queuing, so constructors and service factories must not perform fixture activation as a side effect. With no handler, the existing endpoint behavior remains intact. With a handler, each valid non-cancelled explicit selection invokes it once, including reselecting the same persona. The framework does not cache a successful activation or promise exactly-once writes across requests.

Await completion before both success branches: redirect and control-page rendering. Preserve the [safe target resolver](../../Auth/ForgeTrust.AppSurface.Auth.AspNetCore.DevAuth/AppSurfaceDevAuthLocalReturnUrl.cs): explicit safe `returnUrl` takes precedence over configured persona `LandingUrl`; without either, render the existing control page. The handler cannot supply a new return target or bypass local-target validation.

Handler-resolution exceptions, activation exceptions and cancellation propagate to the host's normal exception/cancellation pipeline. DevAuth does not swallow them, retry them, convert them to success, produce its success page, or take its normal success redirect. The host owns error responses and any compensation. Activation code must throw when required preparation fails rather than catch an error and return normally.

The cookie has already been queued. Depending on the host's exception middleware and whether a response reaches the browser, it may be delivered, replaced or discarded. Fixture writes may already have committed when cancellation or delivery failure occurs. No framework rollback, prior-persona restoration, cookie-delivery guarantee or atomic cookie/data promise is made. Hosts must not treat an authenticated DevAuth cookie as proof that fixtures are ready; a host page that requires fixtures should check its own readiness state and provide a local retry/reselection path. Repeated selection is the supported retry trigger; host persistence decides which partial work to keep or compensate. Cancellation is cooperative: a handler that ignores it may keep running, and the endpoint's post-await check only prevents normal successful navigation once it returns.

## Shared-candidate proof

Extend the existing [DevAuth example](../../examples/auth-aspnetcore-dev-auth/README.md) without replacing its existing admin/viewer auth and landing proofs. Add `labeler` and `reviewer` local personas and a host-owned scoped handler backed by a provider-free local fixture store. The store may be shared within that host process while the handler remains scoped. Use one fixed scenario key, independent of persona ID, to ensure one candidate. Store labeling and review progress separately by operator role. Reselection ensures readiness without overwriting either operator's completed work; concurrent creation uses a host-owned atomic ensure operation. Process restart resets this synthetic sample, which does not claim durable or cross-process idempotence.

The host page displays the stable synthetic candidate ID and the two independent progress states. Read-only page access checks readiness without lazy seeding. Product-like labeling/review actions may update this in-memory host-owned state, but none are seed endpoints. The proof selects `labeler`, observes one ready candidate, records labeler progress, switches to `reviewer`, observes the same candidate and separate review state, then repeats and overlaps selections to verify one candidate and preserved progress. No real identity, provider client or external call participates.

The partial-failure regression is deterministic and test-only. First select labeler successfully and record labeling progress. Substitute a handler that atomically ensures the existing shared candidate, then throws once before marking reviewer activation ready. Immediately after that failure, there is exactly one candidate with its original ID, unchanged labeling progress, no completed review, and reviewer readiness still false. The sample's declared host error policy returns a fixed safe HTTP 500 response while preserving the queued cookie; it includes no raw exception text and takes no redirect. A subsequent reviewer page GET returns a not-ready response with a local reselection link and does not seed data. Reselect reviewer with the one-shot fault exhausted: activation marks reviewer ready, returns the same candidate, and leaves existing progress intact. After completing the separate review, repeat and overlap both selections to assert one candidate and both completed progress states. This sample policy does not prescribe another host's transaction or recovery behavior.

## Alternatives and independent perspective

- **Options callback, declined in D6:** smaller surface, but scoped dependencies require explicit request-service lookup and the stored delegate risks capturing scoped services in singleton options.
- **Activation before cookie queuing, declined in D5:** could reduce persona changes on failure, but changes #772's requested ordering; retain explicit host-owned recovery instead.
