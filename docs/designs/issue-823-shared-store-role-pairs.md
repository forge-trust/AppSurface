## Problem and boundary

Skoolit [#659](https://github.com/forge-trust/skoolit/issues/659) must certify a second, provider-disabled Source Lifecycle worker lane against the same Durable PostgreSQL store, StoreId, and active runtime epoch as its forwarding lane. Each lane needs its own restricted dispatcher and runtime login. The forwarding lane's authority must survive adding the source pair and every later role-recipe run. Source processing remains closed during certification.

The present recipe accepts one dispatcher/runtime pair. It replaces role targets on shared RLS policies, drops and recreates single-runtime policies, grants one dispatcher direct `SELECT` on `flow_dispatch`, and verifies privileges against one pair. Running it with only the new names can remove the active pair from policies. Skoolit's source dispatcher certificate requires Work discovery through `discover_work_dispatch(text[], text[], integer)` and **no direct Durable relation privileges**.

**Security claim:** These pairs separate deployed credentials, secret access, and operational identity. They do not partition rows by lane. Existing transaction-local `scope_id` RLS, Work registration selection, StoreId/epoch fences, and host authorization keep their current meanings. A compromised runtime login can set a permitted scope value and use its existing broad runtime privileges; a dispatcher with Work-function execution can submit any valid contract-name/version list. Neither login is a PostgreSQL-enforced lane-specific row boundary. The Skoolit certificate must describe a *deployed-lane boundary*, not cross-lane row isolation.

## Premises and constraints

1. One shared store has one StoreId and active runtime epoch. The role pair is deployment identity, not another store or epoch.
2. The existing forwarding pair keeps its current capabilities, including direct payload-free Flow discovery, until a separate reviewed change narrows them.
3. The Source Lifecycle dispatcher is a Work-only profile: schema `USAGE` plus `EXECUTE` on the existing Work discovery function, with no effective direct Durable table, column, or sequence privilege and no Flow/Schedule function execution. Its worker must select `DurableRuntimeSurface.Work` for hosted and direct pump passes; the provider's default is `All`.
4. Runtime roles remain the currently restricted, membership-free login leaves and retain the package's existing scoped runtime grant set. A Work-only dispatcher profile does not imply Work-only runtime SQL grants or role-bound scope IDs.
5. A role recipe run must never silently deauthorize an existing pair. Deliberate retirement is a separate, explicitly reviewed operation outside #823.
6. Migrations run before role reconciliation; the role recipe, privilege proof, schema preflight, and lane certificate run before source activation. No production secret, provider data, or source content is needed for the design proof.

## Approaches considered

- **A. Complete role manifest — selected.** A versioned, non-secret manifest supplies the full authorized pair set on every invocation. The existing recipe reconciles all roles transactionally and refuses missing existing pairs. This meets #659 without a numbered migration.
- **B. Database-owned role registry — deferred.** It avoids supplying a manifest on every run, but adds a migration, enrollment/removal lifecycle, and upgrade coordination while #795 is planning the next schema version. Revisit if operators cannot reliably maintain a complete reviewed manifest.
- **C. Function-only discovery for every dispatcher — separate follow-up.** A Flow discovery function could eliminate the legacy direct `flow_dispatch` grant, but changes active-lane provider behavior and binary compatibility. Source certification needs only the Work-only profile.

## Selected contract

### Manifest and invocation

Extend the canonical packaged `configure-postgresql-roles.sql` rather than adding an ad-hoc grant script. It accepts a **complete**, versioned JSON role manifest as psql data (`:'role_pairs_json'`), with the existing migration-owner and retention-operator names still supplied explicitly. The manifest contains no passwords or connection strings. Version 1 has exactly `version` and `pairs` at the top level, with `version: 1` and 1–32 pairs. Each pair has exactly `dispatcher`, `runtime`, and `dispatcher_profile`. Role names are non-empty, contain no control characters, and must resolve without truncation to exact PostgreSQL role OIDs. Supported profile values are `full` and `work_only`; there is no implicit default. `full` preserves the current dispatcher grant surface: Work discovery function, Schedule claim function, and direct `flow_dispatch` `SELECT`. `work_only` grants only the Work discovery function. Unknown fields, profiles, duplicate pairs, duplicate role names across any pair or the owner/retention role, and missing roles fail before mutation. Names remain data and are quoted as identifiers only through PostgreSQL `format('%I', ...)`; no raw manifest text becomes SQL syntax.

An illustrative manifest, stored as a reviewed non-secret deployment file, is:

```json
{
  "version": 1,
  "pairs": [
    { "dispatcher": "forwarding_dispatcher", "runtime": "forwarding_runtime", "dispatcher_profile": "full" },
    { "dispatcher": "source_dispatcher", "runtime": "source_runtime", "dispatcher_profile": "work_only" }
  ]
}
```

The initial conversion manifest lists the already deployed forwarding pair as `full` and the source pair as `work_only`. A one-pair manifest can continue to represent a one-pair store. Once a second pair exists, an old one-pair invocation or a manifest omitting either role must abort before changing a policy or grant. The manifest should live in the deployment's reviewed configuration alongside role-name declarations and be used unchanged on every schema-upgrade recipe rerun. This is a complete-set contract, not an append-only command.

### Atomic reconciliation and proof

Start a transaction and acquire the recipe's existing advisory lock **before** reading any catalog state used to identify current pairs, compare the manifest, or authorize mutations. Move the present pre-`BEGIN` role/privilege checks under that lock; checking before it would allow concurrent recipe runs to make an omission check stale. Parse the supplied manifest, then validate all listed service roles as distinct restricted `LOGIN` leaves: no `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`, database/package-object ownership, grant options, or incoming/outgoing `pg_auth_members` edges. Keep the migration owner and retention operator separate. Inspect the current managed policy targets and direct Durable ACL grantees while locked. Any previously authorized dispatcher/runtime role absent from the manifest is an error; do not interpret omission as retirement. A failed validation or final assertion rolls the entire run back.

The catalog check covers only the package-reserved `appsurface_durable` schema and its known objects, policies, schema ACL, table/column/sequence ACLs, and function ACLs. The migration owner is the required object owner and retains implicit owner rights; the one retention operator retains its existing exact allowlist. The manifest-listed pairs receive only their profile/runtime grants. `PUBLIC` receives no schema, relation, sequence, or function capability. Expand the recipe's existing single-role effective-privilege loops to every manifest role and compare package-object grants against this object-specific allowlist, including grant options and inherited access. A narrower missing grant for a manifest-listed role is reapplied; an unexpected extra grantee, broader service-role grant, or unexplained policy target fails before mutation. The canonical `PUBLIC` revokes are reapplied within the same transaction and must be verified at commit. Superuser authority and application-owned `public` schema grants are outside this package ACL check.

Build exact policy targets from the manifest rather than from the current policy contents. Include **all** runtime-role OIDs in `runtime_heartbeat_runtime_role`, `flow_dispatch_runtime_scope_select`, `schedule_dispatch_runtime_scope_select`, and `schedule_dispatch_scope_update`. Include only `full` dispatcher OIDs plus the migration owner in Flow and Schedule global-discovery/lease policies. Keep the owner-only Work contract discovery policy and the existing scope expressions, permissiveness, commands, and forced-RLS flags unchanged. Retention policies remain targeted to the one retention operator. Where the current recipe drops/recreates a runtime policy, recreate it for the complete runtime set in the same transaction. Never widen a policy to `PUBLIC` or use role membership as a shortcut.

Reconcile direct privileges per exact profile. Every dispatcher receives schema `USAGE` and Work-function `EXECUTE`. Only `full` dispatchers receive the legacy `flow_dispatch` `SELECT` and Schedule-claim `EXECUTE`. `work_only` dispatchers receive no direct Durable table, column, or sequence privilege and no other Durable function execution. Every runtime receives the existing reviewed runtime table/column/sequence/function grants, with existing RLS scope checks. Revoke `PUBLIC` privileges on the package schema, its relations, sequences, and functions, and then grant only the exact allowlists. Verify effective grants with `has_schema_privilege`, `has_table_privilege`, `has_column_privilege`, `has_sequence_privilege`, and `has_function_privilege` for every listed service role, plus direct ACL entries, grant options, memberships, ownership, policy targets, and policy expressions. A `work_only` role carrying stale Flow `SELECT` or Schedule-function `EXECUTE` is a broader-grant error, not an invitation to silently change its profile. A manifest change that would remove an existing role's capability is likewise refused; profile retirement or narrowing needs a separate reviewed procedure. Missing grants within a role's declared profile are restored. An idempotent rerun with the same manifest preserves both pairs; unexpected extra principals fail rather than being silently adopted.

Do not claim zero blocking time: policy DDL and the existing advisory lock may briefly wait on active work. Use the established bounded maintenance/drain procedure for an upgrade, and prove that the forwarding role works both before and after the transaction. Atomic commit prevents a committed state in which one pair has been replaced by the other.

### Function-only source dispatcher and host configuration

The source dispatcher uses `discover_work_dispatch` with the immutable registered Work contract snapshot already introduced by #747. It receives routing values only, not Work payload columns. A source worker configured for `DurableRuntimeSurface.Work` must complete its normal pump/recovery path with this dispatcher profile; an accidental `All`, Flow, or Schedule pass must fail closed rather than acquiring extra SQL authority. The certificate checks effective privileges, not merely intended `GRANT` statements, including inherited access (which the membership-free rule forbids). Skoolit-owned `public` schema grants remain Skoolit's separate responsibility.

The function's caller-supplied contract arrays are a selector, not authentication. A dispatcher holding the credential can request another valid Work contract's routing metadata. The test and documentation must state this rather than presenting a Work-only profile as per-contract database isolation. No Flow function is added in #823; the forwarding dispatcher retains its existing payload-free direct Flow read.

### #795 and upgrade ordering

[#795](https://github.com/forge-trust/AppSurface/issues/795) currently proposes a heartbeat preflight requiring exactly one non-public runtime role. **Target release order:** ship #823's multi-pair recipe against the current schema 10 first; its packaged recipe is authoritative for schema 10. Then #795 must change its proposed preflight *before* publishing schema 11: preflight accepts a non-empty exact restricted runtime-role set, verifies every role's membership-free leaf posture, and compares that set with the heartbeat policy and the due-health/retention function execution allowlists. The manifest-driven role recipe remains the authority for *which* runtime OIDs are authorized; read-only preflight verifies consistent installed catalog state. The schema-11 maintenance function must grant every authorized runtime role and no dispatcher, retention operator, or `PUBLIC` principal. The schema-11-capable package's recipe, not the older schema-10 package's recipe, becomes authoritative after migration 0011; rerun it with the unchanged two-pair manifest before activation. The #795 release gate includes a real schema-10-to-11 upgrade and both-pair reproof. If #795 lands first, block second-pair activation until a combined #795/#823 recipe and preflight pass that proof. Never publish a schema-11 preflight that rejects a valid two-pair store.

Operator order: review manifest and role creation; keep Source processing/activation closed; drain as required; apply pending forward migrations as migration owner; run the canonical role recipe with the complete manifest; run exact role and schema preflight; execute the disposable and connected provider-disabled certification; then use Skoolit's reviewed activation procedure. A failed recipe or preflight leaves Source closed and calls for repair/roll-forward, never a broad grant or a one-pair rerun. The manifest's role names and paired surface profiles must match the deployment's actual connection slots and hosted-surface configuration. StoreId and epoch must match the one shared store even if each lane has its own configuration fields.

## Proof and acceptance

Use a disposable PostgreSQL 16 database and the repository's existing role/schema integration harness. No production credential or provider data is used.

1. Establish the forwarding `full` pair with the existing schema and a synthetic Work/Flow/Schedule fixture. Record its policy/grant catalog and complete one bounded pass.
2. Create the second restricted pair, run the two-pair manifest recipe, and repeat the first lane's Work, Flow, Schedule, health, and scope-fence checks. The first lane must retain its effective privileges and processing results.
3. With the source `work_only` dispatcher, prove allowed Work-function execution returns only the requested eligible routing candidates and no payload; direct reads of `dispatch`, `work`, `flow_dispatch`, Schedule tables, all Durable sequences, and unapproved function calls fail. Prove the Source Work-only pump and recovery path succeeds; Flow/Schedule attempts fail closed under that dispatcher profile.
4. Verify both runtimes pass existing scoped mutation and heartbeat tests, with no ownership, bypass, membership, broad destructive privileges, or grant options. Explicitly verify that a separate runtime login alone does not enforce a lane-specific row partition.
5. Rerun the identical manifest and compare effective catalog state. Run a manifest omitting the first pair, one with duplicate/aliased roles, one with an invalid profile, and one with a hostile extra grant/policy role; each must fail atomically without changing either working pair. Test unexpected `PUBLIC` and membership privilege drift.
6. Apply a forward schema-upgrade fixture, rerun the same manifest, and prove both pairs again. Include #795's heartbeat function/preflight once that change lands; its one-role assertion must become an exact set assertion.
7. Verify provider/package docs, packaged recipe, local example, release/rollout guidance, and the Skoolit certificate all describe the same manifest, Work-only surface setting, and deployed-lane claim. The first-pair proof runs before and after second-pair enrollment.
