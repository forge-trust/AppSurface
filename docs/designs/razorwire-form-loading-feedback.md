# Design: Immediate RazorWire form loading feedback

- Branch: main

## Problem Statement

A user submits a RazorWire form while the serverless host wakes. The click appears to do nothing, so they may click again or abandon the task. This occurred in a consumer application, although the exact form route and cold-start duration have not been recorded. The first release covers remotely submitted rw-active forms; navigation, islands, and arbitrary app requests can join later.

[Turbo](https://turbo.hotwired.dev/reference/attributes) already sets form aria-busy, disables the initiating submitter, supports data-turbo-submits-with, and shows its [page progress bar](https://turbo.hotwired.dev/handbook/drive#displaying-progress) after 500 ms. In the installed Turbo runtime, frame-targeted form submissions do not start that bar. RazorWire's current data-rw-submitting hook depends on failed-form UX; forms with that feature off have no RazorWire loading state. Lazy anti-forgery can pause before turbo:submit-start, creating another silent wait.

## What Makes This Cool

A form can feel responsive even when its server is asleep. The application supplies the spinner, wording, and layout; RazorWire supplies a reliable activity signal and a quiet default top bar if the app supplied no indicator. The same contract works for a small form inside a Turbo Frame and a full-page submission. The first affected app proves the behavior with a real delayed form; other apps receive it through the RazorWire package.

## Constraints and Premises

- Show feedback only after Turbo accepts a remote form submission, after browser validation and any confirmation. Do not infer whether a server is cold.
- Begin before lazy anti-forgery token preparation can stall. Keep feedback until the submission reaches a terminal state, without a duration-based reset.
- Build on the approved May form design: app-authored indicator markup and CSS stay app-owned. The package may own only the fallback bar and state hooks.
- Reuse Turbo's aria-busy and initiating-submitter behavior where reliable. RazorWire owns the additional same-form duplicate guard and any controls it disables.
- Keep public API form-focused. Use an internal activity ledger that can accept other request sources later, without publishing a generic request API now.
- Preserve native form behavior without JavaScript, existing failure UX and events, anti-forgery, Turbo navigation, and server-side idempotency responsibilities.
- “Both” means a reusable RazorWire package feature and an adoption proof in the affected app. Indicator precedence still shows one indicator for a submission.

## Cross-Model Perspective

An independent combo/sub cold read recommended one activity lifecycle driving app-authored local indicators and a top bar. It identified the pre-submit lazy anti-forgery wait and its failure cleanup as the hard boundary. It challenged a strictly form-only internal API: future navigation should be able to join the activity ledger. We accepted extensible internals while keeping this release's public contract form-focused. The second opinion preferred an opt-in bar; this design keeps the fallback enabled by default because the user's request includes a failsafe when an app has no indicator.

## Approaches Considered

- **A — App recipe and docs:** fastest local relief using Turbo attributes and app CSS, but repeats work in every app and leaves default fallback and token preparation uncovered.
- **B — RazorWire form loading layer plus consumer proof:** chosen. Covers the agreed form scope with one app-stylable contract and a default fallback.
- **C — Public request activity API now:** unifies forms and navigation immediately, but commits to unproven non-form semantics and delays the observed consumer fix.

## Recommended Approach

### Public contract

Add RazorWireFormOptions.Loading with these settings:

| Setting | Default | Meaning |
|---|---:|---|
| Enabled | true | Global loading feature switch; false takes precedence over form attributes and leaves failure UX unchanged. |
| ShowFallbackBar | true | Show the package top bar when no applicable app indicator exists. |
| PreventDuplicateSubmissions | true | Block a second submission of the same pending form, including Enter, alternate submit controls, and external form-associated controls. Other forms remain usable. |

The current issue's proposed DisableSubmitControls name should become PreventDuplicateSubmissions because the behavior is a submission guard, not merely disabled styling. The runtime may disable submit controls for visible affordance, but it must preserve and restore only states it owns.

Form attributes:

| Attribute | Meaning |
|---|---|
| data-rw-loading="off" | Opt this rw-active form out of loading state, bar, and loading-layer duplicate guard. |
| data-rw-loading-lock="true" or "false" | Override PreventDuplicateSubmissions on this form when loading is enabled. Invalid values use the global default. |
| data-rw-loading-boundary | Declare a form-local or ancestor loading scope, including a Turbo Frame or body. |
| data-rw-loading-indicator | App-authored element owned by its nearest loading boundary. Initially hidden; app supplies accessible status text and styling. |
| data-rw-loading-state="pending" | Runtime state hook on the form and selected boundary while activity is pending. |
| data-rw-loading-fallback | Package-owned top bar selector and styling hook. |

Every enabled rw-active form gets a loading ownership marker independent of data-rw-form and failed-form mode. Loading must not turn on failed-form headers, messages, or events for forms that opted out of failure UX. The boundary attribute is presence-only: an empty value, "true", or even "false" declares a boundary; remove the attribute to opt out. An indicator belongs to its closest ancestor boundary, and only the first owned indicator in document order is selected for that boundary. Authors should place one indicator per boundary. Starting at the form, search its ancestor boundaries outward for the first one with an owned indicator. A body boundary is site-wide only when the submitting form is inside that body; an indicator elsewhere on the page is not applicable. Search past a boundary without an owned indicator.

Precedence is: Loading.Enabled=false disables this whole layer, including the fallback; then a form with data-rw-loading="off" opts out; otherwise use the nearest applicable indicator; otherwise use the fallback if ShowFallbackBar=true; otherwise show no package indicator. A selected app indicator suppresses the fallback bar. The package snapshots each selected indicator's original hidden state and restores it after the last activity using it. When a form or boundary moves from zero to one pending activity, snapshot its prior data-rw-loading-state value and set "pending"; restore the exact prior value or absence at one to zero. Do not author this runtime state attribute yourself. One shared boundary's state and indicator stay pending until its last associated activity settles. An app may style the fallback with documented data attributes and CSS custom properties following [RazorWire's generated UI contract](../../Web/ForgeTrust.RazorWire/DESIGN.md).

Example markup, with app-owned status text:

~~~html
<body data-rw-loading-boundary>
  <span data-rw-loading-indicator hidden role="status" aria-live="polite">Processing…</span>
  <form rw-active="true" data-rw-loading-boundary>
    <button type="submit">Save</button>
    <span data-rw-loading-indicator hidden role="status" aria-live="polite">Saving…</span>
  </form>
</body>
~~~

This form shows “Saving…”; a form elsewhere under body shows “Processing…”. A form with no applicable app indicator gets the package bar. The bar includes a polite “Processing…” status and a decorative visual line; reduced-motion users receive a steady state. App indicators should remain in place without layout shift where the app's design allows. Focus stays on the submitter unless existing failure UX moves it.

### Lifecycle and cleanup

The internal activity ledger tracks a unique accepted submission, its form, selected boundary, and indicator. Start it on turbo:before-fetch-request when the event target is a loading-owned form. In the installed Turbo version, this event occurs after browser validation and Turbo confirmation, before RazorWire's lazy anti-forgery listener can pause the request. Listener order must not affect the result: the loading listener handles that same dispatched event before an asynchronous token result. It shows pending state by the next paint. Turbo submit-start may advance an internal phase but must not create a second activity. Turbo submit-end normally terminates it. Token-refresh rejection, network error, cancellation, form/frame replacement, and page departure must also settle it exactly once. Two forms sharing a boundary keep it visible until both settle. If locking is disabled, overlapping requests from one form must have distinct identities and counts.

The installed lazy anti-forgery failure path currently rejects while Turbo's before-fetch-request continuation is paused. Implement a settle/cancel path that clears loading even if Turbo does not emit submit-end, leaves the form able to retry, and never sends an unprotected form request. Keep the existing failure UI responsible for explaining why a submit failed. A Playwright regression test verifies the behavior against the installed Turbo runtime; a failure is an ordinary failing feature test to fix, not a separate release decision.

When locking is enabled, a document capture-phase submit listener cancels a new submit event for a form that already has a pending activity, before Turbo's bubbling form observer can start another request. It calls preventDefault and stops propagation; it does not reset the form or change the first activity's counts. This covers a second button, Enter, an external form-associated submitter, a later submitter.click(), and a later form.requestSubmit() while pending. Direct form.submit() bypasses both submit events and Turbo enhancement and is outside this contract. The first submission is not locked until the accepted-request event, so a canceled Turbo confirmation leaves no stale lock. Visible disabled states are an affordance; the capture guard is authoritative. Test two rapid physical user actions and later programmatic requestSubmit/click paths. The app may set data-rw-loading-lock="false" to permit overlapping accepted requests.

When any managed form is pending, a document state marker suppresses Turbo's delayed form bar. If the package fallback bar is visible and a separate Turbo visit begins, keep the fallback as the shared visible progress signal and keep Turbo's bar suppressed until the fallback settles; if Turbo still has a pending visit then, its bar becomes visible under its normal timing. If an app indicator is selected and a separate visit begins, allow Turbo's navigation bar so the visit retains feedback; the app indicator continues to represent the form. A visit initiated by the form response may take over after the form request settles. Observe turbo:visit and terminal navigation events for this bar arbitration only; do not expose a navigation loading API in this release. Browser-test the overlap and canceled/failed visit paths. Never hide an unrelated navigation's only visible feedback.

### Consumer adoption and distribution

Ship the runtime, C# options, generated static asset, public contract manifest, guide, and runnable RazorWire MVC example together. RazorWire is currently consumed from a configured package feed or source build; do not claim public NuGet v0.1 availability until the publish path is live. After package verification, update one real form in the affected app to use a local indicator and verify the site-wide fallback on another form. That app retains its own visual design. Document version and asset-build requirements for package consumers in the [RazorWire start page](../../Web/ForgeTrust.RazorWire/README.md) and a focused loading guide.

## Success Criteria

1. An accepted form submission shows local, site-wide, or fallback feedback by the next browser paint, before a controlled five-second response. Browser validation rejection and canceled confirmation show no pending state.
2. A ten-second wait keeps feedback visible; completion clears it without a timer. In a Playwright test, hold the lazy token response and verify immediate loading before the form POST; then fail the token response and verify loading clears, no form POST occurs, and a later token success permits one retry POST.
3. Form-local indicator wins over site-wide; site-wide wins over fallback. One indicator is visible per submission. Full-page and frame forms show no duplicate Turbo bar after 500 ms.
4. Default locking allows one request for two quick user actions on the same form, including Enter and another associated submitter. A later requestSubmit() or submitter.click() while pending is blocked; direct form.submit() remains native and outside the contract. Other forms can submit. Per-form lock-off permits overlapping requests and correct counts.
5. Success, handled/unhandled HTTP failure, network error, cancellation, DOM replacement, and page departure clear state once. Pre-disabled controls remain disabled.
6. Loading works when EnableFailureUx=false and data-rw-form-failure="off" without re-enabling failure-only behavior. Native submission still works when JavaScript is unavailable.
7. The MVC example and one real form in the affected app demonstrate the API. A controlled delayed consumer check records the time from first click to visible feedback; production cold-start latency remains an observation, not an invented target.

## Open Questions and Risks

- The exact form path in the affected app is unrecorded. Pick one before claiming the production experience is fixed.
- The bar arbitration strategy depends on Turbo visit events and CSS state. Verify it against the installed Turbo version, including a visit overlapping a pending frame form.
