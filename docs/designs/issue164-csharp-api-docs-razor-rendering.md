# Design: C# API Docs Semantic Tree and Razor Partial Rendering

## Problem Statement

`CSharpDocHarvester` currently decides C# API-document semantics and emits the finished HTML in the same pass. Its `StringBuilder` output is then treated as both presentation and data by the aggregation pipeline: source-provenance placeholders are replaced, markup is sanitized, text is extracted for search, child namespaces are prepended, and Markdown README content is spliced into namespace pages. `Details.cshtml` finally emits the resulting string with `Html.Raw`.

This makes API-document structure, anchors, styling, wayfinding, and rendering behavior hard to evolve independently. Issue #164 must establish an incremental, internal rendering boundary without breaking canonical paths, fragments, search behavior, provenance links, or existing C# API content.

## What Makes This Cool

The harvester stops being a hidden HTML renderer. It becomes a semantic producer that makes a namespace page legible as data: types, enums, method groups, overloads, properties, signatures, source declarations, and XML-documentation nodes. Razor then owns the markup that readers see. A maintainer can change one visual/API-document unit and test it directly rather than discovering a buried string-concatenation branch.

## Constraints

- Keep `DocNode`'s public positional constructor and deconstructor unchanged. Its current `Content` property remains the compatibility bridge for Markdown, JavaScript, and any unmigrated document source.
- Keep the new C# API tree and rendering partials internal. Do not introduce a public renderer/template extension point without an adopter-driven follow-up.
- Start with a namespace-page vertical slice. It must exercise type and enum sections, method groups and overloads, properties, XML docs, outlines, anchors, and source provenance.
- Preserve behavioral contracts, not whitespace: canonical paths, fragment IDs, outlines, provenance links, safe encoding, search-visible text, and key semantic elements/attributes.
- Introduce an internal, non-path-based C# render-kind discriminator. The harvester/aggregation projection sets it and the details view model consumes it for C#-specific shell behavior and shell-owned heading preservation. Do not continue inferring C# rendering from `Path.EndsWith(".cs")`; namespace pages are extensionless.
- Do not block or expand #109. Wayfinding, Markdown rendering, JavaScript API rendering, and an all-source `DocContent` framework stay outside #164.
- Treat typed Razor output as encoded/constrained output, not as an HTML string to sanitize afterward. Retain the sanitizer for legacy and Markdown content.

## Premises

1. **The typed C# tree must be authoritative.** Once a namespace page is migrated, API markup, XML-doc content, anchors, outlines, provenance links, and search text derive from its typed projection. No later regex or HTML-string rewrite may modify typed C# output.
2. **XML documentation is part of the first slice.** `summary`, named parameter/type-parameter rows, returns, remarks, examples, exceptions, paragraphs, code, lists, `see`, `paramref`, and `typeparamref` are semantics already recognized by the harvester. Keeping them as rendered HTML would preserve the core coupling #164 is meant to remove.
3. **Aggregation needs explicit typed projections.** `DocAggregator` currently depends on `Content` for source-link resolution, sanitization, search text, child namespaces, and README composition. The C# path needs typed equivalents; moving tags to a partial alone would only relocate the problem.
4. **The public data shape stays stable.** The internal projection is stored alongside cached/resolved C# document state and keyed by stable canonical/source identity, instead of redesigning public `DocNode`.

## Cross-Model Perspective

The independent review agreed with the selected architecture and found no premise to reverse. Its main warning is the two-sources-of-truth failure mode: a typed tree plus post-hoc `DocNode.Content` rewrites would silently retain the old contract. It recommends that the namespace vertical slice include a typed XML-doc AST, typed signature tokens, typed provenance, typed search text, and behavioral parity tests while keeping Markdown, JavaScript, public customization, and #109 work out of scope.

## Approaches Considered

- **Thin typed namespace adapter with one main partial — rejected.** It removes harvester strings quickly but moves too many independently evolving concerns into a new single Razor hotspot.
- **Semantic tree plus focused Razor partial suite — selected.** It establishes the right internal units without widening into an all-document rendering rewrite.
- **Generic internal document-content union across C#, Markdown, and JavaScript — rejected.** It is a credible future architecture but exceeds #164's incremental C# scope.

## Recommended Approach

Build an internal `CSharpNamespaceDocument` projection that is the source of truth for a migrated namespace page. It contains namespace identity, child-namespace links, API sections, typed outlines, metadata, typed symbol-source declarations, a controlled README-intro bridge, and a typed text projection for search.

The API section model consists of type and enum sections, method groups, overloads, property sections, and typed signature parts. XML documentation is a constrained rich-content tree: block nodes for paragraphs, named rows, returns, remarks, examples, exceptions, lists, and code; inline nodes for text, code, references, and parameter/type-parameter references. Values remain raw semantic data until Razor encodes and renders them.

Use focused internal partials for the namespace page, type/enum sections, method groups and overloads, properties, signatures, and XML-documentation content. `Details.cshtml` remains the shell and dispatch point for metadata, breadcrumbs, outline, wayfinding, and C#-vs-legacy content selection. It does not become an API-document renderer.

The aggregation migration is explicit:

- preserve `DocNode` construction and populate an internal C# projection for namespace pages;
- set the internal C# render-kind discriminator from that projection, then replace `DocDetailsViewModel.IsCSharpApiDoc` as the Details render selector rather than inferring behavior from the extensionless namespace path;
- resolve source-link URLs from typed source declarations at render/projection time, preserving the contributor policy and ambiguity behavior;
- produce outlines and search text from typed C# data;
- represent child namespaces and namespace README introduction as controlled typed/bridge regions, never by string insertion into rendered API markup;
- continue sanitizing and resolving legacy HTML only for Markdown, JavaScript, and unmigrated paths.

The rollout boundary is explicit. Only namespace documents with a populated C# semantic projection render through the partial suite in this issue. Any non-migrated C# artifact remains on the current HTML-plus-aggregator path, as do Markdown and JavaScript documents. The dispatch must make that distinction per resolved document, not from a global feature toggle or a source-file suffix. Keep the legacy renderer callable until the compatibility matrix is green; its removal requires both the representative parity suite and a transition checklist confirming that no remaining C# page selects it.

Migration order:

1. Add behavioral compatibility fixtures for one representative namespace page and document the contract matrix.
2. Add the internal C# semantic model, XML-doc nodes, typed signatures, text projection, and structural harvester tests while retaining the present renderer only as a narrow temporary comparison aid.
3. Adapt cached aggregation/details projection for typed C# pages, then add the Razor partial suite and switch the namespace slice to it.
4. Run the representative parity suite against both routes, keeping legacy tests that assert browser/search behavior while replacing harvester-string assertions with structural semantic-tree assertions.
5. Delete the C# raw-HTML generation and post-render C# mutation paths only after the transition checklist is complete; leave non-C# legacy paths untouched.

### Amended Internal Contract

Add an internal `CSharpNamespaceDocument?` non-positional property to `DocNode`, following the existing non-positional `GeneratedApiSymbol` pattern. It is not part of the public positional constructor, deconstructor, serialization contract, or a custom-harvester extension point. Populate it only from the exact built-in `CSharpDocHarvester` implementation; derived/custom harvesters continue through their current public `IDocHarvester` result and therefore remain legacy content paths.

`DocNode.Content` remains present and unchanged for Markdown, JavaScript, and non-migrated documents. For a migrated C# namespace it is no longer the rendering, search, or composition authority. Introduce one internal predicate, named for reader semantics rather than storage such as `HasReaderContent`, that returns true for either non-empty legacy content or a populated `CSharpNamespaceDocument`. Replace every direct “empty content means stub” decision in the slice with that predicate, including route collision ordering, path resolution, sidebar stub classification, and sequence eligibility. This prevents a typed namespace page from losing precedence merely because it no longer carries generated HTML.

The aggregator must preserve this internal property through every `DocNode` copy it makes today: sanitization, internal-link rewriting, and namespace README merge. It must not sanitize, regex-rewrite, or `Html.Raw` the typed C# document. `DocDetailsViewModel` receives an internal typed-document/render-kind member, and `Details.cshtml` dispatches by that member only. A non-null metadata language value or a `.cs` suffix is not sufficient evidence that the typed partial should render.

The semantic tree is immutable after harvesting. It contains the exact display ordering and source-derived IDs required by the current page:

- namespace identity, canonical source path, child-namespace links, and a typed outline;
- type and enum sections, method groups, overloads, properties, signature tokens, and source declarations;
- constrained XML block and inline nodes, retaining raw semantic text until Razor encodes it;
- a typed reader-text projection for search, independent of rendered HTML;
- a typed namespace composition region for child groups, optional sanitized Markdown README intro, validated entry points, and generated API sections.

`CSharpNamespaceDocument` is the only C# source used by partials, outlines, source links, and search. A temporary legacy comparator may exist in tests while the migration is being developed, but the production snapshot must not retain both rendered C# HTML and a typed C# tree as two authoritative representations.

### CEO Review: Strategy and Scope

#### 0A. Premise Challenge

The problem is real: `CSharpDocHarvester` currently owns Roslyn extraction, XML interpretation, HTML construction, CSS class selection, source-link placeholders, and namespace page hierarchy. A partial-only rewrite would leave aggregation string mutations in place, so the chosen typed boundary is the smallest route to independently evolvable API docs.

Premise 1, “the typed C# tree is authoritative,” is accepted with the amended rule that every current `Content`-presence consumer moves to a semantic predicate. Premise 2, typed XML documentation in the first slice, is accepted because keeping XML as pre-rendered HTML would preserve the main unsafe coupling. Premise 3, explicit aggregation projections, is accepted and expanded to namespace entry points, which are currently a second regex-splice system. Premise 4, stable public positional shape, is accepted with an internal non-positional property and no custom rendering hook.

Doing nothing keeps visual changes hostage to a 1,267-line extractor/string-builder and makes every new docs-wide feature a second C# exception path. The higher-level all-source `DocContent` union is attractive but would force Markdown and JavaScript migrations without an adopter or a concrete shared failure. ### CEO Review Sections

#### 1. Architecture Review

The current architecture has two hidden renderers: `CSharpDocHarvester` builds the API HTML and `NamespaceEntryPointPanelRenderer` parses that HTML to build more HTML. The amended plan removes both from the typed path while retaining the legacy pipeline for every other source. The only new coupling is the intentional `DocNode` internal typed projection, which is less coupled than a sidecar map because it survives immutable snapshot copies as one document identity.

```text
Before: CSharpDocHarvester -> Content HTML -> [sanitize, rewrite, splice] -> Details Html.Raw
After:  CSharpDocHarvester -> CSharpNamespaceDocument -> [typed compose, typed text] -> Details partials
                                                     \-> legacy sources keep Content pipeline
```

The typed path has four specified data outcomes: absent projection selects the legacy route; a present projection with no sections still has reader content if it has groups/intro/entry-points; malformed XML omits only that XML node and emits the existing warning; an unreadable/oversize source is a non-fatal harvest diagnostic with no fabricated typed page. Snapshot invalidation remains the existing cache invalidation mechanism. Rollback is a code revert; there is no database change, remote dependency, or state migration.

#### 2. Error and Rescue Registry

| Codepath | Failure | Rescue/action | Reader outcome | Evidence |
| --- | --- | --- | --- | --- |
| C# source read/parse | file too large, unreadable, or syntax parse issue | Existing per-file diagnostic and continue behavior | Other docs remain available; no invented page | Harvester regression tests. |
| XML conversion | malformed XML | Log existing C# XML warning, omit only documentation subtree | Signature/anchor still render if the symbol otherwise qualifies | XML malformed fixture. |
| Typed source URL resolution | disabled contributor policy, invalid URL, duplicate/missing anchor | Omit link and log the existing debug reason | No dead or unsafe Source link | Source-link matrix. |
| README composition | namespace target cannot resolve or source is excluded | Preserve current consume/diagnostic behavior and do not attach an intro | API page stays readable | README/exclusion tests. |
| Entry-point target | no matching typed anchor | Render `Target unavailable` status and existing warning diagnostic | Reader sees an honest non-link state | Entry-point typed composition test. |

There is no catch-all rescue proposed. Every non-fatal continuation preserves the current diagnostic code/severity where one exists.

#### 3. Security and Threat Model

| Threat | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| XML documentation contains hostile text or markup | Medium | High | Parse only known XML semantics; Razor encodes text/code/reference fields; no generated C# `Html.Raw`. |
| Unsafe source URL template/metadata | Low | Medium | Reuse `NormalizeContributorHref`; a rejected URL renders no link. |
| README bridge leaks unsanitized HTML | Medium | High | Continue legacy sanitization/link resolution before typed composition; only that bounded bridge may render trusted sanitized HTML. |
| Anchor or href injection | Low | Medium | IDs remain source-derived through existing safe-ID rules; typed links use route builder/validated fragments, not string concatenation. |

No endpoint, authorization boundary, secret, dependency, or data-classification surface changes. The security-critical acceptance check is that no typed C# semantic text reaches `Html.Raw`.

#### 4. Data Flow and Reader Interaction Edge Cases

```text
source present -> semantic harvest -> snapshot composition -> Details partial -> reader anchors/search
source missing -> no typed projection -> existing legacy/fallback route
source empty   -> typed namespace may still render groups/intro; otherwise no published stub page
```

### Required Architecture and Ownership

    CSharpDocHarvester
      exact internal DocHarvestContext overload
          -> immutable CSharpNamespaceDocument / symbols / anchors / provenance / reader text
          -> DocNode.CSharpNamespaceDocument (internal, non-positional)
          -> DocAggregator snapshot transforms (record with copies only)
          -> route, outline, search, namespace composition, source-link projection
          -> DocsController render kind
          -> Details shell (one H1) + Views/Docs/CSharp typed partials

    public CSharpDocHarvester.HarvestAsync and any derived/custom harvester
          -> existing legacy serialized Content
          -> existing sanitize/link-rewrite/Html.Raw compatibility route

The semantic projection must be immutable by the time it reaches DocNode: arrays/read-only
collections, stable anchor identifiers, display names, declaration kind, summary/remarks,
parameters/type parameters/returns/value/exception data, inheritance/implements/source provenance,
entry-point membership, and a source-derived ReaderText field. The projection is internal; neither
public CSharpDocHarvester contracts nor direct consumers gain a new renderer API in #164.

The exact type check on the internal harvest-context overload is intentional compatibility policy.
Only the built-in CSharpDocHarvester may attach the typed CSharpNamespaceDocument. A direct public
call and any derived/custom harvester must keep producing legacy HTML Content and must not
accidentally select the typed Razor branch when later aggregated.

All DocAggregator transformations that logically preserve a document must use a record with
expression. This includes source-placeholder replacement, sanitization, link rewriting, and README
namespace composition. Tests must demonstrate preservation of CSharpNamespaceDocument,
GeneratedApiSymbol, and HasJavaScriptApiLifecycleProvenance through each pass. A path-keyed sidecar
cache and manual new DocNode copy lists are prohibited.

### Rendering, Content Semantics, and Security Contract

Add a named DocNode.HasReaderContent predicate for user-facing content presence. It must return true
for a typed CSharp namespace even when legacy Content is empty. Where the old condition really means
an empty fragment placeholder, use a separate named IsFragmentStub predicate rather than silently
repurposing content emptiness. Apply this distinction to route collision tie-breaking, path
resolution, sequence joining, and sidebar type-anchor classification.

Details.cshtml always has shell ownership of the document H1. The current C# special case that both
retains a Markdown H1 and hides the page H1 must be removed. The typed C# partials render no H1;
the final page has exactly one visible H1 for both prefixed and unprefixed deployments.

Namespace entry-point panels must consume typed anchor data directly. They must not regex-parse
legacy HTML. Invalid or unresolved entry-point references remain visible only through the existing
safe diagnostic/unresolved treatment; they are not silently promoted into guessed anchors.

Typed fields are Razor-encoded by default. Typed source links are emitted only after the existing
contributor URL normalization / Docs URL builder validation, including PathBase. Do not introduce a
new cref hyperlink resolver in this issue: current cref rendering is encoded display text, and any
future clickable cref implementation requires its own allowlist and threat-model review. The only
permitted Html.Raw use in this path is the already-sanitized README bridge inside the narrow
namespace-intro partial; generated C# XML text, attributes, headings, labels, and URLs never cross
that boundary raw.

The search payload must branch before legacy HTML stripping. Typed namespaces contribute their
snapshot-time ReaderText and do not emit a legacy Source label or source URL. Legacy documents retain
their present string-cleanup behavior.

### Failure and Health Semantics

| Failure | Harvest result | Health/diagnostic behavior | User-visible behavior |

#### Maintainer-Facing Rendering Boundary

projection is an internal implementation detail of the exact built-in aggregation path.
`CSharpDocHarvester` owns the compatibility serializer: it derives legacy-compatible
generated HTML from the same local parsed result rather than keeping a second parser or
hand-maintained renderer. When that public output later enters a hosted aggregate, it still
passes through the existing `DocAggregator` sanitizer and link-rewriter boundary; a direct
public harvester call preserves the current generated-HTML contract and does not imply that
aggregation already occurred.

#### Diagnostics and Recovery Contract

The plan adopts the existing structured harvest-health shape (`Code`, `Severity`,
`Problem`, `Cause`, `Fix`) and explicitly separates local recoverability from aggregate
health:

| Condition | Diagnostic and retained output | Aggregate health | Maintainer recovery |
| --- | --- | --- | --- |
| Malformed XML comment | `appsurfacedocs.csharp.xml_comment_malformed`, **Warning**; declaration, anchor, signature, and sibling sections remain; only the malformed documentation subtree is omitted | `Healthy` when strict harvesters otherwise succeed | Repair the indicated XML at the safe relative path and line/column |
