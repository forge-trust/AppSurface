# Design: AppSurface Logical Configuration Key Contract

## Problem Statement

AppSurface does not currently have one definition of configuration-key identity:

- `FileBasedConfigProvider` traverses dot-separated `JsonObject` properties with case-sensitive lookup.
- `EnvironmentConfigProvider` uppercases keys, treats both `.` and `-` as hierarchy, and also probes flattened aliases.
- LocalSecrets preserves key case, rewrites `__` to `:`, and stores identities with ordinal comparison.
- Google Secret Manager matches explicit keys and convention prefixes with case-sensitive ordinal operations, then applies a lossy secret-id normalization.
- Configuration audit registries and source maps already compare many paths with `OrdinalIgnoreCase`.

The result is a portability failure: an application key can resolve from one provider, miss from another, and appear
under yet another identity in diagnostics. It also diverges from the .NET configuration contract, where logical keys are
case-insensitive, `:` is the hierarchy delimiter, environment variables encode `:` as `__`, and later providers may
override earlier providers. See the [.NET configuration-key guidance](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0),
[custom-provider guidance](https://learn.microsoft.com/en-us/dotnet/core/extensions/custom-configuration-provider),
and the runtime's [`ConfigurationProvider` implementation](https://github.com/dotnet/runtime/blob/main/src/libraries/Microsoft.Extensions.Configuration/src/ConfigurationProvider.cs).

## What Makes This Cool

An application developer declares `Payments:ApiKey` once and can prove that it retains the same identity when the value
moves among JSON, environment variables, LocalSecrets, and Google Secret Manager. The feature is not merely
case-insensitive lookup; it is an executable portability promise:

```text
logical key              file JSON              environment             remote mapping
Payments:ApiKey          Payments / ApiKey      PAYMENTS__APIKEY        exact external id
payments:apikey          same key                same key                 same key
Payments:Api-Key         distinct key            PAYMENTS__API-KEY       explicit or safe convention
```

Provider authors receive the same kernel and a conformance package, so a provider can demonstrate that it preserves
identity, rejects ambiguous source entries before normalization, matches prefixes on segment boundaries, and reports
safe provenance. This creates the foundation for a future value-safe `config explain Payments:ApiKey` command without
making that larger command part of this change.

## Constraints

1. Optimize the public contract for application developers while giving provider authors an enforceable type and test
   contract.
2. Preserve AppSurface's environment-first override, remaining provider priority, missing-value fallback, fail-closed
   terminal diagnostics, and object patching behavior.
3. Do not change environment-name casing or identity; this design concerns configuration keys only.
4. Keep logical identity separate from source spelling and exact external identifiers. Never lowercase or rewrite a
   Google resource name, LocalSecrets backend identity, filename, or diagnostic source locator as a side effect of key
   comparison.
5. Detect collisions before inserting entries into a case-insensitive dictionary. Equal values do not make a collision
   safe.
6. Diagnostics may expose logical keys and already-approved source identifiers, but never configuration values, secret
   payloads, credentials, or raw provider exceptions.
7. Retain deterministic file-layer and provider precedence. A deliberate override is not a collision.
8. Provide a bounded migration for AppSurface's existing dot-delimited input; do not support two permanent logical
   syntaxes.
9. Fully document every changed public and internal API, including defaults, provider-author guidance, migration
   behavior, pitfalls, and canonical examples.
10. Verify nearly all changed branches, including malformed keys, casing variants, separator distinctions,
    representability failures, collisions, precedence, aliases, prefix boundaries, collection paths, and concurrent
    lookups.
11. Treat the provider SPI change as an intentional coordinated pre-1.0 source and binary break. AppSurface packages
    currently use `VersionPrefix` 0.1.0; all built-ins and dependent packages ship together, and third-party provider
    authors receive a compiler-directed migration plus release notes. Do not hide the break behind an optional interface
    that would preserve two provider contracts indefinitely.

## Premises

1. `Payments:ApiKey` and `payments:apikey` are the same logical AppSurface key.
2. `:` is the only logical hierarchy delimiter. Dots, hyphens, underscores, and slashes are ordinary segment content.
3. Logical equality and hashing use `StringComparer.OrdinalIgnoreCase`; no culture-sensitive comparison or Unicode
   normalization is applied.
4. Nested JSON and provider-native identifiers are boundary encodings of a logical key, not alternative logical
   syntaxes.
5. Ambiguity inside one source layer fails closed. Different source layers with documented precedence may intentionally
   provide the same logical key.
6. All key-aware paths—declaration, direct lookup, prefixes, caches, diagnostics, audit discovery, LocalSecrets, file
   configuration, environment variables, and remote providers—must use the same parser and equality contract.
7. Existing dot paths are temporary migration input. Ambiguous legacy input is rejected rather than guessed.

## Cross-Model Perspective

The independent review agreed with the logical-key kernel and identified one missing requirement: a provider must prove
that a key is representable before its native encoding can collapse it with another key. It also called out
segment-aware prefix matching: a `Payments` convention may claim `Payments:ApiKey`, but must not claim
`PaymentsArchive:ApiKey`.

The review recommended making the first public proof one command that exercises every built-in provider, with failures
for case variants, dotted segments, hyphen distinctions, same-source collisions, cross-provider precedence, prefix
boundaries, and legacy ambiguity. It also recommended a reusable provider conformance suite. These recommendations are
included below. A richer `config explain` experience is deliberately deferred.

## Decisions

- Introduce one immutable `AppSurfaceConfigKey` value object in `ForgeTrust.AppSurface.Config`.
- Parse application-facing keys as colon-delimited paths and compare them with `OrdinalIgnoreCase`.
- Preserve the caller's spelling on the value object; identity does not have a lowercase canonical form. Reports choose
  a deterministic representative spelling defined below.
- Make the typed key the required provider-facing API. Keep string conveniences at application boundaries, where they
  parse once before resolution.
- Build source indexes through one shared projection primitive that retains the logical key, source spelling, source
  layer, and exact external identifier.
- Reject same-layer collisions and unrepresentable native encodings before normalized lookup.
- Match provider conventions and audit ancestry by complete segments, never raw `StartsWith`.
- Change generated nested `ConfigKeyAttribute` paths from `Parent.Child` to `Parent:Child`.
- Treat nested JSON properties as segments; a JSON property containing `.` remains one segment.
- Preserve exact-key overrides across documented file layers and across providers. A case-only spelling change across
  file layers is an error, not a silent override.
- Ship the migration in three release trains: compatibility default, strict default, then removal.
- Build the conformance matrix and executable `examples/config-key-contract` proof in the contract slice. Publish a
  framework-neutral `ForgeTrust.AppSurface.Config.Testing` package only after the built-in contract has stabilized.

## Logical-Key Kernel

### Public shape

Add the following public API. These names and signatures are part of the implementation contract; changing them requires
an explicit plan amendment rather than an implementation-time naming pass:

```csharp
public sealed class AppSurfaceConfigKey : IEquatable<AppSurfaceConfigKey>
{
    public string Value { get; }
    public ImmutableArray<string> Segments { get; }

    public static AppSurfaceConfigKey Parse(string value);
    public static bool TryParse(
        string? value,
        [NotNullWhen(true)] out AppSurfaceConfigKey? key);
    public static AppSurfaceConfigKey FromSegments(params string[] segments);

    public bool IsSameOrDescendantOf(AppSurfaceConfigKey prefix);

    public bool Equals(AppSurfaceConfigKey? other);
    public override bool Equals(object? obj);
    public override int GetHashCode();
    public override string ToString();
}
```

`Value` and `ToString()` return a colon-delimited rendering using the spelling supplied to `Parse` or `FromSegments`;
this is not a normalized casing. Equality and hashing use `StringComparer.OrdinalIgnoreCase`. `Segments` is built with
`ImmutableArray.CreateRange`; no constructor or property exposes the caller's mutable array. The type does not implement
ordering; deterministic output orders keys by `Value` with `StringComparer.OrdinalIgnoreCase` and then
`StringComparer.Ordinal` as a tie-breaker.

`FromSegments` throws `ArgumentNullException` when the array is null, `ArgumentException` when it is empty, and
`ArgumentException` naming `segments` and the failing index when an element is null or violates the segment grammar.
It validates each element as one literal segment, so `"Microsoft.Hosting.Lifetime"` remains one segment, copies the
array, and joins the elements with `:`. `Parse` and `FromSegments` therefore produce equivalent values for equivalent
segment sequences.

`IsSameOrDescendantOf` compares segments. `Payments` matches itself and `Payments:ApiKey`; it does not match
`PaymentsArchive` or `Payments-Archive`.

### Grammar

```text
key       = segment *(":" segment)
segment   = 1*(non-colon, non-control character)
```

- Null, empty, leading/trailing `:`, `::`, control characters, and leading or trailing whitespace in a segment are
  invalid.
- Whitespace inside a segment and all non-control Unicode remain unchanged.
- Dots, hyphens, underscores, `/`, and `\` are literal segment content.
- No Unicode normalization, case rewriting, separator collapsing, or trimming occurs.
- A literal colon inside a segment is unsupported. Use another segment spelling or an explicit external mapping.
- The logical kernel imposes no arbitrary total-length limit. Each provider reports its own native length or character
  constraint as a representability result.

`Parse` throws `FormatException` with a value-safe reason. `TryParse` returns `false`, sets `key` to null, and never
returns partially normalized output. Public APIs receiving a string parse immediately and report `ArgumentException`
with parameter name `key`; provider-originated malformed keys use structured diagnostics instead.

## Provider-Facing Contract

### Typed provider API

Change the provider-author contract so implementations receive a parsed key and return one structured outcome:

```csharp
public enum ConfigProviderValueStatus
{
    Missing = 0,
    Found = 1,
    Terminal = 2
}

public sealed class ConfigProviderRequest
{
    public string Environment { get; }
    public AppSurfaceConfigKey Key { get; }
    internal ConfigResolutionScope Scope { get; }
    internal ConfigKeyInputOrigin InputOrigin { get; }
    internal string? OriginalInput { get; }
}

public sealed class ConfigProviderValueResult<T>
{
    public ConfigProviderValueStatus Status { get; }
    public T? Value { get; }
    public ConfigProviderTerminalDiagnostic? Diagnostic { get; }
    public IReadOnlyList<ConfigProviderNotice> Notices { get; }

    public static ConfigProviderValueResult<T> Missing();
    public static ConfigProviderValueResult<T> Found(
        T value,
        params ConfigProviderNotice[] notices);
    public static ConfigProviderValueResult<T> Terminal(
        ConfigProviderTerminalDiagnostic diagnostic);
}

public sealed class ConfigProviderNotice
{
    public string Code { get; }
    public string Problem { get; }
    public string Cause { get; }
    public string Fix { get; }
    public string Docs { get; }
    public bool Retryable { get; }
}

public interface IConfigProvider
{
    int Priority { get; }
    string Name { get; }
    ConfigProviderValueResult<T> Resolve<T>(ConfigProviderRequest request);
}
```

`Missing` carries no value, diagnostic, or notices. `Found` requires a non-null value, carries no terminal diagnostic,
and may carry immutable display-safe notices. `Terminal` requires a display-safe diagnostic, carries no value, and has
no notices. Constructors are private; factories reject null notice arrays or members and defensively copy the array.
A provider returns exactly one result and never writes a follow-up diagnostic cache.

`ConfigProviderNotice` is the non-terminal counterpart to `ConfigProviderTerminalDiagnostic`. It is used when a value
resolved through a compatibility path, such as one legacy provider alias, and therefore cannot be represented as a
terminal failure. Its six fields are required and value-safe. `DefaultConfigManager` logs each distinct notice once per
process by stable code, provider, environment, logical key, and safe source identifier; an audit-owned
`ConfigResolutionScope` also collects notices for the report. The manager never logs or stores the resolved value.
This closes the otherwise impossible contract in which a train-1 legacy alias must both return `Found` and emit
`config-key-legacy-provider-alias`.

`IConfigManager` is the application boundary and no longer inherits the provider SPI:

```csharp
public interface IConfigManager
{
    T? GetValue<T>(string environment, AppSurfaceConfigKey key);
    T? GetValue<T>(string environment, string key);
}
```

The string manager overload is an application-boundary adapter. It uses the configured `IConfigKeyInputParser` and then
invokes the typed member; manager and provider internals are prohibited from calling the string overload. Concrete
built-in providers may retain obsolete `GetValue` string conveniences during the compatibility trains, but they parse
strictly, construct a request, call `Resolve`, and project only `Missing`/`Found`; they throw
`ConfigurationResolutionException` for `Terminal`.

This change is source- and binary-breaking for external `IConfigProvider` implementations. It ships as one coordinated
pre-1.0 package-family release: provider authors replace `GetValue` with `Resolve`, consume `request.Key`, return a
structured result, remove their own case/separator and terminal-cache logic, rebuild, and run the conformance matrix.
Application code resolving through `IConfigManager.GetValue(..., string)` remains source-compatible.

The key-bearing companion signatures become:

```csharp
ConfigProviderAuditResolution IConfigProviderAuditDiagnostics.ResolveForAudit(
    ConfigProviderRequest request,
    Type valueType,
    ConfigAuditSourceRole role);

public sealed record ConfigProviderAuditDiscoveredKey(
    AppSurfaceConfigKey Key,
    object? RawValue,
    ConfigAuditDiscoveredValueKind ValueKind,
    IReadOnlyList<ConfigAuditSourceRecord> Sources,
    IReadOnlyList<ConfigAuditDiagnostic> Diagnostics);

ConfigPatchResult<T> IConfigValuePatcher.Patch<T>(
    ConfigProviderRequest request,
    T? currentValue);

ConfigValueResolution IConfigDiagnosticProvider.Resolve(
    ConfigProviderRequest request,
    Type valueType,
    ConfigAuditSourceRole role);

ConfigPatchDiagnosticResult IConfigDiagnosticPatcher.TracePatch(
    ConfigProviderRequest request,
    object? currentValue,
    Type valueType);
```

`ConfigPatchResult<T>` has exactly three statuses: `NotApplied`, `Applied`, and `Terminal`. `Applied` contains a value
and means at least one child variable was applied after every present candidate in the patch was converted and
validated successfully. It intentionally preserves the current any-successful-child rescue behavior; it does not claim
that every member of `T` is populated. `Terminal` contains one structured diagnostic and no value. Patchers construct
an isolated candidate object, never mutate the lower-provider or default instance in place, and publish it only after
all present child candidates pass validation. A conversion, collision, depth, cycle, or binding failure is therefore
terminal and cannot partially rescue a retained provider failure.

Remove `IConfigProviderTerminalDiagnosticProvider`; `ConfigProviderValueResult<T>.Terminal` replaces its mutable
two-call protocol. Provider-specific richer audit resolution remains, but its expected failures use the same diagnostic
codes and terminal meaning.

`IConfigProviderAuditKeyEnumerator.EnumerateKeys` keeps its existing method shape but returns discovered records whose
`Key` is typed. `ConfigAuditKnownEntry`, wrapper inspection, internal discovered-key records, resolution requests, and
cache identities also hold typed keys. Existing public audit report DTOs retain string `Key`/`ConfigPath` properties for
serialization; those strings are colon-delimited renderings, not normalized casing.

All attributed and manually registered keys are captured as raw immutable declaration descriptors during service
registration. The final `ConfigDeclarationRegistry` is then constructed once by dependency injection after the
container exists, using the complete descriptor set and finalized key-parser options; registration callbacks never
resolve options and never build a second container. Exact colon-delimited duplicates merge through the existing
audit-option merge rules. A case-only difference, or a legacy dot registration that translates to an already-declared
colon key, is `config-key-collision` and fails startup validation. There is therefore at most one declaration spelling.
For report spelling, that declaration wins; if no declaration exists, use the winning provider's projected spelling.
Source records always keep their own spelling. Sorting uses the two-comparer rule above, making output deterministic
without pretending that lowercase text is canonical.

`DefaultConfigManager` parses once, creates one internal `ConfigResolutionScope`, and passes a key-specific
`ConfigProviderRequest` backed by that scope through environment lookup, ordered providers, object patching, logging,
and audit resolution. The parser-created `AppSurfaceConfigKey` carries internal immutable input metadata—typed,
strict-string, or translated-dot origin plus the original composed spelling when applicable. This metadata is excluded
from equality, hashing, public serialization, and `Value`, but survives attribute composition, wrapper initialization,
request construction, provider alias lookup, notices, and audit reporting. Direct `Parse` and `FromSegments` keys are
typed/strict and have no compatibility aliases. This avoids changing the public `IConfig.Init` shape merely to pass
compatibility provenance.

`ConfigResolutionScope` captures one immutable environment name/value snapshot on first environment access and reuses
it for direct values, aliases, collections, patches, and diagnostics. The snapshot builds an ordinal exact-name map,
case-insensitive collision groups, and a prefix index once. Collection and object binding enumerate present children
from that prefix index; they do not issue a fixed number of speculative point lookups. A top-level `GetValue` owns one
scope; an audit report owns one scope for the whole report. Requests and scopes are immutable after construction and
safe for concurrent reads, but are never cached across top-level operations.

`ConfigProviderRequest` has an internal constructor/factory; external providers consume requests but do not construct or
mutate scopes. The conformance harness exercises them through `IConfigManager`. If environment snapshot capture throws,
the environment provider returns terminal `config-environment-snapshot-failed`; the manager does not query lower
providers because it cannot prove whether an override existed.

### Application-boundary parser

Add:

```csharp
public enum LegacyDotPathBehavior
{
    Strict = 0,
    TranslateDotOnlyWithDiagnostic = 1
}

public sealed class AppSurfaceConfigKeyOptions
{
    public LegacyDotPathBehavior LegacyDotPathBehavior { get; set; }
}
```

`IConfigKeyInputParser` is an internal singleton built from `IOptions<AppSurfaceConfigKeyOptions>`. It is the only
component allowed to translate legacy input. It is used by the string manager overload, deferred
`ConfigKeyAttribute` discovery, and deferred `AddConfigAuditKey<T>(string)` registrations. Direct construction from an
`AppSurfaceConfigKey` is always strict. Public `ConfigAuditKnownEntry(string, ...)` constructors become obsolete and
strict; factory/DI registrations provide compatibility behavior.

`AppSurfaceConfigModule` registers the options with the release-train default. Applications override it through normal
`services.Configure<AppSurfaceConfigKeyOptions>(...)` registration. In `Strict` mode, every string uses colon grammar
and dots remain literal. In `TranslateDotOnlyWithDiagnostic` mode, an input containing at least one dot and no colon is
always split on dots and emits the replacement diagnostic; an input containing a colon is strict and retains all dots.
There is never a two-candidate runtime lookup. A caller that needs one literal dot-containing segment while translation
mode is enabled uses `AppSurfaceConfigKey.FromSegments(...)`.

### Resolution state machine

For a strict key, the manager:

1. creates the request/scope and asks the environment provider for `ConfigProviderValueResult<T>`;
2. returns `Found.Value`;
3. on `Missing`, asks remaining providers by descending priority with the same three-result rules;
4. retains the first `Terminal` result without asking a lower source, but preserves the existing rescue order by giving
   the environment patcher one transactional chance to apply one or more valid child variables;
5. applies environment child patches with the same request/snapshot to a lower-provider value or the default value
   associated with a terminal result;
6. returns an `Applied` patch; throws the patch diagnostic for `Terminal`; otherwise throws
   `ConfigurationResolutionException` for the retained provider result;
7. returns `default` only when every eligible provider returned `Missing` and no patch resolved.

Invalid application input fails before provider traversal. Provider collision and unrepresentable outcomes are terminal
and suppress lower-priority fallback for that logical key.

Legacy translation occurs once before this state machine. Provider precedence therefore sees one logical identity and
one source snapshot. Declaration validation rejects a mixed legacy/canonical registration that would silently identify
the same key. Source-only literal-dot keys remain reachable with the typed API during the compatibility train.

one internally consistent snapshot for alias, casing, direct value, collection, and patch checks.

### Source projection

Add one shared internal projection/index primitive used by all built-ins. Each indexed entry records:

- parsed logical key;
- original source spelling;
- source-layer identity;
- exact native identifier or source locator;
- provider-owned metadata needed for retrieval;
- whether the entry came from canonical input or a legacy alias.

The index groups with `AppSurfaceConfigKey` equality before any normalized dictionary insertion. Its outcomes follow
this normative table:

| Existing entry | Incoming entry | Scope | Outcome |
| --- | --- | --- | --- |
| Same logical spelling | Same spelling | Same source layer | `Duplicate`; reject |
| Same identity | Different casing | Same source layer | `Collision`; reject |
| Same logical spelling | Same spelling | Later documented layer | `IntentionalOverride`; retain both provenance records |
| Same identity | Different casing | Later documented layer | `Collision`; reject the affected identity |
| Same key | Different native aliases | Same layer | `Collision`; reject even if values match |
| Different logical keys | Same native identifier | Provider-local mapping index | `Unrepresentable`; reject |
| Same identity | Any spelling | Different providers | Not indexed together; normal manager precedence |
| Legacy raw declaration | Canonical declaration for translated identity | Declaration layer | `Collision`; migrate the legacy declaration |

A source layer is the smallest source unit with no internal precedence: one JSON file, one environment scope, one
LocalSecrets namespace snapshot, or one remote mapping table. Ordered layers are declared by a provider before indexing;
providers may not infer order from enumeration timing.

Static collisions in registrations or mappings fail options/startup validation. Dynamic source collisions fail the
affected lookup with a terminal diagnostic and appear in audit output. Unrelated keys remain resolvable.

Stable diagnostic codes:

| Code | Meaning | Expected fix |
| --- | --- | --- |
| `config-key-invalid` | Input does not satisfy the logical grammar. | Correct the colon path or construct it from valid segments. |
| `config-key-legacy-dot-path` | Compatibility parsing translated a dot-delimited input. | Replace hierarchy dots with colons. |
| `config-key-legacy-provider-alias` | A historical provider-native identifier supplied the value. | Move the value to the displayed canonical native identifier. |
| `config-key-collision` | One collision domain contains equivalent logical keys or aliases. | Keep one source spelling/identifier. |
| `config-key-unrepresentable` | A provider codec cannot encode the key injectively. | Add an explicit native mapping or rename the key. |
| `config-key-prefix-overlap` | Provider conventions can claim the same segment subtree. | Narrow or remove one convention. |
| `config-key-environment-name-case` | A native variable exists only with noncanonical casing. | Rename it to the exact configured uppercase or explicit spelling. |
| `config-environment-snapshot-failed` | The environment provider could not capture one consistent variable snapshot. | Repair the environment source; lower providers are not used. |

Diagnostics include provider name, environment when safe, logical key, source layer, and conflicting source identifiers.
They never include values.

## Built-In Provider Behavior

### File configuration

Replace lookup-time `JsonObject.TryGetPropertyValue` traversal and the separate source-location parse with one
immutable, shape-preserving token projection keyed by `AppSurfaceConfigKey`. The existing token/location machinery is
the starting point, but one `Utf8JsonReader` walk becomes authoritative for property identity, source ranges, value
binding, and provenance.

- Parse UTF-8 bytes with `Utf8JsonReader` and build the projection before deserializing a selected value. The token walk
  tracks the current segment stack, node shape, raw value range, and per-object property set, so exact duplicate
  property names and case-only variants remain observable; do not run a second parser or rely on a materialized DOM
  that may already have discarded one occurrence.
- Each nested JSON property contributes one segment; `{ "Payments": { "ApiKey": "x" } }` becomes
  `Payments:ApiKey`.
- `{ "Microsoft.Hosting.Lifetime": "Warning" }` is one segment and retains both dots.
- Arrays use numeric segments (`Services:0:Url`) for source lookup. Audit display may continue rendering
  `Services[0].Url`, but that display string is not used as logical identity.
- One file is one collision layer. Detect duplicate flattened paths case-insensitively while parsing that file, matching
  .NET JSON-provider behavior.
  The .NET parser performs this check before publishing data; see
  [`JsonConfigurationFileParser`](https://github.com/dotnet/runtime/blob/main/src/libraries/Microsoft.Extensions.Configuration.Json/src/JsonConfigurationFileParser.cs).
- Preserve the current `StringComparer.OrdinalIgnoreCase` filename ordering; that ordered file list defines lower-to-
  higher layers for an environment. An exact-spelling key in a later file replaces the earlier value and retains both
  provenance records. A case-only spelling change across files marks only that logical identity as a collision.
- Two equal flattened paths inside one file are invalid even if later DOM behavior would otherwise retain a last value.
  A collision marks the exact path and every aggregate ancestor as terminal for reads from that effective file stack,
  while unrelated siblings remain available. A later file cannot hide that marker. Object/scalar replacement and
  descendant-origin removal happen only after the incoming layer passes collision validation.
- Null preserves the current provider's missing-value semantics. An empty object or array is a present aggregate.
  Arrays replace arrays as a unit across layers; scalars replace objects/arrays and objects/arrays replace scalars,
  removing superseded descendant origins only after the higher layer is valid.
- A JSON property containing `:`, a control character, or leading/trailing whitespace is unrepresentable as one logical
  segment. Mark its affected subtree terminal with `config-key-unrepresentable`; do not silently split or trim it.
- Keep the winning source file and original JSON path for audit provenance.

### Environment configuration

The canonical codec uppercases invariantly and replaces each logical `:` boundary with `__`. It does not rewrite `.`,
`-`, a single interior `_`, `/`, or `\`. A convention-encoded segment must use portable ASCII letters, digits, `.`,
`-`, `/`, `\`, or single interior underscores; it may not begin or end with `_` or contain `__`. Other logical
segments remain valid for file, LocalSecrets, and explicit remote mappings, but require `MapKey` for the environment
provider. These restrictions make segment boundaries injective instead of relying on collision discovery after lossy
encoding. At the beginning of one top-level manager resolution, the provider obtains one
`CaptureEnvironmentVariables()` snapshot and uses it for direct lookup, collections, object patches, aliases, and
diagnostics.

| Logical key | Canonical environment suffix |
| --- | --- |
| `Payments:ApiKey` | `PAYMENTS__APIKEY` |
| `Logging:LogLevel:Microsoft.Hosting.Lifetime` | `LOGGING__LOGLEVEL__MICROSOFT.HOSTING.LIFETIME` |
| `Payments:Api-Key` | `PAYMENTS__API-KEY` |

The provider has exactly two ordered canonical layers:

1. environment-scoped: `<ENVIRONMENT>__<ENCODED_KEY>`;
2. unscoped: `<ENCODED_KEY>`.

The scoped layer wins when both are set, preserving current override behavior, and audit provenance shows both. Inside
either layer there is exactly one native candidate per logical key.

A logical segment outside that convention grammar, or any key that violates the target environment's supported
identifier policy, is not representable by the convention because it could collide with a hierarchy boundary. In
addition, an unscoped encoded key beginning with `<ENVIRONMENT>__` is convention-unrepresentable in that environment:
otherwise it could equal the scoped form of a shorter logical key. Add an explicit
logical-key-to-environment-variable mapping API:

```csharp
public sealed class AppSurfaceEnvironmentConfigOptions
{
    public AppSurfaceEnvironmentConfigOptions MapKey(
        AppSurfaceConfigKey logicalKey,
        string nativeSuffix);

    public AppSurfaceEnvironmentConfigOptions MapKey(
        string logicalKey,
        string nativeSuffix);
}
```

`nativeSuffix` is one exact provider-native suffix, not an environment-specific full name. The provider derives
`<ENVIRONMENT>__PAYMENTS_API_KEY` and `PAYMENTS_API_KEY`, so the same registration works in every environment. The
environment prefix retains the provider's existing normalization and is not part of logical-key identity.

The string overload parses with strict colon semantics. `nativeSuffix` must be non-empty and contain no control
characters or `__`, must not begin or end with `_`, and may contain only ASCII letters, digits, and single underscores.
It is otherwise exact provider-owned text. These examples are normative:

| `nativeSuffix` | Accepted? | Reason |
| --- | --- | --- |
| `PAYMENTS_API_KEY` | Yes | Unambiguous exact suffix |
| `Payments_ApiKey` | Yes | Exact caller-owned casing is retained |
| `PAYMENTS__APIKEY` | No | `__` is reserved for the environment/key boundary |
| `_PAYMENTS` or `PAYMENTS_` | No | Edge underscores make composed names visually ambiguous |
| `PAYMENTS-APIKEY`, `PAYMENTS.APIKEY`, or non-ASCII text | No | Use a suffix in the portable explicit grammar |

Options are registered through
`services.Configure<AppSurfaceEnvironmentConfigOptions>(...)`.

An explicit suffix replaces—not supplements—the canonical encoded suffix in both layers. The only precedence order is:
scoped explicit over unscoped explicit when a mapping exists, otherwise scoped canonical over unscoped canonical. There
is never a mixed explicit/canonical candidate set for one key. Duplicate explicit mappings for one logical key, two
logical keys mapped to native full names equal under `OrdinalIgnoreCase`, or an explicit full name colliding with
another known key's canonical full name fail options validation. Mappings are frozen into one provider-local
forward/reverse index before lookup; dynamic mapping mutation is unsupported.

The forward/reverse index validates both scoped and unscoped full names for every known declaration. Ad-hoc requests
perform the same atomic reverse-claim check before reading a value. Property tests generate segment boundaries,
underscores, environment prefixes, casing, and scoped/unscoped pairs and assert that unequal logical identities never
produce one accepted full native name. The counterexamples `A_:B` versus `A:_B`, and scoped
`Production` + `Payments:ApiKey` versus unscoped `Production:Payments:ApiKey`, are permanent regression cases.

Object and collection patching caches one immutable reflection/binding plan per runtime `Type`. Plans include writable
members, collection shape, depth accounting, and cycle guards but no environment names or values. The provider walks
only snapshot entries under the requested prefix, so a sparse collection does not perform 1,024 misses per member.

For each expected full native name, inspect snapshot names equal under `OrdinalIgnoreCase`:

- no matching native name means missing in that layer;
- one ordinal-exact match supplies the value;
- one case-only match fails with `config-key-environment-name-case` and the exact replacement;
- more than one case variant fails with `config-key-collision`.

This rule is identical on Unix and Windows. Unix may physically contain both `PAYMENTS__APIKEY` and
`payments__apikey`, which is a collision. Windows normally coalesces them into one native entry; if its preserved name
is not the configured spelling, AppSurface reports the same casing diagnostic instead of relying on OS-insensitive
lookup.

Legacy flattened forms that replace `.`, `-`, or hierarchy with `_` are queried only by the migration adapter. Multiple
present aliases within one scope are a collision; conversion failure in one alias does not permit fallback to another
value for the same logical key. The scoped layer still overrides the unscoped layer after each layer has independently
passed alias validation.

Environment discovery is deliberately forward-only. The provider resolves and audits attributed keys, explicit audit
registrations, and `MapKey` entries; it does not reverse-parse every process environment variable or report unrelated
variables as AppSurface keys.

### LocalSecrets

- Store and lookup identities with `AppSurfaceConfigKey` equality. The original stored spelling remains immutable until
  an explicit migration; a differently cased write updates the value at that existing backend identity and does not
  change its display spelling.
- New writes use canonical colon paths. A write using another casing updates the existing logical entry instead of
  creating a second backend item.
- Remove `__`-to-`:` and backslash-to-slash rewriting from the canonical identity normalizer. Those transformations
  belong only to the legacy migration adapter.
- On read/list/doctor, build an index before selecting an item. Multiple existing case or alias variants fail closed with
  `config-key-collision`.
- Never silently rename or delete an existing secret. Extend the existing
  `IAppSurfaceLocalSecretMigrationStore` capability with:

  ```csharp
  AppSurfaceLocalSecretKeyMigrationResult MigrateKey(
      string applicationName,
      string environment,
      string? keyPrefix,
      string sourceStoredKey,
      AppSurfaceConfigKey destinationKey);
  ```

  `sourceStoredKey` is an exact backend identifier selected from doctor output and is not parsed as a logical key.
  Stores without this capability return `local-secret-migration-unsupported` before reading either value.
- `appsurface secrets migrate-key --from-stored-key <exact> --to <canonical>` acquires the store's namespace mutation
  lock and runs this journaled state machine: `Prepared` → `DestinationWritten` → `DestinationVerified` →
  `SourceDeletePending` → `Complete`. The journal stores operation id, source/destination identities, and state, never a
  value or value-derived fingerprint.
- Every transition is persisted atomically and durably before the next destructive action: write and fsync/commit
  `Prepared`; write destination; write and fsync/commit `DestinationWritten`; reread both values and compare their UTF-8
  bytes with `CryptographicOperations.FixedTimeEquals`; write and fsync/commit `DestinationVerified`; write and
  fsync/commit `SourceDeletePending`; delete source and require backend confirmation; write and fsync/commit `Complete`.
  A backend transaction or platform-equivalent durable replace may satisfy the write-plus-fsync requirement.
- If a destination exists while the source still exists, compare their values inside the store boundary. A mismatch
  stops at `Prepared` without overwriting either entry; a match resumes at `DestinationVerified`. No fingerprint is
  persisted because secret values can be low entropy.
- A delete failure leaves the durable `SourceDeletePending` marker and both values. On retry, reread and compare before
  retrying deletion. If the source is absent and the durable journal had reached `DestinationVerified`, complete without
  rewriting. If the source disappears before durable verification, stop with an unrecoverable-state diagnostic and do
  not alter the destination.
- The protocol is roll-forward only after destination write; it never deletes the destination as rollback. A crash or
  concurrent retry resumes the durable journal under the namespace lock. Resolution remains fail-closed while both
  identities exist and reports the migration id/state.
- The public migration method delegates the entire state machine to the store capability. Its internal backend seam
  exposes namespace lease acquisition, journal read/commit, value read/write/delete, and index publication so every
  transition can be fault-injected without reflection.
- The current platform backends use an exclusive maintenance lease shared by all package-owned writes and deletes in
  that namespace; migration never assumes an instance-local mutex coordinates another process. A backend with
  version-conditioned compare-and-swap may satisfy the same contract instead. If neither guarantee is available, the
  command may copy and verify the destination but must retain the source and return
  `local-secret-migration-unsupported`; it must not perform an unconditional delete.
- Index publication is a journaled transition before source deletion, not a separate best-effort side effect. Lease
  acquisition and backend calls accept cancellation and have documented finite timeouts.
- A backend that cannot provide the shared mutation guarantee, atomic durable journal transition, confirmed write/read,
  confirmed delete, and journaled index publication returns `local-secret-migration-unsupported` before destructive
  work. Completion may compact the journal to a durable tombstone according to existing backend policy. The command
  prints identifiers, state, and status, never values.

Application code keeps the same logical key when moving from LocalSecrets to a remote provider, preserving the promise
from the prior LocalSecrets design.

### Google Secret Manager

- Parse `MapSecret` logical keys and convention prefixes at registration.
- Reject duplicate mappings and prefixes with `OrdinalIgnoreCase`.
- Match conventions by complete segments. Overlap detection uses the same segment operation.
- Preserve explicit secret ids and full resource names exactly; their storage identity may remain case-sensitive.
- Replace the current lossy convention normalization. A convention claims strict descendants of its logical prefix only;
  an exact explicit mapping wins before convention selection. Overlapping convention prefixes are rejected by segment
  comparison.
- The convention encodes the full logical key, not a raw sliced suffix. Every segment must match
  `[A-Za-z0-9_]+(?:-[A-Za-z0-9_]+)*`, which forbids leading/trailing hyphens and `--` inside a segment. Lowercase each
  segment and join hierarchy segments with `--`; prepend `SecretIdPrefix` exactly. A dot, unsupported Unicode, empty
  segment, overlong final id, or invalid prefix/result is unrepresentable and requires `MapSecret`.
- Convention mode requires a non-empty `SecretIdPrefix`, and every convention in one provider instance must use the same
  ordinal-exact prefix. This reserves one generated-id namespace; explicit mappings may enter that namespace only when
  the explicit logical key would generate that same id under its matching convention.
- Validate the final Google secret id and length before lookup. Never guess a lossy spelling.

The typed overloads are primary:

```csharp
public AppSurfaceGoogleSecretManagerOptions MapSecret(
    AppSurfaceConfigKey logicalKey,
    string secretIdOrResourceName,
    string? version = null);

public AppSurfaceGoogleSecretManagerOptions EnableConventionResolver(
    AppSurfaceConfigKey logicalKeyPrefix,
    string secretIdPrefix,
    string? version = null);
```

Existing string overloads remain as strict colon-parsing conveniences. Mapping and convention records expose typed
logical key properties while keeping external identifiers as exact strings.

Examples:

```text
Payments:ApiKey   -> payments--apikey
Payments:Api-Key  -> payments--api-key
Payments:Api:Key  -> payments--api--key
```

Options validation builds one provider-local native-resource index from every explicit mapping and every convention
projection for known attributed/audit-registered keys. An explicit mapping and generated mapping may target the same
resource only for the same logical key; distinct logical keys targeting the same exact resource fail validation.
Ad-hoc convention keys are checked against the same reverse index before network access and atomically registered for
subsequent concurrent lookups. Ad-hoc claims are bounded; exhausting the configured claim capacity is terminal before
network access rather than allowing unbounded process growth. The provider does not enumerate Google Secret Manager:
unclaimed remote secrets are outside its collision domain.

The immutable declaration registry is constructed by dependency injection from all raw declaration descriptors and
finalized parser options. Google validation is split into ordinary option-shape validation and a
declaration-dependent validator registered with `ValidateOnStart`; both consume the same immutable registry. Providers
cannot observe a `Building` state, trigger wrapper activation, or construct a partial index on first request.

The native collision key is the complete resolved version resource name
`projects/{project}/secrets/{secret-id}/versions/{version}`, compared with `StringComparer.Ordinal` because it is an
exact Google identifier. Project and version therefore participate in identity; case-different resource names remain
different external identifiers even though logical keys remain case-insensitive. For convention mappings, concatenate
`SecretIdPrefix` and the encoded full logical key first, then validate the resulting secret-id segment against Google's
allowed characters and 255-character limit, and finally build the full resource name. Explicit short ids and explicit
full resource names use their existing Google validation path rather than the convention grammar.

The runtime reverse index is a `ConcurrentDictionary<string, NativeResourceClaim>` using `StringComparer.Ordinal` and
the full resource name as key. Startup seeds explicit and known convention claims. Ad-hoc convention resolution performs
an atomic `GetOrAdd` before network access: an existing equal logical identity proceeds, while a different logical
identity atomically poisons the claim as `Collision`; the triggering request and all subsequent requests for either
identity return terminal `config-key-collision`. A request that completed before an impossible invariant violation is
discovered cannot be revoked, which is why the injective grammar and generated-namespace reservation are required to
make that branch unreachable for validated options.

Remote payload caching is keyed by the exact full version resource name, not by environment plus logical key. One
`ConcurrentDictionary<string, Lazy<...>>` coalesces concurrent misses; the `GetOrAdd` factory has no network side
effects because it may execute more than once. Failed or cancelled fetch entries are removed after completion.
Successful entries use a size-bounded, expiring cache with a documented default of 1,024 entries and the provider's
existing TTL default. Payload bytes are copied at client, cache, and result boundaries. Caller cancellation stops that
waiter; it does not cancel a shared fetch still needed by other waiters. Audits use bounded concurrency plus an
aggregate default budget of 30 seconds and 256 remote lookups, reporting incomplete coverage explicitly when either
limit is reached.

### Audits, discovery, and diagnostics

- Store known and discovered logical keys as typed keys internally.
- Serialize and render logical identity with colon-delimited paths using the declared spelling or deterministic
  winning-provider spelling; do not call the casing canonical.
- Keep `ConfigAuditPath.DisplayPath` free to use brackets and dots for readability, but build `SourcePath` and matching
  operations from logical segments.
- Replace raw string prefix tests with `IsSameOrDescendantOf`.
- Group, diff, and correlate with the kernel's equality and deterministic display ordering.
- Show intentional cross-provider and cross-file-layer overrides as provenance, not collisions.
- Include legacy and representability diagnostics in structured and text reports.
- Preserve the exact resolved Google version resource name as a value-safe source locator. It participates in
  provenance and collision diagnosis but never changes logical equality and never includes a secret payload.
- Build matching, redaction, and grouping from typed logical segments and source records; rendered dotted/bracketed
  paths are presentation only.
- Trust structured diagnostics only. Built-in providers select messages from a reviewed template catalog and supply
  classified value-safe arguments. `DefaultConfigManager` automatically logs stable codes and bounded safe identifiers,
  not arbitrary `Problem`, `Cause`, or `Fix` text returned by an external provider.
- Escape control characters and cap rendered logical keys/native identifiers at 256 characters plus a stable digest.
  Notice suppression retains at most 4,096 identities. Configuration file reads default to 16 MiB per layer and 256
  files per environment; environment snapshots default to 65,536 entries and 64 MiB of names plus values. Every limit
  is configurable, documented, validated as positive, and fails with a stable value-safe diagnostic rather than partial
  data. No diagnostic or metric includes values.

## Migration and Compatibility

The strict typed API always uses colon semantics. Compatibility exists only at string and persisted-source boundaries.

### Persisted provider aliases

`ConfigProviderRequest` internally records whether its key came from a typed key, a strict string, or a translated
dot-only string, plus the original string when one exists. This metadata never changes `request.Key`; it only lets a
provider enumerate historical native identifiers during the compatibility train.

For environment `Production` and effective logical key `Payments:ApiKey`, the authoritative names are:

| Request origin | Canonical scoped/unscoped | Historical aliases queried during train 1 |
| --- | --- | --- |
| Typed `AppSurfaceConfigKey` | `PRODUCTION__PAYMENTS__APIKEY`, `PAYMENTS__APIKEY` | none |
| Strict string `Payments:ApiKey` | same | `PRODUCTION_PAYMENTS:APIKEY`, `PRODUCTION__PAYMENTS:APIKEY`, `PAYMENTS:APIKEY` |
| Translated string `Payments.ApiKey` | same | `PRODUCTION_PAYMENTS_APIKEY`, `PAYMENTS_APIKEY`; old hierarchical names deduplicate with canonical |

The table is produced by retaining the old normalization functions only inside a train-1 alias generator and testing
their exact output. Hyphens are never newly interpreted as logical hierarchy; a historical hyphen-derived environment
alias is considered only when the original strict string contained that hyphen. Explicit `MapKey` replaces canonical
and legacy convention candidates entirely.

For LocalSecrets, train-1 aliases are:

| Request origin | Canonical backend logical identity | Historical alias |
| --- | --- | --- |
| Typed key | `request.Key.Value` | none |
| Translated dot string `Payments.ApiKey` | `Payments:ApiKey` | exact stored key `Payments.ApiKey` |
| Strict string containing `__` | unchanged new logical key | old `__`-to-`:` stored identity |
| Strict string containing `\` | unchanged new logical key | old backslash-to-slash stored identity |

Google convention mappings do not probe the old lossy generated id as a hidden fallback. Before train 1, the migration
inventory computes the old and new generated ids for every known convention-backed declaration without reading a
secret. When they differ, the inventory emits an exact `MapSecret` replacement that pins the logical key to the existing
secret id. Operators may keep that explicit mapping indefinitely or move the remote secret separately. Unknown ad-hoc
convention keys cannot be inventoried without enumeration and must be registered explicitly before upgrade.

Within each provider layer, canonical and legacy native identifiers form one alias collision domain after exact duplicate
names are removed:

- no present identifier means missing;
- exactly one canonical identifier means normal resolution;
- exactly one legacy identifier means resolution plus `config-key-legacy-provider-alias`; a translated dot request also
  carries `config-key-legacy-dot-path`;
- canonical plus any distinct legacy identifier, or more than one legacy identifier, is `config-key-collision`;
- scoped and unscoped environment layers apply this rule independently, then scoped precedence applies.

Aliases are candidate native identifiers for one already-parsed logical key; they are not additional logical-key
candidates. This is why alias inspection does not contradict the single-path application parser.

The LocalSecrets command is unambiguous and paste-complete. `doctor` prints the exact command with shell quoting for the
active store selection, application, environment, optional prefix, exact source identifier, and proposed destination:

```text
appsurface secrets migrate-key \
  --app MyApp \
  --environment Development \
  [--prefix <configured-prefix>] \
  [--store-file <explicit-fallback-path>] \
  --from-stored-key <exact identifier reported by doctor> \
  --to <strict colon-delimited logical key>
```

`--from-stored-key` bypasses logical parsing and selects one exact, case-sensitive backend identity within the supplied
application/environment/prefix namespace. `--to` uses `AppSurfaceConfigKey.Parse` and never legacy translation.
Strict parsing does not ban dots: `--to Microsoft.Hosting.Lifetime` means one literal segment, while
`--to Logging:LogLevel:Microsoft.Hosting.Lifetime` means three segments. Before confirmation, the command prints the
parsed segment list and destination storage identity without reading a value into output.

### Release train 1: compatibility default

- Generated nested attribute paths switch to `:`.
- A string containing `:` is strict; every dot is literal.
- A dot-only string passed through an existing string API is interpreted as a legacy hierarchy when
  `LegacyDotPathBehavior.TranslateDotOnlyWithDiagnostic` is enabled, which is the release-train default.
- Emit `config-key-legacy-dot-path` once per distinct input per process and in audit output, including the proposed colon
  replacement.
- Developers needing a single dot-containing segment during this train use
  `AppSurfaceConfigKey.FromSegments("Microsoft.Hosting.Lifetime")`; mixed paths use canonical colon syntax.
- The selected mode produces exactly one logical identity before provider traversal. A declaration-layer conflict
  between a translated legacy spelling and canonical spelling fails startup rather than choosing one.

### Release train 2: strict default

- Default `LegacyDotPathBehavior` to `Strict`.
- Applications may explicitly restore `TranslateDotOnlyWithDiagnostic` for one release while completing migration.
- Package and repository migration docs list attribute values, direct reads, audit registrations, LocalSecrets entries,
  environment aliases, and Google mappings that require changes.

### Release train 3: removal

- Remove dot-path translation and legacy flattened environment aliases.
- Remove obsolete string overloads from concrete providers; keep application-facing string extensions as strict colon
  parsers.
- Remove the LocalSecrets legacy identity transformations after the migration command and doctor can prove no legacy
  entries remain.

The migration is pre-1.0 but still receives release notes, compiler obsolescence, runtime diagnostics, and a dedicated
guide. The release-train-1 package notes explicitly call out the coordinated `IConfigProvider` binary break. No provider
silently retries a different logical identity after the adapter is removed.

## Approaches Considered

### Approach A: Central helper with in-place provider retrofits

Rejected because the smallest diff would leave future providers able to bypass pieces of the contract and recreate the
current drift.

### Approach B: Logical-key kernel plus provider boundary contracts

Chosen because it gives application developers one portable identity while making provider integration and conformance
structurally testable.

### Approach C: Replatform onto `Microsoft.Extensions.Configuration`

Rejected because normalization can discard collision evidence and AppSurface's environment-first resolution, provider
priority, object patching, and audit provenance do not map cleanly enough to justify a broader behavioral migration.

## Recommended Approach

Build Approach B in vertical slices, starting with the kernel and executable contract rather than changing providers in
isolation. The target is familiar .NET behavior plus stronger collision, provenance, migration, and provider-author
guarantees—not a wrapper around `IConfiguration`.

The design intentionally follows the ecosystem on case-insensitive colon identity while separating AppSurface logical
keys from case-sensitive storage identifiers. Azure App Configuration documents why storage-level case sensitivity
should not be used to distinguish application configuration keys consumed by case-insensitive frameworks:
[Azure App Configuration key-value guidance](https://learn.microsoft.com/en-us/azure/azure-app-configuration/concept-key-value).

### Section 1. Architecture review

The best architectural seam is a typed key at the application/provider boundary, one request-scoped resolution
context, and provider-owned projections that preserve source spelling. The coupling is justified for identity,
diagnostic codes, and structured outcomes. It is not justified for provider-specific storage mutation, which must
remain behind LocalSecrets and Google capability boundaries.

```text
APPLICATION DECLARATIONS / DIRECT READS
                 |
                 v
        IConfigKeyInputParser
                 |
                 v
        AppSurfaceConfigKey
                 |
                 v
        DefaultConfigManager
          |      |       |
          |      |       +--> Config audit and patch traversal
          |      +----------> ordered IConfigProvider results
          +-----------------> Environment provider first
                                  |
                  +---------------+----------------+
                  |               |                |
                  v               v                v
             File snapshot   LocalSecrets      Google mappings
             + projection    logical/native    logical/native
                  |           separation        separation
                  +---------------+----------------+
                                  |
                                  v

```

The four resolution paths are explicit:

```text
HAPPY: string/typed key -> valid logical key -> claimed provider -> Found -> optional env patch -> value
NIL:   null key -> application argument failure before provider traversal
EMPTY: "" / empty segment -> parser failure with no partial identity
ERROR: provider Terminal -> no lower provider -> environment child rescue -> value or typed exception
```

The new stateful objects are the sealed declaration registry, request-scoped environment snapshot, Google
native-resource claim index, cache single-flight entries, and LocalSecrets migration journal.

```text
DECLARATION REGISTRY: Building -> Sealed -> Resolution
                         |          |
                         +X Add     +X Reseal

GOOGLE CLAIM: Unclaimed -> Claimed
                    \----> Collision (poisoned for provider lifetime)
Claimed + same logical key -> Claimed
Claimed + different logical key -> Collision
Collision -> Claimed is invalid

LOCAL MIGRATION:
Prepared -> DestinationWritten -> DestinationVerified -> SourceDeletePending -> Complete
    |               |                    |                       |
    + retry --------+--------------------+-----------------------+
Source deletion before verification -> Unrecoverable (terminal)
Rollback by deleting destination after verification -> invalid
```

At 10x configuration entries, token flattening and immutable dictionaries should remain linear and bounded by source
size. At 100x, whole-process environment snapshots, repeated audit projections, and unbounded ad-hoc Google claims
become the first memory pressure points. The plan must record counts and duration, cap only provider-native inputs where
the platform already has a limit, and avoid retaining values in diagnostics.

Single points of failure are the input parser, registry sealing, environment snapshot acquisition, and LocalSecrets
journal durability. Rollback is easy before persisted key migration and hard after old and new binaries have observed
different native identities. That is why an upgrade-and-rollback proof is a P1 requirement.

### Section 5. Code quality review

The typed key and structured result simplify identity and remove two-call diagnostic races. The highest code-quality
risk is concentrating parser, precedence, patching, provider applicability, and migration compatibility into
`DefaultConfigManager` or a single projection abstraction. Keep the manager as orchestration, providers as native
projection owners, and the kernel limited to parsing, equality, hashing, segment ancestry, and deterministic rendering.

The environment provider already duplicates normal and audit candidate/patch traversal. The implementation must extract
one source-candidate/projection engine used by direct resolution, patching, and audit rather than adding a third path.
Likewise, file token projection and source-location capture must be one pass, not parallel trees that can disagree.

The journaled LocalSecrets state machine is overbuilt if no backend can meet the capability contract. Implement and
failure-test one backend behind a fake durable store before editing every platform adapter. Do not make unsupported
stores pretend to provide crash safety.

### Section 7. Performance review

There are no database queries, background queues, or connection pools. The likely slow paths are file token projection
at first access, whole-environment snapshot capture per top-level request/report, and Google cache misses. File and
environment work should be O(source entries); lookups after projection should be O(1) average.

Audit owns one shared resolution scope so environment enumeration is not repeated per key. Direct reads intentionally
do not share scopes across calls, which favors freshness but can make repeated single-key reads expensive. Record
snapshot count, entry count, and duration; if measurements show repeated enumeration dominates, introduce an explicit
bounded snapshot lifetime later rather than a hidden global cache.

Google cache misses should be single-flight per exact resource and must not retain caller-owned mutable byte arrays.
No new network retry policy belongs in this key contract; preserve current client semantics and test concurrent misses.

### Section 8. Observability and debuggability review

Every expected failure has a stable diagnostic code, logical key, provider, source role, and value-safe locator. Add
structured counters for parser mode, legacy translation, source collision, unrepresentable mapping, registry seal
failure, environment snapshot failure, Google old-codec inventory, and LocalSecrets migration state. These counters
must not label by arbitrary key or native identifier because that creates high-cardinality and secret-adjacent telemetry.

Audit output is the primary debugging surface. It must reconstruct provider order, winning source, participating
overrides, aliases considered, and why traversal stopped. A startup failure must emit enough safe data to run the same
inventory or doctor command without requiring the host to finish starting.

The rollout runbook needs one entry per stable diagnostic family, with repair commands and rollback consequences.
`config explain` remains a User Challenge rather than an automatic expansion.

The plan changes application strings, package binaries, environment names, LocalSecrets identities, and Google
convention ids. A source-compatible application method does not make the provider ecosystem binary-compatible.
Mixed-version operation is therefore the highest deployment risk.

### Section 10. Long-term trajectory review

The typed key is a useful platform primitive for audit, secret references, deployment preflight, and future explanation
tools. The custom provider SPI creates path dependency and knowledge concentration unless external-provider migration
is tested and documented. Reversibility is 4/5 before persisted migrations, 2/5 after provider binaries and stored
identities have diverged.

In 12 months, a new engineer should see one logical identity contract, provider capability boundaries, and one
conformance suite. They should not need to understand three historical aliases during normal resolution. The accepted
Google lifecycle and migration additions are load-bearing; cache single-flight and low-cardinality metrics fit cleanly.
The deferred analyzer and live credentialed proof are not required to implement the kernel.

The unresolved long-term choice is custom rail versus additive/hybrid integration. Both outside voices recommend a
reversible bridge first. The user's original full-rail choice remains the default pending the gate.

### Developer empathy narrative

I am adding configuration to an application that already uses normal .NET conventions. I expect
`Payments:ApiKey`, `payments:apikey`, and an environment variable named `PAYMENTS__APIKEY` to identify the same
logical setting. I do not expect a dot, hyphen, provider prefix, or secret-store normalization rule to quietly change
what the key means. I can accept a pre-1.0 breaking change, but only if the compiler points me to the replacement and I
can prove the migration before deploying it.

My first move is to find one complete example and run it. The current Config README tells me which types exist but
stops before a value is registered, resolved, overridden, and printed with expected output. That makes me read tests or
module internals before I know whether the package fits. During an upgrade, I need a doctor or preflight result that
names the safe source identifier, explains why it conflicts, and gives me a command I can paste. I should never have to
infer an application name, environment, prefix, store selection, or whether a dot means hierarchy.

The magical moment is small: I change only the casing and the provider source, rerun one command, and see the same
logical key resolve from the intended higher-priority provider. If that works without credentials or secret output, I
trust the contract enough to adopt the deeper migration rail.

## Autoplan Phase 3: Engineering Review

Review scope: the complete logical-key rail, including the public Config API, DI registration lifecycle, built-in
providers, audit and diagnostics paths, LocalSecrets migration, Google caching, compatibility trains, packaging, and
verification. No implementation was performed in this phase.

### Scope challenge

The user-visible request sounds like a comparer change, but the repository does not have one key boundary to patch.
`DefaultConfigManager` passes raw strings through precedence and rescue; wrapper registration composes paths later;
file values and locations use different representations; environment and Google each encode native names; LocalSecrets
persists transformed identities; and audit code still performs dotted string-prefix matching. Changing only dictionary
comparers would make direct lookup appear fixed while leaving collisions, migration, aggregate binding, and diagnostics
inconsistent.

The full logical-identity rail is therefore the correct technical blast radius. The challenge is release scope, not
code reach: both outside voices recommend landing inventory, preflight, and clean-consumer proof before exposing every
provider/binary change. That sequencing remains a final-gate User Challenge because the user explicitly selected and
locked the complete rail.

[`ValidateOnStart` options lifecycle](https://learn.microsoft.com/en-us/dotnet/core/extensions/options).

| Path | Risk before amendment | Enforceable design |
| --- | --- | --- |
| Environment direct/child lookup | Repeated process reads and fixed sparse-index probes | One snapshot with exact, folded, and prefix indexes per top-level operation |

### Security and failure behavior

The value boundary is unchanged: configuration values and secret payloads never enter logs, migration journals,
diagnostics, metrics, cache keys, or test snapshots. New trust boundaries are explicit:

- application and source spellings are escaped and length-bounded before rendering;
- external-provider prose is untrusted and is not automatically logged;
- built-in diagnostic templates accept classified safe identifiers only;
- Google payload buffers are copy-owned at every boundary;
- LocalSecrets source deletion requires durable proof under shared writer coordination;
- resource exhaustion returns a stable diagnostic without partial source publication.

Logger failures must not alter resolution results. Cancellation distinguishes a caller who stops waiting from a shared
operation needed by other callers. Cache and single-flight failures are evicted after completion so a transient failure
does not poison the process indefinitely. Collision claims, by contrast, remain terminal for that provider instance
because allowing them to disappear would make behavior time-dependent.

### Cross-phase themes

The three reviews converge on one product principle: case-insensitive logical identity is the least surprising .NET UX
only when ambiguity is rejected before value selection and every native spelling remains explicit provenance. The CEO
phase challenged rollout and compatibility. The DX phase made success, errors, migration, and proof measurable. The
engineering phase made the kernel enforceable under registration order, concurrency, failure, scale, and hostile input.

The plan remains broader than a local comparer change because current key semantics are distributed across provider
codecs, wrappers, audits, migration, and external package contracts. If the final gate chooses a narrower release, the
safe cut line is after migration inventory and consumer proof—not midway through provider identity.
