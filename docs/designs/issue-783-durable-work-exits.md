## Problem Statement

[Issue #783](https://github.com/forge-trust/AppSurface/issues/783) exposes a gap between the Durable executor boundary and the already-implemented PostgreSQL Work state machine.

The PostgreSQL runtime records an external-effect permit before it invokes a Work executor. Today, the shared [`IDurableWorkerExecutor<TWork, TResult>`](../../Workers/ForgeTrust.AppSurface.Workers/IDurableWorkerExecutor.cs) returns a terminal `TResult` or throws. A returned result becomes success; every ordinary exception after a permit becomes `ASDUR106` / `AmbiguousExternalOutcome` and suspends the Work. That preserves safety when a provider mutation might have happened, but it is too coarse for a typed executor that can prove a transient, read-only failure happened before it accepted data or began a mutation.

The downstream example is Skoolit's receipt-bound Gmail backfill: a retryable error while listing parent-selected senders must not consume the bound receipt, but it occurs after Durable has committed the effect permit.

The existing [`PostgreSqlWorkCompletionKind.ProvenNoEffect`](../../Durable/ForgeTrust.AppSurface.Durable.PostgreSql/PostgreSqlDurableWorkStore.cs) already records a permit observation, applies the configured retry policy, returns Work to `retry_wait`, and restores dispatch availability. It is internal and no public executor path can return it.

## What Makes This Cool

The executor returns one typed local fact and the provider takes responsibility for everything difficult afterwards:

```text
executor exit
  -> current-fence and stale-completion validation
  -> effect-permit observation
  -> cancellation and retry-policy application
  -> authoritative Work and dispatch state
  -> history, diagnostics, Flow projection, and Schedule projection
```

The resulting contract is not a Gmail-shaped retry exception. It is a small exit algebra that lets the code that knows whether it began an effect state that fact explicitly, while Durable preserves its existing safety protocol.

## Constraints

- The [Durable Work protocol](../../Durable/work-protocol-v1.md) remains authoritative: a claim is not authorization, a committed permit precedes provider I/O, and unknown post-permit truth must never be invented.
- `DurableWorkState` remains the provider-owned persisted lifecycle. An executor exit is not a user-settable Work state.
- The shared Workers contract remains unchanged and is not deprecated. Non-Durable Worker consumers must not inherit Durable-specific semantics.
- No executor exit may set persistent state, retry delay, attempt count, deadline, dispatch state, history, permit evidence, or fences directly.
- A typed exit carries no exception object, provider response, payload, URL, credential, or arbitrary metadata. V1 carries only a bounded safe diagnostic code; the established Durable diagnostic boundary is documented in the [ASDUR catalog](../../troubleshooting/durable-diagnostics.md).
- An uncaught executor exception remains an unclassified, potentially effectful failure and follows today's conservative ambiguous-outcome path.
- V1 scopes the new opt-in registration to `DurableProviderSafety.ProviderKeyed`, the safety class named in #783. It does not widen `ReconcileBeforeRetry` or `ManualResolution` semantics without separate evidence and a protocol amendment.
- No schema migration, new scheduler behavior, hosted-service behavior, operator backdoor, or generic application policy hook is in scope.

## Premises

1. The correct abstraction is a portable executor exit, not the PostgreSQL-specific `PostgreSqlWorkCompletion` record. PostgreSQL remains the first implementation; future providers must be able to translate the same exit without learning PostgreSQL persistence details.
2. The exit models all normal executor facts in v1: `Succeeded(result)`, `RetryBeforeEffect(code)`, `FailedTerminal(code)`, and `AmbiguousExternalOutcome(code)`.
3. The executor owns only the local fact it can prove. The provider owns whether that fact is still current and what durable transition is safe under its persisted claim, permit, cancellation, retry, and provider-safety facts.
4. Only an explicit `RetryBeforeEffect` may request the existing proven-no-effect completion. It is not inferred from exception type, cancellation, a timeout, a provider-safety value, or a successful read call.
5. `FailedTerminal` after a permit names an executor fact, not permission to discard potential external-effect truth. The provider may still suspend when the declared safety class requires ambiguity preservation.
6. A generic application hook is unnecessary for #783. The executor already knows the relevant fact and returns it directly; a hook would add indirection and could become an unsafe exception classifier.

## Public Contract

Add a Durable-only opt-in executor interface next to the existing registration machinery. It uses the current `DurableWorkerEnvelope<TWork>` and cancellation ownership, but returns a typed exit instead of a raw result:

```csharp
public interface IDurableWorkExitExecutor<TWork, TResult>
{
    ValueTask<DurableWorkExit<TResult>> ExecuteAsync(
        DurableWorkerEnvelope<TWork> work,
        CancellationToken cancellationToken = default);
}
```

`DurableWorkExit<TResult>` is a closed type with validated static factories:

```csharp
DurableWorkExit<TResult>.Succeeded(TResult result)
DurableWorkExit<TResult>.RetryBeforeEffect(string code)
DurableWorkExit<TResult>.FailedTerminal(string code)
DurableWorkExit<TResult>.AmbiguousExternalOutcome(string code)
```

Only `Succeeded` carries `TResult`; every other case requires a nonempty, bounded, identifier-safe diagnostic code. The type must reject invalid discriminators, a missing success result, or a result attached to a non-success exit.

Use a public `DurableWorkExitKind` enum and a sealed `DurableWorkExit<TResult>` with a private constructor and only the four factories above. Codes use the existing canonical Durable identifier rule and the existing 120-character terminal/problem-code maximum. `Succeeded` cannot carry a code, and the other three cases cannot carry a result. This retains the established payload and diagnostic privacy boundary rather than creating a second metadata channel.

The exact readable surface is part of the contract, not an implementation detail:

```csharp
DurableWorkExitKind Kind { get; }
string? Code { get; }
TResult? Result { get; }

DurableWorkExitKind Kind { get; }
string? Code { get; }
DurableEncodedPayload? Result { get; }
```

The first three members belong to `DurableWorkExit<TResult>`; the second three belong to `DurableEncodedWorkExit`. `Result` is non-null only for `Succeeded`; `Code` is non-null only for non-success exits. Success factories reject a null reference result, and consumer code must branch on `Kind` before using the corresponding nullable property. Tests and the packed consumer must compile against these properties, not only the factories.

Add a clearly named opt-in registration helper:

```csharp
AddDurableWorkExit<TWork, TResult, TExecutor>(
    workName,
    workVersion,
    workCodec,
    resultCodec)
```

The helper has no provider-safety parameter in V1: it constructs an exit-aware registration with `DurableProviderSafety.ProviderKeyed` unconditionally. That makes the scope machine-enforced and prevents an accidental opt-in for `Idempotent`, `ReconcileBeforeRetry`, or `ManualResolution`. The existing `AddDurableWork` continues to require `IDurableWorkerExecutor<TWork, TResult>` and preserves its public API and behavior.

The additive preparation seam is exact and backward compatible:

- Add a public, sealed `DurableEncodedWorkExit` that contains only `Kind`, an optional safe `Code`, and an encoded result only for `Succeeded`. It has no public constructor or arbitrary metadata factory.
- Add `virtual ValueTask<DurableEncodedWorkExit> DurablePreparedWork.InvokeExitAsync(...)`. Its default implementation calls the existing abstract `InvokeAsync(...)` and wraps the encoded payload as `Succeeded`. This is additive, so legacy custom `DurablePreparedWork` implementations remain binary/source compatible and do not need to override a new abstract member.
- Add `DurablePreparedWorkInvocation.InvokeExitAsync(...)` in the Provider SPI. Keep its existing `InvokeAsync(...)` unchanged for legacy providers.
- Implement a separate `DurableWorkExitRegistration<TWork, TResult, TExecutor>` for `IDurableWorkExitExecutor<TWork, TResult>`. Its prepared invocation encodes a success result or returns the three code-only exits. Its legacy `InvokeAsync(...)` succeeds only for `Succeeded`; a non-success exit throws the public `DurableWorkExitCompatibilityException` with this safe message: `"Exit-aware Work returned a non-success exit, but the provider invoked the legacy success-only boundary. Upgrade the provider to InvokeExitAsync."` It carries no raw exit code, result, provider response, or nested exception. A provider that has not adopted `InvokeExitAsync` therefore fails conservatively instead of treating `RetryBeforeEffect` as success or retrying it blindly.
- Change PostgreSQL's internal `IDurableRuntimeExecutionBoundary` and its no-op implementation to carry `DurableEncodedWorkExit`, then map it once in the pump. This internal boundary and the Provider invocation wrapper are the real path that must change; no provider persistence model, SQL function, or schema contract is widened.

This creates a clear migration matrix: legacy registrations on every current provider retain exact behavior; exit-aware registrations require a provider that calls `InvokeExitAsync`; and PostgreSQL is the only V1 provider that translates the new exits. The deliberate escape hatch is to keep a Work on the legacy executor contract when it cannot honestly assert one of the four typed facts. There is no hook, arbitrary exception classifier, custom retry delay, or direct state API.

Exit-aware registration also has a rolling-deployment rule. First deploy the Durable Provider/PostgreSQL binaries that understand `InvokeExitAsync`; then confirm every worker allowed to discover the affected Work contract has that capability; only then publish a new immutable Work version registered through `AddDurableWorkExit` and begin accepting that version. Do not convert an existing Work version in place. The existing contract-selection discovery mechanism must keep an older registry from claiming the new version. A mixed fleet that somehow calls the legacy bridge must fail safe, but it is an unsupported rollout state and must be made visible as the compatibility exception followed by `ASDUR106` after a permit.

## Exit Translation

The PostgreSQL provider translates a current exit only after it has acquired the exact effect permit and only through `RecordCompletionAsync`.

| Executor exit | Internal completion | Provider-owned result |
| --- | --- | --- |
| `Succeeded(result)` | `Succeeded` with the encoded result | `Succeeded`, or `SucceededAfterCancelRequested` when existing cancellation rules require it. |
| `RetryBeforeEffect(code)` | `ProvenNoEffect` | Records `effect_permit.status = proven_no_effect`; applies normal retry delay, maximum-attempt, elapsed-deadline, cancellation, history, and dispatch rules. A current, retry-eligible Work becomes `retry_wait`. |
| `FailedTerminal(code)` | `FailedTerminal` | Retains current post-permit safety mapping. It must not assert that a provider effect was absent merely because the executor considers the operation terminal. |
| `AmbiguousExternalOutcome(code)` | `AmbiguousExternalOutcome` | Retains current ambiguity/reconciliation/manual-resolution mapping and never blindly retries. |
| Uncaught exception | `AmbiguousExternalOutcome` with current `ASDUR106` handling | Exact compatibility behavior for legacy and exit-aware executors alike. |
| Runtime/registration failure | `ContractUnavailable` or the existing provider failure path | Provider-owned; never a user-returned executor exit. |

Every entry still passes through exact lease, scope generation, runtime epoch, Work revision, permit, and dispatch checks. A stale completion remains a stale observation and cannot revive, retry, or overwrite Work. The exception-origin table is deliberately explicit: registration/codec resolution before a permit remains `ContractUnavailable`; an uncaught executor exception, cancellation, lease loss, serialization failure, or compatibility failure after a permit remains `ASDUR106` / ambiguous. Only the executor's explicit `RetryBeforeEffect` creates `ProvenNoEffect`.

## Autoplan CEO Review

### Scope and premise assessment

This is a developer-facing public-preview library enhancement, not a new runtime or a workflow-platform rewrite. The approved additive contract remains the right scope: the immediate user outcome is that a Work executor which can prove a read-only provider operation failed before it began a provider mutation can ask the provider to use its already-implemented no-effect retry path.

The 12-month ideal is a provider-neutral completion vocabulary adopted by more providers only when each has conformance evidence. This change moves toward that ideal by making the vocabulary portable, while deliberately proving it through PostgreSQL and `ProviderKeyed` Work first.

```text
CURRENT
  Post-permit return = success; ordinary exception = ambiguous suspension
      |
      |  typed, code-only fact with provider-owned authority
      v
THIS CHANGE
  legacy result path + opt-in typed exit path -> PostgreSQL completion mapping
      |
      |  second provider/adopter proves a shared need
      v
12-MONTH IDEAL
  portable completion vocabulary implemented by multiple conforming providers
  without a generic policy hook or user-settable persistent state
```

The plan explicitly rejects three tempting expansions: replacing the existing executor contract, adding an exception classifier or policy hook, and adding structured metadata/custom retry controls. Those would broaden the blast radius before a second adopter establishes the shape. The safe escape hatch is the legacy executor contract, whose exceptions retain today's conservative handling.

### What already exists

| Sub-problem | Existing implementation | Reuse in this plan |
| --- | --- | --- |
| Typed execution envelope and provider key | `DurableWorkRegistration<TWork,TResult,TExecutor>.CreateEnvelope` | Reuse unchanged for exit-aware registration. |
| Pre-permit preparation boundary | `DurablePreparedWork` and `DurableProviderWorkAdapter.Prepare` | Add a virtual exit invocation without altering legacy `InvokeAsync`. |
| Permit-backed known-no-effect completion | `PostgreSqlWorkCompletionKind.ProvenNoEffect` plus `RecordCompletionAsync` | Reuse directly for `RetryBeforeEffect`; do not modify the SQL decision matrix. |
| Fence, retry, history, dispatch, Flow, and Schedule projection | `PostgreSqlDurableWorkStore.RecordCompletionAsync` | Continue to own all durable mechanics after translation. |
| Safe identifier validation | `DurableIdentifier.Require` and `DurableProblem` bounds | Reuse the 120-character terminal/problem-code rule for exit codes. |
| Package compatibility guardrails | Durable and Provider `PublicAPI.Shipped.txt`, contract/provider tests, packed consumers | Extend rather than replace the existing snapshots and proof programs. |

### Architecture and data flow

```text
provider claim
  -> DurableProviderWorkAdapter.Prepare
  -> DurablePreparedWorkInvocation
  -> [PostgreSQL commits exact effect permit]
  -> IDurableRuntimeExecutionBoundary.InvokeExitAsync
  -> DurableEncodedWorkExit
  -> PostgreSqlDurableRuntimePump.TranslateExit
  -> PostgreSqlWorkCompletion
  -> RecordCompletionAsync
      -> current-fence validation
      -> permit observation
      -> retry/cancellation policy
      -> Work + dispatch + history
      -> Flow/Schedule projections
```

Shadow paths are fixed by the provider, not by the executor:

```text
explicit exit        -> current claim? -> no: stale observation, no state resurrection
                      -> yes
                          -> RetryBeforeEffect -> proven_no_effect -> retry/cancel/exhaustion policy
                          -> other typed exit  -> existing success/terminal/ambiguity mapping

exception after permit -> ambiguous outcome (`ASDUR106`), never inferred no-effect
preparation failure    -> contract unavailable before executor starts
legacy prepared work   -> virtual bridge wraps encoded result as Succeeded
old provider + exit work non-success -> named compatibility failure, conservatively handled
```

### Error and rescue registry

| Codepath | What can go wrong | Classified as | Provider action | Observable result |
| --- | --- | --- | --- | --- |
| `AddDurableWorkExit` / exit factories | invalid code, undefined kind, missing/extra result | validation failure before execution | reject locally; no Work mutation | argument exception with no payload disclosure |
| `Prepare` | bad payload, missing executor, registry mismatch | `ContractUnavailable` | existing pre-permit completion path | existing safe `ASDUR109` diagnostics |
| `InvokeExitAsync` success | result encoding fails after permit | ambiguous exception | existing `ASDUR106` path | suspended Work and permit evidence |
| `InvokeExitAsync` explicit `RetryBeforeEffect` | executor asserts no provider effect | `ProvenNoEffect` | existing retry/cancel/exhaustion matrix | safe exit code in history/terminal code and `proven_no_effect` permit status |
| `InvokeExitAsync` explicit terminal/ambiguous exit | executor supplies only safe code | existing terminal/ambiguity completion | current provider-safety matrix | existing state and safe code |
| heartbeat/lease/cancellation race | execution result arrives after ownership changed | stale or ambiguous observation | existing fence and cancellation rules | no resurrection or unbounded retry |

### Failure modes and operational rollout

| Failure mode | Guardrail | Test evidence required |
| --- | --- | --- |
| Exit-aware path makes a post-permit exception retryable | only the explicit `RetryBeforeEffect` maps to `ProvenNoEffect` | exception, codec failure, and cancellation remain ambiguous tests |
| Legacy custom prepared work breaks from a new abstract API | virtual default bridge wraps legacy `InvokeAsync` success | provider/adopter compatibility tests |
| Old provider treats a non-success exit as a result | exit registration's legacy invocation throws a named compatibility error | conservative legacy-provider compatibility test |
| Code leaks provider response/PII | code-only factories validate canonical 120-char identifier | invalid, oversized, whitespace/control-character code tests |
| Retry corrupts activity identity or dispatch | store owns retries and reuses the activity/provider key | fake-clock retry, permit/history, dispatch, Flow and Schedule projection tests |
| Operators misread a new retry reason | docs show exit-to-provider state/action matrix | README and diagnostics link/snapshot proof |

Rollout is package-family normal: publish the additive preview in the existing Durable, Provider, and PostgreSQL package family; keep old registrations compiling; prove the exit-aware path in packed consumers; and document one adoption choice. There is no migration, feature flag, new host process, schema change, or performance benchmark requirement because the translation adds no database operation or new query. The existing pump/store integration tests must prove the same number and ordering of durable writes for the mapped completion kinds.

### NOT in scope

- Replacing or deprecating `IDurableWorkerExecutor<TWork,TResult>`: preserve non-Durable and existing Durable consumers.
- Enabling exit registration for `Idempotent`, `ReconcileBeforeRetry`, or `ManualResolution`: require separate protocol evidence.
- Custom retry delay, attempt/deadline mutation, history writes, state transitions, permit manipulation, or provider-response metadata: all remain provider authority.
- Hook-based exception classification: it creates a parallel policy bypass where the executor can return the fact directly.
- Schema, scheduler, broker, host, operator-dashboard, or generic provider rollout work: none is necessary for the proven PostgreSQL mapping.

### CEO review conclusion

The independent `combo/sub` review found that a migration/exception-origin/operations matrix was missing. Those concrete gaps are now incorporated above. Its recommendation to replace the completion model, add hooks, add generic metadata, and deprecate legacy execution is deferred: it contradicts the user-approved additive, no-hook, no-deprecation scope and lacks a second adopter or provider conformance proof. The separate Codex CLI review was not run because it would transmit repository content to an external model service without specific authorization.

### API and documentation decisions

The API is intentionally opinionated and overrideable:

- `AddDurableWorkExit` is the simplest safe registration: fixed `ProviderKeyed`, typed work/result codecs, and no callback or policy parameter.
- The four factories use verbs that name the asserted fact, not a desired store transition. `RetryBeforeEffect` is the only retry-shaped term because it states the evidence boundary.
- The legacy `AddDurableWork` and `IDurableWorkerExecutor` remain the escape hatch when an executor cannot prove one of the four facts.
- The documentation must show `Succeeded` plus the Gmail retry path, then a concise table stating why `FailedTerminal` after a permit can still suspend under provider safety. That avoids a misleading “terminal means finished” mental model.
- The XML docs and README put the evidence boundary beside every factory: `RetryBeforeEffect` means *no provider mutation began*—read-only provider I/O is allowed—and not “before Durable acquired its permit”; `FailedTerminal` names an executor fact and does not force a persisted terminal Work state; `AmbiguousExternalOutcome` is not a direct operator command. The public name remains `RetryBeforeEffect` for this preview, with its sharper semantic explanation documented rather than introducing a late naming churn.

Add an **Exit-aware Work** section to `Durable/ForgeTrust.AppSurface.Durable/README.md` with the complete registration and Gmail sketch; add a provider-adoption compatibility table to `Durable/ForgeTrust.AppSurface.Durable.Provider/README.md`; add the PostgreSQL state/permit table to `Durable/ForgeTrust.AppSurface.Durable.PostgreSql/README.md`; amend the normative Work protocol; and extend the diagnostics catalog with an application-code versus reserved `ASDUR` prefix explanation and safe operator actions. Link the first mention of each concept to its canonical document as required by repository guidance.

```csharp
public ValueTask<DurableWorkExit<BackfillResult>> ExecuteAsync(
    DurableWorkerEnvelope<BackfillRequest> work, CancellationToken cancellationToken = default)
{
    if (!TryListParentSelectedSenders(work.Payload, out var senders))
        return ValueTask.FromResult(DurableWorkExit<BackfillResult>.RetryBeforeEffect("app.gmail.sender_list_transient"));
    return ValueTask.FromResult(DurableWorkExit<BackfillResult>.Succeeded(new BackfillResult(senders)));
}
```

The sample intentionally cannot pass a raw Gmail response, custom retry duration, Work state, permit, or arbitrary metadata. Its note must state that `TryListParentSelectedSenders` is valid only when the failed operation is read-only and no provider mutation was attempted.

Application exit codes are stable, namespaced, append-only application facts such as `app.gmail.sender_list_transient`. Their owning application documents the problem, cause, fix, and optional docs link; changing a persisted code's operational meaning requires the same compatibility review as any other operator-visible contract. The `ASDUR` prefix is reserved case-insensitively for Durable/provider diagnostics. The diagnostics catalog must give one complete application-code example and one `ASDUR106` example, including their different remediation paths.

The adoption proof is named and compile-checked: extend `Durable/packed-consumers/Adopter/Program.cs` to register both a legacy Work and an exit-aware Work, inspect `Kind`, `Code`, and `Result`, and compile it through `Durable/verify-packed-consumers.sh`. The Durable README must source its short code sample from this proof (or an equally compile-checked example) and link onward to PostgreSQL provisioning. The Provider README gets a dedicated **Typed exit provider adoption** section with the `InvokeAsync`/`InvokeExitAsync` compatibility matrix, call-path diagram, conservative unsupported-provider behavior, and required provider conformance tests.

## Autoplan Engineering Review

### Implementation sequence

1. **Define the Durable contract.** Add `DurableWorkExitKind`, `DurableWorkExit<TResult>`, `DurableEncodedWorkExit`, `DurableWorkExitCompatibilityException`, and `IDurableWorkExitExecutor<TWork,TResult>` in a focused Durable source file. Enforce the exact kind/code/result invariants and document the evidence boundary on every factory and property.
2. **Add the compatibility bridge and registration.** In `DurableWorkRegistration.cs`, add the virtual `DurablePreparedWork.InvokeExitAsync` legacy adapter, the `DurableWorkExitRegistration<TWork,TResult,TExecutor>` implementation, and `AddDurableWorkExit`. Keep `DurableWorkRegistration.InvokeAsync` and every legacy registration unchanged; make the new helper fixed to `ProviderKeyed`.
3. **Extend only the Provider invocation wrapper.** In `DurableWorkExecution.cs`, add `DurablePreparedWorkInvocation.InvokeExitAsync` and update Provider public API documentation/snapshot. Do not add provider-specific state or policy to the Durable exit types.
4. **Translate once in PostgreSQL.** Change the internal `IDurableRuntimeExecutionBoundary`, its no-op implementation, and the pump's lease/heartbeat return type from an encoded payload to `DurableEncodedWorkExit`. Add one exhaustive pump translator to form the existing `PostgreSqlWorkCompletion`; leave `PostgreSqlDurableWorkStore.RecordCompletionAsync`, its SQL decision expression, schema, and migrations untouched.
5. **Prove mixed-version and runtime behavior.** Use the existing `PostgreSqlDurableWorkContractSelection` name/version snapshot to prove an old registry does not discover the new Work version. Add exit-aware prepared-work test doubles alongside the existing runtime-pump registrations; preserve the legacy prepared-work tests as bridge proof.
6. **Document and package the contract.** Update the three package READMEs, `Durable/work-protocol-v1.md`, `troubleshooting/durable-diagnostics.md`, `Durable/api-budget.md`, Durable/Provider API snapshots, and the packed adopter program. Make the README sample derive from compile-checked source.
7. **Verify and release.** Run focused contract/provider/PostgreSQL tests, solution coverage, public API snapshot tests, packed consumers, and formatting. Release through the existing coordinated package process only after the worker-fleet rollout condition is documented and verified.

### Deployment and rollback

The deployment order is a protocol requirement, not an operational suggestion:

1. Deploy the package family whose Provider/PostgreSQL runtime calls `InvokeExitAsync`.
2. Confirm every worker eligible to discover the affected contract uses that package family and restart workers so their contract selection snapshots are current.
3. Register and accept a new Work version through `AddDurableWorkExit`; retain the prior version for already accepted legacy Work.
4. Observe the new safe application exit code separately from `ASDUR106` during the first operating window.

To roll back, stop accepting the new Work version, but retain exit-capable workers until every accepted new-version Work reaches a terminal state or an intentional suspension. Do not return to an old-only fleet that cannot execute or discover a version already accepted. No schema rollback is required because this change adds no migration.

### Engineering conclusion

The architecture is sound when it is delivered as an additive public contract, a virtual legacy bridge, a single PostgreSQL translator, and a versioned-work rollout. The high-risk paths are all contract/version boundaries, not the existing store state machine; therefore the tests and documentation center on capability mismatch, fence preservation, and operator-safe diagnostics rather than new SQL behavior.

## Approaches Considered

### Chosen: additive opt-in exit executor

Introduce the new Durable-only typed exit interface and registration path, then adapt it into the existing PostgreSQL completion pipeline. This delivers the full exit vocabulary while leaving `IDurableWorkerExecutor<TWork, TResult>` intact for current Durable registrations and all non-Durable Worker consumers.

It is the smallest public-contract change that satisfies #783 and allows a real adopter to prove the value of exit-aware Work authoring.

### Deferred: canonical exit contract through every Durable prepared-work seam

This is the cleanest long-term architecture, but it would refactor shared public registration and custom-registration seams before a second exit-aware adopter demonstrates the need. Revisit only if the additive bridge becomes a repeated source of adapter complexity.

### Rejected: special-case retry exception or signal

It would solve the Gmail listing failure but violates the chosen direction: normal executor outcomes should be explicit typed exits, not a collection of exception-shaped escape hatches.

## Recommended Approach

Implement the additive opt-in exit executor for `ProviderKeyed` Work.

1. Add the closed exit type and new Durable-only executor interface in `ForgeTrust.AppSurface.Durable`.
2. Add an exit-aware registration helper and a backward-compatible preparation bridge. A legacy executor's returned result becomes `Succeeded`; its exceptions stay unclassified and conservative.
3. Teach `PostgreSqlDurableRuntimePump` to consume the encoded exit and map it to the existing internal completion kinds.
4. Reuse `ProvenNoEffect` only for explicit `RetryBeforeEffect`; do not alter the existing store decision matrix.
5. Document the distinction between an executor fact and the authoritative Work state in package READMEs, the Work protocol, troubleshooting guidance, and the public API snapshots.

This preserves the current durable boundary: the executor can state what it knows, while the provider decides what that fact safely does.

## Success Criteria

- A `ProviderKeyed` exit-aware executor can explicitly return `RetryBeforeEffect` after a permit and the PostgreSQL provider records `proven_no_effect`, applies the configured retry delay, and makes the same immutable Work identity available in `retry_wait`.
- A retry reuses the original ProviderKeyed activity/provider identity while advancing only the documented attempt and lease facts.
- Retry-limit and elapsed-deadline exhaustion, cancellation racing the exit, lease loss, scope-generation change, epoch rotation, and stale completion all retain their existing authoritative outcomes. None can be overridden by an executor exit.
- An exit-aware executor's uncaught exception produces the same ambiguous result as a legacy executor exception.
- `FailedTerminal` and `AmbiguousExternalOutcome` preserve the current post-permit provider-safety matrix rather than silently terminalizing or retrying an effect that may have happened.
- `ReconcileBeforeRetry` and `ManualResolution` registrations cannot opt into this V1 `ProviderKeyed` exit path accidentally.
- The test suite covers each exit kind, duplicate/late delivery, fake-clock retry timing, retry exhaustion, cancellation, claim fencing, permit observation, history, dispatch, Flow activity projection, and Schedule projection.
- Public API snapshot tests, package consumer tests, XML documentation, Durable README guidance, the Work protocol, and the diagnostics catalog describe the new opt-in semantics and the unchanged legacy path.
