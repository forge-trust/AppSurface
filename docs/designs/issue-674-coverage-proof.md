# Design: Truthful packaged-consumer coverage proof for #674

Generated by `/office-hours` on 2026-08-18
Branch: `HEAD` (detached)
Repo: `forge-trust/AppSurface`
Status: APPROVED
Mode: Builder

## Problem Statement

[#674](https://github.com/forge-trust/AppSurface/issues/674) records a real consumer failure: Skoolit ran 2,986 passing Release tests against the AppSurface/RazorWire `0.2.0-preview.4` graph, but its per-project Cobertura report gave the directly exercised `Skoolit.Web` assembly zero line, branch, and method hits. The overall coverage gate consequently failed while patch coverage remained 100%.

That is not a coverage-quality result. It is a false reporting result that makes a release gate untrustworthy. The issue must establish whether the historical preview.4 failure remains live in a current package graph, then make the packaged CLI release proof detect the same class of false success.

## What Makes This Cool

A package release should prove that its coverage tool sees code that its own disposable consumer actually executes. The release gate moves from “an XML file exists” to “the raw report and the merged report both contain real hits for a known class and branch.” That is the small, satisfying invariant: a coverage tool cannot ship while silently measuring nothing.

## Constraints

- Preserve the #672 VSTest collector contract: direct `coverlet.collector` capability, unique collector results directories, one hardened normalized Cobertura attachment, and deterministic canonical artifact paths.
- Treat test engine and coverage integration as separate observed inputs. Record the consumer’s `global.json` runner configuration plus evaluated `TestingPlatformDotnetTestSupport` as `VSTest`, `MTP`, or invalid/unknown; independently record the direct `coverlet.collector`, `coverlet.msbuild`, and `coverlet.MTP` references as `collector`, `MSBuild`, `native`, missing, or conflicting. Derive the displayed workflow label from those two fields before attributing a failure to the collector.
- Do not lower total coverage thresholds, suppress the application assembly, or rely on patch coverage to mask a zero-hit report.
- Do not add MTP support, a public sentinel option, or an MSBuild-driver redesign unless captured consumer evidence proves the selected engine requires it.
- Keep the normal and explicit-MSBuild smoke paths. This issue strengthens the default collector proof; it must not silently broaden or remove compatibility coverage.
- Preserve private-by-default package evidence. Sanitized issue evidence may name the public consumer and package versions, but must not publish raw source, credentials, or unbounded logs.

## Premises

1. A passing project that reports 0% for a directly exercised application assembly has an instrumentation, report, or merge defect.
2. The current collector path remains the supported VSTest integration. Native MTP requires its own coverage integration and is a separate branch only when the consumer classification proves it is in use.
3. The first diagnosis must separate raw canonical per-project Cobertura from merged Cobertura. An all-zero or missing raw report points to collection, inclusion, normalization, or report-shape failure; valid raw hits lost in the merged report point to fan-in. Diagnostics must say which evidence supports that classification.
4. Preview.4 is useful historical baseline evidence. The latest coordinated AppSurface prerelease already published when the current evidence run starts determines whether #674 is still open; a later candidate is comparison evidence only.
5. The durable guard belongs in the existing packed CLI consumer proof because that proof already gates package publication and owns a direct `Smoke.Tests` to `Smoke` execution path.

## Cross-Model Perspective

An independent reviewer agreed that the first diagnostic must inspect raw per-project Cobertura before merge, and that the existing `Smoke` fixture is the right durable guard. It challenged one assumption: the Skoolit proof must capture whether it runs VSTest or MTP before it is described as a collector regression. The reviewer recommended asserting the exact `Smoke.Calculator` class, at least one covered line, exercised conditional branch coverage, and retention of those hits in the merged Cobertura report.

## Approaches Considered

- **Evidence-first closure:** rejected because a current passing Skoolit run alone would answer the issue but leave no release-time semantic guard against recurrence.
- **Consumer-declared coverage sentinels:** rejected because a new public CLI option expands the API and compatibility surface before an adopter has shown that the existing release proof is insufficient.

## Recommended Approach

Extend the existing pre-publish packaged CLI consumer proof with semantic Cobertura validation, while using a classified two-version consumer investigation to decide the issue outcome. For #674, **current package graph** means the latest coordinated AppSurface prerelease already published when the evidence run starts; a later locally packed or prerelease candidate is optional comparison evidence, never a substitute for that baseline.

### 1. Classify the external proof before executing it

For the recorded Skoolit SHA, capture the package version, .NET SDK, nearest-upward `global.json` runner configuration when present, the exact coverage command, and the selected test projects. For every selected project, run the same evaluated metadata query the CLI uses:

```text
dotnet msbuild <project> -getItem:PackageReference \
  -getProperty:TestingPlatformDotnetTestSupport,TargetFramework,TargetFrameworks \
  -property:Configuration=Release -nologo
```

Normalize property/package values with Unicode trimming and ASCII case-insensitive comparison. The only accepted normalized `global.json` runner values are `VSTest` and `Microsoft.Testing.Platform`, matching the [.NET runner-selection contract](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test); missing `global.json` or an omitted `test.runner` maps to VSTest. Any malformed or other runner value is invalid. Evaluate once for a single target framework or once per TFM when `TargetFrameworks` is nonempty; a conflicting per-TFM result is `invalid`, not an averaged answer. For each TFM, `TestingPlatformDotnetTestSupport=true` requires MTP, `false` or unset permits VSTest, and any other value is invalid.

Read only evaluated direct `PackageReference.Identity` values, so conditional `Include` or `Update` entries and central package management are resolved by MSBuild before classification; transitive packages never count. The exact relevant identities are `coverlet.collector` for `collector`, `coverlet.msbuild` for `MSBuild`, and `coverlet.MTP` for `native`; package versions are recorded but do not alter identity. Aliases and original spelling do not create another identity after evaluation. Each TFM must expose exactly one relevant direct identity; zero or multiple identities are missing or conflicting. A global runner/property contradiction or engine/integration mismatch is invalid. Persist the normalized facts, then derive labels such as `VSTest / collector`, `VSTest / MSBuild`, or `MTP / native`; no classification is guessed.

Run exactly one current classified workflow. Attempt at most one historical preview.4 comparison only when the recorded consumer SHA and package inputs are already available; unavailable historical inputs are recorded as unavailable and trigger no retrieval work. Preview.4 explains the issue report but is not the acceptance test. For each attempted run retain bounded, sanitized evidence of the raw per-project report, merged report, gate result, and the `Skoolit.Web` assembly’s line and branch hit totals.

Outcome routing is explicit:

- Current VSTest collector proof contains real raw and merged hits: document the fixed-version boundary and close #674 with the evidence.
- Current VSTest raw report lacks `Skoolit.Web` or has zero hits: inspect collection, inclusion, engine classification, normalization, and expected report identity before changing merge logic.
- Current VSTest raw report has hits but the merged report loses them: investigate `CoverageMerge` fan-in with a focused regression.
- The consumer is MTP: document the engine mismatch or create a separate MTP-scoped issue. Do not quietly alter the VSTest collector contract.
- Engine or integration classification is invalid, unknown, missing, conflicting, or mismatched: block #674 on classification evidence. Draw no collector-regression conclusion and do not authorize a code, merge, or threshold change from that run.
- The required current checkout, restore, or classified workflow cannot run: record #674 as blocked on current external evidence. Do not close the issue or claim a fixed-version boundary; the owned package-proof hardening can still proceed.

### 2. Delivery boundary

The mandatory delivery is the semantic default-collector guard, its focused unit tests, the package-verification run, and the documentation/release evidence that describes that guard. Skoolit evidence determines only #674’s issue disposition and never gates package publication. A coverage-run or merge change is contingent on one demonstrated fault mechanism from the single current classified run; otherwise, no AppSurface runtime or CLI behavior changes.

### 3. Make the packed consumer proof semantic

In [CoverageCliConsumerProof.cs](../../tools/ForgeTrust.AppSurface.PackageIndex/CoverageCliConsumerProof.cs), keep the generated `Smoke` class library and `Smoke.Tests` direct reference. The existing fixture executes both `Calculator.Add` and both outcomes of `Calculator.Sign`; `Calculator.Untested` remains deliberately unexecuted for patch-target coverage.

The default proof selects exactly one VSTest project: `Smoke.Tests`; `Smoke.Msbuild.Tests` and the failing `Smoke.Browser.Tests` sentinel are excluded. `coverage run` must write a per-project `coverage-project.json` beside every project report with schema version, normalized solution-relative test-project path, and allocated slug. The PackageIndex proof enumerates only immediate `projects/*/coverage-project.json` manifests, validates their bounded schema and normalized relative paths, requires exactly one manifest for `Smoke.Tests/Smoke.Tests.csproj`, and then accepts only that manifest directory’s sibling `coverage.cobertura.xml`. It never calls the CLI-private slug allocator, guesses from a directory name, or recursively discovers arbitrary coverage files. An absent, nonregular, malformed, or duplicate matching manifest/report is a distinct failure. The merged report is exactly `TestResults/coverage-merged/coverage.cobertura.xml`; it must be one regular file. The fixture pins `coverlet.collector` 10.0.1, runs in the command’s default Debug configuration, and `Calculator.Sign` is source line 7 of the generated `Smoke/Calculator.cs` file. Do not infer correctness from an XML file’s existence, a report-level percentage alone, or test-process exit code.

Before finalizing parser assertions, run the existing generated fixture once in an isolated local proof directory and preserve the bounded raw and merged `Smoke.Calculator` XML fragments as test input. The supported subset below must match that observed collector/ReportGenerator shape. If the observed supported version differs, update the exact expected structural contract before implementation proceeds; do not silently broaden acceptance. This local contract-capture step is part of the owned fixture work, not an external release dependency.

Parse each file with `XmlReaderSettings` that sets `DtdProcessing=Prohibit`, `XmlResolver=null`, `MaxCharactersInDocument=1_048_576`, and a maximum element depth of 32 and element count of 10,000 enforced by the reader loop. Accept the supported Coverlet/ReportGenerator subset only: `coverage`, `sources`, `source`, `packages`, `package`, `classes`, `class`, `methods`, `method`, `lines`, `line`, `conditions`, and `condition`. Safely ignore unrelated attributes but reject unsupported required shapes, DTDs, entities, missing required identity attributes, or invalid numeric fields with an `unsupported Cobertura schema` diagnostic.

The semantic validator must require, in both reports:

- exactly one `package` named `Smoke`, exactly one `class` named `Smoke.Calculator` beneath it, and a normalized `filename` ending in `Smoke/Calculator.cs` after the fixture’s explicit `[Smoke]*` inclusion;
- at least one executed `Calculator` line with `hits > 0`, plus exactly one line numbered `7` for `Calculator.Sign` with `hits > 0`;
- `Sign` line 7 with `branch="True"`, `condition-coverage="100% (2/2)"`, and exactly one child `condition` with `type="jump"` and `coverage="100%"`. The positive and negative test inputs must cover both ternary outcomes; one covered branch is not sufficient;
- no duplicate expected package, class, line number, or `condition` identity. Any missing, duplicate, conflicting, malformed, or all-zero datum is a semantic failure rather than evidence that an arbitrary report is acceptable;
- ASCII decimal numeric grammar only: positive `line/@number` and `condition/@number` values are `^[1-9][0-9]*$`; nonnegative `line/@hits` is `^(0|[1-9][0-9]*)$`; the supported `Sign` branch value is exactly `100% (2/2)`, agreeing with one `jump` condition at `100%`. Overflow, signs, whitespace, decimals where an integer is required, or inconsistent branch totals are schema failures;
- fatal document-shape failures (`CPV004`) stop semantic extraction only for that report, while the other report is still independently checked. After a report parses, collect all semantic failures in stable order: package, class, filename, line/hits, branch, duplicate identity. The final failure order is raw document/semantics followed by merged document/semantics;
- stable proof invariant identifiers and fields: `CPV001` selected raw manifest/report missing or nonregular, `CPV002` selected raw manifest/report malformed or ambiguous, `CPV003` merged report missing/nonregular, `CPV004` unsupported Cobertura schema, `CPV005` package identity, `CPV006` class identity, `CPV007` filename, `CPV008` `Sign` line/hits, `CPV009` `Sign` branch, `CPV010` duplicate identity, and `CPV011` merge loss. Each rendered failure includes `scope=raw|merged`, ordered `invariants`, and one artifact-relative path;
- report-specific failure wording that says whether the failed invariant was in the raw project report or merged report, and names only the fixture path and stable artifact-relative path.

Keep the existing default collector artifact checks, explicit MSBuild compatibility artifact checks, merge artifacts, passing and failing gate artifacts, patch-target proof, excluded sentinel, and canary proof. The new semantic assertions are mandatory for the default collector path and the merged output derived from that path; they do not claim equivalent MSBuild or MTP semantics without separate evidence.

Normalize a `class/@filename` by rejecting empty/control-character values, replacing `\\` with `/`, splitting on `/`, rejecting empty, `.` and `..` components, and comparing the final two components ASCII case-insensitively to `Smoke/Calculator.cs`. Earlier absolute-path or source-root components are not opened or rendered and may differ by host.

### 4. Preserve release and test seams

Place the focused semantic parse/validation helper with the consumer-proof workflow or an internal, narrowly named companion type. It is package-validation infrastructure, not public CLI API. It returns structured, deterministic result data that the existing Markdown report renderer can expose without absolute paths or raw XML.

Add unit coverage in [PackageArtifactValidationTests.cs](../../tools/ForgeTrust.AppSurface.PackageIndex.Tests/PackageArtifactValidationTests.cs) for successful raw-plus-merged evidence and every failure category: missing or ambiguous report, prohibited DTD/entity, oversized/deep document, incorrect root or unsupported element shape, absent or duplicate expected package/class/line/condition, invalid filename, zero line hits, incomplete `Sign` branch representation, and a merge-only loss of otherwise valid raw hits. Reuse existing test doubles for command execution; no network, package publication, or real Skoolit checkout belongs in this unit test matrix.

If the single classified current VSTest reproduction demonstrates one fault outside the proof contract, add the smallest focused regression only for that demonstrated mechanism in the relevant coverage-run or merge suite. Do not change [CoverageRunDrivers.cs](../../Cli/ForgeTrust.AppSurface.Cli/CoverageRunDrivers.cs), scheduling, watchdog behavior, output ownership, or engine support for unrelated reasons.

### 5. Document the verification boundary

Update the package-proof reference in [packages/README.md](../../packages/README.md), the AppSurface CLI coverage documentation when behavior changes there, and the coordinated release notes. Explain that the pre-publish consumer verifies nonzero raw and merged coverage for an owned, directly exercised assembly; it does not certify arbitrary external application graphs. Link readers to the existing coverage-run driver-selection guidance for the VSTest/MTP boundary.

### Sections 1-11

#### 1. Architecture

```text
packaged CLI
    |
    v
generated Smoke solution
    |
    +--> Smoke.Tests (collector, direct Smoke reference)
    |          |
    |          v
    |     canonical raw report
    |          |
    |          +--> semantic validator (raw scope)
    |          +--> exact selected shard copy
    |
    v
coverage merge --> merged report --> semantic validator (merged scope)
                                      |
                                      v
                             scrubbed package-proof summary
```

Happy path: the one selected raw report and merged report both satisfy the known `Smoke.Calculator` line-7 branch invariant. Missing path: absent/nonregular raw or merged report emits its scoped invariant before any broad discovery can compensate. Empty path: an XML document with no expected package/class/line is a semantic failure. Error path: unsupported or hostile XML is bounded, rejected, and reported without leaking content. The design has no persistent state machine, network service, endpoint, or authorization boundary. Rollback is a normal revert of the package-proof change; no migration or feature flag is needed.

#### 2. Error and rescue registry

| Codepath | Failure | Handling | User/release evidence |
| --- | --- | --- | --- |
| Canonical raw report resolution | Missing, nonregular, duplicate, or wrong-project path | Fail the proof with `CPV001` or `CPV002`; do not fall back to another project. | Release fails with scoped invariant and artifact-relative path. |
| Cobertura extraction | DTD/entity, oversized/deep XML, unsupported shape, malformed numeric field | Reject the affected report as `CPV004`; still inspect the other report independently. | Release fails with bounded schema diagnostic. |
| Semantic validation | Missing/duplicate package, class, line, condition, zero hits, or incomplete branch | Collect stable failures per report in deterministic order. | Release shows invariant IDs and `raw` or `merged` scope. |
| Raw-to-merged comparison | Valid raw evidence missing or weakened after merge | Fail `CPV011`; preserve the raw success evidence. | Release identifies merge loss, not collection loss. |
| External consumer diagnosis | Checkout, restore, classification, identity, or execution fact absent | Mark #674 external evidence blocked/invalid; do not change CLI behavior or close the issue. | Issue record states what was not proven. |

No catch-all success path is permitted. Command logs remain private diagnostics; release-facing rendering contains only scrubbed structured evidence.

#### 3. Security and threat model

| Threat | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| XML entity expansion or oversized document | Medium | High | Prohibit DTDs, null resolver, 1 MiB character limit, depth 32, node cap 10,000. |
| Path traversal or symlink substitution | Medium | High | Resolve expected artifact-relative paths through existing guarded path ownership; require regular files and never open source paths from XML. |
| Host path, credentials, or XML leakage in release output | Medium | High | Add a scrubbed public mode with fixture-relative paths and bounded invariant messages; test redaction. |
| Malicious report ambiguity hides a failing target | Medium | High | Require exactly one canonical selected report and reject duplicates instead of first-match selection. |

There are no new secrets, endpoints, data stores, or runtime dependencies. The only new untrusted input is Cobertura XML already produced within the proof directory.

#### 4. Data-flow and interaction edge cases

```text
expected project identity -> guarded raw path -> parse -> semantic facts -> copy selected shard
          |                       |             |             |                  |
          v                       v             v             v                  v
     invalid slug            missing/ambig    DTD/shape      zero/duplicate      no fallback
          |                       |             |             |                  |
          +-----------------------+-------------+-------------+------------------+
                                                  |
                                                  v
                                           scoped proof failure
```

The plan handles nil/missing, empty, malformed, duplicate, and merge-only-loss paths. There is no interactive UI. The important edge case is a valid unrelated report beside a missing or zero-hit `Smoke.Tests` report; it must fail before copying any shard.

#### 5. Code quality

The helper stays internal and narrowly scoped to `CoverageCliConsumerProofWorkflow` or a companion type. It must share one canonical-report selection result between raw validation and shard copying to prevent duplicated selection logic. Parsing, semantic extraction, and rendering are separated so the renderer cannot reinterpret untrusted XML. A generalized report abstraction is intentionally deferred because the only owned contract is the generated Coverlet/ReportGenerator subset.

#### 6. Test review

```text
fixture creation
  -> canonical slug allocation
     -> raw report resolution: success / missing / duplicate / unrelated valid report
     -> schema parsing: valid / DTD / size / depth / shape / numeric failure
     -> semantics: package / class / filename / Sign line / branch / duplicate identity
     -> merge retention: raw valid + merged valid / raw valid + merged loss
     -> renderer: scoped IDs retained; absolute paths, XML, credentials absent
```

The shipping-at-2am test is a valid raw selected report whose merged report loses only `Smoke.Calculator` line-7 branch evidence and therefore fails `CPV011`. Hostile tests cover an unrelated valid report, duplicate expected report, DTD, path-like filename, zero hits, partial branch, and unsafe text in release evidence. Tests use static fixture XML and the existing recording command runner, so they are deterministic and do not depend on external package feeds, time, or test ordering.

#### 7. Performance

The proof parses at most two bounded XML reports and walks at most 10,000 elements per report. It must stream rather than materialize arbitrary XML and must not recursively scan the proof directory beyond the canonical expected path. This is negligible compared with the existing package-install and `dotnet test` work. A malformed large report fails within configured parser bounds rather than consuming unbounded memory.

#### 8. Observability and debuggability

The summary records proof result, package version/artifact digest, driver boundary, `raw`/`merged` scope, invariant IDs, and artifact-relative paths. Private artifacts retain command logs for maintainers. The issue evidence bundle additionally records consumer SHA, assets/lock fingerprint, SDK, runner, direct coverage identities, filters, target assembly/PDB facts, and report hit totals. This makes a later false-zero report diagnosable without publishing consumer source or machine details.

#### 9. Deployment and rollout

No database migration, environment parity change, or runtime rollout occurs. The delivery sequence is: capture the known fixture report shape; add deterministic parser/semantic tests; extend the consumer proof; run package verification; inspect scrubbed proof evidence; publish through the existing gate. If the proof unexpectedly rejects current valid output, retain the captured artifact privately, adjust the explicitly versioned supported subset, and rerun. ## Autoplan Phase 3: Engineering Review

### Step 0. Scope challenge and current-code evidence

The change is accepted at its current boundary. It affects the existing CLI coverage-output contract, PackageIndex consumer proof, focused CLI/package-index tests, and documentation/release evidence. That is five logical surfaces, not a new service or package. Reducing it would leave either the identity, semantics, provenance, or privacy failure class unaddressed.

The directly verified existing behavior explains the failure mode:

- `CoverageCliConsumerProof.CheckGlob` returns the first matching `projects/*/coverage.cobertura.xml` path, and `CopyCoverageShard` takes the first sorted recursive Cobertura file. Neither proves it belongs to `Smoke.Tests`.
- `CheckArtifact` checks only `File.Exists`, and the recording test runner writes `<coverage />` placeholders. The current proof cannot distinguish a valid report from an empty schema shell.
- `CoverageRun.AllocateProjectSlugs` is private to the CLI project, so PackageIndex cannot safely invoke it without introducing a dependency in the wrong direction.
- The detailed proof renderer emits work, NuGet, artifact, log, command, and output paths. It is a private diagnostic, not safe release evidence.

The engineering decision is a bounded `coverage-project.json` manifest emitted by the CLI next to every per-project report. This preserves the CLI as owner of its allocation rule while giving PackageIndex a stable, dependency-free identity contract. No coverage-driver, scheduler, watchdog, or MTP behavior changes.

### 1. Architecture review

```text
CoverageRun project execution
    |
    v
projects/<allocated-slug>/
    |- coverage-project.json  { schemaVersion, relativeProjectPath, slug }
    |- coverage.cobertura.xml
    |- dotnet-test.log
    |
    v
PackageIndex consumer proof
    |- enumerate immediate manifests only
    |- choose exactly one Smoke.Tests/Smoke.Tests.csproj manifest
    |- require regular sibling raw Cobertura report
    |- hash + validate raw semantics
    |- copy the selected report and compare raw/shard hashes
    v
coverage merge -> merged Cobertura -> independent semantic validation
    |
    +--> private detailed report (existing compatibility)
    +--> versioned scrubbed release evidence (new)
```

The manifest is a narrow output-contract addition, not a new public command. Its parser accepts a fixed schema version and relative project path only; it rejects unsafe values, a mismatched slug/directory, zero/multiple target matches, a nonregular report, and recursive fallback. The selected artifact object carries path, fixture-relative path, manifest facts, SHA-256, raw semantics, and copied-shard SHA-256 to every downstream operation. `CPV011` compares raw and merged semantic facts, not bytes, because ReportGenerator legitimately changes report structure.

The only new production failure is an older/invalid CLI package missing the manifest. It must fail `CPV001` before merge, which is appropriate because the proof is testing the candidate packed CLI. Rollback is a revert before publication. There is no migration, endpoint, persisted state, or runtime deployment concern.

### 2. Code-quality review

The plan avoids a wrong-direction PackageIndex-to-CLI reference and avoids duplicated slug hashing. `CoverageRun` owns allocation and manifest emission; PackageIndex owns consumption and proof semantics. The manifest selection, regular-file validation, hash calculation, XML parse result, and renderer model should be internal types with one immutable selected-artifact value passed to validation and copy operations. No broad `Directory.EnumerateFiles(..., AllDirectories)` remains on the canonical proof path.

The existing private full report remains byte-compatible for maintainer diagnostics. The new scrubbed evidence should be a separate renderer and versioned model, which prevents a security fix from silently changing downstream consumers of the detailed report. The external Skoolit investigation is owned by the #674 implementer as a diagnostic-only record with a bounded JSON schema; it is not invoked by the package consumer workflow.

### Developer perspective

I maintain a .NET repository with a coverage gate. I open the CLI README and find the normal path: run `coverage run --dry-run`, run `coverage run`, then run `coverage gate`. That tells me whether my own selected test projects can produce coverage. I also see `collector` as the default and `msbuild` as a compatibility route, but I need the command output to tell me which guarantee I actually received. When a package release is involved, I use `verify-packages`. Today it creates a consumer-proof report, but the report starts with machine directories and a full command ledger. If it says coverage exists, I still have to infer whether it inspected the intended project, whether it saw an exercised branch, and whether merge retained it. I want the first screen of the artifact to say: collector semantic proof passed or failed; raw and merged scopes; selected fixture-relative report; and exactly what to do next. ### DX implementation contract

The release-facing artifact is exactly `coverage-cli-consumer-proof.evidence.json` with `schemaVersion: 1`. It is produced beside the existing private `coverage-cli-consumer-proof.md`; it does not replace or redact that detailed maintainer report. The schema has only:

```text
verdict, packageVersion, packageArtifactDigest,
driverBoundary { runner, integration, directPackages, assuranceLevel },
raw { outcome, artifactRelativePath, sha256, invariants[] },
merged { outcome, artifactRelativePath, invariants[] },
failures[] { code, scope, cause, nextAction, evidenceRelativePath }
```

The artifact excludes command names/arguments, working directories, NuGet sources/configuration, absolute paths, raw XML, credentials, and arbitrary output excerpts. `CPV` is authoritative for the package consumer semantic proof. `ASCOV` remains authoritative for the underlying public CLI run/merge/gate diagnostic; a CPV `nextAction` may point to the relevant `ASCOV` guide but never replaces it.

The documentation adds one cross-linked “Coverage proof levels and driver boundary” section:

```text
Need to validate your repository's coverage setup?
  -> collector: coverage run --dry-run -> coverage run -> coverage gate
     Guarantee: selected VSTest projects produced normal CLI artifacts.

Need to validate a packed CLI candidate before publication?
  -> PackageIndex verify-packages
     Guarantee: owned Smoke.Tests collector proof retained class/line/branch facts
     from the selected raw report to the merged report.

Need legacy VSTest compatibility?
  -> --coverage-driver msbuild
     Guarantee: artifact compatibility only; not semantic raw-to-merged proof.

Have externally produced matrix shards?
  -> coverage merge -> coverage gate
     Guarantee: fan-in/gate only; not owned collector consumer proof.

Need retention for investigation?
  -> --no-clean only deliberately; retained artifacts may be stale.

MTP selected or runner/package facts conflict?
  -> do not switch drivers to satisfy the proof; capture classification and use
     the separate engine path or issue.
```

The manifest and evidence schemas use additive, versioned evolution. Schema `1` readers reject unknown required structure and unsupported major versions with an actionable incompatibility result. Upgrading Coverlet, ReportGenerator, or runner requires one isolated generated-fixture capture, the package-index fixture suite, and `verify-packages`; an unsupported observed shape is a tool-compatibility result, while a valid shape with missing or zero expected semantics is a coverage defect.
