## Problem Statement

The built-in `coverage` producer measures the whole solution and requires overall thresholds ([EvidenceContracts.cs:186](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/EvidenceContracts.cs), [CoverageEvidenceProducer.cs:174](../../Evidence/ForgeTrust.AppSurface.Evidence.Cli/CoverageEvidenceProducer.cs)). That is the right claim for a repository-wide gate and an expensive one for a pull request: every change pays for every test project. This repository's own gate, `solution-coverage`, declares a 5400 second timeout ([evidence.policy.json](../../.github/evidence.policy.json)). That figure is a budget, not a measured duration.

[#930](https://github.com/forge-trust/AppSurface/issues/930) proposes a coverage producer that runs a declared subset of test projects and gates on changed-line coverage only, under its own assertion id.

## What Makes This Cool

A pull request that touches one package and its tests pays for that package's tests and still gets signed evidence that says exactly what was measured. The claim is narrower than the repository-wide one and it is true. The receipt names the source it answered for, the projects that ran, and every changed line left uncovered.

## Constraints

- Existing policies keep their canonical bytes, `PolicyDigest` and `PlanDigest`. `EvidenceCoverageGateRequirements` is not changed.
- Inferring the project list from project references stays a non-goal, as the issue says.
- The repository-wide gate and its assertions are not changed.
- VSTest and the Coverlet collector only, matching the existing coverage path.
- No new package dependency in v1.

## Premises

Agreed at D4, premise 2 revised at D6 after the cold read.

1. The denominator comes from the diff, not the report. The scoped assertion cannot reuse the gate unchanged.
2. A scoped producer declares the source it answers for, not only its test projects. A changed line in scope counts as covered or uncovered only when the report has a row for it. A changed file in scope with no rows is not applicable only when independent evidence shows its owning assembly was instrumented. Otherwise the claim fails and names what is missing. Report silence is unknown, and unknown fails.
3. A scoped pass never closes a repository-wide assertion. Planner rules on the declaration enforce it.
4. The repository-wide gate keeps running somewhere a merge cannot skip it for long.
5. The first route is one area of this repository, and the real duration of the full run is recorded before anything is built.

## Recommended Approach

### Declaration

Add an optional, init-only `CoverageScope` property to [`EvidenceProducerDeclaration`](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/EvidenceContracts.cs), omitted from JSON when null, the same way `Test` is.

```json
{
  "id": "config-patch-coverage",
  "kind": "coverage",
  "version": "1.0.0",
  "requiredResources": [],
  "assertionIds": ["appsurface/coverage/patch-scoped@1"],
  "artifactSlots": [
    { "logicalName": "scoped-coverage-receipt", "relativeRoot": "coverage-scope", "mediaType": "application/json", "required": true, "maximumBytes": 262144 }
  ],
  "timeoutSeconds": 900,
  "coverageScope": {
    "projects": ["Config/ForgeTrust.AppSurface.Config.Tests/ForgeTrust.AppSurface.Config.Tests.csproj"],
    "sources": [
      { "pattern": "Config/ForgeTrust.AppSurface.Config/**", "assembly": "ForgeTrust.AppSurface.Config" }
    ],
    "minPatchLinePercent": 95,
    "minPatchBranchPercent": 85,
    "patchLineMode": "codecov",
    "tolerancePercent": 0.5
  }
}
```

- `projects`: 1 to 32 unique repository-relative test project paths, validated with the path grammar the `test` producer already uses.
- `sources`: 1 to 32 entries. `pattern` uses the policy rule pattern grammar. `assembly` is the assembly name as it appears in the Cobertura `package` element. The assembly is declared, not inferred from a project file, so no MSBuild evaluation is needed and the value is bound into `PlanDigest`.
- At least one of `minPatchLinePercent` and `minPatchBranchPercent` is required. `patchLineMode` and `tolerancePercent` mean what they mean in `EvidenceCoverageGateRequirements`.
- `coverageExecution` stays available. `coverageGate` must be absent.

The issue asked for overall thresholds to become optional. This design does not do that. A scoped declaration has no overall thresholds because its block has no field for them, and the repository-wide record stays strict.

### Planner validation

New `ASEVD150` and upward, each added to the [planner diagnostic table](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/README.md).

| Condition | Result |
| --- | --- |
| `coverageScope` on a kind other than `coverage` | rejected |
| `coverageScope` together with `coverageGate` | rejected |
| Invalid, duplicate or out-of-bounds project, pattern or assembly; no patch threshold; a threshold outside 0 to 100; unknown mode | rejected |
| A scoped producer whose `assertionIds` is not exactly `appsurface/coverage/patch-scoped@1` | rejected |
| A producer without `coverageScope` that declares `appsurface/coverage/patch-scoped@1` | rejected |
| A scoped producer without the required `scoped-coverage-receipt` slot | rejected |
| A scoped producer in a profile whose scope is not `Targeted` | rejected in v1 |

The fourth row plus the existing `ASEVD115` gives the issue's acceptance line for free: an obligation that names a scoped producer for a repository-wide assertion is already rejected because the producer does not declare that assertion.

**Routing is not validated by the planner.** A rule broader than the producer's sources, for example `Config/**` selecting a profile whose producer answers only for `Config/ForgeTrust.AppSurface.Config/**`, would let a change elsewhere under `Config/` pass with nothing in scope. An earlier draft rejected such rules in the planner by comparing patterns. That check cannot work: the validation tool's `ResolveScope` re-plans each lane through a derived policy whose only rule is `**` ([RepositoryEvidenceWorkflow.cs](../../tools/ForgeTrust.AppSurface.Evidence.Validation/RepositoryEvidenceWorkflow.cs), about lines 238 to 260), so every lane plan and every verify would be rejected. In v1 the guard is therefore two things: the receipt counts out-of-scope changed files so the gap is visible, and each repository that adds a route adds a policy test that every rule selecting a scoped profile matches only paths under that producer's sources or declared test project directories. This repository's test is listed under First route. A general planner guard is open question 2.

### Classifier core

A pure function, next to [`TestRunReconciler`](../../Evidence/ForgeTrust.AppSurface.Evidence.Cli/TestRunReconciler.cs) and tested the same way, with no process or file access:

`Classify(changedLines, sources, reportRows, reportedPackages, thresholds) -> verdict + metrics + per-file results`

Each added line in the diff gets exactly one class:

| Class | Rule |
| --- | --- |
| `OutOfScope` | The path matches no source pattern. Counted, never scored. |
| `Covered` or `Uncovered` | The path is in scope and the report has a row for the line. `patchLineMode` decides partial branches exactly as today. |
| `NotApplicable` | The path is in scope, the report has no row for the line, and the source's declared assembly is in `reportedPackages`. |
| `Unknown` | The path is in scope, the report has no row for the line, and the declared assembly is not in `reportedPackages`. |

Verdict, first that applies:

1. `ScopeAssemblyNotInstrumented`: any declared assembly is missing from `reportedPackages`, whether or not the diff touched it. The check runs for every declared assembly so a drifted project list fails on the first run, not on the first unlucky diff. This also means `Unknown` lines cannot survive to scoring. The class exists so the receipt can list the affected files in `unknownFiles`.
2. `BelowThreshold`: a declared patch metric with at least one measurable line is under its threshold after tolerance.
3. `Complete`: every declared metric is `measured` and at or above threshold, or `notApplicable` with zero measurable lines.

The metric shape reuses [`CoveragePatchMetricResult`](../../Coverage/ForgeTrust.AppSurface.Coverage/CoverageContracts.cs): outcome, reason, changed lines, measurable, covered, percent. Zero measurable lines in scope is `notApplicable` with a null percent, never 100.

**Known gap, stated.** With the assembly present, a file with no rows is `NotApplicable`. That is correct for a file with no sequence points and wrong for a file removed from coverage by `[ExcludeFromCodeCoverage]` or a collector filter. The full gate has the same gap today. PDB sequence points would close it; that is the upgrade, and `reportedPackages` is the single input it would replace.

### Producer behaviour

`CoverageEvidenceProducer` branches on `CoverageScope`:

1. Requires `--solution`, exactly as the unscoped branch does today ([CoverageEvidenceProducer.cs](../../Evidence/ForgeTrust.AppSurface.Evidence.Cli/CoverageEvidenceProducer.cs), lines 86 to 89). Explicit projects skip solution discovery, but one code path and one base directory are worth more than dropping the argument. Missing: `SolutionUnavailable`.
2. Requires a diff snapshot. Missing: `DiffUnavailable`, as for today's patch thresholds.
3. Resolves each declared project path against the repository root, the root the adapter already finds with `GitRepositoryRootResolver`, and passes absolute paths in `TestProjects`. The coverage runner resolves relative explicit projects against the current directory ([CoverageRun.cs](../../Cli/ForgeTrust.AppSurface.Cli/CoverageRun.cs), about line 1496), so the adapter must not pass them through relative. Everything else in the run request is unchanged.
4. On a successful run, reads the merged report through the existing patch evaluator's reader and passes rows and package names to the classifier. Where that reader is reachable from is implementation step 2.
5. Writes the receipt for every outcome it returns, in the shape given under Receipt and summary.
6. Returns the declared assertion only for `Complete`.

The producer enforces an internal deadline earlier than `timeoutSeconds`, with the same reserve rule the `test` producer uses, so it can stop the run and still write the receipt. If the receipt cannot be written, the required slot is missing and the manifest verdict is `Invalid`, which is never gate-eligible.

| Reason | Outcome |
| --- | --- |
| `Complete` | `Passed` |
| `BelowThreshold`, `ScopeAssemblyNotInstrumented`, `RunFailed` (a failed test, merge or artifact step) | `Failed` |
| `SolutionUnavailable`, `DiffUnavailable` | `Unavailable` |
| `DeadlineExceeded` | `TimedOut` |

A failed test in a declared project already fails the coverage run, so no separate completeness check is added. The [`test` producer](../../Evidence/ForgeTrust.AppSurface.Evidence.Cli/README.md) remains the way to claim that every selected test ran.

### Receipt and summary

`scoped-coverage-receipt.json`, schema version 1, in the declared slot:

- declared projects; each source with its pattern, assembly and `assemblyReported` (true, false, or null when no report was read)
- thresholds and mode
- line and branch metrics in the `CoveragePatchMetricResult` shape
- up to 200 in-scope files, each with measurable, covered and up to 50 uncovered line numbers, with a `truncated` flag when either bound is hit
- `unknownFiles`: up to 50 in-scope changed file paths whose source's assembly was not reported, with a `truncated` flag
- the count of out-of-scope changed files
- `overallGateEvaluated: false`
- the reason code

When no report was classified (`RunFailed`, `SolutionUnavailable`, `DiffUnavailable`, `DeadlineExceeded`), the receipt still carries the declared projects, sources, thresholds and reason. Both metrics have outcome `unverified` with null counts, every `assemblyReported` is null, and the file lists are empty.

This answers the issue's second open question: line numbers per file, bounded. `Diagnostic` carries one line, for example `Scoped patch coverage, 1 project, 1 source: line 97.2% (35/36), branch not applicable. The repository-wide gate was not evaluated.` `explain` and `evidence-summary.json` list the projects and sources.

### First route in this repository

Config: source `Config/ForgeTrust.AppSurface.Config/**`, assembly `ForgeTrust.AppSurface.Config`, project `ForgeTrust.AppSurface.Config.Tests`, which references that project directly.

The validation tool needs the same changes the [#929 design](issue-929-test-producer.md) planned for its tooling route and that have not landed: accept a fifth producer id with its fixed declaration, add a scope for it in `ResolveScope`, register the built-in producer by id, add a `selection.json` field, and join a new job to the existing `Coverage evidence gate` job's `needs` so a red scoped job blocks a merge. Whichever of the two routes lands first builds that plumbing.

**The profile.** `config-scoped` is `Targeted`, has no resources, and holds two producers: `config-patch-coverage` with one obligation for `appsurface/coverage/patch-scoped@1`, and the existing `package-checks` with its three existing obligations. It is the current `code` profile with `solution-coverage` swapped for the scoped producer, so package evidence is not lost.

**The rules.** Three, all selecting by path under the Config package:

| Pattern | Profile | Why |
| --- | --- | --- |
| `Config/ForgeTrust.AppSurface.Config/**` | `config-scoped` | the declared source |
| `Config/ForgeTrust.AppSurface.Config.Tests/**` | `config-scoped` | the declared test project, so a source-plus-tests pull request does not fall back to the full gate through the existing `unit-tests` rule (`**/*.Tests/**`, precedence 20) |
| `Config/ForgeTrust.AppSurface.Config/**/*.csproj` | `code` | a project file change can alter what other assemblies get, so it keeps the full gate |

The exact precedence values are set in implementation, with a planner test that pins which profile each of these paths selects: a Config `.cs` file, a Config test file, the Config project file, and the Config README.

What each kind of change then proves:

- **Source, or source plus tests:** the Config tests ran and passed, and changed lines under the source meet the patch thresholds.
- **Tests only:** the Config tests ran and passed. Both patch metrics are `notApplicable`. Today such a change runs the full gate, whose aggregate thresholds would catch a deleted test that drops overall coverage. The scoped route does not catch that on the pull request. The unconditional run on `main` below does, after the merge.
- **README or another non-code file under the source:** `package-checks` runs as it does today for the `packages` profile, and the scoped producer runs the Config tests and reports `notApplicable`. That is more evidence than today, at the cost of one short test run.

**The repository policy test.** A test in the validation tool's test project asserts that every rule selecting `config-scoped` matches only paths under a declared source pattern or a declared test project directory. This is the routing guard described under Planner validation.

**The full gate on `main`.** Premise 4 has to hold in fact. Today [build.yml](../../.github/workflows/build.yml) plans push runs with the same path-routed `--operation plan --scope coverage` step as pull requests (about lines 111 and 1102), so after the route lands nothing would run the full gate for a Config-only change. The mechanism is a validation-tool option, not a workflow flag. `requiresCoverage` is computed from the plan ([RepositoryEvidenceWorkflow.cs](../../tools/ForgeTrust.AppSurface.Evidence.Validation/RepositoryEvidenceWorkflow.cs), line 111), the coverage job re-plans, and `run` requires the supplied plan to equal the re-resolved one and registers only the plan's producers. Overriding the flag in the workflow would start the job and still run no `solution-coverage`. So the tool gains one option, `--full-coverage`, valid with `--scope coverage`: the coverage lane is planned against the `coverage` profile, which holds `solution-coverage`, whatever the changed paths select. `plan`, `run` and `verify` all accept it, so the plan-equality check holds. `build.yml` passes it on `push` to `main` in both places it plans the coverage lane. The pull request path is unchanged. This workflow change lands before the route rules, in its own pull request. A nightly schedule is the alternative and is open question 1.

**Rollout in three steps.**

1. **Full gate on `main`.** The tool option and workflow change above. A Config `.cs` change already selects `code` today, so a live push proves nothing before the route exists. The proof is a validation-tool test: resolve a policy that already contains the `config-scoped` route for a Config-only path set with `--full-coverage` and assert `producerIds` contains `solution-coverage`; the same resolution without the option must not contain it.
2. **Shadow.** A separate workflow file, `.github/workflows/config-scoped-shadow.yml`, because `paths` filters exist only on workflow-level triggers and `build.yml` must keep running for every pull request. It triggers on `pull_request` with `paths` for the two Config directories, is not a required check, and needs none of the validation-tool plumbing. It checks out with full history, writes the patch with `git diff --binary <base sha>...<head sha>`, builds the `appsurface` CLI from source and runs `appsurface evidence run --policy .github/evidence.shadow.policy.json --diff-file <patch> --solution ForgeTrust.AppSurface.slnx --observation-only --output <dir>`. Every flag exists: `--policy` and `--diff-file` at [EvidenceCommands.cs](../../Cli/ForgeTrust.AppSurface.Cli/EvidenceCommands.cs) lines 384 to 393, `--output`, `--solution` and `--observation-only` at lines 147 to 156. `--observation-only` yields a claim that is deliberately ineligible for a gate. The shadow policy holds one profile, the scoped producer with its obligation, and that profile is also the conservative profile, since the planner rejects an empty conservative profile (`ASEVD105`). `combineProfiles` is false. A pull request that touches Config plus anything else therefore still resolves to the scoped profile and the producer runs. The file is deleted when the route lands. Compare elapsed time and line-level results against the full gate on five real pull requests.
3. **Route.** Validation-tool plumbing, the `config-scoped` profile, the three rules and the policy test. Only then does a Config pull request skip `solution-coverage`.

### Documentation

Per [AGENTS.md](../../AGENTS.md): XML docs on every added member; reference, decision and pitfall content in the [Contracts](../../Evidence/ForgeTrust.AppSurface.Evidence.Contracts/README.md), [Planner](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/README.md) and [Evidence CLI](../../Evidence/ForgeTrust.AppSurface.Evidence.Cli/README.md) READMEs. The CLI README sentence "A filtered suite cannot close a coverage assertion" gains the scoped exception with a link. Pitfalls to state plainly:

- A scoped pass says nothing about overall coverage or about changed files outside `sources`.
- A line covered only by a test project that is not declared counts as uncovered. This fails closed and usually means the project list is incomplete.
- The assembly name must match the Cobertura package name. A project that overrides `AssemblyName` needs that name declared.
- A file excluded from coverage by attribute or filter is reported as not applicable.
- A scoped gate without an unconditional repository-wide gate lets overall coverage erode.

### Tests

- Classifier: table-driven, one case per class and per verdict, including the Codex pair (assembly absent fails, marks the source `assemblyReported: false` and lists the file in `unknownFiles`; interface-only file in a present assembly is not applicable), zero measurable lines, out-of-scope only, and both line modes.
- Planner: one test per new diagnostic, plus a test that an unchanged legacy policy keeps its exact digests.
- Adapter: a two-assembly fixture solution where the declared test project references only one assembly. Cases: pass, below threshold, changed line in the unreferenced assembly, failed test, no diff, no solution, and the internal deadline, each asserting the receipt shape.
- No reflection. The classifier's inputs are the seam.

## Open Questions

1. This design runs the full gate on every push to `main`. The issue says "on a schedule". A nightly run costs less and leaves up to a day in which `main` is unmeasured. The owner picks; the design works with either as long as one exists before the route.
2. Should the planner itself guard against a rule broader than a scoped producer's sources? It would have to hold on the root policy and exempt the validation tool's derived `**` policy. v1 uses a per-repository policy test.
3. The issue's first open question: scoped assertion in a `Release` scope profile. This design rejects it in v1. Reverse it if a release profile has a real use for a scoped claim.
4. Final `ASEVD` numbers, and ordering against the open #917 pull request, which touches the same record.

## Success Criteria

- A policy with a `coverageScope` block validates. One with no patch threshold, or with both `coverageScope` and `coverageGate`, is rejected.
- An obligation that names a scoped producer for a repository-wide assertion is rejected at policy validation.
- A run over declared projects with every changed in-scope line covered closes `appsurface/coverage/patch-scoped@1`.
- A changed line in a declared assembly that no declared project instruments fails with `ScopeAssemblyNotInstrumented`. The receipt marks that source `assemblyReported: false` and lists the file in `unknownFiles`.
- A pull request that changes Config source and Config tests together selects `config-scoped` and does not select `solution-coverage`. One that changes the Config project file selects `code`.
- With the route in the policy, a Config-only path set planned with `--full-coverage` contains `solution-coverage`, and without the option does not. The tool test for this lands before the route rules.
- A changed line in an instrumented assembly that no declared project executes counts as uncovered and is listed with its file and line.
- A diff with no measurable in-scope lines reports `notApplicable` and passes, with a null percent.
- `projects`, `sources` and thresholds change `PlanDigest` when edited. A legacy policy's digests are byte-identical before and after.
- On five shadowed Config pull requests, the scoped result agrees line for line with the full gate's patch result for in-scope files, and the measured time saved is recorded.

### R2-1 — feasibility (blocking)

**Problem**

> The full-gate-on-main mechanism does not make solution-coverage run, and its acceptance check passes without the change. requiresCoverage is not a workflow input: tools/ForgeTrust.AppSurface.Evidence.Validation/RepositoryEvidenceWorkflow.cs line 111 computes it as plan.Profile.Producers.Any(id == "solution-coverage") and writes it to selection.json; .github/workflows/build.yml line 115 only copies it to the requires_coverage job output. The coverage job then re-plans (build.yml line 1102) and calls '--operation run --scope coverage' (lines 1103 to 1113), which requires the supplied plan to equal the re-resolved plan (RepositoryEvidenceWorkflow.cs lines 50 to 52) and registers only plan.Profile.Producers (lines 123 to 133). After the route lands, a Config-only push resolves to config-scoped, whose coverage lane projection holds no solution-coverage producer, so overriding the flag in the workflow starts the job but the run still executes no solution-coverage producer, and line 1104 reads requiresCoverage from the re-planned selection.json as false.
