# Offline evidence subject image candidate

The [independent cleanup supervisor](https://github.com/forge-trust/AppSurface/blob/main/docs/evidence-gate-subject-supervisor.md) removes only a labeled per-run container and its verified quota-limited host tmpfs. Its attestation remains non-claiming until a trusted verifier consumes and binds it to the exact subject execution.

## Protected-main publisher (future, non-claiming)

[`evidence-gate-subject-image-publish.yml`](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate-subject-image-publish.yml) is a protected-main-only publisher. It runs after relevant changes land on `main`, never from a manually selected workflow revision, pull request, or unprotected branch. It first runs the complete native validation lane, which builds and validates `appsurface-subject-native-validation:local`. Only after that succeeds does a separate, credentialed job load the exact saved image archive, verify its archive SHA-256 and Docker image ID, and push it to GHCR. Immediately before pushing, it compares the triggering commit with the current `main` head and fails when they differ, so a delayed environment approval or queued run cannot publish a revision already superseded at that check. The publisher tags the image with the source commit and workflow run, reads the registry manifest descriptor and raw manifest, requires the registry config digest to match the validated local image ID, and accepts a digest only when the manifest bytes hash to the registry descriptor's SHA-256. It pulls that immutable digest and checks the image ID and `linux/amd64` platform again before creating a GitHub artifact attestation. The attestation subject is `ghcr.io/forge-trust/appsurface-subject-native-validation@sha256:…`. The workflow does not rebuild after validation, does not run for pull requests or unprotected refs, and its result does not establish evidence-gate eligibility or a coverage claim.

Before its first run, configure the repository variable `EVIDENCE_GATE_SUBJECT_IMAGE` to exactly `ghcr.io/forge-trust/appsurface-subject-native-validation`. Create the `evidence-gate-subject-image-publish` GitHub environment, allow exactly the `main` branch, require at least one reviewer with self-review disabled, and disable administrator bypass of protection rules. The publisher checks those environment settings through GitHub's API before it downloads or loads the image. Its separate [main-ruleset guard](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/evidence-gate-subject-image-publish.yml) reads AppSurface ruleset `7295365` and the repository default branch before loading the image and again immediately before pushing it. The ruleset must actively cover `main`, prohibit force pushes and all bypass actors, require at least one pull-request approval, and dismiss stale approvals or require approval after the last push. The guard fails closed if the ruleset is replaced without a reviewed workflow update. The current ruleset permits organization-administrator bypass and does not require a fresh approval after the last push, so an administrator must correct both settings before this publisher can run. The workflow also fails closed when its repository, event, ref, image name, source SHA, run identity, or environment protection does not match the expected values.

Add `EVIDENCE_GATE_RULESET_INSPECTION_TOKEN` as a secret in that protected publisher environment, scoped to this repository and granted repository Administration (write) permission. GitHub [omits `bypass_actors` from ruleset API responses](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) unless the caller can write the ruleset; the ordinary read-only workflow token cannot prove there are no bypass actors. The secret is used only for the two ruleset reads, before image download and immediately before push. A missing secret or an API response without `bypass_actors` blocks publication. Keep this administration-capable token out of the subject job and all other workflows, and prefer a short-lived repository-scoped GitHub App token when available.

The first successful push creates a private GHCR package by default. After reviewing it, manually change its visibility to Public in package settings before enabling anonymous pulls; GitHub does not allow a public package to be made private again. Confirm the package is linked to `forge-trust/AppSurface` and that the repository has package write access. See GitHub's [Container registry access and visibility guidance](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry#visibility-and-access-permissions). Record the exact digest from the run summary as the candidate image reference; tags and local Docker image IDs are not runtime references. Verify its provenance with the printed [`gh attestation verify`](https://cli.github.com/manual/gh_attestation_verify) command, which constrains the signer to this repository's publisher workflow, `refs/heads/main`, and the exact source commit. Keep this publisher explicitly non-claiming until the separate policy, isolation, and artifact-verification requirements are completed. For how `actions/attest` binds provenance and registry metadata, see [GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations).

`publish_guard.py` contains the publisher's event/ref/repository/image and run-identity checks, checks the environment and current reviewed ruleset without accepting a branch-name match as proof of protection, verifies that the transferred archive is byte-identical to the validation output, confirms the image remains `linux/amd64` with the same local image ID, and verifies the published registry digest against the raw manifest bytes. Its focused tests can be run with `python3 -m unittest discover -s scripts/evidence-gate-subject-image -p 'test_publish_guard.py'`.

The [Containerfile](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject-image/Containerfile) is the base-owned image recipe for the fixed [code-coverage subject entrypoint](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject-entrypoint.py). It starts from the digest-pinned .NET 10.0.401 SDK image, adds Python for the fixed runner, and copies a local NuGet feed into `/opt/appsurface/locked-dependencies`. The [subject launcher](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject.py) accepts only a published image reference ending in `@sha256:<digest>`, requires that exact digest already in rootless Podman storage, and runs it without network, credentials, or writable image layers. The [native validation lane](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml) checks the host SDK feature band and Keycloak test lock selection before image validation; Aspire AppHost lock-file inputs differed under the earlier 10.0.102 image.

Publish only from a reviewed protected-base checkout. Implementation-branch builds are local recipe checks and cannot be promoted as trusted base-owned inputs. The build context must contain `evidence-gate-subject-entrypoint.py` from that same checkout and a `locked-dependencies/` directory assembled from the solution's tracked lock files plus explicitly pinned project SDK packages. `Aspire.AppHost.Sdk` 13.4.4 is such an SDK: project SDK resolution occurs before ordinary package restore, and NuGet does not list that SDK archive in `packages.lock.json`. The [feed builder](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-build-offline-feed.py) accepts it only when a selected project declares the exact ID/version and the archive matches its reviewed content-hash pin. Every archive must match its lock or project-SDK pin; do not populate this directory from an unverified cache or from a PR checkout for publication. This is NuGet's package content hash as reported by [`dotnet nuget verify`](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-nuget-verify), not a plain SHA-512 of the `.nupkg` ZIP bytes, and the cache's `.nupkg.metadata` value alone does not authenticate the archive. A build context assembled for one policy/tool revision is not automatically valid for a later revision. The checked-in recipe pins the *base* image; after publishing, record and configure the **resulting image's** immutable registry digest. A tag, local image ID, or the base image digest is not a valid runtime value.

Use the [offline feed builder](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-build-offline-feed.py) on that protected checkout to select only projects in `ForgeTrust.AppSurface.slnx`, resolve each project's default or `linux-x64` lock exactly as the fixed subject entrypoint does, and verify each copied package with NuGet. A macOS lock beside a selected project does not add packages to this Linux image. The builder takes a physical, already-restored NuGet global cache and a **new** destination directory. For example, after setting `trusted_checkout`, `global_packages`, and `context` to absolute physical paths and creating the empty context parent:

```sh
python3 "$trusted_checkout/scripts/evidence-gate-build-offline-feed.py" \
  --checkout "$trusted_checkout" \
  --solution ForgeTrust.AppSurface.slnx \
  --global-packages "$global_packages" \
  --output "$context/locked-dependencies"
cp "$trusted_checkout/scripts/evidence-gate-subject-entrypoint.py" \
  "$context/evidence-gate-subject-entrypoint.py"
docker buildx build --platform linux/amd64 \
  --file "$trusted_checkout/scripts/evidence-gate-subject-image/Containerfile" \
  --tag appsurface-subject-candidate:local "$context"
```

The context must not contain a PR checkout. The builder fails if a selected archive is missing, linked, malformed, or has the wrong NuGet content hash; a dependency-changing PR that needs a new package therefore remains ineligible until the base-owned image or an approved mirror is refreshed. The builder does not run restore or build hooks. Its result counts are useful for audit logs, but do not attest the final image.

Before building the image, the opt-in native lane records the Keycloak tests project's evaluated `NETCoreSdkRuntimeIdentifier` and `NuGetLockFilePath`. It requires the project to select the tracked `packages.linux-x64.lock.json`, then runs that project in locked, serial mode (`--locked-mode --disable-parallel -m:1`) without overriding the restore runtime. The host sets `NUGET_PACKAGES` to the isolated temporary cache before project evaluation so the project SDK resolver and ordinary package restore use the same candidate package supply. An untracked RID-specific lock generated by the host restore fails preflight and prints `git status --short` for the Keycloak tests directory; the script never regenerates or edits lock files. The machine-readable preflight record is written under the lane's `RUNNER_TEMP` work directory, while both evaluated property values are printed in job output.

Run the feed assembly in a reviewed Linux .NET 10 builder. `dotnet nuget verify` also checks signatures; host trust stores can differ. A local macOS run stopped on `CommandLineParser` 2.9.1 because its historical signature chain was rejected there, while the pinned Linux SDK verified the same archive and reported a matching lock hash. Treat a verifier failure as an unavailable build input and investigate it; do not accept a cache sidecar or bypass the content-hash check.

After building the candidate image, the native lane explicitly transfers it from Docker to rootless Podman with `docker save` and `podman load`, then requires both stores to report the same 64-hex image ID after removing an optional `sha256:` display prefix. Before the Docker cold-cache restore starts, the trusted host mounts a private 4 GiB, 262,144-inode tmpfs with `sudo -n`; rootless Podman bind-mounts only that quota-limited filesystem at `/scratch`. The smoke requests an unprivileged runner with network disabled, a read-only root, dropped capabilities, and bounded CPU, memory, process count, and duration. Its pre-start check accepts Podman's empty effective and bounding capability sets when exposed, or verifies the reported drop of every default capability with no added capabilities when those fields are absent. It also checks Podman's private namespace, unprivileged, and resource-limit request fields; these remain configuration observations, not an enforcement attestation. Only the live process's inherited, permitted, effective, bounding, and ambient zero masks establish the capability observation; `HostConfig.CapDrop` alone is not an attestation. It reads the live `/scratch` filesystem and `statvfs` block/inode limits, verifies the bind source in Podman inspect, and unmounts host scratch after removing the container. A unique container name scopes cleanup to this invocation even when `podman create` fails after creating the container but before returning its ID; scratch stays mounted if removal fails. The later cold-root ownership change is noninteractive and timed out. The script writes and prints a machine-readable JSON result marked `claimEligible: false` and `published: false`. The record is kept in `RUNNER_TEMP` and the job log; this lane does not upload or publish it as gate evidence.

Rootless Podman 4.9 rejects the Linux `noswap` tmpfs option because it requires a rootful mount, and its `--tmpfs` parser also rejects `nr_inodes`. The launcher therefore makes no no-swap claim. The branch launcher now creates a fresh private mountpoint beneath the trusted runner scratch directory, mounts a fixed byte- and inode-limited tmpfs there with noninteractive host privilege, verifies the live mount, and bind-mounts it into the rootless container. The separate cleanup supervisor removes only the ownership-checked container before unmounting. The current implementation still needs a live native launcher and forced-kill pilot; it does not attest an execution envelope or enable a complete claim. The subject must never choose the host mount source or its options. A runner requiring a strict no-swap guarantee needs a different reviewed isolation design.

The optional hosted validation job has a 45-minute outer deadline. Its bounded Docker-to-Podman transfer and smoke can use about 11 minutes at their individual limits, and the subsequent cold restore has a 15-minute workload limit inside a 16-minute Docker-client limit. The remaining time covers host locked restore, feed verification, image build, and cleanup; a job timeout is a failed feasibility result, not a successful scratch or restore proof. The duration must be rechecked against observed native runs before these limits inform any required gate budget.

The smoke runs before the Docker cold restore so its evidence remains in the log if that restore fails. Podman operations are individually bounded (30 seconds, with Docker save and Podman load capped at 180 seconds each); the cold restore has a 15-minute workload timeout and a 16-minute Docker-client timeout. Those limits permit about 11 minutes for the Podman phase including termination grace, before host restore, feed/image build, and cold-root preparation. The workflow allows 45 minutes for the whole job. The [successful native pilot](../../docs/evidence-gate-rollout.md#local-pre-pilot-validation) completed this validation step in 6m11s, including feed verification, image build, Podman smoke, cold restore, and cleanup. This is one observed branch-owned run, not a required-gate latency budget.

Run the cold-cache restore proof on native `linux/amd64`. The local arm64 Docker host could build and start the x64 candidate image, but x64 emulation aborted the .NET SDK during MSBuild project loading before NuGet resolved packages. That attempt proves neither feed completeness nor a lock mismatch; the [rollout record](../../docs/evidence-gate-rollout.md) contains the observed failure. Project SDK resolution occurs during MSBuild evaluation, before the restore command's `--configfile` is applied. The native pilot now places the same closed feed configuration in the disposable subject user's NuGet home, where the [.NET CLI reads user configuration](https://learn.microsoft.com/en-us/nuget/consume-packages/configuring-nuget-behavior#config-file-locations-and-uses), and still supplies `--configfile` for ordinary locked restore. Both paths must remain offline and source-controlled by the trusted host. The Docker subject owns its private cache as UID 65532, so the host's final nonempty-cache inspection uses bounded, noninteractive `sudo` rather than treating a permission-denied directory as empty.

The fixed entrypoint scans the entire feed for links and special files, then restores the subject solution with `--locked-mode` and an offline NuGet config that clears all other sources. It rejects `NuGet.Config` at any level of the subject tree, and gives the project SDK resolver the same closed feed through the private subject user's config before MSBuild evaluates the projects. Do not move restore or build hooks to the trusted controller to make a dependency-changing PR pass. The [policy matrix](../../docs/evidence-gate-policy-matrix.md) keeps code coverage blocked because container-backed tests, subject checkout/isolation attestation, and complete artifact verification are not yet registered. The [rollout record](../../docs/evidence-gate-rollout.md) requires a cold-cache and dependency-change pilot before any check becomes required.

For a Docker-only local recipe smoke check, prepare a disposable context with those two entries, then run `docker build --file scripts/evidence-gate-subject-image/Containerfile --tag appsurface-subject-candidate:local <context>`. That check proves only that the image recipe can start; it does not prove the real feed, rootless Podman envelope, final image digest, or coverage verdict. The opt-in native lane exercises the Podman envelope, but remains branch-owned and non-claiming. Publish and configure a candidate only after the base-owned feed contents, final digest, and isolation pilot have been reviewed.
