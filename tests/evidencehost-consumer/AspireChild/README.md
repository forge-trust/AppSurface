# Provisional restricted Aspire child mechanism

This fixture prepares the next application-child facet of [issue #779's approved boundary](../../../docs/designs/issue-779-evidencehost-trust-boundary.md). It returns no Evidence admission, Trusted result, or supported-platform claim. Integration into the shared host, broker, producer leases, and final collection remains separate work.

## Closed application boundary

`Program.cs` owns the deferred factory, `Build`, `StartAsync`, bounded `StopAsync`, and disposal. Before writing the armed marker or launching the child, the controller requires a watchdog ACK over a private inherited pipe within three seconds, matching the selected watchdog PID and confirming that process is live. The application child receives no ACK pipe descriptors and additionally waits for the controller marker before invoking its factory. There is exactly one Aspire `ExecutableResource`, named `native-http`. It runs the bundled [native HTTP fixture](../NativeHttpResource/README.md) with literal arguments and an HTTP health check over `scratch/http.sock`. Dashboard and container resources are disabled/absent. The child references Aspire 13.4.4 and platform libraries; no Evidence/ForgeTrust runtime assembly is allowed in its bundle.

The [root controller](../aspire-child-proof.py) selects a fresh systemd unit, distinct non-root application UID/GID, immutable root-owned bundle, writable scratch, protected tools/output denial, private network, finite TasksMax 128 / MemoryMax 1G / output, and 45-second runtime. AppHost, DCP and the executable inherit one restricted unit/cgroup; the stuck-descendant control stays in that same group. This mechanism does not yet establish different AppHost/resource identities or independent resource capability grants. It has no authority to read verifier, registration or output roots. The platform `dotnet` runtime must live outside denied protected-tool roots.

The unit explicitly uses `Type=exec`. Pinned [systemd 255 service documentation](https://github.com/systemd/systemd/blob/v255/man/systemd.service.xml#L147-L172) distinguishes completed `execve()` from the earlier fork/setup phase; [systemd-run defaults to `Type=simple`](https://github.com/systemd/systemd/blob/v255/man/systemd-run.xml#L77-L86). The controller queries only its generated service, including `LoadState`, `Type`, `ActiveState`, `SubState`, MainPID, ControlGroup and the numeric query exit status. Within the existing readiness deadline, a successful query reporting `not-found`, an empty `Type`, `inactive`, `dead`, MainPID zero and an empty ControlGroup can be pending only before a loaded exec unit has been observed. Pinned [systemd 255 property-query source](https://github.com/systemd/systemd/blob/v255/src/systemctl/systemctl-show.c#L1964-L2001) returns success for this not-found property query; a nonzero query status is a query failure, never a retry permission. Pinned [service initialization](https://github.com/systemd/systemd/blob/v255/src/core/service.c#L117-L135) leaves Type unset, and [loading](https://github.com/systemd/systemd/blob/v255/src/core/service.c#L859-L875) returns before type assignment for an absent unit; the empty Type is permitted only in this exact pre-load tuple. A freshly loaded exec unit reporting `inactive`, `dead` and MainPID zero also remains **unconfirmed/pending**, within that same finite startup deadline. Pinned [job installation](https://github.com/systemd/systemd/blob/v255/src/core/job.c#L220-L273) installs a waiting job before the later [start operation](https://github.com/systemd/systemd/blob/v255/src/core/job.c#L830-L856) invokes `unit_start()`. The [Job property](https://github.com/systemd/systemd/blob/v255/src/core/dbus-unit.c#L230-L253) exposes the installed identifier; its presence does not prove that operation ran. Repeated initial inactive observations do not renew the deadline, establish a PID/identity or trigger HTTP. This initial grace ends once activating or active state has been observed; a return to inactive/dead is then terminal. A loaded exec unit in a recognized activating startup state remains pending. Acceptance requires exactly `loaded`, `exec`, `active`, `running`, a positive MainPID and the observed exact `/system.slice/<generated unit>` group. Other terminal/unknown states, malformed or duplicate properties, foreign groups, query errors or expiry fail closed with `application-exec-startup-failed`. A unit that disappears after loaded exec was observed cannot return to the initial not-found grace. Only after this execution boundary does it apply the unchanged exact four-UID and cgroup guard to every observed process. Root UID remains rejected even in a running exec unit. This confirms systemd process setup, not application factory or HTTP readiness; those independent controls remain required.

Root readiness uses its own bounded HTTP request, `SO_PEERCRED`, and `/proc/PID/cgroup`; it ignores any child readiness text. Each connect/write/read uses the remaining monotonic readiness deadline, and the controller rechecks that deadline before accepting a healthy or HTTP 503 response. A response completed after expiry cannot establish readiness. The fixture serves successful health only after `File.OpenRead` and `Assembly.LoadFile` of the real `protected-tool.dll` are denied, creation of `native-resource-output-probe` in the fresh protected output root is denied, **and** reading the immutable bundled `proof-input/declared.txt` returns `declared-native-input` plus newline. Both tool operations are attempted independently. The root controller verifies a managed PE tool exists beforehand, and verifies the output probe remains absent after joined teardown. Namespace settings alone are not denial proof. Root records actual AppHost/DCP/resource process roles and PIDs, without publishing raw command lines.

Cooperative stop sends `systemctl kill --kill-whom=main --signal=TERM` to the AppHost only. This lets AppHost own DCP/resource shutdown and does not start PID 1's service-stop timeout. After a fresh five-second grace, unconfirmed process/cgroup exit triggers `systemctl stop --no-block` followed by KILL of the entire cgroup. `KillMode=control-group`, the independent runtime bound and `TimeoutStopSec=10s` remain enforced. Normal/cancel controls additionally require the joined systemd-run process to exit 0; an empty cgroup with a killed, timed-out or unsuccessful process cannot pass as cooperative. When startup failed before a ControlGroup was observed, bounded teardown queries only that same generated service and may discover its actual ControlGroup; it never constructs an unobserved group as proof. Initially supplied and discovered groups must exactly equal `/system.slice/<generated unit>`. Foreign observations remain rejected even if later observations match. Discovery does not restart the cooperative grace or cleanup deadline. Unknown group ownership cannot establish physical exit, even if the launcher exited and pumps joined. The controller then joins output pumps and confirms the validated cgroup is empty before deleting scratch/payload. Stop-time group discovery grants no UID or application authority and cannot clear an earlier startup/identity rejection or lost-watchdog latch. Final output accounting occurs after pump joins, including teardown bursts. If exit confirmation fails, paths stay quarantined. The separate watchdog survives controller process-group cancellation.

Watchdog liveness is checked during readiness and teardown. After confirmed physical exit the root must still find the watchdog live, disarm it explicitly, receive its private disarm ACK and join it with exit 0. Missing/wrong startup ACK, premature exit (including exit 0), missing disarm ACK or nonzero final exit fails closed and retains quarantine. A deadline-expired watchdog cannot acknowledge a successful disarm. The separate watchdog remains armed when physical child/pump exit is unconfirmed.

Each stdout/stderr pump records observed bytes, actual EOF, failure and finished state under a lock. Read, write, flush or close failure cannot count as complete output even if the thread joined. Success requires both pumps to finish with EOF and no failure, and their byte totals must equal the shared budget count. Final JSON includes fixed pump states and error class names, never exception text. Incomplete capture retains quarantine; final quota accounting includes all successfully observed teardown bytes.

At the first startup query/gate failure, public JSON latches `failure: "application-exec-startup-failed"`, `failure_stage: "startup-unit-query"` and boolean `startup_diagnostic_written`. The root-only exclusive `control/startup-diagnostic.json` is mode 0600 and at most 4,096 bytes. Its twelve fields are closed `load_state`, service `type`, `active_state`, service `sub_state`, unsigned 32-bit `main_pid`, bounded numeric `query_exit_status`, elapsed monotonic seconds, closed service `result`, unsigned 32-bit `exec_main_pid`, signed 32-bit `exec_main_code` and `exec_main_status`, and unsigned 32-bit `job_id`. An empty service Type becomes the closed diagnostic value `unset`. Unknown or malformed enums become `unknown`; absent, malformed or out-of-range numeric properties become null. An explicitly observed numeric zero remains zero. Query statuses are restricted to -255 through 255. These substitutions describe failed diagnostics and never authorize startup. No raw stderr, exception message, command line, unit name, path or arbitrary property is included. Creation/write/size failure leaves the capture flag false and preserves the startup rejection. The orchestration exception handler also captures expiry between a successful query and process observation, using the last selected-unit query facts. If startup remains unconfirmed when the launcher exits before the first poll or between queries, the controller makes exactly one final selected-unit property query before initial diagnostic capture, bounded by the remaining startup deadline and a five-second query maximum. A successful complete read replaces stale facts; read failure, malformed/nonzero output or an expired deadline retains the previous facts. This query is diagnostic only: it cannot establish startup, change UID/cgroup ownership or turn the original StartupFailure into success. Capture precedes TERM and all cleanup. Later watchdog, stop, pump or quota failures retain their own outcome fields and cannot replace that first startup category. The parent native wrapper must add **`startup-diagnostic.json`** to the same root-owned, single-link, mode-0600, at-most-4,096-byte private retention whitelist and require its retained copy whenever `startup_diagnostic_written` is true.

The same selected-unit query retains the original six required startup properties and additionally requests `Result`, `ExecMainPID`, `ExecMainCode`, `ExecMainStatus` and `Job`; its remaining-startup timeout and 4,096-byte stdout bound are unchanged. Pinned [systemd 255 service properties](https://github.com/systemd/systemd/blob/v255/src/core/dbus-service.c#L356-L368) and the [ExecMain status macro](https://github.com/systemd/systemd/blob/v255/src/core/dbus-execute.h#L9-L14) define Result text, unsigned PID and signed code/status. Result is restricted to the [v255 service result table](https://github.com/systemd/systemd/blob/v255/src/core/service.c#L5050-L5064). The selected unit exposes [Job as a numeric-ID/object-path tuple](https://github.com/systemd/systemd/blob/v255/src/core/dbus-unit.c#L906), but [systemctl prints only its positive numeric ID or an empty value](https://github.com/systemd/systemd/blob/v255/src/systemctl/systemctl-show.c#L1111-L1124). Observed `Job=` records `job_id: 0`, meaning no queued job was observed; a missing, duplicate or malformed Job records null. No job object path is retained. Optional diagnostic omissions, duplicates, malformed numbers or non-ASCII values cannot change startup acceptance, establish UID/cgroup ownership, or clear the first failure. Portable queued-job and exited-process samples retain distinct private facts but both remain unconfirmed in the same initial loaded/inactive/PID-zero state. Optional Result/ExecMain/Job fields never grant acceptance and are never required for the pending decision. Launcher exit still makes one final diagnostic query and fails; expiry also fails. Orchestration controls cover queued inactive → activating → active, no UID or HTTP observation before completed exec, repeated inactive expiry, inactive regression after activation, launcher exit, malformed properties and foreign groups. These controls use fake launcher/query outcomes and grant no native or Evidence authority.

## Portable Python compiler compatibility

The historical native-v10 run of immutable `d1df8a8ec0e6670709faf54c7ab51965d3e062e3` stopped while importing this fixture on Python 3.12: a long multiple-item `with` exceeded the compiler frame-block limit. The current [portable tests](../test_aspire_child_proof.py) already use `ExitStack` for both long orchestration mock setups; the queued-startup source commit `b672cd0b5c0edb8a091d0b270486965c951cbbfc` contains that correction. Every context is still entered in the original order and unwound in reverse order. Do not turn these setups back into a multiple-item `with`: each item consumes a separate static frame block. Pinned [CPython 3.12 frame-block checks](https://github.com/python/cpython/blob/v3.12.12/Python/compile.c#L1458-L1474), [with-item compilation](https://github.com/python/cpython/blob/v3.12.12/Python/compile.c#L5986-L6038) and [the declared limit](https://github.com/python/cpython/blob/v3.12.3/Include/cpython/code.h#L210) explain the constraint.

No local Python 3.12 executable was available for the follow-up. All test/controller compiler units were checked with a conservative block-count bound that includes each with item, loops, comprehensions and exception/unwind slots, plus Python 3.12 feature-version grammar parsing. The maximum bound was 18 in the tests and 14 in the controller; the historical failing fixture was 25. This is static compatibility evidence, not an actual Python 3.12 compilation or Linux native pass. The full 88-control suite runs on the available local Python with the existing DLL; native-v10 and Aspire-v6 failures remain historical failures.

The sixth native candidate remains an honest **0/5** failure, bound to immutable source `d1df8a8ec0e6670709faf54c7ab51965d3e062e3`. Parent-retained facts for all five initial queries were loaded/exec/inactive/dead, MainPID zero, ExecMain PID/code/status zero, Result success and a positive Job ID at approximately 0.25 seconds. The previous controller rejected this initial state immediately. This correction permits finite observation of the fresh initial state; it proves neither that the native child will start nor that any native control now passes. That candidate retained TasksMax 64 / MemoryMax 1G; the queued-state correction preserved watchdog, stop, pump and quota behavior.

The fifth native candidate also failed all five controls. Its retained query reported loaded/exec/inactive/dead with MainPID zero and query exit 0, with no accepted process topology or child output. The five newly requested properties were not captured in that candidate, so queued startup versus genuine process termination remains unknown. That candidate retained TasksMax 64 and MemoryMax 1G.

The fourth native candidate failed all five controls with `StartupFailure` followed by `watchdog-unavailable`; child stdout/stderr were empty and neither topology nor budget counters were retained. That evidence does not identify which query/state branch failed. The not-found/start-pending distinction and these new facts require a fresh native run; no task or memory budget hypothesis is assumed.

At a startup process identity rejection, public JSON latches only the fixed failure `application-identity-rejected`, stage `startup-identity-validation`, and a private-capture success boolean. That rejection remains terminal even if diagnostic capture or later teardown fails. The guard still requires every observed UID and the selected cgroup to match. Its numeric UID tuple is retained from the rejecting check; cgroup membership is retained from that check when evaluated, or read immediately afterward for diagnostics when a UID mismatch already rejected the process.

The root controller writes a separate `control/identity-rejection.json` with mode 0600, capped at 4,096 bytes, without overwriting an existing file. Its seven fields are candidate PID, target UID, the four numeric kernel UIDs, cgroup match boolean, unit MainPID, unit ActiveState and elapsed monotonic seconds since the root lease began. ActiveState is restricted to `active`, `reloading`, `inactive`, `failed`, `activating`, `deactivating`, `maintenance`, `refreshing` or `unknown`; unrecognized states become `unknown`. Invalid numeric facts, size overflow or write failure leave the capture boolean false and preserve the original rejection. No command line, path, exception text or unknown property is included. Native artifact collection must explicitly retain this fixed private filename alongside the bounded root logs; it is excluded from public receipts. Portable controls cover the private mode/size, closed fields, canary exclusion, guard-fact fidelity and capture failure without changing acceptance.

Immediately before requesting stop, including after a control failure, root attempts a separate `control/budget-diagnostic.json` capture. Only the exact selected `/system.slice/issue779-child-<32 lowercase hex digits>.service` group is eligible. Its directory and fixed files are opened without following symlinks; each input and the final JSON are bounded to 4,096 bytes. The exclusive output is root-owned mode 0600 under the existing root-only control directory. The seven closed fields are `pids_current`, `pids_max`, `pids_events_max`, `memory_current`, `memory_max`, `memory_events` and elapsed monotonic seconds. Maxima use JSON null for the kernel's unlimited `max`; counters are unsigned 64-bit integers. The memory-event object contains only `low`, `high`, `max`, `oom`, `oom_kill`, `oom_group_kill` and `sock_throttled`, with null for the latter two when absent. The [kernel cgroup v2 reference](https://docs.kernel.org/admin-guide/cgroup-v2.html) defines these task and memory counters; samples are sequential observations, not an atomic snapshot.

Public receipts expose only `budget_diagnostic_category: "cgroup-task-memory-counters"` and boolean `budget_diagnostic_written` for this capture. Missing/unreadable groups, unknown or malformed counters, byte overflow and creation/write failure leave the boolean false, without changing the original failure, physical cleanup, watchdog, pump or quota outcome. No raw error, command line or cgroup path is published. The native wrapper must add this fixed filename to its root-owned/single-link/0600/4,096-byte retention whitelist and require a retained copy when the flag is true. The corresponding wrapper source-binding fix label is `exec-startup-and-budget-diagnostics`.

The third native candidate observed AppHost/DCP/resource processes but its four HTTP controls failed with `System.OutOfMemoryException` at thread allocation during ASP.NET startup. The factory control rejected a root-UID candidate during early unit observation. These failures establish no passing mechanism control. That candidate retained `TasksMax=64`, `MemoryMax=1G` and the cleared environment. ## Fixed task-budget selection

Parent-verified Aspire-v7, bound to immutable source `b672cd0b5c0edb8a091d0b270486965c951cbbfc` and harness `a572adb6a6564acebbd3852d184e50a061fe94b1`, passed only the factory-stall control: **1/5**. Their private budget samples reported `pids.max=64` and `pids.events:max` values `[1, 1, 1, 2]`. Memory samples were approximately 134–145 MB under a 1 GiB maximum, with memory max/oom/oom_kill events all zero. These observations establish task-cap hits and no observed cgroup memory-limit/OOM event. The [kernel PID-controller reference](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid) defines the task counter, limit-event semantics and rejection of further fork/clone operations.

The prototype now selects one literal finite `TasksMax=128` for the AppHost/DCP/resource cgroup. MemoryMax remains 1G. The actual argv regression requires exactly that one TasksMax property; no unlimited setting, processor-count override, restart or adaptive cap expansion is introduced. NoNewPrivileges, empty capability sets, protected path/input guards, exact kernel identity checks, deadlines, watchdog, main-only cooperative stop, joined pumps/quota and quarantine behavior remain unchanged. This preparation does not establish that 128 will pass native controls.

Any future [compiled application catalogue entry](../../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/README.md#internal-closed-application-catalogue-prerequisite) using this selection must explicitly declare a 128-task capability. A launcher must enforce the authenticated selected capability; it must never silently widen a descriptor selecting 64 or another limit. This literal prototype choice issues no catalogue registration, worker admission or Trusted claim. Historical `b672` source, its 88-control receipt and the failed 64-task native result remain immutable.

## Pinned SDK payload and portable build

The SDK is pinned in the project to `Aspire.AppHost.Sdk/13.4.4`; central package management pins `Aspire.Hosting.AppHost/13.4.4`. SDK selection uses **the build host's `NETCoreSdkRuntimeIdentifier`**, so locks are named `packages.osx-arm64.lock.json` and `packages.linux-x64.lock.json`. The Linux lock was generated by cross-restore metadata only, not native execution. Each native build must use its matching lock.

The root controller's `/usr/bin/env -i` command sets exactly `ASPIRE__STORE__PATH=<scratch>/.aspire-store`, within the existing writable scratch grant. This is the store **base directory** documented by the pinned [13.4.4 `IAspireStore` source](https://github.com/microsoft/aspire/blob/ccc566c5ab3285c9beb8f38ede34734bb477c029/src/Aspire.Hosting/ApplicationModel/IAspireStore.cs#L9-L20); the [store registration](https://github.com/microsoft/aspire/blob/ccc566c5ab3285c9beb8f38ede34734bb477c029/src/Aspire.Hosting/DistributedApplicationBuilder.cs#L382-L393) appends `.aspire`, yielding `<scratch>/.aspire-store/.aspire`. The controller derives the value from its fresh root-selected scratch and accepts no ambient store path. The portable command control executes only the cleared environment prefix with a Python probe to verify both the selected value and removal of an ambient sentinel.

The first native mechanism candidate failed at AppHost startup with `UnauthorizedAccessException` creating the build checkout's `AspireChild/obj/.aspire`, before DCP/resource readiness. Its embedded `apphostprojectbaseintermediateoutputpath` matches that checkout. Pinned source inspection exposes a limitation of the documented override: [the constructor adds the metadata-derived store path in a later configuration provider](https://github.com/microsoft/aspire/blob/ccc566c5ab3285c9beb8f38ede34734bb477c029/src/Aspire.Hosting/DistributedApplicationBuilder.cs#L253-L273), after loading environment configuration. Immediately after `CreateBuilder`, the [child factory](Program.cs) therefore requires the environment value to equal the canonical `<scratch>/.aspire-store` exactly, rejecting a missing or different value, then sets the public `Configuration["Aspire:Store:Path"]` to that base before `Build` or startup. This prevents the embedded build path from taking precedence and grants no additional writable path. ProtectHome and the closed grants remain enforced; native store-path and DCP/resource success still require a fresh native control run.

The child uses the pinned SDK's recognized `--DcpPublisher:CliPath` argument for `<payload>/dcp/dcp` and `--DcpPublisher:WaitForResourceCleanup true`. The [13.4.4 options resolver](https://github.com/microsoft/aspire/blob/ccc566c5ab3285c9beb8f38ede34734bb477c029/src/Aspire.Hosting/Dcp/DcpOptions.cs#L145-L174) reads `DcpPublisher:CliPath` before assembly metadata and derives its extension directory as the executable's sibling `ext` directory, `<payload>/dcp/ext`. It does not read a separate `ExtensionsPath` override from that section, so the child supplies none. [Cleanup waiting](https://github.com/microsoft/aspire/blob/ccc566c5ab3285c9beb8f38ede34734bb477c029/src/Aspire.Hosting/Dcp/DcpOptions.cs#L227) uses the same `DcpPublisher` section. The second native candidate exposed the earlier unsupported `Dcp:` argument prefix: the SDK selected its embedded build-time NuGet path under `/home`, and DCP dependency checking failed before DCP/resource execution. The corrected arguments still require a fresh native control run.

Aspire 13.4.4 marks AppHost projects non-publishable. `CopyProofPayload` therefore copies the SDK's real platform DCP tree and the resource's build output into the AppHost output. It fails if DCP is absent. There is no direct-process or fake readiness fallback. Building on macOS prepares a macOS DCP bundle; **do not run that bundle on Linux**. Four additional portable controls execute the existing resource DLL with ordinary fixture file permissions: denied tool/output with exact input returns 200; accessible tool, accessible output and mismatched input each return 503. ## Native proof controls (parent CI only)

Prerequisites: root Linux/systemd, unified cgroup v2, .NET 10 platform runtime, an existing dedicated non-root application user/group, and two existing protected directories. The tools directory must contain a real managed binary named exactly `protected-tool.dll`; the fresh output directory must have no `native-resource-output-probe`. A safe synthetic tool is the built resource DLL itself. Root creates the declared input inside the staged read-only payload. Native execution has not been performed during fixture preparation. The controller refuses unsupported hosts rather than substituting a simulated run.

Prepare **new fixture directories** in native CI, outside the real verifier/output roots:

```sh
sudo install -d -m 0755 /opt/issue779-child-tools /var/lib/issue779-child-output
sudo install -m 0444 tests/evidencehost-consumer/NativeHttpResource/bin/Debug/net10.0/NativeHttpResource.dll /opt/issue779-child-tools/protected-tool.dll
```

```sh
sudo timeout 75s python3 tests/evidencehost-consumer/aspire-child-proof.py \
  --bundle "$PWD/tests/evidencehost-consumer/AspireChild/bin/Debug/net10.0" \
  --dotnet /opt/dotnet/dotnet --subject-uid 2401 --subject-gid 2401 \
  --protected-tools /opt/issue779-child-tools \
  --protected-output /var/lib/issue779-child-output --case normal
```

Run the same command separately for `readiness-failure`, `factory-stall`, `cancel`, and `stuck-descendant`. Normal/cancel/stuck require an actual healthy socket plus AppHost and DCP process observations. Normal/cancel must stop cooperatively without controller escalation. Readiness failure must retain live AppHost, DCP and resource processes with the selected UID/cgroup and obtain HTTP 503 from a separately authenticated UDS peer; a startup crash cannot satisfy this control. Factory stall must retain a live AppHost with an owner-checked marker written inside the factory after controller arming, have no observed DCP/resource, and require escalation. Stuck descendant must show the actual descendant PID/UID/cgroup plus its marker written after installing the signal-resistant handler; readiness waits for that evidence before stop. DCP may dispose it itself, otherwise the controller escalates after grace. Receipts record controller escalation explicitly. These controls check finite teardown; `cancel` currently represents a root cancellation request after verified readiness, not the future shared worker cancellation protocol.

Each invocation prints a bounded JSON receipt and retains root-only logs/receipt under `/run/issue779-child-*/control`. Public JSON contains fixed failure categories and error class names; raw child diagnostics stay in byte-bounded private logs. Exit 0 means this provisional control completed with confirmed cgroup/pump exit and cleanup. Unconfirmed exit or unexpected readiness/process evidence returns failure and retains quarantine. Receipts explicitly set `trust_claim: false`. The full approved resource map, capability validation, producer/application lease separation and shared admission/supervision integration still need implementation and native acceptance.
