# Private qualification source bindings

This directory belongs only to the explicitly approved private qualification
candidate. Source preparation is not execution or a passed qualification receipt.
The primary checkout, production registration tables and consumer allowlists are
unaffected. The [root application lane](../LinuxApplication-README.md) still selects
only a registration contained in its source-compiled immutable tuple; candidate
metadata, descriptors and uploaded JSON cannot enroll a registration or issue a lease.

## Fixed account contract

Only `_create_run_accounts` and `_create_application_accounts` in this private
[launcher](../../../scripts/evidencehost-linux-launcher.py) differ from the account
allocation in the original checkout. Their signatures and caller ownership remain
unchanged. Names are still generated by the actual launcher's fresh 12-hex run tag,
and numeric identities are literals in these private functions:

| Identity | Fixed number | Fresh account/group name |
| --- | ---: | --- |
| Worker UID | 65010 | `evw<run-tag>` |
| Worker primary GID | 65011 | `evw<run-tag>g` |
| Producer UID | 65012 | `evs<run-tag>` |
| Producer primary GID | 65013 | `evs<run-tag>g` |
| Application UID | 65014 | `eva<run-tag>` |
| Application primary GID | 65015 | `eva<run-tag>g` |
| Results GID | 65016 | `evr<run-tag>` |
| Resource-access GID | 65017 | `evh<run-tag>` |

The first creator checks the three selected UIDs, five selected GIDs, and its
fresh names before any account utility runs. The application creator checks its
new UID/two GIDs and fresh names again, after run accounts have been reserved.
Occupied assigned IDs/names abort with no allocation fallback or account reuse.
NSS lookups are descriptive checks; exclusive `/usr/sbin/groupadd --gid` and
`/usr/sbin/useradd --uid --gid --no-user-group` remain the actual reservation
operations, without non-unique/force options. A race or utility failure rejects.
`--system`, no home creation and `/usr/sbin/nologin` remain selected. Explicit high
IDs may produce a host utility warning about its system-ID range; this is neither
permission to substitute IDs nor evidence that an actual reservation succeeded.

All five groups are explicitly created and tracked. Each prechecked generated
group/user name is appended as a pending reservation to the existing ownership
ledger **before** its account utility runs. A utility can mutate NSS and then
return nonzero or time out; that identity must already be owned for cleanup.
Occupied IDs/names still reject before any pending reservation or utility call,
so previously occupied foreign identities never enter the ownership ledger.
Any missing or mismatched post-creation identity fails closed and leaves the
reservation owned for cleanup/quarantine. A failure before mutation can leave a
missing pending name: strict deletion then fails closed without clearing ownership
or upgrading the original execution failure. No absence-based cleanup success is
inferred, and no utility retry or identity fallback is introduced.
The existing retained completion keeps accounts reserved through collection,
then requires strict cleanup. Cleanup deletes tracked users in reverse order
before tracked groups, so primary groups remain owned until their users are gone.
An unsuccessful launch/transfer retains the existing quarantine behavior; these
helpers do not establish owned exit or authorize a new cleanup path. Kernel UID,
GID, peer PID and cgroup checks remain mandatory and unchanged.

Primary group names append `g` to their fresh generated user name. This avoids
the documented [shadow-utils `USERGROUPS_ENAB` behavior](https://github.com/shadow-maint/shadow/blob/master/man/userdel.8.xml#L286-L293),
where `userdel` may also remove a same-name group before strict explicit `groupdel`.
The portable utility model includes that behavior; the five distinctly named owned
groups remain for the existing explicit cleanup loop. No host configuration is
changed and deletion success is not inferred from group absence.

## Source-compiled registration template

[`root-registration.py.in`](root-registration.py.in) is a source fragment for the
parent's protected build generator, not an importable loader or runtime API. It
contains exactly one occurrence of each case-sensitive marker:

| Marker | Required protected build input |
| --- | --- |
| `{{canonicalEntryB64}}` | Standard Base64 of the exact C# canonical entry bytes |
| `{{entryDigest}}` | Lowercase 64-hex SHA256 of those decoded canonical bytes |
| `{{catalogueDigest}}` | Exact matching C# compiled catalogue digest |
| `{{policyByteSHA}}` | SHA256 of the exact root-selected policy-file bytes |

The generator must bound canonical bytes to the root module's existing
`MAX_METADATA` (1 MiB), require canonical Base64 round-trip, require all digests
to be lowercase 64-hex, verify the entry-byte SHA, and resolve the catalogue and
policy against the same protected C# definition. The policy byte digest is a
file-byte binding; do not substitute a separately canonicalized policy digest.
Do not reserialize canonical entry bytes in Python to generate their digest.

After validating and substituting all four literals with no unresolved markers,
the generator replaces exactly one empty `_COMPILED_REGISTRATIONS` declaration
in the single adjacent `scripts/evidencehost_linux_application.py` with this
fragment. It must reject an already nonempty/missing/duplicate target and any
unexpected source delta. This source-preparation lane does not perform that edit.
The generated fragment constructs one frozen `_CompiledRegistration`, inside a
one-element tuple. Base64 decoding consumes only a fixed source literal, with
strict validation; no environment, uploaded file, JSON loader, callback, switch
or runtime enrollment supplies authority. Existing candidate/selection and exact
bundle/identity checks remain responsible for rejecting invalid bindings.

The parent must freeze the generated root-module source, generated matching C#
compiled registration, catalogue/bundle inventory, protected policy bytes, workflow
source and published tool build hashes, plus subject/package identities before
launch. Those facts are not implemented or proven by this template. A reviewed
descriptor alone cannot substitute for an actual matching source-owned entry,
authenticated worker, real UID/GID/cgroup, joined work or owned exit. Trusted proof
and production consumer acceptance remain separate; these templates do not enable
Trusted execution or change its empty proof allowlist.

## Bundle and denied-root ordering

The unchanged `_ApplicationWorkspaceOwner` audits
`<tool-root>/application-bundles/<application-id>/<build-id>` and copies its declared
bytes/modes into a fresh root-owned `/run/issue779-app-<32-hex>/bundle` **before**
`prepare_tool_root(tool, worker_gid)` traverses the original tool tree. That later
operation changes the original tree to the worker GID and read/search modes:
for example a declared original `0444` file becomes `0440`, and a `0555` directory
becomes `0550`. The separately copied bundle is outside the tool root, retains its
declared modes and remains the actual pinned bundle for start/rechecks. It is not
affected by the permission traversal.

Freeze/audit the initial deployment bundle before that traversal; do not count a
second audit of the changed original tree as the same declared-mode receipt or
silently normalize the compiled inventory. Fresh disposable deployment inputs are
required for a later attempt. The unchanged workspace guards require an actual
root-owned, single-link managed `protected-tool.dll` probe, protected tool/output
parents without untrusted writes, and absence of the fixed output probe before
start, after authenticated readiness and final join. Keep the actual denied output
ancestor, account separation, capabilities, namespace, quotas and all deadlines.

## Portable controls and remaining integration

[`test_root_bindings.py`](test_root_bindings.py) prepares sixteen portable controls
for actual emitted utility argv, every occupied assigned ID, occupied names,
partial reservation failures, post-creation UID/GID/lookup mismatch, reverse cleanup,
strict cleanup failure, generated names, and exact template markers. They mock
only NSS and the host utility boundary. Four added controls cover run/application
group/user creation followed by `LauncherError` or `TimeoutExpired` (eight
subcases), verify pending ownership before utility I/O and reverse cleanup after
the mutation, and require zero application/process launches. Earlier failures
before mutation retain their pending name and test strict missing-name rejection.
No root account, process, registry or lease is created, and no positive
qualification is fabricated. The new controls are **unexecuted at source-ready**;
historical validation receipts remain separate. The coordinating parent owns
validation authorization.

The unchanged old launcher suite contains account assertions for dynamic
`--user-group` allocation; those expectations are incompatible with this private
fixed-ID variant. This lane does not edit that old suite. Do not report it as
passing based on the new controls or change primary defaults to satisfy it.

Remaining parent-owned contracts are the bounded generator and its exact delta
review; matching C#/Python compiled entries/digests; the protected build/bundle and
managed probe; actual account availability; and the real qualification controller
with retained completion, physical group/pump exit, artifact integrity and cleanup.
The controller must preserve failure/quarantine and all guard facts before any gate.
No generator, root/native launch, CI, build, Git change or acceptance receipt is
created by this source-preparation lane.
