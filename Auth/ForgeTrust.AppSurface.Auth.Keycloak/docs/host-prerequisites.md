# Host prerequisites

The supported host is Unix-like and must preserve executable modes, provide Docker 29-compatible OCI layout build contexts with the containerd snapshotter, and create absent snapshot/context destinations. The host supplies the complete explicit recipe, policy, capture bindings, and actual immutable image identity. The repository-held schema is not currently published; future publication depends on the separate pure publish decision and coordinated dependency authorization. The package uses managed .NET code and two runtime dependencies: `BouncyCastle.Cryptography` for signed Release verification and `ZstdSharp.Port` for compressed Debian payload handling. Python is used only by CI harnesses.

The host should run capture sequentially when disk is bounded. Keep original source archives and captured receipts; remove only package-owned staging, selected copies, and temporary contexts after their hashes and manifests have been recorded. Do not delete captured originals as cleanup.

Docker invocation must use `KeycloakBuildContext.CreateDockerBuildArguments` and `ProcessStartInfo.ArgumentList`. The fixed arguments include `--provenance=false` so the local Docker identity is the selected platform manifest. An attestation-bearing index is rejected as unsupported by the local resolver; resolve an explicit platform manifest before inspection. Do not interpolate the argument list into a shell, add a registry push, or enable network access to the offline build. The image tag is a local host choice; `ResolveLocalImageAsync` must resolve that tag through Docker 29 containerd metadata and full export hashing before inspection. Labels are advisory and cannot replace manifest/config/diff-ID evidence. Resource limits bound work and metadata; they do not promise a fixed process RSS ceiling.

Keep exclusive ownership of the context from `Verify` through completion of the host builder. The context is a mutable host-owned directory; verification is a point-in-time integrity check. Inspection verifies the final immutable image against the documented application and runtime profile checks, and does not attest a hostile host or every unrelated host-composed filesystem path.


## Invocation capacity and host storage

Prepare .NET 10 and a Docker 29-compatible containerd store before acquiring large inputs. The [fixture acquisition guide](../../../examples/auth-keycloak-security-recipes/fixtures/README.md#acquire-the-exact-materials) records the exact source/runtime/frontend associations; the [qualification card](../../../docs/designs/issue-887-feasibility-card.md#proposed-bounded-support-envelope) records measured disk/time observations. Native amd64 system CI required 20 GiB free and observed about 27.7 GiB; those runner measurements are separate from SDK limits. Provision builder storage and target-platform execution explicitly, including any emulation cost. An HTTPS proxy must preserve TLS verification and approved origin/redirect policy; missing material is a stopped run, not permission to change authority.

The internal `TemporaryDiskBudget` applies an 8 GiB cumulative owned-write ceiling to each public invocation. Nested work shares that invocation's AsyncLocal budget. Charges occur before writes and include deleted scratch, so the ceiling is stricter than peak live temporary disk. Context output, including repaired archive bytes, additionally remains within its declared output ceiling (at most 1 GiB), capped before writes. A Docker engine export reserves a conservative 1 GiB charge and the verified archive format has its own 1 GiB bound. Docker builder storage belongs to the host and is outside this SDK disk accounting.

This accounting is neither a host-wide quota nor a reservation, and does not promise a 512 MiB process RSS ceiling. Other invocations and Docker can consume capacity concurrently. Free-space checks are best effort; retain room for the builder, old images and database backup, run sequentially when capacity is limited, and preserve prior outputs on exhaustion. Cleanup removes only owned scratch. See [retention and rebuild availability](material-retention.md) before deleting captured originals, and use the [cold-run record](cold-run.md) to distinguish preparation, cold and warm timing.


Atomic file publication requires a local filesystem supporting same-filesystem hard links. The SDK stages complete bytes beside the destination, then creates the final link with create-if-absent semantics. It rejects unsupported filesystems and existing destination nodes without falling back to a copy or replacing a concurrent winner. The caller retains exclusive ownership of each invocation's staging names. Directory publication continues to publish a complete populated directory through the existing absent-destination contract.
