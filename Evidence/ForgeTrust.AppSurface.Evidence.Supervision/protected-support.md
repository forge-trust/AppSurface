# Protected support-record foundation

The closed record uses schema v3; v2 records and v2's stored `CurrentWorkflowCommit` field are rejected. The worker protocol remains `evidence-worker-linux-v2`. These internal APIs define detached support-record data only. Their local build and controls described below do not enable runtime admission. The registry remains empty. Parsing, hashing and equality matching do not authenticate GitHub, qualify support, create an admission, select Trusted mode, or prove a native control. No field in this model is an authorization boolean.

## Distinct workflow identities

The record carries two different workflow identities:

- `Qualification.WorkflowPath` is fixed to `.github/workflows/evidencehost-protected-qualification.yml`. Its `WorkflowSha256` is the digest of that workflow's actual bytes; `WorkflowCommit` and `SubjectRevision` separately identify the immutable run/source revisions. The row also requires the fixed protected `workflow_dispatch` on `refs/heads/main` and data values `CompletedRunState="completed"` and `Conclusion="success"`.
- `CurrentWorkflowPath` is fixed to `.github/workflows/evidencehost-protected-parent.yml`; `CurrentWorkflowSha256` is the digest of those exact workflow-file bytes. The record deliberately stores no current workflow commit. The current run's commit remains in `EvidenceProtectedSupportFacts` and must be resolved by the real provider resolver, which independently binds the provider run to the checked-out protected commit and tree. The data matcher validates that commit as a canonical 40-character hash but does not compare it with a row field. This avoids requiring a checked-in row to contain the hash of the commit whose tree contains that same row. The qualification run's historical `WorkflowCommit` remains stored and is independently verified as part of qualification.

The state/conclusion strings and workflow fields are claims represented by a schema. Parsing them does not prove that the provider reported them. Before support can be recorded, a separate post-run verifier must resolve the final qualification run and authenticate its canonical repository ID/name, workflow path/ref/event, workflow bytes/commit, run attempt, completed-success state, subject/source capture and required job/artifact evidence. The generic proof-receipt list is only bounded content references; the verifier must enforce the fixed required evidence inventory and compare every receipt hash with the exact retained bytes. Unknown, missing, failed, skipped, stale, or differently sourced controls cannot be filled by adding arbitrary receipt IDs.

## Independent byte anchor and root boundary

`EvidenceProtectedSupportRecord` has a private constructor, so only `Parse(raw, expectedContentSha256)` can produce the matcher’s input wrapper. `Parse` first compares SHA-256 of the exact raw record bytes to a well-formed expected digest supplied by its caller, then requires closed JSON shape, canonical reserialization equality, field/range validity and read-only copies of parsed collections. It does not read the file or establish that `expectedContentSha256` is trusted. The production caller must obtain the exact record bytes from the fixed path in the authenticated current protected commit tree, not from the record itself or an adjacent digest file.

Before Trusted is enabled, the root loader must be implemented and reviewed as a fixed-path read-only component in the protected source tree. For each current run, the provider resolver must authenticate the canonical repository, protected `main` ref, event, workflow path, run/attempt and head commit; it must verify checkout `HEAD` is exactly that authenticated head. The loader then resolves the registry path in that commit's Git tree, reads the fixed file through the existing protected-root reader, rejects non-regular/symlink/multiply-linked or unstable files, and requires the retained bytes to equal the blob bytes addressed by the authenticated tree. It computes SHA-256 over those exact bytes and passes both the same bytes and that digest to `Parse`. It must measure actual tool/runtime/application bytes from the protected root and pass those measured manifests as current facts. This makes the protected commit/tree and review process the independent registry anchor; there is no self-hash sidecar. The record's canonical content digest is an identifier, not a signature or self-authentication mechanism. The equality matcher remains a necessary data comparison only.

## Current protected context and integration boundary

`EvidenceProtectedSupportFacts` models repository name/ID, provider, protected `main` ref, ref-protection state, event, current workflow path/digest/commit, base, current run/attempt/subject, and root-measured deployment/application inventories. These are caller-supplied data. Only a separately reviewed root workflow/API resolver may construct them from authenticated current provider metadata; no candidate descriptor or request string may set or waive them. The matcher requires the canonical repository and protected ref but still does not authenticate these supplied facts.

The only safe sequence is: first review and merge the fixed root loader and provider resolver while Trusted remains closed; run the reviewed qualification workflow on protected `main`; after that run completes, independently verify the final run and all required original artifacts/callbacks/controls plus the unchanged gate; add a support row only through a separately reviewed protected-root source change, using the authenticated commit tree as the record-byte anchor; then implement and review the actual request-to-descriptor-to-plan-to-CLI/Aspire Trusted path and its genuine positive/negative evidence. The row stores the completed historical qualification commit and fixed current workflow path/content digest, while the provider resolver authenticates each current run's commit separately. The support row and matcher must not be wired directly to `AcceptedConsumerProof` or admission. The existing protected parent consumer is later still: its record registry is empty and it requires an independently reviewed record for an already completed producer run. Neither these data APIs nor a successful parser/matcher test closes the qualification, runtime, native, or downstream acceptance gaps.

## Detached controls

The tests use synthetic bytes and deliberately fabricated digests. The earlier v2 proposal's 52 focused parser/matcher cases passed; that is historical validation only. This v3 source preserves those 52 test intentions, adapts the former valid-commit mismatch to reject a malformed current-context commit, and adds three cases for a different valid current commit, v2 schema rejection, and the removed stored field. The first v3 compile caught a constant/property name collision; the distinct internal constant name corrected it without changing the path check. After formatting, all 55 focused v3 cases passed with zero skips or compiler diagnostics. The current full supervision run passed 3,098 ordinary cases and skipped 91 Linux/root-only cases on macOS. None of these local controls is qualification or registry enrollment.

The support protocol identifies the existing application worker descriptor `evidence-worker-linux-v2`, which the root writer and Contracts parser both implement; this proposal does not change that protocol. Record schema v3 is a separate JSON format. Worker protocol v1 and v3 reject. The earlier v2 record correction passed 42 focused cases; ten more boundary controls passed in the 52-case focused run, covering exact collection/length limits, file-directory collisions, malformed members and current-set mismatch rejection. No root/native workflow ran in those controls; the later 55-case v3 local validation above remains detached data verification.
