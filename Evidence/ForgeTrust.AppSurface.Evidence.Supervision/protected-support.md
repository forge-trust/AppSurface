# Protected support-record foundation

The closed record uses schema v2; the incompatible earlier proposal shape is not accepted. These internal APIs define detached support-record data only. Their local build and controls described below do not enable runtime admission. The registry remains empty. Parsing, hashing and equality matching do not authenticate GitHub, qualify support, create an admission, select Trusted mode, or prove a native control. No field in this model is an authorization boolean.

## Distinct workflow identities

The record carries two different workflow identities:

- `Qualification.WorkflowPath` is fixed to `.github/workflows/evidencehost-protected-qualification.yml`. Its `WorkflowSha256` is the digest of that workflow's actual bytes; `WorkflowCommit` and `SubjectRevision` separately identify the immutable run/source revisions. The row also requires the fixed protected `workflow_dispatch` on `refs/heads/main` and data values `CompletedRunState="completed"` and `Conclusion="success"`.
- `CurrentWorkflowPath`, `CurrentWorkflowSha256`, and `CurrentWorkflowCommit` describe the later protected producer execution that may consult support. They are not equated to the qualification workflow identity or run. The caller must independently enforce the exact current workflow allowlist and resolve its current run, attempt, event, ref, protected-ref state, commit and subject from authenticated provider context.

The state/conclusion strings and workflow fields are claims represented by a schema. Parsing them does not prove that the provider reported them. Before support can be recorded, a separate post-run verifier must resolve the final qualification run and authenticate its canonical repository ID/name, workflow path/ref/event, workflow bytes/commit, run attempt, completed-success state, subject/source capture and required job/artifact evidence. The generic proof-receipt list is only bounded content references; the verifier must enforce the fixed required evidence inventory and compare every receipt hash with the exact retained bytes. Unknown, missing, failed, skipped, stale, or differently sourced controls cannot be filled by adding arbitrary receipt IDs.

## Independent byte anchor and root boundary

`EvidenceProtectedSupportRecord` has a private constructor, so only `Parse(raw, expectedContentSha256)` can produce the matcher’s input wrapper. `Parse` first compares SHA-256 of the exact raw record bytes to a well-formed expected digest supplied by its caller, then requires closed JSON shape, canonical reserialization equality, field/range validity and read-only copies of parsed collections. It does not read the file or establish that `expectedContentSha256` is trusted. The production caller must obtain that expected digest independently from the reviewed immutable protected root checkout/source inventory, never from the record, request, descriptor, or a sidecar stored alongside it without an independent root anchor.

A future runtime integration must use the existing protected-root reader to read the fixed record path outside the measured tool/runtime trees and reject non-regular/symlink/multiply-linked or unstable files, hash the exact bytes it retained, compare against that independent anchor, and pass those same bytes plus the expected digest to `Parse`. It must also measure actual tool/runtime/application bytes from the protected root and pass those measured manifests as current facts. The record's canonical content digest is an identifier, not a signature or self-authentication mechanism. The equality matcher remains a necessary data comparison only.

## Current protected context and integration boundary

`EvidenceProtectedSupportFacts` models repository name/ID, provider, protected `main` ref, ref-protection state, event, current workflow path/digest/commit, base, current run/attempt/subject, and root-measured deployment/application inventories. These are caller-supplied data. Only a separately reviewed root workflow/API resolver may construct them from authenticated current provider metadata; no candidate descriptor or request string may set or waive them. The matcher requires the canonical repository and protected ref but still does not authenticate these supplied facts.

The only safe sequence is: run the reviewed qualification workflow on protected `main`; after that workflow is complete, independently verify the final run and all required original artifacts/callbacks/controls plus the unchanged gate; add a support row only through a separately reviewed protected-root source change that anchors its exact bytes; then implement and review the actual request-to-descriptor-to-plan-to-CLI/Aspire Trusted path and its genuine positive/negative evidence. The support row and matcher must not be wired directly to `AcceptedConsumerProof` or admission. The existing protected parent consumer is later still: its record registry is empty and it requires an independently reviewed record for an already completed producer run. Neither these data APIs nor a successful parser/matcher test closes the qualification, runtime, native, or downstream acceptance gaps.

## Detached controls

The tests use synthetic byte strings and deliberately fabricated digests to exercise schema parsing, raw-digest comparison, canonical representation, collection freezing, current-context mismatch rejection, and empty-registry behavior. One matcher test exercises the equality-positive branch using only synthetic data; this is not support qualification, provider authentication, or native acceptance. No test represents an actual successful qualification. The isolated source was formatted and compiled with warnings as errors. Its initial 39 parser/matcher cases passed, including the depth-limit control. The earlier full supervision run passed 3,051 ordinary cases and skipped 77 Linux/root-only cases. These are local controls, not qualification or registry enrollment.

The support protocol identifies the existing application worker descriptor `evidence-worker-linux-v2`, which the root writer and Contracts parser both implement. The record schema remains `evidence-protected-support-v2`; that is a separate JSON format. Worker protocol v1 and the unimplemented v3 reject. The v2 correction passed all 42 focused cases. Ten additional boundary controls then passed in a 52-case focused run, covering exact collection/length limits, file-directory collisions, malformed members and current-set mismatch rejection. No root/native workflow ran in these local controls.
