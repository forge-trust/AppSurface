# AppSurface EvidenceGate runner

`ForgeTrust.AppSurface.EvidenceGate` is the initial first-party machine host for the [policy-driven CI evidence gate](../../docs/plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). It accepts only canonical contract `2.0` plans and the reviewed JSON policy from the trusted base checkout, verifies the plan against that policy and the exact base/head objects in a trusted Git object store, and writes `evidence-plan.json`, `evidence-manifest.json`, and `evidence-summary.json` as bounded canonical JSON. The checked-in policy may be formatted for review; its parsed value is validated and compared with the plan, while untrusted handoff bytes remain canonical-only.

For stable command, host, pilot, and subject-launcher diagnostics, see the [evidence-gate diagnostic guide](../../docs/evidence-gate-diagnostics.md). It distinguishes successful empty-profile host behavior from the current deliberately non-claiming GitHub pilot.

Run it with:

```text
dotnet run --project tools/ForgeTrust.AppSurface.EvidenceGate -- run \
  --plan <canonical-v2-plan.json> \
  --policy <base-owned-policy.json> \
  --repository <trusted-git-object-store> \
  --output-dir <new-output-directory>
```

The input policy and object store must come from the trusted controller's base-owned context. The runner never uses the subject checkout as policy, workflow, or executable host code. It validates exact revisions and both Git change representations through the [revision plan builder](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/EvidenceRevisionPlanBuilder.cs), then composes the [EvidenceHost bootstrap](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceHostBootstrap.cs) using a closed first-party registration set.

## Controller capture

The controller applies one 120-second monotonic capture deadline to Git operations and both authoritative PR API reads. Its production API call uses a process alarm on the supported POSIX runner so a response that slowly trickles bytes cannot extend the capture indefinitely. If the alarm cannot be owned or enforced, capture fails without a handoff.

The [trusted PR capture script](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-controller.py) accepts `--event`, `--output`, `--target-branch`, and optionally `--object-store`. The base-owned `pull_request_target` job must supply `GITHUB_TOKEN`, `GITHUB_REPOSITORY`, `GITHUB_REPOSITORY_ID`, `GITHUB_RUN_ID`, and `GITHUB_RUN_ATTEMPT` from its own context. It validates the bounded event and a fresh PR API view, fetches both full commit IDs into a new retained bare object store, and writes `source.diff` plus `pull-request-run-identity.json` for a same-repository PR. A fork yields `observation.json` only. The caller owns successful-store cleanup after plan and verifier use; no capture output is a final verdict. Run `python3 scripts/evidence-gate-controller.py --help` for input syntax and keep the token outside the subject job.

## Private plan-bound handoff

The [handoff command](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-handoff.py) has `create`, `execute`, and `verify` modes for this one workflow. A same-repository `create` requires `--capture-directory`, `--trusted-scripts-directory`, `--output-directory`, and `--plan-file` pointing at the canonical v2 plan generated by the [base-owned planner](../../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-evidence). A fork observation omits `--plan-file`; supplying one to a fork is invalid. The handoff compares the plan's exact .NET canonical bytes, including escaped punctuation in changed paths, so an edited or differently serialized plan fails closed. Creation binds the plan's base/head, source-diff digest, run identity, and selected profile to the capture, then compares every archived regular file and mode against the captured head Git tree. `export-ignore`, `export-subst`, links, submodules, case collisions, and changed bytes fail closed. The output directory must be new beneath a physical parent.

The credentialless job calls `execute` with the downloaded `--handoff-directory`, new `--subject-checkout` and `--scratch-directory` paths, `--result`, and an optional digest-pinned `--image-digest`. It rechecks the bounded bundle and same-run identity before selecting work. Only an explicitly empty `documentation-only` profile completes without an image; `code-coverage` requires the reviewed offline image, while every other profile returns an unsupported-profile failure until its producer and resource envelope exist. The fixed result always says `claimEligible: false`; exit `0` means only that the selected subject execution completed, and exit `2` means observation, invalid input, unavailable capability, or failure. The [diagnostic guide](../../docs/evidence-gate-diagnostics.md#asehb-private-controller-to-subject-handoff) maps its `ASEHB` codes. Neither job result nor handoff metadata replaces the trusted final verifier.

The base-owned verifier calls `verify` with `--handoff-directory`, `--fresh-capture-directory`, `--subject-result`, and a new `--output-plan` file. It validates the downloaded bundle, compares identity and source-diff digest with an independent current-PR capture, then compares every archived blob and mode with that capture's Git tree. It requires the bounded non-claiming subject result to report success for the same run, head revision, profile, and snapshot. Only after these checks does it copy the canonical plan to the new trusted file consumed by the host and `verify-gate`. This step authenticates the transported source snapshot against fresh Git state and checks the subject result's consistency; it does not attest the subject job's actual checkout, isolation, or any producer artifact.

The trusted verifier job next runs the [cleanup-record verifier](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-verify-cleanup.py) with `--plan` set to that freshly verified plan and `--attestation` set to the attempt-scoped cleanup artifact path. `code-coverage` requires a no-follow, canonical, complete record at that path; `documentation-only` requires it to be absent. Missing, unsafe, oversized, incomplete, or unexpected records fail before host verification with the [ASEGC diagnostics](../../docs/evidence-gate-diagnostics.md#asegc-trusted-cleanup-record-handoff). The successful credentialless subject job and its upload step provide the workflow context; the record itself remains non-claiming and does not authenticate the subject checkout, execution envelope, or producer output.

## Host run behavior

The runner supports any empty targeted profile that is present in the trusted policy, selected for the exact diff by an explicit policy rule, and accepted by gate-policy validation. The checked-in policy currently names its documentation profile `documentation-only`; the runner does not special-case that name. The empty profile runs through `EvidenceHostBootstrap` and yields `NoEvidenceRequired`. No existing workflow job conclusion is imported as a producer result. Every other selected profile receives unavailable outcomes for all declared resources and producers, an incomplete manifest, and exit code `2`. A parseable plan with a bounded manifest identity that is noncanonical or fails trusted revision/policy validation receives an `Invalid` manifest and a nonzero exit. Malformed or oversized input without a trustworthy bounded plan identity receives a stable diagnostic and no invented manifest. Inputs are capped at 4 MiB; plan and manifest outputs at 4 MiB; summary output at 128 KiB. Existing output files are never replaced.

## Protected release inspection seam

The host explicitly registers `release-inspection` from the checked-in [`protected-release` policy profile](https://github.com/forge-trust/AppSurface/blob/main/.appsurface/evidence/evidence.policy.json). Its producer delegates tag, V2 trailer, and prepared-artifact validation to the Release package's existing [`inspect --machine-json` authority](../ForgeTrust.AppSurface.Release/README.md#prepared-to-tagged-state), then can write the bounded machine result and typed digest index through the declared Evidence artifact slots. The result binds the annotated tag object ID, peeled commit, normalized protected base ref, V2 comparison-base commit, and exact digests for the five committed release note/sidecar/manifest/current-pointer artifacts.

This registration is deliberately non-claiming. The production invocation provider currently has no trusted protected-event source and returns unavailable, so inspection does not run from the host command. The host also has no release-specific plan verifier, remote protected-tag freshness check, or producer for the exact NuGet packages and Docs archive; those output digests are not fields in the current Release inspect machine contract. Even a valid local inspect captured through the producer returns `Unavailable` with no satisfied assertion. The release profile is not passed through the pull-request revision verifier, and neither this seam nor the current runner can issue `ReleaseComplete`. These boundaries follow the [issue #777 implementation plan](../../docs/plans/issue-777-policy-driven-ci-evidence-gate-implementation.md#implementation-tasks).

## Subject launcher

The [credentialless subject launcher](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject.py) is a separate, non-claiming OCI execution primitive. Its CLI requires `--subject-checkout`, `--image-digest`, `--scratch-directory`, `--profile-id`, `--source-diff`, `--source-diff-sha256`, and explicit timeout, memory, CPU, PID, and output-byte limits. The source diff must be the controller-captured regular file outside the subject checkout and scratch directory, at most 20 MiB, with the SHA-256 supplied by the validated [private handoff](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-handoff.py); a mismatch fails before starting the container. It accepts only an offline `code-coverage` profile, a locally present digest-pinned image with the fixed `/usr/local/libexec/appsurface-subject-runner` entrypoint, and a Linux GitHub-hosted runner with rootless Podman and cgroup v2. Before starting, it mounts and verifies a private host tmpfs limited to 4 GiB and 262,144 inodes, bind-mounts it at `/scratch`, and checks the created container's read-only subject and `/source.diff` mounts, non-root UID, read-only root filesystem, capability-drop request, no-new-privileges, and no-network configuration. The capability request is a pre-start check, not live capability attestation. It exports only the entrypoint's bounded, canonical nonclaiming result record outside the mount; other container scratch artifacts are discarded. Normal cleanup removes the container before unmounting the tmpfs, but process-local cleanup cannot survive SIGKILL, so an independent supervisor is still required before an eligible claim. Resource-backed profiles, a missing pinned image, or an unenforceable isolation setting fail closed. The launcher's standalone CLI exits nonzero even when the subject process exits zero. The private handoff uses the base-owned plan's selected profile: an explicit empty documentation profile completes without OCI, and only `code-coverage` can reach this launcher. A successful handoff execution may return zero while remaining non-claiming. The trusted controller owns paths and limits; never use subject-provided values as authority. A [candidate image recipe and feed builder](../../scripts/evidence-gate-subject-image/README.md) exist, but no published immutable image digest or complete isolated producer is approved yet.

The [fixed offline entrypoint](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-subject-entrypoint.py) is designed for installation at that image path. It accepts only `--profile-id=code-coverage`, the fixed `/subject`, `/scratch`, `/source.diff`, and `/opt/appsurface/locked-dependencies` paths, the controller diff's `--diff-sha256`, and `--offline`. It requires a read-only source and diff mount, a private writable scratch tmpfs, a read-only package feed in the image, .NET 10, and regular lock files for each solution project. It honors the existing `packages.linux-x64.lock.json` files selected by `NuGetLockFilePath`; the five RID-specific projects were checked with locked-mode restore as recorded in the [rollout record](../../docs/evidence-gate-rollout.md). It copies a clean source snapshot without following links, checks the mounted diff's SHA-256, and uses that exact diff for the 95% patch-line and 85% patch-branch thresholds in `codecov` patch-line mode alongside the 95% aggregate-line and 85% aggregate-branch thresholds. It writes a canonical bounded `evidence-subject-result.json` with fixed step names, output hashes, and `claimEligible: false`, and streams the same record over attached output before the tmpfs disappears. It fails with `ASESE010` before coverage execution when the current solution includes container-dependent test projects without a declared service envelope. The branch-owned native Linux probe now passes a cold in-image restore, but the candidate feed and image have not been published from a protected base as an approved digest. This entrypoint is not a registered EvidenceHost producer and cannot satisfy the [policy's coverage obligation](../../docs/evidence-gate-policy-matrix.md). See the [diagnostic guide](../../docs/evidence-gate-diagnostics.md) for failure codes.

## Verify-gate and current pilot

The terminal and Markdown claim labels come from whether the verified profile selects any resource, producer, or obligation. A profile with a producer and no obligation is still `TargetedComplete`; only a fully empty profile is `NoEvidenceRequired`.

Exit code `0` from `run` means only that the host completed its supported empty profile. It is not the final CI check verdict, does not prove that the subject job ran on the required isolated runner, and does not authenticate the current PR or job provenance. `verify-gate` is a separate trusted-controller command. It bounded-reads and canonical-parses the handed-off plan, manifest, and expected identity; it parses the reviewed policy from the base checkout, calls [`EvidencePullRequestGateVerifier.VerifyAsync`](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/EvidencePullRequestGateVerifier.cs), and writes `evidence-gate-verification.json`, `evidence-gate-summary.json`, and `evidence-gate-summary.md` (the summaries are each capped at 128 KiB). [`EvidenceGateResultRenderer`](EvidenceGateResultRenderer.cs) renders the same bounded result for terminal output and the Markdown summary. `verify-gate` writes terminal status before file output and publishes the authoritative `evidence-gate-verification.json` last. If terminal or summary writing fails, its failure path may leave presentation files, but it does not leave an eligible machine verdict from that invocation. Existing output files are never replaced. The checked-in live workflow invokes this command only as a rehearsal; its final step remains an intentionally failing non-claiming scaffold. The [verifier-context resolver](https://github.com/forge-trust/AppSurface/blob/main/scripts/evidence-gate-verifier-context.py) takes a fresh controller identity, trusted workflow environment, and the attempt-specific GitHub run and job responses to write the expected identity; it never accepts a job ID from the downloaded subject artifact. Nonempty evidence additionally requires the trusted no-follow artifact verifier and an extracted artifact handoff root. The GitHub API reader can report a fresh PR/run/job observation without claiming that it knows the subject checkout; its `SubjectJobHeadRevision` remains empty until a separate `IEvidenceSubjectJobCheckoutAttestationProvider` binds repository, run, attempt, job, and actual checkout revision. The [attempt-specific workflow-jobs API](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) binds the job list to the run attempt even though its documented job object omits `run_attempt`; if that field is present, the reader checks it against the workflow-run attempt. An explicitly empty profile needs no subject checkout and can use the fresh observation, but a nonempty profile cannot become eligible without checkout and isolation attestation. GitHub workflow-run and job `head_sha` fields are never treated as checkout proof. No production checkout attestor is included. Never use `run` as the required check publisher.

The emitted manifest is host evidence, not a complete CI authorization. The checked-in GitHub workflow is a separate pilot scaffold: it captures a subject snapshot, can attempt a bounded subject run, and independently recaptures current PR state before a verifier rehearsal. It still emits `ASEGH003` because the bounded subject result is not a producer manifest or independent checkout/isolation attestation, and complete producer and artifact authority are not wired into the required verdict. The shadow workflow validates contracts only. Neither is a claim-producing required check. A fully empty targeted profile can produce an eligible rehearsal result from fresh PR/run/job authority without a checkout attestor; every nonempty profile additionally needs the subject checkout, isolation, artifact, and cleanup proofs. The complete code-to-cause-to-fix map is in the [diagnostic guide](../../docs/evidence-gate-diagnostics.md).

The required job handoffs remain:

For a nonempty profile, the final authority snapshot must carry an independently verified `SubjectEnvelopeAttested` signal in addition to the manifest's `ValidatedNotAttested` structural status. The current production GitHub provider never sets that signal, so it cannot authorize nonempty evidence even if a checkout attestor is later supplied without a separate isolation proof.

1. The base-owned controller fetches and resolves the complete base/head objects, reads the policy from the protected base revision, captures the fixed-options diff and NUL status set, and creates the canonical v2 plan. It passes only those bounded inputs and the exact subject snapshot to the isolated subject job.
2. The subject job runs the base-built runner and any future supported producer only on an ephemeral, credentialless VM with the subject mounted read-only inside the constrained execution boundary. The current runner executes no head-controlled code, and nonempty profiles fail closed until their producer, resource, dependency, artifact, and cleanup registrations are implemented.
3. The base-owned verifier invokes `verify-gate` with the base-owned policy and Git objects, trusted expected identity, and an authoritative `IEvidencePullRequestGateAuthorityProvider`. It treats the plan, manifest, and subject artifacts as untrusted, independently recreates the plan, verifies manifest and job provenance, checks cleanup and envelope evidence, and re-reads current PR base/head before rendering a gate result. Production GitHub authority leaves the checkout unknown without an attestor, so only an explicit empty profile could pass this boundary. This runner does not consume separate workflow statuses and `run` does not publish a required-check verdict.

See the [policy and producer matrix](../../docs/evidence-gate-policy-matrix.md) for the current implementation gaps and the [EvidenceHost cookbook](../../guides/evidencehost-cookbook.md) for producer and lifecycle concepts.
