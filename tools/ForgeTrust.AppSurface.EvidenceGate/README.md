# AppSurface EvidenceGate runner

`ForgeTrust.AppSurface.EvidenceGate` is the initial first-party machine host for the [policy-driven CI evidence gate](../../docs/plans/issue-777-policy-driven-ci-evidence-gate-implementation.md). It accepts only canonical contract `2.0` plans and a canonical trusted policy, verifies the plan against that policy and the exact base/head objects in a trusted Git object store, and writes `evidence-plan.json`, `evidence-manifest.json`, and `evidence-summary.json` as bounded canonical JSON.

For stable command, host, pilot, and subject-launcher diagnostics, see the [evidence-gate diagnostic guide](../../docs/evidence-gate-diagnostics.md). It distinguishes successful empty-profile host behavior from the current deliberately non-claiming GitHub pilot.

Run it with:

```text
dotnet run --project tools/ForgeTrust.AppSurface.EvidenceGate -- run \
  --plan <canonical-v2-plan.json> \
  --policy <base-owned-policy.json> \
  --repository <trusted-git-object-store> \
  --output-dir <new-output-directory>
```

The input policy and object store must come from the trusted controller's base-owned context. The runner never uses the subject checkout as policy, workflow, or executable host code. It validates exact revisions and both Git change representations through the [revision plan builder](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/EvidenceRevisionPlanBuilder.cs), then composes the [EvidenceHost bootstrap](../../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceHostBootstrap.cs) using a closed first-party registration set.

## Controller capture

The controller applies one 120-second monotonic capture deadline to Git operations and both authoritative PR API reads. Its production API call uses a process alarm on the supported POSIX runner so a response that slowly trickles bytes cannot extend the capture indefinitely. If the alarm cannot be owned or enforced, capture fails without a handoff.

The [trusted PR capture script](../../scripts/evidence-gate-controller.py) accepts `--event`, `--output`, `--target-branch`, and optionally `--object-store`. The base-owned `pull_request_target` job must supply `GITHUB_TOKEN`, `GITHUB_REPOSITORY`, `GITHUB_REPOSITORY_ID`, `GITHUB_RUN_ID`, and `GITHUB_RUN_ATTEMPT` from its own context. It validates the bounded event and a fresh PR API view, fetches both full commit IDs into a new retained bare object store, and writes `source.diff` plus `pull-request-run-identity.json` for a same-repository PR. A fork yields `observation.json` only. The caller owns successful-store cleanup after plan and verifier use; no capture output is a final verdict. Run `python3 scripts/evidence-gate-controller.py --help` for input syntax and keep the token outside the subject job.

## Private plan-bound handoff

The [handoff command](../../scripts/evidence-gate-handoff.py) has `create` and `execute` modes for this one workflow. A same-repository `create` requires `--capture-directory`, `--trusted-scripts-directory`, `--output-directory`, and `--plan-file` pointing at the canonical v2 plan generated by the [base-owned planner](../../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-evidence). A fork observation omits `--plan-file`; supplying one to a fork is invalid. The handoff compares the plan's exact .NET canonical bytes, including escaped punctuation in changed paths, so an edited or differently serialized plan fails closed. Creation binds the plan's base/head, source-diff digest, run identity, and selected profile to the capture, then compares every archived regular file and mode against the captured head Git tree. `export-ignore`, `export-subst`, links, submodules, case collisions, and changed bytes fail closed. The output directory must be new beneath a physical parent.

The credentialless job calls `execute` with the downloaded `--handoff-directory`, new `--subject-checkout` and `--scratch-directory` paths, `--result`, and an optional digest-pinned `--image-digest`. It rechecks the bounded bundle and same-run identity before selecting work. Only an explicitly empty `documentation-only` profile completes without an image; `code-coverage` requires the reviewed offline image, while every other profile returns an unsupported-profile failure until its producer and resource envelope exist. The fixed result always says `claimEligible: false`; exit `0` means only that the selected subject execution completed, and exit `2` means observation, invalid input, unavailable capability, or failure. The [diagnostic guide](../../docs/evidence-gate-diagnostics.md#asehb-private-controller-to-subject-handoff) maps its `ASEHB` codes. Neither job result nor handoff metadata replaces the trusted final verifier.

## Host run behavior

The runner supports any empty targeted profile that is present in the trusted policy, selected for the exact diff by an explicit policy rule, and accepted by gate-policy validation. The checked-in policy currently names its documentation profile `documentation-only`; the runner does not special-case that name. The empty profile runs through `EvidenceHostBootstrap` and yields `NoEvidenceRequired`. No existing workflow job conclusion is imported as a producer result. Every other selected profile receives unavailable outcomes for all declared resources and producers, an incomplete manifest, and exit code `2`. A parseable plan with a bounded manifest identity that is noncanonical or fails trusted revision/policy validation receives an `Invalid` manifest and a nonzero exit. Malformed or oversized input without a trustworthy bounded plan identity receives a stable diagnostic and no invented manifest. Inputs are capped at 4 MiB; plan and manifest outputs at 4 MiB; summary output at 128 KiB. Existing output files are never replaced.

## Protected release inspection seam

The host explicitly registers `release-inspection` from the checked-in [`protected-release` policy profile](../../.appsurface/evidence/evidence.policy.json). Its producer delegates tag, V2 trailer, and prepared-artifact validation to the Release package's existing [`inspect --machine-json` authority](../ForgeTrust.AppSurface.Release/README.md#prepared-to-tagged-state), then can write the bounded machine result and typed digest index through the declared Evidence artifact slots. The result binds the annotated tag object ID, peeled commit, normalized protected base ref, V2 comparison-base commit, and exact digests for the five committed release note/sidecar/manifest/current-pointer artifacts.

This registration is deliberately non-claiming. The production invocation provider currently has no trusted protected-event source and returns unavailable, so inspection does not run from the host command. The host also has no release-specific plan verifier, remote protected-tag freshness check, or producer for the exact NuGet packages and Docs archive; those output digests are not fields in the current Release inspect machine contract. Even a valid local inspect captured through the producer returns `Unavailable` with no satisfied assertion. The release profile is not passed through the pull-request revision verifier, and neither this seam nor the current runner can issue `ReleaseComplete`. These boundaries follow the [issue #777 implementation plan](../../docs/plans/issue-777-policy-driven-ci-evidence-gate-implementation.md#implementation-tasks).

## Subject launcher

The [credentialless subject launcher](../../scripts/evidence-gate-subject.py) is a separate, non-claiming OCI execution primitive. Its CLI requires `--subject-checkout`, `--image-digest`, `--scratch-directory`, `--profile-id`, and explicit timeout, memory, CPU, PID, and output-byte limits. It accepts only an offline `code-coverage` profile, a locally present digest-pinned image with the fixed `/usr/local/libexec/appsurface-subject-runner` entrypoint, and a Linux GitHub-hosted runner with rootless Podman and cgroup v2. It validates a read-only subject mount, private writable scratch, non-root UID, read-only root filesystem, dropped capabilities, no-new-privileges, and no network before starting the container. Resource-backed profiles, a missing pinned image, or an unenforceable isolation setting fail closed. The launcher always reports `claimEligible: false` and its standalone CLI exits nonzero, even when the subject process exits zero. The [private handoff](../../scripts/evidence-gate-handoff.py) uses the base-owned plan's selected profile: an explicit empty documentation profile completes without OCI, and only `code-coverage` can reach this launcher. A successful handoff execution may return zero while remaining non-claiming. The trusted controller owns paths and limits; never use subject-provided values as authority. No reviewed pinned image or locked dependency supply is included yet.

The [fixed offline entrypoint](../../scripts/evidence-gate-subject-entrypoint.py) is designed for installation at that image path. It accepts only `--profile-id=code-coverage`, the fixed `/subject`, `/scratch`, and `/opt/appsurface/locked-dependencies` paths, and `--offline`. It requires a read-only source mount, a private writable scratch mount, a read-only package feed in the image, .NET 10, and regular lock files for each solution project. It honors the existing `packages.linux-x64.lock.json` files selected by `NuGetLockFilePath`; the five RID-specific projects were checked with locked-mode restore as recorded in the [rollout record](../../docs/evidence-gate-rollout.md). It copies a clean source snapshot without following links and writes a canonical bounded `evidence-subject-result.json` with fixed step names, output hashes, and `claimEligible: false`. It fails with `ASESE010` before coverage execution when the current solution includes container-dependent test projects without a declared service envelope. Its aggregate coverage command does not yet bind the controller's diff or enforce patch thresholds. There is no reviewed subject image or supplied offline NuGet feed, so this entrypoint is not a registered EvidenceHost producer and cannot satisfy the [policy's coverage obligation](../../docs/evidence-gate-policy-matrix.md). See the [diagnostic guide](../../docs/evidence-gate-diagnostics.md) for failure codes.

## Verify-gate and current pilot

The terminal and Markdown claim labels come from whether the verified profile selects any resource, producer, or obligation. A profile with a producer and no obligation is still `TargetedComplete`; only a fully empty profile is `NoEvidenceRequired`.

Exit code `0` from `run` means only that the host completed its supported empty profile. It is not the final CI check verdict, does not prove that the subject job ran on the required isolated runner, and does not authenticate the current PR or job provenance. `verify-gate` is a separate trusted-controller command. It bounded-reads and canonical-parses the handed-off plan and manifest plus controller-owned policy and expected identity, calls [`EvidencePullRequestGateVerifier.VerifyAsync`](../../Evidence/ForgeTrust.AppSurface.Evidence.Planner/EvidencePullRequestGateVerifier.cs), and writes `evidence-gate-verification.json`, `evidence-gate-summary.json`, and `evidence-gate-summary.md` (the summaries are each capped at 128 KiB). [`EvidenceGateResultRenderer`](EvidenceGateResultRenderer.cs) renders the same bounded result for terminal output and the Markdown summary. The checked-in live workflow does not invoke this command yet; its verifier step remains an intentionally failing non-claiming scaffold. Nonempty evidence additionally requires the trusted no-follow artifact verifier and an extracted artifact handoff root. The GitHub API reader can report a fresh PR/run/job observation without claiming that it knows the subject checkout; its `SubjectJobHeadRevision` remains empty until a separate `IEvidenceSubjectJobCheckoutAttestationProvider` binds repository, run, attempt, job, and actual checkout revision. An explicitly empty profile needs no subject checkout and can use the fresh observation, but a nonempty profile cannot become eligible without checkout and isolation attestation. GitHub workflow-run and job `head_sha` fields are never treated as checkout proof. No production checkout attestor is included. Never use `run` as the required check publisher.

The emitted manifest is host evidence, not a complete CI authorization. The checked-in GitHub workflow is a separate pilot scaffold: it captures a subject snapshot and can attempt a bounded subject run, but intentionally emits `ASEGH003` because the trusted verifier is not wired to the handoff. The shadow workflow validates contracts only. Neither is a claim-producing required check. A fully empty targeted profile can be verified from fresh PR/run/job authority without a checkout attestor once the trusted workflow invokes `verify-gate`; every nonempty profile additionally needs the subject checkout, isolation, artifact, and cleanup proofs. The complete code-to-cause-to-fix map is in the [diagnostic guide](../../docs/evidence-gate-diagnostics.md).

The required job handoffs remain:

For a nonempty profile, the final authority snapshot must carry an independently verified `SubjectEnvelopeAttested` signal in addition to the manifest's `ValidatedNotAttested` structural status. The current production GitHub provider never sets that signal, so it cannot authorize nonempty evidence even if a checkout attestor is later supplied without a separate isolation proof.

1. The base-owned controller fetches and resolves the complete base/head objects, reads the policy from the protected base revision, captures the fixed-options diff and NUL status set, and creates the canonical v2 plan. It passes only those bounded inputs and the exact subject snapshot to the isolated subject job.
2. The subject job runs the base-built runner and any future supported producer only on an ephemeral, credentialless VM with the subject mounted read-only inside the constrained execution boundary. The current runner executes no head-controlled code, and nonempty profiles fail closed until their producer, resource, dependency, artifact, and cleanup registrations are implemented.
3. The base-owned verifier invokes `verify-gate` with the base-owned policy and Git objects, trusted expected identity, and an authoritative `IEvidencePullRequestGateAuthorityProvider`. It treats the plan, manifest, and subject artifacts as untrusted, independently recreates the plan, verifies manifest and job provenance, checks cleanup and envelope evidence, and re-reads current PR base/head before rendering a gate result. Production GitHub authority leaves the checkout unknown without an attestor, so only an explicit empty profile could pass this boundary. This runner does not consume separate workflow statuses and `run` does not publish a required-check verdict.

See the [policy and producer matrix](../../docs/evidence-gate-policy-matrix.md) for the current implementation gaps and the [EvidenceHost cookbook](../../guides/evidencehost-cookbook.md) for producer and lifecycle concepts.
