### Prepare an application handoff under live PostgreSQL Durable authority — issue #869

The PostgreSQL provider adds a scoped `IDurableWorkHandoffFence` for a running Work executor to revalidate current native invocation authority and write application-owned authorization/ledger state in the caller's exact `ReadCommitted` transaction. Preparation remains provisional until the caller commits; callback denial removes callback writes, and the caller releases the transaction and connection before provider I/O.

Use the [handoff contract](../Durable/handoff-fence.md), [package entry point](../Durable/ForgeTrust.AppSurface.Durable.PostgreSql/README.md#prepare-an-application-handoff), and [canonical Durable diagnostics catalog](../troubleshooting/durable-diagnostics.md) for eligibility, lock order, cleanup, host timeout ownership, cause-to-action refusal guidance, and uncertain-commit recovery. The contract records the repository-pinned Npgsql 10.0.3 `SaveAsync` behavior: the SAVEPOINT is queued with the next command, so method completion alone is not server acknowledgement. See the [#869 test plan](../docs/plans/issue-869-handoff-test-plan.md) for the required 44 scenario IDs and supplemental PostgreSQL/package proof. Check the [progress record](../docs/issue-869-progress.md) for current receipts and strict gate outcomes; this unreleased note does not represent a passing proof, published package, or downstream adoption.

## Migration watch


### Durable execution policies — [issue #765](https://github.com/forge-trust/AppSurface/issues/765)

Durable Work can retain legacy completion-relative backoff or opt into an exclusive absolute deadline and deterministic acceptance-relative retry slots. PostgreSQL makes each effect admission decision against the authoritative cutoff; cancellation of an already-running executor remains cooperative. Schema `12` raises the compatible reader/writer floor, so stop new submissions and drain pre-schema-12 hosts and activators before applying the migration. Deploy compatible packages to every host before accepting the new Work version. For rollback, stop new acceptance and keep schema-12-capable packages available to drain or reconcile accepted Work; do not restore a pre-floor binary. Follow the canonical [execution-policy guide](../Durable/execution-policies-v1.md) and [schema-12 migration and rollback checklist](../Durable/migrations/execution-policies-v1.md).

### Select one typed Config wrapper from a Domain package

A `.NET 10` AppSurface host can select one compatible `IConfig` wrapper from a
Domain assembly outside normal module discovery with
[`AddAppSurfaceConfig<TConfig>()`](../Config/ForgeTrust.AppSurface.Config/README.md#explicitly-register-one-typed-wrapper).
The call keeps lazy singleton initialization and adds the selected wrapper's
attributed declaration for audit; it does not scan assemblies or compose providers
for the host. See the [three-step Domain example](../Config/ForgeTrust.AppSurface.Config/README.md#three-step-domain-example),
[logical-key and registration reference](../guides/config-logical-keys.md#explicit-type-registration),
and the [packed Domain consumer proof](https://github.com/forge-trust/AppSurface/blob/main/tests/config-package-consumer/README.md).

Before adopting this pre-1.0 API, upgrade the coordinated AppSurface package set and
rebuild external providers and wrappers together. Keep the existing manual
registration path until the candidate consumer and staged-host proofs are accepted.
For rollback, restore that path together with the previously supported coordinated
package set. Registration does not migrate persisted keys or secret identities;
follow the [compatibility and rollback guide](../guides/config-key-migration.md#explicit-registration-and-rollback).
