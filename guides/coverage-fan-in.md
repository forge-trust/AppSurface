# Native coverage fan-in

AppSurface dogfoods complete primary solution execution together with independently required Linux, Windows and macOS evidence. The reusable [Coverage facade](../Coverage/ForgeTrust.AppSurface.Coverage/README.md) and [installed CLI](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) provide the native path. AppSurface supplies its explicit policy rather than embedding its solution name, project count, platform set or CI provider in the library.

The primary aggregate and composed patch gates remain 95% line / 85% branch with the existing 0.5-point tolerance and Codecov patch mode. Native supplements never replace missing or failed primary projects. The [storage contract](coverage-storage.md) governs native ownership, leases, history and recovery. Separate downstream consumer adoption and onboarding measurements are deferred; current acceptance focuses on AppSurface dogfooding.

The repository coverage path is selected by the shared [evidence policy](https://github.com/forge-trust/AppSurface/blob/main/.github/evidence.policy.json) and executed by the C# [repository evidence validation tool](../tools/ForgeTrust.AppSurface.Evidence.Validation/README.md). The workflow's `coverage` scope projects the root policy selection to solution coverage. Test-only changes select only that producer and use its direct Codecov-mode patch gate. Source-code changes select coverage and package checks; on CI pull requests that producer union also requires native fan-in. The checked-in `build.yml` PR-native path selects contract v3 with `--native-coverage-contract-version 3`, paired with the current-attempt native capture directory and full pinned event PR base. Local runs keep their existing scoped behavior, test-only PRs keep the direct patch gate, and aggregate-only main runs do not request a patch evaluation. The reusable API, CLI and Dogfood adapter retain their v2 defaults. Local `local` and `local-plan` support `all`, `native`, `coverage`, and `packages` scopes; a scoped run closes only its lane, and `all` is the complete local policy selection.

## Current CI path

In [build.yml](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml), the coverage planning job collects event-bound changed paths and resolves the policy. Its `selection.json` exposes `requiresNativeCoverage`, true when root selection includes `solution-coverage` and at least one other producer. Only that selection starts the Linux, Windows, and macOS security-platform jobs, downloads their captures, and enables PR fan-in. The candidate, native captures and primary use the exact event head rather than the synthetic PR merge commit. Each capture records its actual source, SDK, platform, test scope, coverage policy, report hashes, and workflow run identity. The collected PR base supplies the identical patch baseline to all producers. Test-only coverage skips this native matrix and runs the existing direct patch gate against the solution report.

The build job runs the full solution coverage producer through the validation DLL, using the same source-, SDK-, run- and attempt-bound installed CLI candidate as the native producers. It verifies the complete solution inventory and timings and evaluates the independent primary aggregate gate. For PRs selecting native coverage, the validator passes `--native-coverage-contract-version 3` together with the three current-attempt Linux, Windows and macOS captures and the full pinned event PR base. The installed CLI performs v3 acceptance and a separate read-only verification; the typed patch applicability and bound diff proof remain with the accepted generation and Evidence artifacts. The [Dogfood adapter](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/README.md) and reusable API continue to default to v2 for standalone and compatibility callers. Without native evidence, the producer keeps the existing direct patch-gate path when a patch is requested, or aggregate-only behavior when no patch base exists. This path does not invoke Python. The unconditional `coverage-solution.sh` and optional `coverage-gate-fanin.sh` remain compatibility workflows; they are not the policy-selected `build.yml` entry point.

Coverage acceptance preserves the repository's full-solution aggregate minimums of 95% line and 85% branch, plus the Codecov-mode patch minimums of 95% line and 85% branch for measured points. Both gates retain the existing 0.5 percentage-point tolerance. As documented by the [CLI patch gate](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-gate), a direct patch metric with no measurable changed lines or branches reports 100%; this behavior remains in use for test-only PRs. In the v3 PR-native path, a dimension with no points reported by the accepted collector is `notApplicable`, including when the diff has changed lines. That result describes the report under its accepted collector and policy; it does not prove that changed source has no executable code. V2 fan-in retains its strict nonempty measurable-line requirement and existing zero-branch/100% convention. Main-branch runs have no patch baseline and evaluate the aggregate gate without a patch gate. PRs selecting native evidence require exactly one Linux, Windows, and macOS capture from the same workflow run and attempt, and native-only measurable points may not be discarded from composition.

The artifact layout under `TestResults/coverage-evidence/` is:

- `coverage/`: full-solution collector output, timing and test diagnostics, and aggregate/patch gate reports.
- `coverage-fanin/`: the native adapter request/result documents, locally captured primary, imported native inputs, `composed/` reports and verification receipt, and `accepted/` acceptance generation, when native fan-in is selected.
- `evidence-manifest.json`, `evidence-summary.md`, and `artifacts/`: the evidence host's retained manifest and producer artifacts.

The workflow uploads these outputs as coverage diagnostics and gate reports. The full-solution aggregate gate remains independently required; the composed report's aggregate percentage is informational. Codecov receives the composed report on PRs selecting native coverage, otherwise the full-solution report. Main runs without a patch baseline also report the full-solution report.

## Opt-in schema-v3 report-based patch applicability

> **Interpretation pitfall:** In v3, `PatchOutcome == "PatchAccepted"` means the requested patch evaluation was accepted, including when one or more dimensions are valid `notApplicable`. Pin the expected `contractVersion: 3` and preserve the complete primary/composed line/branch applicability results. V3 accepts valid N/A without an additional measured-only switch; `PatchAccepted` alone does not include the four metric details.

V3 makes patch applicability a versioned result based on points reported by the accepted collector and an independently rederived, source-bound Git diff. It does not prove that the collector reported every executable point. V3 is explicitly selected; it adds no separate “allow N/A” flag. A `CoverageFanInPolicy` remains v2 by default (`ContractVersion = 2`, `ReportProfileId = null`). Select v3 with `ContractVersion = 3` and exact `ReportProfileId = "coverlet-collector-cobertura-v1"`; a strict CLI request uses envelope `schemaVersion: 3` and the same policy fields. In aggregate-and-patch mode, v3 also requires a full lowercase `Gate.DiffBase` commit ID in the repository's object format and `ExpectedPatchSha256` for the exact patch bytes. The API rejects movable refs; a trusted adapter may resolve a friendly ref once and freeze that commit.

V3 `ReplaceOwned` requires the exact registered purpose. Repeated rejections can replace rejected output and repeated acceptances can replace accepted output, subject to unchanged custody/history checks. A rejected evaluation cannot replace an acceptance destination or the reverse; preserve the prior generation and select a fresh destination for that transition. V2 retains its existing gate-evaluation replacement compatibility.

All inputs and generations in one v3 operation are homogeneous v3 evidence: use fresh v3 primary and required supplementary captures from the same source, SDK, configuration, policy, run and attempt. Do not combine v1, v2 and v3 envelopes, captures, compositions, or receipts, and do not relabel historical artifacts. A v3 capture or composition, aggregate-only acceptance, or failure before metric evaluation has `PatchApplicability: null`. The old v1 compatibility verifier and v2 behavior remain versioned separately.

The checked-in `build.yml` PR-native coverage authority explicitly selects v3 through the repository validator's `--native-coverage-contract-version 3` setting, paired with the native capture directory and the full immutable event PR base commit. The primary and exactly three Linux, Windows and macOS captures belong to the current source, workflow run and attempt. The installed CLI accepts the v3 fan-in and independently verifies it read-only. The producer retains the typed primary/composed line and branch applicability, `patch-applicability.json`, `diff.patch`, `diff-metadata.json`, acceptance receipt, gate reports and verification result with its Evidence artifacts. The v3 policy and Dogfood adapter's own defaults remain v2; v2 schemas, defaults and historical generations are unchanged.

V3 changes patch applicability reporting at the collector trust boundary. A valid dimension with no points reported by the accepted collector is `notApplicable`; it is not proof that the changed source contains no executable code and does not permit reducing the declared test or producer inventory. The rollout does not change aggregate or patch thresholds, the 0.5-point tolerance, instrumentation or exclusions, producer selection, or required jobs. Test-only PRs continue to use the direct patch gate, local/test-only paths remain available, and aggregate-only main runs continue without a patch baseline. Preserve the existing coordinated rollback procedure and the separate [#903 selection mitigation](https://github.com/forge-trust/AppSurface/issues/903); retiring that mitigation requires a separately identified change after equivalent fresh proof.

### API outcomes and decision rules

The public [Coverage API](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) returns `CoverageFanInResult.PatchApplicability`, a `CoveragePatchApplicability` with required `Primary` and `Composed` metric sets. Each `CoveragePatchMetricSet` has required `Line` and `Branch` results. The v3 CLI result exposes the same four dimensions. Each metric has six required wire fields: `outcome`, `reason`, `changedLines`, `measurable`, `covered`, and `percent`; nullable values remain explicit JSON `null`.

| Outcome | Exact reason and field constraints | Meaning |
| --- | --- | --- |
| `measured` | `reported-points`; nonnegative Int32 `changedLines`; positive Int32 `measurable`; Int32 `covered` from 0 through `measurable`; non-null decimal `percent` from 0 through 100, rounded to four places, midpoint away from zero | At least one changed point was reported and independently recomputed. A below-threshold composed metric is a numeric rejection. |
| `notApplicable` | `no-reported-patch-points`; nonnegative Int32 `changedLines`; `measurable: 0`; `covered: 0`; `percent: null` | The admitted report has no measured points for this dimension. `changedLines` can be positive; this does not mean the patch changed no source. |
| `unverified` | `invalid-evidence`; `changedLines`, `measurable`, `covered`, and `percent` are all explicit `null` | Evidence prevents a trustworthy metric calculation. It cannot satisfy acceptance. |

`changedLines` counts new-side source lines in validated diff `addedRanges`, not lines the collector measured. It is the same patch-line count in all four metrics. Deleted lines do not contribute. For line metrics, exact canonical repository-relative `(path, line)` identities are deduplicated across report occurrences and hit state is ORed. Reported branch counts are summed for every retained class/method/overload occurrence; occurrences remain preserved in originals and composition even when their line identity is shared. Thus branch `measurable` can exceed `changedLines`. Under Codecov line mode, a line is covered only when hit and its reported branches are absent or fully covered; branch points are never invented from IL or source analysis.

V3 independently evaluates primary and composed line and branch metrics. The primary aggregate gate remains numeric and mandatory; primary patch metrics are diagnostic. Existing patch thresholds and the 0.5-point tolerance apply to measured composed metrics. A valid N/A dimension does not fail by itself, but it never hides a known uncovered measured dimension or another failed gate. `PatchAccepted` requires all four dimensions to be complete measured/N-A results and all required gates to pass. V2 policy encoding bytes and digests, fan-in CLI result shape and behavior, and direct `appsurface coverage gate` JSON and its zero-denominator 100% behavior remain unchanged. V2 fan-in still requires positive patch lines and permits its existing zero-branch/100% convention; it emits no v3 applicability.

### Collector profile and trust boundary

The initial closed v3 profile is exactly `coverlet-collector-cobertura-v1`. Supervised v3 VSTest collection requires `coverlet.collector` 10.0.1; keep that version pinned and qualify any upgrade as a new report profile with fresh report-preservation evidence. The profile admits the existing bounded direct Coverlet Cobertura originals and reuses v2 admission/normalization, class/method identity, count, condition, and raw-to-canonical mapping checks. Required line facts include a valid source filename, positive line number, hit count, and consistent branch-condition counts; a line marked as branch-bearing without valid condition coverage is invalid. Preserve every byte-exact original and its project mapping. Microsoft binary-to-Cobertura conversion is not an accepted profile because the observed conversion loses branch detail. Do not use converted output in place of the pinned direct collector report.

The collector is authoritative for which measurable line and branch points it reports. A newly added `[ExcludeFromCodeCoverage]`-style attribute honored by the unchanged accepted collector policy can remove every changed measurement and yield N/A, or remove only part of a mixed patch so the remaining reported points can pass. V3 has no `excluded-by-policy` outcome and does not classify the source attribute; these cases use generic absence of measured points. Different declared include/exclude or collector settings fail policy/profile admission. Silent collector omissions and report misattribution remain possible even when a report is internally valid. Therefore N/A means only “no changed measurements reported under this accepted collector and policy”; it is not evidence of no executable code, a source-completeness proof, or permission to reduce the declared producer/test inventory.

The supervised v3 collector preflight verifies the restored collector identity for every selected target framework before creating the output artifact session. A matching declared package version alone is insufficient: restore must resolve the supported collector version in both the selected framework/RID targets and the library inventory. Unless `NoRestore` is set, preflight performs a supervised restore in the selected configuration; collection then suppresses implicit restore to consume the checked graph. With `NoRestore`, the existing assets must already pass the same checks. The evaluated `ProjectAssetsFile` must be a regular, link-free `project.assets.json` under the evaluated project extensions directory, identify the selected project, and fit the 1 MiB/depth-32 admission bounds. Correct missing, unsupported or mismatched restored metadata and rerun preflight; do not relabel a report from another collector as the accepted profile.

### V3 applicability and diff artifacts

For aggregate-and-patch acceptance, `patch-applicability.json` has exactly these root fields: `schemaVersion: 3`, `reportProfileId`, `policyDigest`, `source`, `run`, `diffSha256`, `diffMetadataSha256`, ordered `captureManifestHashes`, `primaryReportSha256`, `composedReportSha256`, `primary`, and `composed`. Each metric set contains required `line` and `branch` objects with the six fields above. Manifest hashes are ordered primary first, then supplementary producer IDs in ordinal order. `primaryReportSha256` hashes the composition's `primary-paths.cobertura.xml`; `composedReportSha256` hashes its `coverage.cobertura.xml`. V3 gate JSON carries the same patch metric copies beside aggregate and threshold fields; the independent verifier rejects disagreement among those copies.

`diff-metadata.json` has the exact root shape `{ "schemaVersion": 3, "requestedBaseCommit": "…", "mergeBaseCommit": "…", "headCommit": "…", "diffPolicyId": "appsurface-git-patch-v1", "diffSha256": "…", "empty": false, "changes": [...] }`. Each change contains `kind`, nullable `oldPath` and `newPath`, and `addedRanges` of positive `{ "start": n, "count": n }` spans. Kinds are `added`, `modified`, `deleted`, `renamed`, and `modeChanged`; added has `oldPath: null`, deleted has `newPath: null`, and a rename retains both distinct paths. Ranges are sorted, nonoverlapping and coalesced when adjacent. The metadata records the selected diff policy. A [qualified screenshot replacement](#screenshot-baseline-updates) retains its path and carries an empty range list.

`empty: true` is valid only when the canonical patch has exactly zero bytes and the pinned-object raw change inventory is also empty. A recognized deletion, metadata-only rename/mode change, or empty new file is `empty: false` with no added ranges; either case can yield N/A only after full validation. `ExpectedPatchSha256` is required even for the exact empty byte sequence and must match the recomputed patch hash. The v3 acceptance receipt hashes the applicability claim, gate reports, patch and diff metadata. A numeric rejection retains measured metrics and a `gate-failed` rejection claim. An invalid-evidence result has no acceptance receipt; a typed unverified claim and `rejection.json` are retained only when all referenced identities were admitted and safe owned staging is available. Otherwise, the operation returns bounded diagnostics/effects without publishing that claim. Verify is read-only and never promotes or repairs a rejected generation.

The operation's `TotalRecords` limit applies across XML readers sharing its v3 invocation budget, before a further document is materialized. Reusing a reader's cached document adds no records; independently materialized documents in separate readers consume the shared allowance. Byte, per-report structure and deadline limits remain separate checks.

### Deterministic Git policy `appsurface-git-patch-v1`

V3 requires Git 2.46 or later before reading objects. Numeric upstream versions and recognized Apple Git/Windows vendor suffixes are accepted; unknown or older output fails closed as `unsupported-git-version`. This floor enables enforced attribute-source and no-lazy-fetch behavior. The same corpus must run on the actual Linux, Windows and macOS Git versions before enablement; no byte-identity promise is made for untested future Git releases.

Every Git call uses an argument vector, `UseShellExecute=false`, an absolute validated repository working directory, strict UTF-8, and a linked per-probe deadline of `min(remaining operation time, IdentitySeconds)` (30 seconds by default) inside the existing 300-second operation budget. Clear every inherited `GIT_*` variable in the child environment, case-insensitively on Windows. Set `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to the OS null device (`NUL` on Windows, `/dev/null` on Unix), `GIT_ATTR_NOSYSTEM=1`, `GIT_ATTR_SOURCE=<pinned head commit>`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `GIT_NO_LAZY_FETCH=1`, `LC_ALL=C`, and `LANG=C`. Do not change the parent environment, `HOME`, or cache paths. No fetch, hook, helper, temporary config/index/worktree, or report file is used by read-only verification.

The common Git argument prefix is `--no-pager --no-replace-objects -c core.fsmonitor=false -c core.quotePath=true -c core.attributesFile=<OS null device> -c diff.renames=true -c diff.renameLimit=1000 -c diff.orderFile=<OS null device> -c diff.mnemonicPrefix=false -c diff.noprefix=false -c diff.suppressBlankEmpty=false`. The fixed diff options for raw views and patch generation are:

```text
diff --no-color --no-ext-diff --no-textconv --no-relative
  --no-renames --find-renames=50% --no-rename-empty -l1000
  --diff-algorithm=myers --no-indent-heuristic
  --ignore-submodules=none --submodule=short
```

The retained patch additionally uses `--patch --unified=0 --inter-hunk-context=0 --full-index --src-prefix=a/ --dst-prefix=b/ --output-indicator-new=+ --output-indicator-old=- --output-indicator-context= ` and then `<mergeBase> <head> --`. The final context-indicator value is one argv item ending in a literal space. The independent raw view uses `--raw -z --no-abbrev` with the same endpoints. A no-renames raw preflight bounds candidates before content matching; more than 1,000 added/deleted candidates or any rename-limit warning fails. Similarity is fixed at 50%, copies are not detected, and there is no automatic no-renames success fallback.

Resolve a friendly requested base exactly once in the trusted adapter with `rev-parse --verify --end-of-options <base>^{commit}` and freeze the full lowercase object ID. The public v3 API accepts only that ID. The exact supplied base object must have Git type `commit`; a full annotated-tag object ID is refused even though Git could peel it. Source commit and tree must match the checkout; object format must be SHA-1 (40 hex) or SHA-256 (64 hex). `merge-base --all <requestedBase> <head>` must return exactly one locally available base; the patch uses requested-base-to-head semantics via that unique merge base and head, and the requested base need not equal the merge base. Shallow history, partial clones/promisor configuration, missing or multiple merge bases, source drift, unsupported repository state, and nonempty common-Git-dir `info/attributes` or `info/grafts` are refusals. There is no automatic fetch or rebase.

System/global attributes are disabled and committed attributes are read only from pinned head. Effective repository/worktree `diff.*` configuration is inspected without printing values: custom `diff.<driver>.*` and any setting not explicitly neutralized by this policy reject. Neutralized names are `diff.renames`, `diff.renameLimit`, `diff.orderFile`, `diff.mnemonicPrefix`, `diff.noprefix`, `diff.suppressBlankEmpty`, `diff.context`, `diff.interHunkContext`, `diff.algorithm`, and `diff.indentHeuristic`. Admitted config, attributes and source observations are rechecked before returning.

The V3 source check also isolates Git's system and global configuration when checking for local changes. On Windows, the [native coverage job](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml) disables the runner's automatic CRLF conversion before checkout so that files without committed line-ending attributes retain their Git bytes. A dirty checkout returns `ASCOV302` with cause `identity-mismatch` and role `source` before capture reads a report.

The default diff policy supports regular text files. Binary content/markers, symlink/type/gitlink changes, malformed or truncated patch/raw correspondence, traversal or path aliases, and unsupported UTF-8/C-quoted paths reject the whole requested patch; a measured subset is never accepted after an unsupported file is skipped. Ordinary Unicode, spaces, quotes and leading dashes are supported when they have an unambiguous portable identity. The admitted tracked inventory must also use these portable path identities, including unchanged files; this is a repository prerequisite for v3 capture and replay. Case/NFC normalization detects aliases but never joins distinct names. Renames retain origin and destination; additions are measured at surviving new-side paths. Copy-like changes are ordinary additions. There is no whitespace-ignore, forced-text, path-filter, suffix exemption, or untracked-file fallback.

### Screenshot baseline updates

AppSurface CI selects `appsurface-visual-baseline-png-v1` for its v3 native coverage jobs. Use this policy when a PR updates an existing Playwright baseline alongside documentation or code. Standalone v3 callers get the strict text policy when they omit `diffPolicyId`. Every capture, composition, acceptance and verification in a run must use the same policy. Changed paths must use Git’s automatic diff classification or the explicit binary attribute (`-diff`). A forced text diff or named diff driver on a changed path prevents acceptance.

A screenshot qualifies only when Git reports a modification at the same path, both versions have mode `100644`, and both pinned blobs pass the PNG checks. The filename must be directly inside `Web/ForgeTrust.RazorWire.IntegrationTests/VisualBaselines/AppSurfaceDocsGraphite/` or its sibling `AppSurfaceDocsLight/`. Use a basename containing ASCII letters, digits, hyphens or underscores followed by `.png`. Both images must use noninterlaced 8-bit RGB with a PNG header, image-data chunks and a terminal end chunk. The reader checks chunk lengths and checksums, validates the compressed scanlines and applies a 20 MiB decoded-size limit per image. Additions, deletions, renames and other binary changes fall outside this qualification. If a coverage report identifies the screenshot as source, acceptance fails.

The gate retains the binary change in the canonical patch and records its path in `diff-metadata.json` with empty `addedRanges`. A PR that also changes covered C# still has its changed lines and branches evaluated. A screenshot-only PR can receive `notApplicable` after the verifier checks both the patch and the collector reports. The [visual baseline tests](https://github.com/forge-trust/AppSurface/tree/main/Web/ForgeTrust.RazorWire.IntegrationTests) still compare the rendered pages with the committed images.

### Budgets, diagnostics, and maintainer recovery

The defaults in [`CoverageOperationLimits`](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) remain 512 MiB per XML, 1 MiB per JSON/other text, 4 GiB total admitted/staged bytes, depth 64, 1,000,000 line records/report, 2,000,000 branch records/report and retained records/operation, 32 input bundles, 8,000,000 XML elements/report, 32 attributes/element, 65,536 token characters, 300 seconds/operation, and 30 seconds/identity probe. Collection has its separate 1–86,400 second deadline. V3 Git additionally caps each stdout/stderr/config/raw stream at 1 MiB, object-list stdin at 1 MiB, retained patch at 20 MiB, each distinct old/new regular blob at 20 MiB and total distinct regular blobs at 256 MiB. All v3 process stdin/stdout/stderr, logical source/blob work, admitted inputs and retained/staged outputs charge one invocation-local checked budget under `TotalBytes`; the v3 CLI proof field `result.accounting` reports `usedBytes` and the unchanged `limitBytes`. The internal proof snapshot also records admitted XML/JSON bytes, parsed line/condition records and admitted staging bytes/files. These are bounded admission measurements, not decoded DOM heap or process RSS; consumer qualification measures wall time, peak RSS and retained output size separately. No operation budget is increased or reset. These are logical byte bounds, not a promise about Git's process working set. Truncation or exhaustion cancels, drains and reaps the child and cannot become an empty patch.

V3 `CoverageDiagnostic.Cause` is closed to `unsupported-version`, `unsupported-profile`, `invalid-policy`, `missing-diff`, `malformed-diff`, `truncated-diff`, `unsupported-diff`, `merge-base-unavailable`, `identity-mismatch`, `report-invalid`, `reported-record-loss`, `applicability-mismatch`, `limit-exceeded`, `threshold-failed`, `cancelled`, `deadline-exceeded`, `unexpected-failure`, `delivery-failed`, and `unsupported-git-version`. Context may contain only `contractVersion`, `reportProfileId`, `diffPolicyId`, `baseCommit`, `headCommit`, `exceptionType`, `gitExitCode`, and `gitVersion`. Expected failures have no trace. Unexpected traces have at most eight sanitized frames of 256 characters, only from Coverage, Evidence.Coverage and CLI namespaces (or a fixed labeled handler location when none is eligible); paths, arguments, environment, stderr and exception messages are not exposed.

| Failure | Stable result | Recovery |
| --- | --- | --- |
| Unsupported host Git | `ASCOV302`, cause `unsupported-git-version`, role `git` | Install Git 2.46 or later, use a fresh matching checkout with complete pinned history, then regenerate. No automatic fetch. |
| Missing/multiple base or shallow/partial history | `ASCOV302`, cause `merge-base-unavailable` | Provide complete local history and an owner-approved requested base with one merge base; do not automatically rebase. |
| Binary/type/path/attribute/config shape outside policy | `ASCOV302`, cause `unsupported-diff` | Ask the maintainer to resolve the input or qualify a new diff policy. Do not skip files, force text, or fall back to v2 for the same claimed result. |
| Unsupported path in the pinned tracked-file inventory | `ASCOV302`, cause `unsupported-diff`, role `source` | Inspect the tracked-file inventory, including submodules; the name can be outside the patch. Resolve the source inventory before fresh evidence. Arbitrary rejected names are not copied into diagnostics. |
| Malformed, truncated, mismatched or excluded report facts | `ASCOV302`, cause identifies invalid evidence/record loss | Regenerate complete original supported reports and correct detectable mapping loss. Never edit N/A flags or fabricate an empty diff. |
| Fixed byte, blob, candidate, record or deadline limit | `ASCOV302` or existing `ASCOV306`, with `limit-exceeded` / `deadline-exceeded` | Preserve limits and required scope; ask the maintainer to restructure supported input or qualify a separate policy. |
| Uncovered measured composed points | `ASCOV307`, cause `threshold-failed` | Add honest tests for the reported points; keep thresholds, tolerance, exclusions and producer inventory unchanged. |

Invalid public API policy remains a pre-effect `ArgumentException`/`ASCOV301`; malformed CLI admission is `ASCOVF001` with exit 2. V3 evidence rejection is `ASCOV302`; numeric rejection is `ASCOV307`; cancellation/deadline is `ASCOV306` (CLI exit 130/124), and actual committed effects remain reported after post-commit cancellation or delivery failure. Reconcile unknown/partial effects before at most one corrected fresh retry. A safe recovery does not rewrite claims or erase retained evidence.

The rollout requires fresh actual-source, installed-consumer, native-platform, selected-Evidence-producer and decoded/staged/retained-budget proof. Missing infrastructure or a failed lane blocks qualification. Preserve its diagnostics for the maintainer. Rollback coordinates writer, verifier, adapters and repository policy back to explicit v2 while preserving artifacts and the #903 mitigation. Use v3-capable coordinated tooling to inspect retained v3 history after rollback.

## Native schema-v2 workflow

The neutral [Coverage package](../Coverage/ForgeTrust.AppSurface.Coverage/README.md) supplies asynchronous collection/capture, composition, acceptance and independent read-only verification. The [AppSurface CLI](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) exposes the same operations. V2 remains the default for the reusable policy/API, installed CLI requests that omit a contract version, and standalone Dogfood invocations. The checked-in `build.yml` PR-native repository path opts into v3 explicitly with `--native-coverage-contract-version 3`. The [EvidenceHost adapter](../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md#coverage-fan-in-producer) requires independently accepted current-run evidence and successful result delivery before it returns an assertion. Capture/compose success is never an acceptance result.

Use ordinary `coverage merge` to combine compatible reports when source/run-bound acceptance is unnecessary. Fan-in adds exact intended project/native inventories, clean commit/tree and SDK/configuration identity, explicit instrumentation/run policy, conservative class/method composition, a separate primary aggregate gate, and independent semantic verification. It does not sign artifacts or prove that arbitrary caller-supplied tests actually ran. `CollectedExecution` originates in supervised collection; `TrustedProducer` is an explicit trust boundary. Local import preserves either observation and never claims new execution.

The public contracts and defaults are in the [package reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md). Every request supplies a complete intended primary inventory and exact supplementary IDs/platforms/filters. Supplementary project inventories may be narrower than the primary only when explicitly declared. Paths use slash-relative identities, not a project-name suffix convention. The reusable engine never substitutes AppSurface's project count or CI variables for consumer declarations. AppSurface supplies its own complete policy in the [dogfood adapter](https://github.com/forge-trust/AppSurface/blob/main/tools/ForgeTrust.AppSurface.Coverage.Dogfood/Program.cs), including all solution projects and Linux/Windows/Darwin native evidence.

For copyable calls to all five facade operations, the shipped Evidence producer, a generated strict-v2 CLI request/result walkthrough, and the exact installed package proof command, run the [coverage dogfood examples](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md). The examples use runtime source/run identity and actual producer artifact paths. They do not embed reusable-looking hashes or claim that a platform's native matrix passed.

### C# operations and ordering

All facade methods return `ValueTask<CoverageFanInResult>` and accept the optional cancellation token plus caller-owned progress and diagnostic writers. The concrete calls and parameters are in [CoverageFanInApiExample.cs](https://github.com/forge-trust/AppSurface/blob/main/tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/CoverageFanInApiExample.cs); use the exact result contract to distinguish completed work from acceptance.

1. `CoverageFanIn.CollectAndCaptureAsync(CoverageCollectRequest, token, progress, diagnostics)` runs the declared inventory through the supervised collector and captures only success. Supply a collection directory and explicit 1–86,400 second deadline. Collection always writes indexed original collector evidence, including for a one-project inventory. Alternatively `CaptureAsync(CoverageCaptureRequest, ...)` validates a trusted normalized primary plus its successful timings, a one-project `RawCoveragePath` with optional bounded-XML `CoveragePath` compatibility input, an indexed `RawCoveragePaths` inventory of one or more projects with complete timings, or an imported portable capture plus its exact original source root. Native measurements are derived from original collector facts; `CoveragePath` never supplies them. Fresh output is the default; `ReplaceOwned` is explicit.
2. `ComposeAsync(CoverageComposeRequest, ...)` requires the primary and exact supplementary set. It retains all class and method occurrences, overloads and native-only points. Matching-denominator individually full observations may promote a branch; partial observations never add together to invent full coverage.
3. `AcceptAsync(CoverageAcceptRequest, ...)` checks the complete primary aggregate, the composed patch when explicitly requested, then independent facts and gate arithmetic. It commits an exact accepted generation only after required work completes. Numeric gate failures retain rejected gate reports without an acceptance receipt.
4. `VerifyAsync(CoverageVerifyRequest, ...)` checks existing retained captures/composition/acceptance against trusted caller expectations. It creates no coordination, repairs nothing, and makes no historical evidence fresh. `Outcome == Succeeded` and `Verified == true` establish consistency under the supplied expectations; neither property authenticates a producer or independently proves arbitrary test execution.

Requests snapshot caller collections before mutation; subsequent caller edits do not change a running policy. Callers own writers and cancellation sources, which are not disposed or retained. The .NET SDK, Git, consumer test SDK and supported Coverlet collector prerequisites must be installed. Native fan-in measurements come from retained collector facts, not a ReportGenerator-normalized hybrid. The private support package's [pinned ReportGenerator runtime](../Evidence/ForgeTrust.AppSurface.Evidence.Coverage/README.md#reportgenerator-runtime-payload) remains available to workflows that require it; native projection does not use its output as the measurement oracle.

Use a clean, complete checkout without Git index entries marked `assume-unchanged` or `skip-worktree`. Fan-in checks every pinned submodule, including those marked inactive, and rejects missing checkouts, mismatched commits, hidden index flags, or dirty files. Source and patch checks ignore replacement refs and use the original objects behind the pinned Git IDs. The index walk allows at most 32 checkouts including the root and shares the identity deadline. Each Git probe has a 1 MiB output limit per stream; an incomplete index listing is rejected.

Read-only verification checks the pinned source, SDK and clean state both before reading evidence and after validating the accepted generation, before returning `Verified`. A source change during verification rejects the operation without changing the evidence. Use a dedicated checkout without concurrent writers: these checks detect changed observations, but do not lock every compiler input or make the worktree immutable.

Commit every declared primary and supplementary test project in the pinned repository or a pinned submodule. A project file present only on disk, such as an ignored local project, is rejected even if Git reports a clean worktree.

For supervised collection, use a dedicated checkout and put evidence and local scratch outside it. Collection rejects ignored files before and after execution, except directories named exactly `bin/` or `obj/` beside a tracked .NET project with no ancestor project directory. An SDK project can compile ignored source through default globs, including files under a nested project's output directory. Use trusted restore outputs and committed build configuration. This check does not isolate MSBuild or authenticate its dependencies.

`CoverageGateMode.AggregateOnly` is an explicit baseline with `PatchNotRequested`. It creates no patch-pass artifact and cannot satisfy a patch-required obligation. `AggregateAndPatch` requires the declared Git revision (option-like bases beginning with `-` are rejected), the identical frozen diff for primary/composed analysis, nonempty measurable changed lines and line/branch denominators no smaller than the primary reference. The [Git patch reader](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-gate) disables external diff drivers and text converters so the patch describes committed source. Both the gate and the independent verifier reject a Git filename with a literal backslash rather than assigning its lines to a different file. This choice never silently follows from an absent diff. AppSurface's configured thresholds/tolerance, Codecov mode, complete primary and native requirements remain authoritative.

### Installed commands and request schema

The four parser-registered commands are `appsurface coverage fan-in capture`, `compose`, `accept`, and `verify`. The `capture` command has a `--collect` selector for the fifth facade operation, collection-and-capture. Each takes `--request <file>`; writing commands require `--result <new-file>` in an existing safe directory. Add `--json` for exactly one bounded terminal document on stdout; progress and diagnostics use stderr. Verify's result destination is optional and only records adapter delivery; it does not authorize modification of evidence. Every requested result file must be fresh.

Collection uses a strict versioned request whose envelope has `operation: "collect"` and whose `request` is a complete `CoverageCollectRequest` (including policy, clean repository root, fresh capture and collection destinations, producer ID, and deadline). V2 is the repository default; v3 requires a homogeneous v3 policy and fresh capture set. Observed collection rebuilds before testing. Omit `noBuild` or set it to `false`; a true value is rejected before execution. Set `noRestore` only if you have already restored the inputs. The exact parser invocation is:

```sh
"$APPSURFACE_CLI" coverage fan-in capture \
  --request "$COLLECT_REQUEST_JSON" \
  --result "$COLLECT_RESULT_JSON" \
  --json --collect
```

The same command without `--collect` requires `operation: "capture"` and a producer report or portable import. Do not change only the envelope or only the selector: they must agree. The installed headless fixture's [`--package-proof` walkthrough](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md#run-the-installed-headless-package-proof) demonstrates real supervised collection using the packed neutral packages and records its generated stage evidence.

The request, request-file and result-file paths must pass the CLI's regular, link-free filesystem checks. Request JSON is limited to 1 MiB and depth 64, rejects comments/trailing commas, and rejects duplicate property names at every depth. JSON property names and enum tokens are case-sensitive; decimal values are read losslessly. Missing optional members take the public record defaults, but the complete policy members and operation-required selectors must be present. See the exact requests generated by the [dogfood walkthrough](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md#generate-exact-cli-requests-and-results).

Requests use the exact v2 envelope `{ "schemaVersion": 2, "operation": "capture", "request": { ... } }`, with camelCase request members and string enums. V3 uses `schemaVersion: 3` and requires `policy.contractVersion: 3` plus `policy.reportProfileId: "coverlet-collector-cobertura-v1"`; standalone Dogfood callers may select it with the adapter's documented `--contract-version 3` option, whose default remains 2. The repository PR-native validator setting is `--native-coverage-contract-version 3` and requires paired native captures plus a full pinned diff base. Collection uses `operation: "collect"` together with `capture --collect`. Unknown, duplicate, missing required, wrongly typed or contradictory fields fail before execution. API/package versions, CLI request schema, capture schema, local coordination and policy encoding are separate version domains; `coverage-policy-c14n-1` identifies canonical policy bytes, not an execution claim.

V2 `accept` requests may set `expectedPatchSha256` to bind patch acceptance to the exact unified Git diff used during planning. V3 requires it for patch acceptance. It must be a 64-digit SHA-256 and is invalid for aggregate-only requests. V2 patch coverage requires measurable changed lines and uses its 0/0 convention when the patch contains no measurable branch conditions. Both versions preserve measurable branch points from the primary report during composition.

Exit 0 means the requested operation succeeded; 1 means rejection, failed/incomplete work or delivery failure; 2 means invalid input; 130 means cancellation; 124 preserves the terminal watchdog/deadline result. Inspect both the requested operation/outcome and delivery status. A composed capture may succeed while no accepted coverage exists. A committed accepted generation may survive failed adapter delivery; reconcile that exact generation before retrying delivery. Never blindly rerun or reuse the previous invocation's success.

The v2 CLI JSON result keeps its existing outer `schemaVersion: 2`, `operation`, `status`, nullable `operationOutcome`, effects, safe operation result, delivery state and bounded diagnostics. V3 uses outer `schemaVersion: 3` and adds the four `result.patchApplicability` metric results and v3 diagnostic context/trace fields; `PatchAccepted` may include valid N/A. The v3-only `result.accounting` proof snapshot has Int64 fields `usedBytes`, `limitBytes`, `xmlBytes`, `jsonBytes`, `lineRecords`, `branchRecords`, `stagedBytes`, and `stagedFiles` and is internal telemetry, not a supported public API. It reports charged logical budget work, admitted XML/JSON input bytes and XML records, and admitted output staging bytes/files, including the completion marker. Cached reads and cached document parses are counted once. The staged snapshot bounds one fresh publication; it does not measure decoded DOM heap, child-process RSS or wall time. The v2 codec omits this field, and neither the canonical metric artifact nor `diff-metadata.json` root shape changes. Measure process wall time, peak RSS and output size separately in consumer qualification proof. The adapter samples available process peaks before child exit; unavailable or zero-valued runtime observations are explicit null and do not complete the memory proof. A succeeded command requires operation success and result delivery; `deliveryFailed` can coexist with `operationOutcome: "succeeded"` and `generationCommitted: true`. The artifact projection omits host paths. For Evidence, the shipped [`EvidenceCoverageFanInProducer`](../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md#coverage-fan-in-producer) writes a bounded JSON acceptance result to its declared artifact slot before it may return the declared assertion. Its v3 projection carries all four applicability outcomes and its assurance check allows valid N/A while requiring the set to be complete; see the [producer contract](../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md#coverage-fan-in-producer).

### Portable inputs, replay and replacement

Indexed native inventories support one or more projects. Supervised collection binds one original collector attachment to each successful project invocation, always writes the indexed form, and retains every original byte sequence, complete timings and the exact project-to-file index. To capture an existing trusted indexed inventory, supply `rawCoveragePaths` as an exact object mapping every declared project path to its original report path and `timingsPath` as the complete successful inventory; omit `coveragePath` and `rawCoveragePath`. The package [request and artifact reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) defines the index shape, file names and limits. The single-report compatibility form uses `rawCoveragePath` for exactly one declared project, permits optional `coveragePath` that must pass bounded XML admission, and requires `timingsPath` to be absent. The established single-project output filenames `collector.cobertura.xml`, `coverage.cobertura.xml`, and `manifest.json` remain unchanged. Import has no report or timing selectors. Capture schema v2 is unchanged.

Every load and import independently verifies native evidence against the original collector bytes, and composition, acceptance and read-only verification repeat that check. The canonical projection preserves class, method, line and occurrence facts and derives root totals from class-line points. Existing v2 single-report captures are accepted only when their stored facts and root totals already equal that canonical projection. Older folded, reconstructed, or inflated hybrid projections are rejected even if their hashes are valid; recapture from the original reports into a fresh destination. The historical v1 reader and its strict behavior remain unchanged. A one-report indexed inventory cannot satisfy a declaration containing multiple projects.

A downloaded v2 capture is transported data, not receiving-host ownership. Use `CaptureAsync`/`capture` with `importDirectory`, the exact `originalSourceRoot` and a fresh receiving destination. The receiver validates original bytes, source/run/attempt/policy and relative identities, creates new local custody, and preserves original producer observations. Copying lock files or inode metadata never grants authority. The same current trusted run's imported native evidence may contribute to acceptance only after exact caller expectations and independent checks pass. On compose, accept and verify, the CLI result's `primaryImported` distinguishes imported primary evidence from imported supplements. EvidenceHost's `requireObservedPrimary` rejects an imported primary even if its observation is `CollectedExecution`. Historical replay remains historical, even if a caller changes its label or local directory.

Primary imports must pass the same measurable-point validation as fresh captures; a valid payload hash and successful timings cannot admit malformed coverage numbers or escaping source paths. The original source root supports POSIX, Windows drive, and UNC paths independently of the receiving operating system. It maps recorded source paths rather than locating files on the receiver.

Outputs default to fresh-only. Explicit `ReplaceOwned` additionally requires an existing generation with compatible private registration, purpose, current physical identity, exclusive custody and exact retained inventory/hashes. A missing destination is rejected without creating its root or lock; use `Fresh` for the first publication. Acceptance and numeric rejection are two states of one gate-evaluation purpose: replacing accepted output with a failed evaluation commits the rejection reports without an acceptance receipt, and a corrected retry can replace that rejected generation. Capture and composition cannot replace gate-evaluation output or each other. Unknown, altered, linked or foreign contents survive refusal. A populated legacy tree is never marked to manufacture ownership. Stage validation precedes prior retirement. A completion marker is the commit boundary: cancellation before it yields no complete generation; cancellation after it reports actual committed state. Required cleanup occurs before commit, and incomplete effects remain explicit.

### Coordinated release rollback

If a consumer must roll back after installing a coordinated package release, pin and reinstall the previous supported versions of `ForgeTrust.AppSurface.Coverage`, its exact-version `ForgeTrust.AppSurface.Evidence.Coverage` private engine dependency, and `ForgeTrust.AppSurface.Cli` together. Confirm the matching family and version in the [package chooser](../packages/README.md) and follow the [package installation and version contract](../Coverage/ForgeTrust.AppSurface.Coverage/README.md). If the consumer uses the Evidence adapter, restore its integration to the matching prior release as well. Do not combine a facade with a different engine version.

Resume with fresh output roots and a schema and policy supported by that prior release. Preserve existing captures and reports for diagnosis; do not rewrite them, adopt populated directories, or feed envelopes the prior release does not support. Rerun collection or capture, composition, acceptance, and verification with the restored installed consumer, then pass the installed-package and native dogfood checks before promoting that release family again. The [dogfood examples](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md) document candidate-package proof and fresh output behavior.

For an AppSurface CI rollout, revert the coherent migration commit and its matching configuration together, restoring the previous producer only while it remains compatible with the repository's current evidence and gate contracts. Keep the existing thresholds and required evidence policy; rollback does not authorize lowering gates. This procedure coordinates a release recovery and does not publish, unpublish, or otherwise change package releases.

V1 captures and the original [Aspire verifier API](https://github.com/forge-trust/AppSurface/blob/main/Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceCoverageFanIn.cs) retain their original strict read-only contract. V1 and v2 cannot mix. There is no in-place conversion that relabels old reports as new execution; recapture a new run and use fresh destinations when custody cannot be established.

### Diagnostics

`ASCOV301` identifies invalid explicit input; `ASCOV302` identifies failed evidence/custody checks; `ASCOV306` identifies cancellation/deadline or terminal watchdog; `ASCOV307` identifies rejected numeric gates; `ASCOV309` identifies post-operation delivery failure; `ASCOV310` identifies an unmet Evidence assurance requirement. CLI admission/delivery diagnostics use `ASCOVF001`–`ASCOVF006`, and runtime closure uses `ASCOV140`.

Read the stable code, operation/stage, field role, policy digest, operation/generation identity and recovery action. Expected rejection and cancellation do not include raw exception traces. Preserve failure artifacts, inspect the exact scope/identity/report that disagrees, correct the declared input or add honest tests, then retry once into a fresh safe destination. Unknown effects require reconciliation before retrying. Diagnostics must not copy arbitrary report data, secrets, raw child logs or dependency exception text into terminal output.

The current acceptance target is AppSurface dogfooding with its own solution and native matrix. Separate downstream consumer adoption and onboarding measurements are deferred by user direction; they are not established by local fixture tests or this guide.

## Historical v1 evidence

The original Python producer and shell policy checks are the schema-v1 behavioral baseline. Historical captures use their original strict source/SDK/configuration/filter/run rules and read-only [Aspire verification API](https://github.com/forge-trust/AppSurface/blob/main/Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceCoverageFanIn.cs). They are neither generic v2 captures nor new execution. Preserve old downloaded evidence; do not add ownership markers, mix schemas, rewrite manifests or relabel old reports to satisfy a new run. Recapture through the native path and select fresh output when custody cannot be established.

The independent v2 regressions preserve class/method occurrence and overload records, native-only points, conservative individually full branch promotion, and patch denominator scope. The [native test families](https://github.com/forge-trust/AppSurface/blob/main/Cli/ForgeTrust.AppSurface.Cli.Tests/CoverageFanInIndependentVerifierTests.cs) use hand-authored expected facts and altered-output cases; a producer receipt is never its own oracle.

The primary aggregate gate retains the exact original normalized primary root counters, including compiler points that ReportGenerator may summarize without serialized class lines. Replacing those counters with class-derived totals would change the established aggregate measurement. Native projection follows a separate ownership rule: original collector class and method facts define its records, and collector root summaries cannot supply missing points. Composition retains every primary record and its denominator, then merges supplementary raw facts conservatively; the composed root totals derive from the complete resulting class-line points; patch metrics also inspect method points. The independent verifier checks the unchanged primary aggregate counters and separately re-derives native and composed facts from retained raw reports. These measurement rules do not change the configured aggregate or patch thresholds, tolerance, or patch mode. See the [Coverage API reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) for native input forms and the raw-summary edge case.

For AppSurface CI, the optional [gate wrapper](https://github.com/forge-trust/AppSurface/blob/main/scripts/coverage-gate-fanin.sh) preserves the existing primary `aggregate-gate/coverage-gate.json`/`.md` and root patch `coverage-gate.json`/`.md` plus patch-target report paths by invoking the installed gate command against separate composed inputs. Numeric rejection retains reports and returns failure. Baseline builds with no diff base publish only the primary aggregate reports. The immutable acceptance generation remains the authoritative native evidence; canonical CI reports are additional presentation artifacts.

## Evidence and troubleshooting

The installed [Coverage commands](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) verify capture manifests and hashes, source and SDK identity, exact test inventory, workflow provenance, conservative composition and gate evidence. The repository validator supplies the selected policy and requires successful native acceptance plus independent read-only verification before closing its coverage assertion. For the checked-in v3 PR-native path, the validator also retains and checks the complete typed patch applicability and its bound diff proof. The validation tool's separate `capture-native` operation and the original `EvidenceCoverageFanIn` API retain their historical schema-v1 compatibility contract; standalone callers remain on v2 by default unless they explicitly opt in.

When a coverage lane fails, download the `coverage-gate-reports` and `test-result-diagnostics` artifacts from the same workflow run. Inspect the full-solution timings and test logs under `coverage/`, the evidence summary and manifest, and, when selected, the fan-in verification receipt and retained accepted proof under `coverage-fanin/`. Missing projects, required native captures, mismatched provenance or report hashes, incomplete typed v3 applicability, invalid `notApplicable` results, and failed applicable thresholds are hard failures. A direct patch metric with no measurable points follows the CLI's documented 100% behavior; v3 native fan-in instead records `notApplicable` only when the accepted collector reported no patch points for that dimension. Regenerate evidence from the current source and workflow run rather than relabeling old reports.

The compatibility shell wrappers remain documented in their source for callers that explicitly select them. Their artifact layout and historical Python test commands do not describe the current policy-selected workflow.
