# Native coverage fan-in

AppSurface dogfoods complete primary solution execution together with independently required Linux, Windows and macOS evidence. The reusable [Coverage facade](../Coverage/ForgeTrust.AppSurface.Coverage/README.md) and [installed CLI](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) provide the native path. AppSurface supplies its explicit policy rather than embedding its solution name, project count, platform set or CI provider in the library.

The primary aggregate and composed patch gates remain 95% line / 85% branch with the existing 0.5-point tolerance and Codecov patch mode. Native supplements never replace missing or failed primary projects. The [storage contract](coverage-storage.md) governs native ownership, leases, history and recovery. Separate downstream consumer adoption and onboarding measurements are deferred; current acceptance focuses on AppSurface dogfooding.

The repository's current coverage path is selected by the shared [evidence policy](https://github.com/forge-trust/AppSurface/blob/main/.github/evidence.policy.json) and executed by the C# [repository evidence validation tool](../tools/ForgeTrust.AppSurface.Evidence.Validation/README.md). The workflow's `coverage` scope projects the root policy selection to solution coverage. Test-only changes select only that producer and use its direct Codecov-mode patch gate. Source-code changes select coverage and package checks; on CI pull requests that producer union also requires native fan-in. Local `local` and `local-plan` support `all`, `native`, `coverage`, and `packages` scopes; a scoped run closes only its lane, and `all` is the complete local policy selection.

## Current CI path

In [build.yml](https://github.com/forge-trust/AppSurface/blob/main/.github/workflows/build.yml), the coverage planning job collects event-bound changed paths and resolves the policy. Its `selection.json` exposes `requiresNativeCoverage`, true when root selection includes `solution-coverage` and at least one other producer. Only that selection starts the Linux, Windows, and macOS security-platform jobs, downloads their captures, and enables PR fan-in. The candidate, native captures and primary use the exact event head rather than the synthetic PR merge commit. Each capture records its actual source, SDK, platform, test scope, coverage policy, report hashes, and workflow run identity. The collected PR base supplies the identical patch baseline to all producers. Test-only coverage skips this native matrix and runs the existing direct patch gate against the solution report.

The build job runs the full solution coverage producer through the validation DLL, using the same source-, SDK-, run- and attempt-bound installed CLI candidate as the native producers. It verifies the complete solution inventory and timings and evaluates the independent primary aggregate gate. When native evidence is selected, the [dogfood adapter](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/README.md) invokes schema-v2 capture/import, composition, acceptance and a separate read-only verification command. Otherwise the producer evaluates the patch gate directly on the solution report. This path does not invoke Python. The unconditional `coverage-solution.sh` and optional `coverage-gate-fanin.sh` remain compatibility workflows; they are not the policy-selected `build.yml` entry point.

Coverage acceptance preserves the repository's full-solution aggregate minimums of 95% line and 85% branch, plus the Codecov-mode patch minimums of 95% line and 85% branch where measurable. Both gates retain 0.5 percentage-point tolerance. As documented by the [CLI patch gate](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-gate), a patch metric with no measurable changed lines or branches reports 100%; this existing direct-gate behavior is used for test-only PRs. Native fan-in retains its strict nonempty measurable-denominator checks and does not weaken them. Main-branch runs have no patch baseline and therefore evaluate the aggregate gate without a patch gate. PRs selecting native evidence use the collected event base and require exactly one Linux, Windows, and macOS capture from the same workflow run and attempt. Native-only measurable coverage points may not be discarded from the composition.

The artifact layout under `TestResults/coverage-evidence/` is:

- `coverage/`: full-solution collector output, timing and test diagnostics, and aggregate/patch gate reports.
- `coverage-fanin/`: the native adapter request/result documents, locally captured primary, imported native inputs, `composed/` reports and verification receipt, and `accepted/` acceptance generation, when native fan-in is selected.
- `evidence-manifest.json`, `evidence-summary.md`, and `artifacts/`: the evidence host's retained manifest and producer artifacts.

The workflow uploads these outputs as coverage diagnostics and gate reports. The full-solution aggregate gate remains independently required; the composed report's aggregate percentage is informational. Codecov receives the composed report on PRs selecting native coverage, otherwise the full-solution report. Main runs without a patch baseline also report the full-solution report.

## Native schema-v2 workflow

The neutral [Coverage package](../Coverage/ForgeTrust.AppSurface.Coverage/README.md) supplies asynchronous collection/capture, composition, acceptance and independent read-only verification. The [AppSurface CLI](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) exposes the same operations. The [EvidenceHost adapter](../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md#coverage-fan-in-producer) requires independently accepted current-run evidence and successful result delivery before it returns an assertion. Capture/compose success is never an acceptance result.

Use ordinary `coverage merge` to combine compatible reports when source/run-bound acceptance is unnecessary. Fan-in adds exact intended project/native inventories, clean commit/tree and SDK/configuration identity, explicit instrumentation/run policy, conservative class/method composition, a separate primary aggregate gate, and independent semantic verification. It does not sign artifacts or prove that arbitrary caller-supplied tests actually ran. `CollectedExecution` originates in supervised collection; `TrustedProducer` is an explicit trust boundary. Local import preserves either observation and never claims new execution.

The public contracts and defaults are in the [package reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md). Every request supplies a complete intended primary inventory and exact supplementary IDs/platforms/filters. Supplementary project inventories may be narrower than the primary only when explicitly declared. Paths use slash-relative identities, not a project-name suffix convention. The reusable engine never substitutes AppSurface's project count or CI variables for consumer declarations. AppSurface supplies its own complete policy in the [dogfood adapter](https://github.com/forge-trust/AppSurface/blob/main/tools/ForgeTrust.AppSurface.Coverage.Dogfood/Program.cs), including all solution projects and Linux/Windows/Darwin native evidence.

For copyable calls to all five facade operations, the shipped Evidence producer, a generated strict-v2 CLI request/result walkthrough, and the exact installed package proof command, run the [coverage dogfood examples](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md). The examples use runtime source/run identity and actual producer artifact paths. They do not embed reusable-looking hashes or claim that a platform's native matrix passed.

### C# operations and ordering

All facade methods return `ValueTask<CoverageFanInResult>` and accept the optional cancellation token plus caller-owned progress and diagnostic writers. The concrete calls and parameters are in [CoverageFanInApiExample.cs](https://github.com/forge-trust/AppSurface/blob/main/tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/CoverageFanInApiExample.cs); use the exact result contract to distinguish completed work from acceptance.

1. `CoverageFanIn.CollectAndCaptureAsync(CoverageCollectRequest, token, progress, diagnostics)` runs the declared inventory through the supervised collector and captures only success. Supply a collection directory and explicit 1–86,400 second deadline. Collection always writes indexed original collector evidence, including for a one-project inventory. Alternatively `CaptureAsync(CoverageCaptureRequest, ...)` validates a trusted normalized primary plus its successful timings, a one-project `RawCoveragePath` with optional bounded-XML `CoveragePath` compatibility input, an indexed `RawCoveragePaths` inventory of one or more projects with complete timings, or an imported portable capture plus its exact original source root. Native measurements are derived from original collector facts; `CoveragePath` never supplies them. Fresh output is the default; `ReplaceOwned` is explicit.
2. `ComposeAsync(CoverageComposeRequest, ...)` requires the primary and exact supplementary set. It retains all class and method occurrences, overloads and native-only points. Matching-denominator individually full observations may promote a branch; partial observations never add together to invent full coverage.
3. `AcceptAsync(CoverageAcceptRequest, ...)` checks the complete primary aggregate, the composed patch when explicitly requested, then independent facts and gate arithmetic. It commits an exact accepted generation only after required work completes. Numeric gate failures retain rejected gate reports without an acceptance receipt.
4. `VerifyAsync(CoverageVerifyRequest, ...)` checks existing retained captures/composition/acceptance against trusted caller expectations. It creates no coordination, repairs nothing, and makes no historical evidence fresh. `Outcome == Succeeded` and `Verified == true` establish consistency under the supplied expectations; neither property authenticates a producer or independently proves arbitrary test execution.

Requests snapshot caller collections before mutation; subsequent caller edits do not change a running policy. Callers own writers and cancellation sources, which are not disposed or retained. The .NET SDK, Git, consumer test SDK and supported Coverlet collector prerequisites must be installed. Native fan-in measurements come from retained collector facts, not a ReportGenerator-normalized hybrid. The private support package's [pinned ReportGenerator runtime](../Evidence/ForgeTrust.AppSurface.Evidence.Coverage/README.md#reportgenerator-runtime-payload) remains available to workflows that require it; native projection does not use its output as the measurement oracle.

Use a clean, complete checkout without Git index entries marked `assume-unchanged` or `skip-worktree`. Fan-in checks every pinned submodule, including those marked inactive, and rejects missing checkouts, mismatched commits, hidden index flags, or dirty files. Source and patch checks ignore replacement refs and use the original objects behind the pinned Git IDs. The index walk allows at most 32 checkouts including the root and shares the identity deadline. Each Git probe has a 1 MiB output limit per stream; an incomplete index listing is rejected.

Read-only verification checks the pinned source, SDK and clean state both before reading evidence and after validating the accepted generation, before returning `Verified`. A source change during verification rejects the operation without changing the evidence. Use a dedicated checkout without concurrent writers: these checks detect changed observations, but do not lock every compiler input or make the worktree immutable.

Commit every declared primary and supplementary test project in the pinned repository or a pinned submodule. A project file present only on disk, such as an ignored local project, is rejected even if Git reports a clean worktree.

For supervised collection, use a dedicated checkout and put evidence and local scratch outside it. Collection rejects ignored files before and after execution, except directories named exactly `bin/` or `obj/` beside a tracked .NET project with no ancestor project directory. An SDK project can compile ignored source through default globs, including files under a nested project's output directory. Use trusted restore outputs and committed build configuration. This check does not isolate MSBuild or authenticate its dependencies.

`CoverageGateMode.AggregateOnly` is an explicit baseline with `PatchNotRequested`. It creates no patch-pass artifact and cannot satisfy a patch-required obligation. `AggregateAndPatch` requires the declared Git revision (option-like bases beginning with `-` are rejected), the identical frozen diff for primary/composed analysis, nonempty measurable changed lines and line/branch denominators no smaller than the primary reference. The [Git patch reader](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-gate) disables external diff drivers and text converters so the patch describes committed source. Both the gate and the independent verifier reject a Git filename with a literal backslash rather than assigning its lines to a different file. This choice never silently follows from an absent diff. AppSurface's configured thresholds/tolerance, Codecov mode, complete primary and native requirements remain authoritative.

### Installed commands and request schema

The four parser-registered commands are `appsurface coverage fan-in capture`, `compose`, `accept`, and `verify`. The `capture` command has a `--collect` selector for the fifth facade operation, collection-and-capture. Each takes `--request <file>`; writing commands require `--result <new-file>` in an existing safe directory. Add `--json` for exactly one bounded terminal document on stdout; progress and diagnostics use stderr. Verify's result destination is optional and only records adapter delivery; it does not authorize modification of evidence. Every requested result file must be fresh.

Collection uses a strict-v2 request whose envelope has `operation: "collect"` and whose `request` is a complete `CoverageCollectRequest` (including policy, clean repository root, fresh capture and collection destinations, producer ID, and deadline). Observed collection rebuilds before testing. Omit `noBuild` or set it to `false`; a true value is rejected before execution. Set `noRestore` only if you have already restored the inputs. The exact parser invocation is:

```sh
"$APPSURFACE_CLI" coverage fan-in capture \
  --request "$COLLECT_REQUEST_JSON" \
  --result "$COLLECT_RESULT_JSON" \
  --json --collect
```

The same command without `--collect` requires `operation: "capture"` and a producer report or portable import. Do not change only the envelope or only the selector: they must agree. The installed headless fixture's [`--package-proof` walkthrough](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md#run-the-installed-headless-package-proof) demonstrates real supervised collection using the packed neutral packages and records its generated stage evidence.

The request, request-file and result-file paths must pass the CLI's regular, link-free filesystem checks. Request JSON is limited to 1 MiB and depth 64, rejects comments/trailing commas, and rejects duplicate property names at every depth. JSON property names and enum tokens are case-sensitive; decimal values are read losslessly. Missing optional members take the public record defaults, but the complete policy members and operation-required selectors must be present. See the exact requests generated by the [dogfood walkthrough](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md#generate-exact-cli-requests-and-results).

Requests use the exact envelope `{ "schemaVersion": 2, "operation": "capture", "request": { ... } }`, with camelCase request members and string enums. Collection uses `operation: "collect"` together with `capture --collect`. Unknown, duplicate, missing required, wrongly typed or contradictory fields fail before execution. API/package versions, CLI request schema, capture schema, local coordination and policy encoding are separate version domains; `coverage-policy-c14n-1` identifies canonical policy bytes, not an execution claim.

An `accept` request may set `expectedPatchSha256` to bind patch acceptance to the exact unified Git diff used during planning. It must be a 64-digit SHA-256 and is invalid for aggregate-only requests. Patch coverage requires measurable changed lines; when the patch contains no measurable branch conditions, the branch gate uses its existing 0/0 convention. Composition still cannot drop measurable branch points from the primary report.

Exit 0 means the requested operation succeeded; 1 means rejection, failed/incomplete work or delivery failure; 2 means invalid input; 130 means cancellation; 124 preserves the terminal watchdog/deadline result. Inspect both the requested operation/outcome and delivery status. A composed capture may succeed while no accepted coverage exists. A committed accepted generation may survive failed adapter delivery; reconcile that exact generation before retrying delivery. Never blindly rerun or reuse the previous invocation's success.

The CLI JSON result has its own outer `schemaVersion: 2`, `operation`, and `status`, along with nullable `operationOutcome`, known effects, safe operation result, delivery state, and bounded diagnostics. A succeeded command requires operation success and result delivery; a `deliveryFailed` status can coexist with `operationOutcome: "succeeded"` and `generationCommitted: true`. Its artifact projection omits host paths. For Evidence, the shipped [`EvidenceCoverageFanInProducer`](../Evidence/ForgeTrust.AppSurface.Evidence.Aspire/README.md#coverage-fan-in-producer) writes a bounded JSON acceptance result to its declared artifact slot before it may return the declared assertion; its registration/declaration example also requires observed primary collection and patch acceptance.

### Portable inputs, replay and replacement

Indexed native inventories support one or more projects. Supervised collection binds one original collector attachment to each successful project invocation, always writes the indexed form, and retains every original byte sequence, complete timings and the exact project-to-file index. To capture an existing trusted indexed inventory, supply `rawCoveragePaths` as an exact object mapping every declared project path to its original report path and `timingsPath` as the complete successful inventory; omit `coveragePath` and `rawCoveragePath`. The package [request and artifact reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) defines the index shape, file names and limits. The single-report compatibility form uses `rawCoveragePath` for exactly one declared project, permits optional `coveragePath` that must pass bounded XML admission, and requires `timingsPath` to be absent. The established single-project output filenames `collector.cobertura.xml`, `coverage.cobertura.xml`, and `manifest.json` remain unchanged. Import has no report or timing selectors. Capture schema v2 is unchanged.

Every load and import independently verifies native evidence against the original collector bytes, and composition, acceptance and read-only verification repeat that check. The canonical projection preserves class, method, line and occurrence facts and derives root totals from class-line points. Existing v2 single-report captures are accepted only when their stored facts and root totals already equal that canonical projection. Older folded, reconstructed, or inflated hybrid projections are rejected even if their hashes are valid; recapture from the original reports into a fresh destination. The historical v1 reader and its strict behavior remain unchanged. A one-report indexed inventory cannot satisfy a declaration containing multiple projects.

A downloaded v2 capture is transported data, not receiving-host ownership. Use `CaptureAsync`/`capture` with `importDirectory`, the exact `originalSourceRoot` and a fresh receiving destination. The receiver validates original bytes, source/run/attempt/policy and relative identities, creates new local custody, and preserves original producer observations. Copying lock files or inode metadata never grants authority. The same current trusted run's imported native evidence may contribute to acceptance only after exact caller expectations and independent checks pass. On compose, accept and verify, the CLI result's `primaryImported` distinguishes imported primary evidence from imported supplements. EvidenceHost's `requireObservedPrimary` rejects an imported primary even if its observation is `CollectedExecution`. Historical replay remains historical, even if a caller changes its label or local directory.

Primary imports must pass the same measurable-point validation as fresh captures; a valid payload hash and successful timings cannot admit malformed coverage numbers or escaping source paths. The original source root supports POSIX, Windows drive, and UNC paths independently of the receiving operating system. It maps recorded source paths rather than locating files on the receiver.

Outputs default to fresh-only. Explicit `ReplaceOwned` additionally requires an existing generation with compatible private registration, purpose, current physical identity, exclusive custody and exact retained inventory/hashes. A missing destination is rejected without creating its root or lock; use `Fresh` for the first publication. Acceptance and numeric rejection are two states of one gate-evaluation purpose: replacing accepted output with a failed evaluation commits the rejection reports without an acceptance receipt, and a corrected retry can replace that rejected generation. Capture and composition cannot replace gate-evaluation output or each other. Unknown, altered, linked or foreign contents survive refusal. A populated legacy tree is never marked to manufacture ownership. Stage validation precedes prior retirement. A completion marker is the commit boundary: cancellation before it yields no complete generation; cancellation after it reports actual committed state. Required cleanup occurs before commit, and incomplete effects remain explicit.

### Coordinated release rollback

If a consumer must roll back after installing a coordinated package release, pin and reinstall the previous supported versions of `ForgeTrust.AppSurface.Coverage`, its exact-version `ForgeTrust.AppSurface.Evidence.Coverage` private engine dependency, and `ForgeTrust.AppSurface.Cli` together. Confirm the matching family and version in the [package chooser](../packages/README.md) and follow the [package installation and version contract](../Coverage/ForgeTrust.AppSurface.Coverage/README.md). If the consumer uses the Evidence adapter, restore its integration to the matching prior release as well. Do not combine a facade with a different engine version.

Resume with fresh output roots and a schema and policy supported by that prior release. Preserve existing captures and reports for diagnosis; do not rewrite them, adopt populated directories, or feed envelopes the prior release does not support. Rerun collection or capture, composition, acceptance, and verification with the restored installed consumer, then pass the installed-package and native dogfood checks before promoting that release family again. The [dogfood examples](../tools/ForgeTrust.AppSurface.Coverage.Dogfood/examples/README.md) document candidate-package proof and fresh output behavior.

For an AppSurface CI rollout, revert the coherent migration commit and its matching configuration together, restoring the previous producer only while it remains compatible with the repository's current evidence and gate contracts. Keep the existing thresholds and required evidence policy; rollback does not authorize lowering gates. This procedure coordinates a release recovery and does not publish, unpublish, or otherwise change package releases.

V1 captures and the original [Aspire verifier API](https://github.com/forge-trust/AppSurface/blob/main/Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceCoverageFanIn.cs) retain their original strict read-only contract. V1 and v2 cannot mix. There is no in-place conversion that relabels old reports as new execution; recapture a new run and use fresh destinations when custody cannot be established.

### Diagnostics

`ASCOV301` identifies invalid explicit input; `ASCOV302` identifies failed evidence/custody checks; `ASCOV306` identifies cancellation/deadline or terminal watchdog; `ASCOV307` identifies rejected numeric gates; `ASCOV309` identifies post-operation delivery failure; `ASCOV310` identifies an unmet Evidence assurance requirement. CLI admission/delivery diagnostics use `ASCOVF001`–`ASCOVF006`, and runtime closure uses `ASCOV140`.

Read the stable code, operation/stage, field role, policy digest, operation/generation identity and recovery action. Expected rejection and cancellation do not include raw exception traces. Preserve failure artifacts, inspect the exact scope/identity/report that disagrees, correct the declared input or add honest tests, then retry once into a fresh safe destination. Unknown effects require reconciliation before retrying. Diagnostics must not copy arbitrary report data, secrets, raw child logs or dependency exception text into terminal output.

The current acceptance target is AppSurface dogfooding with its own solution and native matrix. Separate downstream consumer adoption and onboarding measurements are deferred by user direction; they are not established by local fixture tests or this guide.

## Historical v1 evidence

The original Python producer and shell policy checks are the schema-v1 behavioral baseline. Historical captures use their original strict source/SDK/configuration/filter/run rules and read-only [Aspire verification API](https://github.com/forge-trust/AppSurface/blob/main/Evidence/ForgeTrust.AppSurface.Evidence.Aspire/EvidenceCoverageFanIn.cs). They are neither generic v2 captures nor new execution. Preserve old downloaded evidence; do not add ownership markers, mix schemas, rewrite manifests or relabel old reports to satisfy a new run. Recapture through the native path and select fresh output when custody cannot be established.

The independent v2 regressions preserve class/method occurrence and overload records, native-only points, conservative individually full branch promotion, and patch denominator scope. The [native test families](https://github.com/forge-trust/AppSurface/blob/main/Cli/ForgeTrust.AppSurface.Cli.Tests/CoverageFanInIndependentVerifierTests.cs) use hand-authored expected facts and altered-output cases; a producer receipt is never its own oracle.

The primary aggregate gate retains the exact original normalized primary root counters, including compiler points that ReportGenerator may summarize without serialized class lines. Replacing those counters with class-derived totals would change the established aggregate measurement. Native projection follows a separate ownership rule: original collector class and method facts define its records, and collector root summaries cannot supply missing points. Composition retains every primary record and its denominator, then merges supplementary raw facts conservatively; the composed root totals derive from the complete resulting class-line points; patch metrics also inspect method points. The independent verifier checks the unchanged primary aggregate counters and separately re-derives native and composed facts from retained raw reports. These measurement rules do not change the configured aggregate or patch thresholds, tolerance, or patch mode. See the [Coverage API reference](../Coverage/ForgeTrust.AppSurface.Coverage/README.md#request-and-result-reference) for native input forms and the raw-summary edge case.

For AppSurface CI, the optional [gate wrapper](https://github.com/forge-trust/AppSurface/blob/main/scripts/coverage-gate-fanin.sh) preserves the existing primary `aggregate-gate/coverage-gate.json`/`.md` and root patch `coverage-gate.json`/`.md` plus patch-target report paths by invoking the installed gate command against separate composed inputs. Numeric rejection retains reports and returns failure. Baseline builds with no diff base publish only the primary aggregate reports. The immutable acceptance generation remains the authoritative native evidence; canonical CI reports are additional presentation artifacts.

## Local commands

Plan the selected evidence without running producers, then execute it on the current OS:

```sh
dotnet run --project tools/ForgeTrust.AppSurface.Evidence.Validation --configuration Release -- --operation local-plan
dotnet run --project tools/ForgeTrust.AppSurface.Evidence.Validation --configuration Release -- --operation local
```

Both commands compare local changes with `origin/main` by default. Add `--base <revision>` to select another base and `--scope all|native|coverage|packages` to select a lane. The `coverage` scope runs full-solution coverage against the local diff; local collection cannot substitute for any selected three-OS CI matrix. The local output defaults under ignored `TestResults/repository-evidence/`; see the tool guide for source-drift behavior, options, and evidence details.

## Evidence and troubleshooting

The installed [Coverage commands](../Cli/ForgeTrust.AppSurface.Cli/README.md#appsurface-coverage-fan-in) verify capture manifests and hashes, source and SDK identity, exact test inventory, workflow provenance, conservative composition and gate evidence. The repository validator supplies the selected policy and requires successful native acceptance plus independent verification before closing its coverage assertion. The validation tool's separate `capture-native` operation and the original `EvidenceCoverageFanIn` API retain their historical schema-v1 compatibility contract; current CI captures use the schema-v2 dogfood adapter.

When a coverage lane fails, download the `coverage-gate-reports` and `test-result-diagnostics` artifacts from the same workflow run. Inspect the full-solution timings and test logs under `coverage/`, the evidence summary and manifest, and, when selected, the fan-in verification receipt under `coverage-fanin/composed/`. Missing projects, required native captures, mismatched provenance or report hashes, incomplete measurable patch denominators in native fan-in, and failed applicable thresholds are hard failures. A direct patch metric with no measurable points follows the CLI's documented 100% behavior. Regenerate evidence from the current source and workflow run rather than relabeling old reports.

The compatibility shell wrappers remain documented in their source for callers that explicitly select them. Their artifact layout and historical Python test commands do not describe the current policy-selected workflow.
